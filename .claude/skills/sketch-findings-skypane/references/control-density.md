# Control Density

## Design Decisions

**Button geometry.** Base `button` shrinks from `min-height: 44px` SUPERSEDED to `height: 30px` (06.6.4 D-01), `padding: 0 12px` (was `0 var(--space-md)`/16px SUPERSEDED), `font-size: 13px` (was `--font-body-size`/16px SUPERSEDED), `border-radius: 6px` (was `--radius-control`/8px SUPERSEDED), plus new `font-weight: var(--weight-semibold)` and `letter-spacing: -0.01em`. This is a deliberate WCAG 2.5.5 (Level AAA, 44px) trade the developer accepted after being shown it three times against a live reference artifact; WCAG 2.5.8 (Level AA, 24px) is still met.

**Sub-960px button growth (06.6.4.1.1 D-18/UIR-26) — an extension of D-01, not a reopening of it.** Below `960px` (a `max-width: 959.98px` media query, the fractional-pixel boundary avoiding a one-device-pixel gap against the `>=960px` breakpoint used everywhere else in this file), the base `button` rule grows to `height: 36px; font-size: 14px;`. The override rule is deliberately a bare `button` selector at the same `(0,0,1)` specificity as the base rule — adding a `:not()` qualifier to try to scope it more tightly would RAISE specificity and start winning against every class-scoped control that declares its own geometry (`.theme-form .theme-option`, `.copy-btn`, the nav-footer theme segments), which must all keep their own sizes untouched. Because neither rule exceeds `(0,0,1)` specificity, **source position decides the cascade**: this override is placed last in the file, after every other `button` rule including the `>=960px` block, so it wins on position, not specificity — a harness check in `test_status_pages.py` pins this source-order relationship explicitly, not just the declared values. At `>=960px` buttons stay exactly as D-01 left them (30px/13px); nothing above 960px changed.

**Quiet-at-rest / reveal-on-hover, the wash-strength register.** Every distinct hover/active wash percentage in the file, presented as one register rather than isolated numbers: base quiet buttons are `color-mix(in srgb, var(--color-text) 4.5%, transparent)` at rest with a `9%`-mix border, revealing `7.5%` background / `14%` border on hover; `.copy-btn` (icon-only) uses `7%` on hover with no resting wash at all; nav links (`.sidebar-link`, `.mobile-nav__link`) and the theme-picker segments use `4.5%` on hover for inactive items; active-state pills (nav links, theme segments) use `12%` accent-tinted background. The base `button` rule's background/border declarations are each written twice — a `rgba()` literal fallback immediately before the `color-mix()` form — for browsers without `color-mix()` support (WR-02); this is not two competing values, the second declaration wins in every supporting browser.

**Primary-action treatment and cascade mechanics.** `button[type="submit"]` gets an accent fill with `box-shadow: inset 0 1px 0 rgba(255,255,255,.14), 0 1px 2px rgba(18,21,27,.14)` (hover deepens to `inset ... .16, 0 2px 5px ... .18`), theme-neutral black/white alphas by design — no dark-mode variant needed. The part most likely to be got wrong: theme-picker buttons are also `<button type="submit">`, but never receive this fill. What actually excludes them is `.theme-form .theme-option`'s **doubled specificity** (`0,2,0`, two classes) outranking `button[type="submit"]`'s `0,1,1` — not their absence from any accent-reservation list. Two other quiet submit buttons (`.logout-form button`, `.dirty-bar__cancel`) are excluded a different way: equal `0,1,1` specificity to `button[type="submit"]`, so **source order** (placed after it) decides the winner instead — the same reasoning documented at each of those rules. This is the case where source order, not specificity, decides the cascade, and both rules must stay after `button[type="submit"]` in the file for the override to hold.

**Press affordance.** `button:active { transform: translateY(1px); }` applies to every button, primary and quiet alike. It is placed *before* `button:disabled` in source order specifically so a disabled button's own (later, winning) treatment is never overridden by an active-press effect a disabled control cannot actually receive.

**Icon-only button pattern.** `.copy-btn` (and any future icon-only action button) is a 22×22px visual box with `border: none`, `background: transparent`, `border-radius: 6px`, `display: inline-flex` centring — no accessibility trade-off, unlike the base button's 30px reduction. A `::before` pseudo-element (`content: ""; position: absolute; inset: -11px;`) synthesizes a real 44×44 hit area centred on the glyph (22 + 11×2 = 44). This is the pattern to reuse for any future icon-only button rather than reintroducing a minimum-size floor on the visual box itself. `.copy-btn .icon` is scoped down to 14px (the global `.icon` default is 20px) — at the original 28px box this nearly filled the button and read as oversized; the 22px box plus 14px glyph reads as a quiet inline affordance instead.

**Segmented theme control.** `.theme-form` is a bordered container (`border: 1px solid var(--color-border); border-radius: var(--radius-control); padding: 2px; gap: 2px;`) wrapping three borderless `.theme-option` buttons (`height: 28px; padding: 0 12px; font-size: 13px; border-radius: 6px;`). The doubled-specificity selector (`.theme-form .theme-option`, not the bare class) is load-bearing, not stylistic — see Primary-action treatment above. `.theme-option--active` reuses the exact same tinted-pill idiom `.sidebar-link--active` uses (12% accent background, accent text, semibold) — the same visual language, not a reinvention.

**Shared active-pill idiom and `:not()`-scoping.** Both nav renderings (`.sidebar-link--active`, `.mobile-nav__link--active`) and the theme segments use one signal: a `color-mix(in srgb, var(--color-accent) 12%, transparent)` background plus accent text and semibold weight — a single cue, not the two-cue (left-border plus tint) model an earlier revision used SUPERSEDED (06.6.4 D-05 dropped the redundant left-border on nav links). The corresponding hover rules are `:not()`-scoped (`.sidebar-link:not(.sidebar-link--active):hover`, etc.) — an unscoped hover selector at equal specificity, later in source, would outrank the active modifier and erase the active tint the instant the pointer crossed it. This scoping pattern is the correct way to add a hover state next to an existing active-pill rule; do not add an unscoped hover instead.

**Filter bar field.** `.filter-bar__field input` is scoped to 32px (`height: 32px; min-height: 0;` — the `min-height: 0` is load-bearing, since the global `input`/`select` rule's 44px minimum otherwise outranks any plain `height` declaration regardless of specificity), with a transparent background instead of the global filled-secondary style. This scoping is intentional and narrow: the global native `input`/`select` rule keeps its 44px floor for every other field in the app — only this one wrapper's descendant input is exempted.

**Hidden form controls, the fourth floor-register category (quick task 260902-l9w, joined by 06.6.4.1.1-05).** `input.visually-hidden, select.visually-hidden` clears both 44px minimums (plus native control theming) off any form control that also carries the `.visually-hidden` utility class — originally the three Runway-picker radios (`config_page.py`'s `runway_fieldset()`), now joined by the 16 theme-picker chip radios (`config_page.py`'s `theme_fieldset()`, 06.6.4.1.1-05, sketch 004 variant B). This is a distinct category from kept / traded / relocated, added alongside them below: **exempt-by-delegation** — an off-screen control with no hit area of its own, whose wrapping label (`.runway-card` or `.theme-chip`, both of which exceed 44px in both axes on every viewport) is the real activation target. It is explicitly NOT a fifth entry in the traded-away list: no accessibility floor was given up, because the control was never the hit target to begin with. See `references/accessibility-contrast.md`'s `.visually-hidden` entry for the mechanism (why the utility's own 1px sizing is otherwise inert on an `<input>`/`<select>`).

**Card hairline-at-rest contract.** 06.6.4 (D-03) reverses 06.6.1's shadow-at-rest treatment: every card in the set (`.stat-tile`, `.page-section`, `.battery-trend-section`, `.runway-card`, `.history-card`, `.login-card`, `.airline-card`, `.theme-status`, and — 06.6.4.1.1-05 — `.theme-chip`) now declares `border: 1px solid var(--color-border); box-shadow: none;` at rest, with `border-color: transparent; box-shadow: var(--shadow-card-hover);` on `:hover`/`:focus-within`. The two states are mutually exclusive, not additive — never restore both a resting shadow and the hairline at once.

**Hover amendment: the transparency covers three edges, not four, and the reveal is scoped off the Frame strip (Phase 22, T9).** The flat `border-color: transparent` across all four edges is SUPERSEDED — the shorthand also cleared `border-block-start`, which on any `.stat-tile` carrying a status or accent modifier IS the tile's own top rail, so pointing at a warning tile erased the warning. The hover state now declares `border-inline-color: transparent; border-block-end-color: transparent;` and leaves the block-start edge alone. **"The two states are mutually exclusive, not additive" is unchanged and still binding** — this amends only *how many edges* the transparency applies to (three), never the mutual exclusivity itself, and it is not a partial return to the shadow-plus-hairline model 06.6.4 D-03 reversed. Separately, the whole reveal is now `:not(.frame-strip)`-scoped: the Frame strip borrows `.stat-tile.stat-tile--accent`'s surface wholesale but is a **control area**, not a browsable card, and a card that lifts when a button inside it is hovered reads as a misfire rather than as an affordance. Any future component that borrows a card class for a control surface belongs in that same `:not()` list.

**Selected-card treatment: border + check glyph + background wash (06.6.4.1.1-06, developer checkpoint follow-up).** `.runway-card--selected` and `.theme-chip--selected` both carry an always-visible 2px accent border, unaffected by the hairline-at-rest contract above — it already overrides the general border with a real signal, and each component's hover rule is `:not(...--selected)`-scoped so hovering a selected card can never clear that border. This USED to be the whole selected-state signal (border plus a small stroke-only check glyph), and the developer's real-device checkpoint review reported it was too subtle to notice at a glance, site-wide, especially against `.theme-chip`'s photo-heavy preview band at 16-chip density. The fix adds a `color-mix(in srgb, var(--color-accent) 12%, transparent)` background wash on both selected states — the SAME idiom `.theme-form .theme-option--active` and the nav-pill active-link rules below already use, so this is the third component to reuse the app's one "current selection" language rather than a fourth invented one. On `.runway-card--selected` the wash covers the whole card (no separate body wrapper exists to scope it more narrowly, and the card's only other content — a number and an optional airport-diagram image — is not obscured by 12% opacity). On `.theme-chip--selected` the wash is scoped to `.theme-chip__body` specifically, NOT the whole chip, because unlike `.runway-card` this component has a real rendered preview band (`.theme-chip__preview`) that must stay visually untinted so the theme's own colours read correctly. Border-only selection SUPERSEDED as this app's general selected-card idiom — do not add a third selectable-card component with a border-only treatment; reuse the wash.

**SUPERSEDED (quick task 260904-bbi): keying the strong treatment to `--selected` alone was itself a defect.** The paragraph above describes what 06.6.4.1.1-06 shipped, and it is now SUPERSEDED as the *mechanism* (not the visual language, which is unchanged) — `--selected` is a server-computed modifier painted once from the SAVED config, so it never updated when the user clicked a different card client-side. The border/wash/check-glyph treatment kept following the *saved* value, not the user's *live* choice: clicking "Blue" while "White" was saved left White painted as selected and Blue painted as unselected, with only the dirty bar changing. 06.6.4.1.1-06's own wash addition made this WORSE, not better — it was the right idiom (reusing the app's one active-state wash) applied to the wrong signal, so the stale highlight became more visually insistent, not less.

**Current contract: the strong treatment is keyed to live `:has(input:checked)` state; `--selected` is now a quiet "this is what is saved" marker.** Both `.theme-chip` and `.runway-card` gain a parallel, `:has()`-keyed rule set inside one `@supports selector(:has(*)) { ... }` block (placed immediately after the `.theme-chip` group in `style.css`, for readability only — every rule inside wins on specificity alone, not source order):

- `.theme-chip:has(input:checked)` / `.runway-card:has(input:checked)` carry the SAME 2px accent border + 12%-accent wash + check-glyph-shown treatment the old `--selected` rules carried, now keyed to the live native radio's `:checked` state rather than a server-rendered class. Since the saved radio is server-rendered with the `checked` HTML attribute, this is correct on first paint too, not only after a click.
- `.theme-chip--selected` and `.runway-card--selected` are UNCHANGED, byte-for-byte, everywhere outside the `@supports` block — they remain the no-`:has()` **fallback**: a browser without `:has()` support never evaluates the feature query, skips the whole block, and is left with exactly the 06.6.4.1.1-06 behaviour above. Nothing regresses to unstyled.
- When the saved value is no longer the live-checked one, `--selected` instead paints a QUIET, accent-free marker: a `2px dashed color-mix(in srgb, var(--color-text) 70%, transparent)` ring (the file's own established muted-text strength, reused rather than inventing an eighth wash percentage), its own wash cleared to transparent, its own check glyph hidden, and an English `"Current"` `::after` tag. At rest (saved value == live-checked value) the `:has()`-keyed rule wins on specificity and no tag ever shows.

**Specificity arithmetic (the part most likely to be got wrong by a future reader).** `:has(X)` and `:not(X)` each take the specificity of their most specific argument. `.theme-chip--selected` is `(0,1,0)`. `.theme-chip:has(input:checked)` is `(0,1,0)+(0,1,1) = (0,2,1)`, which beats the fallback. `.theme-chip--selected:not(:has(input:checked))` is ALSO `(0,2,1)` — equal specificity to the rule above is not a conflict, because the two selectors are structurally incapable of matching the same element (one requires a checked descendant, the other forbids one). The existing hover guard `.theme-chip:not(.theme-chip--selected):hover` is `(0,3,0)`, which OUTRANKS `(0,2,1)` and matches the newly-clicked chip (which lacks `--selected`) — left alone, it would clear the newly-checked chip's live-state border on hover. **The fix is a positive restore rule**, `.theme-chip:has(input:checked):hover, .theme-chip:has(input:checked):focus-within { border-color: var(--color-accent); box-shadow: none; }`, at `(0,2,1)+(0,1,0) = (0,3,1)`, which wins. Do **not** instead rewrite the base guard's `:not(.theme-chip--selected)` to `:not(:has(...))` — an unsupported `:has()` invalidates the WHOLE selector list it appears in, silently dropping the hover reveal entirely in non-supporting browsers and breaking the fallback story above. Identical reasoning and rule shape apply to `.runway-card`.

**SUPERSEDED (Phase 22, T6): the 2px accent BORDER is gone; the border width is now constant at 1px and the accent signal is an inset ring.** Everything above describing the selected state as "a 2px accent border" is superseded as the *mechanism* — the visual language (a 2px accent edge, the 12% wash, the check glyph) is unchanged and is not reopened. The defect: a border is part of the box, so a selected card was 2px larger than its unselected siblings. Selecting one shifted its neighbours, made a chip grid's rows uneven, and — on the vertical `.frame-colours__list` — nudged every row below it. **Current contract:** `border-color: var(--color-accent)` at the same constant 1px every unselected sibling carries, plus `box-shadow: inset 0 0 0 2px var(--color-accent)`, which paints inside the box and therefore costs the layout nothing.

Four consequences, each of which a future editor will otherwise undo:

- **It covers THREE selectable surfaces, not the two the audit's row names** — `.theme-chip`, `.runway-card` **and** `input:checked + .frame-colours__row` (the row-as-label list, whose column layout made the 2px growth a vertical shove rather than a grid unevenness).
- **Both dashed saved-state markers converted too**, for the same reason and in the same commit: `.theme-chip--selected:not(:has(input:checked))` and its `.runway-card` twin are now `1px dashed` with an explicit `box-shadow: none`. A card can be saved-but-not-live at the very moment its neighbour is live-selected, so a dashed 2px ring against 1px siblings is the identical layout shift wearing a different dash pattern. The `box-shadow: none` is load-bearing, not tidy-up: this rule must CLEAR the accent ring the `--selected` fallback paints, and a `border` shorthand cannot reach a `box-shadow`.
- **Both `:has(input:checked):hover` positive-restore rules had to move with it.** They used to declare `box-shadow: none`, whose only job was to suppress the hover elevation the `(0,3,0)` guard would otherwise paint. Once selection *is* a box-shadow, `none` stops being a suppression and becomes an **erasure** — hovering a selected card would wipe its ring. The restore rules now restate the inset ring instead, which still replaces the elevation outright (`box-shadow` is one property) while keeping the selection signal.
- **`.theme-chip` additionally needs a `::before` overlay carrying `box-shadow: inherit`.** An inset shadow paints on the element's own background/border layer, *beneath* its children — and `.theme-chip__preview` is a full-bleed `width: 100%` image occupying the chip's top band, so the ring would be hidden along the whole preview and visible only around the body, reading as a rendering fault. The overlay is **one unconditional rule**, not a duplicate of every selected-state rule: `box-shadow: inherit` redraws whatever the chip currently computes, above the image instead of below it, so every state tracks automatically. `pointer-events: none` keeps it out of the hit path, and the chip's own `overflow: hidden` clips the outer hover shadow so only the inset ring survives. `.runway-card` needs no equivalent — its image sits inside `var(--space-md)` of padding and never reaches the ring. **This is the general rule for any future selectable card with an edge-to-edge child.**

**Marker-slot asymmetry: chip bottom-right, runway top-right — one reason, not two.** `.runway-card`'s quiet-marker tag sits top-right (the check glyph's own vacated slot) because the card's only other content is a plain-text number and an optional airport-diagram image below it — top-right is free. `.theme-chip`'s tag sits bottom-right instead, specifically because top-right on THIS component sits over `.theme-chip__preview`, the rendered panel image — the identical constraint that already scopes this chip's selected-wash to `.theme-chip__body` rather than the whole chip (see the paragraph above). Both slots reuse the same label voice: 12px, `var(--weight-semibold)`, uppercase, `0.06em` letter-spacing, `color-mix(in srgb, var(--color-text) 70%, transparent)` — no new type role, no new colour.

**Pseudo-element, not a `<span>` — four-point justification.** The `"Current"` tag is a CSS `::after` (`content: "Current"`), not a real DOM element, so `config_page.py` keeps a zero diff. (1) The authoritative selection state for assistive technology is the native radio's own `checked` property inside a real radio group, already announced natively — the tag adds no information AT does not already have. (2) The pending-vs-saved distinction is separately carried in real, announced DOM text by the dirty bar ("Theme changed · Save settings · Cancel"). (3) A real `<span>` would inject a redundant announcement into exactly 1 of 16 chips for zero accessibility gain, and would force retargeting `test_config_page.py`'s exact-count markup assertions (H6/H7 in that plan's own hazard table). (4) Modern engines do expose `content` text in the accessibility tree, so this is not invisible to AT either — it simply is not relied upon. Do not "fix" this into a `<span>` — that breaks the harness's exact-count assertions for no accessibility benefit.

**The compact theme chip (Phase 20, D-14d/D-15b).** `.theme-chip--compact` is a size-only modifier on the existing `.theme-chip` base — narrower (104px), a shorter 36px preview band, tighter body padding, a 12px chip name, smaller swatch dots and a smaller check glyph/icon. It declares NO selected-state rule of any kind: the border, the background wash, the check glyph, the live `:has(input:checked)` layer and its no-`:has()` fallback all continue to apply automatically, since they are declared once against the base `.theme-chip`/`.theme-chip--selected` selectors this file already carries — a compact chip is selected exactly the same way a full-size one is, just smaller. Used for the Calendar card's theme choice and Flight colours' add-form theme choice, both `role="radiogroup"` chip grids that need to sit compactly beside other controls rather than occupy a full card of their own. **That usage sentence is no longer exhaustive (Phase 22, X6).** `.theme-chip--compact` is now the **only chip density on the whole Display page** — the Frame colours card's own full-size grid converted too, because 18 always-expanded 160×108 chips were the single largest contributor to that page's height. The modifier itself is **unchanged**: still size-only, still declaring no selected-state rule of any kind, so the border, the inset ring, the wash, the check glyph, the live `:has(input:checked)` layer and its no-`:has()` fallback all continue to apply automatically from the base selectors. Two things this row does NOT authorise: the audit's own page-height pixel target is **not** met by density alone and cannot be (folding the grid behind the big preview is D5, Phase 23 — recorded so a future reader does not read the shortfall as a defect in this change); and X6's prescribed swatch **legend copy was wrong and was not shipped** — the spec said `Background · Ink` / `Fond · Encre`, but the two swatches are the departing and arriving inks, so the shipped copy is `Departures · Arrivals` / `Départs · Arrivées`. Recorded here so the skill does not preserve a copy string the code deliberately contradicts. No touch-target register entry changes: the chip's own hidden radio is still exempt-by-delegation (`input.visually-hidden`, its wrapping `.theme-chip` label still exceeds 44px in both axes at every size this modifier ships).

**The native-radio segmented control for "Match by" (Phase 20, D-15b, Structural Note 5).** Flight colours' three-way "Flight / Aircraft / Airline" chooser reuses `.theme-form`/`.theme-form .theme-option`'s own bordered-container-plus-borderless-segment geometry verbatim, but built on real native `<input type="radio">` elements (visually hidden via the pre-existing `.visually-hidden` utility) with an adjacent `<label>` styled at the segment's own 28px/13px geometry — `:checked + label` gets the identical 12%-accent active-pill treatment `.theme-option--active` uses, `:not(:checked) + label:hover` gets the identical 4.5% hover wash, and `:focus-visible + label` carries the keyboard-focus ring the hidden input's own outline could never show. This was chosen over three JS-driven `<button>`s specifically because native radios have zero degraded state — no `rule-form.js` exists this phase, and the control works identically with or without script. No touch-target register entry changes either: the hidden radio is exempt-by-delegation exactly like the theme chip's own radio above, and the visible `<label>`'s 28px height is the theme-picker segment's own pre-existing "traded" register entry (see the Touch-target floor register paragraph in `SKILL.md`), not a new trade.

**The small grey secondary button (Phase 21, R-09, `.calendar-disconnect-btn`) — the first named secondary-button treatment in a codebase with no `.btn` family.** Every button in this file up to Phase 21 was styled by an element/attribute selector (`button`, `button[type="submit"]`) or a control-specific class that also changes the control's *function* (`.theme-form .theme-option`, `.copy-btn`) — there had never been a plain "make this one quiet button smaller and greyer than its neighbours" class. The Calendar card's small "Disconnect" button needed exactly that: small enough to sit inline beside the "Replace the feed URL" `<details>` link without dominating the line, and visually subordinate to it (never the accent-filled `button[type="submit"]` treatment, matching this app's unbroken no-red-destructive-button precedent). `.calendar-disconnect-btn` is one additive rule block on top of the base `button` rule's already-quiet wash: `min-height: 30px; padding: 4px var(--space-sm); font-size: 12px;` with its own `6%`-text wash at rest and `12%` on hover/focus-visible, `20%`-text hairline border — all values pulled from this file's own existing wash-strength register (6%/12%/20% are not new percentages; see the register above), not invented for this one button. This is the pattern to reuse the next time this app needs a small, deliberately de-emphasized secondary action next to a more prominent control — a new additive class on the bare `<button>` idiom, not a `.btn`/`.btn--secondary` family (none exists, and this one instance does not start one).

**That prediction is confirmed twice over (Phase 22, X7 and X5) — TWO new call sites, not one.** The component gained (1) Airlines' per-card **"Replace picture"** control (22-11, the X7 row's own example) and (2) Flights' **picture control** in the expanded detail row (22-09) — three call sites in total with Config's original Disconnect. It is **still not a `.btn` family**: `grep -c "^button\.calendar-disconnect-btn {"` returns 1 and `.btn--` returns 0. Three things to record with it:

- **The base selector is now element-qualified: `button.calendar-disconnect-btn`, and the qualification is load-bearing (T2).** The bare class was `(0,1,0)` against `button[type="submit"]`'s `(0,1,1)`, so on Config — the only `type="submit"` call site of the three — the primary accent fill won outright and the app's one **destructive** control rendered as the page's primary CTA while every declaration in the block above was dead. The fix is the equal-specificity-plus-source-order mechanism this file already documents for `.logout-form button` and `.dirty-bar__cancel`: `(0,1,1)` against `(0,1,1)`, thousands of lines later, so source order decides. A future reader "simplifying" it back to the bare class silently restores the defect. Deliberately **not** a `:where()` wrapper around the primary rule: dropping that rule to `(0,0,0)` would surrender the accent fill to every competing zero-specificity rule in the file at once. `box-shadow: none` is new and equally load-bearing — a submit button otherwise keeps the primary rule's inset highlight even once the fill is repainted, which is what made the control read as raised.
- **The reuse discipline that kept the base rule singular.** The Airlines call site needed different *placement*, so it got `.airline-card .calendar-disconnect-btn { display: block; width: 100%; margin-top: var(--space-sm); }` — placement only, at `(0,2,0)`, declaring **no** size, colour, border, radius or shadow. The single base rule remains the one definition of this component's geometry. Copy that discipline, not a fork.
- **The defect was invisible on two of the three call sites**, because Airlines' and Flights' controls are `type="button"`. That is the argument for element-qualifying the base rule rather than patching the one site where the collision showed.

**`.frame-colours__row` — a 44px row-as-label, met directly, not traded (Phase 21, D-08).** The Frame colours card's four-row `colour_usage` assignment list uses this file's one already-established "hidden native input + whole-element label" idiom (`input.visually-hidden` inside a `<label>` that is the entire visible row) — the same mechanism `.runway-card`/`.theme-chip` already use, joining them as a third/fourth consumer, not inventing a fourth mechanism. Unlike those two, though, `.frame-colours__row` does not appear in the touch-target floor register's "exempt-by-delegation" category: its own `min-height: 44px` clears the WCAG 2.5.5 AAA floor directly, on the row itself, because the row already needs to be at least that tall to hold its swatch/label/meta-text row content comfortably — there was no reduction to trade away here, so this entry does not join the traded-away list either. It is simply a control that happens to meet the floor as a side effect of its own content, the same way native `input`/`select` do.

**The Flights table's 30px "More"/"Plus" row-toggle button — an existing trade, not a new one (Phase 21, D-15). SUPERSEDED (Phase 22, X5, 22-09-PLAN.md Task 1) — and this is a RECORDED REJECTION being REVERSED, so read the reasoning before re-reversing it.** The Phase 21 entry read, in full: *"`.row-toggle` is a plain `<button>` at the base geometry this file already documents as traded away (30px at `>=960px`, 36px below it) — it introduces no new entry to the touch-target floor register, since it is simply the base `button` rule's own already-accepted WCAG 2.5.5 trade-off, applied to a new control. The 44×44 real-hit-area pattern (`.copy-btn`'s `::before` synthesis) was considered and rejected for this control: unlike `.copy-btn`, the row-toggle carries visible text ("More"/"Plus"), so a 22px icon-only visual box was never the right shape to begin with — the base button geometry is the correct register entry, not a variant of the icon-only pattern."* That entry is kept verbatim above rather than rewritten, because the whole value of a recorded rejection is that a later reader can see what was rejected and on what ground.

**Why the reversal is defensible: X5 dissolved the rejection's own stated ground.** The rejection rested on exactly one fact — that this control carries visible text. The audit found fifty of those text buttons running down the Flights table with nothing else to look at, and X5 removed the label outright (fifty "More"/"Plus" buttons leaving the scan path is the entire point of that fix). With the visible text gone, the control IS icon-only, and the sentence "unlike `.copy-btn`, the row-toggle carries visible text" is simply no longer true of the shipped code. The reversal follows from the premise changing, not from a change of taste — which is the only kind of reversal this file accepts against a recorded rejection.

**Current contract.** `.row-toggle` **moves from the touch-target register's TRADED-AWAY category to its RELOCATED category**, joining `.copy-btn` and `.settings-checkbox`: a 22×22px visual box with a `::before` (`content: ""; position: absolute; inset: -11px;`) synthesizing a real 44×44 hit area (22 + 11×2 = 44). **Both register entries change** — one control leaves the traded list and enters the relocated list, and the traded list is correspondingly one shorter for this control. Every value is `.copy-btn`'s own, reused verbatim rather than re-chosen: the 22×22 box, the 6px radius, the negative-11px inset, the 7% hover wash, the 14px glyph. **The control is BIGGER than the 30px text button it replaces, not smaller** — this is a hit-area gain, not another trade.

Three further facts, each of which is easy to get wrong later:

- **`.row-toggle` had no CSS rule at all before this phase.** It shipped in Phase 21 as markup only (`history_page.py`), riding the base `button` rule's geometry. So this is a **new rule block created**, not an existing one edited — there was nothing to diff against, which is precisely why the Phase 21 register entry above described a geometry no selector in the stylesheet actually declared.
- **The accessible name must advertise the picture reachable inside.** The name swaps between "Show flight details and picture" / "Hide flight details and picture" (and their French pair) rather than a bare "Show details" — an icon-only control whose name understates its own contents is the *same defect class* the icon-only conversion was meant to fix, just moved from the visual layer to the accessibility layer. X5's own audit row named the 16px icon-only eye as the only access to the panel picture; a name that does not mention the picture recreates that.
- **The glyph rotation takes no transition of its own.** A rotating-chevron transition is D3 / Phase 23's motion budget; the global `prefers-reduced-motion` block already covers a plain `transform` for free, and a per-rule block here would be dead code, not a safety net.

**A 20px control now wears the label voice, and the register needs to say so (Phase 22, X7).** Airlines' manual-resolution filter control (`.manual-summary`) moved inside the filter bar and now wears `.airline-card__chip` verbatim — a **20px-high** interactive `<button>`, below the 30/36px button register and well below 44px. It is recorded here as a **named, justified exception rather than a silent one**: (1) it *replaces* a 12px bare underlined link with no declared box at all, so it is strictly a hit-area gain and cannot be a regression against anything this register previously protected; (2) stated honestly rather than waved past: **20px is below the WCAG 2.5.8 Level AA 24px floor as well as the 44px AAA one**, measured as a bounding box — 2.5.8's spacing exception may well cover it, since the control sits alone on its line inside the filter bar, but that has **not** been measured and must not be assumed. The chip class is a **label voice**, designed for a non-interactive token, and this is the app's first interactive consumer of it. The plan that shipped it followed the UI spec's prescribed treatment verbatim and flagged the gap rather than deviating silently. **Disposition: re-examine the height before adding a second interactive consumer of `.airline-card__chip`** — the cheapest fix is a `::before` hit-area relocation exactly like `.copy-btn`'s and `.row-toggle`'s (the pattern this file already owns), which would move it into the relocated category with no visual change at all. Do not read this entry as authorising a 20px control anywhere else.

**The composition rule (Phase 22, C4) — stated narrowly on purpose, so it does not reopen protected geometry.** The audit's C4 row is about controls that sit on one row at four different heights and two different radii (44px r8 inputs, 30px r6 buttons, 28px segments, a 30px grey Disconnect) and read as an accident. The rule this file adopts is deliberately **not** "everything on a row matches":

> **Controls that read as ONE object — a field and its adjacent action — share height and radius. Controls that read as SEPARATE objects on a shared row are centre-aligned instead, each keeping its own registered geometry.**

Two worked examples, both now in code:

- **One object: the login card's field plus Sign in (X3, 22-13).** A password field with its own submit directly beneath it reads as a single entry control, so both are 44px tall and both take `var(--radius-control)` (8px). Measured: 278×44 / 278×44 at 390px and 296×44 / 296×44 at 1280px, a 16px gap, shared radius — against the audit's own 225×44 r8 field beside a 68×30 r6 button sitting 7px lower.
- **Separate objects: Flight colours' add form (X6, 22-10) and the lightbox's action row (22-11).** The add form's segmented "Match by" control, value input, compact chip grid and Add button are four distinct things that happen to share a line, so the row takes `align-items: center` and the 28px segment and the 44px native input each keep their registered heights. Likewise the lightbox's Close and Save deliberately declare **no** `height`, `min-height` or `border-radius` of their own; a future plan "tidying" them to a shared height would be **reversing** C4, not completing it, and a harness check asserts the absence of those three declarations for exactly that reason.

This resolves C4 without touching either of the two geometries this file protects explicitly — the 28px theme-picker segment and the 44px native-input floor. Neither is reopened, and neither may be "harmonised" under this rule.

**The tab bar joins the MET-DIRECTLY category (Phase 22, X9/D-10) — explicitly NOT a fifth entry in the traded-away list.** `.tab-bar__link`'s cells measure **78 × 56px at 390px** (`flex: 1 1 0`, not `1 1 auto`, so the widest label cannot buy itself a wider tab; 56px is the row height with `env(safe-area-inset-bottom)` added as padding underneath, so the row never shrinks on a device with a home indicator). That clears the WCAG 2.5.5 AAA 44px floor **directly, in both axes**, which puts it alongside `.frame-colours__row` in the met-directly category: **nothing was traded for it**, so it is not a fifth traded entry and must not be filed as one. The active/hover tint is painted on an inner `.tab-bar__pill` wrapper rather than on the cell, so the pill reads as inset while the cell keeps its full 78×56px tap area — reuse that split rather than shrinking a cell to fit a pill. `.mobile-nav__link` (44px/16px) is now **shared** between the retired dropdown menu and the tab bar's "More" sheet: its floor is load-bearing for the sheet, and it must not be compacted.

**`.login-card button[type="submit"]` is a named 44px exception joining the KEPT category (Phase 22, X3, 22-13).** It does not belong in the traded-away list, and the distinction matters: the base `button` rule's 30/36px geometry is a *trade* this file records the developer accepting; this selector **restores** the WCAG 2.5.5 floor on one surface rather than giving it up. Three-point justification, recorded because a future density pass will otherwise compact it by reflex:

1. **Floor gain, not floor loss.** 44px here is a restoration; nothing is surrendered.
2. **C4 composition.** Matching the field's height and radius is what makes the pair read as one object, which is the composition rule above applied, not an exception to it.
3. **No density argument to trade against.** This is the app's only pre-auth surface — one card, two controls, no list to compact and no viewport pressure. This is the identical reasoning quick task 260902-qkm used to restore `.mobile-nav__link`'s own 44px floor after 06.6.4 D-05 reached it by mistake, and it should be read as the second instance of one precedent, not a new exception type.

**Two Phase 23 additions to the MET-DIRECTLY category, and neither is a trade (D2/D7, CFG-36/CFG-37).** The register's four categories are unchanged — kept, traded-away, relocated, exempt-by-delegation — plus met-directly, where `.frame-colours__row` and `.tab-bar__link` already sit. Both of the following join them, and **neither may be filed as a fifth or sixth traded entry**: nothing was surrendered for either, and in both cases the control is BIGGER than what it replaced.

1. **`.switch` — the app's first `role="switch"` control, three consumers, one builder (`layout.quick_switch_html()`: Screen, Quiet hours, Diagnostic LED).** The button carries `min-width: 44px; min-height: 44px` with `padding: var(--space-xs)` around a `.switch__track` of **52 × 32px** holding a **24px** `.switch__thumb` (at `top: 3px; left: 3px`, travelling `translateX(20px)` when checked). **The floor lives on the button, not on the track, and that placement is load-bearing** — the button is what is focusable and pressable; a 52 × 32 track is below 44px in one axis, and a register entry pointing at the track would be recording the wrong box. Measured in a real Chromium at the **360px** contract floor, in both languages, with scripts blocked: every one of the three clears 44px in **both** axes. What it replaced: two `type="submit"` text buttons in the Frame strip (30/36px, the base button trade) and one 16px native checkbox inside a 44px `<label>` (the relocated `.settings-checkbox` pattern) — so this is a hit-area gain on all three surfaces. **Three declarations that are part of the register entry rather than styling:** `height: auto` (the global `button` rule's fixed 30/36px height would otherwise clamp the box back below the floor — the same shape as `.filter-bar__field input`'s load-bearing `min-height: 0`, in the opposite direction); `background: none; border: 0` on the base rule; and an explicit `.switch:hover, .switch:active { background: none; border: 0; transform: none; box-shadow: none; }`, because the global button wash and press-scale are written for a *labelled* button and on a switch they paint a box around a control whose whole visual is the track inside it. The track's own colour change is the feedback. **`.settings-switch-row`** (`display: flex; align-items: center; justify-content: space-between; gap: var(--space-md)`) is the one rule that gives a settings card the state-word-plus-control relationship the Frame strip's cells get from their own three-row grid; `space-between` rather than a fixed gap so that at 360px the state word stays left and the switch stays at the edge its thumb travels toward.

2. **`.history-card__summary` — a whole card face as the activation target.** The Flights phone card's `<details>` now opens from the card's own primary line, secondary line and airline line rather than from a separate control. Measured at 360px, the summary's box is the card's: **312 × ~120px**, which clears 44px many times over in both axes. Two declarations are load-bearing rather than cosmetic: `min-height: 0` (the global 44px floor would otherwise fight a box that is already several lines tall — and unlike case 1 above, here the floor is the thing that must yield), and `margin: calc(var(--space-md) * -1)` paired with `padding: var(--space-md)`, which is the entire "anywhere on the card" property — `.history-card` carries `var(--space-md)` of padding, and without pulling the summary out by exactly that amount a tap on the card's rim lands on the `<li>` and does nothing, **which reads as a broken control rather than as a boundary**. That is asserted by measurement, not by inspection: removing the pair drops the summary to 278px inside a 312px card and the check fails naming both numbers. `color: inherit` keeps the flight's own data out of the accent colour; the chevron keeps it, moved to the trailing edge by `order: 1` on the **shared** `summary::before` — reused, never redrawn, so the global disclosure marker, its rotation and its reduced-motion reasoning all still apply.

**One register entry this phase did NOT close, restated so it does not silently age out:** `.airline-card__chip`'s 20px interactive consumer (Phase 22, X7) is still the app's one control below the WCAG 2.5.8 Level AA 24px floor, still unmeasured against 2.5.8's spacing exception, and its stated disposition — re-examine the height before adding a second interactive consumer — is unchanged. Phase 23 added no consumer of that class.

## What to Avoid

- Reintroducing a blanket minimum-size floor on an icon-only button's visual box instead of relocating the hit area into a `::before` pseudo-element — the relocation pattern is what avoids the accessibility trade-off.
- Writing a lower-specificity (or bare-class) hover rule for the theme-picker segments or any `button[type="submit"]`-adjacent quiet button — it cannot reach past `button[type="submit"]`'s or `.theme-form .theme-option`'s specificity and will silently do nothing.
- Restoring a resting card shadow on any of the card set (nine components as of 06.6.4.1.1-05) — 06.6.4 (D-03) is a deliberate reversal of 06.6.1's own direction, not an oversight to "fix."
- Adding a second muted-text strength or a new hover-wash percentage instead of reusing the existing register (4.5% / 7% / 7.5% / 9% / 12% / 14%) — the file already documents having fixed a second-muted-strength defect twice; a new value reopens it. The 12% background wash on `.runway-card--selected`/`.theme-chip--selected` (06.6.4.1.1-06) reuses this exact register value, not a new one.
- Reintroducing a border-only selected-card treatment on any future selectable-card component — 06.6.4.1.1-06 found this too subtle to notice at a glance once a second, denser instance of the pattern shipped; reuse the border-plus-wash-plus-check-glyph combination instead.
- Adding a background wash across a whole `.theme-chip` (rather than scoped to `.theme-chip__body`) — it would sit behind and visibly tint the rendered preview band, which must stay undithered so the theme's real colours are legible.
- Keying a selected-state treatment off a server-rendered class ALONE on any form control whose selection can change client-side without a page reload — this is exactly the 260904-bbi defect (the strong highlight followed the saved config, not the live choice). Any future selectable card must key its strong treatment to live `:has(input:checked)` (or equivalent live state) inside `@supports`, with the server class demoted to the no-`:has()` fallback and/or an honest "saved" marker.
- Rewriting either base hover guard's `:not(--selected)` to `:not(:has(...))` to "simplify" it into one selector — an unsupported `:has()` invalidates the WHOLE selector list it appears in, silently dropping the hover reveal in non-supporting browsers. Use a positive `:has(input:checked):hover` restore rule instead (see the specificity-arithmetic paragraph above).
- Introducing a new muted-text strength or a new wash percentage for a quiet "this is saved, not selected" marker — reuse the file's existing `color-mix(in srgb, var(--color-text) 70%, transparent)` register value, the same discipline the 12% accent wash above already follows.
- **Signalling selection with a wider `border` on any selectable card** — Phase 22 (T6) converted all three surfaces to a constant 1px border plus `box-shadow: inset 0 0 0 2px`, precisely because a border is part of the box and a 2px selected card shoves its siblings. This applies to the quiet dashed saved-state markers too.
- **Writing `box-shadow: none` in a `:hover`/`:focus-within` restore rule on a selectable card** — it reads as "suppress the hover elevation" and now means "erase the selection ring." Restate the inset ring instead; `box-shadow` is a single property, so declaring the ring replaces the elevation outright.
- **Simplifying `button.calendar-disconnect-btn` back to the bare class** — the element qualifier is what gives it equal `(0,1,1)` specificity against `button[type="submit"]` so source order can decide. Dropping it silently restores T2: the app's one destructive control painted as the page's primary CTA.
- **Compacting `.login-card button[type="submit"]` or `.mobile-nav__link` in a density pass** — both are named 44px *restorations* in the kept category, each with a recorded three-point justification, not survivors of the 30/36px trade that were simply missed.
- **Filing the bottom tab bar under the traded-away touch targets** — it meets 44px directly in both axes at 78 × 56px; nothing was traded for it. The same goes for `.switch` and `.history-card__summary` (Phase 23): all three are met-directly entries, and all three are hit-area GAINS over the controls they replaced.
- **Putting the `role="switch"` touch floor on `.switch__track` instead of on `.switch`** — the track is 52 × 32px and is not the focusable or pressable element; the button around it is. A register entry naming the track records the wrong box and invites a later plan to "fix" the button's padding away.
- **Giving a `role="switch"` control an ACTION as its accessible name** (`Switch off`, `Éteindre`) — it announces an action and a state contradicting each other about one control. The name is the SETTING; the state lives in `aria-checked`; the visible state span is `aria-describedby` and elaborates (Quiet hours' carries its window) rather than repeating. A harness check forbids the four retired action wordings' return, so reintroducing one means deleting the check that forbids it.
- **"Harmonising" `.history-card__summary`'s negative margin away** — the `margin: calc(var(--space-md) * -1)` / `padding: var(--space-md)` pair is what makes the whole card face tappable; without it the card's rim is dead, measured at 278px inside a 312px card.
- **Adding a second interactive consumer of `.airline-card__chip` at its 20px height** without first relocating the hit area — see the register entry above; that class is a label voice, and its one interactive consumer is recorded as an open exception, not as a precedent.
- **Disabling a submit button INLINE in a submit handler** (Phase 22, T14, recorded here because this is where a future double-submission guard will be written). The app has one shared `submit-guard.js`, a delegated document-level listener registered once on the authenticated shell, and it disables the submitting control from a **zero-delay timer** — deliberately, not incidentally. A submit button's `name`/`value` joins the form data set only *after* the listeners return, and this app's **theme and language pickers are named submit buttons whose name/value is the entire request**: disabling inline would strip the payload and turn every theme switch into a no-op. The guard also changes no label, so nothing shifts under the pointer. Do not write a per-form guard, and do not "simplify" the timer away.
- **Re-rejecting the icon-only pattern for `.row-toggle` by citing the Phase 21 entry** — that entry is SUPERSEDED in place above, and its stated ground (the control carries visible text) stopped being true when X5 removed the label. Re-reversing it requires a new argument, not the old one.
