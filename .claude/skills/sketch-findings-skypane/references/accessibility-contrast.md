# Accessibility & Contrast

## Design Decisions

**06.6.2's accent darkening.** Light-mode `--color-accent` moved from `#E8622C` SUPERSEDED to `#B13F16` (D-14, UXA-04) to meet WCAG AA text contrast — the accent is used as text (links) and as a fill with white/`--color-on-accent` text (primary buttons), so both directions needed checking. The accent-hover token moved with it, from `#D2521F` SUPERSEDED to `#963610`. Dark-mode accent (`#FF8A5C`) was already compliant and is unchanged. `WCAG_AA_NORMAL_TEXT` (4.5), `WCAG_AA_LARGE_TEXT` (3.0) and `WCAG_AA_UI_COMPONENT` (3.0) in `companion/contrast_check.py` are the named threshold constants this change was checked against, reproduced from the published WCAG 2.1 SC 1.4.3 spec text and verified in `06.6.2-RESEARCH.md` to reproduce `06.6.1-UX-AUDIT.md`'s own published contrast numbers exactly.

**The three-level surface model.** A two-level model (`--color-dominant` doing double duty as both page background and card surface) could not survive the accent/contrast work: once cards needed to visually separate from the page again, one token could no longer serve both roles without either flattening the page (no card definition) or losing the warm-canvas direction. 06.6.2 (D-14) split this into `--color-canvas` (page background), `--color-dominant` (primary card/control surface) and `--color-secondary` (secondary/elevated/nav surface), in both themes. `.page-section` was the one component this split initially missed — it kept a pre-split "no background at all" rule that was correct under the two-level model but rendered Config's Poll/LED sections and both of Preview's sections as shadowed canvas-coloured blocks once every other card had moved to the dominant surface; that gap is closed in the current stylesheet.

**The executable colour-separation contract.** For three phases, "the accent must stay distinguishable from every status colour" was prose only in `style.css`'s header comment, and it named only the accent-vs-warn pair — the one pair 06.6.1's D-04 actually examined and accepted (dE76 28.6 in light mode). That gap is exactly how 06.6.2's WCAG-AA accent darkening was able to move the accent to within dE76 22.9 of the then-current `--color-status-error` (`#DC2626`) unnoticed: contrast checks (foreground-vs-background) stayed green throughout, because contrast and signal-separation are different questions — contrast asks "can this be read against that background," separation asks "can these two colours be told apart as different signals at a glance." The heading-color-consistency debug session closed the gap by adding three functions to `companion/contrast_check.py` — `hue_degrees()`, `hue_separation()` (0-180°, shortest angular distance) and `perceptual_distance()` (CIE76 delta-E in CIE L*a*b*, D65) — plus two named thresholds: `MIN_SIGNAL_PERCEPTUAL_DISTANCE = 28.0` (the primary gate, applied to every accent-vs-status pair in both themes, calibrated to the one pair 06.6.1's D-04 already validated) and `MIN_SIGNAL_HUE_SEPARATION = 24.0` (the secondary gate, applied to the accent-vs-ERROR pair only, since both are saturated red-oranges and hue angle is the only channel left to separate them with once lightness is controlled for). `companion/test_contrast_check.py`'s separation section enforces both on every accent/status pair — a token change that violates either now fails a test, not a reading of a comment.

**The status-error recolour.** `--color-status-error` moved from `#DC2626`/`#F87171` (light/dark) SUPERSEDED to `#BE123C`/`#FB7185` in the heading-color-consistency debug session, once the new separation contract measured the old error red at only dE76 22.9 / 15.9° from the darkened accent — closer than the accent-vs-warn pair 06.6.1 had already accepted, which is why a primary-action button and an error edge were reading as the same brick red on screen. Moving to crimson (hue ≈345°) restores separation (dE76 29.3, 30.5° hue) without touching the accent, so UXA-04's WCAG-AA fix stays intact; it also raised the token's own worst-case contrast on the three light surfaces from 3.96 to 5.16, making it safe as text and not only as a fill.

**Dark mode can now be MEASURED rather than read — new in Phase 24 (CFG-45, 24-02), and this is the first time in the project's history.** Until this phase **no browser check in this repository had ever switched theme**, so every dark-mode claim this design system has ever made rested on *reading CSS*: the token block declares a dark value, the rule spends the token, therefore the pixel is right. That inference is sound only while nothing between the declaration and the pixel fails, and three of the things that can fail there are invisible to any source scan.

- **The mechanism.** `companion/test_browser_ux.py`'s `_set_ui_theme(page, theme)` puts an already-loaded page into a named theme and returns the paint that theme actually produces. It drives the explicit `html[data-ui-theme]` attribute — **not** `emulate_media(color_scheme=…)` — and the reason is recorded in the helper's own comment rather than left as a preference: that attribute is what the app's own picker sets, and `style.css` declares those two blocks specifically so they **outrank** `prefers-color-scheme` (CFG-09). Driving the OS preference would exercise a path the app deliberately lets the user override *and* leave the measurement at the mercy of the host's setting. `"auto"` is refused **with its reason** — it declares no override rule of its own, so it resolves to whatever the host OS prefers, which is the one thing a measurement must not depend on. The vocabulary is derived from `layout.UI_THEME_CHOICES` rather than restated, so a renamed choice fails here instead of silently measuring nothing. **The read is the wait:** every value goes through `getComputedStyle`, which forces a style flush, so there is no sleep, no timeout and no `transitionend` listener anywhere in it — a timing wait on the slowest file in the suite is a flakiness generator, and an intermittently red check is worse than no check.
- **The helper refuses to return unless the two themes genuinely differ**, and that clause is the difference between a helper and a decoration. If the `html[data-ui-theme="dark"]` override were ever renamed, dropped or outranked, both themes would resolve to the same paint and every "this differs between themes" assertion built on it would be comparing a value to itself while printing PASS. So it samples `--color-canvas` and `--color-text` in **both** explicit themes on every call and raises if either pair matches. The verification is deliberately **not** a literal-value assertion — hard-coding `#F7F4EF`/`#0C0F14` would copy this stylesheet into a harness and start failing on a palette change that is not a defect. What is asserted is *the property the two override blocks exist to produce*: that they **invert**. It caught a real defect on its first run, before any caller existed (the probe reset the document to the first theme rather than the requested one, so the helper lied about the state it left the page in).
- **What it catches that reading could not.** `_computed_paint(page, selector, props)` reports the browser's **resolved** paint, after the cascade has run, after `currentColor` has resolved against the inherited `color`, and after the theme token has been substituted. It is the only thing in this repository that can tell **(a)** a shape painted by a token from one that fell through to the **SVG default** — `fill` `rgb(0, 0, 0)`, `stroke` `none` — which is exactly what a class that resolves to no selector produces; **(b)** two states that have collapsed to the same colour (the ring's value arc and its track resolving to one paint, so the gauge reads as a plain circle with no reading in it); and **(c)** a rule that matches nothing, since an unmatched selector **raises** rather than returning a sentinel a caller has to remember to guard. Its `svg_default` field names the offending properties rather than returning a verdict, because a shape that legitimately declares `stroke: none` reports `stroke` too.
- **`_assert_no_page_overflow(page, where, expected_width)`** is the third, and it measures `documentElement` — matching both of this file's pre-existing page-level checks, because a third convention for what "the page" means is how three checks come to disagree. It was **measured before choosing**: `body`'s own `overflow-x: hidden` does *not* clamp `body.scrollWidth`, because CSS propagates a body overflow to the viewport while `<html>`'s own overflow is `visible`, so the two boxes agree exactly and the choice is consistency rather than capability. A deliberately-scrollable `.data-table-wrap` overflowing its own box leaves this assertion clean by construction, so it cannot start disagreeing with the wrap-level check that owns that question.
- **The measured result, for every drawing this phase shipped: sixteen resolved paint values, none the SVG default, in both themes and with scripts blocked.** The battery ring's value arc `rgb(22, 163, 74)` / `rgb(74, 222, 128)` against a track of `rgb(223, 215, 200)` / `rgb(42, 48, 64)`; the chart's area, line and mark sharing **one** ink per theme (`rgb(23, 25, 31)` / `rgb(241, 243, 246)` — that shared ink *is* the dark-mode mechanism) against a threshold that deliberately does not (`rgb(217, 119, 6)` / `rgb(251, 191, 36)`, because a judgement painted in the data's own colour is not a judgement anyone can read); the day band's frame, span and marks; and the grid's four cell states. **The combination actually measured is dark mode with scripts blocked**, on the stated ground that it is the one most likely to be wrong.

**A translucent fill is measured as a COMPOSITE over its own background, never as a resolved fill (new, Phase 24, 24-05).** "Painted but invisible" is this feature's specific failure mode and a resolved-paint reader is structurally blind to it — `fill: currentColor` at `fill-opacity: 0.001` reports the same ink as at 0.14. The shipped measurement composites the resolved fill over the element's **own resolved background** at the resolved alpha and runs the result through this app's own `contrast_check.contrast_ratio()`. Measured at the shipped `fill-opacity: 0.14`: light `#DFDFE0` over the card's `#FFFFFF` for **1.3317:1**, dark `#343840` over `rgb(21, 25, 34)` for **1.4955:1**. **The floor is 1.20:1, deliberately not WCAG's 3:1** — that figure is for a UI component a user must find and identify, and at 3:1 this would be a block of ink rather than a tint under a line. The floor was **located by sweeping alpha rather than asserted**: it is first missed between `fill-opacity` 0.08 (1.173 light) and 0.09 (1.202 light), so it bites at roughly two thirds of the shipped value rather than sitting decoratively below it. The same idiom carries the day band's three floors — frame vs card 1.148:1 / 1.106:1 against a 1.05 floor, shaded span vs the band's own surface 1.246:1 / 1.208:1 against 1.15, and a mark crossing that shaded span at **12.292:1 / 11.842:1** against 4.50, which is the pair that matters because most of a night's check-ins land inside that span.

**The colour-separation contract gains its first STATUS-vs-STATUS pairs (new, Phase 24, 24-07, CFG-43).** For every phase until this one, `companion/test_contrast_check.py`'s separation section measured the **accent** against each status colour and nothing else, because everywhere in this app a status colour appears **alone beside its own word**: one tile border, one dot with its label, one section edge. Health's check-in regularity grid is the first surface where all three appear **side by side as squares of colour with nothing but colour between them**, and *"can these two be told apart as different signals"* becomes a question about that pair set for the first time. **Nothing pinned it anywhere.** Six checks were added — three pairs (ok/warn, ok/error, warn/error) × two themes — held to the existing `MIN_SIGNAL_PERCEPTUAL_DISTANCE` (28.0) and **not** to the hue floor, which stays applied to the accent-vs-error pair alone for the reason already recorded above. At the shipped palette the closest pair in either theme is **light warn/error at dE76 55.3**, comfortably past the floor: this section ships green, and its job is to stay that way through a future palette edit rather than to report a defect today. `EXPECTED_CHECK_COUNT` in that harness moves 43 → **49**. It is also the fourth state that makes the grid honest as much as the three colours: `drawing-cell--none` is `--color-border`, this file's structural token, so "no observation" reads as absent rather than as a verdict — and `cell_class()` falls to *that* class for anything unrecognised, never to on-cadence (which would report health from a value nobody recognised) and never to missing (which would accuse the device on the same).

**The no-JS floor, and the reduced-motion floor, both held by construction in Phase 24 — and the construction is the point.** Every drawing this phase shipped is **server-rendered SVG**, so the deferred-script pin is still **14**, its pre-phase value: the phase added no script, and the four drawings are complete with scripts blocked (measured through `_no_js_page()`, in **dark** mode, at the 360px floor — one ring value arc per page still resolving `rgb(74, 222, 128)`; the band's frame, two spans and five marks all still painting dark-mode tokens; the grid's cells the same; the hero's every child at an identical left, width and gap to the scripted run). The `.drawing*` block declares **no `transition` and no `animation` at all** — the `@keyframes` count is still 4, the `reduce`-block count still 2 and the `no-preference` count still 1, exactly where Phase 23 left them — so this phase's drawings sit outside the reduced-motion question entirely rather than being switched off by it. **One accessibility decision inside the drawings is worth stating on its own, because it goes the other way from every other label in them:** the axis labels are `aria-hidden` (every point already announces its own value through the existing keyboard path), and the low-battery **legend is deliberately NOT** — nothing anywhere else announces where "low" starts. A cell built with no `<title>` **raises** rather than emitting silently, because a silent cell is a coloured verdict with nothing naming what it judged, and every title goes through the drawing module's own escaping helper with no exception path.

**Focus-visible floor.** Every focusable element (`a`, `button`, `input`, `select`) — and, since Phase 22 (T15), `summary`, which is a native interactive element and had been missing from the list all along — gets a 2px solid `--color-accent` outline with a 2px offset on `:focus-visible`. An accessibility floor (D-22), never removed without a replacement.

**Two repairs to that floor, both Phase 22 (T15), both reusing the floor's own values rather than inventing a treatment.**
- **A selected card's focus state was pixel-identical to rest.** `.runway-card`/`.theme-chip` delegate their hit area to a wrapping label around an off-screen hidden radio, and that radio's own outline cannot be seen, so keyboard focus on a selected card showed nothing at all. Fixed with `.runway-card:has(input:focus-visible), .theme-chip:has(input:focus-visible)` carrying the global floor's own `outline: 2px solid var(--color-accent); outline-offset: 2px;`. It lives **inside the ONE existing `@supports selector(:has(*))` block** — this stylesheet is pinned at exactly one, never two (see `references/settings-page-patterns.md`, whose own stale "exactly two" claim was corrected in the same sweep). **Documented degradation:** a browser without `:has()` keeps today's behaviour, the same accepted-degradation framing the live-selection state already uses; `:has()` has been Baseline widely-available since December 2023.
- **Every `<details>` had lost its open/closed indicator.** `summary { display: flex }` suppresses `::marker`, so nothing showed a disclosure was a disclosure. Restored with an explicit chevron `::before`. This consumes the **already-reserved** `<summary>` disclosure-marker accent entry — it is a restoration, **not a new accent consumer**, and the reservation list does not change. The rotation is a plain `transform` and is covered by the **global** reduced-motion block: adding a per-rule block here would be dead code, not a safety net (see "What to Avoid"). One deliberate local divergence: on the bottom tab bar's "More" summary the chevron is taken out of flow and its rotation is inverted, because that sheet opens upward — see `references/mobile-navigation.md`.

**Skip link.** `.skip-link` is the first focusable element in `<body>` (06.6.2-05, UXA-10) — visually hidden 40px above the viewport until it receives keyboard focus, at which point it becomes the first visible, high-contrast element on the page (accent fill, `--color-on-accent` text), letting a keyboard user bypass the nav entirely.

**`.visually-hidden` utility.** Off-screen-but-present text (the Health nav-tab's "— attention needed" suffix, the runway check glyph's "Selected" label). Must never be given `display: none` or `visibility: hidden` — either removes the text from the accessibility tree and defeats its only purpose. The correct implementation is the file's own: `position: absolute; width: 1px; height: 1px; padding: 0; margin: -1px; overflow: hidden; clip-path: inset(50%); white-space: nowrap; border: 0;`.

**Form-control caveat (quick task 260902-l9w).** On a `<span>` this utility's own 1px sizing is the whole story. On an `<input>` or `<select>` it is not: the global native `input, select` rule's 44px touch-target minimums (`min-height`/`min-width`) are a layout-time floor, not a cascade competitor, so they clamp the utility's 1px box back up to a real 44x44 box regardless of which rule wins on specificity. This is exactly the bug that let the three Runway-picker radios (`config_page.py`'s `runway_fieldset()`) paint a visible 44x44px native radio dot on real mobile browsers despite carrying `class="visually-hidden"`. The fix is a second, narrowly scoped rule — `input.visually-hidden, select.visually-hidden` — that clears both minimums (and native control theming) for elements carrying this class; it does not touch the `.visually-hidden` block itself or the global floor. See `references/control-density.md`'s touch-target floor register for the exempt-by-delegation category this creates.

**Global reduced-motion override.** A single `@media (prefers-reduced-motion: reduce)` block (D-19), placed after the token blocks and before the universal box-sizing reset, sets `transition-duration`/`animation-duration` to `0.01ms` and `scroll-behavior` to `auto` on every element — every later rule's colour/border/shadow transition inherits this for free. `.js .mobile-nav`'s own `max-height` transition carries one narrow additional override (`transition: none`) inside the same media query, since its transition duration is otherwise set inline on the base rule rather than only via the global shorthand properties. The stylesheet's live `reduce`-block count is **two** and is pinned by a named constant (`EXPECTED_REDUCED_MOTION_REDUCE_BLOCKS` in `companion/test_companion_app.py`); moving it is a deliberate two-file edit, never a side effect.

**The floor's FIRST named exception, and it is genuinely not reachable — the `::view-transition` pseudo-element tree (Phase 23, D3/D10, CFG-32/CFG-33).** Until this phase the paragraph above read as universal, and every entry in this file treated it that way ("every later rule … inherits this for free"). **It is not universal, and the boundary is precise rather than a matter of degree.** `*, *::before, *::after` are ELEMENT selectors — the universal selector matches elements, and the two pseudo-element selectors name exactly two pseudo-elements. The `::view-transition` root and the `::view-transition-group()` / `::view-transition-old()` / `::view-transition-new()` tree beneath it form a **separate pseudo-element tree** that none of those three selectors matches, so a cross-document view transition is **not** switched off by the global override. On a page with `@view-transition { navigation: auto; }` and a reduce-motion visitor, the browser's own default cross-fade would run at full duration with nothing in this stylesheet able to reach it.

- **The mechanism that closes it:** the at-rule is nested inside `@media (prefers-reduced-motion: no-preference)`. One wrapper, one at-rule, no second belt. `EXPECTED_REDUCED_MOTION_NO_PREFERENCE_BLOCKS` is pinned at **1** and is frozen there — the licence to move it from 0 was granted to exactly one plan and has been spent.
- **Why the wrapper beats zeroing the pseudo-elements' durations, stated because the obvious alternative is an `animation: none` override inside the existing reduce block.** The wrapper prevents the transition from being **SET UP AT ALL**; an override sets one up and then runs it fast. Those are different outcomes, not the same outcome reached two ways — a transition that is set up still snapshots the old and new documents, still builds the pseudo-element tree, and still hands the visitor a (very brief) animated state. It is also the strictly weaker guarantee: a UA or a future spec level can introduce a property on that tree the override does not name, whereas a transition that was never set up has no tree to acquire one. `.js .mobile-nav`'s own narrow `transition: none` rests on the same reasoning from the other direction, and the "What to Avoid" entry below about dead-code per-rule blocks is the general case of it.
- **Proven in a browser, from the at-rule's own parent rule.** `test_browser_ux.py` walks the author stylesheets for `CSSViewTransitionRule`, asserts exactly one exists, asserts its `parentRule` is a `CSSMediaRule` mentioning `prefers-reduced-motion`, and evaluates **that rule's own `conditionText`** through `matchMedia` in both a default and a `reduced_motion="reduce"` context. **Reading the condition off the guarded rule is the whole design**: `matchMedia('(prefers-reduced-motion: no-preference)')` on its own is a statement about the browser, not about this app — it is false in a reduce context whether the at-rule is wrapped, unwrapped, or absent, so the vacuous form passes on the exact defect it claims to catch. An unwrapped at-rule, an inverted wrapper, a wrapper around some *other* rule and a wrapper narrowed so it can never match all four fail the shipped form; three of the four were mutation-run, and each leaves every source-level scan in the repository green.
- **`::backdrop` is inside the same blind spot and is handled by having nothing to switch off.** `<dialog>`'s backdrop is not an element and is not `::before`/`::after`, so the global override does not reach it either; `.lightbox::backdrop` therefore declares a `background` and **no** transition or animation at all. An animated backdrop would be motion a reduced-motion visitor cannot switch off. Treat this as the standing rule for the whole blind spot: **either the motion is prevented from being set up, or it is not declared on an unreachable pseudo-element in the first place.**
- **What is NOT an exception, checked rather than assumed:** `summary::before`'s chevron rotation and every `::before`/`::after` transition in the file are covered by the global block's own second and third selectors, and `summary::marker` / `summary::-webkit-details-marker` declare `color` only.

**Floors that survived 06.6.4's density pass.** 06.6.4 traded the 44px AAA touch-target floor away on four named selectors (buttons, desktop sidebar nav links, theme segments, filter input — see `references/control-density.md`), but every accessibility floor in this section was left untouched by that pass: focus-visible outlines, the skip link, `.visually-hidden`'s implementation, and the reduced-motion override all still apply exactly as described above regardless of any component's visual density.

**No-JS degradation floors.** `.js`-gated rules only ever govern the *visual/animated* state; the underlying accessibility state is set independently by JS and degrades safely when JS never runs. `.js .mobile-nav`'s `max-height: 0; overflow: hidden` clipping rule is scoped under `.js` (added unconditionally by `nav-dropdown.js`'s first statement) — without that class ever appearing, the base `.mobile-nav` rule alone renders the panel in its natural, unclipped, fully visible document flow (UXA-12's floor). Separately, `nav-dropdown.js`'s own `panel.hidden` toggling (UXA-02's floor) is what removes the closed panel from the accessibility tree and tab order once JS confirms it is closed — the two rules must never be edited independently of each other. `.js [data-static-save-fallback] { display: none; }` similarly only hides Settings' always-server-rendered bottom Save button once `.js` proves script ran; without JS, that button remains the only way to save (D-06 graceful degradation). **Phase 22 (B1/D-01) tightened that last one, and the reason is the sharpest available statement of this whole floor's point:** keying the hide on `.js` alone said only "some script ran somewhere", not "the replacement bar is actually live" — so any failure in an unrelated script left the fallback Save hidden with nothing to replace it, and the Display page could not be saved at all. A JS defect became "no way to save". The gate now requires proof from the bar's own script that its bar exists and has been shown. **A hiding gate must be keyed to the thing it is replacing, never to a proxy for it.**

**A component whose base rule declares `display` needs its own `[hidden]` selector (Phase 22, X3/T13).** An author-stylesheet `display` always beats the user-agent `[hidden] { display: none }` regardless of source order, so a server-rendered `hidden` attribute silently does nothing — which on the login card's show-password toggle produced a **visible control that did nothing** with scripts blocked, exactly what the no-JS floor forbids. Four components now carry the fix (`.dirty-bar`, `.refresh-pill`, `.login-reveal`, `.banner__pill`); full contract in `references/settings-page-patterns.md`. Note the class of defect for what it teaches: **no string-comparison harness can see it**, because the declaration is present and correct in the file. It took a real browser.

**The no-JS floor becomes a CONTROL floor — new in Phase 25 (CFG-46/CFG-52, 25-01/25-02), and it is the sharpest form this floor has taken.** Everything above is about a page degrading; this is about a *control* degrading, and the distinction is the whole point: **a control is not "usable" because it is rendered.** Phase 22's own P0 was a fallback Save that rendered perfectly and had a zero-size box. Three weaker proofs all look right and all pass against a broken control:

- *"the input is present with scripts blocked"* — passes against a control that saves nothing. This is the Phase 22 shape exactly.
- *"the page navigated after submit"* — passes against a POST the server rejected and redirected straight back from.
- *"the reloaded page shows the value"* — **passes against this app deliberately**, because `wake_interval_group()`'s own docstring records D-07 requiring a rejected submission's raw string be echoed back into the field. A DOM-only check reads `900` back off a page that stored nothing.

So the verdict is **the value read back FROM DISK**, through the app's own loader, after a real operate-submit round trip with scripts blocked at 360 px; the reloaded DOM is corroboration and is *optional* (`notifications_topic_url` is write-only by design and stores correctly while rendering empty forever). The DOM clause being optional and the disk clause never being optional is the shape to copy.

**Four accessibility clauses inside that floor, each paid for by a measurement:**

- **The `.js` gate hides with `display: none`, never `visibility` or `opacity`** — both of those leave a **focusable ghost** a keyboard visitor can tab into with scripts blocked. The gate is asserted in *both* directions in a real browser: zero height and **zero focusable descendants reached in a 24-step walk of the real tab order** with scripts blocked (the wrapper holding at least one focusable candidate, so the walk ran rather than short-circuiting), and a real box with scripts on. **A gate asserted in the blocked direction alone passes against an affordance hidden from everybody** — measured, against `.dirty-bar` with nothing ever arming it.
- **`display: none` destroys FOCUSABILITY, and that is not what a click-based check measures.** 25-06's prescribed mutation gave the carousel's radios `display: none` instead of `.visually-hidden`, and the no-JS save check would have stayed **green**: `_persist_without_js()` operates a radio through `target.click()`, and `HTMLElement.click()` works perfectly well on a `display: none` element, so the save still reached disk. What that mutation actually destroys is focus, and with it arrow-key selection. The check gained an explicit clause — focus the saved radio through its own `.focus()` with scripts blocked, assert it became `document.activeElement`, then press a real `ArrowDown` and require the selection to move (radiogroup arrow navigation is the browser's default action and needs no listener at all). **Never use `display: none` on a form control you mean to hide; the utility is `.visually-hidden`, and the check that proves it must ask the keyboard question directly.**
- **The announcement gate, applied to a dragged value.** A continuous-value readout must **not** be a `role="status"` live region — dragging fires it continuously and a screen reader would read the same phrase on every pixel. The native, debounced path is the focused control's own `aria-valuetext`, and it must sit **on the element a keyboard visitor lands on**, never on the wrapper around it (with it on the wrapper, a reader is told the value the control had *before* the drag — measured: the handle announcing `23:00` while its own input already held `12:00`). The mirror rule: **do not add `role="slider"` to an `<input type="range">`** — it is already a slider with its own `aria-valuenow`, and a role on top is the classic double-role error.
- **Contrast still applies to a control's refusal message.** 25-07's `.upload-drop__message` measures **5.73:1** light and **7.13:1** dark against the page canvas, both past WCAG AA 4.5, and every colour in that block comes from a theme token so both themes stay load-bearing (a literal is correct in one theme only and is invisible to `companion/test_contrast_check.py`).

**The Content-Security-Policy shapes what a control may DO, and the right answer is to change the control (new, Phase 25, D19/CFG-51, 25-07).** The plan's central mechanism for the artwork preview was `URL.createObjectURL()`. Measured against the real app **before** writing it, Chromium answered: *"Loading the image 'blob:…' violates the following Content Security Policy directive: `img-src 'self' data:`."* A `blob:` URL is matched by neither value, so the preview would simply never have rendered — and the plan's own acceptance criterion (`createObjectURL` paired with `revokeObjectURL`, asserted by source scan) **would have passed against a broken preview**, because a pair of calls is a pair of calls whether or not the image ever loads.

There were two ways out and only one is right for this control. Adding `blob:` to `img-src` would widen a security header so a thumbnail can render — in the one control on that page that accepts bytes from outside the app. `data:` is *already* allowed, for the inline favicon `layout.py` emits. So the preview reads the file with a `FileReader` and assigns a `data:` URL, **`companion/app.py` is untouched by one line** (verified by an empty `git diff` against the plan's base commit), and the object-URL leak the plan worried about does not exist to leak: there is no object URL. The same lifetime discipline applies to what replaced it — the `<img>`'s `src` is **removed** (not merely hidden) on every replacement, on every refusal and when the dialog closes, and a browser check fails if it is not. **Record this as the precedent: measure the policy against the real app before designing on top of it, and change the control rather than the header.**

**One validation seam, not two, and the structure is what guarantees it.** A drop and a pick must not validate differently, and the shipped answer is structural rather than procedural: a drop constructs a `DataTransfer`, adds the `File` and assigns it to the form's **own** `<input type="file">`, so from that point there is nothing left to keep in sync — same multipart POST, same route, same size cap enforced before the body is read, same parser discarding the client-declared filename, same server-side normaliser. There is exactly **one** validator (`uploadRefusal(zone, files)`) with exactly **two** call sites, asserted by source scan on a definition count of one and a call count of two, with the refusal proven **textually to precede the assignment** (a refusal that runs after the assignment refuses nothing) and the size cap **imported from `companion/app.py` at render time** rather than retyped. The client check is a **courtesy** and says so in the file: it refuses only what it positively knows is wrong and hands a browser reporting *no* MIME type to the server — **failing open toward the real check is the correct direction for a courtesy**, and it is what stops it refusing a legitimate PNG the picker would have taken.

**The one asymmetry, stated rather than hidden:** on the drop path the file is refused *before* anything is assigned; on the picker path the same validator runs and the same message appears, but `input.files` is never touched. That is principled — a drop is the script's own act, so declining to perform it is the script doing nothing; a pick is the visitor's act through the browser's own control, and silently discarding their choice would be the script undoing a person's input to spare them a server error it is not entitled to predict.

## What to Avoid

- Reverting the accent toward the SUPERSEDED `#E8622C` value without re-checking WCAG AA text contrast — that is the regression 06.6.2 (D-14, UXA-04) fixed.
- Shifting either the accent or a status colour without re-running `companion/test_contrast_check.py`'s separation section — a contrast-clean change can still collide as a signal, which is exactly how the accent/error collision happened the first time.
- Giving `.visually-hidden` a `display` or `visibility` value that removes it from the accessibility tree — its entire purpose is to stay in the tree while invisible on screen.
- Adding a per-rule reduced-motion block for a simple colour/border/shadow transition — the global override (D-19) already covers it; a redundant per-rule block is dead code, not a safety net. **This verdict survived Phase 23 unchanged and was tested by it**: four `@keyframes` blocks and a dozen new transitions shipped, and the live `reduce`-block count is still two, because every one of them is declared on a real element or on `::before` and the global block reaches all of them for free.
- **Adding an `animation: none` "second belt" on the `::view-transition-*` pseudo-elements** — it is strictly weaker than the `no-preference` wrapper that already guards the at-rule (it runs a transition that was set up, instead of preventing the setup) and it is the same dead-code-not-a-safety-net pattern as the entry above, in the one place where a reader is most likely to think it is warranted.
- **Declaring a `transition` or an `animation` on a pseudo-element outside `::before`/`::after`** — `::backdrop`, `::marker`, `::placeholder`, `::selection` and the `::view-transition` tree are all outside the global override's reach, so motion declared there cannot be switched off by a visitor's preference. Either prevent the setup with a media wrapper or do not declare the motion.
- **Writing a reduced-motion assertion as `matchMedia('(prefers-reduced-motion: no-preference)')`** — that is a statement about the browser, not about this app: it is false in a reduce context whether the guarded rule is wrapped, unwrapped or absent, so it passes on the exact defect it claims to catch. Read the condition off the guarded rule's own `parentRule` and evaluate *that* string.
- **Asserting that a translucent fill "is not the SVG default"** and calling that a visibility check — it is green at `fill-opacity: 0.001`. A resolved-paint reader cannot see a translucent fill's actual visibility at all; composite it over the element's own resolved background and run the result through `contrast_ratio()`, and locate the floor by sweeping alpha rather than picking one.
- **Reading a dark-mode claim off the stylesheet** now that a browser can answer it. A declaration being present proves nothing about the pixel: a class that resolves to no selector, two states collapsing to one colour, and a fill falling through to the SVG default all leave every source-level scan green. Use `_set_ui_theme()` + `_computed_paint()`, and prefer the dark + scripts-blocked combination, which is the one most likely to be wrong.
- **Hard-coding a theme's hex values into the browser harness** to prove a theme switch landed — that duplicates `style.css` into a test and fails on a palette change that is not a defect. Assert the property the two override blocks exist to produce: that they **invert**.
- Narrowing any of the three-file DOM contract's pieces (`.js .mobile-nav`'s clipping rule, `nav-dropdown.js`'s `panel.hidden` toggle, and the underlying `NAV_TOGGLE_ID`/`MOBILE_NAV_ID`/`MOBILE_NAV_OPEN_CLASS` literals) independently of the other two — they must be edited together or the no-JS floor silently breaks.
- **Proving a control degrades by asserting it RENDERS** (Phase 25) — "present with scripts blocked", "the page navigated" and "the reloaded page shows the value" all pass against a control that saves nothing, and the third passes *by design* on this app, which echoes a rejected submission back into the field. Read the value back **from disk**.
- **Hiding a gated affordance with `visibility: hidden` or `opacity: 0`** — both leave a focusable ghost a keyboard visitor reaches with scripts blocked. `display: none`, and assert the gate in **both** directions: a gate checked only in the blocked direction passes against an affordance hidden from everybody.
- **Using `display: none` to hide a form control you still mean to be operable** — it destroys focusability and with it arrow-key navigation, while `HTMLElement.click()` keeps working, so a click-based check stays green on exactly that defect. The utility is `.visually-hidden`, and the check must ask the keyboard question directly (`.focus()`, then a real arrow key).
- **Making a continuous-value readout a live region** — a drag fires it on every pixel. The focused control's own `aria-valuetext` is the native, debounced announcement, and it belongs on the **focusable** element, never on the wrapper.
- **Widening a security header so an enhancement can render** (Phase 25, D19) — `img-src 'self' data:` blocks a `blob:` preview outright; the answer was a `FileReader` `data:` URL and `companion/app.py` untouched by one line, not `blob:` added to the policy. Measure the policy against the real app **before** designing on top of it.
- **Letting a dropped file and a picked file reach two validators** — one validator, two call sites, asserted by source scan, with the refusal proven textually to precede the assignment and the cap imported from the app rather than retyped. And keep the client check a courtesy that **fails open** toward the server: a browser reporting no MIME type must be handed on, not refused.
