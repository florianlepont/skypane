### Pattern 1: Reuse the codebase's own `color-mix()` idiom instead of new rgba literals

**What:** CONTEXT.md's D-01b/D-02/D-05 each specify a light-mode `rgba(23,25,31,.0NN)` wash with the dark-mode value marked "not live-validated, planner's call". The codebase already has an established, token-based idiom for exactly this "neutral wash that auto-adapts to both themes with zero per-theme override" need: `color-mix(in srgb, var(--color-text) N%, transparent)`. `--color-text` already resolves to a near-black in light mode (`#17191F`) and a near-white in dark mode (`#F1F3F6`) — so a single `color-mix` declaration produces a dark wash on light backgrounds and a light wash on dark backgrounds automatically, with no `@media (prefers-color-scheme: dark)` or `html[data-ui-theme="dark"]` block needed.

**When to use:** For every one of D-01b's `background: rgba(23,25,31,.045)`, D-02's `background: rgba(23,25,31,.07)`, and D-05's `background: rgba(23,25,31,.045)` — recommend `color-mix(in srgb, var(--color-text) 4.5%, transparent)` / `7%` / `4.5%` respectively as drop-in equivalents that also solve the "dark-mode analogue" gap CONTEXT.md leaves open.

**Example:**
```css
/* Source: companion/static/style.css line 672 (existing, VERIFIED) */
.sidebar-link--active {
  background: color-mix(in srgb, var(--color-accent) 12%, transparent);
}

/* D-07 itself already proposes the identical idiom for row hover: */
.data-table tbody tr:hover {
  background: color-mix(in srgb, var(--color-text) 4%, transparent);
}
```
This is not a new pattern being introduced by this research — it is the project's own established convention (`.sidebar-link--active`, `.banner` and its severity modifiers all use `color-mix(in srgb, ...)` already) applied consistently to the three "planner's call" gaps.

## Common Pitfalls

### Pitfall 1: `.data-table-wrap th`'s sticky-header background silently defeats D-07's "quiet label" goal

**What goes wrong:** D-07 says to remove `background: var(--color-secondary)` from `.data-table th` (line 1004) to get the quiet uppercase-label look. But `.data-table-wrap th` (lines 1018–1023) — a SEPARATE rule needed for the sticky header's scroll-opacity, per its own comment ("The explicit `background` prevents body rows from visibly scrolling underneath a see-through sticky header") — carries its own `background: var(--color-secondary)` declaration. Both selectors have equal specificity (0,1,1); `.data-table-wrap th` sits later in source order, so it always wins on `background` regardless of what the base `th` rule says. Editing only the base rule leaves the header rendering exactly as before (a solid filled block) once shipped.

**Why it happens:** Two rules for the same element, one purely for a sticky-positioning side effect (opacity, not colour intent), never revisited when the colour intent changed.

**How to avoid:** Change `.data-table-wrap th`'s `background` too — to something that stays opaque (still needed for the scroll-through fix) but reads as "quiet", e.g. `var(--color-dominant)` (the plain card surface, matching what a `.stat-tile`/`.page-section` table normally sits inside) rather than `var(--color-secondary)` (the "elevated/filled" surface). Both rules must land in the same edit or the sticky-scrolled state and the static state will visibly disagree.

**Warning signs:** Header looks correct in a screenshot taken without scrolling, but reverts to the old filled look the moment the table is scrolled past its header (only reproducible on a long table, e.g. History with many rows).

### Pitfall 2: `row_class`/`row-alt` server-side computation becomes dead code, not a bug, if left in place

**What goes wrong:** `companion/layout.py:1068`, `companion/pages/history_page.py:357`, and `companion/pages/airlines_page.py:232` all compute `row_class = "row-alt" if index % 2 else "row"` and interpolate it into every `<tr class="%s" ...>`. If D-07 removes the `.data-table tr.row-alt { background: ... }` CSS rule (lines 1036–1038) but leaves this Python computation untouched, the class attribute still renders — it just no longer matches any CSS rule. This is harmless (dead markup, no visual or functional effect) but will look like an incomplete refactor to a future reader.

**Why it happens:** CONTEXT.md itself flags this as "planner's call" — either remove the CSS rule and stop emitting the class (3 Python edit sites), or remove the CSS rule and leave the class emission (0 Python edits, tiny dead-code cost).

**How to avoid:** Given this phase's own stated minimal-blast-radius goal (a pure visual refinement, not a refactor), recommend the CSS-only path — remove the CSS rule, leave `row_class` computation in all 3 Python sites untouched. Document the decision in the plan so it doesn't read as an oversight.

**Warning signs:** None — purely a documentation/cleanliness question, not a defect.

### Pitfall 3: The `.copy-btn`'s pre-existing 44×44 comment becomes actively wrong after D-01/D-02

**What goes wrong:** The current comment above `.copy-btn` (lines 906–910) reads: "Inherits the global `button` rule's 44x44 hit-target floor unmodified — never reduce min-height/min-width below 44px — and only overrides padding/background". After D-01 shrinks the global `button` rule to `height: 30px` (dropping `min-height`/`min-width: 44px` entirely) and D-02 gives `.copy-btn` its own explicit `width: 28px; height: 28px` plus a `::before`-based 44×44 hit area, this comment describes a mechanism (inheriting a 44px floor from the base rule) that no longer exists — the 44×44 target is now synthesized entirely by the new pseudo-element, not inherited.

**Why it happens:** D-01c's own instruction ("update comments... for the specific rules this phase touches") applies here but is easy to miss since the comment sits on `.copy-btn`, a D-02 concern, while the stale premise comes from D-01's change to a different rule (`button`).

**How to avoid:** Rewrite this comment as part of D-02's edit, not as an afterthought — state the new mechanism (28×28 visual box, 44×44 hit area via `::before { inset: -8px }`) explicitly.

### Pitfall 4: No touch-target-size test exists anywhere in this codebase — CONTEXT.md's own assumption is unconfirmed

**What goes wrong:** D-01 and the phase's own investigation prompt both assume `companion/test_contrast_check.py` (or some other test) "asserts 44px on `button`" and will need updating. `grep -n "44px\|min-height\|min-width" companion/test_*.py companion/contrast_check.py` [VERIFIED] returns zero matches across every test file in the package. `companion/test_contrast_check.py`'s 31 checks (`EXPECTED_CHECK_COUNT = 31`) are exclusively colour-contrast-ratio and hue-separation assertions (WCAG 1.4.3-style relative luminance and CIE76 dE) — there is no dimension/size assertion of any kind anywhere in the file.

**How to avoid:** Do not add a task to "update the 44px test" — there is none to update. This also means D-01/D-02/D-05/D-06/D-08's size reductions carry zero automated-test risk on this front; only the class-name/markup-presence assertions catalogued in the Validation Architecture section below are load-bearing.

### Pitfall 5: D-06a's "markup change is needed" premise may not hold against the real codebase

**What goes wrong:** CONTEXT.md's D-06a states the theme picker needs "a shared wrapping container that doesn't exist in today's `.theme-form` markup (currently a bare flex row with no shared visual boundary)". Reading `companion/layout.py`'s `_theme_form_html()` (lines 613–627) [VERIFIED] shows the 3 `<button type="submit">` elements are already wrapped in exactly one element: `<form class="theme-form" method="post" action="/ui-theme">`. `.theme-form`'s own CSS rule already exists (lines 563–566: `display: flex; gap: var(--space-xs);`). D-06's new CSS (border, `border-radius: 8px`, `padding: 2px`, `gap: 2px`) can be applied directly to this EXISTING `.theme-form` selector with zero markup changes — the `<form>` element itself already serves as "the wrapping container" the decision describes. The live reference artifact this phase's decisions were validated against most likely used a generic `<div>` wrapper (common in a throwaway HTML mockup), which does not reflect that the real codebase's `<form>` already does this job.

**Why it happens:** The reference artifact was a standalone HTML mockup, not a rendering of the real Python templates — its DOM shape does not necessarily match `_theme_form_html()`'s actual output.

**How to avoid:** Before touching `companion/layout.py`, try the CSS-only path first: add `border: 1px solid var(--color-border); border-radius: 8px; padding: 2px;` and change `gap: var(--space-xs)` to `gap: 2px` directly on the existing `.theme-form` rule (line 563–566), remove the per-button border from `.theme-form .theme-option` (lines 574–587), and verify visually. Only fall back to a new wrapper `<div>` inside `_theme_form_html()`/`_mobile_nav_html()` if the `<form>`-as-container approach produces a real rendering defect (none is apparent from the CSS alone — forms accept padding/border/border-radius like any block element). If a Python change does prove necessary, it is a small, contained edit to `_theme_form_html()` only (both the sidebar-footer and mobile-nav-footer copies of the theme picker are built from this single function, so one edit reaches both render sites).

**Warning signs:** If prototyping shows the `<form>`-direct approach is visually indistinguishable from a `<div>`-wrapped approach, there is no reason to touch `layout.py` at all for D-06a specifically.

def _theme_form_html(resolved_theme):

        % "".join(options))
