## Warnings

### WR-01: Generic `a:hover` overrides nav-link text colour on hover, including the active link, despite the D-05 `:not()` scoping meant to prevent exactly this

**File:** `companion/static/style.css:356-363, 485-517, 704-740`

**Issue:** `a { color: var(--color-accent); }` / `a:hover { color: var(--color-accent-hover); }` (lines 356-363) has specificity `(0,1,1)` (one pseudo-class + one type selector). `.mobile-nav__link`/`.sidebar-link` (base, `color: var(--color-text)`) and `.mobile-nav__link--active`/`.sidebar-link--active` (`color: var(--color-accent)`) are single-class selectors with specificity `(0,1,0)`. Since `(0,1,1) > (0,1,0)`, `a:hover` wins the `color` property **regardless of source order**, for both the active and inactive nav links (both are confirmed `<a>` elements in `companion/layout.py`, `sidebar_nav()`/`_mobile_nav_html()`).

The D-05 comment at line 511-514 explicitly says the `:not(.mobile-nav__link--active):hover` scoping "is what keeps the two states from ever colliding" — but that scoped rule (and its `.sidebar-link` twin at 738-740) only ever declares `background`, never `color`. The generic `a:hover` rule was never scoped and still reaches both link classes for `color` at higher specificity. The net effect:
- Hovering the **active** nav link silently shifts its "single active cue" colour from `--color-accent` to `--color-accent-hover`, even though nothing in D-05's design intends the active indicator to change on hover.
- Hovering an **inactive** nav link is documented to be "a neutral wash" only (background-only, per the D-05 comment) but the text colour also shifts to an accent tint — a use of accent colour that is not in the file's own "kept exhaustive on purpose" accent-reservation list (lines 10-22).

**Fix:**
```css
/* After a:hover (or anywhere with >= (0,2,0) specificity): */
.sidebar-link:hover,
.mobile-nav__link:hover {
  color: var(--color-text);
}

.sidebar-link--active:hover,
.mobile-nav__link--active:hover {
  color: var(--color-accent);
}
```

### WR-02: Extensive `color-mix()` usage with no fallback anywhere in the file

**File:** `companion/static/style.css` — e.g. `930-953` (base `button` background/border), `506`, `637`, `730` (active-pill tints), `1011-1012`, `1053-1055`, `1072-1073`, `1132` (button washes), `1248`, `1295`, `1461`, `1491` (muted text)

**Issue:** `color-mix(in srgb, ...)` is used as the *sole* value for `background`/`border`/`color` in well over a dozen rules, with no `@supports` gate and no plain-colour fallback declared earlier in any of these rules. On a browser without `color-mix()` support, the whole declaration is invalid and dropped — the property falls back to its inherited/initial value, not to a "close enough" colour. This is most severe for the base `button` rule (930-953): both `background` and `border` are color-mix-only, so on an unsupported browser every non-primary button (Cancel, Sign out, filter Clear, copy-icon buttons, quiet buttons generally) would render with **no visible background wash and no border at all** — functional, but visually indistinguishable from plain text, which directly undermines the file's own stated D-01b intent ("near-invisible at rest, revealed on hover" — it would become *literally* invisible, not near-invisible). The task description asked specifically to check for this; it is present with no mitigation anywhere in the file.

**Fix:** Add a solid-colour fallback declared before the `color-mix()` line for `background`/`border` on the base `button` rule at minimum (the browser keeps the first valid declaration when the second is invalid):
```css
button {
  background: rgba(23, 25, 31, 0.045); /* fallback for browsers without color-mix() */
  background: color-mix(in srgb, var(--color-text) 4.5%, transparent);
  border: 1px solid rgba(23, 25, 31, 0.09);
  border: 1px solid color-mix(in srgb, var(--color-text) 9%, transparent);
  ...
}
```

### WR-03: `.filter-bar__field input:focus` uses `border-color: var(--color-accent)`, directly contradicting the file's own "Border is structural only ... never substitutes for the accent" contract

**File:** `companion/static/style.css:1452-1454` vs. the header contract at `companion/static/style.css:36-39`

**Issue:** The file's header states: *"Border is structural only ... It is never used as an interactive-state signal and never substitutes for the accent or status colours."* Yet `.filter-bar__field input:focus { border-color: var(--color-accent); }` (introduced this phase, D-08 / 06.6.4-05) does exactly both things it says never happens: it uses border colour as an interactive-state (focus) signal, and it substitutes the border colour for the accent colour. It is also not present in the file's separately maintained "kept exhaustive on purpose" accent-use list (lines 10-22), and `06.6.1-UI-SPEC.md`'s Color section still only lists "the focused-input outline" (not a focus border) as the sanctioned accent use for form controls — the header explicitly instructs "do not broaden this list without updating 06.6.1-UI-SPEC.md's Color section," which does not appear to have happened.

**Fix:** Either add this as a narrow, named exception to both the header comment and 06.6.1-UI-SPEC.md's Color section (matching the pattern already used for `.stat-tile__caption`'s serif exception), or bring the rule into compliance with the existing "focused-input outline" pattern instead of a border-color override:
```css
.filter-bar__field input:focus {
  outline: 2px solid var(--color-accent);
  outline-offset: 1px;
}
```

### WR-04: `test_contrast_check.py`'s live-pair suite is missing the dark-mode "primary-button label on accent fill" pair that light mode tests

**File:** `companion/test_contrast_check.py:116-132`

**Issue:** `live_pairs` includes 6 light-mode pairs (including `("light: primary-button label on accent fill", "#FFFFFF", "#B13F16")`) but only 4 dark-mode pairs, and none of the dark ones cover the equivalent primary-button-label pair (`--color-on-accent` `#151922` on `--color-accent` `#FF8A5C`). This is precisely the class of pair the module's own docstring warns can silently regress ("a token change here now fails a test, not a reading") — but for dark mode, a future change to `--color-on-accent` or `--color-accent` that broke primary-button-label contrast would ship undetected by this suite.

```python
        ("dark: primary-button label on accent fill", "#151922", "#FF8A5C"),
        ("dark: body text on card surface", "#F1F3F6", "#151922"),
    )
```
and bump `EXPECTED_CHECK_COUNT` from 33 to 34.

### WR-05: `_clear_control_shared_attribute_contract`'s CSS-rule regex only handles single-line selectors, silently truncating multi-line comma-grouped selectors

**File:** `companion/test_view_pages.py:796-814`

**Issue:** `re.finditer(r"\n([^{\n]*\{[^}]*\})", declarations)` requires the selector and `{` to occur on the same line (no `\n` allowed in `[^{\n]*`). `style.css` itself uses multi-line, comma-grouped selectors elsewhere in the same file (e.g. `a:focus-visible,\nbutton:focus-visible,\ninput:focus-visible,\nselect:focus-visible {` at lines 348-354, or `h1,\nh2,\nh3,\nlegend,\n.text-heading {`). If a future edit added a competing Clear-control rule as part of such a multi-line group (entirely plausible given this file's own conventions), the regex would only capture the *last* line of that selector list as `selector`, silently dropping the earlier lines from the check's view — undermining the very regression guard this test exists to provide. It currently passes only because no such rule happens to exist yet, not because the regex is robust.

**Fix:** Normalize whitespace before matching, e.g. collapse selector-list newlines first:
```python
declarations = re.sub(r"/\*.*?\*/", "", css, flags=re.S)
declarations = re.sub(r",\s*\n\s*", ", ", declarations)  # join multi-line selector groups
```

### IN-02: Six new hardcoded font-sizes introduced this phase (11px/12px/13px) depart from the file's declared "exactly 4 sizes" typography scale with no acknowledgment

**File:** `companion/static/style.css:626, 933, 1244, 1447, 1460, 1488`

**Issue:** The header block states "Typography scale: exactly 4 sizes, 2 weights" (`--font-label-size: 14px`, `--font-body-size: 16px`, `--font-heading-size: 20px`, `--font-page-title-size: 30px`). This phase adds six new bare pixel `font-size` declarations that match none of the four tokens: `.theme-form .theme-option` (13px), `button` (13px), `.data-table th` (11px), `.filter-bar__field input` (13px), `.filter-bar__count` (12px), `.filter-bar [data-filter-clear]` (12px) — confirmed new via `git diff` against this phase's base commit. Unlike other deliberate exceptions in this file (e.g. `.stat-tile__caption`'s serif treatment, explicitly called "a narrow, named exception — not a licence to extend serif to other Label text elsewhere"), none of these six carry a comment acknowledging the departure from the declared scale.

**Fix:** Either introduce named size tokens for the new density tier (e.g. `--font-micro-size: 12px`) and update the header's "exactly 4 sizes" claim, or add a short comment at each site (or once, near the scale definition) documenting this as a deliberate fifth tier for dense/quiet UI.

### IN-03: New `.data-table` cell padding (13px/10px) departs from the declared "multiples of 4" spacing scale with no acknowledgment

**File:** `companion/static/style.css:1250, 1280`

**Issue:** The header states the spacing scale is "multiples of 4" (`--space-xs: 4px` ... `--space-2xl: 48px`). `.data-table th { padding: 0 var(--space-md) 10px; }` and `.data-table td { padding: 13px var(--space-md); }` (both new this phase, D-07) use 10px/13px vertical padding, neither a multiple of 4 nor a declared token.
