# Phase 06.6.4 Plan 02: Button system density and hierarchy Summary

**`companion/static/style.css`'s button system shrinks from a uniform 44px filled block to a 30px semibold control with a lit primary action, near-invisible quiet actions, and a 28x28 icon button with a genuine synthesized 44x44 hit area — three tasks, one file, zero markup changes.**

## Performance

- **Duration:** 9 min
- **Started:** 2026-08-31T22:19:00Z
- **Completed:** 2026-08-31T22:28:25Z
- **Tasks:** 3
- **Files modified:** 1

## Accomplishments
- Base `button` rule dropped both `min-height`/`min-width: 44px` declarations (D-01's deliberate WCAG 2.5.5 AAA trade-off) and became a 30px, 13px-semibold, 6px-cornered control with a near-invisible `color-mix`-based wash and hairline border (D-01b's resting half)
- `button[type="submit"]` gained an inset top highlight plus a soft drop shadow at rest, a deeper pair on hover, and an explicit `border-color: transparent` neutralizing the new base hairline (D-01a)
- A single `button:active { transform: translateY(1px); }` rule gives every button — primary and quiet — a pressed state, placed before `button:disabled` so the disabled treatment still wins
- `.logout-form button` and `.dirty-bar__cancel` moved onto the same quiet wash plus `box-shadow: none` (so neither inherits the primary button's new inset highlight), and a new `button:hover` rule reveals a stronger wash/border for every quiet control, correctly source-ordered after both overrides
- A 44px floor register comment above the base `button` rule exhaustively lists which selectors gave up the floor this phase (text buttons, nav links, theme-picker segments, filter input) and which keep it (hamburger toggle, native input/select, disclosure summary), stating the WCAG 2.5.8/2.5.5 criterion the trade-off rests on
- `.copy-btn` became a 28x28 transparent glyph box with `border: none` and explicit flex centring, gaining a `::before { inset: -8px }` pseudo-element that synthesizes a real 44x44 pointer/touch target with no accessibility trade-off, plus its own 7% hover wash and a rewritten comment describing the new mechanism

## Decisions Made
- Resolved D-01b's and D-02's open "dark-mode analogue needed" questions with `color-mix(in srgb, var(--color-text) N%, transparent)` rather than a literal `rgba(255,255,255,.0NN)` value — this is the codebase's own established idiom (already used at `.sidebar-link--active`/`.banner`), is numerically equivalent to CONTEXT.md's light-mode figures, and needs no per-theme override block
- Kept the `.copy-btn` class name (no rename) — D-02 left the rename as a planner's call, and the lower-blast-radius option wins since `history_page.py`'s `_copy_button_html()` builder and the app's DOM-contract test guards already reference the name
- Placed the new `button:hover` quiet-reveal rule after both `.logout-form button` and `.dirty-bar__cancel` in source order. `.logout-form button` shares `button:hover`'s (0,1,1) specificity, so order genuinely decides the winner there. `.dirty-bar__cancel` is lower-specificity (0,1,0), so `button:hover` would already win regardless of order — but placing it after both anyway keeps the ordering rule simple and uniform to audit, rather than relying on that asymmetry between the two overrides

## Deviations from Plan

None — plan executed exactly as written. The comment I initially drafted for the `button:hover` placement rationale stated both quiet overrides share identical specificity with `button:hover`; on review this was only true for `.logout-form button` (0,1,1) — `.dirty-bar__cancel` is a bare single-class selector (0,1,0), strictly lower. Corrected the comment's wording before committing so it states the real specificity values rather than an inaccurate generalization; no CSS behavior changed, this was a comment-accuracy fix caught during the same task, not a separate deviation.
