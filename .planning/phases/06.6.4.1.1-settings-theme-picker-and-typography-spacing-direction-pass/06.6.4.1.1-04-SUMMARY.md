# Phase 06.6.4.1.1 Plan 04: Flash-slot move and serif-boundary guard closure Summary

**Flash confirmation banner now splices below `page_header()` via a single-definition marker token (D-17), and the serif-boundary contract test now catches plan 02's already-shipped D-09/D-13 CSS changes instead of silently tolerating them.**

## Performance

- **Duration:** ~30 min
- **Started:** 2026-09-04T06:44:00+02:00 (approx, from first commit's preceding work)
- **Completed:** 2026-09-04T06:48:06+02:00
- **Tasks:** 2
- **Files modified:** 2 (`companion/layout.py`, `companion/test_companion_app.py`)

## Accomplishments

- Saving on Settings (or any `page_header()` page) no longer shifts the page title down — the flash confirmation now renders in the conventional slot directly below the header, not above it.
- `FLASH_SLOT_MARKER`, a module-level, single-definition-site substitution token in `companion/layout.py`, is emitted by `page_header()` and consumed by `page_shell()`; an unconditional second `replace()` guarantees it can never reach the browser on any path (flash or no-flash, `page_header()` or fallback).
- Pages that never call `page_header()` (login, 404, and any future bare page) keep rendering the flash banner in the original before-body slot untouched — no such caller needed to change.
- The serif-boundary guard gap plan 02 quietly opened (retiring `.stat-tile__caption`'s serif Label role via D-13, and giving the nested card-title selector a sans override via D-09, neither caught by the existing two checks) is now closed: `_serif_never_reaches_dense_content()`'s forbidden list names `.stat-tile__caption`, and `_every_heading_role_is_serif()` asserts the nested card-title's `font-family: var(--font-ui)` exception by name.
- The negative-control experiment required by the plan's acceptance criteria was actually run: temporarily reintroducing serif on `.stat-tile__caption` makes the harness fail (143/144, exit 1); reverting restores 144/144, exit 0.

## Decisions Made

- Chose the marker-substitution mechanism over the two alternatives the plan itself weighed (a threaded `flash_html` parameter through every page module's `render()`, or a CSS `order`/flex trick on `<main>`): the marker is the only option that is both deterministic and confined entirely to `companion/layout.py`, matching the plan's own reasoning documented inline in the code comment.
- Placed `FLASH_SLOT_MARKER`'s definition immediately above `page_shell()` (its sole consumer) rather than grouping it with unrelated top-of-file constants, for locality with the one function that reads it.
- Task 2's guard extensions were done as in-place edits per the plan's stated preference, keeping `EXPECTED_CHECK_COUNT` unchanged rather than adding two more standalone checks.
