(D-17, UIR-25), and close a small design-system hygiene gap left open by plan 02.

Purpose: today `page_shell()` emits the flash banner before `body`, so every save on
Settings inserts a block above the `<h1>` and visibly shifts the page title down. Below
the header is the conventional slot and it removes the shift.

Output: a marker-slot mechanism in `companion/layout.py` plus harness coverage, and one
extended serif-boundary guard in `companion/test_companion_app.py`.

  <action>
  Add a module-level constant to `companion/layout.py`:

  `FLASH_SLOT_MARKER = "<!--flash-slot-->"`

  with a comment stating it has exactly one definition site, is emitted by `page_header()`
  and consumed by `page_shell()`, and is always removed before the response is returned —
  it is a substitution token, never markup that ships.

  Append `FLASH_SLOT_MARKER` to `page_header()`'s returned string, immediately after the
  closing `</div>`. Every authenticated page's body therefore carries exactly one marker,
  at the exact point D-17 wants the banner.

  In `page_shell()`, before the big interpolation, add:

  ```
  if FLASH_SLOT_MARKER in body:
      body = body.replace(FLASH_SLOT_MARKER, flash_html, 1)
      flash_html = ""
  body = body.replace(FLASH_SLOT_MARKER, "")
  ```

  and keep the existing `flash_html, banner_html, body` interpolation unchanged. Three
  properties follow, and all three belong in the code comment:
  - A page that DOES use `page_header()` gets its banner inside the body, right after the
    header block — the D-17 position.
  - A page that does NOT (login, and any future bare page) keeps today's before-body
    emission untouched, so no caller has to change and no page silently loses its banner.
  - The unconditional second `replace()` guarantees the marker never reaches the browser,
    including on the no-flash path where `flash_html` is `""`.

  Why a marker rather than the alternatives, for the comment: `page_shell()` receives
  `body` as one opaque pre-built string, so it has no structural handle on "just after the
  header". Threading a `flash_html` parameter through `page_header()` would touch every
  page module's `render()` for a shell-level concern. A CSS `order` trick would require
  making `<main>` a flex container, which would turn every top-level page element into a
  flex item and change margin collapsing across all five pages. The marker is the only one
  of the three that is both deterministic and confined to this module.

  Add harness checks in `companion/test_companion_app.py`, bumping
  `EXPECTED_CHECK_COUNT` with an inline arithmetic comment in the file's existing style.
  </action>

  <behavior>
  - For an authenticated page rendered with a flash: the rendered document contains
    `class="page-header"` and `banner--flash`, and the index of `banner--flash` is GREATER
    than the index of `</div>` closing the page header — i.e. the banner is below the
    title, not above it.
  - For the same page with no flash: no `banner--flash` appears, and the document is
    otherwise unchanged.
  - `FLASH_SLOT_MARKER` never appears in any rendered document, with or without a flash.
  - `page_shell()` called with a `body` that contains no marker still emits the flash
    banner (the login/404 fallback path).
  - An anomaly banner (`banner=`) is unaffected and still renders in its existing slot.
  </behavior>
