### Pattern 1: `_safe_query()` per-section DB isolation (health_page.py + airlines_page.py)

**What:** Both `health_page.py` (lines 211-222) and `airlines_page.py` (lines 85-94) define an identical-shaped `_safe_query(state_dir, fn)` helper that opens a fresh `history_db` connection, runs `fn(conn)`, and returns the `_DB_UNAVAILABLE` sentinel object instead of raising on `(sqlite3.Error, OSError)`.

**When to use:** Every DB read this phase's Health "Server & data" section performs — Pipeline-freshness, Corroboration, Resolution-rate, and the migrated Unresolved-prefixes/Resolution-statistics reads — must keep this per-query isolation. D-11 explicitly warns against merging these into `health_page.py`'s existing `_read_health_inputs()` single dict in a way that makes one query's failure take down sections that used to fail independently. `airlines_page.py`'s `unresolved_rows()` does NOT go through `_safe_query()` today (it reads `poll_state.json` via `poll_loop.load_poll_state()`, a different failure mode than SQLite) — this distinction must be preserved when the function moves.

**Example (health_page.py, current shape):**
```python
# Source: companion/pages/health_page.py lines 211-222 (verbatim)
def _safe_query(state_dir, fn):
    try:
        with history_db.open_db(state_dir) as conn:
            return fn(conn)
    except (sqlite3.Error, OSError):
        return _DB_UNAVAILABLE
```

### Pattern 2: Validate-then-join for any user-influenceable path segment

**What:** `companion/app.py`'s `_serve_runway_image()` (lines 699-715): membership test against a known-safe set happens BEFORE any path is constructed; an unknown id and a real-id-but-missing-file both produce the identical 404.

**When to use:** D-15's new illustration-serving route MUST follow this exact shape. Do not sanitize-then-join (regex-strip the input then build a path); validate membership against a set derived from `illustrations.target_filenames()` or the `_ILLUSTRATION_TARGETS` list, and only build a path with `illustrations.illustration_path_for_key()` (which has its OWN independent boundary check, `_UNSAFE_KEY_RE`, at line 585 — defense in depth, not a substitute for the route-level membership check).

**Exact code to mirror:**
```python
# Source: companion/app.py lines 699-715 (verbatim)
def _serve_runway_image(self, runway_id):
    if runway_id not in device_config.RUNWAY_IDS:
        return self.send_html(404, self._not_found_page())
    path = _runway_image_path(runway_id)
    try:
        with open(path, "rb") as fh:
            payload = fh.read()
    except OSError:
        return self.send_html(404, self._not_found_page())
    return self.send_bytes(200, "image/png", payload, cache_seconds=300)
```

The illustration route's version should use a filename/key (not an integer/enum-like `runway_id`), so the membership set should be built from `illustrations.target_filenames()` (returns full `.png` filenames — 43 entries today, including the 27 airlines' files, the 7 `generic-{shape}.png` files, and `generic-fallback.png`) filtered down to just what the gallery actually needs (arguably a narrower set: only the primary + variant files listed per airline in `_ILLUSTRATION_TARGETS`, not the generic fallbacks the gallery never shows) — OR simply reuse `target_filenames()` wholesale since it is already a closed, static, server-controlled list with `outstanding_filenames() == []` confirmed (verified live, see Summary). Either is safe; the narrower set is marginally more defensible under least-privilege but both close the actual threat (path traversal) identically, since neither ever interpolates the raw request into a path before the membership check.

### Pattern 4: `stat_tile()` vs full-width `page_section`/`battery-trend-section` card — the D-11 root cause

**What:** `companion/static/style.css`'s own `.stat-tile` rule (lines 1567-1576) carries this exact, load-bearing comment: *"`min-width: 0` is the first declaration and is load-bearing — a grid item's default minimum size is its content's intrinsic width, and the Battery-trend tile contains a `.data-table` carrying `min-width: max-content`... Without `min-width: 0` that intrinsic width propagates up and stretches the tile's whole dashboard-grid track far past the 240px floor, pushing sibling tiles off-grid and forcing horizontal scroll on the page itself."* This is the EXACT bug D-11 diagnoses for the old Airlines page's Unresolved-prefixes 5-column table forced into a `.stat-tile` grid column.

**When to use:** The Unresolved-prefixes/Resolution-statistics cards moving to Health's "Server & data" section must use the SAME full-width card class the Battery trend section already uses to escape this — `.page-section` (lines 1783-1807) or `.battery-trend-section` (lines 1709-1723), both already carrying the 06.6.4 hairline-at-rest/shadow-on-hover contract, both already outside `.dashboard-grid`. `.page-section` is the more generic/reusable of the two (used today for Settings' Poll section and Health's source-fault block); `.battery-trend-section` carries one deliberate omission (no hover lift/transform, since it holds an interactive chart) that doesn't apply to a static table card. **Recommendation: reuse `.page-section` verbatim for both migrated cards — zero new CSS needed.**

### Pattern 5: The gallery-grid CSS pattern already exists for the Airlines illustration cards

**What:** `companion/static/style.css` already defines `.gallery-grid` (line 1876) and `.gallery-tile` (used by `preview_page.py`'s `gallery_tiles()`) — a card-grid-of-thumbnails-with-caption pattern.

**When to use:** D-14's Airlines gallery (27 cards: illustration + name + fleet chips) is structurally close to this existing pattern (image + caption per tile) but needs a new modifier for the fleet-variant chips row — Claude's Discretion area covers exact breakpoints, but the base grid/tile CSS should be reused, not reinvented, per the "no new component patterns beyond what 06.6.4 already established" discretion note.

### Anti-Patterns to Avoid

- **Duplicating the Copy-{field} accessible-name pattern inconsistently:** `history_page.py`'s `_copy_button_html(value, label)` (lines 277-291) is the established "Copy {field}" contract (`_COPY_CALLSIGN_LABEL = "Copy callsign"`, etc.). If Health's new Resolution-rate tile or Airlines' filter needs a similar affordance, follow this exact shape (button + `data-copy-feedback` sibling span consumed by `copy-button.js`), never a bespoke clipboard implementation.
- **Re-deriving `_ILLUSTRATION_TARGETS` data in a second hardcoded list:** `target_airline_names()` (lines 708-724) and `target_filenames()` (lines 727-752) already de-duplicate/order-preserve from the single source-of-truth list. The gallery's fleet-variant chips must group `_ILLUSTRATION_TARGETS` entries by `airline_name` and collect non-`None` `shape` values per airline in-memory at render time — never a second hand-typed per-airline shape table.
- **Blending independently-failing DB reads into one dict without preserving per-section fallback:** see Pattern 1.

## Common Pitfalls

### Pitfall 1: Test files test BOTH old-Airlines-content and Health in the SAME file

**What goes wrong:** `companion/test_status_pages.py` (currently 1746 lines, `EXPECTED_CHECK_COUNT = 59`) is a single harness covering both `health_page.py` AND `airlines_page.py` (its own docstring, lines 1-17, explicitly names both modules' contracts). Moving the registry/stats tests to describe `health_page.render()` output instead of `airlines_page.render()` output, while ALSO adding entirely new assertions for the reborn Airlines gallery, all inside one file, risks losing track of which checks are "moved" (retarget in place, don't double-count) vs. "new" (do count) vs. "deleted" (the old Airlines page's iconless-tile check, its two-tile/Coverage-heading check — both already once retargeted for 06.6.3-06, per the file's own header comment at lines 66-70).

**Why it happens:** The file's own historical comment block (lines 56-70) shows this project's own established discipline for exactly this situation — every prior EXPECTED_CHECK_COUNT bump documents precisely which checks were "new" vs. "retargeted in place, not counted as new." This phase must follow the same discipline or the count will drift from the real check total.

**How to avoid:** When writing the plan's task-level `EXPECTED_CHECK_COUNT` guidance, explicitly instruct "compute the bump from the file's real starting count at execution time" (this project's own stated precedent, repeated in STATE.md across 6+ plan summaries) — never hardcode a predicted final number in the plan itself.

**Warning signs:** A plan that says "bump EXPECTED_CHECK_COUNT to N" with a literal final number, rather than "+M for new checks, recompute from the real starting count."

### Pitfall 2: `_serve_runway_image()`'s membership set is `device_config.RUNWAY_IDS` (3 short string ids) — the illustration route's set is 27-43 filename strings, a materially larger surface

**What goes wrong:** Runway ids are 3 short enum-like strings defined in `server/device_config.py`; illustration keys are derived from live airline names via `normalise_airline_key()` (accent-stripping, lowercasing, slug conversion) and can carry hyphens (multi-word airline names) and shape suffixes (`-a320`, `-a350-1000`). A route mirroring the pattern too literally might build the membership set from a live re-derivation of `normalise_airline_key()` at request time instead of the precomputed `target_filenames()` list — functionally similar but a second code path that could theoretically diverge (e.g., a future airline name change).

**Why it happens:** Reflexively "mirror `_serve_runway_image()`" could mean re-deriving membership from `device_config.RUNWAY_IDS`-equivalent (i.e., `illustrations.target_airline_names()`, then re-running `normalise_airline_key()` per request) instead of using the already-materialized filename list.

**How to avoid:** Build the illustration route's known-safe set ONCE at module load time (or per-request from a cheap function call — `target_filenames()` has no I/O, it's pure list comprehension over `_ILLUSTRATION_TARGETS`) via `illustrations.target_filenames()`, not by re-deriving slugs inline in `app.py`. Membership test the requested filename string directly against that set.

**Warning signs:** New `normalise_airline_key()`-adjacent logic appearing in `app.py` itself rather than a single call into `illustrations.py`.

### Pitfall 3: `companion/pages/__init__.py`'s "no page module imports another page module" boundary — does importing `server.plane.illustrations` from `companion/` cross a layering rule?

**What goes wrong:** Verified: `companion/pages/__init__.py`'s docstring documents ONE explicit boundary — no page module may import another page module (the reason `_read_health_inputs()`-style helpers live in `layout.py` when shared, and why `airlines_page.py`'s docstring reuses `STATS_UNAVAILABLE_TEXT` as a literal copy of Health's string "rather than importing companion.pages.health_page"). There is NO documented rule against a page module importing `server.*` — every existing page module already does this (`config_page.py` imports `server.device_config`/`server.panel_format`; `health_page.py` and `airlines_page.py` both import `server.history_db`/`server.poll_loop`; `history_page.py` imports `server.device_config`/`server.history_db`/`server.plane.render`). `server/plane/illustrations.py` is a peer module to `server/plane/render.py`, which `history_page.py` already imports for presentation-mapping reuse (`display_airline_name()`, `_TYPE_DISPLAY_LABELS`) — the exact same "reuse the panel's own presentation mapping so the web page and the panel never drift" precedent applies to `airlines_page.py` importing `illustrations.py`.

**Why it happens:** A cautious planner might assume "companion/ never imports server.plane.*" is a rule, by analogy to the page-to-page import ban, when no such rule exists in this codebase.

**How to avoid:** `airlines_page.py` importing `from server.plane import illustrations` is SAFE and matches established precedent — document this explicitly in the plan so a reviewer doesn't flag it as a boundary violation. `companion/app.py`'s new illustration-serving route handler will ALSO need `illustrations.illustration_path_for_key()` and `ILLUSTRATION_DIR` — `app.py` already imports `server.device_config`/`server.history_db`/`server.panel_preview`/`server.poll_loop`, so adding `server.plane.illustrations` is consistent.

### Pitfall 4: `_ILLUSTRATION_TARGETS`' shape field is NOT always a `SHAPE_SLUGS` member

**What goes wrong:** `SHAPE_SLUGS` (line 473-481) has exactly 7 members: `a320`, `b737`, `atr72`, `beechcraft1900d`, `embraer`, `a330`, `a350`. But `_ILLUSTRATION_TARGETS` contains a variant entry `("Air Caraïbes", "a350-1000", ...)` — `"a350-1000"` is NOT a `SHAPE_SLUGS` member (it's a distinct, more specific string used only for filename construction). A naive chip-rendering implementation that validates variant shapes against `SHAPE_SLUGS` before rendering a chip would silently drop the Air Caraïbes A350-1000 chip.

**Why it happens:** `SHAPE_SLUGS` is documented as the canonical 7-shape classification for `classify_aircraft_type()`'s ICAO-type-to-illustration mapping — a DIFFERENT purpose than `_ILLUSTRATION_TARGETS`' free-text shape labels used for filename suffixes. The two are related but not the same domain.

**How to avoid:** Render fleet-variant chips directly from each airline's own list of non-`None` `shape` strings in `_ILLUSTRATION_TARGETS` — do not filter or validate them against `SHAPE_SLUGS`. Confirmed actual per-airline variant shapes (grouping the real table): Air Corsica -> `atr72`; Transavia France -> `a320`; Royal Air Maroc -> `embraer`; Air Caraïbes -> `a330`, `a350-1000`, `atr72` (three variants, matching CONTEXT.md's own example verbatim); Amelia -> `embraer`; Air France Hop -> `atr72`.

### Pitfall 5: `layout.NAV_TABS` self-updating call sites vs. hardcoded-5 test literals

**What goes wrong:** Most of `companion/app.py`/`companion/layout.py`'s own logic derives its allowlists FROM `NAV_TABS` at runtime (`_validated_next_route()`'s `allowed = {route for route, _ in layout.NAV_TABS}`, `_referring_tab()`'s identical pattern, `_nav_links()`'s iteration) — these all silently adapt to whatever `NAV_TABS` becomes (4 entries instead of 5) with zero code change needed. But `companion/test_companion_app.py` has verified hardcoded literal tuples that will NOT self-adjust: line 1456-1460's `for _tab_path, _heading in (("/config", "Config"), ..., ("/preview", "Preview"))` five-tuple, and comment references to "all five NAV_TABS routes" at lines 1017/1150/1454 (comments only, but signal the code nearby assumes 5). `_PAGE_TITLES` in `app.py` (lines 185-191) is a separate, NOT-derived-from-NAV_TABS dict that must be hand-edited (drop the `/preview` entry, add/rename `/config` -> whatever title Settings ends up using).

**Why it happens:** `NAV_TABS` and `_PAGE_TITLES` are two independent sources of truth for route metadata that happen to have stayed in sync by discipline, not by construction.

**How to avoid:** The route-table plan (Wave 3, Plan E above) must grep for every literal 5-tuple/`("/preview"`/`"all five"` reference across `test_companion_app.py` and update each explicitly — do not assume `NAV_TABS`-derived logic covers everything.

### Pitfall 6: The Settings URL — `/config` route rename is UNSPECIFIED in CONTEXT.md

**What goes wrong:** D-13 is explicit that Airlines "reuses the same URL" (`/airlines`) — but no decision in `06.6.4.1-CONTEXT.md` states whether Settings' URL path changes from `/config` to `/settings` alongside its nav label/page-title rename. See Open Questions below — this is flagged, not resolved, by this research.

**How to avoid:** Default assumption (documented in Assumptions Log below) is that `/config` stays the URL (matching the low-risk, "reuse the route, change only presentation" pattern D-13 explicitly sets for Airlines) while the nav label, page `<title>`, and `<h1>` text change to "Settings." This keeps `/config-led`'s merge (D-05) simpler (still merging into `/config`, not a simultaneously-renamed route) and avoids a second redirect requirement CONTEXT.md never asked for. **This should be confirmed with the developer before planning locks it**, since a URL rename is a larger blast radius (bookmarks, `_PAGE_TITLES`, `_validated_next_route()`'s allowlist, `NAV_TABS` tuple's first element, every test's literal `"/config"` string — dozens of occurrences across all 4 test files).

### `_ILLUSTRATION_TARGETS` grouping for fleet-variant chips

```python
# NOT existing code -- the pattern the new airlines_page.py render() needs,
# derived from server.plane.illustrations._ILLUSTRATION_TARGETS's real shape
# (a flat list of (airline_name, shape_or_None, note) tuples, verified above).
from collections import OrderedDict
from server.plane import illustrations as ill

def _airline_variants():
    """One (airline_name, [variant_shape, ...]) pair per distinct airline,
    order-preserving -- mirrors target_airline_names()'s own de-dup discipline
    but also collects the non-None shape values as chip text."""
    grouped = OrderedDict()
    for airline_name, shape, _note in ill._ILLUSTRATION_TARGETS:
        grouped.setdefault(airline_name, [])

    return list(grouped.items())
```
