## Note on process

Unlike a typical discuss-phase session (a short menu of gray areas resolved via AskUserQuestion turns), this phase's design work happened over an extended prior session as an iterative sketch-and-review process: each page (or page-merge proposal) was built as a real, standalone HTML artifact using this project's actual CSS tokens and real page content, shown to the developer, revised based on live reaction, and re-shown until explicitly approved ("top", "c'est parfait", "c'est genial"). By the time this formal discuss-phase step ran, nearly every implementation decision was already locked through that process — this log captures the shape of that discussion, not a literal AskUserQuestion transcript for each item.

## Settings (renamed from Config) — single-column layout + unified save bar

**Trigger:** Live-browser reaction to the shipped Config page: "c'est catastrophique d'un point de vue UI et UX" — the Runway section's 2-column grid was visibly broken.

**Root cause found by reading code, not guessing:** `config_page.py`'s `runway_fieldset()` emits 5 flat top-level elements with no wrapper div, unlike `theme_fieldset()`'s correct `<div class="theme-status">` wrap.

**Iteration:** First two layout proposals (A: side-by-side preserved, B: Theme-compact-bar) both rejected — "Aucune des deux ne me va", developer wanted the full page in context, not isolated fragments. Redesigned as single-column stacked sections (matching Health/History/Airlines' existing pattern) — approved.

**Follow-up ask:** "ça manque d'une petite description de chaque paramètre" → per-section descriptions added.

**Follow-up ask:** Save-bar UX was "à moitié" (half-implemented) per-section — developer wanted a Discord-style single page-level bar. Real bug found in the process: `dirty-state.js` never hides the static no-JS fallback Save button.

**Selected:** Single-column stacked sections; one page-level Discord-style save bar naming which sections changed; LED form backend-merged into the same `/config` route as Theme+Runway (the old separate-route justification — avoiding an orphan row in the 2-column grid — no longer applies).

## Health — banner/battery content gaps

**Trigger:** "et le battery health?" — fresh-eyes look found no default numeric battery readout, no chart axes, value only revealed via forced interaction.

**Iteration:** First banner mockup replaced full-sentence anomaly text with short category pills. First Corroboration mockup deleted the 3 detail paragraphs entirely — developer caught this as information loss ("j'ai un son qui manque des informations"), corrected to a `<details>` disclosure instead (defer, don't delete).

**Chart iteration:** First chart proposal was validated ("c'est très joli") but flagged as missing real interaction — developer explicitly asked to inject real values and test the "View 5 readings" interaction directly, not just look at a static mockup. Then asked why not full page width — widened, approved ("top").

**Selected:** Category-pill banner; Corroboration behind `<details>`; full-width interactive chart with labeled axes, default latest-reading value, working hover/click/keyboard reveal.

## Health/Airlines merge

| Option | Description | Selected |
|--------|-------------|----------|
| Merge Airlines into History | Both are "flight identification" content | |
| Merge Airlines into Health | Both are system diagnostics, different subsystems | ✓ |
| Keep Airlines standalone, cross-link from Health | Avoids urgency/cadence mismatch (real-time vs slow-moving) | (superseded by developer's explicit framing below) |

**User's choice:** "Health peut contenir la partie Health de l'écran. Et health du serveur et des données." — explicit two-part framing (device/screen health vs. server/data health) that resolved the urgency-mismatch concern Claude had raised: not a flat merge, but two clearly labeled sections.

**Root cause confirmed by reading code:** Airlines' `resolution_stats()` (queries `history_db.route_source_counts()`, DB-backed) and `unresolved_rows()` (reads `poll_loop`'s registry JSON) are genuinely independent data sources — this is *why* "No resolution data yet" could legitimately sit above real Unresolved-prefixes data. The `.stat-tile { min-width: 0 }` CSS comment independently confirmed the nested-scroll bug's exact mechanism (a wide table forced into a narrow grid column) — the same class of bug D-02 already fixed for Health's own battery-trend chart pre-06.6.1.

**Follow-up ask:** "'52.6% resolved' pas dans une tuile à côté des deux autres ?" → promoted from a bare headline to a third stat-tile alongside Pipeline/Corroboration.

**Follow-up ask:** "Description des resolution statistic... seulement dans un hovering" → `white-space: nowrap` on every table cell was forcing the Description column into horizontal-scroll; fixed to wrap normally.

**Follow-up ask:** "Box de taille différente et elle devrait être alignée... Évitez aussi le scroll horizontal" → the two-column `resolution-grid` layout was replaced with a single-column stack (matching Battery trend's own full-width precedent) — this fixed both the alignment complaint and the horizontal-scroll complaint in one change, since a 2-column split was what caused both.

**Selected:** Two sections, "Screen" (Device tile + Battery trend) and "Server & data" (Pipeline/Corroboration/Resolution-rate tiles, then Unresolved-prefixes and Resolution-statistics as full-width stacked cards).

## History/Preview merge

| Option | Description | Selected |
|--------|-------------|----------|
| Keep Preview standalone, add a per-row link from History | Avoids merging two different "jobs" (live status vs. historical browsing) | |
| Fully merge Preview into History | Developer's explicit preference | ✓ |

**User's choice:** "je voulais que preview disparaisse" — full merge, not a cross-link.

**Technical grounding (verified before proposing):** Gallery filenames carry real ISO timestamps (`_save_to_gallery()`/`_gallery_name_to_iso()`), so a nearest-by-timestamp lookup from a History row to a gallery render is a render-time computation against already-available data, not a new stored relationship — confirmed feasible before committing to the design.

**Selected:** "Now showing" section at the top of History (live image + caveat), Recent-renders gallery demoted to a collapsed `<details>`, per-row lookup button opening a lightbox for the nearest render (tested live in the sketch, working click-to-open interaction).

## Airlines reborn as illustration gallery

**Trigger:** "ça aurait été sympa aussi d'avoir une onglet Airlines... afficher visuellement l'ensemble des compagnies... voir les avions en PNG."

**Correction during discussion:** Claude initially assumed no aircraft-illustration assets existed in the project and proposed either a manual drop-in-asset pattern or generated avatar badges. The developer corrected this directly: "Non, c'est faux. L'ensemble des photos des avions est disponible dans le projet." A repo search confirmed 43 real PNG illustrations already exist at `server/assets/icons/illustrations/`, with a complete, already-built selection module (`server/plane/illustrations.py`) used by the physical panel's own renderer.

**Selected:** Airlines nav slot and route reused (not removed) for a new gallery page — 27 airline cards, each with its real illustration PNG (served via a new route mirroring the existing `/runway-image/{id}.png` validate-then-join pattern), name, and fleet-variant chips; a filter bar. Validated with 8 real downscaled illustration thumbnails embedded in the sketch alongside placeholder cards for the rest.
