# Phase 06.6.4.1 Plan 07: Settings route rename to /settings + LED route retirement Summary

**Flipped Settings from the dormant `/config` path to the live, dispatched `/settings` route everywhere it is linked/titled/redirected (D-26), and retired the separate `POST /config-led` route together with `led_fieldset()`, `led_section()`, and `handle_led_post()` outright (D-05) — one settings route, one settings handler, no second settings-writing path reachable.**

## Performance

- **Duration:** ~40 min
- **Tasks:** 3/3 completed
- **Files modified:** 5 (`companion/app.py`, `companion/layout.py`, `companion/pages/config_page.py`, `companion/test_companion_app.py`, `companion/test_config_page.py`)

## Accomplishments

- `companion/app.py`'s route constant is now `SETTINGS_ROUTE = config_page.SETTINGS_ROUTE` (a rebind, not a re-typed literal, mirroring the existing `RUNWAY_IMAGE_ROUTE_PREFIX` precedent) — every dispatch site updated: `do_GET`/`do_POST` path comparisons, the login-authenticated redirect, the not-found page's back-link, `_referring_tab()`'s fallback, `_handle_login_post()`'s default, and all three of `_handle_poll_now()`'s redirect targets. `_validated_next_route()`'s docstring no longer states a literal route count, since the nav tuple changes again in plan 08.
- `companion/layout.py`'s `NAV_TABS[0]` and `NAV_ICON_IDS`' first key retargeted from `config`/`Config` to `settings`/`Settings`; the gear SVG symbol id (`icon-nav-config`) stays unchanged by name, per the plan (cosmetic churn UI-SPEC §5.0 marks optional) — the icon whitelist keeps its current membership.
- `companion/pages/config_page.py`'s `layout.page_header("Config")` call retargeted to `"Settings"` so the rendered `<h1 class="page-title">` agrees with the new route, nav label, and `<title>` — not explicitly named in the plan's Task 1 action text, but required by its own acceptance criteria and must_haves (documented as a deviation below).
- Deleted `LED_ROUTE`, its whole `do_POST` branch, and (in `config_page.py`) `led_fieldset()`, `led_section()`, and `handle_led_post()` outright — confirmed first, by reading `handle_post()`, that all three documented submitted-value shapes (absent → False, checked → True, anything else → reject-whole-submission) were genuinely implemented there (landed by plan 03). The retired path now falls through to the standard 404 — no new code, no new failure mode.
- Swept both harnesses this plan owns for any remaining hardcoded `/config`/`/config-led` literal (none found beyond the deliberate retired-path-404 checks themselves); confirmed by grep that `test_status_pages.py`/`test_view_pages.py` (not owned by this plan) carry no such literal.
- Added a standing contract guard, `_nav_page_titles_icon_route_standing_contract_guard()`, mirroring this file's existing three-file DOM-contract guards — asserts `NAV_TABS` and `_PAGE_TITLES` agree in length and key set, `NAV_ICON_IDS`' keys equal the nav slugs one-to-one, and `app.SETTINGS_ROUTE == NAV_TABS[0][0]`, so plan 08's own nav-route change fails loudly here instead of silently.
