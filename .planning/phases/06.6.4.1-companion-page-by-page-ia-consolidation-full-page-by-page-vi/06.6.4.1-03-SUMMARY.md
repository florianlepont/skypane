# Phase 06.6.4.1 Plan 03: Settings single-column consolidation + LED merge Summary

**Rebuilt Settings/Config as one merged `<form action="/settings">` with three wrapped, described, `data-dirty-section`-named sibling groups (Theme/Runway/Diagnostic LED), a section-naming unified save bar, and one all-or-nothing `handle_post()` that now absorbs LED validation — while leaving `led_fieldset()`/`led_section()`/`handle_led_post()` and the live `/config-led` route untouched for plan 07 to retire.**

## Performance

- **Duration:** ~35 min
- **Tasks:** 3/3 completed
- **Files modified:** 3 (`companion/pages/config_page.py`, `companion/static/dirty-state.js`, `companion/test_config_page.py`)

## Accomplishments

- Fixed D-01's actual root cause: `runway_fieldset()` used to return five flat top-level elements (an `<h2>`, N cards, a `<p>`, no wrapper) that broke once nested in a two-column grid. It's now wrapped in the same `.theme-status` container `theme_fieldset()` already used — reused verbatim, no new wrapper class.
- Added D-02's two new description sentences (Theme, Runway), each a `<p class="text-body">` directly under its group's heading; Diagnostic LED needed none — its existing `LED_HELPER_TEXT` already reads as one.
- Merged the LED control into the same form as Theme/Runway via a new `led_group()` function: no more separate `<fieldset>`/`<legend>`/independently-submittable `<form action="/config-led">` — all three groups now render as `<h2 class="text-heading">`-headed siblings at one consistent heading level, with zero `<fieldset>`/`<legend>` occurrences left in `render()`'s output.
- `handle_post()` now validates and persists theme, tracked_runway, and led_enabled together in a single `save_device_config()` call. Documented (not just implemented) the deliberate asymmetry: theme/runway absence means "leave unchanged" (radio/select semantics), while led_enabled absence means `False` (an unchecked HTML checkbox is omitted from the POST body entirely) — conflating the two would silently re-enable a disabled LED on every save.
- `dirty-state.js`'s save bar now names which section(s) changed ("Theme changed" / "Theme and Runway changed" / "Theme, Runway, and Diagnostic LED changed") via a new `dirtySectionLabels()` DOM walk over `[data-dirty-section]`, in document order, never a hardcoded label list — with a never-silent raw-count fallback if a differing field somehow sits outside every wrapper.
- Left `led_fieldset()`, `led_section()`, and `handle_led_post()` completely untouched, each with a one-line comment naming plan 07 as their removal site — `companion/app.py`'s separate `POST /config-led` route still dispatches to `handle_led_post()` and continues to work unmodified (`test_companion_app.py` passes 96/96, unmodified).

## Decisions Made

- `SETTINGS_ROUTE` is defined and used in `render()`'s form action now, but `companion/app.py` is deliberately NOT updated to route `POST /settings` in this plan — it still dispatches the old `/config` path, per the plan's own explicit key_links constraint. Plan 07 flips both the route and the LED-route retirement together. Verified this doesn't break the live end-to-end save flow: `test_config_page.py`'s own HTTP round-trip check posts to `/config` directly (not by parsing the form's action attribute), which continues to work since `app.py`'s `POST /config` handler still calls the now-extended `config_page.handle_post()`.
- `led_fieldset()`/`led_section()`/`handle_led_post()` left byte-for-byte untouched, exactly matching the plan's known pitfall — `render()` no longer calls either function, but neither is deleted, and `companion/app.py`'s live `POST /config-led` route continues to work against `handle_led_post()` unmodified.
- `led_group()` reuses the `.theme-status` class name verbatim rather than inventing a third wrapper class, matching D-01's explicit instruction that all three groups share one wrapping idiom (also means zero new CSS was needed — `git diff --quiet companion/app.py companion/layout.py companion/static/style.css` confirms no change to any of those three files).
