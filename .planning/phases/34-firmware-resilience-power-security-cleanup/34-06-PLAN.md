exactly as specified here so 34-09 only changes internals.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| server responses -> device | Status codes and JSON bodies are untrusted |
| device flash (secret partition) -> network | The enrolment secret leaves the device only inside the TLS-protected setup request |
| build configuration -> URL policy | CONFIG_SKYPANE_ALLOW_HTTP decides whether plaintext is possible |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-34-06-01 | Spoofing | enrolment | mitigate | Per-device secret from the secret partition; server checks it against the registry (plan 34-03) |
| T-34-06-02 | Information Disclosure | secret / token handling | mitigate | Secret and request body zeroed on every path; bodies of non-200 responses never logged; no credential in any log line |
| T-34-06-03 | Tampering | plaintext downgrade | mitigate | http:// base -> FP_ERR_CONFIG and http:// image_url -> FP_ERR_HTTP_JSON unless CONFIG_SKYPANE_ALLOW_HTTP; CI proves production has it off (plan 34-04) |
| T-34-06-04 | Denial of Service | 401 handling | mitigate | Token erased only on 401/403 from /display; a transient 5xx keeps the token; re-enrol happens after normal backoff, so a hostile 401 cannot cause a hot loop |
| T-34-06-05 | Denial of Service | sleep_s from server | mitigate | fp_sleep_s_parse caps at 86400 (FW-04) |
| T-34-06-06 | Tampering | secret partition | mitigate | Application never erases or writes the secret partition; init errors are reported, not "repaired" by erasing |
| T-34-06-07 | Repudiation | failure diagnosis | mitigate | Distinct sentinels map to distinct step tokens (auth, enrol, secret, config) |
</threat_model>
