- **P5 — Deployment currently runs from the developer's laptop** using their personal SSH access, per `deploy/README.md`. CI needs its own credential. Reusing the personal key would mean revoking CI access and the developer's own access together, and would give a cloud runner a key that likely opens more than this one host.

<task type="auto">
  <name>Task 2: Create the repository, the deploy credential, and the approval gate — before pushing</name>
  <files></files>
  <read_first>
    - `.github/workflows/ci.yml` from plan 04-04 — the exact environment name and the exact three secret names it references. These must match character for character; a mismatched secret name yields an empty string rather than an error.
    - Plan 04-04's SUMMARY — it records those names explicitly for this task.
    - `deploy/README.md` — the SSH login model on this host (direct root, or a user with passwordless sudo), which determines the shape of the SSH target and where the CI public key must be installed.
  </read_first>
  <action>
    Do all of this **before** the first push. Creating the repository empty, configuring its protections, and only then pushing means there is never a window in which the default branch exists without its gate.

    **Create the repository.** Public (D-02), under the authenticated account, with a description drawn from the README's opening line. Do not let the creation step generate a README, licence, or ignore file — all three already exist locally and a generated one would conflict with the first push.

    **Mint a dedicated deploy credential (P5).** Generate a new keypair used for nothing but this deployment. Install its public half in the appropriate account's authorized_keys on the production host, following the login model `deploy/README.md` documents. Verify it works by running a harmless remote command with that key and nothing else in the agent — the key must be proven to work before CI depends on it, because a deploy failing on authentication inside a gated job is an unpleasant place to discover a typo. Do not reuse the developer's personal key: a dedicated key is revocable on its own, and limits what a cloud runner holds.

    **Create the three repository secrets**, named exactly as the workflow references them: the private half of the new keypair, the SSH target string, and the production host's expected public host key. Take the host key from the host itself over a connection you have already authenticated, not from an unauthenticated scan. Never paste any of these values into a shell history, a commit, or a log — pipe from a file or use the CLI's stdin input, and remove any temporary file afterwards.

    **Create the environment and attach the gate.** Create the deployment environment under the exact name the workflow declares, and add the developer as a required reviewer. This protection rule is the whole of D-11 — without it the workflow's environment declaration is decorative and the deploy runs unattended. Optionally restrict the environment's deployment branches to the default branch, which makes the workflow's own branch condition belt-and-braces.

    **Verify the configuration matches the workflow** rather than trusting that it does: read back the environment and confirm it has at least one required reviewer, and read back the secret list and confirm all three referenced names are present. Compare against the names parsed out of the workflow file itself, so a rename on either side is caught here rather than mid-deploy.
  </action>
  <verify>
    <automated>R=$(gh repo view --json nameWithOwner,visibility,isPrivate -q '.nameWithOwner+" "+.visibility') &amp;&amp; echo "repo: $R" &amp;&amp; gh repo view --json isPrivate -q '.isPrivate' | grep -qx false &amp;&amp; ENV=$(grep -A2 -E '^[[:space:]]*environment:' .github/workflows/ci.yml | grep -oE 'name:[[:space:]]*[A-Za-z0-9_-]+' | head -1 | awk '{print $2}') &amp;&amp; test -n "$ENV" &amp;&amp; gh api "repos/{owner}/{repo}/environments/$ENV" -q '.protection_rules[] | select(.type=="required_reviewers") | .reviewers | length' | grep -qE '^[1-9]' &amp;&amp; for s in $(grep -oE 'secrets\.[A-Z0-9_]+' .github/workflows/ci.yml | cut -d. -f2 | sort -u); do gh secret list --json name -q '.[].name' | grep -qx "$s" || { echo "MISSING SECRET: $s"; exit 1; }; done &amp;&amp; echo REPO_CONFIG_OK</automated>
  </verify>
  <acceptance_criteria>

    - Every secret name referenced in `ci.yml` exists in the repository's secret list — checked by parsing the names out of the workflow file, not from memory.
    - The environment named in `ci.yml` exists and has at least one required reviewer attached.
    - The dedicated CI key is proven to authenticate to the production host by a successful remote command run with only that key loaded, and its public half appears in the target account's authorized_keys.

    - The repository was created without a generated README, licence, or ignore file.
  </acceptance_criteria>

  <action>
    Push, then prove each gate actually gates. A pipeline that has only ever been observed passing has not been tested; D-09 and D-11 both describe blocking behaviour, and blocking behaviour is only real once it has been seen to block.

    **Push.** Add the remote and push the default branch. Confirm the push is accepted and the commit count on the remote matches local.

    **Prove CI goes green.** Watch the triggered run to completion and confirm the test job succeeded — lint, all 9 harnesses, the coverage threshold, and the attribution check. Confirm from the run's own log that 9 harnesses reported, not merely that the job exited zero: the whole reason D-07's file list was stale is that a silently short list looks identical to a correct one.

    **Prove CI blocks.** On a throwaway branch, open a pull request carrying a change that must fail — the smallest thing that trips the linter is enough. Confirm the run fails and that the pull request reflects a failing check. Then confirm the deploy job did **not** appear in that run at all, which is the observable proof that a pull request cannot reach the deployment credentials. Close the pull request and delete the branch. Do not merge it.

    **Prove the firmware workflow behaves.** Confirm it did not run for a change touching no firmware file, which is the path restriction working. Then trigger it with a trivial firmware-affecting change and confirm the containerised build succeeds and produces an image.

    **Prove the deploy gate holds.** On the push to the default branch, confirm the deploy job entered a waiting state rather than running — query the run's pending deployments and confirm one is awaiting review. That the job pauses is the machine-checkable half of D-11 and must be confirmed programmatically. Then approve it as the reviewer, and confirm the deploy job runs, `deploy/deploy.sh` completes, and the production services come back healthy by the checks `deploy/README.md` documents. Confirm the run log contains no secret value.

    If the deploy fails for an infrastructure reason rather than a workflow reason, fix the infrastructure and re-run rather than weakening the workflow — the gate design is not the thing under question at that point.
  </action>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| local history → the public internet | The first push is irreversible in effect: third parties may archive whatever it contains within minutes. |
| GitHub Actions runner → production VPS | The runner holds a key granting shell access to the host serving a physical device. |
| untrusted contributor → repository automation | A public repository accepts pull requests from anyone, and its workflows decide what those runs can reach. |
| repository configuration → workflow behaviour | The approval gate lives in repository settings, not in the reviewed workflow file. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-04-06-01 | Information Disclosure | Pushing a history that reintroduced a scrubbed literal in a document added after Wave 1 (P4) | high | mitigate | Task 1 re-runs the scrub verification against the current tree immediately before the push and blocks on a non-zero count; nothing is pushed until it passes |
| T-04-06-02 | Information Disclosure | Publishing the entire `.planning/` tree without ever looking at what it exposes beyond the named literals (P3) | medium | mitigate | Task 1 includes a deliberate publication-surface review with a human confirmation before the push, and routes anything found back through plan 04-01's scrub mechanism rather than a follow-up commit |
| T-04-06-03 | Elevation of Privilege | Giving a cloud runner the developer's personal SSH key (P5) | high | mitigate | A dedicated keypair is generated for this purpose alone, installed on the host, and proven to authenticate on its own before CI depends on it; an acceptance criterion requires the personal key not be used |
| T-04-06-04 | Repudiation | The environment declared in the workflow but never created, silently degrading the approval gate to no gate | high | mitigate | Task 2 creates the environment and verifies at least one required reviewer is attached, reading the environment name out of the workflow file itself; Task 3 then observes the pause programmatically on a real run |
