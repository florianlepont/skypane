<planner_findings>
Established live during planning.

- **D1 — There is no README at the repository root**, and none of the four existing ones (`server/`, `deploy/`, `stub-server/`, `adsb-test/`) covers the project as a whole. `firmware/` has no README at all — only `VENDOR.md` — so the root README has to carry the firmware build-and-flash path itself rather than delegating it.
- **D2 — The material to point at already exists and is good.** `hardware/BOM.md` is the bill of materials. `hardware/BRINGUP-LOG.md` records real first-light behaviour including a diagnosed non-bug worth warning a newcomer about. `firmware/build.sh`'s header comment documents its own usage and explains why flashing is deliberately a host-native step rather than a containerised one. `deploy/README.md` is the full VPS runbook. D-15 asks for a README that lets someone build and deploy from scratch — that means orienting and sequencing these, not restating them.
- **D3 — Six top-level directories exist**: `adsb-test/`, `deploy/`, `firmware/`, `hardware/`, `server/`, `stub-server/`. Both existing READMEs use a "what each file/directory does" table; the root README's version of that table is what tells a reader which of the six they need for the task at hand.
- **D4 — The stale architecture document is genuinely stale.** `.planning/research/ARCHITECTURE.md` dates from 2026-08-04, before any code existed, and describes generic domain patterns rather than this system. D-16 is explicit that it is reference material, not something to republish.
- **D5 — The adsb.fi attribution is absent from every public-facing surface** (confirmed in plan 04-03's findings, L7). The README's data-sources section is where it becomes visible; COMPLIANCE.md is where it is explained.
- **D6 — Every command this README will recommend has been executed during planning and works**: the clean-venv setup from `server/requirements.txt` on both Python 3.11 and 3.14, all 9 harnesses green, and the aggregate runner from plan 04-02. Nothing here is aspirational, and the acceptance criteria require it stay that way.
</planner_findings>

    Cover the three subsystems the decision names, each grounded in the files that implement it and naming them so a reader can verify every claim:

    - **Device firmware.** The wake-poll-display-sleep cycle as a state machine: what happens on each wake, which of the three protocol endpoints are called in what order, how the image hash short-circuits an unnecessary panel refresh, what persists in non-volatile storage across a full power loss, and how exponential backoff behaves when the server is unreachable. Note the measured panel full-refresh duration, because it is a real constraint on how often refreshing is worth doing.

    - **Server render pipeline.** The path from an aggregator response to a panel image: geofenced detection, the deterministic multi-aircraft selection rule, departing-versus-arriving inference from vertical rate with its deadband, enrichment for airline and route with its persistent cache that stores misses as well as hits, then composition — typography, the dithered background, illustration selection with its generic fallback — and finally the panel encoding the device downloads. Be specific about which decisions are deterministic and which have a designed fallback state, because the fallbacks are load-bearing rather than rare: route enrichment misses roughly half the time for this airport's traffic mix, so the unavailable-route render is a first-class state.

    - **Deployment topology.** What runs on the production host and how the pieces fit: the service and timer units, the reverse proxy terminating TLS, where state lives, how the device authenticates, and how the deploy script updates it all. Refer to the host by placeholder only.

    Include a diagram of the end-to-end data flow from aggregator to glass. Keep it in plain text or fenced ASCII so it renders anywhere and stays diffable.

    Close with a short section on the deliberate constraints that shaped the design and would otherwise look like omissions: battery-only operation with no wall power or solar, a poll-only device that never accepts inbound pushes, a single view in v1 with the RER view deferred, and no freshness or stale-data indicator. These were choices; record them as choices with their reasons, drawing on `.planning/PROJECT.md`.
