<planner_findings>
Established live during planning. Two of these correct stale claims in this phase's own input documents.

- **L1 — `server/assets/icons/illustrations/VENDOR.md` already exists.** 04-CONTEXT.md's canonical-refs section says it "still doesn't exist," and 04-PATTERNS.md lists it as a flagged gap to fill. Both are stale: the file is present and substantial, with a provenance summary, per-file digests, local modifications, and a coverage note. This plan **verifies** it, and does not recreate it.
- **L2 — There is a real attribution gap, but it is a different one.** `server/assets/fonts/VENDOR.md`'s Inter entry states that "the full OFL 1.1 text is vendored alongside the upstream release archive's own `LICENSE.txt`." No such file exists. The directory contains `PTSerif-OFL.txt` and `ZillaSlab-OFL.txt` but **no OFL text for Inter**, while `Inter-Regular.ttf` and `Inter-Bold.ttf` are both still committed. OFL 1.1 requires the copyright and licence notice to travel with the font files, so the notice is currently incomplete for that family — and VENDOR.md asserts otherwise. This is exactly the kind of thing D-14 item 3's "verify completeness" exists to catch.
- **L3 — Inter is retained but no longer loaded.** Phase 3 replaced it with Zilla Slab; `grep` finds no reference to `Inter-` anywhere in `server/*.py` or `server/plane/*.py`. VENDOR.md already documents this supersession and the deliberate decision not to delete the files. Retention does not reduce the OFL obligation — the files are still distributed.
- **L4 — Full asset inventory (22 files, all currently named in some VENDOR.md):** three font families plus two OFL texts under `fonts/`; `aircraft-silhouette` and the `plane-takeoff`/`plane-landing` pairs (SVG + PNG each) under `icons/`; eight airline/fallback PNGs under `icons/illustrations/`.
- **L5 — PRIM/IDFM and AeroDataBox are genuinely absent from shipped code.** A case-insensitive grep across `server/` and `stub-server/` for either name, and for `iledefrance`, returns nothing. This independently confirms 04-RESEARCH.md's assumption A4. `server/plane/detect.py` reaches exactly two aggregators, plus `server/plane/enrich.py`'s callsign lookup against adsbdb.
- **L6 — adsbdb.com is a fourth data source that none of the phase documents name.** `server/plane/enrich.py` queries it on every enrichment attempt for airline and route data. D-14 enumerates three APIs; this one ships in the code and therefore belongs in the compliance document alongside them.
- **L7 — The adsb.fi attribution is genuinely absent.** Grep across all non-`.planning/` markdown finds mentions of the aggregators only in internal engineering notes (`adsb-test/RESULTS.md`, `adsb-test/README.md`, `server/fixtures/README.md`) — never as a citation, never with a link to their home page, and there is no public-facing README at all yet. 04-RESEARCH.md's Pitfall 4 is confirmed by inspection.
- **L8 — The airplanes.live terms could not be read.** 04-RESEARCH.md records two automated fetch attempts of their API guide, both returning HTTP 403, and flags the resulting characterisation as secondary-source-only. The developer has a clarification email pending with them. This stays an open item.
