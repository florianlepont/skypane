<planner_findings>
Established live during planning.

- **W1 — `actionlint` is installed on this machine** at `/opt/homebrew/bin/actionlint`. Workflow YAML can therefore be validated for real — schema, expression syntax, embedded shell, and action-reference shape — without pushing anything. Use it; do not settle for a plain YAML parse.
- **W2 — The clean-venv recipe is proven.** A virtualenv created from scratch and installed from `server/requirements.txt` alone runs all 9 harnesses green, on both Python 3.11 and Python 3.14. CI has no hidden dependency on the developer's local virtualenv, and the interpreter version is not a risk.
- **W3 — Cross-workflow job dependencies do not exist.** 04-RESEARCH.md's "Recommended Project Structure" shows `ci.yml` and `deploy.yml` as separate files with the deploy job depending on CI success, but a job in one workflow cannot declare a dependency on a job in another. The only cross-workflow mechanism is a workflow-run trigger, which evaluates against the default branch's workflow definition and carries well-known context pitfalls. 04-RESEARCH.md's own working code skeleton, by contrast, puts both jobs in one workflow with an ordinary dependency — that is the shape to build. The firmware build is genuinely independent and does belong in its own file.
- **W4 — `firmware/build.sh` already wraps the exact toolchain.** It runs the pinned `espressif/idf:v5.3.1` image in Docker with the two-file sdkconfig defaults and a separate build directory. Docker is preinstalled on GitHub-hosted Linux runners. Calling this script directly therefore resolves 04-RESEARCH.md's Open Question 2 and Assumption A2 outright: there is nothing to verify about a marketplace action's parameter mapping, because no marketplace action is involved, and the CI build is identical to the local one by construction.
- **W5 — The firmware build needs a credentials header that is deliberately never committed.** `firmware/main/secrets.h` is gitignored. `firmware/main/secrets.example.h` is tracked and defines the same four symbols — verified during planning by comparing the defined symbol names in both files. Copying the example into place before building yields a compile-only image with placeholder values: enough to prove the code compiles, incapable of connecting anywhere.
- **W6 — The 9-file list and the coverage threshold live in plan 04-02's artifacts**, not in workflow YAML. CI must call `scripts/run-all-tests.sh` and let `pyproject.toml` supply the threshold. Restating either in YAML reintroduces exactly the drift that made D-07's list go stale in the first place.

  <action>
    Add a deploy job to `.github/workflows/ci.yml`, ordered after the test job so a failing pipeline can never deploy. W3 explains why this belongs in the same file rather than a second workflow.

    Gate it three ways, all of which must hold:
    - It depends on the test job succeeding.
    - It runs only when the event is a push and the ref is the default branch. It must never run for a pull request — a forked pull request able to run this job would be a route to the deployment credentials.
    - It declares a named deployment environment. That declaration is what makes GitHub pause the job for a required reviewer before any of its steps execute (D-11). Plan 04-06 creates the environment and attaches the reviewer; the YAML side is this declaration. Add a comment in the workflow saying exactly that, because a reader seeing only this file cannot otherwise tell that the gate depends on repository configuration living elsewhere — and a missing environment silently degrades the gate to no gate at all.

    Steps:
    - Check out the repository.
    - Load the deployment SSH private key from an encrypted repository secret into an agent, using the pinned SSH-agent action 04-RESEARCH.md identifies. Use the agent rather than writing the key into a workspace file — the whole point of that action is that the private key never lands somewhere a later step can read.
    - Establish the host key. Do **not** scan the target's key at deploy time and trust whatever answers; that is trust-on-first-use on every single run and accepts an impostor host silently. Instead take the expected host key material from its own repository secret and write it into the known-hosts file. This is a deliberate hardening over 04-RESEARCH.md's Pattern 2, which reaches for the scan.
    - Invoke `deploy/deploy.sh` with the SSH target drawn from a secret. That is the entire deploy action. Do not add file-sync steps, do not add service restarts, do not add a dependency install — every one of those already exists inside the script, tested and working, and duplicating them is what D-12 forbids.

    Three secrets are referenced, and each is a separate secret rather than one value later steps slice apart: the private key, the SSH target, and the expected host key. Separate secrets are each masked independently in logs, whereas a substring derived from a larger secret is not masked and would print in the clear.

    Never print a secret's value in a run step, even though recognised values are masked — masking is a backstop, not the control.

    Re-validate the whole file with `actionlint` once the job is added.
  </action>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| untrusted pull request → CI runner with repository context | Anyone may open a pull request against a public repository; the workflow definition decides what their code can reach. |
| CI runner → production VPS | The deploy job holds a private key granting shell access to the host serving a physical device. |
| third-party action → workflow with secret access | Every referenced action executes with the job's permissions and environment. |
| workflow YAML → public repository | Workflow files are world-readable the moment the repository is published. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-04-04-01 | Elevation of Privilege | Deploy job reachable from a pull-request event, exposing deployment credentials to untrusted code | high | mitigate | Deploy job conditioned on push events on the default branch only; verification greps for that condition and the SUMMARY must state explicitly that the pull-request trigger cannot reach it |
| T-04-04-02 | Tampering | Third-party action pinned to a mutable branch, letting an upstream change run inside this repository | high | mitigate | Every action reference pinned to a released version tag; all three tasks' verifications fail on a mutable branch reference |
| T-04-04-03 | Spoofing | Deploy connecting to an impostor host because the host key is scanned and trusted at deploy time | high | mitigate | Host key supplied from a dedicated repository secret and written to known-hosts; host-key scanning explicitly prohibited and grep-verified absent |
| T-04-04-04 | Information Disclosure | Production hostname or address baked into a world-readable workflow file, undoing plan 04-01's scrub | high | mitigate | All three host-bearing values come from secrets; both files are grep-verified to contain no dotted-quad address and no production hostname |
| T-04-04-05 | Information Disclosure | The deployment private key written into the workspace or printed in a log | high | mitigate | Key loaded into an agent by the pinned SSH-agent action rather than written to a file; no step prints a secret value; three separate secrets so no unmasked substring is ever derived from a larger one |
| T-04-04-06 | Tampering | Deploy logic drifting from `deploy/deploy.sh` because it was reimplemented in YAML | medium | mitigate | The only deploy action is invoking the script; verification fails if any file-sync or service-management command appears in the workflow |
| T-04-04-07 | Repudiation | A production deployment happening with no human decision and no audit record | high | mitigate | Named deployment environment declared on the job, which pauses for a required reviewer; plan 04-06 attaches the reviewer and verifies the pause actually occurs before the phase closes |
| T-04-04-08 | Repudiation | The environment declared in YAML but never created, silently degrading the gate to nothing | high | mitigate | A comment in the deploy job records the dependency on repository configuration; plan 04-06 has an explicit acceptance criterion that the job is observed pausing for approval on a real run |
| T-04-04-09 | Information Disclosure | Real device credentials entering the firmware build | low | mitigate | The build uses the tracked placeholder template; the real header stays untracked, and a clean `git status --porcelain` is an acceptance criterion |
| T-04-04-10 | Tampering | The ESP-IDF container image supplying the firmware toolchain | low | accept | Image is pinned to an exact vendor-published version tag inside `firmware/build.sh`, already in use for every local build since Phase 1; CI introduces no new trust here |
</threat_model>
