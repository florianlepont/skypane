# Phase 15 — UI Design Contract

> Visual and interaction contract for the Settings-page additions this phase ships: a checkbox-revealed arrivals theme override, and a per-flight colour-rules editor (add form + list + delete). Generated by gsd-ui-researcher, verified by gsd-ui-checker. Authoritative source of decisions: `15-CONTEXT.md` (D-01..D-13). This spec does not re-litigate any locked decision — it specifies the *shape* those decisions take in markup, copy and CSS.

## Design System

| Property | Value |
|----------|-------|
| Tool | none — hand-written, build-step-free, stdlib-only Python HTTP app |
| Preset | not applicable |

## Section Anatomy

### 1. Theme group (existing section, extended — no new heading, no new caption)

```html
<div class="theme-status" data-dirty-section="Theme">
  <h2 class="text-heading">Theme</h2>
  <p class="text-label section-caption">{THEME_SECTION_CAPTION, unchanged}</p>

  <div class="theme-chip-grid">
    <!-- 18 chips, name="theme" — byte-identical to today's markup -->
  </div>

  <label class="settings-checkbox">
    <input type="checkbox" name="theme_arriving_enabled" value="on"{checked if theme_arriving is set}>
    Use a different theme for arrivals
  </label>

  <p class="text-label theme-direction-label">Arrivals theme</p>
  <div class="theme-chip-grid theme-chip-grid--arrivals" data-arrival-grid>
    <!-- 18 chips, name="theme_arriving" — same chip markup, second radio group,
         pre-selected on the effective arrivals theme (theme_arriving if set,
         else the same theme_id the departures grid has selected) -->
  </div>
</div>
```

Why the label above the revealed grid, and not above the first grid too: before the checkbox exists there is exactly one grid and it needs no label (unchanged today). Once revealed, two grids sit in sequence and the checkbox text between them already disambiguates the first ("Theme" heading + "Use a different theme for **arrivals**" reads naturally as "the grid above is departures/default, the grid below is arrivals") — adding a second "Departures" label would be a control-density regression `sketch-findings-skypane` would flag (an extra line of chrome the checkbox's own wording already makes redundant). Only the revealed grid gets the "Arrivals theme" label, because it is the one grid whose purpose is not otherwise self-evident from what's already on the page.

### 2. Rules section (new — its own `.page-section`, own heading, own single caption)

```html
<section class="page-section">
  <h2 class="text-heading">Per-flight colour rules</h2>
  <p class="text-label section-caption">{RULES_SECTION_CAPTION}</p>

  <!-- Add form: its own POST route, immediate action, outside #settings-form -->
  <form method="post" action="/settings/rules/add" class="rule-add-form">
    <div class="rule-add-form__field">
      <label for="rule-kind">Match by</label>
      <select id="rule-kind" name="rule_kind" required>
        <option value="callsign">Callsign</option>
        <option value="hex">ICAO24 hex</option>
        <option value="prefix">Callsign prefix</option>
      </select>
    </div>
    <div class="rule-add-form__field">
      <label for="rule-key">Value</label>
      <input type="text" id="rule-key" name="rule_key" maxlength="8" required autocomplete="off">
      <p class="text-label section-caption">{RULE_VALUE_HINT}</p>
    </div>
    <div class="rule-add-form__field">
      <label for="rule-theme">Theme</label>
      <select id="rule-theme" name="rule_theme_id" required>
        <!-- 18 <option> entries, THEME_IDS order, labels via device_config.theme_label() -->
      </select>
    </div>
    <button type="submit">Add rule</button>
  </form>

  <!-- List: empty state OR cards (<960px) + table (>=960px), mirroring
       airlines_page._manual_resolutions_section_html()'s exact pairing -->
  {empty_state OR (data-cards then data-table-wrap, in that DOM order)}
</section>
```

**Placement note — an explicit, HTML-validity-driven deviation from a literal reading of D-10, flagged for the planner to confirm rather than silently resolved.** D-10 says the editor lives "under the Theme group." The Rules section's add-form and each row's delete form are real `<form>` elements, and HTML forbids nesting a `<form>` inside another `<form>` — so the Rules section cannot be a literal descendant of `<form id="settings-form">` (which wraps Theme through Display today). Two ways to honour D-10 while respecting that constraint:

- **Recommended (lower risk, zero change to existing groups' markup):** render the Rules `<section>` immediately after `</form>` closes and the dirty-bar markup, in the same slot the Poll section currently occupies — i.e., Rules becomes the first thing after the whole settings-form block, and Poll moves to be the section after it. This keeps every existing group (Theme, Runway, LED, Quiet hours, Wake interval, Display) byte-identical in its DOM nesting; only the top-level ordering of sections after the form changes.
- **Alternative (literal adjacency to Theme, higher-touch):** shorten `<form id="settings-form">` to wrap only the Theme group, and give every other group's inputs (`tracked_runway`, `led_enabled`, the three quiet-hours fields, `wake_interval_s`, `display_enabled`) an explicit `form="settings-form"` attribute so they still submit with the one shared form despite no longer being its DOM descendants — this is not a new idiom; it is the exact technique the dirty-bar's own Save/Cancel buttons already use to submit a form they are not nested inside. This achieves literal "Rules sits directly below Theme, before Runway" adjacency at the cost of touching every group emitter's markup.

This spec recommends the first option as the default; the planner should confirm which one ships, since it is a real structural choice with a real (if small) blast radius, not a purely cosmetic one.

The Rules `<section>` carries **no** `data-dirty-section` attribute — it is not part of the tracked settings form, exactly like the existing Poll section, whose add/trigger action is likewise immediate and un-tracked by the dirty bar.

## Reveal Mechanism (checkbox → second chip grid, CSS-only, no JavaScript)

**Mechanism:** progressive enhancement via `@supports selector(:has(*))`, matching this codebase's own already-established pattern for the exact same class of problem (quick task 260904-bbi's live `:has(input:checked)` selected-card state, documented in `references/control-density.md`). No JavaScript is written or required.

```css
/* Phase 15 D-05: the arrivals-override reveal. The second grid is
 * unconditionally visible (both grids always rendered, per D-05's own
 * "must always be present in the HTML" requirement) unless :has() is
 * supported, in which case it is hidden until the checkbox is checked.
 * A browser without :has() support simply always shows both grids —
 * denser, never broken, never dependent on script. */
@supports selector(:has(*)) {
  .theme-status:has(#theme-arriving-toggle):not(:has(#theme-arriving-toggle:checked))
    [data-arrival-grid],
  .theme-status:has(#theme-arriving-toggle):not(:has(#theme-arriving-toggle:checked))
    .theme-direction-label {
    display: none;
  }
}
```

(The `:has(#theme-arriving-toggle)` outer guard scopes this rule to the Theme card specifically, so the same `[data-arrival-grid]` attribute selector can never accidentally match an unrelated future component — belt-and-braces, not strictly required with today's single consumer.)

**Why `:has()` here rather than the plain sibling-checkbox-hack (`input:checked ~ target`):** the plain hack requires the `<input>` to be a preceding sibling of the revealed content, which means it cannot be nested inside `<label class="settings-checkbox">` — the exact wrapping idiom every other checkbox on this page uses (`led_group()`, `quiet_hours_group()`, `display_group()`). Breaking that nesting for one checkbox, just to enable a plain sibling selector, would be the "invented one-off idiom" this spec is supposed to avoid. `:has()` lets the checkbox stay nested in `.settings-checkbox` exactly like its three siblings, at the cost of needing the `@supports` gate — a cost this codebase has already decided is acceptable once, for the selected-card mechanism, and is choosing to accept a second time here rather than diverge the checkbox markup.

**Focus and keyboard behaviour.** The checkbox is a native `<input type="checkbox">` inside a native `<label>` — it receives focus in normal tab order (no `tabindex` manipulation), and `Space` toggles it exactly as any checkbox does. Checking it re-flows the following content in place (the `[data-arrival-grid]` block appears/disappears via `display`, not an animated transition — this codebase adds no motion to any state change of this kind, and `prefers-reduced-motion` is therefore not implicated). Once checked, the 18 radios inside the newly-visible grid become reachable in natural document order on the next `Tab` press — no focus is programmatically moved into the revealed content, matching this app's existing no-JS-required-for-correctness floor.

**What a screen reader announces.** Exactly what a native, unmodified checkbox announces: "Use a different theme for arrivals, checkbox, not checked" (or "checked"). No `aria-expanded` or `aria-controls` is added — this is deliberate, not an oversight: the reveal is real layout content becoming present/absent, not a collapsible-disclosure widget (`<details>`/`<summary>`, which this app does use elsewhere and which own `aria-expanded` semantics natively), and this app already has a precedent for a checkbox gating always-relevant-but-conditionally-meaningful content with no extra ARIA (`quiet_hours_group()`'s Start/End time fields, which stay in the DOM and in the tab order regardless of the enable checkbox's state, with no `aria-*` wiring either). Adding `aria-controls` here without a matching precedent elsewhere in the app would be a new, isolated pattern; this spec chooses consistency with the existing checkbox-gating precedent over textbook-perfect ARIA that nothing else in the app uses.

## Rules List Shape

**Desktop (`>=960px`): `.data-table-wrap` / `.data-table`**, structurally identical to `_manual_resolution_table_html()` — same wrapper class, same `<thead>`/`<tbody>` shape, same `row`/`row-alt` computation (inert markup only, per the retired-zebra-striping contract — striping itself is not rendered, the class is kept for parity with every other table on the site).

| Kind | Key | Theme | Added | (delete) |
|------|-----|-------|-------|----------|
| Callsign | `AFR1234` (mono) | ● White | 06:12 UTC (3d ago) | [Delete] |

## Add-Form Shape and Validation Feedback

Three fields, one submit button, laid out as a column stack on every viewport (no side-by-side arrangement) — matching this codebase's already-stated register: "the developer chose the sober option every time a denser one was offered." A three-field inline row would also be the first horizontally-arranged settings form on the page (every existing group is a single control or a vertical stack), which is exactly the kind of new layout pattern this spec should not introduce without a stronger reason than "it would fit."

1. **Match by** — native `<select name="rule_kind">`, three options (Callsign / ICAO24 hex / Callsign prefix), no default pre-selected blank option (the first listed option, Callsign, is the implicit default — mirrors every other `<select>` on this page, none of which uses a blank placeholder option).
2. **Value** — `<input type="text" name="rule_key" maxlength="8" required autocomplete="off">`, with a `.section-caption`-styled hint line directly beneath it (`RULE_VALUE_HINT`) rather than relying on a `placeholder` — a placeholder disappears the instant the user starts typing and this codebase's own convention is a persistent caption for anything the user needs to reference more than once. `maxlength="8"` is a generous outer bound (covers the longest of the three shapes with margin) — not a per-kind constraint, because a single text input serving three different key kinds cannot express a per-kind `pattern` or `maxlength` without JavaScript to swap it when the kind selector changes, and this phase adds no JavaScript. **No `pattern` attribute is set** — the server is the single source of truth for per-kind format validation (mirrors `config_page.handle_post()`'s existing "the write path reports errors, never silently coerces" discipline), so an HTML5 constraint-validation false rejection can never block a legitimately-formatted value the field's `pattern` guessed wrong.
3. **Theme** — native `<select name="rule_theme_id">`, 18 `<option>` entries in `THEME_IDS` order with `device_config.theme_label()` text, no swatch inside the `<option>` (native `<select>` cannot render inline coloured chips without JavaScript or a full custom-select rebuild — out of scope, D-11 explicitly calls for "a native `<select>`," not a styled one).

**Validation feedback is exclusively the server round-trip + flash message** — there is no client-side inline validation beyond the browser's own native `required` handling (an empty submit is blocked by the browser before it ever reaches the server, standard behaviour, no extra markup needed). A malformed value that passes `required` but fails the kind-specific format check redirects back to Settings with `rule_key_invalid`'s flash message (see Copywriting Contract) — the same shape every other form on this page already uses (`config_page.handle_post()`'s `FLASH_SAVE_FAILED`, `airlines_page`'s `FLASH_MANUAL_NAME_*` family). Do not add a JavaScript-driven inline error message; it would be the first client-side form-validation script in this codebase.

**Legibility of "this replaced an existing rule" (D-09).** The add route's result determines which of two flash keys fires: `rule_added` (no prior rule existed for that exact `(kind, value)`) or `rule_replaced` (one did, and this submission overwrote it) — see the Flash Messages table above. This is the entire UI surface D-09 requires; no separate confirmation dialog, no highlighted row, no "undo" affordance is added, matching the sober register and the "no confirm-before-mutate" precedent this app's one existing delete flow already sets.

## Control Density — reused classes vs. genuinely new rules

**Reused verbatim, zero modification:**
- `.theme-status`, `.theme-chip-grid`, `.theme-chip`, `.theme-chip__preview`, `.theme-chip__body`, `.theme-chip__name`, `.theme-chip__swatches`, `.theme-chip__dot`, `.theme-chip__check` — the second grid is a second instance of the exact same chip markup, not a variant.
- `.settings-checkbox` — the arrivals-override checkbox uses this class exactly like Diagnostic LED/Quiet hours/Display's checkboxes; no new checkbox treatment.

- `.page-section`, `.data-table-wrap`, `.data-table`, `.data-cards`, `.data-card`, `.data-card__primary`, `.data-card__secondary`, `.data-card__label`, `.data-card__value`, `.cell-primary`, `.mono` — the rules list is a third consumer of the exact table/card-list pairing History and Airlines' manual-resolutions section already established, at the exact same `>=960px` breakpoint via the exact same `.data-cards ~ .data-table-wrap` sibling-combinator toggle.

## Accessibility Floors

- **Focus visibility.** Every new interactive element (the checkbox, both `<select>`s, the text input, Add rule, each Delete button) is a native form control or native button — the existing global `:focus-visible` outline rule (already covering every such element site-wide) applies with zero new CSS. No custom-styled control that could lose focus-ring coverage is introduced.
- **Touch-target register.** See Control Density above — no new entry, no new trade. The checkbox is 44px via its wrapping label (relocated category); native `<select>`/`<input>` keep the 44px floor (kept category); buttons are 30px/36px (already-accepted AAA trade, AA-compliant).
- **Contrast against the accent-reservation contract.** Nothing new consumes accent, so nothing new needs a contrast check against the accent hue. The theme swatch dots are drawn at each theme's real panel colour (`_palette_hex()`), exactly as the existing single-theme status row and every theme chip already render them — no new contrast obligation, since this is the same swatch mechanism already shipped and already exempt from the UI's own text-contrast requirements (a decorative colour indicator, always paired with the theme's text label, never colour-alone — matching `_manual_superseded_marker_html()`'s "never colour alone" convention, which this row already satisfies via the adjacent label text).
- **Colour is never the sole signal.** The rules list's Kind column and the "replaced vs added" flash distinction are both carried in text, never in colour alone — consistent with the codebase-wide convention cited above.
- **No motion.** The checkbox reveal is an instant `display` toggle, not a transition or animation — nothing here needs a `prefers-reduced-motion` guard because nothing here moves.
- **Screen-reader legibility of the reveal.** Covered in the Reveal Mechanism section above — native checkbox semantics only, no custom ARIA, matching the Quiet-hours-fields precedent for "a checkbox that gates the relevance, not the presence, of already-visible-or-visible-content."
- **Native `required`/`maxlength` on the add form** provide baseline browser-level feedback for empty submission before any server round-trip is needed — not a substitute for the server-side format check, but a first line that prevents the most common accidental-empty-submit case with zero extra markup.
