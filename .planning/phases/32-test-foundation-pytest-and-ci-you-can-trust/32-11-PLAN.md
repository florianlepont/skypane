<planner_findings>
- `companion/app.py:_handle_poll_now()` (~3286-3325) calls `poll_loop.run_once(state_dir=..., geofence=self.args.geofence)` in-process; any exception → flash `poll_failed`, success → `poll_triggered`. `detect.poll_current_aircraft()` catches only `(requests.RequestException, ValueError)`, so under the guard alone (no fake provider) a provider call raises `SocketConnectBlockedError` / `NetworkAccessBlocked` (RuntimeError) → `poll_failed` → the existing check "a first poll trigger redirects with the poll_triggered flash key" fails. The fake provider is therefore required, not optional, once the guard is on.
- With the default fake responses (empty aircraft lists) run_once completes a no-flight cycle; adsbdb is not called when no flight is detected. `detect.DEFAULT_PROVIDER_ORDER = ("adsbfi", "adsblol")`, so both are queried.
- `detect.MIN_SECONDS_BETWEEN_CALLS = 1.1` still applies in the child (sitecustomize does not zero it). Keep it that way: `_poll_now_concurrent_requests_serialize_on_the_lock` needs run_once to last long enough for two requests to overlap; the live network used to provide that latency, the 1.1 s pacing sleep now does. If that check becomes flaky, report it rather than adding sleeps to production code.
- `Harness.start()` (~1249-1262) builds `env = dict(os.environ)` then sets `env[auth.PASSWORD_ENV_VAR]`; `Harness.tmpdir` is the app's state dir; `Harness.stop()`/`cleanup()` remove it.
- `_InProcessHarness` (~1302) runs companion/app.py's server in a thread of the harness process; the check at ~11770-11800 ("a calendar save immediately followed by a manual poll trigger...") POSTs /poll-now to it, so run_once runs in the harness process itself.
- `/poll-now` checks today: `_poll_trigger_first_call`, `_poll_trigger_cooldown_same_session`, `_poll_trigger_cooldown_second_opener`, `_poll_trigger_failure_uses_distinct_flash_key` (nonexistent geofence → poll_failed, still correct under the fake), `_poll_now_concurrent_requests_serialize_on_the_lock`, and the in-process calendar one.
- The harness's `EXPECTED_CHECK_COUNT` is reassigned many times in its header; the LAST assignment (~line 904, currently 319) is the one enforced.
- Other companion harnesses also start companion/app.py children and may do DNS for calendar URLs (they fake `socket.getaddrinfo` in-process via `_fake_public_hostname`) or post notifications (ntfy.sh URLs appear around ~11463-11537). Once the shim passes `child_env()`, any check that silently depended on the real network will now fail loudly — that is the point.
</planner_findings>
