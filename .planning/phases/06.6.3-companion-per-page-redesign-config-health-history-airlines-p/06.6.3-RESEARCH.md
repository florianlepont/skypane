## Summary

This phase is almost entirely an *internal-codebase* research problem, not an external-library one: the whole companion service is stdlib-only Python (`html`, `datetime`, `sqlite3`, `json`) rendering HTML strings, plus two existing ES5 vanilla-JS files (`battery-trend.js`, `nav-dropdown.js`) with an established, well-documented convention (`"use strict"` IIFE, `getElementById`/`querySelectorAll`, no framework, no build step). The UI-SPEC (`06.6.3-UI-SPEC.md`) already resolved almost every open design question — this research's job was to verify its claims against the real code and surface the handful of places where the actual code disagrees with the UI-SPEC's assumptions, plus fill in concrete implementation shapes for the six specific questions raised.

**Two corrections to carry into planning, found by reading the real code (not assumed):**

1. **History's `confirmed_state` raw values are `"departing"`/`"arriving"`, not `"on_runway"`/`"approaching"`/`"departed"`** as the audit (UXA-05) and UI-SPEC's copy table both state. `server/plane/runway_config.py`'s `STATE_DEPARTING = "departing"` / `STATE_ARRIVING = "arriving"` are the only two non-`None` values `infer_runway_config()` ever returns, and `history_db`'s `confirmed_state` column is written directly from that value (`server/poll_loop.py:772`). The presentation-label mapping the planner writes must map `"departing"` → `"Departing"`, `"arriving"` → `"Arriving"`, and anything else (including the empty-string default `history_page.format_event_row()` already substitutes for a falsy value) through the UI-SPEC's own documented fallback: title-cased, underscore-stripped rendering of the raw value. Do not implement the audit's literal `on_runway`/`approaching`/`departed` labels — they describe a state model this codebase does not have.
2. **`data_table()`'s escaping trap (which the UI-SPEC flags for Health's battery table) also affects Airlines' unresolved-prefix table**, once D-09's `concise_timestamp_html()` is applied to its First seen/Last seen columns (UI-SPEC's own Airlines section requires this). That makes 2 of the 3 live `data_table()` call sites need "already-safe markup in a cell" support, which tips the right fix from "hand-roll a third table" (History's existing precedent) to "extend `data_table()` with a small opt-in raw-column parameter" — see Code Examples below.

**Primary recommendation:** Implement D-20 filtering as pure client-side JS with zero server/route changes (confirmed against `companion/app.py`'s actual `do_GET` — there is no `?q=` handling anywhere and none is needed); implement D-07/D-08's disclosures as bare native `<details>`/`<summary>` with no CSS open/close animation (the target browser floor cannot animate `height: auto` without either JS or Chrome-only `interpolate-size`, and D-19's motion-polish decision does not require animating disclosures); extend `layout.data_table()` with a `raw_columns=()` parameter rather than a third hand-rolled table function; and extend `battery-trend.js` in place with a roving-tabindex `keydown` handler that reuses the file's existing `reveal()`/event-registration pattern verbatim.

## Architectural Responsibility Map

This is a single-tier server-rendered application (Python HTTP handler → HTML string → browser), with a thin browser-side progressive-enhancement layer. There is no SSR/CSR split, no API/backend split, and no CDN — every "tier" below is really "server-rendered Python" vs. "browser-side vanilla JS enhancement."

| Capability | Primary Tier | Secondary Tier | Rationale |
|------------|-------------|----------------|-----------|
| Dirty-state save bar (D-03) | Browser/Client (JS) | API/Backend (existing POST `/config`) | Visual affordance only; actual persistence always goes through the existing server-side `config_page.handle_post()` validation — JS never bypasses or duplicates it |
| Read-only Theme swatch (D-04) | API/Backend (Python render) | — | Swatch hex values are derived server-side from `panel_format.PALETTE_RGB`; zero client-side computation |
| Runway selectable cards (D-05) | Browser/Client (native HTML radio + CSS) | API/Backend (markup/selected-class) | Selection itself is a native `<input type="radio">`; the `--selected` visual class is computed server-side from the current value (never a CSS `:has()` trick — target browser floor not assumed) |
| Battery roving-tabindex chart (D-13) | Browser/Client (JS, extends `battery-trend.js`) | API/Backend (SVG markup, one point tabbable) | Keyboard model is pure client-side DOM/attribute manipulation over already-rendered SVG points; no new data fetch, no new server computation |
| History/Airlines filtering (D-20) | Browser/Client (JS, `list-filter.js`) | API/Backend (`data-filter-text` attrs, pre-lowercased server-side) | Confirmed against `companion/app.py::do_GET` — no `?q=` query param exists or is needed; entirely client-side over rows already in the DOM |
| Copy-to-clipboard (D-23) | Browser/Client (JS, `copy-button.js`) | — | Browser Clipboard API / `execCommand` fallback; no server round-trip of any kind |
| Native disclosures (D-07 mobile card, D-08 readings table) | Browser/Client (native HTML, zero JS) | API/Backend (markup) | `<details>`/`<summary>` is browser-native disclosure semantics; the server only decides *what* markup goes inside |
| Freshness/stale banner (D-12) | Browser/Client (JS, one-shot/deferred check) | API/Backend (server-computed severity, never recomputed client-side) | Client only toggles visibility of an already-server-rendered, `hidden`-by-default banner; must never independently recompute Health's `ok`/`warn`/`error` verdict (UXA-13's explicit constraint, already honored by `health_page.py`'s single-computation design) |
| Gallery caption timestamp (D-22) | API/Backend (Python, filename → ISO reversal) | — | The gallery filename → ISO parse (see Pitfall 2 below) happens server-side inside `preview_page.gallery_tiles()`, not in JS |

### Pattern 1: New static JS file wiring (matches `nav-dropdown.js`'s exact precedent)

**What:** Every new static JS file needs a route constant, a path constant, a `_serve_*_script()` method (or reuse the shared `_serve_script_file()`), a pre-auth `do_GET` branch, and a `<script src="..." defer>` tag emitted from `layout.py`.
**When to use:** For each of `dirty-state.js`, `list-filter.js`, `copy-button.js`, `freshness.js`.
**Example (from the real, shipped `nav-dropdown.js` wiring, `companion/app.py`):**
```python
# Source: companion/app.py:87-98, 585-627, 728-729 (this project's own code)
NAV_SCRIPT_ROUTE = "/static/nav-dropdown.js"
_NAV_DROPDOWN_JS_PATH = os.path.join(_STATIC_DIR, "nav-dropdown.js")

def _serve_script_file(self, abs_path):
    # shared body — reuse this for all 4 new files, do not write 4 new methods
    try:
        with open(abs_path, "rb") as fh:
            payload = fh.read()
    except OSError:
        return self.send_html(404, self._not_found_page())
    return self.send_bytes(200, "text/javascript", payload, cache_seconds=300, public=True)

def _serve_nav_dropdown_script(self):
    return self._serve_script_file(_NAV_DROPDOWN_JS_PATH)

# in do_GET(), BEFORE any require_session() gate — matches SCRIPT_ROUTE's own precedent:
if path == NAV_SCRIPT_ROUTE:
    return self._serve_nav_dropdown_script()
```
`layout.py`'s `page_shell()` already emits exactly one `<script src="%s" defer>` for `nav-dropdown.js`; a second, analogous `<script>` tag per new file needs to be added to `page_shell()`'s template (all four are needed on every authenticated page, since `dirty-state.js`/`list-filter.js`/`copy-button.js`/`freshness.js` all early-return via guard clauses on pages that don't need them — matching `battery-trend.js`'s and `nav-dropdown.js`'s own "served to every page, no-ops when its marker is absent" convention, confirmed in both files' header comments). Do not conditionally include scripts per-page — that would be a second thing to keep in sync with which page needs which script.

### Pattern 3: `data_table()` extended with an opt-in raw-column mode (this phase's concrete fix for Research Question 4)

**What:** `layout.data_table()` currently unconditionally calls `escape_html(cell)` for every cell (`companion/layout.py:959`), which double-encodes `concise_timestamp_html()`'s pre-built `<span title="...">` markup and prints the literal tags as visible text. Confirmed this affects **two** live call sites once D-09 lands, not one:
  1. `health_page.py::_battery_section()`'s Timestamp column (the case the UI-SPEC already flagged).
  2. `airlines_page.py::_registry_section()`'s First seen/Last seen columns (UI-SPEC's own Airlines section says these "switch to `concise_timestamp_html()`" but its "Integration note" only analyzed the Health case — this is the gap this research closes).

**When to use:** Any `data_table()` cell that must render pre-built, already-safe HTML instead of plain escaped text.
**Recommended fix — extend, don't hand-roll a third table:**
```python
# Source: companion/layout.py:939-969 (current code, showing the minimal diff)
def data_table(headers, rows, mono_columns=(), raw_columns=()):
    """... existing docstring ...

    `raw_columns` (new) names zero-based column indices whose cell value
    is ALREADY-SAFE, pre-built HTML (e.g. concise_timestamp_html()'s
    <span title="..."> output) and must be interpolated verbatim — the
    same "caller has already escaped/built this" contract stat_tile()'s
    content_html parameter uses. Do not put the same column index in both
    mono_columns and raw_columns' escaping behavior — mono_columns only
    controls the <td> CSS class, orthogonal to raw_columns' escaping
    bypass, but concise_timestamp_html()'s own <span class="mono"> makes
    a redundant mono_columns entry unnecessary for that specific case.
    """
    if not rows:
        return empty_state("No data yet.", "Nothing to show here yet.")
    header_cells = "".join("<th>%s</th>" % escape_html(h) for h in headers)
    body_rows = []
    for row_index, row in enumerate(rows):
        row_class = "row-alt" if row_index % 2 else "row"
        cells = []
        for column_index, cell in enumerate(row):
            cell_class = ' class="mono"' if column_index in mono_columns else ""
            cell_html = cell if column_index in raw_columns else escape_html(cell)
            cells.append("<td%s>%s</td>" % (cell_class, cell_html))
        body_rows.append('<tr class="%s">%s</tr>' % (row_class, "".join(cells)))
    return (
        '<div class="data-table-wrap"><table class="data-table">'
        "<thead><tr>%s</tr></thead><tbody>%s</tbody></table></div>"
    ) % (header_cells, "".join(body_rows))
```
Both existing call sites (`airlines_page.py`'s two `data_table()` calls) pass zero args for the new parameter by default (`raw_columns=()`), so this is fully backward-compatible — no existing call site's rendered output changes.

**Call-site changes required:**

### Pattern 4: Roving tabindex extension of `battery-trend.js` (Research Question 3 — concrete shape)

**What:** Left/Right/Home/End across the existing per-point SVG circles, reusing the file's own `reveal()` and per-point event-registration conventions.

```python
for index, (value, ts) in enumerate(pairs):
```

**`battery-trend.js` extension — one new function plus one new listener per point, added inside the existing per-point IIFE loop (do not write a second loop):**
```javascript
// Source: extends companion/static/battery-trend.js's existing structure (lines 42-105)
function moveFocusTo(index) {
  // Clamp, not wrap — matches D-13's chosen "no wrap" contract at both ends.
  if (index < 0) { index = 0; }
  if (index > points.length - 1) { index = points.length - 1; }
  for (var j = 0; j < points.length; j++) {
    points[j].setAttribute("tabindex", j === index ? "0" : "-1");
  }
  points[index].focus();   // .focus() fires the EXISTING "focus" listener below,
                            // which already calls reveal(point) — no duplicate call needed.
}

// Inside the existing `for (var i = 0; i < points.length; i++) { (function (point) { ... `
// IIFE loop, alongside the existing click/mouseenter/focus/keydown(Enter/Space) listeners:
point.addEventListener("keydown", function (evt) {
  var currentIndex = Array.prototype.indexOf.call(points, point);
  if (evt.key === "ArrowRight" || evt.key === "ArrowDown") {
    evt.preventDefault();
    moveFocusTo(currentIndex + 1);
  } else if (evt.key === "ArrowLeft" || evt.key === "ArrowUp") {
    evt.preventDefault();
    moveFocusTo(currentIndex - 1);
  } else if (evt.key === "Home") {
    evt.preventDefault();
    moveFocusTo(0);
  } else if (evt.key === "End") {
    evt.preventDefault();
    moveFocusTo(points.length - 1);

  // matching the file's own convention of one listener per concern.
```

### Pattern 5: Native `<details>`/`<summary>` composition (Research Question 1)

**What:** How `<details>` composes with the existing `data_table()`/hand-rolled-table and `stat_tile()` output, and the concrete styling gotchas.
**Findings:**
- `<details>` is a generic flow-content container — it composes cleanly around **any** existing block markup (`data_table()`'s `<div class="data-table-wrap"><table>...`, or History's hand-rolled `<dl>`/`<dt>`/`<dd>` detail region). No collision with `.data-table-wrap`'s own `overflow-x: auto` — that rule applies inside the `<details>` exactly as it does anywhere else.
- No existing `style.css` rule targets `details`/`summary` at all (`grep` confirmed zero matches) — this is a clean slate, not a collision-risk area.
- **44px hit-target floor:** the global `button`/`input`/`select` 44px rule does **not** apply to `summary` (it is not a form control) — a new, explicit rule is required: `summary { cursor: pointer; min-height: 44px; display: flex; align-items: center; }`, exactly as the UI-SPEC already specifies.
- **Marker styling cross-browser gotcha (verified via MDN + community sources):** `summary::marker` is the standard pseudo-element (Chrome/Firefox support it fully), but **Safari does not support `::marker` on `<summary>` specifically** (it supports `::marker` on `<li>` but not `<summary>`) — a parallel non-standard `summary::-webkit-details-marker` rule is required for Safari/iOS to get any marker styling at all. `[CITED: github.com/Fyrd/caniuse, blog.logrocket.com]`. The UI-SPEC's own CSS guidance ("style `summary::marker` (and the `::-webkit-details-marker` fallback)") is correct and should be implemented as literally two rules, not one:
  ```css
  summary::marker { color: var(--color-accent); }
  summary::-webkit-details-marker { color: var(--color-accent); }
  ```
- **Animating open/close is NOT reliably possible with plain CSS across this project's target browser floor.** Animating to `height: auto` has historically required either JS or the CSS Grid `0fr`↔`1fr` trick; the modern zero-JS `interpolate-size` property (which *does* let `<details>` animate through `::details-content`) currently has **Chrome-only** support. `[CITED: nerdy.dev/open-and-close-transitions-for-the-details-element, blog.logrocket.com]`. **Recommendation: do not attempt to animate `<details>` open/close at all this phase.** This is not a regression against D-19 (motion polish) — D-19's own decision text names only "the mobile menu's existing height/opacity transition" as needing a reduced-motion path; it does not mandate animating every new disclosure, and animating `<details>` correctly would require either a new JS file (contradicting the UI-SPEC's explicit "zero-new-JS disclosures" choice) or an inconsistent-across-browsers CSS-only trick. An un-animated snap-open/closed `<details>` is the correct, lowest-risk choice.

## Common Pitfalls

### Pitfall 1: Trusting the audit's/UI-SPEC's literal `confirmed_state` values
**What goes wrong:** Implementing UXA-05's presentation-label mapping literally (`on_runway` → "On runway", `approaching` → "Approaching", `departed` → "Departed") produces a mapping dict whose keys never match any value the database actually contains.
**Why it happens:** The audit's evidence section describes values from either an earlier iteration of this codebase or a misreading; `server/plane/runway_config.py`'s `infer_runway_config()` — the only function that ever produces a `confirmed_state` value written to `history_db` — returns exactly `"departing"`, `"arriving"`, or leaves the prior value unchanged (never `"on_runway"`/`"approaching"`/`"departed"`).
**How to avoid:** Map `"departing"` → `"Departing"`, `"arriving"` → `"Arriving"`; use the UI-SPEC's own documented fallback (title-cased, underscore-stripped raw value) for anything else, including the empty string `history_page.format_event_row()` already substitutes when the column is falsy.
**Warning signs:** A regression test asserting `"On runway" in rendered` for synthetic test data seeded with `confirmed_state="on_runway"` — that test would pass against wrong code and wrong data simultaneously; seed test fixtures with `"departing"`/`"arriving"` instead, matching real `history_db` rows.

### Pitfall 2: Gallery filename → timestamp reversal is not a simple `.replace("-", ":")`
**What goes wrong:** `server/poll_loop.py::_save_to_gallery()` names files via `now_iso.replace(":", "-") + ".png"` — e.g. `2026-08-30T19-20-42+00-00.png`. A naive reverse (`name.replace("-", ":")`) also converts the **date** portion's hyphens (`2026-08-30` → `2026:08:30`), producing an unparseable string.
**Why it happens:** The sanitization is one-directional and lossy about which hyphens were originally colons vs. originally date separators; nothing in the codebase currently reverses it (the current `gallery_tiles()` caption is just the raw filename minus `.png`, which D-22 replaces).
**How to avoid:** Split on `"T"` first, then only convert hyphens in the time+offset portion after it:
```python
# Source: implements D-22 against server/poll_loop.py:605's actual naming contract
import re

_GALLERY_TIME_PATTERN = re.compile(
    r"^(\d{2})-(\d{2})-(\d{2})([+-]\d{2})-(\d{2})$")

def _gallery_name_to_iso(name):
    """Reverse server/poll_loop.py::_save_to_gallery()'s ':' -> '-'
    filename sanitization. Returns None (never raises) on anything that
    doesn't match the exact expected shape — a renamed/foreign file in
    the gallery directory must degrade to the raw-filename caption, not
    crash the page.
    """
    stem = name[:-4] if name.endswith(".png") else name
    if "T" not in stem:
        return None
    date_part, _, time_part = stem.partition("T")
    match = _GALLERY_TIME_PATTERN.match(time_part)
    if not match:
        return None
    hh, mm, ss, tz_sign_hh, tz_mm = match.groups()
    return "%sT%s:%s:%s%s:%s" % (date_part, hh, mm, ss, tz_sign_hh, tz_mm)
```
**Warning signs:** A gallery caption showing a garbled or missing "Captured …" string for every entry, or `datetime.fromisoformat()` raising inside `preview_page.gallery_tiles()` if the reversal result is passed straight to `layout.parse_iso()`/`concise_timestamp_html()` without the `None`-on-mismatch guard above.

### Pitfall 3: `raw_columns` cells must be pre-escaped by the caller, same trap `content_html` already documents
**What goes wrong:** Passing a raw ISO string (not `concise_timestamp_html()`'s output) into a `raw_columns`-marked column would skip `escape_html()` entirely, and any special character in that raw value would be interpreted as markup — a real (if narrow, server-generated-data-only) injection surface.
**Why it happens:** `raw_columns` inverts the safety default for that column; every caller must remember the column now requires manual escaping/building, the same discipline `stat_tile()`'s `content_html` docstring already documents (and the same discipline this codebase has never violated at any existing `content_html`/`banner`/`freshness_html` call site).
**How to avoid:** Only ever put `raw_columns` entries where the cell value is the direct return of a builder that already escapes internally (`concise_timestamp_html()`, `status_dot()`). Never put a bare `row.get("ts")` string into a `raw_columns` cell.
**Warning signs:** A code reviewer should treat any new `raw_columns=(...)` call site as requiring the same scrutiny as any other `escape_html()`-bypassing call in this codebase.

### Pitfall 4: `<details>`/`<summary>` inside a `hidden`-toggled ancestor
**What goes wrong:** If a future task nests a `<details>` disclosure inside an element `list-filter.js` or `nav-dropdown.js` toggles via the `hidden` attribute, the native open/closed state of the inner `<details>` is preserved but invisible while the ancestor is hidden — generally correct HTML behavior, but worth being deliberate about, since this phase's History mobile card puts a `<details>` inside a `<li>` that `list-filter.js` also toggles `hidden` on.
**Why it happens:** `hidden` and `<details open>` are independent, orthogonal states — nothing in this codebase currently combines them.
**How to avoid:** No special handling needed — a filtered-out (`hidden`) history card correctly hides its `<details>` regardless of open/closed state, and re-showing it (clearing `hidden`) correctly restores whatever open/closed state the user had left it in. Confirmed this is the platform-native, expected behavior; flagged here only so the planner doesn't invent unnecessary state-reset logic in `list-filter.js`.
**Warning signs:** None expected — this is a "verify it's fine, don't add code" pitfall, not a "code needs to handle this" one.

### Pitfall 5: `data-filter-text` attribute values need HTML-attribute escaping, not just lowercasing
**What goes wrong:** Building `data-filter-text="%s" % lowercased_text` without `escape_html()` risks a broken attribute if the underlying value ever contains a `"` character (unlikely for ADS-B callsigns/hex codes specifically, but this codebase's own ASVS V5 discipline — "a client-controlled value is never trusted as-is," already applied to theme/runway ids and cookie values elsewhere in `layout.py` — argues for escaping defensively rather than relying on upstream data shape assumptions).
**How to avoid:** `'data-filter-text="%s"' % escape_html(combined_lowercased_text)` — same single escaping choke point as every other dynamic attribute this codebase renders.
**Warning signs:** A code reviewer should flag any new `data-*` attribute interpolation that doesn't route through `escape_html()`, matching this codebase's own "single-escaping-choke-point discipline" (`companion/pages/__init__.py`'s own stated contract).

### `layout.concise_timestamp_html()` (D-09, new function)
```python
# Source: implements the UI-SPEC's literal contract, following
# absolute_and_relative()'s existing docstring conventions verbatim
def concise_timestamp_html(ts, now_ts, fallback="no reading yet"):
    """"<span class="mono" title="<full ISO>"><HH:MM> UTC (<relative>)</span>"
    — D-09's concise-timestamp-by-default format. The full ISO string is
    demoted to the title attribute; the visible text is a concise clock
    time plus the existing relative_age_text() suffix, preserving
    absolute_and_relative()'s established absolute-first ordering
    convention (do not reverse to relative-first).

    Returns the escaped `fallback` (wrapped in no markup — a bare string,
    matching absolute_and_relative()'s own no-markup fallback contract)
    when `ts` is falsy. Returns already-safe HTML otherwise — this is a
    RAW-MARKUP-PRODUCING function; callers must interpolate its return
    value verbatim (never re-escape it) and must place it only in
    data_table()'s new raw_columns, never its default escaped columns.
    """
    if not ts:
        return escape_html(fallback)
    parsed = parse_iso(ts)
    age = age_seconds(ts, now_ts)
    if parsed is None or age is None:
        return '<span class="mono" title="%s">%s</span>' % (
            escape_html(ts), escape_html(ts))
    clock = parsed.strftime("%H:%M")
    return '<span class="mono" title="%s">%s UTC (%s)</span>' % (
        escape_html(ts), escape_html(clock), escape_html(relative_age_text(age)))
```
Note the `fallback` branch returns an **escaped plain string**, not markup — `data_table()` callers must therefore put this function's output in `raw_columns` unconditionally (both the markup branch and the escaped-fallback branch are safe to interpolate verbatim, since the fallback branch already ran `escape_html()` itself).

### Known Threat Patterns for this stack

| Pattern | STRIDE | Standard Mitigation |
|---------|--------|---------------------|
| Reflected/stored XSS via an unescaped `data-filter-text`/`data-copy-value` attribute | Tampering / Information Disclosure | `escape_html()` on every attribute interpolation, matching this codebase's single-choke-point discipline (Pitfall 5) |
| Double-escaping via `data_table()`'s new `raw_columns` misuse (a raw, non-pre-escaped string reaching a `raw_columns` cell) | Tampering | Restrict `raw_columns` cell values to only the output of builders that already escape internally (`concise_timestamp_html()`, `status_dot()`) — never a bare `row.get(...)` string (Pitfall 3) |
| Clipboard API called from a non-secure context silently no-oping | (not a STRIDE threat, but a functional-degradation risk) | `try`/`catch` around the Clipboard API call with an `execCommand` fallback, never a bare unguarded call (Standard Stack / Don't Hand-Roll) |
| A gallery filename that doesn't match the expected `_save_to_gallery()` naming shape (e.g. a manually-dropped file) crashing the reversal parser | Denial of Service (page-level, not system-level) | `_gallery_name_to_iso()`'s regex-match-or-`None` contract, never raising (Pitfall 2) — mirrors this codebase's existing `_safe_query()`/`parse_iso()` "never raise, degrade to a documented fallback" discipline throughout `layout.py`/`health_page.py` |

No new attack surface is introduced: this phase adds zero new routes, zero new POST handlers beyond the existing `/config` form (D-03's dirty-state bar submits through that exact same, already-validated path), and zero new external network calls (Clipboard API is a browser-local operation, not a network request).
