<decisions>
## Implementation Decisions

**How these were captured:** see the Split note above — every decision here was made during 06.6.2's original discuss-phase session, where the developer declined a normal multi-area discussion and delegated all decisions to "the audit's recommendations or your own judgment." Findings that already carry a single clear "Recommended direction" in the audit (UXA-01's mobile half, UXA-05, UXA-06, UXA-11, UXA-13, UXA-16, UXA-17, UXA-18, and UXA-08's Config-specific half) are NOT re-decided here — research/planning should follow the audit's own Detailed Findings sections directly for those, same discipline as 06.6.2.

### Config page (folds the developer's original ask + UXA-08's Config-specific half)
- **D-02:** `Bring-up LED` is renamed to `Diagnostic LED` in every user-facing string (H2, fieldset legend, helper text). Internal Python identifiers (`LED_HELPER_TEXT`, `led_fieldset`, etc.) are unchanged — this is a copy-only rename resolving UXA-05's "internal identifiers leak into operator copy" for this specific term.
- **D-03 — Save behavior, overrides an earlier in-conversation preference:** ships as a **dirty-state action bar**, not full auto-save. A "N unsaved changes" bar with explicit `Save settings`/`Cancel` actions appears only once a Theme/Runway value actually changes; the existing always-available server-rendered `<form method="post">` submit path is preserved unchanged for no-JS use. Earlier in the original conversation the developer said "explorer l'auto-save" for the Save button — flagging explicitly that this decision **does not do full auto-save**. Rationale for the override: the audit's own Config-page-redesign section explicitly recommends dirty-state + explicit save over auto-save, because auto-save on a Theme/Runway pick — which only takes effect on the device's *next scheduled poll*, per D-06/D-28 in `06-CONTEXT.md` — risks silently persisting a still-being-decided choice before the developer has settled on it; an explicit Save keeps that one-poll-cycle lag legible. The no-JS floor is also simpler to keep correct without a JS-driven auto-save path. If the developer still wants literal auto-save after seeing this, that's a one-line override at plan time.
- **D-04:** The Theme fieldset becomes a **read-only status display with a small preview swatch**, not a one-choice radio group, since exactly one hardware theme ("sky") exists today (confirmed live-glass-corrected per `STATE.md`'s Phase 7 notes) and a one-option radio has no real decision value. Reverts to an editable picker automatically once a second theme is added to `device_config.THEMES` — this is a rendering-count check (`len(THEME_IDS) == 1`), not a hardcoded assumption.
- **D-05:** Runway radios become **selectable cards** — designation + orientation + the optional airport-diagram `<img>` (already wired in Phase 06.4) inside one card, the whole card is the label/hit target, and the selected card gets a clear border/check rather than relying on the native radio's own visual alone. This directly answers the developer's original complaint ("les boutons radio runway sont surdimensionnés/incohérents avec le reste du design"). The three runway images the developer is separately producing (a stylized isometric Paris-Orly illustration, settled 2026-08-31 — see Specific Ideas below) drop into this same card once supplied — no code change needed for that part, per the existing `RUNWAY-IMAGES.md` contract.
- **D-06 (heading-dedup half — the `accent-color` token half of this decision already shipped in Phase 06.6.2):** The duplicate `Bring-up LED` / `Diagnostic LED` (per D-02) heading is de-duplicated to one accessible group name (keep the fieldset legend, drop the redundant `<h2>`, or vice versa — planner's call, just not both). This phase's Runway cards and Theme swatch should use the `accent-color: var(--color-accent)` token 06.6.2 already established for native controls — confirm it applies correctly rather than re-deriving it.

### Health
- **D-08:** The Battery Health readings table is **collapsed behind a closed-by-default `View {N} readings` disclosure**, and the chart is moved to appear immediately after the Battery status summary — before the (now-collapsed) table, matching UXA-06's acceptance criterion that the chart precede raw readings in visual and DOM order.
- **D-13:** The battery chart's keyboard model becomes **roving tabindex**: the chart adds exactly one stop to the page's normal Tab order, Left/Right arrow keys move chronologically between readings and update the existing readout line, Home/End jump to first/latest. Chosen over "single chart focus target" (functionally similar, roving tabindex is the more conventional/testable pattern) and over "make it non-interactive" (which the audit itself ranks lower and which would be a real regression from the per-point interactivity Phase 06.5 deliberately built) — this preserves full interactive parity while fixing the 20-Tab-stop problem.

### Cross-page: History, Health, Preview
- **D-09:** Timestamps default to **relative + concise local time** everywhere (already the house style per 06.6 D-02); the full ISO value is demoted to a `title`/details-disclosure attribute rather than shown inline by default, per UXA-05's recommended direction. This doesn't change the already-decided relative-vs-absolute ordering fight noted in `06.6-CONTEXT.md` — that ordering stays as-is, only the ISO-suffix's default visibility changes.
- **D-10:** Every bounded dataset gets a visible **"Latest N" label** (History "Latest 50", Battery "Latest 20 readings", Gallery "Latest 12 renders"). No pagination or older-data access is added this phase — deliberately narrower than the audit's optional "add pagination if older data has diagnostic value" branch, to keep this phase from growing a new backend capability.
- **D-12:** Health/Preview (the long-lived monitoring pages) get an **explicit Refresh action plus a stale-view warning** past a defined age threshold — no automatic background polling. This is the audit's own more conservative recommended default ("prefer a restrained freshness pattern over continuous background polling"); avoids new steady-state request volume and keeps authoritative health severity server-computed only. **SUPERSEDED (quick task 260902-chc), no-automatic-polling half only, Health only:** after living with the manual-refresh pattern in real use, the developer chose a genuine light auto-refresh instead — a named-interval, Page-Visibility-gated `location.reload()` (`companion/static/freshness.js`), replacing the manual Refresh action and the stale-view banner outright. The reason is the developer's own explicit choice after real use, not a re-audit; see `freshness.js`'s own header for the full mechanism decision and its accepted costs. The severity half of this same decision — authoritative health severity stays server-computed only — is **NOT superseded** and still stands; the reload mechanism regenerates every verdict server-side, so no severity is ever recomputed client-side.

### Per-page recomposition (D-18) — scoped exactly as the audit describes, no invented embellishment
- **Health:** status banner, then three compact signal cards (Device/Pipeline/Sources) sized to content (not stretched to the tallest card), then the battery hero + chart (already relocated by D-08), then the collapsed readings disclosure.
- **History:** sticky table header on desktop, callsign visually primary/hex secondary, state and corroboration as compact text badges. Mobile representation is one compact card per flight (see below).
- **Preview:** the live render centered in a quiet matte/frame treatment evoking the physical panel's aspect ratio, caption below.
- **Airlines:** one page header, one prominent resolved-rate figure, unresolved prefixes as the primary actionable list; no decorative donut chart.

### History
- **D-07:** History's mobile representation becomes **one compact card per flight**: primary line = callsign + relative time, secondary line = route + state, remaining fields (aircraft/airline, corroboration, runway, hex, absolute timestamp) sit behind a per-card disclosure (e.g. `<details>`). All seven data categories UXA-01's acceptance criteria requires stay reachable, just not all on the visible face of the card. Desktop keeps the existing table; the desktop-overflow half of UXA-01 (constraining `.dashboard-main`/`.data-table-wrap` so intrinsic table width can never expand the document) was already fixed in Phase 06.6.2 — this phase only needs the mobile card redesign, not the containment fix.

### Operator efficiency accelerators (from UXA-18)
- **D-20:** History and Airlines gain client-side filtering over their already-rendered, already-bounded rows (D-10's "Latest N" — no new backend query, no new data source). Each filter needs a visible label, a clear/reset action, a result count, and an empty-result state.
- **D-22:** Gallery captions (Preview page) switch from raw filenames to task-oriented capture time/state text.
- **D-23:** Copy-to-clipboard actions for callsign, hex ID, and full timestamp — small, non-intrusive success feedback, no new dependency.

### Claude's Discretion
- Exact `<details>` vs. custom-disclosure markup for History's mobile per-card details and Battery's readings-table collapse — whichever composes more cleanly with the existing `data_table()`/`stat_tile()` helpers.
- Exact swatch styling for the read-only Theme status (D-04) and exact card visual treatment for Runway (D-05) — should read as siblings of each other and of the existing `.runway-option` styling `06.4-01` already shipped, not as a third unrelated pattern.
- Exact stale-view threshold (D-12) and exact roving-tabindex wrap/no-wrap behavior at the chart's first/last point (D-13) — pick sensible defaults, document them in the plan.
- Exact card-grid balancing approach for D-18's Health tiles — the audit gives a strong direction, not a pixel-locked spec; planning should propose concrete values and confirm visually (screenshots, both themes) before treating them as final, same discipline 06.6.1 already used.
- All findings the audit already gives a single "Recommended direction" for and that land in this phase's pages (UXA-01's mobile half, UXA-05, UXA-06, UXA-08's Config half, UXA-11, UXA-13, UXA-16, UXA-17, UXA-18) — implement per the audit's own text, no re-decision needed here.

## Existing Code Insights

### Reusable Assets
- `companion/layout.py::status_dot()`, `stat_tile()`, `icon_html()`/`ICON_DEFS_HTML` — the existing status/card/icon primitives this phase's page recomposition should compose with rather than duplicate.
- Phase 06.6.2's new `page_header()`, refined sidebar, severity function, and design tokens — the primitives this phase builds directly on top of.
- `companion/static/nav-dropdown.js` — the ES5-safe vanilla-JS pattern (`"use strict"` IIFE, no framework) this phase's new client-side bits (roving-tabindex chart nav, dirty-state Save bar, explicit Refresh, filtering, copy-to-clipboard) should follow.
- `companion/pages/config_page.py::runway_fieldset()` / `RUNWAY_IMAGE_ROUTE_PREFIX` — the existing registry-driven, session-gated image wiring D-05's card redesign extends.

### Established Patterns
- Every page module reads `ctx` computed once per request in `companion/app.py::page_context()` — cross-page signals are threaded this way, never via one page module importing another (`companion/pages/__init__.py` forbids it). D-12's freshness signal likely follows this pattern.
- Asymmetric read/write validation discipline (`config_page.py::handle_post()`'s docstring) — the read path forgives unrecognised values via `normalise_*()` fallbacks, the write path rejects the whole submission. D-03's dirty-state Save must not weaken this.
- No-JS floor is a running project discipline (battery chart, poll-cooldown countdown, nav dropdown all ship a working no-JS fallback) — D-03, D-12, D-13, D-20 all need one too.

### Integration Points
- `companion/static/style.css` — the single stylesheet every visual-consequence fix (D-04 swatch, D-05 cards, D-18's per-page recomposition) lands in; consume Phase 06.6.2's new tokens, don't invent parallel ones.
