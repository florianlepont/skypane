Run a real capture against live traffic, using the shipped code rather than a bespoke script: repeatedly invoke `server/plane/detect.py` with each of the three runway ids and the JSON output flag, recording each poll's full selection dict including the geometry tags. Run long enough to observe traffic — Phase 1's own sample took roughly ninety minutes to cover twenty aircraft, so plan for a comparable window and say in the record how long it actually ran and how many distinct aircraft it saw.

For every selection, record the runway id requested, the aircraft hex and callsign, the cross-track offset, the along-track position, the track deviation, and whether the corridor and alignment gates each passed. Then answer the three questions that matter, each with the measured numbers rather than an impression:

1. **Does the gate select genuine traffic on each runway?** For each of 06/24 and 02/20, did any aircraft the capture believes was using that runway get selected when that runway was requested?
2. **Is the gate exclusive?** Did any aircraft selected for one runway also get selected for another in the same poll? A single aircraft cannot be on two runways, so an overlap is a defect, not a curiosity.
3. **Is there measured separation?** For each runway, what is the largest cross-track offset among accepted aircraft and the smallest among rejected ones? Runway 3's own thresholds sit inside an empty band between those two figures; state whether an equivalent empty band exists for each new runway, and how wide.

Write `adsb-test/RUNWAY-GATE-VERIFICATION.md` recording: the capture window and its duration, the provider used, the raw counts, a table of every selection with its geometry, the three answers above, and an explicit verdict per runway — confirmed, corrected, or still unvalidated.

Be honest about a null result. Orly's runway configuration is wind-dependent and a capture window may simply contain no traffic on one of the two new runways. If that happens, say so plainly, record what was and was not observed, and leave that runway's verdict as still unvalidated with the `threshold_status` string in the geofence file unchanged. A capture that observed nothing is a real and reportable outcome; describing it as confirmation would be worse than not running it.

If the capture contradicts the copied thresholds — an accepted aircraft further off centreline than the half-width should allow, or a rejected aircraft that was plainly on the runway — correct the numbers in `adsb-test/runway3.json`'s corresponding entry and rewrite that entry's `threshold_status` string to record the derivation the same way runway 3's own block does: the measured accepted maximum, the measured rejected minimum, the resulting empty band, and the date. Re-run `server/test_plane_detection.py` after any such change.
