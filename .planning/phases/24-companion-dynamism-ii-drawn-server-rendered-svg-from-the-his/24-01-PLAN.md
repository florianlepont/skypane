<objective>
Four drawings are about to be added to two pages across five plans. Before any of
them runs, the phase needs the two things that stop five drawings becoming five
dialects: one estimator and one geometry module — plus a guard that fails when a
plan invents a third.

The estimator is not new. `companion/battery.py` was created by 19-01 for exactly
this problem ("let home_page.py and health_page.py share one estimate without
either importing the other") and is already called by both pages. This plan
**extends** it and makes the sharing enforceable, rather than creating a second
shared module and leaving the first one as the trap.

The geometry is new, but its content is not: `health_page.battery_sparkline_svg()`
has carried a correct, carefully-reasoned coordinate scheme since 06.5, refined
twice since. This plan lifts the reusable half into `companion/draw.py` **without
changing what the existing chart renders** — plan 24-05 changes that, deliberately
and separately.

Output: an extended `companion/battery.py`, a new `companion/draw.py`, the shared
CSS vocabulary the drawings paint through, and one harness check that makes the
drawing contract a test rather than a review comment.
</objective>

<no_js_floor>
D-09 is absolute and this plan is where the phase earns it. Server-rendered SVG is
chosen over every client-side charting approach for one decisive reason: the
drawing arrives complete in the first HTTP response, so it paints identically with
scripts blocked, needs no measurement pass, and is unaffected by
`script-src 'self'`. `draw.py` therefore emits **complete** markup — no element
whose position, size or colour is filled in later by a script. A primitive that
returns markup a script must finish is out of contract; if one seems necessary,
stop and record it in the SUMMARY.
</no_js_floor>

Binding constraints:
- `companion/draw.py` is stdlib-only. It imports no page module, nothing from
  `server/`, and nothing from `companion/layout.py` (which would drag the page
  shell into a geometry module). It may import `companion/battery.py`; state in
  the docstring whether it does and why.
- **Do not change what the existing sparkline renders.** This plan may move code
  into `draw.py` and have `health_page.py` call it — but the rendered output must
  be byte-identical, proven by capturing the emitter's return value against a
  seeded series before and after. If byte-identity cannot be preserved, DO NOT
  refactor the existing emitter at all: land `draw.py` as new primitives that
  24-05 adopts, and record the reason in the SUMMARY. A silent rendering change
  here would be attributed to whichever later plan happened to touch the chart.
- Two coordinate schemes, two helpers, two names. `24-RESEARCH.md`'s Risk 2 table
  is the contract: a percentage-scheme helper for card-filling time series (no
  viewBox, absolute pixel sizes) and a user-unit helper for aspect-locked marks
  (a viewBox). One helper with a `use_viewbox=` flag is the shape to avoid — a
  flag is exactly how the two get mixed inside one drawing.
- Every value interpolated into markup is escaped. The drawings carry timestamps,
  firmware strings and airline names into `<title>` elements; `draw.py` owns one
  escaping helper and every emitter uses it. There is no "this value is always
  safe" exception.
- Two new motion tokens are NOT needed and must not be added: this plan animates
  nothing. `--motion-fast`/`--motion-slow` exist from 23-01 and this phase spends
  from them only if a later plan has a reason.
- `style.css` is pinned at zero stray comment terminators. New comments go INSIDE
  a block comment.
