<objective>
Prove D-02 actually works, on the device class it was written for.

Plans 06.5-01 and 06.5-02 are fully covered by automated checks — but every one of those checks asserts *markup and source*, never *behaviour*. This project's test harness is stdlib-only with no headless browser and no JavaScript engine (`06.5-VALIDATION.md`, Manual-Only Verifications), so "tapping a point reveals its reading" is structurally outside its reach. D-02 exists specifically because of `06-CONTEXT.md` D-22 — the developer will realistically check this from their phone — and `06.5-RESEARCH.md`'s Pitfall 1 warns in as many words that a mouse-emulated tap in a desktop device-toolbar is *not* proof, because it does not reproduce the real touch-to-focus behaviour the whole scoped-JS decision was made to route around.

This plan therefore follows this project's own established precedent — `05-CONTEXT.md`'s "real preview renders before committing to visual decisions", already applied on real glass in Phases 3 and 5 — and closes the loop with a real device.

`workflow.human_verify_mode` is `end-of-phase`, so this is not a blocking mid-execution checkpoint task: the automation runs to completion unattended, and the human judgement is expressed as this plan's `<human-check>` verification.

Purpose: without this, the phase would ship an interaction nobody has ever performed.
Output: a running seeded preview, an automated proof that the page and the script both serve correctly over real HTTP, and a recorded sign-off (or a named defect) in `06.5-03-SUMMARY.md`.
</objective>

  <action>
Stage the preview, automate everything that can be automated, then hand the developer a short, specific checklist. Automate first, ask second — never ask a human to do something a command can prove.

**Part A — seed a realistic fixture.**

1. Create a throwaway state directory under the system temp dir (do not use `server/state/`, which holds the real pipeline's data).

2. Seed it with **twelve** `device_health` rows through `server.history_db.record_device_health()` — the same writer the harness uses, so the fixture cannot drift from the schema. Space the timestamps a few minutes apart and give the millivolt values a gently declining curve with **no** consecutive drop reaching `health_page.BATTERY_DROP_WARN_MV`, so the badge renders healthy and the chart has enough points for the tap-density question to be real. Twelve is chosen deliberately: enough that consecutive points sit close together (`BATTERY_TREND_LIMIT` is 20, so twelve is representative of a well-used device), which is exactly the condition 06.5-RESEARCH.md's Pattern 2 enlarged hit target exists to handle.

3. Also write a fresh `META_LAST_PIPELINE_RUN` meta value so the pipeline signal reads healthy and the anomaly banner stays absent — the preview should show the ordinary, all-clear state, not a page full of warnings.

**Part B — serve it and prove the wire is correct, automatically.**

4. Export `SKYPANE_COMPANION_PASSWORD` with a throwaway value for this session only. `companion/auth.py` fail-closes without it and `companion/app.py` will exit 1.

5. Start `server/.venv/bin/python3 companion/app.py --port 8643 --state-dir <the seeded dir>` in the background and wait for its startup line.

6. Log in over HTTP with that password to obtain a session cookie, then fetch `/health` and assert, from the **real HTTP response body** (not from re-importing the module):
   - the `BATTERY_STATUS_LABEL` text is present;
   - a `dot--ok` class is present;
   - exactly one `<script` occurrence appears and its `src` is `/static/battery-trend.js`;
   - `SPARKLINE_HIT_CLASS` appears twelve times and `data-mv` appears twelve times;
   - the `BATTERY_READOUT_ID` element is present.
7. Fetch `/static/battery-trend.js` **without** the session cookie and assert a 200, a `text/javascript` content type and a non-empty body — the same route plan 06.5-01 added, now proven in the exact context the browser will use it.
8. Print the LAN URL the developer's phone should open. Derive the host's LAN address (not `127.0.0.1`, which a phone cannot reach) and print it together with the throwaway password, so the developer can act without hunting for either.

**Part C — the human half.**

9. Present the checklist in this task's `<verify><human-check>` block and wait for the developer's response before proceeding.

10. Record the outcome in `06.5-03-SUMMARY.md` under a "Real-device verification" heading, capturing: the phone model and browser used, the desktop browser used, a per-item pass/fail for each checklist line, and — if anything failed — a precise description of what was observed rather than a guess at the cause. If the tap behaviour fails specifically on iOS Safari, say so explicitly and cite 06.5-RESEARCH.md Assumption A2, because that is the assumption whose falsification it would represent.

11. Stop the background service and delete the seeded temp directory. Do not leave a password-bearing process running.

12. If everything passes, state plainly in the SUMMARY that D-02 is verified on real hardware and name the device — this is the sentence a future reader will look for. If anything fails, do **not** patch source here: record the defect and note that the fix belongs in a follow-up plan against `06.5-01` (the script or the styles) or `06.5-02` (the emitted markup).
