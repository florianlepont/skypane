<objective>
Make the Battery trend section carry both halves of this phase's goal: a persistent at-a-glance verdict (D-01, absorbed from the superseded Phase 06.1) and a chart whose points reveal their exact reading on hover or tap (D-02).

Everything here is server-rendered Python. The client half — `companion/static/battery-trend.js`, its stylesheet rules, and the pre-auth route that serves it — already shipped in plan 06.5-01 (wave 1), which is why this plan can emit a `<script src>` tag that resolves on the very first render.

Purpose: today Battery trend is the only Health section without a status badge, and its sparkline is a bare `<polyline>` a user cannot interrogate — the raw-mV table underneath is the only way to read an exact value, which does not scale on a phone.
Output: a badge, per-point interactive markup, a reserved readout line, one external script reference, and eight new automated checks.
</objective>

## Two decisions this plan locks (do not re-derive them)

### Assumption A1 — the empty-history badge renders `"ok"`, not `"warn"`

`06.5-RESEARCH.md` flagged this as an open judgment call (Assumptions Log A1, Open Question 2). **It is decided here: `"ok"`.** Two independent reasons, both of which must be written into `_battery_section()`'s docstring so a future reader does not have to reconstruct them:

1. **Precedent.** `corroboration_status()` in this same file already maps the unknown state (`"None"` — only one ADS-B source answered) to `"ok"`, never a warning, with the explicit rationale that an absence of information is not a failure. `_CORROBORATION_ROWS` says so in its own comment. The battery section's "no readings yet" state is the same shape of unknown. Device check-in and ADS-B pipeline do map never-seen to `"warn"` via `staleness_status()`, but those two are *staleness* signals where silence genuinely means something is wrong; "no battery history yet" on a device that has simply never reported is not.
2. **A real coupling, not a style preference.** `render()` passes `_battery_section()`'s second return value straight into `collect_anomalies()`, which appends the literal copy *"A battery reading shows an abnormal drop."* for any non-`"ok"` battery state. A `"warn"` on the empty branch would therefore make a freshly-provisioned deployment with zero readings display a banner asserting an abnormal drop that never happened — factually wrong copy (06.5-RESEARCH.md, Pitfall 2). Keeping `"ok"` means one value can honestly serve both consumers, so no decoupling is needed and `render()` stays untouched.

Task 1 adds a permanent regression check for exactly this: zero battery rows must produce an `ok` badge **and** no anomaly banner.
