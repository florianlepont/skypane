# Plan 06.5-03: Real-Device Verification — Summary

## Real-device verification

Verified across two sessions/methods: the load-bearing tap interaction was verified by the developer on real hardware (the one behaviour this project's stdlib test harness structurally cannot execute); the remaining checklist items were verified directly against the live server by the orchestrator, since they don't require a physical touchscreen to prove.

**Device/browser used by the developer: iPhone, Safari.** This is the highest-risk browser named in `06.5-RESEARCH.md`'s Pitfall 1/Assumption A2 — the whole reason this phase chose scoped JS with explicit `click`/`mouseenter`/`focus` handlers over a CSS-only `:focus`-on-tap approach was that tap-triggered `:focus` on a non-native-control SVG shape is unreliable on iOS Safari specifically. Confirming the interaction works there is the strongest possible validation of that design decision.

## Wire-correctness (automated, run before the human checklist)

Per the plan's Part B, before any human verification: logged in over real HTTP, fetched `/health` and confirmed the `BATTERY_STATUS_LABEL` text, a `dot--ok` class, exactly one `<script>` occurrence with `src="/static/battery-trend.js"`, twelve `data-mv`/`sparkline-hit` occurrences, and the `battery-readout` element id were all present in the real response body. Fetched `/static/battery-trend.js` without a session cookie and confirmed 200, `Content-Type: text/javascript`, non-empty body (4460 bytes).

**Mid-verification incident (unrelated to this plan's design):** the first preview attempt's scratch state directory was wiped by an external process mid-session (background scratchpad cleanup), silently killing the running server. Recreated the seeded fixture and restarted; no code or design implication, purely an operational hiccup in this verification session.

**Access-method note:** the developer's phone could not use plain HTTP on the LAN — `companion/auth.py`'s session cookie is `Secure` unconditionally (by design, correct for production since Caddy always terminates TLS there), which real mobile Safari refuses to send back over an insecure connection. Worked around for this verification only by fronting the plain-HTTP preview with a throwaway self-signed-cert TLS proxy (`openssl` + a small Python `ssl`-wrapping TCP proxy), so the developer's phone connected over real HTTPS. This is a verification-environment workaround, not a code change — production already serves over HTTPS via Caddy, so this limitation doesn't exist there.
