# Phase 06.5: Interactive battery trend chart with overall status - Context

**Gathered:** 2026-08-28

<domain>
## Phase Boundary

Upgrades `companion/pages/health_page.py`'s existing Battery Trend section: today it renders a static, non-interactive SVG sparkline plus a raw-mV data table, with drop-anomaly detection feeding only a generic banner (no persistent status badge). This phase adds (a) a persistent overall-status badge next to the section heading, matching the pattern the Device/Pipeline sections already use, and (b) real interactivity — tap-or-hover on a chart point reveals its exact reading and timestamp, working on both desktop (hover) and mobile (tap).

**This phase absorbs Phase 06.1** ("Battery status on companion web interface"), which is now marked superseded in ROADMAP.md. Codebase investigation found 06.1's ask — a battery-status verdict on the companion web interface — targets the exact same `health_page.py` section as this phase, so the missing status badge (06.1's core ask) and the interactive chart (this phase's own title) ship together here rather than touching the same section twice. See `.planning/phases/06.1-battery-status-on-companion-web-interface/` for the (never-planned) original phase entry and ROADMAP.md's Phase 06.1 section for the full supersession note.

**Origin note:** the underlying idea traces back to `05-CONTEXT.md`'s deferred section, which explicitly anticipated this: "a future richer battery UI (e.g. a companion web interface health view — see REQUIREMENTS.md's CFG-03)" — this phase is that anticipated follow-up, now happening after CFG-03's initial (non-interactive) implementation shipped in Phase 6.

<decisions>
## Implementation Decisions

### Status badge
- **D-01:** Add a persistent **status badge** next to the Battery Trend section heading, reusing the exact `status_dot()` pattern the Device and Pipeline sections already render (currently Battery Trend is the one section without one).

### Interactivity
- **D-02:** Hovering **or tapping** a chart point must reveal its exact reading (mV) and timestamp — explicitly required to work via tap on mobile, not just desktop hover, given the companion app's established mobile-responsiveness bar (`06-CONTEXT.md` D-22).

### Known implementation tension — flagged for research/planning, not resolved here
- The current sparkline (`battery_sparkline_svg()`) is deliberately script-free, and an existing regression test (`test_status_pages.py`) explicitly asserts the page contains no `<script>` tag. Tap-to-reveal on mobile is not reliably achievable with pure hover-only mechanisms (native SVG `<title>` tooltips work on desktop hover but not on mobile tap without JS). **The planner must explicitly decide and document** whether to (a) add a small, scoped JS interaction and update the no-script test's rationale accordingly, or (b) find a no-JS approach that still satisfies D-02's tap requirement (e.g. always-visible per-point labels at low density, or a details-on-focus pattern) — do not silently drop the mobile-tap requirement to keep the test unchanged.
- **Edge case to define:** what the status badge shows when there is no battery history yet (empty table) — the existing binary `battery_status()` returns only `"ok"`/`"error"`; whether "no data yet" needs its own third state (mirroring `health_page.py`'s existing `_CORROBORATION_ROWS` precedent, where `"None"` maps to `"ok"`, not a failure) is left to planning, but should not silently render as an error/warning it isn't.

### Claude's Discretion
- Whether the overall-status verdict reuses `battery_status()`'s existing ok/error binary as-is, or extends it — no specific richer-status request was made beyond "an overall status," and the existing binary already satisfies the plain requirement.
- Exact tooltip/detail-reveal visual treatment (popover, inline expansion, etc.).

</decisions>
