## Summary

This phase touches exactly one file's rendering logic (`companion/pages/health_page.py`) plus its test harness (`companion/test_status_pages.py`), and — if the JS path is taken (recommended below) — adds exactly one new static asset and one new pre-auth route in `companion/app.py`. The two deliverables are independent and low-risk individually: (a) the status badge is a two-line change reusing `layout.status_dot()` exactly as `_device_section()`/`_pipeline_section()` already do; (b) the interactive chart is the harder problem, and the phase's own CONTEXT.md correctly flags it as needing a real decision.

**The central research question (no-JS vs. scoped-JS) resolves to: use a small, scoped, external vanilla-JS file.** A CSS-only `tabindex` + `:focus` approach was investigated in depth and rejected — it is not reliably tap-triggered on iOS Safari for non-native-control elements (an SVG `<circle>` is neither a link nor a form control), which is a well-documented, still-live gap as of the current WebKit release cycle. Given D-22's explicit mobile-testing bar ("the user will realistically check this from their phone"), betting the phase's entire user-facing requirement on an unreliable-on-iOS technique is not acceptable. The existing "no `<script>` tag" test turns out to be **narrower in scope than it first appears** — it only exercises `battery_sparkline_svg()`'s own isolated return value, not the full rendered page — so the JS path can be added with a small, additive, well-justified test change rather than a wholesale relaxation of an existing guarantee.

**Primary recommendation:** Keep `battery_sparkline_svg()` itself free of `<script>`/`url(`/`<image` (it gains `<circle>` hit-targets with `data-mv`/`data-ts` attributes, nothing else) — this means the existing test assertion (`_sparkline_has_no_external_reference`) needs **zero code changes**, only a docstring/comment update to note it now also carries per-point markers. Add exactly one new, externally-hosted `<script src="/static/battery-trend.js">` tag, emitted only by `_battery_section()` (only when a sparkline actually renders — never on the empty-state path), served via a new pre-auth static route mirroring `_serve_stylesheet()`'s existing pattern. The script does one thing: on `click`/`keydown(Enter/Space)` of a circle, write that point's mV + timestamp into an adjacent readout element via `textContent` (never `innerHTML`) — `click` fires from both mouse-click and touch-tap, so no separate touch-event wiring is needed, and CSS `:hover` on the circles gives desktop hover a free, JS-independent preview using the existing `<title>` element as a fallback tooltip (belt-and-braces: hover users on desktop get the native tooltip even if JS fails to load; tap users on mobile get the JS-driven persistent readout). Add one new, additive test asserting the full page contains **exactly one** `<script` tag and **zero** inline event-handler attributes (`onclick=`, `ontouchstart=`, etc.) anywhere in the rendered output — this is what actually encodes and enforces the "this one script, nothing else" contract going forward.

### Pattern 1: Server-rendered data-point markers + client-side reveal
**What:** The Python side embeds all the data (`data-mv`, `data-ts` attributes on each `<circle>`) directly in the SVG markup at render time — no client-side fetch, no JSON payload, no API call. The JS only reads attributes already present in the DOM and writes them into a sibling readout element.
**When to use:** Any time a small, fully-known dataset (here: ≤20 points) needs client interactivity without introducing a data-fetching layer.
**Example:**
```python
# companion/pages/health_page.py — inside battery_sparkline_svg(), per point:
# Source: this codebase's own existing escape_html()-free numeric interpolation
# convention (battery_mv is already type-checked int, ts is an ISO string from
# history_db — both server-controlled, not user input, matching this file's
# existing trust model for chart coordinates).
'<circle class="sparkline-point" tabindex="0" cx="%.1f" cy="%.1f" r="3" '
'data-mv="%d" data-ts="%s"><title>%s mV at %s</title></circle>' % (
    x, y, value, escape_html(ts), value, escape_html(ts))
```
```javascript
// companion/static/battery-trend.js — the entire interactive surface.
// Source: MDN Web/API/EventTarget/addEventListener, Web/API/HTMLElement/dataset
// (standard DOM APIs, no framework).
(function () {
  "use strict";
  var readout = document.getElementById("battery-readout");
  if (!readout) return;
  function reveal(circle) {
    readout.textContent = circle.dataset.mv + " mV — " + circle.dataset.ts;
  }
  document.querySelectorAll(".sparkline-point").forEach(function (circle) {
    circle.addEventListener("click", function () { reveal(circle); });
    circle.addEventListener("keydown", function (evt) {
      if (evt.key === "Enter" || evt.key === " ") { evt.preventDefault(); reveal(circle); }
    });
  });
})();
```

### Pattern 2: Enlarged invisible hit-target for dense tap points
**What:** At `BATTERY_TREND_LIMIT=20` points spread across a `viewBox="0 0 300 60"` (usable width 292px after 4px padding), consecutive points sit ~15.4px apart. A visible `r="3"` marker (6px diameter) is too small to reliably tap. Add a second, transparent, larger circle (`r="8"`, `fill="transparent"`) at the same coordinates as the actual tap/click/focus target; keep the small visible circle purely cosmetic.
**When to use:** Whenever a chart's real estate is small relative to the number of interactive points and the interaction must work via touch.
**Example:**
```
<!-- Source: standard SVG hit-testing behavior — a transparent fill is still
     "opaque" for pointer-event purposes unless pointer-events:none is set. -->
<circle class="sparkline-hit" tabindex="0" cx="12.0" cy="30.0" r="8" fill="transparent" data-mv="4180" data-ts="..."><title>...</title></circle>
<circle class="sparkline-dot" cx="12.0" cy="30.0" r="3" fill="currentColor" aria-hidden="true"/>
```

### Anti-Patterns to Avoid
- **`innerHTML` for the readout update:** Even though `data-mv`/`data-ts` originate from the server's own trusted DB, using `innerHTML` here would be an unnecessary XSS-shaped foot-gun and inconsistent with this codebase's single-escaping-choke-point discipline (`layout.escape_html()`). Use `textContent` in the JS — it needs no escaping function at all.
- **Separate `touchstart`/`touchend` handlers:** Unnecessary complexity. `click` already fires on tap in every mobile browser (it's a synthesized event derived from touch, standard since the mobile-Safari-300ms-delay era was fixed years ago via `touch-action: manipulation` / modern browser defaults). Adding raw touch listeners duplicates logic and risks double-firing.
- **Inline `onclick="..."` attributes:** Would defeat the entire point of the new page-level test (see below) and reintroduce exactly the kind of untracked JS-creep vector D-02's own CONTEXT.md flags. All wiring goes through `addEventListener` in the one external file.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Desktop hover tooltip | A custom CSS/JS tooltip positioning system | The native SVG `<title>` element (already zero-cost, already used for `role="img" aria-label`-style accessibility elsewhere in this file) | Browsers render `<title>` as a native tooltip on hover for free, with zero layout/positioning code and zero JS — exactly the "hover" half of D-02's "hovering or tapping" requirement, at zero implementation cost |
| Detecting touch vs. mouse to conditionally wire different handlers | `ontouchstart` feature-detection branching | A single `click` listener | `click` already unifies both input types at the browser level; branching on input type is unnecessary complexity for this interaction |

**Key insight:** The phase's apparent complexity ("mobile tap AND desktop hover, no framework, one file") collapses to something small once the browser's own primitives (`click`'s dual-origin semantics, `<title>`'s native tooltip) are used instead of re-derived. The only genuinely new code is ~15-20 lines of JS and a handful of new SVG attributes.

## Common Pitfalls

### Pitfall 1: Trusting CSS-only `tabindex`+`:focus` for mobile tap
**What goes wrong:** A developer implements the D-02 requirement using only `tabindex="0"` on each `<circle>` plus a CSS rule showing a hidden `<text>`/tooltip on `:focus`, believing this avoids JS entirely. On desktop this works. On a real phone (particularly iOS Safari, which the project's own hardware/testing loop already treats as a first-class target), tapping a non-native-control, non-link element with `tabindex` does **not** reliably trigger `:focus` — this is a long-documented WebKit behavior gap (Safari has historically only auto-focused actual form controls/links on click/tap; adding `tabindex="0"` forces *keyboard* focusability but has been unreliable for *tap*-triggered focus specifically) and the fix reported for iOS 17 is scoped to native `<button>` elements, not arbitrary `tabindex`-ed SVG shapes.
**Why it happens:** The CSS-only tooltip pattern is a well-known, widely-blogged desktop technique, and its mobile gap is easy to miss without testing on real iOS hardware.
**How to avoid:** Do not ship this as the primary/only mechanism. Use the scoped-JS `click` handler as the mechanism of record; CSS `:hover`+`<title>` is a free desktop bonus layered on top, not a replacement.
**Warning signs:** "Works when I click with a mouse in Chrome DevTools' device-toolbar emulation" is not proof — device-toolbar mouse-emulated taps do not reproduce Safari's real touch-to-focus gap. This must be verified with a real preview/device check per this project's own established pattern (`05-CONTEXT.md`'s "real preview renders before committing to visual decisions" precedent, explicitly cross-referenced in this phase's own CONTEXT.md).

### Pitfall 2: `_battery_section()`'s single `state` return value serves two different purposes
**What goes wrong:** `render()` calls `battery_html, battery_state = _battery_section(trend_rows)`, and `battery_state` feeds directly into `collect_anomalies(device_state, pipeline_state, battery_state, disagreement_warn)` (line ~450-451 today). If the empty-history badge is changed to show `"warn"` (to visually match Device/Pipeline's own "never checked in → warn" convention), that same `"warn"` value will also flow into `collect_anomalies()`, which appends the literal string `"A battery reading shows an abnormal drop."` to the anomaly banner — **factually wrong** copy for a freshly-provisioned device that simply has zero data yet.
**Why it happens:** The existing code already couples "what badge color to show" and "what to tell `collect_anomalies()`" into one value, because until now the empty-history case only needed one classification (`"ok"`) that happened to satisfy both consumers simultaneously.
**How to avoid:** Either (a) keep the empty-history state `"ok"` for both purposes (matches the current code exactly, avoids the coupling problem entirely, and matches `_CORROBORATION_ROWS`'s "unknown ≠ failure" precedent cited in this phase's own CONTEXT.md — **recommended**, see Assumptions Log A1), or (b) if a `"warn"` empty badge is chosen instead for stronger visual parity with Device/Pipeline, decouple the two consumers explicitly — e.g. have `collect_anomalies()` keep calling `battery_status(trend_rows)` directly (which already correctly returns `"ok"` for `<2` rows, independent of whatever the badge shows) rather than trusting `_battery_section()`'s returned tuple for that purpose.
**Warning signs:** A test seeding zero battery rows and asserting the anomaly banner is absent (extending the existing `_no_anomaly_banner_when_all_healthy` pattern to the zero-rows case) will catch this immediately if it regresses.

### Pitfall 3: Phase execution order vs. Phase 06.3's already-written, line-number-pinned plans
**What goes wrong:** `06.3-04-PLAN.md` (already fully planned, 5 plans, not yet executed per STATE.md) rewrites `health_page.py`'s `render()` at **specific pinned line numbers** (428-470) and explicitly declares `_battery_section`, `battery_sparkline_svg`, and `battery_status` **"Unchanged"** as a load-bearing assumption for its own diff/verification. If **this** phase (06.5) executes first and modifies those exact functions (adding `status_dot()`, `<circle>` markers, and the new `<script>` tag), Phase 06.3's plan will be planning against stale line numbers and a stale "unchanged" assumption.
**Why it happens:** Both phases touch the same file's same functions; 06.3 was planned first but assumed it would land against the pre-06.5 code shape (06.5's own CONTEXT.md canonical_refs explicitly acknowledges the reverse order as a contingency: "If 06.3 has not executed yet when this phase executes... 06.3 will re-home the markup into a tile frame later without changing the badge/chart logic itself").
**How to avoid:** Prefer executing 06.3 before 06.5 if both are still pending — 06.3's plan is the one with hard line-number/content pins, so it's cheaper to have it land on the *original* code shape and let 06.5 land on top (06.3's `stat_tile()` passes `content_html` through untouched per `06.3-01-PLAN.md`, so a `status_dot()` + interactive `<circle>` markers added inside `_battery_section()`'s returned `content_html` composes cleanly regardless of order — the risk is purely about 06.3's own line-pinned diff/verification steps, not runtime behavior). If 06.5 must execute first, flag `06.3-04-PLAN.md`'s Task ("Unchanged" list, line ranges 428-470) for a mechanical re-check/replan before 06.3 executes.
**Warning signs:** `06.3-04-PLAN.md`'s own pinned checks (`grep -c 'layout.stat_tile(' companion/pages/health_page.py) = "4"`, `grep -c 'def _section(' ...) = "0"`) failing or needing hand-adjustment during 06.3's execution is the direct symptom.

### Pitfall 4: `EXPECTED_CHECK_COUNT` is a literal, hard-coded gate
**What goes wrong:** `companion/test_status_pages.py`'s `main()` returns exit code 1 unless `passed == total == EXPECTED_CHECK_COUNT` (currently `25`). Adding new `check(...)` calls without bumping this constant makes the whole harness fail even though every individual check passes.
**Why it happens:** This is a deliberate anti-silent-skip guard (catches a check being accidentally removed or never registered) but it is easy to forget when *adding* checks.
**How to avoid:** Any plan/task that adds checks to this file must also bump `EXPECTED_CHECK_COUNT` by the exact number of new checks added, in the same commit.
**Warning signs:** `status-pages: N/M checks pass` printing `N == M` but the script still exiting non-zero (or vice versa) — the tell that `EXPECTED_CHECK_COUNT` drifted from the real count.

## Code Examples

### New pre-auth static route (mirrors the existing stylesheet route exactly)
```python
# Source: companion/app.py's own existing _serve_stylesheet() (lines 326-332),
# STYLE_ROUTE dispatch (line 392) — pattern replicated verbatim for the new file.
SCRIPT_ROUTE = "/static/battery-trend.js"
_BATTERY_TREND_JS_PATH = os.path.join(_HERE, "static", "battery-trend.js")

def _serve_battery_trend_script(self):
    try:
        with open(_BATTERY_TREND_JS_PATH, "rb") as fh:
            payload = fh.read()
    except OSError:
        return self.send_html(404, self._not_found_page())
    # text/javascript, not application/javascript — RFC 9239 (2022) obsoletes
    # the application/ form; text/javascript is the sole current standard.
    return self.send_bytes(200, "text/javascript", payload, cache_seconds=300)

# in do_GET(), alongside the existing `if path == STYLE_ROUTE:` check:
if path == SCRIPT_ROUTE:
    return self._serve_battery_trend_script()
```

### Updated test scope note (no code change needed to the existing assertion)
```python
# companion/test_status_pages.py — _sparkline_has_no_external_reference stays
# exactly as-is (it only exercises battery_sparkline_svg()'s own return value,
# which never contains url(/<image/<script). ADD a new, separate page-level
# check instead:
def _page_allows_exactly_one_scoped_script_no_inline_handlers():
    tmp = _mkstate("h-script-scope")
    try:
        base = _now()
        _seed_device_health(tmp, [
            (_iso(base - timedelta(minutes=1)), 4200),
            (_iso(base), 4190),
        ])
        rendered = health_page.render(_ctx(tmp, now=_iso(base)))
        if rendered.count("<script") != 1:
            return False, "expected exactly one <script tag, got %d" % rendered.count("<script")
        for forbidden in ("onclick=", "onmouseover=", "ontouchstart=", "onfocus="):
            if forbidden in rendered:
                return False, "found forbidden inline event-handler attribute %r" % forbidden
        return True, ""
    finally:
        shutil.rmtree(tmp, ignore_errors=True)
```

## State of the Art
