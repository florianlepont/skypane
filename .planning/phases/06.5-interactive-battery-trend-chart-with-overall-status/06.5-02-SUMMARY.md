**Battery trend now carries the same status_dot() badge every other Health section has (D-01), and every sparkline point is a finger-sized, keyboard-focusable hit target with a native tooltip revealing its exact mV reading and timestamp (D-02, server-rendered half) — all server-side Python, with zero JavaScript changes since the client script already shipped in plan 06.5-01.**

## Accomplishments
- `companion/pages/health_page.py`: `BATTERY_STATUS_LABEL` + `_battery_badge_block()` added; `_battery_section()` rewritten to prepend the badge on every data-bearing branch (empty-history and real-data), gained a docstring documenting Assumption A1's two-part reasoning (the `corroboration_status()` unknown-is-not-a-failure precedent, plus the real `collect_anomalies()` coupling), and now hoists `battery_status(trend_rows)` to a local so the badge and the returned state are provably the same value. `render()` is byte-identical.
- `battery_sparkline_svg()`: each plotted point now emits a cosmetic `<circle class="sparkline-dot">` marker plus a transparent, enlarged (`r="8"`) `<circle class="sparkline-hit">` hit target carrying `data-mv`, `data-ts` (escaped), `tabindex="0"`, `role="button"`, an `aria-label`, and a `<title>` — the hit targets are emitted last in document order so they receive pointer events over the cosmetic markers. The `<svg>`'s ARIA role changed from `"img"` to `"group"` so the new focusable children stay reachable to assistive tech. The function's own no-external-reference guarantee (`no url(`, `<image`, `<script` in its return value) stays true and its regression check is untouched.
- `_battery_readout_block()` and the conditional `<script src=BATTERY_TREND_SCRIPT_SRC defer></script>` tag: both are emitted by `_battery_section()`, never by `battery_sparkline_svg()`, and only when `sparkline_html` is non-empty — so a single-reading device or the empty-history path stays script-free.
- New constants: `BATTERY_READOUT_ID`, `SPARKLINE_HIT_CLASS`, `SPARKLINE_DOT_CLASS`, `BATTERY_TREND_SCRIPT_SRC` (must equal `companion/app.py`'s `SCRIPT_ROUTE`), `BATTERY_READOUT_PLACEHOLDER`.
- `companion/test_status_pages.py`: fixed `_independent_thresholds_one_warn_one_ok` (now expects two healthy dots, not one); added 8 new checks across both tasks (badge present/healthy, empty-history ok badge/no anomaly banner, real drop drives badge+banner, per-point interactive markup, one-scoped-script/no-inline-handlers, empty-path stays script-free, hostile-timestamp escaping, cross-file Python/CSS/JS contract drift guard). `EXPECTED_CHECK_COUNT` 28 → 36 (the file's real on-disk baseline was already 28, not the plan's stated 25 — Phase 06.3-04 had already restructured `render()` into `layout.stat_tile()` calls by the time this plan executed, exactly the contingency the plan itself pre-registered).

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 - Bug] Task 2 check (b)'s "zero seeded rows" fixture was structurally unachievable as literally specified**
- **Found during:** Task 1, writing `_battery_empty_history_ok_badge_no_anomaly_banner`
- **Issue:** The plan's check (b) specification says: "With zero seeded rows, assert ... `health_page.ANOMALY_BANNER_TEXT` is absent." `_device_section()` and `battery_trend_rows()` both read the same `device_health` SQLite table (`latest_device_health()` vs. `recent_device_health()`). A truly empty state directory therefore makes **both** Battery's trend rows *and* Device check-in's "last seen" empty — and Device check-in's own `staleness_status(None, ...)` maps a never-seen signal to `"warn"`, which trips the anomaly banner for an unrelated reason (`"Device check-in is stale."`), not because of anything Battery-specific. The literal check as specified could never pass without also seeding Device/Pipeline into a healthy state — but a fresh device_health row would then also make `trend_rows` non-empty, defeating the "zero rows" premise.
- **Fix:** Kept the plan's core intent (an ok badge, no error class, no abnormal-drop copy) but proved it two ways: (1) a direct unit-level call to `_battery_section([])` confirming state `"ok"` and no non-healthy class in its markup — genuinely zero battery rows, isolated from Device/Pipeline; (2) a page-level fixture seeding Device check-in and pipeline meta fresh, with a single (non-drop-comparable) battery reading, confirming no error class, no anomaly banner, and no abnormal-drop copy at the full-render level. This isolates the battery-specific guarantee from Device/Pipeline's separate, untouched staleness behavior, which this plan's own `<action>` explicitly forbids modifying.
- **Files modified:** `companion/test_status_pages.py`
- **Verification:** `server/.venv/bin/python3 companion/test_status_pages.py` — the check passes; `_battery_section([])` is asserted directly inside it.
- **Committed in:** `068017e` (Task 1 commit)

**2. [Rule 3 - Blocking] Reworded source comments containing the literal substring `<script`**
- **Found during:** Task 2, running the task's `<verify>` grep gate (`grep -c '<script' companion/pages/health_page.py` must equal `1`)
- **Issue:** Several docstring/comment sentences explaining the "no `<script>` tag" guarantee and the conditional script-emission logic contained the literal substring `<script`, which the hard-fail line-count gate counts alongside the one genuine emitted `<script src=...>` tag.
- **Fix:** Reworded four comment/docstring lines to say "script tag" or "a script tag" instead of the literal `<script` fragment, preserving the same meaning without tripping the gate.
- **Files modified:** `companion/pages/health_page.py`
- **Verification:** `grep -c '<script' companion/pages/health_page.py` returns `1`; `ruff check companion/` still exits 0.
