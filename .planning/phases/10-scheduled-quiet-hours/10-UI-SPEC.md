# Phase 10 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

This phase has **two distinct UI surfaces** with two different design systems. Do not
cross-apply values between them:

1. **Companion web app** (`companion/pages/config_page.py` + `companion/static/style.css`)
   — a new "Quiet hours" fieldset on the existing Settings page. Governed by the
   hand-rolled companion design system (`sketch-findings-skypane` skill). Covered by
   the standard template sections below.
2. **E-ink panel screen** (`server/plane/render.py`) — a new `_build_quiet_hours_canvas()`
   render state on the 1200×1600, 6-color Spectra 6 panel. NOT a web surface — no CSS,
   no shadcn, a constrained 6-index palette and PIL/Pillow drawing primitives instead.
   Covered by its own dedicated section (`## Panel Screen Contract`) below, since the
   template's Design System/Color/Typography tables are web-shaped and do not fit it.

## Interaction Contract (Companion Web App)

Specific to this phase's new fieldset — not covered by the generic template tables above.

**Group placement and structure.** A fourth `.theme-status`-wrapped group, sibling to
the existing Theme/Runway/Diagnostic LED groups, in the same merged `<form
action="/settings">`. No `<fieldset>`/`<legend>` — matches `led_group()`'s established
pattern exactly (a `<div class="theme-status">` with an `<h2 class="text-heading">`
heading, since a `<legend>` only has accessible-name semantics inside a `<fieldset>`,
which this group deliberately does not have).

**Field order (top to bottom), locked by this spec:**
1. `<h2 class="text-heading">Quiet hours</h2>`
2. `<p class="text-label section-caption">{QUIET_HOURS_SECTION_CAPTION}</p>`
3. Enable checkbox (`<label class="led-checkbox">` reused verbatim, or generalized —
   see CSS note below)
4. "Start" `<label><input type="time" name="quiet_hours_start"></label>` — full width,
   own line
5. "End" `<label><input type="time" name="quiet_hours_end"></label>` — full width, own
   line

**Layout: stack Start/End vertically, do NOT put them in a side-by-side flex row.**
`.theme-status__row` exists and could technically wrap two labels horizontally, but this
phase deliberately does not use it here: (a) it avoids any narrow-viewport (320-375px)
wrapping risk from two native time-picker controls plus a gap, and (b) it stays
consistent with 06.6.4.1 (D-01)'s explicit removal of the Settings page's `>=960px`
two-column grid — this page's established direction is single-column, and this new
group should not reintroduce a side-by-side layout the rest of the page just moved away
from.

**Unchecked-checkbox semantics (resolves RESEARCH.md's Open Question 2 / Assumption
A1):** an unchecked "Enable quiet hours" checkbox does **not** disable, grey out, or
otherwise visually suppress the Start/End time inputs. They remain fully interactive
and editable, and `handle_post()` persists any valid edited value regardless of the
checkbox's state. This lets a user pre-configure a window before ever turning it on. Do
NOT add a `disabled` attribute or a `.disabled`/dimmed visual treatment tied to the
checkbox — that would suggest the fields are inert when they are not.

**CSS reuse note (Claude's Discretion on exact class naming, per `10-CONTEXT.md`):**
the checkbox needs the exact same normalization `.led-checkbox` already provides
(shrinks the native checkbox to 16px, relocates the 44px touch-target floor onto the
wrapping `<label>`). Recommended: generalize the existing `.led-checkbox` rule into a
shared `.settings-checkbox` class (rename the selector, update both `led_group()`'s and
the new `quiet_hours_group()`'s markup to use it) now that there are two consumers of an
identical pattern, rather than duplicating the 4-declaration rule under a second
class name. Acceptable fallback: duplicate the rule verbatim under a new
`.quiet-hours-checkbox` class if the executor judges the rename too invasive for this
phase's scope.

**`<input type="time">` inherits the global `input, select` rule cleanly — confirmed,
no override needed.** This is the first `type="time"` input in the codebase
(`10-CONTEXT.md`'s phase-scope note flags this as unconfirmed). Verified against
`companion/static/style.css`'s existing rule (`input, select { min-height: 44px;
min-width: 44px; padding: var(--space-sm); background: var(--color-secondary); border:
1px solid var(--color-border); border-radius: var(--radius-control); color:
var(--color-text); font-size: var(--font-body-size); font-family: var(--font-ui);
accent-color: var(--color-accent); }`): every declaration applies equally to
`type="time"` as to `type="text"`/`<select>` — no type-specific CSS exists that would
need extending. Touch target: 44px min-height/min-width already clears both WCAG 2.5.8
(AA, 24px) and 2.5.5 (AAA, 44px) with no trade needed, unlike the base `button` rule.

**One required CSS addition — `color-scheme`, to keep the native time-picker icon
theme-consistent.** No `color-scheme` property exists anywhere in `style.css` today.
The site's dark/light mode is driven by an explicit `data-ui-theme="light"/"dark"`
attribute (CFG-09) that can diverge from the OS's own `prefers-color-scheme` — without
`color-scheme`, a browser's native time-input picker icon (`::-webkit-calendar-picker-
indicator`) renders using the OS-level scheme, which can produce a dark (hard-to-see)
icon on the dark-mode `--color-secondary` fill, or vice versa, whenever the explicit
override and the OS preference disagree. Add:
```css
html[data-ui-theme="light"] { color-scheme: light; }
html[data-ui-theme="dark"] { color-scheme: dark; }
/* default (data-ui-theme="auto" / no override): follow the OS, same as today's
   prefers-color-scheme-driven default block */
:root { color-scheme: light dark; }
```
Place these alongside the existing `html[data-ui-theme="light"]`/`html[data-ui-theme=
"dark"]` blocks (`style.css` lines ~175-191) — same selectors, one more declaration
each.

**Applies-on-next-poll copy: reuse the existing generic flash message, no new copy.**
Saving the quiet-hours fields reuses the shared `FLASH_KEY_SAVED` flash: "Saved — will
apply on the frame's next scheduled refresh." Per `10-CONTEXT.md` D-02, no distinct
"this could now be hours away" warning is added — this is an accepted, already-decided
trade-off, not an oversight. Do not add a special-cased flash message for this field
group.

### New copy this phase introduces (fieldset-specific)

| Constant | Copy |
|----------|------|
| `QUIET_HOURS_SECTION_HEADING` | "Quiet hours" |
| `QUIET_HOURS_SECTION_CAPTION` | "Pauses the frame's wake, poll and display cycle overnight. Applies on the next scheduled poll, which may now be hours away." |

| Start field label | "Start" |
| End field label | "End" |

`QUIET_HOURS_SECTION_CAPTION` deliberately restates D-02's "applies on next poll, could
now be hours away" fact directly in the caption (unlike Theme/Runway/LED's captions,
which only say "next scheduled poll" without a duration caveat) — this is the one
config field on the page where the wait can meaningfully stretch to hours instead of
minutes, so the caption is the right, low-friction place to set that expectation once,
rather than adding a second flash message.

## Panel Screen Contract (E-Ink, `server/plane/render.py`)

This is the second UI surface (`phase_scope_note`'s point 2). It is **not** a web page:
1200×1600px, a fixed 6-index palette (`IDX_BLACK`, `IDX_WHITE`, `IDX_YELLOW`, `IDX_RED`,
`IDX_BLUE`, `IDX_GREEN`), drawn with PIL/Pillow primitives, with a `SAFE_BOX` margin
contract (`(64, 64, 1136, 1536)`) every element must stay inside. The template's
web-shaped Design System/Color/Typography/Spacing tables above do not apply here — this
section is the complete, self-contained contract for this surface instead.

### Locked decisions (from `10-CONTEXT.md`)

- **D-05:** a dedicated `_build_quiet_hours_canvas()` render state, drawn once at the
  poll that first detects window entry — a deliberate, confirmed exception to the
  project's "no on-screen status text" rule, same class as the Phase 5 battery icon.
- **D-06:** English copy, shape **"QUIET HOURS" / "Back at HH:MM"**.
- **D-07:** no symmetric "waking up" screen at window exit — out of scope for this
  contract entirely.

### Visual structure — locked default: mirror `_build_empty_canvas()` exactly

Per `10-RESEARCH.md` Pattern 3 and Open Question 1, this spec locks the **starting
contract** as structurally identical to the existing empty state, with different copy —
the lower-risk, more-consistent-with-project choice, and the one RESEARCH.md's own
recommendation converges on:

| Property | Value |
|----------|-------|
| Canvas background | Flat `IDX_WHITE` — always, regardless of the currently configured theme (`theme_id` is ignored for this screen, exactly like the empty state) |
| Ink color | `EMPTY_INK` (= `IDX_BLACK`) for all text and icons on this screen |
| Heading text | `"QUIET HOURS"` (all-caps, per D-06's locked shape) |
| Heading font | `PT_SERIF_BOLD`, base size 72px (reuse `EMPTY_HEADING_FONT`'s size), shrunk via `fit_text_size()` down to a 48px floor (reuse `EMPTY_HEADING_MIN_SIZE`) against `safe_width` — same mechanism `_build_empty_canvas()` already uses for its own heading, even though "QUIET HOURS" (11 characters) is short enough that the shrink path is unlikely to trigger in practice; specify it defensively anyway so a future longer variant (e.g. localized text, if ever revisited) degrades gracefully instead of tripping `_assert_in_safe_box()` |
| Body text | `"Back at {HH:MM}"` where `{HH:MM}` is the window's local end time in **Europe/Paris wall-clock time** (from `seconds_until_quiet_hours_end()`'s computed `end_dt.strftime("%H:%M")`) — never UTC, never a raw seconds count. Example: `"Back at 07:00"` |
| Body font | `PT_SERIF_REGULAR`, size 40px (reuse `EMPTY_BODY_FONT`), wrapped via `_wrap_text()` against `safe_width` (defensive; the string is short enough to always fit on one line at 40px within the 1072px safe width) |
| Layout | Centered heading, then `SPACE_SM` (16px) gap, then centered body line(s) — vertically centered as a block in the full 1600px canvas height, using the identical `total_height` / `start_y` centering formula `_build_empty_canvas()` already uses |
| Safe-box assertion | Both the heading bbox and the body-line bbox MUST pass `_assert_in_safe_box()` before drawing, exactly like every other text element in `render.py` |
| Battery-low icon | Bottom-left, in `EMPTY_INK`, drawn via the existing `draw_battery_icon()` call, when `battery_low=True` — same precedent as `_build_empty_canvas()` (a device-health fact independent of what's on screen; the two screens should not diverge on this) |
| Source-fault badge | Bottom-center, in `EMPTY_INK`, drawn via the existing `draw_source_fault_badge()` call, when `source_fault=True` — same precedent |

### Open item this spec deliberately does NOT resolve — flag to planner/executor

**Whether "QUIET HOURS" should be visually distinguishable from the empty state beyond
its text content** (RESEARCH.md Open Question 1) is intentionally left as a real-preview
checkpoint, not resolved here as a fixed pixel spec. This spec's locked default is
"identical structural treatment, different copy" (above) — build that first. Before
treating the screen as final, validate it against a real on-glass or on-screen preview,
following the exact discipline `05-CONTEXT.md` used for the battery icon and
`03-CONTEXT.md` used for the two-flight poster redesign (both cited directly in
`10-CONTEXT.md`). If that review finds "QUIET HOURS" reads as confusingly similar to
"Watching Runway 3" at a glance, the acceptable follow-up adjustments — in order of
preference, least to most invasive — are: (1) nothing, if the differing text alone
proves sufficient in practice; (2) a slightly larger/bolder heading treatment than the
empty state's, still within White/Black; (3) only as a last resort, a distinct flat
fill color for this screen alone (still 6-palette-legal, still passing
`_assert_legal_palette()`). Do not skip the real-preview check and ship option (2) or
(3) speculatively — this spec's job is to hand the executor a concrete option (1) to
build and test against, not to pre-select a heavier option nobody has looked at yet.
