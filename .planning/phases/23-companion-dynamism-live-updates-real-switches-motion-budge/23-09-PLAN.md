<objective>
The save bar is the most-iterated component in this app: four recorded design
iterations, a P0 defect in Phase 22 when its hiding gate was keyed to a proxy, a
z-index reversal argued through its own escape clause, and a measured content
clearance at both breakpoints. It currently appears instantly and its count
changes instantly.

Purpose: D3 asks for the bar to slide in with an animated count and for
"Saving… / Saved ✓" states. Two of those are straightforward CSS and one is not:
saving is a full form POST that replaces the document, so a "Saved ✓" state on the
bar could only exist by persisting a flag across a navigation — and this app holds
no client state at all, deliberately (grep finds no `localStorage` or
`sessionStorage` anywhere). The honest delivery is a "Saving…" label while the
request is in flight and the existing confirmation flash as the "Saved ✓", on the
page the browser actually lands on.
Output: an entrance, a count that moves, an in-flight label, and a confirmation
that arrives where the user's eyes are.
</objective>

<no_js_floor>
Unchanged, and it is the floor this app has already broken once.

The save bar is itself a script-only enhancement: with scripts blocked it never
appears, and `[data-static-save-fallback]`'s always-server-rendered Save button is
the only way to save — which is exactly why 22-01/B1 re-keyed the hide gate from
"some script ran" to "the bar exists and has been shown". This plan does not touch
that gate and must not.

The "Saving…" label is applied by script to a control that, with no script, simply
submits with its normal label. The animation is CSS on a component that, with no
script, is never rendered visible. Nothing here adds a control, and nothing
changes what a scripts-blocked user can do: the acceptance criteria re-assert the
fallback Save at 360 px rather than trusting that an animation could not have
reached it.

One specific trap to avoid: `.dirty-bar`'s base rule declares `display`, which is
why it needs its own `[hidden]` selector — an author `display` beats the UA
`[hidden] { display: none }` regardless of source order. Phase 22 found that class
of defect on the login card, where it produced a visible control that did nothing.
An entrance animation that sets `display` or `visibility` on the bar must keep
that `[hidden]` override intact and must be asserted against it.
</no_js_floor>

Binding constraints:
- Spend the two duration tokens. A third would break plan 23-01's budget and its
  guard.
- Do not animate `height` or `max-height` on the bar. `.js .mobile-nav`'s
  `transition: none` at style.css:763-767 is the documented precedent for why a
  size-interpolating transition running at 0.01ms can strand an intermediate
  computed value — a stranded save bar is a blocked save.
- The count is inside a `role="status"` region. An animation that rewrites the
  text more than once per change would announce more than once. Animate the
  element's presentation; change the text exactly once, when the number changes.
- The "Saving…" label must not break `submit-guard.js`. Read its header before
  writing: it disables from a zero-delay timer precisely so the submitter's
  name/value survives. A relabel that runs inline is safe for a control whose
  name/value is not load-bearing — but `.dirty-bar__save` must be checked, not
  assumed, and the finding stated.
- French first, not afterwards: every new visible word is a catalogue entry, and
  `test_i18n.py` Check 6 will demand one for any English fallback literal added to
  either script.
