# Phase 06.3: Companion UI visual design and desktop layout pass - Research

**Researched:** 2026-08-28
**Domain:** Server-rendered HTML/CSS (Python stdlib `http.server`, no framework, no build step) — visual refresh + CSS-Grid desktop dashboard layout
**Confidence:** HIGH

## Summary

This phase touches exactly four files: `companion/layout.py` (the shared page shell and component library), `companion/static/style.css` (the single stylesheet), and two page modules — `companion/pages/health_page.py` (stat-tile wrapping) and `companion/pages/history_page.py` (the `.data-table-wrap` bug fix). No other page module (`config_page.py`, `airlines_page.py`, `preview_page.py`) needs a Python change beyond what CSS alone can express, because `06.3-UI-SPEC.md`'s Layout Contract keeps their body markup unchanged and layers desktop-only presentation on top via `page_shell()` and new CSS rules.

The codebase's existing architecture makes this phase materially lower-risk than a typical "add a sidebar" task: every one of the 5 pages renders its **body only** (`render(ctx) -> str`, per `companion/pages/__init__.py`'s documented contract) and `companion/app.py` wraps that body in `layout.page_shell()` exactly once per response, at 10 call sites. `page_shell()` is therefore the **single, already-established integration point** for the sidebar nav — no page module needs to change to gain it, confirmed by reading all 5 page modules and `companion/pages/__init__.py`'s contract docstring.

The two genuine risks this research surfaces that the UI-SPEC does not call out: (1) a CSS Grid "blowout" hazard where the Battery-trend stat tile's nested `<table class="data-table">` (which sets `min-width: max-content`) can force its grid track wider than the `minmax(240px, 1fr)` track sizing intends, unless the tile itself gets an explicit `min-width: 0` override (a well-known CSS Grid default-sizing gotcha); and (2) this codebase's test harness is pure string/markup assertion (stdlib `unittest`-free, hand-rolled `check()` calls) with **no precedent for asserting computed CSS/breakpoint behavior** — the 960px dashboard activation itself cannot be exercised by the existing automated suite and needs a manual/visual verification step, not a new automated check.

**Primary recommendation:** Extend `page_shell()` in place (new `sidebar_nav()` + a CSS Grid dashboard-shell wrapper around the existing header/main), add a `stat_tile()` builder to `layout.py` that wraps content exactly the way `health_page.py`'s existing `_section()` already does (raw, pre-escaped `content_html` passed through unescaped), and fix `history_page.py`'s `_history_table_html()` with a two-line wrap-div change. All CSS work lands in `style.css` following its existing section-comment/token conventions — no new file, no new tooling.

### Pattern 1: Single-choke-point page shell extension

**What:** `page_shell()` is the only place that assembles `<header>`/`<nav>`/`<main>`. Because every page module returns body-only markup (`companion/pages/__init__.py`'s documented `render(ctx) -> str` contract), adding sidebar markup here cannot desync from any individual page.
**When to use:** Any phase-wide chrome change (nav, theme toggle, page title) belongs in `layout.py`, never duplicated into a page module.
**Example (current `page_shell()` — the site to extend, not replace):**
```python
# Source: companion/layout.py lines 97-138 (read directly this session)
def page_shell(title, active, body, ui_theme="auto", flash=None, banner=None):
    ...
    return (
        "<!DOCTYPE html>\n"
        '<html lang="en" data-ui-theme="%s">\n'
        "<head>...</head>\n"
        "<body>\n"
        '<header class="site-header">\n'
        '<span class="site-title">%s</span>\n'
        '<nav class="nav-bar">%s</nav>\n'
        "%s\n"                # theme_form_html
        "</header>\n"
        '<main class="page-content">\n'
        "%s\n%s\n%s\n"         # flash_html, banner_html, body
        "</main>\n"
        "</body>\n</html>\n"
    ) % (...)
```
**Implementation approach for this phase:** Wrap the existing `<header>`+`<main>` pair in a new outer `<div class="dashboard-shell">` and add a second, vertical nav block (`sidebar_nav()`) plus a second `theme_form_html()` call before `</div>`. Both the horizontal `.nav-bar` (existing) and the new vertical sidebar nav render into the DOM on every response; `@media (min-width: 960px)` CSS decides which is visible (`display: none` on the loser at each breakpoint — see Pitfall 2 below for why `display: none`, not `visibility: hidden`, is required here).

### Pattern 2: Raw-content-html tile wrapper (matches `_section()`'s existing convention exactly)

**What:** `health_page.py`'s existing `_section(name, content_html)` helper (line 338 of `health_page.py`) interpolates `content_html` **without** escaping it — this is intentional, because `content_html` is always the pre-built, already-escaped output of `layout.status_dot()`, `layout.data_table()`, or hand-built `<p>` strings that already ran their own values through `escape_html()`. A new `stat_tile()` builder must follow the exact same convention.
**When to use:** Whenever wrapping already-safe markup in a new frame element — never re-escape.
**Example (current pattern to mirror):**
```python
# Source: companion/pages/health_page.py lines 338-344 (read directly this session)
def _section(name, content_html):
    return (
        '<section class="page-section">'
        '<h2 class="text-heading">%s</h2>'
        "%s"
        "</section>"
    ) % (escape_html(name), content_html)
```
**Recommended `stat_tile()` shape (in `layout.py`, mirroring this convention):**
```python
_STAT_TILE_BORDER_CLASSES = {
    "ok": "stat-tile--ok",
    "warn": "stat-tile--warn",
    "error": "stat-tile--error",
    # falls back to accent-neutral (no dict entry needed if the CSS default
    # rule on .stat-tile is the accent-neutral top border)
}

def stat_tile(caption, content_html, status=None):
    """A card wrapper around already-built, already-escaped `content_html`
    (never re-escapes it — same convention health_page.py's `_section()`
    already established). `caption` is escaped here."""
    css_class = "stat-tile " + _STAT_TILE_BORDER_CLASSES.get(status, "stat-tile--accent")
    return (
        '<div class="%s">'
        '<p class="text-label stat-tile__caption">%s</p>'
        "%s"
        "</div>"
    ) % (css_class, escape_html(caption), content_html)
```
This keeps `status_dot()`'s unescaped `<span class="dot ...">` embedding (used throughout Device/Pipeline/Corroboration sections and in History's Corroboration column) completely unaffected — `stat_tile()` never touches `content_html`, exactly like `_section()` today.

### Pattern 3: `auto-fit`/`minmax` dashboard grid (reuses `.gallery-grid`'s established idiom)

**What:** The codebase already has exactly one CSS Grid (`.gallery-grid`, `style.css` lines 363-367), using `repeat(auto-fill, minmax(160px, 1fr))`. `06.3-UI-SPEC.md` specifies `repeat(auto-fit, minmax(240px, 1fr))` for the new dashboard grid — same idiom, different function (`auto-fit` vs `auto-fill`) and minmax floor, which is a real, deliberate distinction (see Pitfall 1) not a typo to "fix" into consistency with `.gallery-grid`.
**Example (current precedent to extend, not copy verbatim):**
```css
/* Source: companion/static/style.css lines 363-367 (read directly this session) */
.gallery-grid {
  display: grid;
  grid-template-columns: repeat(auto-fill, minmax(160px, 1fr));
  gap: var(--space-md);
}
```

### Anti-Patterns to Avoid

- **Duplicating `NAV_TABS` iteration logic between `_nav_html()` and `sidebar_nav()` without extraction:** Both need the same active-tab class logic and the same escaped route/label pairs. Extract a shared internal helper (e.g. `_nav_links(active)` returning a list of `(css_class, route, label)` tuples, or a list of pre-built `<a>` strings that each caller wraps differently) so a future route addition or escaping fix only needs to land in one place. `06.3-UI-SPEC.md` explicitly requires "reusing the existing `NAV_TABS` constant — no duplicated route list" — extend that discipline to the per-link *rendering* logic too, not just the data list.
- **Re-escaping `content_html` inside `stat_tile()`:** Would double-encode `status_dot()`'s intentionally-raw `<span>` markup, printing visible `&lt;span...&gt;` text instead of a colored dot — this is exactly the bug `06.3-CONTEXT.md`'s canonical refs flag as the risk to avoid.
- **Giving the dashboard sidebar's duplicate theme-form/nav a different `name`/`action` than the header copy:** Both must post to the same `/ui-theme` action and use the same `name="ui_theme"` field so `companion/app.py`'s existing POST handler (unchanged by this phase) keeps working regardless of which copy was visible when submitted.
- **Hiding the non-active nav/theme-form copy with `visibility: hidden` or `opacity: 0` instead of `display: none`:** leaves it focusable/tabbable and in the accessibility tree, producing duplicate landmarks and a confusing tab order for keyboard/screen-reader users. Must be `display: none` (see Pitfall 2).

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Responsive multi-column grid | A hand-computed pixel-width column system, or JS-based layout switching | Native CSS Grid (`repeat(auto-fit, minmax(...))`), exactly as `.gallery-grid` already does | Zero-JS constraint (no build step, no framework) makes CSS Grid the only real option, and the codebase already has a working, tested precedent to extend |
| Horizontal-scroll table cropping fix | A JS resize observer or a redesigned table markup | The already-proven `.data-table-wrap { overflow-x: auto }` pattern (`layout.data_table()` lines 200-207) | This exact problem was already solved once for Airlines/Health; History's bug is that the fix was never applied there, not that the fix doesn't exist |
| Active-nav-tab state | Client-side JS reading `window.location` | Server already computes `active` per-request (`companion/app.py` passes it into `page_shell()`) | The server always knows which page it's rendering; there is no client-side routing to duplicate |

**Key insight:** Every "don't hand-roll" item in this phase already has a working precedent somewhere else in this same file/module — the task is consistent extension, not invention.

## Common Pitfalls

### Pitfall 1: CSS Grid track blowout from the nested `<table>` inside the Battery-trend stat tile

**What goes wrong:** `06.3-UI-SPEC.md`'s Component Patterns table says the Battery-trend tile's existing table+sparkline (`_battery_section()`'s unchanged output) renders "inside the Battery-trend stat tile's card frame instead of a bare section." That table is built by `layout.data_table()`, which sets `min-width: max-content` on `.data-table` (`style.css` line 328) specifically so it never crops (Pitfall this exact phase is fixing for History). Inside a `grid-template-columns: repeat(auto-fit, minmax(240px, 1fr))` track, a grid item's default `min-width` is `auto`, which means the browser sizes the *track* to fit the item's intrinsic content width — and `min-width: max-content` on a nested table is about as wide an intrinsic-content signal as CSS has. The Battery tile (and therefore its whole grid row) can end up far wider than 240px, breaking the "multi-column stat-tile grid" visual the whole phase is for.
**Why it happens:** CSS Grid items don't shrink below their content's intrinsic minimum size unless explicitly told to (`min-width: 0` or `min-inline-size: 0` on the grid item, or `overflow` on an ancestor establishing a new formatting context) — a well-documented, frequently-hit CSS Grid default-sizing gotcha, not specific to this codebase.
**How to avoid:** Add `min-width: 0` (or `overflow: hidden`/`min-inline-size: 0`) to `.stat-tile` in the new CSS rules, so `.data-table-wrap`'s own `overflow-x: auto` (already present, line 322-324) is what handles the width instead of the grid track being forced to grow. Verify visually at 960-1100px viewport widths specifically (the narrowest range where 3-4 tiles must actually fit side by side) once implemented — this cannot be caught by the string-based test harness (see Pitfall 3).
**Warning signs:** The Health page's dashboard grid renders correctly on a very wide monitor but the Battery tile visibly overflows its column or forces horizontal page scroll at exactly the 960-1200px range.

### Pitfall 2: Duplicate interactive elements (nav links, theme-toggle buttons) left focusable when hidden by breakpoint

**What goes wrong:** Because `page_shell()` must render both the horizontal `.nav-bar` (mobile, <960px) and the new vertical sidebar nav (desktop, ≥960px) in the same DOM (no server-side viewport detection is possible with a stdlib HTTP server), whichever one is "hidden" by CSS at a given viewport width can still receive keyboard focus (Tab key) if hidden the wrong way — a screen-reader or keyboard user tabbing through a desktop-width page would hit 5 invisible nav links and 3 invisible theme buttons before reaching the visible sidebar copy.
**Why it happens:** `visibility: hidden` and `opacity: 0` remove an element visually but leave it in the tab order and (for `opacity`) the accessibility tree; only `display: none` (or newer `content-visibility`/`hidden` attribute equivalents) actually removes an element from both.
**How to avoid:** Use `display: none` on the losing nav/theme-form copy at each breakpoint (e.g. `.dashboard-sidebar { display: none } @media (min-width: 960px) { .dashboard-sidebar { display: flex } .site-header .nav-bar, .site-header .theme-form { display: none } }`). Confirmed D-22's 44px tap-target and existing `:focus-visible` outline rules (style.css lines 136-142) stay correct either way since they're unconditional on any visible element.
**Warning signs:** Tabbing through the page at desktop width lands on invisible links before the visible sidebar nav.

### Pitfall 3: Assuming the existing test harness can verify breakpoint/CSS behavior

**What goes wrong:** A plan that writes a `check()` asserting "the dashboard grid activates at 960px" against `companion/static/style.css`'s raw text (e.g. `"960px" in css_source`) tests that the *string* "960px" exists somewhere in the file — not that the layout actually behaves correctly at that width. A plan that assumes Playwright/Selenium/a headless browser is available to genuinely test rendered layout would also be wrong: no such tool exists in this repo (grepped: no `package.json`, no browser-automation dependency anywhere in the codebase).
**Why it happens:** Every existing companion test (`test_companion_app.py`, `test_status_pages.py`, `test_view_pages.py`, `test_config_page.py`) is stdlib-only markup/string assertion against `render(ctx)` return values or raw HTTP responses — verified directly: `grep` for `style.css` across all four test files finds only a content-type check (`GET /static/style.css succeeds ... returns a CSS content type`, `test_companion_app.py` line 607-617) and a "the stylesheet link exists in the document" check (line 444) — never any assertion about what a CSS rule *does* at a given viewport.
**How to avoid:** Scope automated tests to what the harness can actually verify — new markup shape (sidebar nav emits `aria-label="Primary navigation"` and all 5 `NAV_TABS` links; `stat_tile()` escapes its caption and applies the right status class; `_history_table_html()` now contains `<div class="data-table-wrap">`). Treat the actual 960px breakpoint's visual correctness (including Pitfall 1's grid-blowout risk) as a **manual/visual verification step** — this project's `human_verify_mode: "end-of-phase"` config setting already expects this pattern (see Validation Architecture below).
**Warning signs:** A plan task tries to assert computed CSS behavior through a Python string check.

### Pitfall 4: `.page-section` and `.gallery-tile` currently have zero CSS rules

**What goes wrong:** Assuming `.page-section` (used by `health_page.py`, `airlines_page.py`, `config_page.py`, `preview_page.py`) already carries spacing/border styling that the new `.stat-tile` treatment can simply extend. It doesn't — grepped `style.css` directly: `.page-section` and `.gallery-tile` (used by `preview_page.py`'s gallery tiles) appear **only** in the Python page modules, never once in `style.css`. Today's section spacing comes entirely from default browser margins on the `<h2>`/`<p>` elements inside them.
**Why it happens:** Easy to assume a class referenced 6+ times across the codebase has a corresponding CSS rule; it doesn't in this specific case.
**How to avoid:** When adding `--color-border` card treatment to the mobile/tablet "stacked `_section()` blocks" (per `06.3-UI-SPEC.md`'s Mobile/tablet floor: "still get the new Border/card treatment for visual consistency, just stacked instead of gridded"), a real new `.page-section` CSS rule (border, padding) needs to be added — this is new CSS, not an extension of an existing untouched rule.
**Warning signs:** Sections look unstyled/unbordered below 960px even after the visual refresh ships.

## Open Questions

1. **Does `_battery_section()`'s returned `table_html + sparkline_html` need any structural change to fit inside a 240px-minimum tile, beyond the `min-width: 0` CSS fix in Pitfall 1?**
   - What we know: The UI-SPEC explicitly says the mechanism (SVG sparkline + table) is unchanged, just re-parented into a tile frame. The sparkline SVG has a fixed `viewBox="0 0 300 60"` (`battery_sparkline_svg()`, `health_page.py` line 267) — a fixed-width SVG inside a narrower tile will need `width: 100%` / `height: auto` CSS (the SVG already has explicit `width`/`height` attributes on the `<svg>` element itself, which would need a CSS override, e.g. `.stat-tile svg { width: 100%; height: auto }`, to actually shrink responsively).
   - What's unclear: Whether 300px fixed-width SVG plus a `min-width: max-content` table together, even with `min-width: 0` on the tile, still look acceptable at exactly 240px tile width, or whether the Battery tile needs to be allowed to span 2 grid columns (`grid-column: span 2`) as a deliberate exception.
   - Recommendation: Treat as an implementation/verification detail for the execute phase, not a planning blocker — flag for a manual visual check at the narrowest dashboard width (960-1100px) per Pitfall 3.

2. **Should the shared `_nav_links()` extraction (Anti-Patterns section) happen in this phase, or is a small amount of duplication between `_nav_html()` and `sidebar_nav()` acceptable?**
   - What we know: `06.3-UI-SPEC.md` only mandates reusing the `NAV_TABS` *data* constant, not the rendering logic.
   - What's unclear: Whether the planner judges the extraction worth the extra diff surface in a phase already touching `layout.py` significantly.
   - Recommendation: Low-cost, low-risk refactor (both functions are ~10 lines); recommend doing it, but not a blocker if the planner chooses simple duplication instead.
