# Phase 06.3: Code Review Report

**Reviewed:** 2026-08-28
**Depth:** standard
**Files Reviewed:** 10
**Status:** issues_found

## Summary

Reviewed the companion service's escaped page-shell/component library (`layout.py`), the hand-written stylesheet (`style.css`), four page modules (`history_page.py`, `config_page.py`, `health_page.py`, `airlines_page.py`), and their four stdlib-only contract-test harnesses.

The Python is disciplined: every dynamic value reaches HTML through `escape_html()` or a small set of pre-escaped component builders, `_safe_query()` degrades every database section independently instead of faulting the whole page, and the four test harnesses' `EXPECTED_CHECK_COUNT` constants were verified by hand-counting every `check()` call in each file — all four match, so the suites cannot be silently under-covering their own claimed check counts. `history_page.py`'s reuse of `panel_render.ROUTE_FALLBACK_TEXT` for a missing airline was cross-checked against `server/plane/render.py`'s actual fallback condition and is semantically correct, not a copy-paste mismatch.

The stylesheet is where the real defects are: two CSS cascade/specificity bugs silently defeat visual states the code's own comments claim are correct. Both are provable from the cascade rules alone (no browser needed), and neither is caught by the Python test suites, since none of them assert on computed CSS.

## Critical Issues

### CR-01: `.page-section`'s border shorthand silently overrides `.banner--anomaly`'s destructive left border, despite a comment claiming the opposite

**File:** `companion/static/style.css:290-306,472-482`
**Issue:** `health_page.py`'s `_source_fault_block()` (the ADS-B "source outage" alert, D-14/CFG-05) renders `<section class="page-section banner banner--anomaly">`. `.banner--anomaly` (style.css:300-302, defined first) sets `border-left-color: var(--color-destructive)`. `.page-section` (style.css:477-482, defined later in this phase's own `30e3f18` commit) sets the shorthand `border: 1px solid var(--color-border)`, which — per the CSS border shorthand — resets `border-left-color` on all four sides, including the left edge. Both selectors are single classes (equal specificity, 0-1-0); with equal specificity, the declaration that appears later in source order wins for a given property. Because `.page-section` appears after `.banner--anomaly` in the stylesheet, its shorthand's implicit `border-left-color: var(--color-border)` wins over `.banner--anomaly`'s explicit `border-left-color: var(--color-destructive)`.

The result: the source-fault outage banner renders with the same neutral gray border as an ordinary page section, not the 4px destructive-red left border the design system (and the code's own comment) says it has. `--color-destructive` (style.css:57/70/84/96) is used nowhere else in this file, so this is the one production combination the variable exists for, and it is unreachable as written.

The comment directly above `.page-section` (style.css:474-476) explicitly asserts the opposite of what the cascade actually does: *"health_page.py's source-fault block combines page-section with banner banner--anomaly, so its 4px destructive left border keeps overriding this rule's left edge — that is intended, not a conflict."* This is backwards — `.page-section` overrides `.banner--anomaly`, not the other way around.

**Fix:** Scope `.page-section`'s border so it never touches `border-left` when combined with a banner, or raise the anomaly banner's specificity/order so it wins. The smallest fix that preserves the shared card treatment:
```css
.page-section {
  padding: var(--space-md);
  margin-bottom: var(--space-lg);
  border-top: 1px solid var(--color-border);
  border-right: 1px solid var(--color-border);
  border-bottom: 1px solid var(--color-border);
  border-left: 1px solid var(--color-border);
  border-radius: 2px;
}

/* Combined with .banner--anomaly / .banner--flash, restore the banner's
   left-edge accent color — .page-section's own border-left must never
   win this fight. */
.page-section.banner--anomaly {
  border-left-color: var(--color-destructive);
}
.page-section.banner--flash {
  border-left-color: var(--color-accent);
}
```
(Longhand sides avoid resetting `border-left-color` implicitly; the two combinator rules make the intended override explicit and specificity-safe regardless of future reordering.)

### CR-02: `button[type="submit"]`'s higher specificity defeats `.theme-option`/`.theme-option--active`, making the CFG-01 theme picker's active-state indicator effectively invisible

**File:** `companion/static/style.css:210-224,352-355`
**Issue:** `layout.py`'s `_theme_form_html()` renders each theme choice as `<button type="submit" name="ui_theme" value="..." class="theme-option[ theme-option--active]">`. `.theme-option` sets `background: transparent; color: var(--color-text)`, and `.theme-option--active` sets `border-color: var(--color-accent); color: var(--color-accent)` for the currently-selected theme — the only visual signal distinguishing the active theme from the other two.

`button[type="submit"]` (style.css:352-355, commented `/* Primary button — the one non-nav, non-link accent use. */`) is an element+attribute selector, specificity (0,1,1) — strictly higher than `.theme-option`/`.theme-option--active`'s single-class specificity (0,1,0). Because every theme button is a `<button type="submit">`, this rule wins regardless of source order:
- `background: var(--color-accent)` overrides `.theme-option`'s `background: transparent` on **all three** theme buttons (not just the active one).
- `color: var(--color-dominant)` overrides `.theme-option--active`'s `color: var(--color-accent)`, so the active button's text color is never actually accent-colored.

Net effect: all three theme buttons render with an identical accent-colored background, and the "active" one additionally gets `border-color: var(--color-accent)` — an accent-colored border on an accent-colored background, i.e. no visible border at all. The only surviving distinction is that the two *inactive* buttons have a light gray border (`var(--color-secondary)`) against the accent fill, while the *active* button has no visible border edge. This is backwards from a usability standpoint (the selected option should be the one that stands out) and does not match the "distinct active state" behavior `06.3-UI-SPEC.md`'s Component Patterns and this phase's own accent-color contract describe.

This also means `button[type="submit"]` is not "the one... accent use" its own comment claims — it unconditionally applies to every submit button on every page (Save Settings, Save LED Setting, Trigger Poll Now, and all three theme-picker buttons), four to six accent uses beyond the five enumerated at the top of the file.

**Fix:** Give the primary-action styling to a dedicated class instead of an attribute selector, so it stops shadowing component-specific button styling:
```css
/* Primary button — apply only where the caller opts in. */
.btn-primary {
  background: var(--color-accent);
  color: var(--color-dominant);
}
```
and update `layout.py`'s "Save Settings" / "Save LED Setting" / enabled "Trigger Poll Now" buttons to carry `class="btn-primary"` explicitly, while leaving `.theme-option`/`.theme-option--active` alone (they already carry their own distinct class-based styling and no longer need to fight a higher-specificity attribute selector). If `button[type="submit"]` styling must stay attribute-based for now, at minimum add an explicit override so the theme picker regains its own colors:
```css
.theme-option[type="submit"] {
  background: transparent;
  color: var(--color-text);
}
.theme-option--active[type="submit"] {
  color: var(--color-accent);
}
```

## Warnings

### WR-01: `history_page.py`'s row-loop variable is misleadingly named `cell` for a whole row dict

**File:** `companion/pages/history_page.py:137`
**Issue:** `for index, cell in enumerate(formatted_rows):` iterates over `formatted_rows`, a list of per-row dicts produced by `format_event_row()` (each holding `ts`, `callsign`, `hex`, etc.). The loop variable is named `cell`, but every line inside the loop (`cell["ts"]`, `cell["callsign"]`, ...) treats it as a whole row, and the actual per-column values built a few lines later are locally named `cells` (plural, a tuple of `<td>` strings). The near-identical names (`cell` vs `cells`) for two different things — one row-dict, one list of column strings — makes the function harder to scan correctly under review and easy to typo against during a future edit.
**Fix:** Rename the loop variable to `row` (matching `data_table()`'s own `for row_index, row in enumerate(rows)` naming in `layout.py`, which this function is documented as mirroring):
```python
for index, row in enumerate(formatted_rows):
    row_class = "row-alt" if index % 2 else "row"
    cells = (
        '<td class="mono">%s</td>' % escape_html(row["ts"]),
        ...
```

### WR-02: `.theme-option`/`.theme-option--active` have no `aria-current`/`aria-pressed` state, so the active theme is invisible to assistive technology even once the CSS bug (CR-02) is fixed

**File:** `companion/layout.py:126-137`
**Issue:** `_theme_form_html()` marks the active theme purely via a CSS class (`theme-option--active`). A screen-reader user gets no programmatic signal for which of the three submit buttons represents the currently-selected theme — there is no `aria-pressed="true"`, `aria-current="true"`, or equivalent. This is a real a11y gap independent of the CSS specificity bug above: even after CR-02 is fixed and the active button is visually distinguishable, it remains indistinguishable to non-visual users.
**Fix:**
```python
for choice in UI_THEME_CHOICES:
    is_active = choice == resolved_theme
    css_class = "theme-option theme-option--active" if is_active else "theme-option"
    options.append(
        '<button type="submit" name="ui_theme" value="%s" class="%s" aria-pressed="%s">%s</button>'
        % (
            escape_html(choice), css_class, "true" if is_active else "false",
            escape_html(choice.capitalize()),
        )
    )
```

## Info

### IN-01: `button[type="submit"]`'s comment ("the one non-nav, non-link accent use") is inaccurate — it matches every submit button on the site

**File:** `companion/static/style.css:351`
**Issue:** Independent of CR-02's visual bug, the comment's factual claim is wrong on its own terms: `button[type="submit"]` is an attribute selector that matches "Save Settings", "Save LED Setting", the enabled "Trigger Poll Now" button, and all three theme-picker buttons — not "the one" button. This file's header comment (lines 10-15) separately states accent is "reserved to exactly five uses" and lists them; `button[type="submit"]`'s reach quietly exceeds that enumerated list. Whether or not CR-02 is fixed with a dedicated `.btn-primary` class, the stale comment should be corrected or the selector narrowed to match what it claims.
**Fix:** Update the comment to reflect what the selector actually targets, or (preferably, see CR-02) replace the attribute selector with an opt-in class so the comment and the code agree by construction.

### IN-02: `history_page.py`/`health_page.py` reach into `server.plane.render`'s underscore-prefixed `_TYPE_DISPLAY_LABELS`

**File:** `companion/pages/history_page.py:98`
**Issue:** `panel_render._TYPE_DISPLAY_LABELS.get(type_key, aircraft_type)` accesses a private (underscore-prefixed) module attribute of `server.plane.render` from an external module. This is explicitly a deliberate, documented reuse strategy per this file's own docstring (and is pinned by `test_view_pages.py`'s `_history_page_never_redefines_type_labels` regression guard), so it is not a defect — but it is worth naming as a maintainability note: nothing in `server/plane/render.py` marks `_TYPE_DISPLAY_LABELS` as a stable cross-module contract, so a future rename/refactor of that private attribute inside `render.py` would silently break `history_page.py` without any signal from `render.py`'s own public API.
**Fix:** Consider exposing a small public alias (e.g. `TYPE_DISPLAY_LABELS = _TYPE_DISPLAY_LABELS`) in `server/plane/render.py` so the cross-module dependency is declared explicitly rather than inferred from a private name, or add a comment in `render.py` itself flagging that `_TYPE_DISPLAY_LABELS` is a de facto public contract consumed by `companion/pages/history_page.py`.
