# Phase 06.3: Companion UI visual design and desktop layout pass - Context

**Gathered:** 2026-08-28
**Status:** Ready for planning

<domain>
## Phase Boundary

A full visual refresh (colors/type/spacing) of the companion web app, plus a genuine desktop-width layout — a dashboard treatment (sidebar nav + multi-column stat tiles), not just a wider single column — replacing today's identical fluid single-column layout at every viewport width. Also closes a real, pre-existing gap found during investigation: the mobile table-crop fix that STATE.md describes as covering "Airlines/History" only actually reached Airlines (and Health) — History's own hand-rolled table never got it.

**This explicitly supersedes `06-CONTEXT.md`'s D-21** ("the page is a plain utility tool... deliberately less visual investment than the physical frame's own carefully-tuned poster aesthetic... allowed to just be functional"). The user, having now lived with the utility-page aesthetic through Phase 6's real build and sign-off, confirmed a full visual refresh is wanted — not just a layout pass. This is a deliberate, confirmed reversal, not an oversight; treat `06-CONTEXT.md`'s D-21 as historical record of the *original* scoping decision, now superseded for this phase only.

</domain>

<decisions>
## Implementation Decisions

### Scope and depth
- **D-01 (supersedes `06-CONTEXT.md` D-21):** Go beyond layout — revisit colors, type, and spacing too. Not a pure utility page anymore; deliberate additional visual investment, confirmed explicitly after being offered the smaller "layout only, keep current identity" alternative.
- **D-02:** Desktop treatment is a **true dashboard layout** — sidebar navigation plus multi-column stat tiles/groups — not merely a centered, wider single column. This is a bigger structural change than a `max-width` tweak: it changes the page shell's navigation model, not just its content width.
- **D-03:** Fold in fixing **History's incomplete mobile table-crop fix** as part of this same pass (`companion/pages/history_page.py`'s hand-rolled table never received the `data-table-wrap` treatment Airlines/Health already have).

### Carried forward from `06-CONTEXT.md` (still valid, not re-discussed)
- **D-22:** Must stay responsive on mobile — basic adaptation (readable text, tappable controls). A dashboard/sidebar layout is a desktop-width addition, not a replacement for the existing mobile-first fluid layout; the two need to coexist via a real breakpoint.
- **D-23:** UI copy stays in English.
- **D-24:** Keep a simple "SkyPane" title/header — no logo or elaborate branding, even under the fuller visual refresh.
- **D-25:** Multi-page structure (Config / Health / Airlines / History / Preview) stays — the sidebar nav this phase adds is a new *presentation* of that existing page set on wide viewports, not a restructuring of the pages themselves.

### Claude's Discretion
- Exact new color palette, typography choices, and spacing scale values — no specific aesthetic direction given beyond "full refresh"; stay consistent with the existing CSS-custom-property token architecture (extend/replace token values rather than hardcoding new ones inline).
- The desktop breakpoint's exact pixel value and which pages get which stat-tile groupings.
- Whether the sidebar nav replaces or supplements the current top `.nav-bar` at narrow widths (the existing nav-bar's horizontal-scroll fallback below 480px should likely stay for mobile either way).

</decisions>

<code_context>
## Existing Code Insights

### Reusable Assets
- The CSS-custom-property token architecture already in place (spacing scale, type scale, light/dark tokens) — a visual refresh can restyle by changing token *values*, not rewriting every rule that consumes them.
- `.gallery-grid` — the one existing CSS grid in the codebase, a working precedent for the new dashboard multi-column layout.
- `layout.data_table()` / `.data-table-wrap` — the correct, already-proven pattern for History's fix; the task is replicating it there, not inventing a new approach.

### Established Patterns
- Every page currently renders through `layout.page_shell()`, so a sidebar-nav addition has exactly one integration point rather than five per-page changes.
- The 480px mobile-nav breakpoint is the only existing width-based CSS branch — the new desktop breakpoint is a genuinely new pattern for this file, not an extension of an existing one.

### Integration Points
- `companion/layout.py`'s `page_shell()` — where sidebar-nav markup would need to slot in alongside (or replacing, at wide widths) the existing `.nav-bar`.
- `companion/static/style.css` — single stylesheet, single place to add the desktop breakpoint and dashboard-grid rules.
- `companion/pages/history_page.py`'s `_history_table_html()` — needs to gain the wrap div without losing its unescaped `status_dot()` embedding (the exact reason it couldn't use `data_table()` directly the first time).

</code_context>
