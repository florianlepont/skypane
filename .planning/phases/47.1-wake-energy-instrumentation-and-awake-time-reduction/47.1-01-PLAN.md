Create 47.1-DECISIONS.md and hardware/WAKE-ENERGY.md (English). Content to record, each item dated and labelled owner-reported where it came from the owner:

1. Owner decisions of 2026-11-03 (owner-reported, quoted from 47.1-CONTEXT.md): WAKE-03 retargeted on redraw wakes; the freeze list measured_fields_freeze.json may be amended to accept the new telemetry header (the agreement is written into the pull request by plan 03); first firmware release is instrumentation only, after the 2026-11-07 Phase 47 bilan, with the owner's approval at each gate (signing, then production); the reduction release is separate and comes after the recorded baseline; a plane can pass every 30 s, so fewer redraws is a product choice put to the owner (in Phase 47.2), not an assumed implementation; retrospective access-log counts of image downloads were declined as unnecessary.
2. The contract, decided here (Claude's discretion area, one header, no second request, no new libraries): request header X-Wake-Stats on GET /device/v1/display, value a semicolon-separated key=value list starting with v=1. Fourteen header keys, all optional except v: v (version, validated, not stored), seq (the NVS boot counter of this wake), bt (ms from app start to Wi-Fi start), wf (ms Wi-Fi connect plus time sync), att (Wi-Fi attempts), and the previous-wake keys carried in RTC memory across deep sleep: p_seq, p_aw (total awake ms at sleep entry), p_rq (display request ms), p_dl (image download ms), p_dr (panel draw ms), p_sp (SPI transfer ms inside the draw, timer reads only), p_tls (first TLS connect ms), p_rd (0 no draw, 1 drawn, 2 deferred), p_out (outcome token, lowercase letters, digits and hyphen, 1 to 16 characters, ok or the failure step). The parser therefore yields thirteen column values (every key except v). Bounds: seq and p_seq 0 to 4294967295; every ms key 0 to 3600000; att 0 to 16; p_rd 0 to 2; whole value at most 160 bytes. Grammar rule: any violation (unknown key, duplicate key, out-of-range, bad token, unknown version, oversize) makes the whole header ignored and every wake column NULL; the battery reading and the other telemetry are still stored. A frame that does not send the header produces NULL columns and works as today.
3. Database route (the planner's choice, recorded): nullable columns added to device_health by a guarded ALTER TABLE ADD COLUMN driven by PRAGMA table_info inside init_schema (one row per wake stays one row; no join). The guard must also tolerate the race of two processes (the companion's open_db and the poll oneshot both run init_schema): a duplicate column name error from ALTER is caught and treated as already migrated. Thirteen columns: wake_seq, boot_ms, wifi_ms, wifi_attempts, prev_seq, prev_awake_ms, prev_request_ms, prev_download_ms, prev_draw_ms, prev_spi_ms, prev_tls_ms, prev_redraw (integers) and prev_outcome (text). The read-only export falls back to its current five-column select when the columns do not exist yet so it never returns 503 before the migration runs (the migration runs in the 30 s poll oneshot after a deploy). Export keys are the five existing names followed by the thirteen column names above (eighteen keys), always present, null when absent. Documents and comments that state "five keys" or "four-name allowlist" or "a new column would need a migration mechanism" are updated by plan 02.
4. Rejected, with reasons from the research: a second request for telemetry (costs awake time), a second battery read at sleep entry (about 1 mV per wake, below ADC noise), several separate headers (each needs an allowlist and freeze entry), a new table (needs a join and a table-exists fallback).
5. The awake proxy: gap between wakes minus sleep_s is NOT a clean awake time (the research shows a hypothesis, labelled unproven, that the deep-sleep timer runs about 0.45 percent short; 47.1-RESEARCH.md Section 4). Until device-reported p_aw decides it, no document may call the gap excess awake time; plan 09 decides and then corrects the wording in FIELD-VALIDATION.md.
6. Evidence rules carried: a cost per wake is an energy estimate from voltage and timing, not a current measurement; ratings and the discharge curve are not measurements; the top of the curve above 4000 mV is not calibrated; owner-reported facts carry their date.
7. Release timing: no firmware release or server deploy lands during the open 3600 s window (to the 2026-11-07 bilan) without the owner's agreement; the instrumentation release stays apart from connecting the replacement pack so pack data stay attributable (research open question 6, recommendation adopted unless the owner says otherwise at the plan 08 gate).
8. Assumptions Log handling: A1 and A6 are settled by device data in plan 09 (p_aw against the gap; the p_tls field at long cadence). A2 is reported, not settled (the ROM and bootloader time before app start is outside bt and p_aw; plan 09 compares p_aw with the gap and states the difference as unexplained time). A3, A5, A7, A8 concern reduction candidates and are verified by the first task of the Phase 47.2 plan that depends on them, or the candidate is not built. A4 is not relied on.
9. Known telemetry gap after an OTA: after a successful OTA the firmware calls esp_restart() (state_machine.c, in the OTA branch) and bypasses enter_deep_sleep, so the OTA wake's own record is never written and the RTC data are reinitialised by the restart. The next wake therefore sends no p_ keys, and its seq need not follow the previous row's seq by one (every app start increments the boot counter). The server parser, the export and the model tool treat a missing p_ block or a gap in seq as unknown wakes, never as an error and never as zeros.
10. Baseline window rule (decided here, owner-facing text in plan 09): the model needs at least 6 segments after the first 24 h is ignored, and the segment length is 48 h (24 h segments carry a voltage fall that is inside the ADC and curve noise at hourly cadence, so they are rejected). The baseline is therefore a window of at least 14 days at one interval (24 h ignored, six segments of 48 h, one day of margin for quiet-hour exclusions), which satisfies the minimum of 12 days. Say it up front to the owner: because traffic at the owner's address changes the image at almost every long-interval wake, the redraw share per segment will probably be near constant in one window, and the fit will probably refuse for low redraw spread; the baseline is then a long window plus, if the owner agrees, a second window of at least 14 days at another interval. A refusal that names the missing data is a recorded outcome, not a failure.
11. Phase split (PROPOSED, needs the owner's agreement; the orchestrator asks): WAKE-01 and WAKE-02 stay in Phase 47.1 (instrumentation, server and model tooling, the instrumentation-only release gate, the baseline and the model run; WAKE-02's criterion is that the tool is committed and tested and, run on the baseline, either prints a fit with its ranges or refuses with the exact missing data named, both outcomes recorded). WAKE-03 and WAKE-04 move to Phase 47.2 with proposed closure rules written in 47.2-CONTEXT.md.
