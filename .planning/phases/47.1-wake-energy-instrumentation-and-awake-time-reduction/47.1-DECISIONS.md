## 2. Telemetry contract (decided here, Claude's discretion area)

One header, no second request, no new library. Request header `X-Wake-Stats` on `GET /device/v1/display`. Value: a semicolon-separated `key=value` list starting with `v=1`.

Fourteen header keys, all optional except `v`:

| Key | Meaning | Bound |
|-----|---------|-------|
| v | version, validated, not stored | must be 1 |
| seq | NVS boot counter of this wake | 0 to 4294967295 |
| bt | ms from app start to Wi-Fi start | 0 to 3600000 |
| wf | ms Wi-Fi connect plus time sync | 0 to 3600000 |
| att | Wi-Fi attempts | 0 to 16 |
| p_seq | previous wake's seq (RTC memory across deep sleep) | 0 to 4294967295 |
| p_aw | previous wake total awake ms at sleep entry | 0 to 3600000 |
| p_rq | previous wake display request ms | 0 to 3600000 |
| p_dl | previous wake image download ms | 0 to 3600000 |
| p_dr | previous wake panel draw ms | 0 to 3600000 |
| p_sp | SPI transfer ms inside the draw (timer reads only) | 0 to 3600000 |
| p_tls | previous wake first TLS connect ms | 0 to 3600000 |
| p_rd | 0 no draw, 1 drawn, 2 deferred | 0 to 2 |
| p_out | outcome token: lowercase letters, digits, hyphen, 1 to 16 characters; `ok` or the failure step | token |

The parser yields thirteen column values (every key except `v`).

Size cap: whole value at most 192 bytes. Worst case with every field at its bound (v=1, seq and p_seq at 4294967295, six ms keys at 3600000, att 16, p_rd 2, a 16-character p_out) is 173 bytes (checked with a one-line Python count on 2026-11-03: 173 bytes, 14 keys); 192 leaves margin. One source of truth per language: `WAKE_STATS_MAX_BYTES` in `server/wake_stats.py` and `FP_WAKE_STATS_MAX_LEN` in `firmware/main/wake_telemetry.h`; a check compares the two.

Grammar rule: any violation (unknown key, duplicate key, out-of-range value, bad token, unknown version, oversize) makes the whole header ignored and every wake column NULL. The battery reading and the other telemetry are still stored. A frame that does not send the header produces NULL columns and works as today.

## 3. Database route (planner's choice, recorded)

Nullable columns added to `device_health` by a guarded `ALTER TABLE ADD COLUMN`, driven by `PRAGMA table_info`, inside `init_schema`. One row per wake stays one row; no join. The guard tolerates the race of two processes (the companion's `open_db` and the poll oneshot both run `init_schema`): a "duplicate column name" error from ALTER is caught and treated as already migrated.

Thirteen columns: `wake_seq`, `boot_ms`, `wifi_ms`, `wifi_attempts`, `prev_seq`, `prev_awake_ms`, `prev_request_ms`, `prev_download_ms`, `prev_draw_ms`, `prev_spi_ms`, `prev_tls_ms`, `prev_redraw` (integers) and `prev_outcome` (text).

Mapping from header key to column: seq to wake_seq, bt to boot_ms, wf to wifi_ms, att to wifi_attempts, p_seq to prev_seq, p_aw to prev_awake_ms, p_rq to prev_request_ms, p_dl to prev_download_ms, p_dr to prev_draw_ms, p_sp to prev_spi_ms, p_tls to prev_tls_ms, p_rd to prev_redraw, p_out to prev_outcome.

The read-only export falls back to its current five-column select when the columns do not exist yet, so it never returns 503 before the migration runs (the migration runs in the 30 s poll oneshot after a deploy). Export keys: the five existing names followed by the thirteen column names (eighteen keys), always present, null when absent. Documents and comments that state "five keys", "four-name allowlist" or "a new column would need a migration mechanism" are updated by plan 02.

## 4. Rejected (reasons from the research)

- A second request for telemetry: costs awake time.
- A second battery read at sleep entry: about 1 mV per wake, below ADC noise.
- Several separate headers: each needs an allowlist and freeze entry.
- A new table: needs a join and a table-exists fallback.

## 5. The awake proxy is unproven

The gap between wakes minus `sleep_s` is NOT a clean awake time. 47.1-RESEARCH.md Section 4 carries a hypothesis, labelled unproven, that the deep-sleep timer runs about 0.45 percent short. Until device-reported `p_aw` decides it, no document may call the gap excess awake time. Plan 09 decides, then corrects the wording in `hardware/FIELD-VALIDATION.md`.

## 9. Known telemetry gap after an OTA

After a successful OTA the firmware calls `esp_restart()` (in the OTA branch of `firmware/main/state_machine.c`) and bypasses `enter_deep_sleep`. The OTA wake's own record is never written and the RTC data are reinitialised by the restart. The next wake sends no `p_` keys, and its `seq` need not follow the previous row's `seq` by one (every app start increments the boot counter). The server parser, the export and the model tool treat a missing `p_` block or a gap in `seq` as unknown wakes, never as an error and never as zeros.

## 10. Baseline window rule (decided here; owner-facing text in plan 09)

The model needs at least 6 segments after the first 24 h is ignored, and the segment length is 48 h (24 h segments carry a voltage fall inside the ADC and curve noise at hourly cadence, so they are rejected). The baseline is therefore a window of at least 14 days at one interval: 24 h ignored, six segments of 48 h, one day of margin for quiet-hour exclusions. This satisfies the minimum of 12 days (arithmetic by Claude).

To say up front to the owner: because traffic at the owner's address changes the image at almost every long-interval wake, the redraw share per segment will probably be near constant in one window, and the fit will probably refuse for low redraw spread. The baseline is then a long window plus, if the owner agrees, a second window of at least 14 days at another interval. A refusal that names the missing data is a recorded outcome, not a failure.
