<objective>
The wake interval is currently a number box with the word "seconds" beside it. To
set it you have to know two things the page never tells you: that a smaller number
means the frame notices a plane sooner, and that it also means the battery dies
sooner. The whole point of the setting is that trade-off, and the control shows
neither side of it.

D18 makes both sides visible: a slider you can sweep, and two gauges that move
with it.

The interesting problem is not the slider. It is that **one of the two gauges is
honest and the other one cannot be, yet.**

- *Freshness* is honest and free: "a plane appears at most N minutes after
  passing" is the wake interval restated the way a person experiences it. It is
  true by construction, as long as it says "at most".
- *Battery life* is the audit's "estimated battery life ≈ 38 days", and **that
  figure does not exist anywhere in this codebase.** Computing it needs a per-wake
  energy cost that has never been measured — DEVICE-05's multi-day discharge run
  is still deferred at the end of the project. A number invented from an assumed
  cost, printed next to a slider a user will act on, is exactly the class of
  dishonest state Phase 22's X2/B2/B3 arc spent a phase removing.

So this plan ships the gauge that can be true today and makes the second one say
only what this device's own observed history supports — with a named "not enough
history yet" state rather than a confident fiction.

Output: a native range input behind the `.js` gate, a number input that is
byte-identical to today's, and two gauges whose claims a check can verify.
</objective>

Binding constraints:
- The `<input type="number">` keeps its id, name, min, max, placeholder, the
  value-attribute guard, the raw-submitted echo, its error attributes and its unit
  sibling. It remains the submitting control.
- The range input carries NO `name`. A named range would submit a second value for
  the same setting, and whichever arrived last would win silently.
- `min`/`max`/`step` are read from `device_config`, never re-typed as literals —
  the same cross-file convention the number input already follows.
- Do NOT add `role="slider"` to the native range. Give it an `aria-label` and point
  `aria-describedby` at the gauges.
- The gauges are NOT a live region. They change on every slider step and would
  flood a screen reader — the same reasoning 25-04 applied to its readout.
- The life estimate comes from `companion/battery.py`. A second days-remaining
  computation in this page module is the exact drift 19-01 created that module to
  prevent.
- `interpolate-size` and `calc-size(` are BANNED. No new `@keyframes`. No per-rule
  reduced-motion block.
- The `@supports selector(:has(*))` block count stays exactly 1.

| Boundary | Description |
|----------|-------------|
| a dragged range → `wake_interval_s` | a pointer gesture becomes the frame's poll cadence |
| stored battery history → a days-remaining claim | arithmetic over stored rows becomes a sentence a user acts on |
| `device_config` bounds → two controls | one range must not widen what the number input enforces |
