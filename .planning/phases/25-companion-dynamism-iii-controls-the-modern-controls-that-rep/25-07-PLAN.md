<objective>
Uploading artwork today means finding the "Choose an image" control, opening a file
picker, and hoping. The form is correct — it validates, it normalises, it discards
the client's filename — but the gesture people actually reach for is dragging the
file onto the card.

D19 adds that gesture. The design work is mostly subtraction, and each subtraction
has a named ground:

- **No client-side canvas crop.** `companion/illustration_normalize.py`'s own
  docstring says it plainly: it exists because a *second, differently-thresholded
  measurement silently drifted from the first*, and *"this module must never become
  a second implementation for that same measurement to drift against"*. A canvas
  crop that "matches" it is exactly that second implementation, written in a
  language the server cannot check, on a machine the server cannot trust.
- **No progress bar.** `submit-guard.js` already disables a form's submit button
  on submit, app-wide. A 4 MB cap against a household server does not need
  `XMLHttpRequest.upload.onprogress`; it needs the word "Uploading…".
- **No hover-only aircraft types.** Hover is unreachable by touch — the same
  ground CFG-28 used when it moved this app's tooltips behind copy controls.

What remains is the part that is actually useful: drop a file on the card, see what
you picked and how it will be framed, and let the server do the same thing it
already does.

Output: a drop target and a framing preview over two upload forms that are
byte-identical to today's, and a normaliser that is still the only thing deciding
what an illustration looks like.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| a dropped file → the upload form's file input | attacker-chosen bytes enter the same path a picked file enters |
| client-side validation → server-side validation | a courtesy check must never be mistaken for a control |
| an object URL → document memory | the whole file is held until revoked |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-25-07-A | Tampering | a client-transformed image becoming the stored artwork | mitigate | no transform exists — the script is asserted free of every canvas API, and the picked-vs-dropped equivalence check would fail if one appeared |
| T-25-07-B | Tampering | a client-side type/size check relaxed into a trusted gate | mitigate | the server's 4 MB pre-read cap and its own validation are untouched and asserted; the script's comment states its check is a courtesy |
| T-25-07-C | Spoofing | a client-declared filename reaching storage | n/a | `parse_single_uploaded_file()` discards it entirely and is untouched; a drop cannot change that because it assigns to the same input |
| T-25-07-D | Denial of Service | an oversized drop consuming memory before the cap applies | mitigate | the cap is enforced server-side before the body is read; client-side the file is refused before assignment, and object URLs are revoked |
| T-25-07-E | Information Disclosure | the illustration route serving an uploaded file | accept | unchanged and still session-gated; this plan neither adds nor widens a route |
| T-25-07-SC | Tampering | npm/pip/cargo installs | n/a | this plan installs zero packages in any ecosystem |
</threat_model>
