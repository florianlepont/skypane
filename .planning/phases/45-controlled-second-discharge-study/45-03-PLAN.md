    6. Removes the USB power (the pack takes over) and reports the wall-clock disconnect time in UTC (`disconnect_time_utc`) and the time the protocol was confirmed (`protocol_confirmed_utc`: 2026-10-05, the owner's reply; the exact time is whatever the owner states).

<task type="checkpoint:human-action" gate="blocking">
  <what-built>The pack is running on the confirmed cadence. This is a physical wait of about 3 to 12 days expected (up to the confirmed ceiling, 21 days) and cannot be completed by an agent. Plan 45-03 is PAUSED here; nothing is recorded until the owner returns.</what-built>
  <how-to-verify>
    Owner leaves the device untouched. Optional visibility check-ins only. **Freeze step at about 48 hours (mandatory, Run 2 Protocol section 4a):** once at least 48 hours have elapsed since the first exported row, the owner saves the export so far with the run-one read-only remote query (unmodified, bounded by the disconnect time) to `hardware/logs/battery-run2-export-48h.jsonl` and runs `python3 hardware/logtools.py reference-interval hardware/logs/battery-run2-export-48h.jsonl --interval-s 60`. The helper prints the value, the gaps used and excluded and the export sha256, and reads only the first 48 hours; it refuses an export shorter than 48 hours (wait and export again). The executor records the printed value verbatim as `reference_interval_s` in the params file, with `reference_interval_source` (owner-written: date, helper run on which export) and `reference_interval_export_sha256` (the helper's `export_sha256` line), copies the helper's full output into `## Run 2 Start Record` as a dated line, and commits params and record BEFORE `run-report` is run on any run data. This is the one executor action in this plan that touches a computed value; the value comes only from the helper's output, is never hand-calculated and is never edited afterwards, whatever the later report shows. If the 48 h export or the helper output is missing, the executor stops and does not run `run-report` (a run is not silently judged against the bare interval). The run ends when ONE of these is true, and the owner reports which:
    - depleted: the device stops polling (last reading well below 3400 mV; the frame will park on BATTERY EMPTY once 3300 mV is crossed, then poll hourly until it dies); or
    - ceiling: 21 elapsed days are reached with the device still alive; the owner then reports the exact end time so it can be recorded as `end_time_utc` (the ceiling check allows only one 60 s interval of overshoot, and the export must be bounded by it).
    If firmware changes, the deployed server revision changes, quiet hours/display-off is enabled, or the cadence is edited mid-run, the run is INVALID: the owner reports it and a new protocol cycle (plan 45-01 onward) is required; the executor must not salvage it.
  </how-to-verify>
  <resume-signal>Reply "run ended: depleted" or "run ended: ceiling" with the date/time, or "run invalid: <reason>". Do not resume this plan before the run has actually ended.</resume-signal>
</task>
