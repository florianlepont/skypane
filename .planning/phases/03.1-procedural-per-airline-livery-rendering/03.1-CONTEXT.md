<domain>
## Phase Boundary

**Major scope revision from ROADMAP.md's original framing — see D-02 below.** ROADMAP.md currently describes this phase as building "a server-side rendering pipeline that composites the real airline's livery colors onto the correct aircraft-type SVG shape... without depending on an external image-generation tool at all." That specific architecture was explored this session and found not viable with real, license-compatible source material (D-02). The phase's actual boundary, as re-scoped in this discussion:

1. `server/plane/detect.py` extracts and surfaces the real ICAO aircraft-type field (`t`) from the live ADS-B response, alongside the existing callsign/altitude/vertical-rate fields (ROADMAP success criterion 2 — unchanged).
2. The per-airline illustration set is expanded and corrected to real per-flight aircraft-type accuracy — still externally AI-generated by the user (same D-09 hand-off discipline as Phase 3), now covering a verified, real list of airlines × aircraft types (D-03) instead of Phase 3's one-representative-type-per-airline approximation.
3. Illustration selection logic gains a second key (aircraft type, alongside the existing airline_name key) and a new tiered fallback (D-06/D-07/D-08).

**ROADMAP.md needs a revision pass during/before planning** to replace its "procedural server-side compositing, no external tool" language with this static-but-type-accurate approach — see D-10.

This phase does not cover the RER view, physical button, battery indicator, or any new requirement scope beyond PLANE-01/PLANE-02's existing "airline" element.

## Implementation Decisions

### Prerequisite confirmation (ROADMAP success criterion 1)
- **D-01:** Confirmed live this session via a real `curl` to `server/plane/detect.py`'s own `adsbfi` URL template (`https://opendata.adsb.fi/api/v2/lat/.../lon/.../dist/25`, real coordinates near the install site): the ICAO aircraft-type designator field (`"t":"B738"`, `"t":"A321"`, `"t":"A20N"`, etc.) is genuinely present on real in-flight aircraft. This directly satisfies success criterion 1. (Prior session's own attempt from a network-restricted sandbox could not confirm this — this session's sandbox has working network access.) Not yet wired into `detect.py`'s `select_runway3_aircraft()` return dict (criterion 2) — that's planning/implementation work.

### Architecture: procedural render-time compositing abandoned for now
- **D-02 (major decision, supersedes ROADMAP.md's stated architecture):** A real, live search this session for free/CC0-or-compatible, side-profile (not top-down), per-aircraft-type SVG or line-art shapes — the asset the "true" procedural engine needs — found no viable ready-made source:
  - A flight-sim repaint-template forum (`airlineenterprise.com`, ~100+ PSD templates, correct side-profile angle and per-type detail) explicitly prohibits redistribution ("do not redistribute... out of respect to the work and craftsmanship") — incompatible with committing to this project's public MIT-licensed GitHub repo, regardless of the project being non-commercial. Format is PSD, not SVG, adding a conversion problem on top of the licensing one.
  - Wikimedia Commons has a real, cleanly-licensed (CC-BY-SA 4.0, single author "FlyingPete") SVG silhouette set for ~15 Boeing types — but it's a **top-down plan view** (designed for map-style flight trackers), not the side-profile nose-left view this project's existing illustrations use. Wrong angle, not reusable as-is.
  - Wikimedia's Airbus "Line drawings" category has A319/A320/A321 side-profile diagrams, but only as PNG (not SVG) with per-file licenses unverified, and no equivalent clean single-author set exists for the full type roster needed (ATR72, Embraer, Beechcraft, A330, A350).
  - Generic CC0 clipart sites (openclipart, svgsilh, publicdomainvectors) only have one generic universal jet silhouette — exactly what the project already has (`aircraft-silhouette.svg`) — no per-type differentiation.
  - **Conclusion, confirmed by the user:** sourcing/drawing real per-type shape outlines is a genuine one-time design task, not a downloadable asset — given the scale involved (see D-03), the user chose to abandon the render-time shape+color compositing architecture for now (see Deferred below) and instead extend Phase 3's proven external-AI-generation workflow (D-09 in `03-CONTEXT.md`) to cover real per-flight type accuracy directly, via more generated static images rather than a programmatic engine.

### Fallback / selection-priority behavior (new — Phase 3 only had one axis)
- **D-06 (case: known airline, type mismatch):** When a recognized airline's real detected ADS-B type doesn't match what was generated for it (e.g., Transavia detected as B737 but only an A320neo illustration exists, or vice versa, until D-05's gap is closed), show **the airline's existing illustration anyway** — brand identity wins over exact type precision, same tolerance already established in Phase 3 (`03-CONTEXT.md` D-19: "type plausible/représentatif suffisant").
- **D-07 (case: unknown airline, known+covered type):** When the airline is unrecognized (an `adsbdb` miss — e.g. easyJet Europe, KM Malta, confirmed misses per `illustrations/HANDOFF.md`) but the real detected type is one of the 7 base shapes in D-03's table, show a **new neutral-colored, correct-shape** fallback — not the single universal generic. This requires generating **~7 additional neutral illustrations** (one per base shape: neutral A320-family, neutral B737-family, neutral ATR72, etc.), not one.
- **D-08 (case: both unknown):** When neither the airline nor the type is recognized/covered, fall back to the existing single universal generic illustration — unchanged from Phase 3 (`03-CONTEXT.md` D-08).
