## Summary

This phase is a **data-plumbing and asset-scaling** exercise, not a rendering-architecture change. `poll_loop.py`'s two-deep flight history (`last_flight`/`previous_flight`, D-25/D-26 from Phase 3) already round-trips whatever dict `detect.py` returns through `poll_state.json` verbatim — adding a new `aircraft_type` key to `select_runway3_aircraft()`'s return dict requires **zero changes to `poll_loop.py`**. The real work is: (1) extract and normalize the ICAO type designator (`t`) in `detect.py`; (2) extend `illustrations.select_illustration()` from a one-key (`airline_name`) lookup to a two-key (`airline_name`, `aircraft_type`) lookup with the D-06/D-07/D-08 tiered fallback, using a new type-code → 7-bucket classification function; (3) extend `render.py`'s `_flight_line2_text()` to actually render `{airline} · {aircraft_type}` instead of airline-name-only (its own docstring already flags this as a stub pending Phase 3.1); (4) massively extend `HANDOFF.md`/`VENDOR.md` for a much larger illustration set (potentially ~24 airline files + up to a handful of secondary-type variants + 7 new neutral fallbacks, vs. today's 8); (5) confirm a critical, previously-undocumented constraint discovered live this session — **filenames must match adsbdb's exact resolved `airline_name` string, which does not always match the airline's real-world brand name** (CCM Airlines / Air Corsica is the concrete, now-confirmed example).

A second load-bearing finding from this session's live verification: several airlines D-03 lists as in-scope (easyJet proper via `EZY`, Wizz Air, ITA Airways, LOT Polish Airlines, French Bee, Air Europa, Royal Air Maroc, Air Caraïbes) resolve cleanly on `adsbdb` today — this materially widens the illustration set worth generating beyond Phase 3's original 7, and specifically **easyJet is not uniformly a miss**: only the Austrian-AOC `EJU` (easyJet Europe) prefix is a confirmed miss; the UK-AOC `EZY` (easyJet proper) prefix resolves fine as `"easyJet"`. Several other D-03 airlines (Tunisair, ASL Airlines France, Pegasus, Amelia International, Chalair, Twin Jet, Corsair International, La Compagnie) were not confirmed this session (guessed flight numbers missed) and should be live-verified with real callsigns during Task 1, following the exact methodology `illustrations.py`'s own module docstring already establishes for Phase 3.

**Primary recommendation:** Add `aircraft_type` to `detect.py`'s return dict (a pure extraction, no behavior change elsewhere); extend `illustrations.py` with a `classify_aircraft_type()` shape-bucket function and a `{airline-slug}-{shape-slug}.png` → `{airline-slug}.png` → `generic-{shape-slug}.png` → `generic-fallback.png` four-tier lookup; update `render.py`'s line-2 text builder to consume the new field; before generating any new art, live-resolve every not-yet-confirmed D-03 airline's exact `adsbdb` string using real callsigns (not guesses).

## Code-Level Findings

### 1. `detect.py`: adding the `aircraft_type` field

`select_runway3_aircraft()` (line ~138) already extracts `callsign` and `vertical_rate_fpm` with the file's established never-raise, `.get()`-then-normalize convention:

```python
# Existing pattern (lines 177-180):
callsign = (winner.get("flight") or "").strip() or None
vertical_rate_fpm = winner.get("baro_rate")
if vertical_rate_fpm is None:
    vertical_rate_fpm = winner.get("geom_rate")
```

The type field follows the same shape — a single raw key (`t`), no fallback key needed (unlike `vertical_rate_fpm`'s baro/geom fallback), string not numeric:

```python
aircraft_type = (winner.get("t") or "").strip().upper() or None
```

Add this line alongside the existing extraction block, and add `"aircraft_type": aircraft_type,` to the returned dict (line ~182-192). This is the **entire extraction change** — no new provider call, no new geofence logic, no change to `filter_in_geofence()` or `poll_current_aircraft()`.

### 2. `poll_loop.py`: confirmed — zero changes needed

`run_once()` stores and shifts `flight`/`last_flight`/`previous_flight` as **opaque dicts**, never destructuring specific keys out of them:

```python
poll_state["last_flight"] = flight              # whole dict, JSON round-tripped
poll_state["previous_flight"] = previous_flight  # whole dict, shifted from the prior last_flight
```

Once `detect.py` adds `aircraft_type` to its return dict, this key rides along through `poll_state.json` and into `render.render_panel(flight, ..., previous_flight=previous_flight, ...)` automatically. **This directly confirms the CONTEXT.md hypothesis: the existing two-deep history structure needs no changes.** The only place the new field is actually *read* is inside `render.py`'s call to `illustrations.select_illustration()` and the new line-2 text builder (see below) — both already receive `flight`/`previous_flight` as full dicts, so `flight.get("aircraft_type")` is available with no signature change to `run_once()` itself.

One second-order consideration for planning: `run_once()`'s log line (`"poll_loop: hex=%s callsign=%s altitude_ft=%s ..."`, line ~267) does not currently log `aircraft_type`. Not required by any decision, but cheap to add for on-VPS debugging (`journalctl` visibility into which shape/tier was selected) — flag as a nice-to-have, not a requirement.

### 3. `illustrations.py`: two-key lookup + tiered fallback design

**Recommended selection algorithm** (extends `select_illustration()` in place, keeps the existing single-arg call sites working via a default):

```python
def select_illustration(route, aircraft_type=None):
    airline_name = route.get("airline_name") if isinstance(route, dict) else None
    airline_key = normalise_airline_key(airline_name)          # existing function, unchanged
    shape_key = classify_aircraft_type(aircraft_type)            # NEW function, see below

    # Tier 1: exact airline + shape match (D-03's mixed-fleet variants,
    # e.g. transavia-france-b737.png / transavia-france-a320.png)
    if airline_key and shape_key:
        exact = illustration_path_for_key("%s-%s" % (airline_key, shape_key))
        if exact and os.path.isfile(exact):
            return exact

    # Tier 2 (D-06): known airline, no exact-shape file -> its primary/
    # default file, regardless of type match ("brand wins").
    if airline_key:
        primary = illustration_path_for_key(airline_key)
        if primary and os.path.isfile(primary):
            return primary

    # Tier 3 (D-07): unknown airline, but a recognized+covered shape ->
    # the neutral per-shape fallback.
    if shape_key:
        neutral = illustration_path_for_key("generic-%s" % shape_key)
        if neutral and os.path.isfile(neutral):
            return neutral

    # Tier 4 (D-08): both unknown -> the existing universal fallback.
    fallback = generic_fallback_path()
    if os.path.isfile(fallback):
        return fallback
    return None
```

This preserves every existing behavior/test when `aircraft_type=None` is passed (or omitted) — Tier 1 and Tier 3 both short-circuit on `shape_key is None`, falling straight through to today's exact Tier 2 → Tier 4 path, so **all 22 existing `test_illustrations.py` checks stay valid unmodified**, only new checks are additive.

### 6. `render.py`: `_flight_line2_text()` needs a real implementation

The function's own docstring already documents this exact gap:

> "D-26's brief also asked for `{airline} · {aircraft_type}` — real per-flight aircraft-type data does not exist yet (that is Phase 3.1, deliberately deferred...), so this line is the airline name alone rather than a fabricated type."

Recommended change — thread the flight dict's new `aircraft_type` through, with a **friendly display label**, not the raw ICAO code (a raw code like `B39M` or `A21N` is not legible to someone glancing at the frame; D-26's own worked example was `"Air France · A320"`, a friendly label):

```python
_TYPE_DISPLAY_LABELS = {
    "A320": "A320", "A319": "A319", "A321": "A321",
    "A20N": "A320neo", "A21N": "A321neo",
    "B738": "737-800", "B737": "737-700", "B733": "737-300",
    "B38M": "737 MAX 8", "B39M": "737 MAX 9",
    "AT72": "ATR 72", "AT76": "ATR 72-600", "AT43": "ATR 42",
    "BE9L": "Beechcraft 1900D",
    "E145": "E145", "E170": "E170", "E190": "E190", "E195": "E195",
    "A332": "A330-200", "A333": "A330-300", "A339": "A330-900neo",
    "A359": "A350-900", "A35K": "A350-1000",

def _flight_line2_text(route, aircraft_type=None):
    airline_name = route.get("airline_name") if route is not None else None
    if not airline_name:
        return ROUTE_FALLBACK_TEXT
    label = _TYPE_DISPLAY_LABELS.get((aircraft_type or "").strip().upper())
    if label:
        return "%s · %s" % (airline_name, label)
    return airline_name
```

Both call sites (`draw_main_text_block()` and `draw_previous_text_block()`) need their `flight`/`previous_flight` dict's `aircraft_type` passed through to this function. Note `_flight_line2_text()`'s two call sites currently only receive `route` — this is a genuine signature change, not additive, so **every existing caller and every `test_render.py` check that asserts on line-2 text content needs a matching update** (see Testing section below).

`[ASSUMED]` the exact display-label table above — this is a UX/copywriting judgment call (should "B738" read as "737-800" or "Boeing 737"? should neo variants say "A320neo" or just "A320"?) that the existing decisions do not pin down. Flag as an **Open Question** for the planner/discuss-phase to confirm, or leave as Claude's Discretion during implementation with a documented rationale.

## Common Pitfalls

### Pitfall 1: Renaming an asset file to match a "corrected" brand name breaks selection
**What goes wrong:** `ccm-airlines.png` → `air-corsica.png` looks like an obvious cleanup (D-04 flagged the name as "stale"), but `select_illustration()` keys off `adsbdb`'s resolved `airline_name`, which is still literally `"CCM Airlines"` (confirmed live this session).
**Why it happens:** The stale-looking filename is actually correct — it mirrors upstream data, not the airline's current public brand.
**How to avoid:** Never rename an illustration filename without first live-querying `adsbdb` for that airline's current resolved string. If a nicer display name is wanted, add a display-only alias table, never touch the selection key.
**Warning signs:** A `--validate` pass that suddenly reports an "unexpected file" for the old name, or a real Air Corsica flight silently rendering the generic fallback after a rename.

### Pitfall 2: Guessed callsigns produce false "miss" signals
**What goes wrong:** Several plausible-looking callsign guesses this session (`TAR758`, `PGT1234`, `XTJ501`, etc.) returned `"unknown callsign"` — but this reflects a wrong/nonexistent flight number, not confirmed non-coverage of that airline.
**Why it happens:** `adsbdb`'s callsign lookup is per-flight-number, not per-airline-prefix; a airline can be well-covered while a specific guessed flight number simply doesn't exist in their crowdsourced DB.
**How to avoid:** Before excluding an airline from the illustration hand-off as "not covered," verify with a **real, currently-flying** callsign (capture one from a live `poll_loop.py` cycle or the aggregator's raw feed), not a guessed one. `Royal Air Maroc` is the clearest example this session: `RAM1284` missed, `RAM754` hit — the airline itself is well covered.
**Warning signs:** A hand-off spec that excludes an airline based on a single missed guess rather than a documented real-flight test.

### Pitfall 3: Mixing up "which type is primary" silently picks the wrong illustration for the common case
**What goes wrong:** For a mixed-fleet airline (Transavia, Air Corsica, Royal Air Maroc, Air Caraïbes), Tier 2 of the fallback (D-06, "airline's existing illustration anyway") returns whichever file is named `{airline-slug}.png` — if that happens to be the *minority* type, most real detections of that airline will show a less-representative aircraft shape than necessary, even though a same-airline different-type illustration exists right next to it.
**Why it happens:** The primary/secondary designation is a human judgment call (see `[ASSUMED]` note in Code-Level Finding #5), easy to get backwards without checking real fleet-mix data.
**How to avoid:** When naming the primary (unsuffixed) file for a mixed-fleet airline, pick the numerically dominant type per D-03's own table (e.g., Transavia's existing `transavia-france.png` is correctly B737 today, its pre-transition majority — but D-05 already flags this majority is shifting to A320neo over 2026-2031; the planner should note this as a file that may need its primary/secondary roles swapped in a future phase, not now).
**Warning signs:** A real flight of a well-known type consistently rendering the "wrong" (technically valid, but visually mismatched) illustration for that carrier.

### Pitfall 4: A silently-absent `t` field on one aggregator provider is treated as a real "no type" case rather than a provider gap
**What goes wrong:** If `airplanes.live` (never observed with a nonzero sample this session) turns out not to carry `t` in some response shape, every flight picked up via that provider would silently render with `aircraft_type=None` — falling to Tier 2/4 fallback — while the same real flight picked up via `adsb.fi` would get full type accuracy. This produces confusing, provider-dependent illustration behavior for the same real airline.
**Why it happens:** The two providers are not guaranteed identical schemas just because they share a common lineage (readsb/tar1090).
**How to avoid:** Test `detect.py`'s new extraction against a real, non-empty `airplanes.live` response before considering Task 2 (D-01/criterion 2) fully closed — not just against `adsb.fi`'s already-confirmed shape.
**Warning signs:** `aircraft_type` is consistently `None` in `journalctl` logs specifically when `provider=airplaneslive` won the poll, but populated when `provider=adsbfi` won.

## Open Questions

1. **Should `ccm-airlines.png`'s selection key stay "CCM Airlines" while the *displayed* text says "Air Corsica"?**
   - What we know: `adsbdb` still resolves `"CCM Airlines"` (confirmed live). The user's own D-04 concern was about brand accuracy on the rendered panel, not the filename per se.
   - What's unclear: whether the user wants a display-only alias (`"CCM Airlines"` → shows as `"Air Corsica"` in the rendered line-2 text) or is fine with the panel literally showing "CCM Airlines" since that's what the data source calls it.
   - Recommendation: surface this as a quick discretion call during planning; either is a small, contained change (a one-entry alias dict applied only in `_flight_line2_text()`, never in `select_illustration()`).

2. **Exact display-label wording for `_TYPE_DISPLAY_LABELS`.**
   - What we know: D-26's original brief example was `"Air France · A320"` — a short, friendly label, not a raw ICAO code.
   - What's unclear: whether neo/MAX variants should say e.g. "A320neo"/"737 MAX 8" or collapse to the base family name ("A320"/"737") for brevity/consistency with the "one shape per family" simplification already accepted elsewhere.
   - Recommendation: default to the more specific/accurate label (neo/MAX called out) since it's genuinely more informative and D-03's own table already distinguishes neo variants; can be simplified later if it reads as cluttered on real glass.

3. **Should easyJet (`EZY`, confirmed hit) get an illustration even though easyJet Europe (`EJU`, confirmed miss) won't benefit?**
   - What we know: both operate flights that could plausibly use Orly; only `EZY`-prefixed flights will ever display an easyJet-specific illustration once one exists.
   - What's unclear: how much of Orly's real easyJet traffic is `EZY` vs `EJU` — not measured this session.
   - Recommendation: generate it anyway (D-07's neutral-shape fallback would otherwise show for every easyJet-brand flight the code *can* attribute correctly) — low cost, strictly additive coverage improvement, consistent with D-03 listing "easyJet" as a real, verified Orly carrier.
