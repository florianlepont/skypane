### Cross-check: does Phase 3.1 touch or worsen Phase 3's render.py exception-handling gap?

Phase 3's own verification (`03-VERIFICATION.md`, `status: gaps_found`) found that `server/plane/render.py`'s `_resize_illustration()` (`Image.open(path).convert("RGBA")`, line 268) has no `try`/`except` anywhere in its call chain, so a corrupt-but-present illustration file crashes `render_panel()` with an uncaught `PIL.UnidentifiedImageError` instead of degrading to a fallback — the old `draw_silhouette()` safety net was removed by the D-25/D-26 redesign and nothing replaced it.

**Checked directly against the git history of this phase's own commits:** `git show 1c4dfd9 -- server/plane/render.py` (plan 03.1-04, Task 2 — the only 03.1 commit that touches `_build_active_canvas()`, the caller of `_resize_illustration()`) shows exactly two changed lines, both adding a second (`aircraft_type`) argument to the two existing `select_illustration()` calls. `_resize_illustration()` itself (line 268-277, containing the unguarded `Image.open()`) is untouched by any 03.1 commit — confirmed by `git log --oneline -- server/plane/render.py`, which shows only `f3837d5` and `1c4dfd9` for Phase 3.1, neither of which lines up with `_resize_illustration()`'s line range.

**Conclusion:** this gap is purely inherited from Phase 3's render-time exception-handling design; Phase 3.1 neither introduces nor worsens it at the code level. It is correctly out of scope for this phase's fix-plan and belongs to Phase 3's existing `gaps_found` verification. One second-order observation worth flagging for whoever plans Phase 3's gap-closure: Phase 3.1 expanded the vendored illustration set from 8 files to 33, which quantitatively widens the number of files that could someday become corrupted on disk and trigger this pre-existing crash path — this doesn't change the nature or ownership of the gap, but it modestly raises its practical likelihood over time.
