# Phase 16 — UI Design Contract

> Visual and interaction contract for the single Settings-page addition this phase ships: a read-only "configured / not configured" calendar status line plus a theme-assignment `<select>` for calendar-matched flights. Generated by gsd-ui-researcher, verified by gsd-ui-checker. Authoritative source of decisions: `16-CONTEXT.md` (D-01..D-04, plus the Claude's Discretion list) and `.planning/ROADMAP.md`'s "Phase 16" section (the three measured findings — load-bearing on copy). This spec does not re-litigate any locked decision — it specifies the *shape* those decisions take in markup, copy and CSS, matching Phase 15's register exactly since this is the same Settings page.

## Copywriting Contract

Locked-English module constants, matching this codebase's existing family (`THEME_SECTION_CAPTION`, `RULES_SECTION_CAPTION`, etc.) — one caption per section, per `references/settings-page-patterns.md`.

**Every string below was written against the measured-findings constraint in `.planning/ROADMAP.md`'s Phase 16 section, finding 3.** None of them uses "track," "watch," "follow," "monitor," "notify," or any verb implying the frame knows a flight is happening independent of what is on screen. Every sentence is phrased as a conditional: *when the flight being shown happens to be one the calendar lists.*

| Element | Copy |
|---------|------|
| Section heading (`CALENDAR_SECTION_HEADING`) | "Calendar" |
| Section caption (`CALENDAR_SECTION_CAPTION`) | "When the flight the frame is currently showing is one your connected calendar lists, it uses this theme instead of the usual one. It can only colour a flight that happens to be on screen — it does not track or announce anything on its own. Applies on the frame's next scheduled poll, not immediately." |
| Status — not configured (`CALENDAR_STATUS_NOT_CONFIGURED`) | "Not configured. Set `SKYPANE_CALENDAR_ICS_URL` in `skypane.env` on the server to connect a calendar." |
| Status — configured, never yet synced (`CALENDAR_STATUS_CONFIGURED_PENDING`) | "Connected — waiting for the first sync." |
| Status — configured, synced at least once (`CALENDAR_STATUS_CONFIGURED_SYNCED`) | "Connected — last synced {relative timestamp}." (the `{relative timestamp}` fragment is `layout.concise_timestamp_html()`'s existing "absolute + relative" rendering, e.g. "2026-09-07T09:12:04 (12m ago)" — never a bare ISO string, matching every other timestamp on this page) |
| Theme field label | "Theme" |
| Theme field hint (`CALENDAR_THEME_HINT`, `.section-caption`-styled, under the `<select>` — not a placeholder, matching the Rules add-form's `RULE_VALUE_HINT` precedent) | "Used only when a flight from the calendar happens to be the one on screen." (a short, load-bearing repeat of the caption's own core constraint, placed right where the operator picks the theme — deliberate redundancy, not filler: this is the single sentence most likely to be skimmed past if it only appears once, at the top of the section) |

### What this section deliberately does NOT say

- No count of upcoming flights, no next-match preview, no flight numbers, times, or routes anywhere on this page. See "Configured / Not Configured State" below for the full reasoning.
- No mention of the calendar owner, by name, initials, or role. The section heading is "Calendar," not "Crew schedule," "Duty roster," or any wording that identifies a person or their employer.
- No language implying real-time awareness ("currently flying," "in the air now," "on duty") — the frame only ever knows what is on screen at the moment of a render.

### Flash messages

**None are added by this phase.** The Calendar group's only interactive element (the theme `<select>`) is a normal tracked field inside the existing `<form id="settings-form">` — it saves through the same "Saved — your changes are live on the frame's next poll" flash (or whatever the existing generic settings-save flash constant is) that Theme, Runway, Diagnostic LED, Quiet hours, Wake interval, and Display already share. A malformed/tampered `calendar_theme_id` (not a member of `THEME_IDS`) is a hostile-request shape, not a genuine user mistake — it reuses the existing generic settings-save-failed flash, matching `config_page.handle_post()`'s own established asymmetry for a crafted out-of-range value (same precedent Phase 15's `rule_theme_id` handling and 11-UI-SPEC.md both already cite). No new flash-key constant is needed.

### Destructive actions

There are none on this page for this feature. Disconnecting the calendar happens by removing the env var over SSH — entirely outside the companion web UI's surface, by design (D-01/D-02 of the security framing: the URL never appears in the web UI in either direction, in or out).

## Configured / Not Configured State — the phase's one genuinely undecided question, resolved here

**Decision: show status text only (configured / not-configured / last-synced-when), and nothing about the calendar's contents.** No flight count, no upcoming-flights preview, no next-match indicator.

**Why, given `16-CONTEXT.md` explicitly flags a preview as "attractive but... needs a deliberate decision rather than a reflex":**

1. **Measured finding 3 is the deciding fact.** The frame catches roughly one in three flights on a good day, and on the one real measured duty day, it caught *zero of three*. A page that shows "3 upcoming flights parsed from the calendar" sets an expectation the frame is highly unlikely to meet — the same overstatement problem the caption copy above is written to avoid, just relocated from prose into a number. A confident-looking stat tile reading "Next: in 4h 12m" is a much stronger promise than the feature can honestly make, and it is exactly the kind of thing a screenshot travels with.
2. **A preview renders a named person's real work schedule into a web page**, verbatim, even without naming them — flight-level detail (route, time) is itself potentially identifying to anyone who already knows who the operator lives with or is close to, which is a strictly worse privacy posture than the parsed-registry file already accepts (D-03's short rolling window, at rest, unseen by anyone who doesn't have server access). The web page is the one surface in this whole feature that other people in the room might glance at.
3. **A count alone (no flight detail) was considered and rejected too.** Even "1 flight in the next 48h" is schedule signal — on a quiet week it either confirms or denies a specific day, to anyone glancing at the screen who has reason to care. The feature's own generalisation away from naming a person (ROADMAP's "connect your calendar" framing) is undercut if the page still leaks a countable signal about that person's whereabouts.
4. **A last-synced timestamp carries none of that risk.** It answers the one operationally useful question ("is this actually working, or is my feed broken") without saying anything about *what* was fetched. This mirrors the existing Health-page idiom precisely: staleness is communicated by a relative-age timestamp everywhere else in this app (Device check-in, ADS-B pipeline), never by a content preview of what the stale/fresh data actually contains.

**What ships:**
- Not configured → `CALENDAR_STATUS_NOT_CONFIGURED`.
- Configured, no successful fetch yet → `CALENDAR_STATUS_CONFIGURED_PENDING`.
- Configured, at least one successful fetch → `CALENDAR_STATUS_CONFIGURED_SYNCED`, with the relative timestamp.

**No separate staleness warning banner.** A long-stale last-synced timestamp (e.g. "3d ago") is left to speak for itself via the relative-age text — exactly as Device check-in and ADS-B pipeline rows already do elsewhere in this app, with no additional colour or icon escalation. Introducing a warning threshold here would be a new judgment call ("how stale is too stale") with no existing precedent to anchor it, for a feature whose failure mode is already silent-by-design on the panel (per `16-CONTEXT.md`'s own discretion note: "A feed that has been unreachable for a long time should degrade to 'no matches' silently on the panel"). Consistency argues for the same quiet degradation on the companion page.

**No "test connection" button.** This phase's surface is deliberately small ("a small surface, deliberately," per the task framing). A manual test action would be the fetch-triggering sibling of the existing rate-limited Trigger Poll Now button (CFG-07) — a second, calendar-scoped rate limit, a second cooldown countdown, a second set of flash states, for a feature whose entire point is to fire rarely and unattended. The existing "Last synced" text already answers "is it working" without a new control. If this proves insufficient in practice, it is a small, additive follow-up — not a gap this spec is leaving unresolved by omission.

## Section Anatomy

**One new group in the existing Settings page, inside the tracked `<form id="settings-form">` — not a new immediate-POST section like Phase 15's Rules editor.** Unlike Rules (which needed its own `<form>` for add/delete actions and therefore could not nest inside `<form id="settings-form">`), Calendar's only interactive control is a single `<select>` with no independent action of its own — it saves through the shared Save Settings / dirty-bar flow exactly like Wake interval or Display. There is no HTML-validity constraint here forcing it outside the form, unlike Phase 15's Rules section.

```html
<div class="page-section" data-dirty-section="Calendar">
  <h2 class="text-heading">Calendar</h2>
  <p class="text-label section-caption">{CALENDAR_SECTION_CAPTION}</p>

  <p class="calendar-status">{status string — one of the three states above}</p>

  <div class="rule-add-form__field">
    <label for="calendar-theme">Theme</label>
    <select id="calendar-theme" name="calendar_theme_id" required>
      <!-- 18 <option> entries, THEME_IDS order, labels via device_config.theme_label(),
           pre-selected on the saved calendar_theme_id if one exists, else defaulting
           to the same theme_id the base Theme grid currently has selected — mirrors
           Phase 15's arrivals-grid default-selection precedent exactly. -->
    </select>
    <p class="text-label section-caption">{CALENDAR_THEME_HINT}</p>
  </div>
</div>
```

**Card class: `.page-section`, not `.theme-status`.** `.theme-status` is specifically the Theme group's own card (it also backs the single-theme read-only fallback row and the chip grid) — reusing it here would imply this card is a variant of theme *selection*, when structurally it is a distinct group that happens to contain one theme-assigning field, exactly like the Rules section is a `.page-section` even though it also assigns themes per row. `.page-section` is this codebase's generic Settings-group card class (Poll, Quiet hours, Wake interval, Display, and Rules all use it); Calendar joins that set rather than the Theme-specific one.

**`.rule-add-form__field` reused verbatim for the label+select+hint stack** — this is the exact wrapper Phase 15's Rules add-form already uses for its own "Theme" field (`<div class="rule-add-form__field"><label>Theme</label><select name="rule_theme_id">...</select></div>`), just without the surrounding `<form>` (there is nothing here to submit independently — the `<select>` submits with the whole settings form). Reusing this wrapper rather than inventing a new one keeps the label/spacing/hint layout byte-identical to a pattern the checker has already validated once this milestone.

**Placement — lowest-risk option, matching Phase 15's own precedent for exactly this kind of question.** Recommended: append the Calendar group as the **last** section inside `<form id="settings-form">`, immediately after Display and before the form's closing tag (and before the always-rendered static Save Settings fallback button). This is a pure zero-disruption append — Theme, Runway, Diagnostic LED, Quiet hours, Wake interval, and Display all keep their existing relative order and DOM nesting untouched; only one new sibling section is added at the end.

*Alternative considered and not recommended:* placing Calendar directly after Theme, ahead of Runway, on the reasoning that it is conceptually a third theme-assignment mechanism (base theme → arrivals override → calendar → rules, in resolution-precedence order) and a reader scanning top-to-bottom might expect the theme-related groups adjacent. This spec does not recommend it, because it would insert a new section in the *middle* of an already-shipped, already-verified group sequence rather than at its edge — a larger, avoidable diff for a purely narrative-ordering benefit. The planner may still choose it if desired; either position is compatible with this spec's copy, markup and CSS. Confirm at plan time, same flagging discipline Phase 15's own UI-SPEC used for its Rules-section placement question.

The Calendar section **does** carry `data-dirty-section="Calendar"` (unlike Phase 15's Rules section) — it is a genuinely tracked settings field, changing it dirties the save bar exactly like changing Runway or Wake interval does.

## Theme Control

**Reuses Phase 15's native `<select>` exactly — not the Theme group's chip grid, not a third UI idiom.** Same reasoning Phase 15 gave for the Rules editor's own theme field applies here with equal force: this is "assign a theme to a specific condition" (a calendar match), not "choose the frame's one ambient look" (which is what the photographic-preview chip grid is for, and what it already does twice — base Theme and the Phase-15 arrivals override). A third chip grid for a third condition-scoped theme assignment would visually compete with the two the page already has, at real estate cost, for a field the operator sets once and rarely revisits. `<select name="calendar_theme_id">`, 18 `<option>` entries in `THEME_IDS` order, `device_config.theme_label()` text, no swatch inside the `<option>` — byte-for-byte the same shape as Phase 15's `rule_theme_id` select (`15-UI-SPEC.md`'s Add-Form Shape, point 3), reused as a second consumer of that exact pattern rather than a variant.

## Control Density — reused classes vs. genuinely new rules

**Reused verbatim, zero modification:**
- `.page-section`, `.text-label`, `.section-caption` — the card, heading, and caption/hint treatment.
- `.rule-add-form__field` — the label+control+hint stack (see Section Anatomy above for why this specific wrapper, not a new one).
- Native `<select>` — inherits the global 44px-floor rule unmodified, exactly like every other `<select>` on this page.
- `button[type="submit"]` (the shared Save Settings button and the dirty bar's Save button) — completely unmodified; Calendar saves through the exact same mechanism as every other tracked field, adding zero new buttons.

**Genuinely new, justified here:**
- `.calendar-status` — the status-line paragraph. Justification: no existing selector targets "a plain body-text status sentence inside a `.page-section`" (the closest existing thing, `.theme-status__row`, is scoped to rendering a theme swatch dot plus label, which this is not — there is no swatch here, just a sentence). The rule itself declares nothing beyond what a bare `<p>` already inherits from the page's base body-text styles; it exists purely as a hook, not to carry new declarations. If it needs zero declarations at implementation time, that is a valid outcome — it can be dropped in favor of a bare `<p>` with no class, at the executor's discretion, since this spec's requirement is the *text and its role*, not the presence of a CSS class for its own sake.

No touch-target trade is introduced: the `<select>` stays in the "kept" category (native `input`/`select`'s unmodified 44px floor), matching `<input type="time">` and `<input type="number">`'s own precedent. Nothing in this phase needs a new entry in the touch-target floor register.

## Accessibility Floors

- **Focus visibility.** The `<select>` is a native form control — the existing global `:focus-visible` outline rule applies with zero new CSS.
- **Touch-target register.** No new entry, no new trade. The `<select>` keeps the 44px floor (kept category, same as every other `<select>`/`<input>` on this page).
- **Colour is never the sole signal.** The configured/not-configured/synced states are distinguished by text alone (three distinct sentences), never by colour — there is no status dot, no badge, no colour-coding on this line at all (see Color section above for why status-ok/status-warn colour was deliberately declined).
- **No motion.** Nothing on this surface toggles visibility or transitions — the status line always renders one of its three fixed strings, and the `<select>` is always present regardless of configured state (matching the Quiet-hours-fields precedent: a control stays in the DOM and in tab order regardless of whether its prerequisite is currently active).
- **Screen-reader legibility.** The status line is a plain paragraph, read as ordinary text by any screen reader — no ARIA needed, nothing hidden, nothing conditionally rendered based on JavaScript.
- **No JavaScript required.** This entire section works with scripting disabled: the status line is server-rendered plain text, the `<select>` is a native control, and saving goes through the existing static Save Settings fallback button exactly like every other tracked field already does.

## Open Questions for the Planner (not blocking — recorded per instruction)

1. **Exact env var name.** This spec uses `SKYPANE_CALENDAR_ICS_URL` in the not-configured copy string, matching the existing `SKYPANE_COMPANION_PASSWORD`/`SKYPANE_SLEEP_S` naming convention. `16-CONTEXT.md` leaves the exact name to plan-time discretion — if the planner picks a different name, only that one copy string needs to match it; nothing else in this spec depends on the literal string.

The alternative (directly after Theme) is explicitly compatible with this spec too — confirm at plan time, same as Phase 15's own Rules-section placement question.

If no such timestamp is persisted by the fetch mechanism as planned, the fallback is `CALENDAR_STATUS_CONFIGURED_PENDING`'s copy used unconditionally whenever configured — never a fabricated or estimated time.
4. **Whether `.calendar-status` needs any CSS declaration at all**, or can be a bare `<p>` with no class (see Control Density above) — left to the executor, since this spec's binding requirement is the text content and its Body-role typography, not the presence of a named selector.
