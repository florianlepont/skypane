<objective>
Correction 5, and it is two changes that the shared helper makes cheap and one trap
that would make them expensive.

**The cheap half.** `_theme_carousel_html(grid_html)` is already a pure presentation
wrapper — its own docstring says so — and returns
`'<div class="theme-carousel">%s%s%s%s</div>' % (disclosure_html, grid_html,
pagers_html, dots_html)`. "Voir tous les thèmes" is `disclosure_html` and it is
**first**. Moving it below the strip is a reorder of that one format string, and it
is correct for every grid that uses the helper — which is exactly why extending the
helper is better than reproducing it.

**The trap, and it is real.** `THEME_CAROUSEL_STRIP_ID = "theme-carousel-strip"` is a
**single `id`**, and it is both the strip's id and what the two pagers point at.
Wrapping a second and third grid with the helper as it stands renders **duplicate
ids** on one page, and every pager drives the first strip. That is the difference
between extending the carousel and breaking the page, and it must be fixed before the
helper is used a second time.

**And one correction to this phase's own research, found by reading.** The research
predicts the height saving as "three times the departures saving". It is not.
`theme-preview.js` **already collapses the non-selected usage panels** at load, so
with scripts running the arrivals and calendar grids are barely contributing height
at all. Folding them into strips is still right — it is right for the no-JS reader,
and right the moment the reader switches panels — but it will **not** move the
scripted page-height measurement much. The prediction below says so, and says it
before the measurement rather than after it.
</objective>
