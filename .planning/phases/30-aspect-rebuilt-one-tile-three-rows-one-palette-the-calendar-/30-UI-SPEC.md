## Swatch Rendering Contract

Every swatch in this card (row summary swatch, palette-chip swatch, rule-row swatch) draws from the
**same six real ink hex values** (`_palette_hex()`, from `server.panel_format.PALETTE_RGB`):

| Index | Hex | Name |
|-------|-----|------|
| 0 | `#000000` | Black |
| 1 | `#FFFFFF` | White |
| 2 | `#F0E050` | Yellow |
| 3 | `#A02020` | Red |
| 4 | `#2D5F9B` | Blue |
| 5 | `#326941` | Green |

**Rule (locked, matches the sketch's own CSS comment verbatim):**
- **PLAIN themes** (no `band_index` key in `THEMES[id]`) fill solid: `background: {hex of
  departing_index}`.
- **BAND themes** (`band_index` present) paint a white base with a coloured stripe across the
  middle third: base `background: #FFFFFF` (or `{hex of departing_index}` when that differs from
  white — check `departing_index` per-theme, do not hardcode white for all eleven band themes),
  plus a `.swatch__band` positioned `top: 33%; height: 34%; left: 0; right: 0;` filled with
  `{hex of band_index}`.
- **`band_blue_field` and `band_red_field`** have `departing_index == band_index` in the real
  registry (18/18 themes, unrelated Phase 25 finding, still true) — their swatch is therefore a
  **solid fill**, not a fake two-tone band. Do not special-case these two into looking banded when
  the real panel would not paint them that way — this is the exact "does not hide it behind a fake
  distinction" discipline the sketch's own header comment states.
- **Dithered themes** (`dithered: True`) render their flat ink colour in the swatch — no dither
  texture at 44-64px. Dithering is a full-panel rendering detail; texturing a swatch this small
  would not read as dithering, it would read as a dirty pixel. This matches the existing
  `.theme-chip__dot`'s own flat-hex treatment (it does not attempt to show dithering either).
- The row-summary swatch (32px in the sketch, `.usage-row__swatch`) and the rule-row swatch (20px,
  `.rule-row__swatch`) draw the **currently selected/saved** theme only — one swatch, not the
  two-dot departing/arriving pair `.theme-chip__dot` uses (that pairing is retired here because,
  per the already-recorded Phase 25 finding, `departing_index == arriving_index` for all 18 themes,
  so a second dot never distinguished anything — this is CFG-85's own stated ground for going to
  ONE swatch per row).

## No-JS / Control Contract (Floors — do not move)

Directly from CFG-85's own text and the app's existing no-JS **control** floor (not merely a page
floor — see skill file, "Controls" section):

1. **The accordion needs zero script for open/close, in any browser, scripts blocked or not.**
   `<details name="aspect-rows">` is native HTML — the one-open-at-a-time behaviour is the
   browser's own grouped-`<details>` feature. There is nothing to gate behind a `.js` class here;
   unlike a JS-enhanced control that defaults to a broken/collapsed state and needs a script to
   become interactive, this is complete and correct with zero script from first paint.
2. **Every palette selection is a native radio cross-submitting via `form="settings-form"`** —
   `colour_usage` itself (which row is *displaying*) is never submitted; only the four real
   theme-id fields (`theme`, `theme_arriving`, `calendar_theme_id`, `rule_theme_id`) are, unchanged
   from today.
3. **The preview is server-rendered for the SAVED theme** — a scripts-blocked reader sees a correct,
   non-interactive preview, never a blank box.
4. **The verdict is the value read back from disk** after a real operate-submit round trip with
   scripts blocked at 360px, in both languages — matching this app's existing `_NO_JS_CONTROL_
   REGISTRY` discipline (`companion/test_companion_app.py`). Register every new/moved control (the
   palette radios, the "Same as departures" leading radio, the rule-add form's fields — most of

## 6. One resolved discrepancy vs. ROADMAP prose (record, not a re-litigation)

ROADMAP's point 4 describes the calendar row as carrying "a 'Gérer' disclosure holding the URL
line, Replace-URL, Disconnect and How-it-works UNDER the row." **The developer-approved sketch does
not build a third, wrapping "Gérer"/"Manage" `<details>`** — it renders the status line, masked URL,
Replace-URL disclosure, Disconnect button and How-it-works disclosure **directly** inside the
Calendar row's own `<details>`, with no extra nesting layer (see the sketch's Row 3 markup, lines
273-291). This is not a gap: Replace-URL and How-it-works are already their own `<details>`
elements (pre-existing, unchanged), so a further "Gérer" wrapper would be a third disclosure layer
around two disclosures that already exist — redundant, not clarifying. Build the sketch's flatter,
approved shape. If a future session wants the extra "Gérer" layer, that is a new decision to make
explicitly, not an omission in this contract.
