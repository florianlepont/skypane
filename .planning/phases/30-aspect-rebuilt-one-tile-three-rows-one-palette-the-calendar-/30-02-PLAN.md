Build the palette's three new renderers as pure, additively-tested functions, BEFORE anything calls
them. Nothing in this plan changes a rendered page: `_frame_colours_card_html()` and
`calendar_group()` are untouched, `render()` is untouched, every existing check stays green.

This is deliberate interface-first ordering. The genuinely new work in Phase 30 is not the merge —
it is the swatch: the app's first CSS-drawn, non-photographic themed swatch, whose correctness
depends on three registry facts that are easy to get wrong (18 themes; `departing_index ==
arriving_index` for all 18, so ONE swatch replaces the retired two-dot pair; `departing_index ==
band_index` for `band_blue_field`/`band_red_field`, so those two are solid and not fake-banded).
Getting that wrong inside a 200-line merged-card rewrite would be discovered by eye, late. Getting
it wrong here is discovered by a check, now.

Purpose: isolate the one piece of this phase with no existing analog, and pin it against the LIVE
registry rather than against any transcription of it.
Output: `_palette_swatch_html()`, `_palette_chip_html()`, `_palette_grid_html()`,
`_usage_row_summary_html()`, plus the checks that prove them.

**TWO CORRECTIONS to the developer-approved sketch's own transcribed registry, found by importing
the real module.** Both matter and neither changes the approved design:

1. `band_blue_light` and `band_green_light` do **NOT** carry `dithered: True`. They carry a
   separate `band_dithered` key. The sketch's JS table marked both `dithered: true`.
2. The sketch's `paintSwatch()` applies `fill.style.opacity = '0.72'` to dithered themes. That is a
   sketch flourish and is **NOT** in 30-UI-SPEC.md's Swatch Rendering Contract, which says the
   opposite in as many words: a dithered theme "renders their flat ink colour in the swatch — no
   dither texture at 44-64px". Do not ship the opacity.

**Consequence, locked:** the swatch renderer reads `departing_index` and `band_index` and **nothing
else**. It never reads `dithered`, never reads `band_dithered`, never reads `ink_index`, never reads
`weight`. That is the whole rule, and it makes both corrections above moot by construction rather
than by remembering them.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| authenticated browser → `/display` GET | server-rendered HTML string interpolation; the only untrusted values reaching these renderers are a stored `theme_arriving`/`calendar_theme_id` that failed validation and a rejected POST's `submitted` dict |
| stored config → rendered swatch | a theme id read from disk selects a registry entry; an unknown id must never reach an interpolation site |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-30-05 | Tampering / Information Disclosure (XSS) | `_palette_chip_html()`, `_palette_grid_html()`, `_usage_row_summary_html()` | medium | mitigate | Every interpolated value passes `escape_html()` — `field_name`, `theme_id`, the translated label, the hex, and `radio_form_id`. No raw f-string/`%`-without-escape is introduced. |
