It imports `json`, `os`, `re`, `threading`, `datetime` from the stdlib, plus `server.device_config` (for `THEMES` membership validation). It must import no other `server.plane` sibling — specifically not enrich, detect, illustrations, manual_resolutions or render — because `poll_loop.py` already imports all of those plus this module, and the reverse direction would be a real cycle risk (D-13).

Module docstring, mirroring `manual_resolutions.py`'s own docstring structure paragraph-for-paragraph:
- What this file is: the per-flight colour-rule registry (D-07/D-08/D-09/D-12) plus the single effective-theme resolution function (D-13).
- The leaf-import rule spelled out as its own paragraph, in the same shape as the template's import-cycle paragraph, naming the five forbidden sibling modules and the reason.
- The caching warning copied in substance from the template: the process-scoped cache is for the once-per-cycle poll pipeline only; `companion/` is a long-running `ThreadingHTTPServer` and every request must call the fresh loader instead.
- **The D-02 extensibility note (this phase's one documentation obligation for the deferred roster half):** state that a rule record is a dict, deliberately not a bare theme-id string, so a future entry can carry fields this phase does not define — and state just as plainly that no such field is reserved, added, or read here, because rules in this phase are purely manual.
- That the file survives a redeploy because `deploy/deploy.sh` rsyncs `server/` with `--delete` while excluding `state`.

Module-level constants:
- `COLOUR_RULES_FILENAME = "colour_rules.json"`.
- `COLOUR_RULE_MAX_ENTRIES = 200` — total entries summed across all three kinds, not per kind. Comment it with `manual_resolutions.MANUAL_RESOLUTION_MAX_ENTRIES` as the named precedent and the same policy: a hard reject at the cap, never weakest-entry eviction, because this registry is authenticated-human-curated one entry at a time. This number is also what `companion/`'s registry-full flash copy interpolates, so it and that copy must agree.
- `RULE_KIND_CALLSIGN = "callsign"`, `RULE_KIND_HEX = "hex"`, `RULE_KIND_PREFIX = "prefix"`, and `RULE_KINDS = (RULE_KIND_CALLSIGN, RULE_KIND_HEX, RULE_KIND_PREFIX)`. Comment that this tuple's order is load-bearing twice over: it is D-09's most-specific-wins resolution order, and it is `rule_rows()`'s sort order.
- `ARRIVING_STATE = "arriving"` — the one render state the arrivals override applies to (D-04/D-06).
- Three positive-allowlist regexes, each compiled once, each the module's share of threat T-14-01: `_CALLSIGN_RULE_RE` matching two-to-eight uppercase alphanumerics; `_HEX_RULE_RE` matching exactly six uppercase hex digits; `_PREFIX_RE` matching exactly three uppercase letters. Comment each with its source shape: the callsign one duplicates `enrich.normalise_callsign()`'s strip-and-upper transform plus an eight-character real-world bound taken from `enrich.py`'s own comment; the prefix one duplicates `manual_resolutions.normalise_prefix()`'s gate; the hex one is new ground — no ICAO24 normaliser exists anywhere in this codebase today — and canonicalises to UPPERCASE even though live ADS-B `hex` values arrive lowercase, so the resolver must uppercase the live value before looking it up.
- Result constants, plain module-level strings: `ADD_OK_NEW = "ok_new"`, `ADD_OK_REPLACED = "ok_replaced"`, `ADD_REJECTED_KIND = "rejected_kind"`, `ADD_REJECTED_KEY = "rejected_key"`, `ADD_REJECTED_THEME = "rejected_theme"`, `ADD_REJECTED_FULL = "rejected_full"`, `ADD_FAILED = "failed"`. Document that the `ADD_OK_NEW`/`ADD_OK_REPLACED` split is this module's one deliberate divergence from the template's single success code, and why: D-09 requires the companion to say "replaced" rather than "added", and computing that at the HTTP layer would be a TOCTOU race against the write that just happened. These are not flash keys; `companion/app.py` maps them onto its own flash vocabulary and this module must not know flashes exist.
- `_WRITE_LOCK = threading.Lock()` and `_cached_rules = None` at module level.

Functions:

`colour_rules_path(state_dir)` — joins `state_dir` and `COLOUR_RULES_FILENAME`.

`normalise_rule_kind(raw)` — returns the member of `RULE_KINDS` when `raw` is exactly one of them, else `None`. Never raises.

`normalise_rule_callsign(raw)` / `normalise_rule_hex(raw)` / `normalise_rule_prefix(raw)` — each: non-string or falsy returns `None`; otherwise strip and uppercase, test against that kind's regex, return the canonical value or `None`. Never raise.

`normalise_rule_value(kind, raw)` — dispatches to the three above on a normalised kind; an unknown kind returns `None`. This is the single entry point `add_rule()`, `load_colour_rules()`, `delete_rule()` and `companion/app.py`'s delete route all use, so there is exactly one definition of "a valid rule key" in the codebase.

`normalise_rule_theme_id(raw)` — returns `raw` only when it is a string present in `device_config.THEMES`, else `None`. Never raises, never degrades to `device_config.DEFAULT_THEME_ID` — an unrecognised theme id means the rule is invalid and gets dropped, not silently retargeted at the default.

`load_colour_rules(state_dir)` — never raises. Missing, unreadable, non-JSON or non-dict-at-top-level all yield the empty registry shape (a dict with all three `RULE_KINDS` keys mapping to `{}`), so every caller can index by kind without a `.get()` dance. Then, for each kind in `RULE_KINDS`, iterate that kind's sub-dict in `sorted()` key order, dropping any entry where `normalise_rule_value(kind, key)` is `None`, the value is not a dict, `normalise_rule_theme_id(value.get("theme_id"))` is `None`, or `value.get("created_at")` is not a string. Rebuild every surviving entry from scratch — never reuse a parsed dict. Stop once `COLOUR_RULE_MAX_ENTRIES` surviving entries have been accumulated across all kinds, by breaking out of both loops, so a hand-edited oversized file cannot make a page render or a poll cycle unbounded. When the raw file held more entries than survived, print (never raise) a one-line warning naming the drop count, matching the template's own silent-data-loss-must-be-visible fix.

`add_rule(state_dir, kind, value, theme_id, now=None)` — returns one of the `ADD_*` constants and never raises. Validate everything before touching the filesystem, in this order: `normalise_rule_kind()` -> `ADD_REJECTED_KIND`; `normalise_rule_value()` -> `ADD_REJECTED_KEY`; `normalise_rule_theme_id()` -> `ADD_REJECTED_THEME`. Then take `_WRITE_LOCK` and hold it across the entire load-check-mutate-write sequence, not just the final replace. Inside the lock: load the current registry; compute `replacing` as whether the normalised value is already a key under that kind — this membership test is the added-versus-replaced answer and must be computed here, inside the lock, before mutating; when not replacing and the total entry count across all kinds is already at `COLOUR_RULE_MAX_ENTRIES`, return `ADD_REJECTED_FULL`. Otherwise default `now` to a UTC ISO-8601 string at seconds resolution, set the entry to a fresh dict carrying `theme_id` and `created_at`, then write: `os.makedirs(state_dir, exist_ok=True)`, dump JSON to a temp path whose name embeds both `os.getpid()` and `threading.get_ident()` (a single fixed `.tmp` suffix would let two concurrent companion writers interleave — T-14-02), then `os.replace()` onto the real path. Any exception during the write: remove the stray temp file inside a nested try/except and return `ADD_FAILED` rather than re-raising, because the caller is an HTTP route handler that needs a flash key, not a traceback. Return `ADD_OK_REPLACED` when `replacing` was true, else `ADD_OK_NEW`.

`delete_rule(state_dir, kind, value)` — returns `True` when an entry was removed, `False` otherwise (unknown kind, malformed value, absent key, or a write failure). Idempotent, never raises. Same `_WRITE_LOCK` discipline and the same tmp-write-then-replace block with `except` cleanup, returning `False` instead of `ADD_FAILED` on exception.

`rule_rows(registry)` — takes an already-loaded registry and returns a list of `(kind, value, theme_id, created_at)` tuples ordered by kind in `RULE_KINDS` order then by value ascending, skipping any malformed entry, never raising. This is what the Settings rules list renders from, so its determinism is what makes that list's markup testable.

`set_colour_rules_state_dir(state_dir)` — sets `_cached_rules` to `load_colour_rules(state_dir)` when `state_dir` is truthy, else to the empty registry shape. Docstring: call once per poll cycle from `run_once()`, beside the existing `illustrations.set_override_state_dir()` and `manual_resolutions.set_manual_registry_state_dir()` calls, for the reason `poll_loop.py`'s own comment already gives for `device_cfg` — a companion-side save landing mid-cycle must never split one rendered panel across two configurations. Also state that a process which never calls this setter sees an empty registry, i.e. exactly today's behaviour, which is what keeps every existing test unchanged.

`resolve_effective_theme_id(state, flight, device_cfg)` — **the D-13 resolver**, and the only function in this phase that decides what colour the panel is. Reads `_cached_rules` only; never touches disk. Never raises; always returns a member of `device_config.THEMES`. Docstring must state the order explicitly as the module's contract: exact callsign rule, then hex rule, then prefix rule, then the arrivals override when and only when `state` equals `ARRIVING_STATE`, then `device_cfg["theme"]`. Body: derive the normalised callsign and the normalised uppercase hex from `flight` defensively (a non-dict or absent field yields `None`); derive the candidate prefix as the first three characters of the normalised callsign, accepted only when they pass `_PREFIX_RE`, so a callsign that does not begin with three letters yields no prefix rather than a bogus one. Look up each kind in `RULE_KINDS` order, taking the first hit; return its `theme_id` only after re-checking it against `device_config.THEMES` (a tampered cache must not reach `build_canvas()` — T-14-05). With no rule hit and `state` equal to `ARRIVING_STATE`, return `device_cfg`'s `theme_arriving` when it is a non-`None` member of `device_config.THEMES`. Otherwise return `device_cfg["theme"]`, falling back to `device_config.DEFAULT_THEME_ID` if that key is somehow absent or invalid. Read `theme_arriving` with `.get()` so this module works unchanged against a `device_cfg` produced before plan 14-02 lands.

Add a comment at the resolver naming the ordering trap this module cannot enforce on its own: this function must be called only where `render_state` and `current_flight` are already settled, never hoisted beside `poll_loop`'s top-of-cycle config read — plan 14-03 owns that placement.
