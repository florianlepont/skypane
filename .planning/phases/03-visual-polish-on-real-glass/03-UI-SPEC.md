# Phase 03 — UI Design Contract (Amendment)

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

**This is an amendment document, not a from-scratch design contract.** Phase 2 shipped and verified `02-UI-SPEC.md` Revision 2 on real Spectra 6 glass (legibility "clearly legible", edges "hard, flat" — `02-05-SUMMARY.md`). Phase 3 makes exactly **one scoped, locked change**: the aircraft-illustration zone (zone 3 of `02-UI-SPEC.md`'s Layout & Composition section) changes from a flat, single-color, hard-edged CC0 silhouette to a full multi-color, Floyd-Steinberg-dithered, per-airline illustration (with a single dithered generic fallback for uncovered airlines and the "Route unavailable" state). **Every other zone — background field, state label, flight-number caption, route/airline captions, bottom static tag — is unchanged from `02-UI-SPEC.md` Revision 2.** This document specifies only what changes; where a section is unchanged, it says so explicitly and points back to `02-UI-SPEC.md` rather than re-deriving it.

**Source of every decision below:** `03-CONTEXT.md` D-01 through D-13 (user decisions from `/gsd-discuss-phase 3`) and `03-RESEARCH.md` (technical verification, this session, against the real installed `Pillow==12.3.0` and the real `server/panel_format.py`/`server/plane/render.py` code). Nothing in this document is newly decided here — it packages already-made decisions into the design-contract format the planner/executor/checker consume.

**Scope note (unchanged framing from `02-UI-SPEC.md`, restated for this amendment):** This is not a web/React UI. The "frontend" is a Python/Pillow raster-rendering pipeline on the server that produces a single 960,000-byte, 4-bit-per-pixel indexed-color panel image (`docs/PROTOCOL.md` §1), blitted directly to a 13.3" E Ink Spectra 6 panel by firmware with no rendering logic of its own. There is no browser, no DOM, no component tree, no user input this phase. The shadcn initialization gate does not apply (confirmed again this session — still no `components.json`/`tailwind.config.*`/`package.json`, stack is still Python).

## Illustration Asset Contract (D-09, D-10 — the file hand-off spec)

This is the precise, unambiguous spec the user follows when generating illustration files externally (AI image generation, per D-09 — this environment has no image-generation tool). Deliver files against this spec before any illustration-compositing code is wired to real files.

| Property | Requirement |
|---|---|
| **File format** | PNG, with an alpha (transparency) channel. The background around the aircraft shape must be transparent, not white or any solid color — this eliminates the need for any automated background-removal step (see `03-RESEARCH.md` Don't Hand-Roll: automated segmentation is explicitly rejected as disproportionate weight for a problem the hand-off spec solves for free). |
| **Source orientation** | **Nose-left**, matching the retired silhouette's documented `SILHOUETTE_SOURCE_NOSE = "left"` convention in `server/plane/render.py`. Every file in the set must use this same orientation — there is no per-file metadata field, so this is enforced by spec + human verification only (see Pitfall 4 below), not by code. |
| **Aspect ratio** | Loose landscape — roughly wider than tall (not an exact ratio requirement). The existing `draw_silhouette()` fit-within-both-caps sizing logic (`SILHOUETTE_TARGET_W = 900px` width cap, `SILHOUETTE_MAX_H = 260px` height cap, whichever binds first, preserving the source's own aspect ratio) is reused unchanged for the new illustration path — it already handles any reasonable landscape aspect ratio without modification. |
| **Minimum resolution** | ~1200px minimum width, for downscale headroom (comparable to the retired silhouette's own 1800px vendored raster width). |
| **Color content** | **Real airline brand/livery colors**, not grayscale or tonal art — under D-11 (full multi-color dithering, not the 2-color alternative), the render pipeline preserves color information through Floyd-Steinberg dithering rather than discarding it. Ask for the airline's actual identifiable brand colors (e.g. Air France's blue/white/red, Vueling's yellow, TAP's red) so the dithered output reads as that airline, not a generic gray jet. |
| **Naming convention** | `server/assets/icons/illustrations/{normalise_airline_key(airline_name)}.png` — see the normalization function below. One file per covered airline plus exactly one `generic-fallback.png`. |
| **File count (recommended set)** | **7 files**: 6 confirmed-`adsbdb`-hit carriers (Air France, Iberia, TAP, Air Algérie, CCM Airlines/Air Corsica, Vueling) + 1 generic fallback (D-08). Transavia France is an optional 8th (numerically dominant in real traffic but only a 2/20 `adsbdb` resolve rate — see Pitfall/rationale below). **Do not request `easyJet Europe` (`EJU`) or `KM Malta Airlines` (`KMM`)-specific illustrations** — both are confirmed `adsbdb` misses; an illustration for either would never be selectable regardless of art quality (`03-RESEARCH.md` Common Pitfalls Pitfall 5). |
| **Provenance** | Each vendored illustration gets the same provenance-note discipline as `stub-server/VENDOR.md`/`firmware/VENDOR.md` — generation date, tool/method (e.g. "ChatGPT image generation"), and the prompt used if practical to record — appended to a new `server/assets/icons/illustrations/VENDOR.md`, even though the asset is AI-generated rather than third-party-sourced. |

### Airline name → filename normalization (deterministic, no live lookup)

```python
# server/plane/render.py (or a small new module) — mirrors enrich.py's
# normalise_callsign() discipline: deterministic, never raises, returns
# None for anything falsy. This is a PURE function of airline_name; it
# makes no network call.
import re
import unicodedata

def normalise_airline_key(airline_name):
    """'Air Algérie' -> 'air-algerie', 'CCM Airlines' -> 'ccm-airlines'."""
    if not airline_name:
        return None
    ascii_name = unicodedata.normalize("NFKD", airline_name).encode("ascii", "ignore").decode("ascii")
    slug = re.sub(r"[^a-z0-9]+", "-", ascii_name.lower()).strip("-")
    return slug or None
```

Illustration selection: `route.get("airline_name")` (already resolved by the existing `server/plane/enrich.py` `lookup_route()` call in `poll_loop.py`'s `run_once()` — no new enrichment call) → `normalise_airline_key()` → look up `server/assets/icons/illustrations/{key}.png`; if the file doesn't exist (unresolved airline, or enrichment returned no route at all — the "Route unavailable" state), fall back to `generic-fallback.png`.

### Coverage caveat — do not conflate "seen in ADS-B traffic" with "resolvable to an illustration"

Illustration selection depends transitively on `adsbdb`'s crowdsourced coverage (already only 52.6% overall per `02-RESEARCH.md`), the same lookup PLANE-01/02's caption text already depends on. `EJU` and `KMM` prefixes are **confirmed misses** — an illustration generated for either airline is wasted effort; those flights always render the generic fallback regardless. Size the hand-off set around confirmed-hit carriers (table above), not around every callsign prefix seen in raw ADS-B samples.

## Fallback Illustration Treatment (D-08)

The fallback illustration (uncovered airlines + the "Route unavailable" enrichment-failure state) is a **single dithered generic illustration**, in the **same rendered style** as the per-airline set — full 6-color Floyd-Steinberg dithering, not a return to the old flat-White CC0 treatment. Recommended default (Claude's Discretion per `03-CONTEXT.md`, not yet a file that exists): a dithered re-render of the retired CC0 silhouette shape itself, in a neutral (non-airline-specific) color treatment — e.g. metallic/gray tones rather than any real airline's brand colors, so it visually reads as "generic jet," not as an accidental impersonation of an uncovered airline. This keeps one less external asset to hand off (the shape is already vendored) while still exercising the new dithered rendering path. This is a **recommendation for the executor to confirm with the user**, not a locked decision — the user may instead choose to AI-generate a bespoke generic illustration alongside the per-airline set.

The fallback illustration must be mirrored by state exactly like every per-airline illustration (D-10) — no exception for the fallback case.

## Color

**The background field, state label, all caption text, and bottom tag color contracts are UNCHANGED from `02-UI-SPEC.md` Revision 2** (Blue/Green full-bleed dominant, White foreground-only, Black used only in the Empty state). This phase adds exactly one narrowly-scoped addition: an exception for the illustration zone, plus a resolution of the previously-unverified panel RGB values.

### Illustration-Zone Exception (D-11 — new this phase)

Within the aircraft-illustration's own rendered bounding box **only** (inside zone 3, itself inside `SILHOUETTE_ZONE_TOP`..`+SILHOUETTE_ZONE_HEIGHT`), a per-airline dithered livery illustration may use the panel's full 6-color legal palette (Black, White, Yellow, Red, Blue, Green) via Floyd-Steinberg dithering — not White only. **This is a spatial exception, not a palette-wide reopening.** Every other foreground element in the Departing/Arriving states (state label glyph + text, flight-number caption, route line, airline line, bottom static tag) remains White-only, and the full-bleed background field remains Blue/Green-only, exactly as `02-UI-SPEC.md`'s existing per-state tables lock. `server/test_render.py` must enforce this spatial boundary directly (see Validation notes below) — a numeric "raise the color-count ceiling" check is insufficient and explicitly rejected (`03-RESEARCH.md` Common Pitfalls Pitfall 1).

| Zone | Legal colors this phase | Unchanged from `02-UI-SPEC.md`? |
|---|---|---|
| Full-bleed background field | Blue (departing) / Green (arriving) only | Yes |
| State label, flight-number caption, route/airline lines, bottom tag | White only (Black only in Empty state) | Yes |
| **Aircraft illustration bounding box** | **All 6 legal colors** (Black, White, Yellow, Red, Blue, Green) via Floyd-Steinberg dither | **No — new this phase (D-11)** |

### Cross-phase reservation update (D-12 — supersedes `02-UI-SPEC.md`'s note for the illustration zone only)

Yellow's presence in a per-airline illustration is explicitly **permitted** — the illustration zone and Phase 4's still-upcoming low-battery indicator are visually/spatially distinct enough that reuse isn't confusing. Red's original reservation rationale in `02-UI-SPEC.md` ("Phase 3's disruption banner, RER-03") is stale: RER-03 was deferred to v2 in the 2026-08-11 scope cut and has no scheduled consumer in this roadmap at all, so Red is likewise free for illustration use. This supersedes `02-UI-SPEC.md`'s cross-phase reservation note **for the illustration zone specifically only** — Yellow/Red remain unused everywhere else on the panel, unchanged.

### Panel RGB Calibration (D-13 — resolved this phase, interim values)

`server/panel_format.py`'s `PALETTE_RGB` constant has used unmuted pure-primary placeholder values since Phase 2 (`D-P2-03`), flagged unverified in `02-UI-SPEC.md`'s original draft. Now load-bearing: livery midtones could otherwise quantize to legally-correct but visually-wrong panel inks. Resolved this session as follows — both authoritative sources D-13 named (Waveshare `EPD_13in3e` reference driver; Seeed's official SKU 100088646 datasheet) were read in full and confirmed to publish **zero** RGB/colorimetric data (this is expected — e-ink controllers are commanded with color-plane nibbles, never RGB values, and ink chromaticity is typically manufacturer-confidential). A community estimate was found instead:

| Color | Interim starting value | Confidence |
|---|---|---|
| Red | `#A02020` (160, 32, 32) | **LOW — community forum estimate (Pimoroni "mattdm"), gathered by eye against a different branded product, not measured with instrumentation. NOT final.** |
| Yellow | `#F0E050` (240, 224, 80) | LOW, same caveat |
| Green | `#608050` (96, 128, 80) | LOW, same caveat |
| Blue | `#5080B8` (80, 128, 184) | LOW, same caveat |
| Black / White | Left at nominal `(0,0,0)`/`(255,255,255)` | Not contested by any source checked |

**Interim step (this phase, low-risk):** Update `PALETTE_RGB`'s Yellow/Red/Blue/Green entries to the values above as a documented starting point. This is a render-internal-only constant (never crosses the wire to the device, per `panel_format.py`'s own existing comment) — zero risk to the protocol, and very likely closer to the real panel than the current pure-primary placeholders regardless of exact-match uncertainty.

**Required follow-up (`checkpoint:human-verify`, must happen before final illustration hand-off files are quantized against production code):** a hardware-calibration pass extending `hardware/BRINGUP-LOG.md`'s existing `## Panel Observations` entry (2026-08-25, six-color-band verification already confirmed clean/distinct bands on the real panel):
1. Render a small 6-swatch preview using the interim `PALETTE_RGB` values above, view on a normal monitor.
2. Compare side-by-side against the real panel showing the existing `stub-server/make_test_panel.py --pattern palette` six-band test image.
3. Adjust the four contested triples by eye until the preview approximates the real panel's ink hues — explicitly informal (no colorimeter; e-ink panels are widely reported incompatible with consumer colorimeter probes), sufficient for this constant's actual accuracy bar (nearest-neighbor hue matching across a closed 6-color set, not colorimetric precision).
4. Record the final tuned values, comparison method, and date in `hardware/BRINGUP-LOG.md`, extending the existing Panel Observations entry.

This does not block starting illustration-selection/compositing code — only the *subjective color-matching quality* of a livery's quantized output depends on the exact values; the wire-format legality is already verified independent of them (`03-RESEARCH.md` Pattern 1, local execution confirmed).

## Validation Notes (for planner/checker — not a new template section, included because this amendment has direct test-file implications)

`03-RESEARCH.md`'s Validation Architecture section has the exact line-level `server/test_render.py` change plan; summarized here for the checker's Dimension 3 (Color) and Dimension 2 (Visuals) sign-off:

- The existing "exactly 2 distinct palette indices" whole-canvas guard rail must become **spatially scoped**: illustration bbox may use up to 6 legal indices; a copy of the canvas with the illustration's bbox blanked to `bg_idx` must contain **exactly** `{bg_idx, IDX_WHITE}`.
- The existing whole-buffer Yellow/Red reservation checks must be rewritten to operate on the pre-pack canvas with the same bbox-blanking technique — asserting no Yellow/Red **outside** the illustration zone, not "no Yellow/Red anywhere."
- The existing silhouette "shape painted"/"mirroring differs" checks (currently hardcode `IDX_WHITE`) must generalize to non-background-index counting, since a dithered illustration may legitimately contain little or no White.
- Illustration-selection logic (`normalise_airline_key()`, known-airline hit, unresolved-airline fallback) needs new unit checks.
