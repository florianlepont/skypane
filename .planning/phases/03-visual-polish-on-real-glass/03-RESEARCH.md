## Summary

This phase's engineering core is narrow and already fully traceable in the existing codebase: `server/plane/render.py`'s `_build_active_canvas()` composites a full-bleed state-color background, a flat White silhouette, and flat White caption text onto a Pillow `"P"`-mode canvas, then asserts (a "guard rail") that exactly 2 distinct palette indices exist before packing. Phase 3 adds a **new, spatially-scoped compositing step** — a dithered per-airline illustration — dropped into the same zone-3 box `draw_silhouette()` already reserves, selected by `route.get("airline_name")` (already resolved by `server/plane/enrich.py`'s `lookup_route()`, already wired into `poll_loop.py`'s `run_once()`).

The single most consequential finding, verified this session by running real code against the real installed Pillow (12.3.0) and the real `server/panel_format.py` palette: **Floyd-Steinberg dithering does not require introducing new palette colors.** `Image.quantize(palette=<a genuinely 2-entry P-mode image>, dither=Image.FLOYDSTEINBERG)` against just the current state's two legal colors (White + Blue-or-Green) produces a bi-level stipple pattern that reads as tonal/photographic gradient while using **only the two already-legal indices** — confirmed by direct `getcolors()` inspection. Mirroring that dithered result post-hoc via `Image.transpose(Image.FLIP_LEFT_RIGHT)` was also verified to introduce zero new colors. This means: **if the illustration stays within the existing White-on-Blue/Green palette, `_build_active_canvas()`'s "exactly 2 distinct palette indices" guard rail does not need to change at all**, and `server/test_render.py`'s two existing "no Yellow/Red nibble (cross-phase reservation)" checks (lines 194-215) stay green with zero modification. This directly contradicts the phase description's assumption that "that 2-color assertion will need to change for a dithered region" — it does not, under the recommended (2-color) approach.

The counter-reading — literal per-airline **livery colors** (the user's own phrase, "covering") — would require the illustration to use Yellow/Red/Black too, which *would* break the existing cross-phase-reservation test (Yellow is held in reserve for Phase 4's low-battery indicator, still upcoming) and would require an explicit `02-UI-SPEC.md` addendum, since the phase's own canonical_refs note states the Color contract "stay[s] locked as-is." **This is the single most load-bearing open question for planning** (see Open Questions #1) and should be resolved with the user — ideally via a `checkpoint:human-verify` early in the plan, before the user spends effort generating illustration files in a color gamut the plan later can't legally render — rather than assumed either way.

The illustration hand-off itself (D-09) is a real external dependency with no code-side substitute: the user generates files outside this session and hands them to Claude. The existing `stub-server/VENDOR.md`/`server/assets/icons/VENDOR.md` provenance-note convention is the right precedent to extend (record generation tool/date/prompt instead of a third-party URL/license). The existing `02-05-PLAN.md` Task 3 (`type="checkpoint:human-verify" gate="blocking"`) is the right task-type precedent for both the illustration hand-off gate and the on-glass verification pass this phase's ROADMAP success criteria already require.

**Primary recommendation:** Implement per-airline illustrations as 2-color (White + state-background) Floyd-Steinberg-dithered art, spatially confined to the existing zone-3 box, selected by a new `normalise_airline_key(airline_name)` → filename lookup keyed off `enrich.lookup_route()`'s existing `airline_name` field, with a `checkpoint:human-verify` task gating the illustration hand-off (specifying transparent-PNG format, nose-left source orientation, and the exact filename/count contract) before any per-airline rendering code is written against real files.

### Pattern 1: Constrained-palette dithering with index remap (the core new mechanism)

**What:** Quantize a source illustration (RGB or grayscale) down to exactly the current state's 2 legal palette indices using Floyd-Steinberg dithering, then remap the resulting local 0/1 indices to the canvas's real `IDX_WHITE`/`IDX_BLUE`/`IDX_GREEN` constants before compositing — so the dithered region can be `canvas.paste()`d directly with no new palette entries introduced anywhere on the panel.

**When to use:** For every per-airline illustration and the D-08 generic fallback, inside `_build_active_canvas()`, replacing (or alongside, if a flat fallback shape is retained for some case) the current `draw_silhouette()` call.

**Example (verified this session against the real `server/panel_format.py` module — `[VERIFIED: local execution, Pillow 12.3.0]`):**
```python
# Source: verified locally against server/panel_format.py's actual IDX_WHITE/IDX_BLUE
from PIL import Image
from server import panel_format as pf

def dither_to_state_palette(source_rgb, bg_idx):
    """source_rgb: a Pillow "RGB" (or "L".convert("RGB")) source image.
    bg_idx: pf.IDX_BLUE or pf.IDX_GREEN (the current state's background index).
    Returns a "P"-mode image whose only two pixel values are bg_idx and
    pf.IDX_WHITE - safe to canvas.paste() directly, no mask required for
    color correctness (a mask is still needed if the source has non-
    rectangular alpha-transparent edges - see Pattern 2).
    """
    white_rgb = tuple(pf.PALETTE_RGB[pf.IDX_WHITE * 3: pf.IDX_WHITE * 3 + 3])
    bg_rgb = tuple(pf.PALETTE_RGB[bg_idx * 3: bg_idx * 3 + 3])

    # A genuinely 2-entry palette image - NOT zero-padded to 256 entries.
    # Zero-padding to 256 with an unrelated filler color (e.g. black) is a
    # verified pitfall: any source pixel that exactly matches the filler
    # RGB gets quantized to a 3rd, illegal palette index.
    pal_img = Image.new("P", (1, 1))
    pal_img.putpalette([bg_rgb[0], bg_rgb[1], bg_rgb[2], white_rgb[0], white_rgb[1], white_rgb[2]])

    quantized = source_rgb.quantize(palette=pal_img, dither=Image.FLOYDSTEINBERG)
    # quantized's local indices are 0=bg, 1=white (matching putpalette order).
    # Remap to the REAL canvas indices before paste - a P-mode paste() copies
    # raw index values, so they must already match the destination palette.
    remap = {0: bg_idx, 1: pf.IDX_WHITE}
    return quantized.point(lambda i: remap.get(i, i))
```

### Pattern 2: Alpha-masked paste for non-rectangular illustration edges

**What:** If the handed-off illustration has a transparent background (recommended — see Don't Hand-Roll), preserve its alpha channel separately from the dithering step and use it as the `mask=` argument to `canvas.paste()`, exactly as `paste_mask()` already does for the flat silhouette — but do NOT hard-threshold this mask to strictly binary (that's specific to the flat-fill pipeline); a soft alpha edge composited against a dithered region is fine since the dithered content itself is already constrained to the 2 legal indices.

**When to use:** Whenever the source illustration isn't already a clean rectangle (almost certainly true for AI-generated art).

### Pattern 3: Mirror-after-dither, not dither-per-orientation

**What:** Dither the illustration once in its canonical (source) orientation, then call `Image.transpose(Image.FLIP_LEFT_RIGHT)` on the resulting `"P"`-mode dithered image for whichever state needs the opposite orientation — verified this session to introduce zero new colors (pure index repositioning, no re-quantization needed). This resolves the CONTEXT's open question #5 directly: mirroring after dithering is safe and simpler than dithering twice.

**When to use:** Every illustration render, exactly where `draw_silhouette()` currently computes `mirror = required_nose != SILHOUETTE_SOURCE_NOSE` and calls `paste_mask(..., mirror=mirror)`.

### Pattern 4: The established synthetic-render forcing technique (D-02/D-04)

### Anti-Patterns to Avoid
- **Zero-padding a quantize target palette to 256 entries with an arbitrary filler color:** verified this session to silently introduce a 3rd, illegal palette index whenever a source pixel exactly matches the filler RGB. Always build a genuinely N-entry `Image.new("P", (1,1))` with `putpalette()` sized to exactly the colors you want selectable.
- **Pasting a quantized image's raw indices onto the canvas without remapping:** a throwaway 2-entry palette image's local index 0/1 numbering has no relationship to the canvas's real `IDX_*` constants unless you explicitly remap via `.point()` first — a direct paste without remapping will silently introduce wrong colors (e.g. accidental Black) that are visually invisible in isolated testing but wrong against the real canvas palette.
- **Automated background removal as a code solution:** no segmentation library exists in this project and adding one (e.g. `rembg`/`onnxruntime`) is disproportionate weight for a problem the hand-off spec can eliminate entirely by requiring transparent-PNG input.

## Common Pitfalls

### Pitfall 1: Assuming the "exactly 2 palette indices" guard rail must change
**What goes wrong:** A planner reads the phase description's own framing ("that 2-color assertion will need to change for a dithered region") and rewrites `_build_active_canvas()`'s guard rail to allow more indices, before checking whether the chosen dithering approach actually needs them.
**Why it happens:** Dithering is intuitively associated with "more colors" (photographic gradients), but Floyd-Steinberg dithering with exactly 2 target colors is a well-established bi-level halftone technique (this is literally how classic 1-bit-display dithering works) and was verified this session to stay within the existing 2-index contract when constrained to White + the state background.
**How to avoid:** Decide the color-gamut question (Open Question #1) *first*. If 2-color is chosen, leave the guard rail and `test_render.py`'s existing "no Yellow/Red" checks untouched. Only widen the guard rail if the full-livery-color path is explicitly chosen by the user.
**Warning signs:** A plan task that modifies `_build_active_canvas()`'s guard-rail assertion and `test_render.py`'s reservation checks in the same commit as the illustration feature, without a preceding decision task establishing why more colors are needed.

### Pitfall 2: Zero-padded quantize target palette silently introducing a 3rd color
**What goes wrong:** `Image.new("P", (1,1)).putpalette(two_colors + [0,0,0]*254)` (padding the unused 254 slots with black, the common naive pattern) causes `quantize()` to select index 2+ (black) whenever a source pixel's RGB exactly equals `(0,0,0)` — verified this session (a test source with a pure-black gradient endpoint produced exactly this 3rd index).
**Why it happens:** Pillow's palette-nearest-neighbor matching considers all 256 slots, and an all-zero filler is itself a valid, distinct color that can legitimately "win" the nearest-neighbor comparison for near-black source pixels.
**How to avoid:** Build a genuinely 2 (or N)-entry palette image with no padding at all, or pad every unused slot with a duplicate of one of the real target colors — never with an unrelated color like black.
**Warning signs:** `canvas.getcolors()` reporting more distinct indices than expected after compositing an illustration whose source content includes near-black or near-white extremes.

### Pitfall 3: Direct-pasting unmapped local quantize indices onto the real canvas
**What goes wrong:** `canvas.paste(quantized_image, box)` where `quantized_image`'s local palette indices (0, 1 from its own throwaway 2-entry palette) don't match the canvas's real `IDX_*` numbering — this silently pastes the wrong colors (e.g. `IDX_BLACK` where White was intended) because P-mode `paste()` copies raw index values, not RGB.
**Why it happens:** It's easy to assume a "P"-mode image's colors travel with it; they don't — only the index numbers do, and two different P-mode images' index-to-RGB mappings are independent unless explicitly aligned.
**How to avoid:** Always `.point()`-remap a quantized image's local indices to the destination canvas's real constants before pasting (Pattern 1's `dither_to_state_palette()`).
**Warning signs:** A dithered illustration that looks correct in an isolated preview PNG but renders with unexpected black/wrong-color speckle once composited onto the real state-color canvas.

### Pitfall 4: Ambiguous nose orientation across a multi-file illustration set
**What goes wrong:** Unlike the single vendored silhouette (whose `SILHOUETTE_SOURCE_NOSE = "left"` is a single documented constant), a per-airline set generated by the user across multiple external sessions/tools risks inconsistent source orientation — one file's nose left, another's nose right — silently breaking D-10's mirror-by-state contract for whichever files are inconsistent.
**Why it happens:** The user is generating these files externally with no code-side validation of orientation until a human looks at the render.
**How to avoid:** Make source-nose orientation an explicit, single documented requirement in the D-09 hand-off spec (e.g. "every file must be nose-left, matching the retired silhouette's convention") — not a per-file metadata field, since there's no code-side way to detect it automatically. Verify visually as part of the illustration hand-off checkpoint, per file, before wiring any of them into the render path.
**Warning signs:** A departing-state render where the mirrored illustration's nose points the wrong way for one specific airline but not others.

### Pitfall 5: Enrichment misses silently reduce the achievable "per-airline" coverage below what the illustration count suggests
**What goes wrong:** The planner sizes the illustration hand-off around "every airline seen in Phase 1 samples" (38 distinct callsigns, spanning ~10 apparent airlines), but illustration selection is keyed off `route.get("airline_name")` from the *same* `adsbdb` lookup that already only resolves 52.6% of real traffic (`server/plane/enrich.py` docstring, `[VERIFIED: 02-RESEARCH.md line 59]`). Two of the callsign prefixes seen in Phase 1 samples (`EJU`, `KMM`) are *documented adsbdb misses* (`02-RESEARCH.md` line 96: "hexdb.io recovered 2 of 4 sampled adsbdb misses (EJU84YF, KMM466)") — meaning `airline_name` is never available for those flights regardless of how good an illustration exists for them, so they always fall through to the D-08 generic fallback no matter what.
**Why it happens:** It's easy to conflate "airlines seen in ADS-B traffic" with "airlines the illustration-selection logic can actually resolve" — they are not the same set, because selection depends transitively on `adsbdb`'s crowdsourced coverage, not on ADS-B detection alone.
**How to avoid:** Size the illustration hand-off around airlines confirmed (or strongly likely, given `02-RESEARCH.md`'s carrier-class finding) to resolve via `adsbdb`, not around every callsign prefix seen in raw samples. See the concrete candidate list under Open Questions / State of the Art below.
**Warning signs:** The user generates a `KMM` (KM Malta Airlines) or `EJU` (easyJet Europe) illustration expecting it to render, and it never does because the enrichment step upstream of illustration selection was already a miss for that callsign.

### Airline-name normalization for filename matching

`enrich.py`'s `lookup_route()` returns `airline_name` verbatim from `adsbdb`'s response (e.g. `"Transavia France"`, confirmed via a live lookup this phase in `02-04-SUMMARY.md`). No normalization currently exists in the codebase for this field — a new small helper is needed:

```python
# Source: new code, following enrich.py's own normalise_callsign() convention
import re
import unicodedata

def normalise_airline_key(airline_name):
    """'Air Algérie' -> 'air-algerie', 'CCM Airlines' -> 'ccm-airlines'.
    Mirrors enrich.normalise_callsign()'s discipline: deterministic,
    never raises, returns None for anything falsy.
    """
    if not airline_name:
        return None
    ascii_name = unicodedata.normalize("NFKD", airline_name).encode("ascii", "ignore").decode("ascii")
    slug = re.sub(r"[^a-z0-9]+", "-", ascii_name.lower()).strip("-")
    return slug or None
```

This must be a pure function of `airline_name` only (no live API call), matching `enrich.normalise_callsign()`'s existing discipline of keeping normalization deterministic and side-effect-free.

## Open Questions

1. **Does D-06/D-07's "richer illustration" mean 2-color dithered tonal art (White + state background only), or literal multi-color airline livery ("covering," using Yellow/Red/Black too)?**
   - What we know: `02-UI-SPEC.md`'s locked Color contract reserves Blue/Green for background-only and White for foreground-only in the active states, and explicitly holds Yellow/Red in reserve for Phase 4's upcoming low-battery indicator. `server/test_render.py` has two existing, currently-green tests asserting no Yellow/Red nibble appears in departing/arriving renders. The phase's own canonical_refs note says this phase changes "the aircraft-illustration rendering treatment and detail level, NOT the background/color/typography/copy contracts, which stay locked as-is." Yet the user's own phrasing in CONTEXT.md's Specific Ideas is "Illustration de l'avion et de son covering" — livery is inherently multi-color.
   - What's unclear: Whether the user considers 2-color dithered tonal shading (which CAN read as "richer"/photographic without literal brand colors) sufficient, or specifically wants recognizable airline colors.
   - Recommendation: Default to 2-color dithering (this research's primary recommendation) since it is zero-risk against the existing locked spec and existing tests, and is what's actually verified working this session. Surface this explicitly as a `checkpoint:human-verify` decision point early in the plan — ideally before the user spends effort generating illustration files, since the answer changes what to ask them to generate (grayscale-appropriate tonal art vs. full-color art that will then be visually degraded to 2 colors anyway if 2-color is ultimately chosen).

2. **If full 6-color livery dithering is chosen instead, do real Spectra 6 panel RGB values become load-bearing?**
   - What we know: `02-UI-SPEC.md` already flags panel RGB values as unverified LOW confidence. `server/panel_format.py`'s `PALETTE_RGB` uses nominal primary-color RGB triples (pure red/green/blue/yellow) explicitly documented as "render-internal only... never cross the wire to the device" (D-P2-03).
   - What's unclear: For 2-color (White/bg) dithering, only the *legal index identity* matters (verified this session — nearest-neighbor quantization against 2 known-legal indices works correctly regardless of their nominal RGB, since there's no competing 3rd/4th/5th color to confuse the match). For full 6-color dithering, the nominal RGB values directly determine which of the 6 real inks a given source pixel's *hue* gets mapped to — if the real panel's Blue/Yellow/Red inks look meaningfully different from the nominal primaries used for quantization, midtones in the source art could map to visually wrong panel colors even though the wire format itself stays correct.
   - Recommendation: Not load-bearing under the recommended 2-color path. Becomes load-bearing only if Open Question #1 resolves toward full-color livery — in that case, resolve real panel RGB (e.g. against the Waveshare `EPD_13in3e` reference driver, per `02-UI-SPEC.md`'s own open note) before finalizing the quantization palette, or accept a documented risk that livery colors may render with some hue drift.

3. **Exact file-handoff aspect ratio / resolution / format contract for the user**
   - What we know: The existing silhouette's placement constraints are `SILHOUETTE_TARGET_W = 900`, `SILHOUETTE_MAX_H = 260` (`server/plane/render.py` lines 148-149), with the vendored asset's ~2.22:1 aspect ratio meaning the height cap binds first (per `server/assets/icons/VENDOR.md`).
   - What's unclear: Whether to ask the user for images pre-cropped to ~2.2:1, or to accept any aspect ratio and let the render code fit-within both caps (same logic `draw_silhouette()` already implements) — the latter is more forgiving of what an AI image tool actually produces.
   - Recommendation: Ask for a *loose* aspect-ratio target (roughly landscape, wider than tall) rather than an exact ratio, and reuse `draw_silhouette()`'s existing fit-within-both-caps sizing logic unchanged — it already handles "whichever cap binds first" correctly and needs no modification for this phase. Specify: PNG format, transparent background (alpha channel), nose-left source orientation (matching the retired silhouette's documented convention so D-10's mirror-by-state logic needs no per-file metadata), and a minimum width of roughly 1200px for downscale headroom (comparable to the existing silhouette's 1800px vendored raster width).

4. **Whether the "wall-mounted ambient art" success criterion (ROADMAP criterion 4) can be meaningfully closed this phase at all**
   - What we know: D-03 explicitly flags the frame is currently on a desk, not wall-mounted, and instructs recording this as a provisional caveat rather than a blocker.
   - What's unclear: Whether the plan should include a distinct, separately-tracked follow-up verification step for "once wall-mounted," or just note the caveat in the phase's SUMMARY and move on.
   - Recommendation: Follow D-03 literally — record the caveat, don't block phase closure on it, and don't invent a new tracked follow-up task unless the user asks for one during planning.
