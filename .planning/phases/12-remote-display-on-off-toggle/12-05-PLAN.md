Add the Display group to the companion Settings page: a single on/off checkbox saved
through the same merged form and the same single `save_device_config()` call every other
setting already uses (D-08), defaulting to on (D-09), with a caption that tells the truth

added. This plan implements an approved contract; it is not a design exercise.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| browser HTTP POST -> `handle_post()` | An untrusted submitted checkbox value crosses into a persisted document that decides whether the frame renders |
| `handle_post()` -> `save_device_config()` | The single write path for all eight settings fields; a partial write would desynchronise the page from disk |
| saved config -> `render()` | A stored value is interpolated back into HTML on the next page load |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-12-05-01 | Tampering | `handle_post()`'s checkbox resolution | high | mitigate | Exactly three shapes are resolved and no others: absent means off, the exact `DISPLAY_CHECKBOX_VALUE` means on, anything else rejects the whole submission before `save_device_config()` is called. This is the same ladder `led_enabled`/`quiet_hours_enabled` already use; Task 2 check 4 covers all three plus byte-identity on rejection |
| T-12-05-02 | Tampering | All-or-nothing rejection across eight fields | high | mitigate | There is still one form and one `save_device_config()` call, so a crafted value in any field aborts before the write rather than persisting the valid remainder and leaving disk out of step with what the page would redisplay |
| T-12-05-03 | Elevation of Privilege | The Settings route | medium | accept | This group adds no new route, no new handler and no new HTTP verb — it rides the existing merged `<form action="/settings">` already behind the companion app's session auth, unchanged by this phase |
| T-12-05-04 | Information Disclosure | Rendered HTML | medium | mitigate | Every interpolated value passes through `escape_html()`, matching the five sibling groups. The only value rendered is a boolean-derived `checked` flag, so there is no attacker-controlled string on this path in the first place |
| T-12-05-05 | Spoofing | The operator's expectation of when the change lands | medium | mitigate | The caption states the roughly-five-minute latency in both directions rather than implying immediacy (D-02), and the verify command asserts the caption makes no immediacy claim. The panel screen itself makes no return-time promise either (plan 12-02, D-04) |
| T-12-SC | Tampering | npm/pip/cargo installs | high | accept | This plan adds zero packages and zero front-end dependencies — the companion app is server-rendered HTML strings with no client framework and no component registry (`12-UI-SPEC.md` Registry Safety: not applicable, no `components.json` in this repo) |
</threat_model>
