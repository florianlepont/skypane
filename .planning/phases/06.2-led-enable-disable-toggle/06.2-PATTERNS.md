### `companion/pages/config_page.py` (controller, request-response)

**Analog:** same file — `theme_fieldset()` (lines 52-75) and its `handle_post()` branch (lines 152-197)

**Fieldset render pattern** (lines 52-75), adapted to a single checkbox instead of a radio group per RESEARCH.md's Code Examples section:
```python
LED_HELPER_TEXT = (
    "Controls the board's built-in bring-up LED, lit only during the "
    "device's brief active wake window - not visible from the wall-facing "
    "side. Applies on the device's next scheduled poll.")

def led_fieldset(current_led_enabled):
    checked = " checked" if current_led_enabled else ""
    return (
        "<fieldset>"
        "<legend>Bring-up LED</legend>"
        "<label>"
        '<input type="checkbox" name="led_enabled" value="on"%s> Enabled'
        "</label>"
        '<p class="text-label">%s</p>'
        "</fieldset>"
    ) % (checked, escape_html(LED_HELPER_TEXT))
```

**Independent-section pattern to follow per D-01** — mirror `poll_trigger_section()` (lines 105-124), NOT `theme_fieldset()`'s placement inside the single `<form action="/config">` at lines 136-148. `poll_trigger_section()` demonstrates the codebase's existing convention for an "own dedicated, independently-submittable section": its own `<form method="post" action="/poll-now">`, distinct from the Theme/Runway form. RESEARCH.md's Open Question recommends giving the LED toggle its own `<form method="post" action="/config-led">` (or similar) for this exact reason — checkbox absence is otherwise ambiguous inside a shared form using the "absent = leave unchanged" convention that `theme`/`tracked_runway` rely on (radio groups, always present). This resolves cleanly with a separate form/route.

**`render()` pattern** (lines 127-149): add a third section, following the existing `poll_trigger_section()` `<section class="page-section">` wrapper shape (lines 141-144) rather than folding into the first `<form>`.

**`handle_post()` pattern** (lines 152-197): existing shape is explicit membership test -> reject whole submission -> `save_device_config()` call inside try/except (ValueError, OSError) -> return `FLASH_SAVE_FAILED`/`FLASH_SAVED`. For the LED checkbox, presence in `form` (not membership) is the check — if a separate route/handler is added per D-01, it can be a small parallel function `handle_led_post(form, ctx)` mirroring `handle_post()`'s structure exactly:
```python
def handle_led_post(form, ctx):
    state_dir = ctx["state_dir"]
    led_enabled = "led_enabled" in form  # unchecked checkbox = absent = False
    try:
        device_config.save_device_config(state_dir, led_enabled=led_enabled)
    except (ValueError, OSError):
        return FLASH_SAVE_FAILED
    return FLASH_SAVED
```

**Flash-key constants** (lines 41-49): reuse `FLASH_SAVED`/`FLASH_SAVE_FAILED` — no new flash keys needed for this phase's success/failure cases (matches how `poll_trigger_section()` reuses `FLASH_POLL_TRIGGERED`/`FLASH_POLL_COOLDOWN`/`FLASH_POLL_FAILED` for its own distinct action rather than overloading the Save-Settings keys — if the LED toggle truly gets its own route/form, consider whether it needs its own flash pair too, following that same precedent of one flash-key pair per distinct POST action).

## Shared Patterns

### Fail-open defensive JSON read
**Source:** `server/device_config.py:127-146` (`load_device_config`) and `stub-server/byos_server.py:63-68` (`load_state`)
**Apply to:** `normalise_led_enabled()`, `read_led_enabled()`
```python
try:
    with open(path) as fh:
        data = json.load(fh)
except (OSError, ValueError):
    data = {}  # or a safe scalar default
if not isinstance(data, dict):
    data = {}
```
Never raise; always degrade to a documented safe default.

### Atomic JSON write (tmp-write-then-os.replace)
**Source:** `server/device_config.py:178-191` (`save_device_config`), `stub-server/byos_server.py:71-75` (`save_state`)
**Apply to:** `save_device_config()`'s extended body (no new write path needed — `led_enabled` rides the existing writer)
```python
tmp = path + ".tmp"
try:
    with open(tmp, "w") as fh:
        json.dump(new_config, fh, indent=1)
    os.replace(tmp, path)
except Exception:
    if os.path.exists(tmp):
        try:
            os.remove(tmp)
        except OSError:
            pass
    raise
```

### Asymmetric validation discipline (read forgives, write rejects)
**Source:** `companion/pages/config_page.py:152-166` (`handle_post()` docstring, T-06-01-01)
**Apply to:** `config_page.py`'s new LED POST handling, and `server/device_config.py`'s `save_device_config()`
A malformed/hostile value read from disk silently degrades to a safe default (`normalise_led_enabled()`). A malformed/hostile value submitted via POST rejects the whole submission with `FLASH_SAVE_FAILED` — never silently coerced. This asymmetry is deliberate project convention, not an oversight.

### Explicit type/membership check before dict-key or JSON-response use
**Source:** `server/device_config.py:108-117` (`normalise_theme_id`), `stub-server/byos_server.py:96-105` (`parse_battery_mv`)
**Apply to:** every boundary this phase touches (POST form field, on-disk JSON value, response JSON value)
Never trust a value's type or membership implicitly — check explicitly (`isinstance(value, bool)`, `value in THEMES`) before it is used as a dict key or placed in a response body (ASVS V5, T-06-01-01).
