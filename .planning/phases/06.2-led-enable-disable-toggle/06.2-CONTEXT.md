# Phase 06.2: LED enable/disable toggle - Context

**Gathered:** 2026-08-28
**Status:** Ready for planning

<domain>
## Phase Boundary

This phase adds a companion-web-interface control that lets the user enable/disable the device's existing bring-up/debug LED remotely. The LED itself (firmware) and the wire protocol that carries the setting to the device are **already fully built** — this phase closes the one remaining gap: there is currently no way to change the setting away from its hardcoded value, because no store, no endpoint, and no web control exist yet.

</domain>

<decisions>
## Implementation Decisions

### Placement and default
- **D-01:** The toggle gets its **own dedicated section** on the config page, not folded into the existing theme/runway settings form — consistent with how `theme_fieldset()` and `runway_fieldset()` are already separate, independently-submittable sections in `companion/pages/config_page.py`.
- **D-02:** Defaults to **ON (enabled)** — matches the LED's current hardcoded always-on behavior, so existing behavior doesn't change for anyone until they explicitly opt out.

### Claude's Discretion
- Exact toggle copy/label text and whether it renders as a checkbox or a Yes/No radio pair — follow whichever existing `config_page.py` fieldset pattern reads most consistently; not a user-specified preference.
- How the LED field is named in `device_config.py`'s persisted JSON (e.g. `led_enabled`) — pick something consistent with the existing `theme`/`tracked_runway` field naming.

</decisions>

## Canonical References

**Downstream agents MUST read these before planning or implementing.**

### Firmware and wire protocol (already complete — do not re-implement)
- `firmware/main/led.c` / `firmware/main/led.h` — `fp_led_on()`/`fp_led_off()`, GPIO21 (XIAO's built-in User LED), active-low via Kconfig, strictly scoped to the active wake window
- `firmware/main/state_machine.c:64-65` — the only firmware consumer of the server's answer: `if (!disp.led_enabled) { fp_led_off(); }` — can only turn the LED off earlier, never force it on
- `firmware/main/api_client.h:48`, `firmware/main/api_client.c:310,346` — `led_enabled` bool already parsed from the `/display` JSON response; fail-open (missing/non-bool → enabled; only an explicit `false` disables)

### Server side (this phase's actual work)
- `stub-server/byos_server.py` (~line 234) — `GET /device/v1/display` handler **hardcodes** `"led_enabled": True`, with its own comment stating plainly there is no store/endpoint/web control behind it yet. **Despite the directory name, this is the real production device-facing server**, deployed via `deploy/skypane-byos.service` — a separate systemd unit/process from the companion app.
- `server/device_config.py` — the single source of truth for user-settable settings (currently `THEMES`, `RUNWAYS` registries feeding `theme`/`tracked_runway`). The LED field belongs here, following the same persisted-JSON pattern.
- `companion/pages/config_page.py` — `theme_fieldset()` (52-75) and `runway_fieldset()` (78-102) are the direct pattern to follow for a new LED fieldset + its `handle_post()` validation branch.
- `.planning/seeds/bring-up-debug-led-remote-toggle.md` — the original seed proposal: reuse the existing `sleep_s`-style pattern (server decides the value, device reads it on its next poll), and converge with CFG-03 (health status). Read this in full before planning.
- `REQUIREMENTS.md:89` — confirms the project's "no status LEDs" anti-feature exclusion explicitly does **not** cover this bring-up LED (it's scoped to a *permanently wall-visible* indicator; this LED is behind the frame, active only during the brief wake window).

<code_context>
## Existing Code Insights

### Reusable Assets
- `config_page.py`'s existing fieldset + `handle_post()` validation shape (render from a registry/current value, reject non-member values server-side) — the same shape fits a boolean toggle with minimal new plumbing.

### Established Patterns
- `device_config.py` registries are written by the companion UI and read by whichever server component needs them (`render.py`, `poll_loop.py` today). The LED field should follow the same "config.py owns the value" shape.

### Integration Points — flagged risk
- **Cross-process boundary:** `byos_server.py` (device-facing, `skypane-byos.service`) is a **separate running process** from the companion app (`companion/app.py`, `skypane-companion.service`) and from `poll_loop.py`. Today's registries (`theme`, `tracked_runway`) are read by `poll_loop.py`/`render.py`, not by `byos_server.py` — there is no confirmed existing precedent for `byos_server.py` reading `device_config.json`. **This needs the phase researcher to confirm exactly how (or whether) `byos_server.py` currently reads any shared config file**, since a naive implementation could set the value in the wrong process and have it silently never reach the device's `/display` response.

</code_context>
