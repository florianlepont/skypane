# Phase 06.2 Plan 02: Developer sign-off on the cross-process LED toggle and the real hardware LED Summary

**Both halves of the checkpoint are approved: the companion-saved `led_enabled` value crosses the real companion<->byos_server.py process boundary correctly (Part A, 6/6 sub-checks), and after investigating and resolving a genuine "still lit" false alarm, the developer confirmed the physical LED on deployed hardware behaves exactly as the firmware was designed to (Part B).**

## What This Plan Verified

This plan's single task (`06.2-02-01`, `checkpoint:human-verify`) is itself the entire plan, per its own `<verification>` gate — it produces no source changes, only a recorded verdict. `06.2-01` shipped the store/endpoint/web-control code; this plan's job was to catch a wiring mistake automated tests are structurally blind to (two separately-launched OS processes silently disagreeing about which `--state-dir` they share, per `06.2-RESEARCH.md` Pitfall 2), and separately, to get the real physical LED confirmed on hardware.

### Part A — cross-process toggle, local, no hardware

Verified by the orchestrating agent before the branch was merged. All 6 sub-checks passed:

1. Initial poll against a `--state-dir` with no `device_config.json` present -> `"led_enabled": true` — confirms D-02's default-enabled behavior on a fresh deployment.
2. The companion Config page renders a distinct "Bring-up LED" section: its own `<form action="/config-led">`, separate from the Theme/Runway form, checkbox reflecting current state, readable helper text — confirms D-01.
3. Unchecking the box and saving -> "Saved — will apply on the frame's next scheduled refresh." banner shown, checkbox stays unchecked after reload.
4. Polling `/display` immediately after -> `"led_enabled": false` — the value crossed from the companion process to the device-facing process correctly. This is the central risk this plan exists to catch.
5. Re-checking the box, saving, polling again -> back to `"led_enabled": true`.
6. Negative control: deleted `device_config.json` entirely, polled again -> `true`. This rules out a stale-read false positive and confirms genuine fail-open-to-enabled behavior rather than a coincidental leftover value from step 5.

All four required observed `/display` values (steps 6, 9, 10, 11 per the plan's acceptance criteria) are recorded above as `true`, `false`, `true`, `true` respectively, in that order.

### Merge and deploy (between Part A and Part B)

PR #16 (this branch — Phase 06.2 Wave 1 code plus all of 06.1-06.6's planning docs) was merged to `main` and auto-deployed to production via this project's CI/CD pipeline. `skypane-poll.service` and `skypane-companion.service` both restarted cleanly on the VPS, confirmed via a real poll cycle in the deploy log immediately after restart. This merge happened ahead of full phase verification specifically because Part B requires the new code to be live on the device's actual server.

### Part B — real physical hardware

The developer's own observation, in two rounds:

**Round 1 (false alarm, investigated and resolved):** The developer disabled the LED via the production companion UI, then reported the physical LED still appeared lit. The orchestrating agent read `firmware/main/led.c`, `firmware/main/app_main.c`, and `firmware/main/state_machine.c` in full to investigate. The firmware's actual design:

- `fp_led_on()` is called unconditionally as the literal first statement of `app_main()`, before WiFi/NVS even initialize — an intentional "device is alive" signal.
- `fp_led_off()` is called conditionally right after the `/display` poll response arrives, only if `led_enabled: false` — `state_machine.c`'s own comment documents this placement as deliberate, positioned before the download/blit ("the longest part of the wake") so a disabled LED is dark through that whole window.
- `fp_led_off()` is called unconditionally again right before deep sleep, regardless of the setting — a hard DEVICE-05 battery-life invariant, explicitly documented as "not conditioned on any server-supplied preference."

The consequence: the LED is *always* lit briefly during the WiFi-connect + poll window, in both the enabled and disabled states. A developer glancing at the frame only during that brief window — or checking before the device's first poll against the newly deployed code — would see the LED lit either way and could reasonably mistake that for "the toggle does nothing."

**No code changes were made in response to this report.** Investigation concluded the firmware logic was already correct as designed; the initial observation was a timing/expectation mismatch, not a defect. This is stated plainly here rather than silently dismissed, per the plan's own instruction: a real user report was investigated, root-caused, and resolved as "works as designed" with a concrete, traceable explanation.

**Round 2 (sign-off):** The developer re-observed with the corrected expectation — watching through a full wake cycle rather than a brief glance — and confirmed: *"ah si j'ai compris, donc ça marche"* (translation: "ah yes I understand now, so it works"). The toggle behaves as designed.

### Final verdict

**APPROVED.** Both Part A and Part B confirmed. No open issues carried forward.
