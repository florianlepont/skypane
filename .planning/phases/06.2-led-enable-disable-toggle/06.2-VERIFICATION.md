### Firmware Reasoning Sanity-Check (Independent Re-derivation)

The 06.2-02-SUMMARY.md "Round 1 false alarm" root-cause claim was independently re-checked against firmware source rather than taken at face value, per the task instructions:

- `firmware/main/app_main.c:108` — `fp_led_on()` is called unconditionally as the literal first statement of `app_main()`, confirmed by direct read (comment at lines 103-107 explains this is deliberate: a signal that must appear before NVS init, which can take seconds on the recovery path).
- `firmware/main/app_main.c:97` — `fp_led_off()` is called unconditionally in `enter_deep_sleep()`, the single noreturn exit every code path funnels through; comment explicitly states "not conditioned on any server-supplied preference" (DEVICE-05 battery invariant — a network-supplied value must never hold a pin high through deep sleep).
- `firmware/main/state_machine.c:64-65` — `if (!disp.led_enabled) { fp_led_off(); }` is the only conditional path, placed immediately after the `/display` response is parsed and before the (long) download/blit window.

This independently confirms the SUMMARY's technical claim: the LED is unconditionally lit during the WiFi-connect+poll window in both the enabled and disabled states, by firmware design — a developer glancing at the frame only during that brief window would see it lit regardless of the setting. The reasoning holds; this was a genuine timing/expectation mismatch, not a masked defect, and no code change was warranted.

- **WR-01** (`save_device_config()`'s unguarded read-modify-write race) — **partially related, not fully unrelated as characterized.** The underlying missing-lock defect is pre-existing (it predates this phase — `save_device_config()` has never held a lock, even under the single pre-existing `/config` route). However, the review's own text states this phase's new `/config-led` route is a **second concurrent caller** of the same unguarded function, which is accurate: `handle_led_post()` (this phase's own artifact) does call `device_config.save_device_config()`, and a near-simultaneous `/config` + `/config-led` submission could race and lose an update. This is a real, narrow, non-blocking gap in this phase's write path — flagged here rather than silently accepted, since the "all three are pre-existing/unrelated" framing understates WR-01's connection to this phase's new route. It does not block the phase goal: the truths above (toggle persists correctly under normal single-request use, verified by both automated harnesses and the human cross-process checkpoint) all hold. Note: no dedicated follow-up-task file was found under `.planning/todos/` tracking CR-01/WR-01/WR-02 at verification time — the "spawned follow-up task" reference in the phase orchestration note could not be independently located; this is a paperwork gap, not a functional one, and does not affect this phase's own goal achievement.
- **IN-01** (drift risk between `normalise_led_enabled()` and `read_led_enabled()`'s duplicated logic) — confirmed genuinely tied to a deliberate D-03 tradeoff already documented in VENDOR.md, correctly disposed as informational/no-action-required.

None of these findings — including WR-01 — invalidate any of the six Observable Truths above; they are quality/robustness notes on the surrounding concurrency model, not evidence the LED toggle fails to work.
