## Summary

This phase closes a wiring gap, not a design gap: firmware, the wire protocol field, and the persistence-registry pattern (`server/device_config.py`) all already exist and are proven (CFG-01/CFG-12 shipped the identical shape for `theme`/`tracked_runway`). The one genuinely new question this phase's CONTEXT.md flagged — how a value set in the companion web UI reaches `stub-server/byos_server.py`'s `GET /device/v1/display` handler, given that file is a separate OS process — is now fully answered by reading the actual deployment topology, not by inference.

**The flagged risk turns out to be smaller than the CONTEXT.md worried it was.** All three production services (`skypane-byos.service`, `skypane-companion.service`, `skypane-poll.service`) are started with the identical `--state-dir ${SKYPANE_STATE_DIR}` (`deploy/skypane-byos.service:24`, `deploy/skypane-companion.service:26`, `deploy/skypane-poll.service:19`) — all three already point at the same directory, `/opt/skypane/state`. `byos_server.py` already has an open, hardened (`ReadWritePaths=/opt/skypane/state`), file-level channel into that directory — it already reads `byos_state.json` (tokens) and writes `battery_state.json` there. It simply has never been taught to read `device_config.json`, the file `companion/pages/config_page.py`'s `handle_post()` already writes via `device_config.save_device_config()`. There is no new cross-process mechanism to invent — only a new *read* to add inside a mechanism (shared state directory + JSON files) that already exists and is already proven safe by the theme/runway and battery precedents.

**On D-03 ("never modify byos_server.py"):** the plain-language rule is not applied literally in this codebase — `stub-server/VENDOR.md` documents that the file has already received three deliberate local modifications since being vendored byte-for-byte (`--state-dir`, `--image-url-scheme`, and DEVICE-04's `X-Battery-Mv` validation/persistence), each scoped narrowly, each fully documented in VENDOR.md, none touching PROTOCOL.md's wire contract. D-03's real intent, read against this precedent, is "do not let this file organically drift from upstream / do not fold it into another service" — not "this file is a byte-for-byte freeze forever." A fourth, equally narrow modification (reading one boolean out of `device_config.json` inside the already-modified `/display` handler) is squarely inside the same established discipline, and should be recorded as VENDOR.md modification #4.

**Primary recommendation:** Add `led_enabled` as a third simple-boolean field to `server/device_config.py` (default `True`, matching firmware's own fail-open contract), add a matching fieldset + `handle_post()` branch to `companion/pages/config_page.py` (mirroring `theme_fieldset()`), and — inside `stub-server/byos_server.py`'s existing `/display` handler only — add a small, self-contained, stdlib-only, fail-open JSON read of `<state_dir>/device_config.json`'s `led_enabled` key (do NOT `import server.device_config` from `byos_server.py` — see Pitfall 1). Document the change as VENDOR.md modification #4 and update `stub-server/test_poll_cycle.py`'s hardcoded `led_enabled:true` assertion.

**Key distinction this diagram makes explicit:** `theme`/`tracked_runway` reach the device by being baked into `panel.bin`'s pixels (rendered once per poll cycle by `poll_loop.py`, then served as opaque bytes by `byos_server.py`). `led_enabled` is architecturally different — it is a **top-level JSON field in the `/display` response itself**, computed fresh on every device poll by `byos_server.py`'s own handler, completely independent of what `panel.bin` currently contains. ### Pattern 1: Shared-state-directory config, per-field fail-open normalisation
**What:** Every user-settable field in `device_config.json` is validated against an explicit, named rule (`normalise_theme_id()`, `normalise_runway_id()`, and now `normalise_led_enabled()`) that never raises and always returns a safe default on anything malformed, missing, or hostile.
**When to use:** For `led_enabled` specifically.
**Example:**
```python
# Source: server/device_config.py's existing normalise_theme_id()/normalise_runway_id() pattern
DEFAULT_LED_ENABLED = True  # D-02: matches the LED's current hardcoded always-on behaviour

def normalise_led_enabled(value):
    """Return `value` unchanged only when it is an actual bool - otherwise
    return DEFAULT_LED_ENABLED. Never raises. A JSON `true`/`false` decodes
    to a real Python bool, so this mirrors normalise_theme_id()'s "wrong
    type -> default" discipline without a membership test (there is no
    registry to check against for a boolean)."""
    if isinstance(value, bool):
        return value
    return DEFAULT_LED_ENABLED
```

### Pattern 2: Self-contained, fail-open, stdlib-only read inside byos_server.py
**What:** Because `byos_server.py` is a vendored, stdlib-only file that must not gain a dependency on `server.device_config`, the LED read is a small self-contained function living entirely inside `byos_server.py` itself — same style as `load_state()`'s own try/except degrade-to-default shape.
**When to use:** Inside the `do_GET` `/device/v1/display` branch, replacing the hardcoded `"led_enabled": True,` line.
**Example:**
```python
# Source: mirrors byos_server.py's own load_state()/parse_battery_mv() defensive-read style
def device_config_path(state_dir):
    return os.path.join(state_dir, "device_config.json")


def read_led_enabled(state_dir):
    """Best-effort read of the companion-set led_enabled flag from the
    SHARED device_config.json (written by companion/app.py's config page,
    server/device_config.py's save_device_config()). Missing file,
    unreadable file, malformed JSON, a non-dict document, or a non-bool
    value under the "led_enabled" key all degrade to True (matching
    firmware's own api_client.c fail-open contract: absent/non-bool ->
    enabled). Never raises. This is the ONLY place in byos_server.py that
    reads device_config.json - poll_loop.py's theme/tracked_runway reads
    are unrelated and untouched by this function.
    """
    try:
        with open(device_config_path(state_dir)) as fh:
            data = json.load(fh)
    except (OSError, ValueError):
        return True
    if not isinstance(data, dict):
        return True
    value = data.get("led_enabled")
    return value if isinstance(value, bool) else True
```
Then, in `do_GET`'s `/display` branch, replace the hardcoded literal:
```python
                "led_enabled": read_led_enabled(self.args.state_dir),
```

### Anti-Patterns to Avoid
- **Importing `server.device_config` from `byos_server.py`:** Breaks the file's stated "stdlib only" design, requires a `sys.path` bootstrap this file has never had, and couples a vendored/do-not-drift file to actively-changing project internals. Use the self-contained inline read instead (Pattern 2).
- **Having `poll_loop.py` write `led_enabled` into `panel.bin` or into `poll_state.json`:** `led_enabled` is a response-JSON-level field, not a pixel or a detection-pipeline concern. Routing it through `poll_loop.py` would add an unnecessary hop and a second, redundant read path for no benefit — `byos_server.py` already has direct file access to the same `state_dir`.
- **A registry (`LED_STATES = {...}`) for a plain boolean:** Adds indirection with no payoff — see Alternatives Considered.
- **Treating D-03 as a literal byte-for-byte freeze:** `stub-server/VENDOR.md` already documents three real modifications since vendoring; a plan that refuses to touch `byos_server.py` at all would misread the actual project convention and leave `led_enabled` permanently hardcoded, defeating this phase's entire purpose.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Atomic JSON persistence | A new write helper | `device_config.save_device_config()`'s existing tmp-write-then-`os.replace()` pattern, extended with a third parameter | Already proven, already tested, already matches every other state file in this repo |
| Server-side validation of a submitted form field | A generic form-validation library | The existing explicit-membership-test-then-reject-whole-submission pattern in `config_page.handle_post()` | This project's established discipline (06-CONTEXT.md D-06/D-07): a write of an unrecognised value is a client error reported back, never silently coerced — for a boolean, "unrecognised" simply means "not exactly `\"on\"`/`\"true\"`/whatever HTML checkbox convention is chosen" |
| Cross-process config delivery | A message queue, a socket, an HTTP callback between the two services | The already-existing shared `state_dir` + JSON file pattern | D-03 already rejected merging the services; a lightweight file read is strictly simpler than adding IPC, and the shared directory + hardened `ReadWritePaths` already exists in the systemd units for both processes |

**Key insight:** Every piece of infrastructure this phase needs (shared state directory, atomic JSON writer, fail-open reader, server-side form validation, flash-message plumbing) already exists in this codebase for the theme/runway precedent. This phase is close to pure repetition of an established pattern, not new architecture — the main design decision is *where* the new read happens (byos_server.py, not poll_loop.py) and *how* it stays within D-03's spirit (inline stdlib code, not a cross-package import).

## Common Pitfalls

### Pitfall 1: Importing `server.device_config` into `byos_server.py`
**What goes wrong:** The vendored file gains a dependency on actively-changing project code, and its own "Stdlib only" docstring claim becomes false.
**Why it happens:** `server.device_config.load_device_config()` already exists and does exactly the right thing for the companion/poll_loop side — it's tempting to reuse it verbatim.
**How to avoid:** Write a small, self-contained, duplicate-but-isolated read function directly inside `byos_server.py` (Pattern 2). A few lines of duplication is the correct tradeoff here, matching VENDOR.md's existing minimal-diff, self-contained-modification discipline.
**Warning signs:** Any `import server` or `sys.path.insert` appearing in `byos_server.py` that wasn't there before.

### Pitfall 2: Forgetting the two services' default `--state-dir` values differ outside of production
**What goes wrong:** A developer running `byos_server.py` locally without an explicit `--state-dir` gets the script's own directory (`stub-server/`) as the default, while `companion/app.py`'s default is `server/poll_loop.DEFAULT_STATE_DIR` (`server/state/`) — two different directories. A local manual test that saves a theme via the companion UI and expects `byos_server.py` to see it will silently fail to observe the change unless both are pointed at the same `--state-dir` explicitly.
**Why it happens:** Each script's CLI default was chosen independently and predates this phase; only the *deployed* systemd units happen to agree (`${SKYPANE_STATE_DIR}` for all three).
**How to avoid:** Any new local/manual verification step in the plan must explicitly pass the same `--state-dir` to both processes. The fail-open default (`True`) means a mismatched directory just silently behaves as "LED always on" rather than crashing — which is the safe direction, but can look like "nothing happened" during manual testing if not accounted for.
**Warning signs:** A manual test toggles the setting in the companion UI, polls the device (or curls `/device/v1/display`), and the response never changes — check both processes' actual `--state-dir` argument before assuming a code bug.

### Pitfall 3: Test-harness state-dir isolation masking a real read failure
**What goes wrong:** `stub-server/test_poll_cycle.py` launches `byos_server.py` with its own tempdir `--state-dir` (see its own header docstring: it isolates itself from the long-running dev instance). Since no `device_config.json` is ever written there, the existing hardcoded-`led_enabled:true` assertion will continue to pass even if the new read function has a bug that always falls through to the `True` default — a broken "read the actual value" path could ship undetected if the only test coverage is the pre-existing assertion.
**Why it happens:** The fail-open default and "no config file present" scenario produce the same observable result (`True`) as "broken read code that never actually parses the file."
**How to avoid:** Add a NEW test case to `test_poll_cycle.py` that explicitly writes a `device_config.json` with `{"led_enabled": false}` into the harness's own `--state-dir` before polling `/display`, and asserts the response reflects `false`. This is the only check that actually exercises the read path rather than only the fallback path.
**Warning signs:** Test coverage for this feature that only ever asserts the `True` case.

### Pitfall 4: Treating the D-03 "vendored, do-not-modify" language as absolute
**What goes wrong:** A plan concludes `byos_server.py` genuinely cannot be touched at all, and either (a) abandons the feature, or (b) tries to route `led_enabled` through some indirect mechanism (e.g. having `poll_loop.py` somehow inject it into `panel.bin`'s bytes, which is architecturally wrong per the diagram above — `led_enabled` is a JSON field, not a pixel).
**Why it happens:** 06-CONTEXT.md's D-03 text reads as an unconditional rule ("never modifying the vendored `stub-server/byos_server.py`") when quoted in isolation.
**How to avoid:** Cross-reference `stub-server/VENDOR.md`, which documents this file already received three real local modifications post-vendoring, each narrowly scoped and fully written up. The correct read of D-03 is "this file is not folded into another service, and any change is deliberate/documented/minimal" — not "zero further bytes, ever." This phase's change is modification #4 in that same ledger.
**Warning signs:** A plan that proposes not touching `byos_server.py` at all, or that proposes a workaround more complex than a ~10-line addition to an already-modified handler.

## Open Questions

1. **Checkbox "absent means unchecked" vs. this project's established "absent means leave unchanged" convention for POST /config**
   - What we know: `config_page.handle_post()`'s existing contract for `theme`/`tracked_runway` is "a field absent from `form` means leave unchanged" (both fields are radio-button groups always rendered inside the same `<form>`, so in practice they're always present on any real submission from this page). An HTML checkbox, by contrast, is omitted from its form's POST body entirely when unchecked — there is no way to distinguish "user didn't touch this form" from "user explicitly unchecked the box" using presence/absence alone if the checkbox lives in the SAME `<form>` as fields that use the "absent = unchanged" convention.
   - What's unclear: D-01 says the LED toggle gets its **own dedicated, independently-submittable section** — if it truly posts to its own `<form action="...">` route (distinct from the Theme/Runway form's `POST /config`), this ambiguity disappears entirely (that form's only field is the checkbox, so "absent" unambiguously means "submitted unchecked", not "some other field wasn't touched"). If instead it's folded into the same `POST /config` form purely visually (still one `<form>` tag), the ambiguity is real and must be resolved (e.g. a hidden `<input type="hidden" name="led_enabled_present" value="1">` sentinel, a common HTML pattern for this exact problem).
   - Recommendation: Re-read D-01 literally — "independently-submittable sections" strongly implies a SEPARATE `<form>`/POST action per section (this is also how `poll_trigger_section()` already works: its own `<form method="post" action="/poll-now">`, distinct from the Theme/Runway form's `<form method="post" action="/config">`). If the planner follows this precedent and gives the LED toggle its own `<form method="post" action="/config-led">` (or similar), the checkbox-absence problem never arises. Flag this explicitly in the plan rather than assuming.
