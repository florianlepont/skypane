<objective>

</objective>

  <how-to-verify>
**Part A — cross-process, local, no hardware (required).**

Run both processes against ONE shared directory. This is the whole point of the checkpoint: their CLI defaults differ, so the `--state-dir` value below must be identical in both commands.

1. Pick a scratch directory and export it, e.g. `export SKYPANE_CHECK_DIR=$(mktemp -d)`.
2. Generate a panel image for the stub server to serve: run `stub-server/make_test_panel.py` with `--pattern palette` and `--out "$SKYPANE_CHECK_DIR/panel.bin"`.
3. In terminal 1, start the device-facing server with `--state-dir "$SKYPANE_CHECK_DIR"`, `--image "$SKYPANE_CHECK_DIR/panel.bin"`, and a free `--port`.
4. In terminal 2, start the companion app with the SAME `--state-dir "$SKYPANE_CHECK_DIR"` and a different `--port`, with the companion password environment variable set.
5. Enroll a device token: `POST /device/v1/setup` against the stub server with a JSON body carrying a `mac` and an `hw_rev`. Keep the returned `device_token`.
6. Poll `GET /device/v1/display` with `Authorization: Bearer <device_token>`. **Expected: `"led_enabled": true`** — no config file exists yet, so this confirms D-02's default (this is the state a fresh deployment is in).
7. Open the companion app in a browser, log in, and go to Config. **Expected:** a distinct "Bring-up LED" section, visually separate from the Theme/Runway form and from the Poll section, with its checkbox already checked and its helper text readable.
8. Uncheck the box and submit that section. **Expected:** a redirect back to Config, the "Saved — will apply on the frame's next scheduled refresh." banner, and the checkbox now rendering unchecked after the page reloads.
9. Poll `GET /device/v1/display` again with the same bearer token. **Expected: `"led_enabled": false`.** This is the assertion that matters — it proves the value crossed from one OS process to the other.
10. Re-check the box, submit, poll once more. **Expected: back to `true`.**
11. Negative control (proves you were not just reading a stale default): `rm "$SKYPANE_CHECK_DIR/device_config.json"` after step 9's `false`, poll again, and confirm it returns to `true`.

If step 9 shows `true` when you expect `false`, check both processes' actual `--state-dir` arguments before assuming a code bug — a mismatch fails open to enabled and produces exactly this symptom.

**Part B — real hardware (required to be *answered*, not required to be *done now*).**

If the change is deployed to the VPS and the frame is powered and enrolled:
1. Disable the LED in the companion UI.
2. Wait for the frame's next scheduled wake (or trigger a poll and wait out the sleep interval).
3. Watch the board's built-in User LED (GPIO21, behind the frame) during the wake window. **Expected: it stays dark for the whole wake window.** It is lit only during that brief window — you have to be watching when the device wakes.
4. Re-enable, wait for the next wake, confirm it lights again.

If the change is not deployed, or the frame is not currently available, say so — that is a legitimate answer. This project already has precedent for carrying a hardware-only confirmation forward (DEVICE-05's discharge run). It will be recorded in the summary as an explicit carried-forward item with its reason, never as a silent pass.

**Cleanup:** stop both processes and `rm -rf "$SKYPANE_CHECK_DIR"`.
  </how-to-verify>
