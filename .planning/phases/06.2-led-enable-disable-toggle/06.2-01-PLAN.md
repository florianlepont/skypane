<objective>
Close the last gap in the bring-up LED remote toggle: give the setting a store, a web control, and a real read on the device-facing wire.

Firmware and the wire protocol are already complete and are NOT touched — `firmware/main/led.c`, `firmware/main/state_machine.c` (`if (!disp.led_enabled) { fp_led_off(); }`) and `firmware/main/api_client.c` (fail-open bool parse) already implement the read-and-obey half. Today `stub-server/byos_server.py` hardcodes the field, with its own comment saying there is no store, endpoint, or web control behind it.

This plan adds all three, following the exact `theme`/`tracked_runway` precedent already shipped in the same files:
- **D-01:** the toggle gets its own dedicated, independently-submittable section on the Config page — not folded into the existing Theme/Runway `<form action="/config">`.
- **D-02:** the default is enabled, so nothing changes for anyone until they explicitly opt out.
- **D-03** (inherited from `06-CONTEXT.md`): the vendored `byos_server.py` change stays minimal, self-contained, stdlib-only, and is recorded in `stub-server/VENDOR.md` as local modification #4 — the same discipline its three prior modifications already follow.

Purpose: without this, the LED can only be changed by physically reflashing the board.
Output: a persisted `led_enabled` field, a Config-page section that writes it, a `/display` handler that reads it, and 16 new automated checks across three existing harnesses.
</objective>
