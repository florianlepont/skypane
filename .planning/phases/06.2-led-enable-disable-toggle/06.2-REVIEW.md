# Phase 06.2: Code Review Report

**Reviewed:** 2026-08-28T13:05:27Z
**Depth:** standard
**Files Reviewed:** 8
**Status:** issues_found

## Summary

Reviewed the LED enable/disable toggle feature: `server/device_config.py`'s
`led_enabled` field (validation, persistence, defaults), the companion
`/config-led` page and route (`companion/pages/config_page.py`,
`companion/app.py`), the vendored `byos_server.py`'s new
`read_led_enabled()` read path, and the three associated test harnesses.

The LED-specific code itself (`normalise_led_enabled()`,
`led_fieldset()`/`led_section()`, `handle_led_post()`,
`read_led_enabled()`) is solid: strict `isinstance(x, bool)` typing,
fail-closed on write / fail-open on read exactly as documented, atomic
tmp-write-then-`os.replace()` persistence, and no injection surface
(validated by the SQL-placeholder-only test in
`test_config_history.py`). No hardcoded secrets, no `eval`/`exec`, no
empty catch blocks.

The findings below are concurrency/robustness defects in the
surrounding `companion/app.py` code that the LED feature's own new
`/config-led` route shares (`save_device_config()`'s read-modify-write
is now invoked from two independent POST routes instead of one), plus
one pre-existing bug in the "Trigger Poll Now" cooldown gate that
directly contradicts its own documented guarantee. None of these are
new regressions introduced by this phase's diff in isolation, but they
are live in the reviewed files and materially affect the reliability
of the config-save path this phase extends.

## Critical Issues

### CR-01: Poll-trigger cooldown can be bypassed by concurrent requests — mark-after-work TOCTOU

**File:** `companion/app.py:478-494`
**Issue:** `poll_cooldown_remaining()`'s docstring (line 130-136) explicitly
promises: "Server-global and persisted in `history.db`'s meta table
... so a second browser tab cannot bypass it." The implementation does
not deliver that guarantee: `_handle_poll_now()` checks
`poll_cooldown_remaining()`, then calls the (potentially slow —
network calls to AeroDataBox/PRIM) `poll_loop.run_once()`, and only
**after** that call succeeds does it call `mark_poll_triggered()` to
record the trigger time.

```python
def _handle_poll_now(self):
    state_dir = self.args.state_dir
    remaining = poll_cooldown_remaining(state_dir)
    if remaining > 0:
        return self.redirect(...)
    try:
        poll_loop.run_once(state_dir=state_dir, geofence=self.args.geofence)
    except Exception:
        return self.redirect(...)
    mark_poll_triggered(state_dir)   # <-- only recorded AFTER the work completes
    return self.redirect(...)
```

`companion/app.py` runs on `ThreadingHTTPServer` (line 587), so two
concurrent `POST /poll-now` requests (a double-click, a second browser
tab, or a retried request on a slow connection) both read
`remaining == 0` before either has finished, and both proceed to call
`poll_loop.run_once()` concurrently. This defeats the documented
purpose of the cooldown (a double-click guard per D-17) and risks two
concurrent `run_once()` invocations racing on `poll_state.json` — the
exact "two processes read-modify-writing the same JSON file" hazard
`server/device_config.py`'s own module docstring calls out as
Pitfall 5, except here it's two threads of the same process instead of
two processes. It also burns AeroDataBox API quota unnecessarily
(project constraints: $5/mo tier, 1 req/s, 6,000 units/mo).

**Fix:** Mark the trigger time before doing the work, closing the race
window to the (fast, local) sqlite round trip instead of the full
`run_once()` duration:
```python
def _handle_poll_now(self):
    state_dir = self.args.state_dir
    remaining = poll_cooldown_remaining(state_dir)
    if remaining > 0:
        return self.redirect(
            "%s?flash=%s" % (CONFIG_ROUTE, quote(FLASH_KEY_POLL_COOLDOWN)))
    mark_poll_triggered(state_dir)  # mark first: closes the TOCTOU window
    try:
        poll_loop.run_once(state_dir=state_dir, geofence=self.args.geofence)
    except Exception:
        return self.redirect(
            "%s?flash=%s" % (CONFIG_ROUTE, quote(FLASH_KEY_POLL_FAILED)))
    return self.redirect(
        "%s?flash=%s" % (CONFIG_ROUTE, quote(FLASH_KEY_POLL_TRIGGERED)))
```
This still leaves a small window between the `get_meta` read and the
`set_meta` write inside `poll_cooldown_remaining()`/
`mark_poll_triggered()`, so for a fully airtight fix, guard the
check-and-mark pair with a single `threading.Lock()` (or a single
SQL transaction doing a conditional `UPDATE ... WHERE` compare-and-set)
so the read and the write are atomic with respect to other threads.

## Warnings

### WR-01: `save_device_config()` has an unguarded read-modify-write race under concurrent requests

**File:** `server/device_config.py:167-216`
**Issue:** `save_device_config()` reads the current on-disk config
(`current = load_device_config(state_dir)`), merges in the caller's
non-`None` fields, and writes the merged result — with no lock. This
phase adds a second independent POST route
(`companion/app.py`'s `/config-led`, calling
`config_page.handle_led_post()`) that calls this same function
concurrently with the pre-existing `/config` route
(`config_page.handle_post()`), on a `ThreadingHTTPServer`. Two
concurrent saves — e.g. a user submits "Save Settings" (theme/runway)
and "Save LED Setting" in close succession, or the same form
double-submits — can race: both handlers read the same `current`
snapshot, and whichever writes last silently discards the other's
change (a classic lost update). This is the same class of hazard the
module's own docstring (lines 6-13) says was the deliberate reason
`device_config.json` was split out from `poll_state.json` in the first
place — but the fix (a separate file) does not protect against two
threads of the *same* process racing on that file.

**Fix:** Serialize writes with a module-level lock:
```python
import threading

_SAVE_LOCK = threading.Lock()

def save_device_config(state_dir, theme=None, tracked_runway=None, led_enabled=None):
    if theme is not None and theme not in THEMES:
        raise ValueError(...)
    if tracked_runway is not None and tracked_runway not in RUNWAYS:
        raise ValueError(...)
    if led_enabled is not None and not isinstance(led_enabled, bool):
        raise ValueError(...)

    with _SAVE_LOCK:
        current = load_device_config(state_dir)
        new_config = {...}
        os.makedirs(state_dir, exist_ok=True)
        path = device_config_path(state_dir)
        tmp = path + ".tmp"
        try:
            with open(tmp, "w") as fh:
                json.dump(new_config, fh, indent=1)
            os.replace(tmp, path)
        except Exception:
            ...
            raise
```
A `threading.Lock` is sufficient since this is a single-process
`ThreadingHTTPServer` (it would not help if the companion service were
ever run with multiple worker processes — a file lock, e.g.
`fcntl.flock`, would be needed then).

### WR-02: Poll-trigger failure is silently swallowed — no diagnostic ever reaches the logs the user is told to check

**File:** `companion/app.py:484-491`
**Issue:**
```python
try:
    poll_loop.run_once(state_dir=state_dir, geofence=self.args.geofence)
except Exception:
    return self.redirect(
        "%s?flash=%s" % (CONFIG_ROUTE, quote(FLASH_KEY_POLL_FAILED)))
```
The bare `except Exception:` discards the exception entirely — no
`print`, no `traceback.print_exc()`, nothing. Yet the corresponding
flash message (`FLASH_MESSAGES[FLASH_KEY_POLL_FAILED]`, line 100-102)
tells the user: "Poll trigger failed — please try again. If this keeps
happening, **check the companion service logs**." Those logs will
contain nothing about why the poll failed, making this class of bug
undiagnosable from the documented remediation path. Compare with
`main()` (line 573-577), which does log a startup failure to stderr —
this handler is the outlier.

**Fix:**
```python
import traceback
...
try:
    poll_loop.run_once(state_dir=state_dir, geofence=self.args.geofence)
except Exception:
    traceback.print_exc()
    return self.redirect(
        "%s?flash=%s" % (CONFIG_ROUTE, quote(FLASH_KEY_POLL_FAILED)))
```

## Info

### IN-01: `read_led_enabled()` reimplements `normalise_led_enabled()`'s validation logic independently — drift risk

**File:** `stub-server/byos_server.py:85-107`
**Issue:** `stub-server/VENDOR.md` (lines 115-123) documents this as a
deliberate choice to keep the vendored file stdlib-only and decoupled
from project internals. That tradeoff is reasonable, but it means the
"a bool, else default" contract now exists in two independently
maintained places — `server/device_config.py`'s
`normalise_led_enabled()` and this file's `read_led_enabled()`. If the
canonical registry-style validation in `device_config.py` ever changes
(e.g. the module's own comment at line 131-136 floats a future
`LED_STATES` registry "mirroring THEMES/RUNWAYS"), this shadow copy
will not be updated automatically and could silently diverge from the
companion app's write-side contract.
**Fix:** No change required now given the stated stdlib-only
constraint, but consider adding a small cross-check in
`stub-server/test_poll_cycle.py` or `server/test_config_history.py`
that runs the same table of inputs through both
`byos_server.read_led_enabled()`'s inline logic and
`device_config.normalise_led_enabled()` and asserts identical outputs,
so a future divergence fails a test instead of shipping silently.
