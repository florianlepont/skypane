<objective>
The developer's words: *"Change pictures ne s'affiche pas quand je scroll ce qui n'est
pas dingue d'un point de vue UX."*

Investigated and confirmed **as coded, by design**: the carousel's dots are decorative
per-theme swatches carrying no position state, and the live preview `<img>` only ever
changes on an actual chip click or keyboard-select. Scrolling the strip does nothing.

**The product decision is already made** — AskUserQuestion, 2026-09-15, developer's own
choice: *"Aperçu suit le scroll (recommandé)."* While scrolling or swiping, the preview
follows whichever chip is centered. It does not select it.

**That distinction is the whole plan.** There is exactly one clean separation point in
the existing script and PATTERNS.md located it: `applyPreviewSrc(src)` is the only thing
that writes the preview's `src`, and it is called from two places — `showUsage()` and the
delegated `change` listener that reads `data-preview-src` off the CHECKED radio's parent
label. The new scroll behaviour reuses `applyPreviewSrc` as its sink and **must never**
call `input.checked = true` or dispatch a `change` event, either of which would also fire
`showUsage`/persist a selection and turn a preview into a commit.

**27-07's `strip_id` parameter exists precisely to stop carousels sharing state.** Any new
per-strip state — an `IntersectionObserver`, a scroll handler, a cached centered index —
must be built once per strip inside the same kind of loop the pager wiring already uses
(`card.querySelectorAll("[" + PAGER_ATTR + "]")`), never as one shared observer keyed by
a hardcoded id.

**No IntersectionObserver exists anywhere in this static JS tree today** (PATTERNS.md
confirmed 0 hits). This plan introduces the mechanism, which is why the check that proves
it must drive real scroll across several intermediate positions rather than trusting a
listener's existence.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| browser script → the live preview `<img>` | a scroll-driven code path now writes an image source |
| browser script → form state | the new path is adjacent to controls that persist a setting, and must not reach them |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-28-05-A | Tampering | a scroll-driven path writing a persisted setting | mitigate | the new path calls `applyPreviewSrc()` only; the forbidden-operations list is a comment at the call site and M-C proves the not-selection clauses catch a violation |
| T-28-05-B | Information Disclosure | an image source from an untrusted origin reaching the preview | mitigate | the src is always a server-rendered `data-preview-src` already in the DOM; `img-src 'self' data:` blocks blob: and third-party origins, and the acceptance criteria pin zero `createObjectURL`/`blob:` occurrences |
| T-28-05-C | Denial of Service | a scroll handler firing per frame on a touch device could jank a phone | mitigate | the trigger is `IntersectionObserver`-backed where available and the decision is a cheap nearest-centre comparison over the chips already in the strip; a strip in a collapsed panel is skipped entirely |
| T-28-05-D | Tampering | one strip's tracker overwriting another's preview (the 27-07 hazard) | mitigate | one tracker per strip built in a loop, no hardcoded ids, and a cross-instance isolation clause mutation-tested by M-D |
| T-28-05-SC | Tampering | npm/pip/cargo installs | n/a | zero packages installed; no build step, no bundler, no dependency, no new script file |
</threat_model>
