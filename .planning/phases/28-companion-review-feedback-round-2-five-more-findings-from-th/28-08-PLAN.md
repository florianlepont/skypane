<objective>
**Phase 27 removed the settings save bar. The developer wants it back, and they were
asked twice.**

The reversal is not a bug report, and it must not be planned as one. The auto-save
mechanism 27-04 shipped **worked correctly the whole time** — the developer captured a
real Safari Network tab showing `POST /settings` → **204**, every field present, the value
genuinely persisted after reload. The only real defect was that nothing ever visibly
confirmed it. Having seen that evidence, the developer rejected the auto-save **model**,
not just its missing feedback: *"Mais ce n'était pas le comportement d'enregistrement
qu'on a choisi. Je veux garder la pop up qui apparait et qui propose d'enregistrer."* And
when asked directly, with their own original "je veux aucun bouton" complaint quoted back
at them: *"Oui, avec les boutons Enregistrer/Annuler comme avant."*

So this plan restores the pre-Phase-27 dirty save bar: a bar that appears when a settings
field changes, names which section(s) changed, and offers real **Enregistrer** /
**Annuler** actions over a genuine native form POST.

**The one structural idea that makes CFG-78 possible.** Phase 27 never deleted the native
submit. CFG-64's own AST-level proof (27-03) pins `STATIC_SAVE_FALLBACK_ATTR` to exactly
one bare-`Name` reference inside `render()`'s single, non-nested `return` — it is emitted
unconditionally on every scope, and it is currently hidden purely by
`.js [data-static-save-fallback] { display: none; }`. **That button becomes the bar's
visible Save.** Not a second button beside it; the same element, relocated into the bar's
markup, with `form="settings-form"` preserving native submission from outside the form.
One save affordance, two rendering conditions, provably the same element.

**The visibility polarity INVERTS, and this is the plan's most important non-obvious
decision.** The old bar was server-rendered `hidden` and un-hidden by script, because a
no-JS visitor still had a separate always-visible bottom Save button to fall back to.
There is no second button any more. So the bar must render **visible** by default — that
IS the no-JS floor now — and `dirty-state.js` hides it at init once it has proven itself
live, then reveals it whenever `countDifferences() > 0`. Get this backwards and a
scripts-blocked visitor has no way to save settings at all, which is precisely the hole
CFG-64 exists to keep shut.

Purpose: give the developer back the save model they chose, without weakening the floor
CFG-64 built underneath it.
Output: a working dirty bar; one save affordance; every fetch-era artifact of the settings
form's auto-save removed; five falsified comment blocks superseded in writing.
</objective>
