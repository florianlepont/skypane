<objective>
The phase's closing plan, and the LAST of the four restoration plans (28-08 → 28-10 →
28-11 → 28-09). Three jobs, in this order: prove the consolidation, prove the path CFG-74
named before it was superseded, and write the record.

**Prove the consolidation (CFG-78).** 28-08 relocated the native submit into the bar and
deleted the `.js`-hide rule. The claim "exactly one save affordance on the settings pages"
is now true by construction — but "by construction" is what 27-06 said about the title
form, and it was wrong. So it gets an executable contract, shaped so it cannot drift:
resolve every submit-shaped control's own `.form` property in a live browser and require
exactly one whose form is `settings-form`. That excludes Calendar's
connect/replace/disconnect, Airlines' "Enregistrer le nom", the three `role="switch"`
instant toggles, the per-flight rules add/delete, the notifications test and the quick-LED
form automatically, because each genuinely belongs to a different form — no hand-maintained
allow-list to rot.

**Prove the runway path.** This was the developer's ORIGINAL, narrower report before
everything else happened — *"Quand je fais un changement de paramètre (comme la piste) je
ne vois pas le bouton enregistrer apparaître"* — and it is the one clause of the superseded
CFG-74 that carries forward with its value intact. The runway radios live OUTSIDE the
settings form and reach it only through a `form="settings-form"` attribute; a form element
never receives a `change` event from a control that is merely `form=`-associated with it,
which is exactly the B1 defect `dirty-state.js`'s document-level delegation exists to
handle. That path deserves the same pass/fail contract every natively-nested control meets,
and it has never had one. Now it is proven against the restored bar's real POST, end to
end, to disk.

**Write the record, against the code.** The Phase 28 coverage ledger, the ROADMAP entry,
the design-system skill's now-false "Settings auto-save" standing paragraph — and the
per-requirement traceability table, which currently stops dead at CFG-71 and is missing
every one of this phase's own requirements.

**What this plan must NOT do.** CFG-74 is not ticked and is not rounded up. Nothing here
was built for it, because it was superseded before implementation — and the reason is worth
writing down accurately rather than glossing. The requirement's own text named "a
regression from Phase 27's removal of the manual save button" as its root cause, and with
that button restored, the resilience machinery it specified has no fetch left to wrap. The
real Safari Network-tab data the developer captured while testing the silent auto-save (a
genuine 204 success, the value persisted, with zero visible confirmation) is what led
directly to the reversal, and it stands as CFG-74's own evidence for why
resilience-around-a-silent-mechanism was the wrong fix for the symptom it correctly
diagnosed. Say that; do not say "fixed", and do not say "not met".
</objective>
