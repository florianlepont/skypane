<objective>
The developer's words: *"Le bug est aussi que le curseur se déplace au milieu de
l'horloge."*

**This is not a maths bug and the investigation already proved it.** The angle and
pointer arithmetic is correct in every scenario tried. `.quiet-dial__handle` is a real
`<button>`, and the app's global `button:active { transform: translateY(1px); }` rule
(specificity 0,0,1,1) beats the handle's own single-class positioning rule (0,0,1,0)
for as long as the press lasts. Because CSS `transform` **replaces wholesale and never
composes**, winning that collision does not add a 1px nudge to the polar position — it
deletes the polar position, including the `translate(-50%, -50%)` centring term. The
base `button` rule's `transition: transform .15s ease` then animates the handle sliding
through the chord to the dial's centre and back.

Measured live, on a plain press-and-hold with no drag at all: **78px from centre
(correct, on the ring) at press → 14-16px (the centre) by 90-150ms → back to 78px about
200ms after release.**

That recovery is why this survived a phase of checks: **the position is correct at
rest.** Any check written as before/after passes on the broken code. The check this plan
adds therefore SAMPLES the resolved position repeatedly while the button is held — which
is this project's own standing "assert relationships, not just endpoints" contract
applied to a time axis instead of a surface axis.

**Out of scope, explicitly:** 27-02's cross-surface agreement model (arc/handles/caption
as functions of the PAIR) is verified still correct and is not touched. Bug A — the
readout's HH:MM format and live duration — is 28-03's, in different files.
</objective>
