  <action>
Edit `server/plane/enrich.py` only. Three edits, all additive; no signature change, no new function, no change to what counts as a resolvable route.

**1. `_parse_route()` — read and return the field.** Read it with `flightroute.get("callsign_iata")`, from the top level of the `flightroute` object rather than from `airline`/`origin`/`destination`, because that is where adsbdb actually puts it. Append it to the returned dict as a sixth key named exactly `callsign_iata` — the same name the API uses and the same name plan 08-04's renderer will read, so no translation layer exists to drift.

**Do NOT add it to the required-non-empty validation loop.** That loop exists to reject a half-resolved route the UI has no state to render, and its five members are exactly the fields that make a route usable at all. A route with a real airline, real cities and no IATA identifier is still fully usable — it is precisely CONTEXT.md's tier-2 case in plan 08-04's content ladder. Making the new field required would turn currently-resolvable flights into misses, blanking route text on the panel for every carrier adsbdb has no IATA callsign for. That is the single most damaging way this task can go wrong.

Because it is optional, normalise it defensively on the way out rather than trusting it: a value that is not a non-empty string after stripping must become `None` in the returned dict, never an empty string, never a non-string object, never a bare-whitespace string. This is the same never-trust-the-payload discipline the surrounding function already applies to the five required fields; the difference is that a bad value here degrades one field to `None` instead of failing the whole route. Do not apply `to_sentence_case_city()` or any other transform — a flight identifier is not a city name.

Extend the function's docstring to say which fields are required and which one is optional, and to record in one sentence why this one is optional. The docstring currently implies every parsed field is mandatory; after this edit that is no longer true and a future reader must not have to infer it from the loop.

**2. `_route_from_entry()` — read it back out of the cache.** Add a sixth line reading `callsign_iata` from the entry with the identical `entry.get(...)` shape every sibling line already uses. Without this, a route that survives a process restart and comes back through the persisted cache loses the field while a freshly-fetched one keeps it — an intermittent, restart-dependent difference in what the panel displays, which is exactly the failure mode CONTEXT.md's Integration Points bullet warns about.

**3. `airline_only_route()` — keep the shape parity it already promises.** Add `callsign_iata` as a sixth key with value `None`, alongside the four existing `None` fields. This is not optional polish and it is not scope creep: that function's own docstring states it produces the same key set `_parse_route()` produces, and `server/test_enrich.py` has a currently-passing check that derives its expected key set from a real `_parse_route()` result and compares it against this function's output. Adding the field to `_parse_route()` without adding it here breaks that check. Behaviourally the change is inert — a consumer calling `.get("callsign_iata")` gets `None` either way — but the documented invariant stays true. Update the docstring's "same four keys" wording to match the new count.

**`lookup_route()` needs no edit at all.** Its cache write is a generic `cache_entry = dict(route)` copy, so it carries whatever keys `_parse_route()` produced. Its return path goes through `apply_airline_name_correction()`, which either returns the route object unchanged or returns a shallow `dict(route)` copy with one key replaced — also generic. Read both to confirm this holds before concluding it, then leave them alone; an unnecessary edit here is a chance to break the correction seam for no benefit.

**Scope boundary.** This plan touches the enrichment layer only. Do not edit `server/plane/render.py` — the consumer side, including the ladder that decides when the new field is actually displayed, is plan 08-04's work and depends on this one. Do not add the field to any companion page: `08-CONTEXT.md`'s Phase Boundary keeps the companion web app out of this phase entirely.
  </action>
