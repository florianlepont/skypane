## Why this plan is a gate and not a formality

Every single decision this phase implements was made by the developer looking at
PNGs on a monitor. `hardware/BRINGUP-LOG.md` records two prior occasions where
exactly that kind of judgment was overturned by real Spectra 6 ink mid-session:
the Blue/Green hue, which had to be darkened twice and then dithered; and the
text backing plate itself, which was *added* in Phase 7 precisely because real
ink revealed a legibility problem the monitor had not shown.

This phase removes that backing plate. It is entirely possible that real glass
says the same thing it said in Phase 7 and that PT Serif Bold alone is not
enough. That outcome is not a failure of this plan — it is the reason the plan
exists. What would be a failure is closing the phase on preview PNGs.

<objective>
Put every visual and textual change this phase made in front of the real deployed Spectra 6 panel, capture the developer's verdict in their own words, apply whatever bounded correction the glass calls for, and record the findings alongside the panel's other physical observations.

</objective>

<expectation_note id="N-08-06-01">
**A forced render stays on the glass until the next real detection.** The poll loop holds the last panel through detection gaps by design. Every forcing step below therefore ends the same way: restart the poll timer. If the session ends with that timer stopped, the frame sits on a synthetic test image indefinitely and looks like it is working. That is why the timer's final state and a real post-restart poll cycle are both acceptance criteria rather than instructions buried in a step.

**Each observation costs a full panel refresh**, roughly 31.5 seconds on this hardware, and the device wakes on its own poll cycle. Batch the forced renders in the order given rather than tweaking and re-looking one change at a time.

**Confirm the deployed paths before forcing anything.** This plan writes the expected values — application root, service user, interpreter and state path — but the operator should confirm them against the deploy directory and the environment file on the host rather than trusting a document. Plan 08-05 corrected the render module's own printed reminder to name the real unit; if anything in this plan still disagrees with the host, the host wins and the discrepancy goes in the summary.
</expectation_note>

<in_session_correction_scope>
This session may apply bounded corrections directly, in the Phase 7 precedent, rather than deferring everything to a future phase. What counts as bounded here:

- A point-size adjustment on any text role, respecting that role's existing `fit_text_size()` floor.
- A geometry-constant nudge for bezel clearance or spacing.
- An adjustment to the previous card's optical offset value, if a real illustration on real glass shows the 20px value landing wrong. Plan 08-05's spot-check may already have named a candidate outlier — start there.
- A palette RGB tweak for one of the newly-exercised inks, if a background hue reads wrong on real ink the way Blue and Green did in Phase 7.

What is **not** bounded, and requires an explicit, recorded decision from the developer in the session before it is touched:

- Reinstating any form of backing plate, outline or drop shadow. D-05 removed it deliberately and the spike record shows outline and shadow were both built, both read as legible, and were both rejected on visual grounds. If Bold alone proves insufficient on glass, that is a genuine reopening of a locked decision — surface it, get the developer's explicit instruction, and record their words verbatim. Do not quietly restore a rejected technique because the glass looked bad.
- Changing which default theme ships, removing a theme, or changing a theme's ink pairing.
- Changing the content ladder's tier definitions or reintroducing the raw callsign at any tier.
- Changing which edge the previous card's alignment measures. The measurement is exact; only the offset added on top of it is adjustable.
- A different font family, a new illustration asset, or a materially different composition. Those need a new phase.

Every correction applied in session must be re-rendered and re-confirmed on the glass before its step is considered closed, and the full test suite must pass again before the session ends.
</in_session_correction_scope>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Operator laptop -> live cloud VPS over SSH | A production host is modified by hand: code is deployed, a systemd timer is stopped, and the file the device fetches is overwritten with synthetic content. |
