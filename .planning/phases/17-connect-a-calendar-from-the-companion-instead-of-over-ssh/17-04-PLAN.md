<objective>
Close the loop: the settings write path becomes its own handler, a saved calendar syncs immediately, and the page says what happened.

Purpose: this is the only moment at which a wrong URL can be reported usefully. Without it a mistyped feed is indistinguishable from a correct one for up to thirty minutes — which is precisely the window in which the operator doubts their copy and paste and starts changing things that were never wrong. The immediate fetch is also where the phase's remaining leak risk lives: the failure message has to name a cause without ever re-rendering the URL, and network and name-resolution exception strings routinely embed the full request URL, so the message is built from a classified result code and from nothing else.

Two corrections this plan inherits rather than repeats. The refresh function's throttle bypass is genuinely new work, not a call-site option — the parameter did not exist until plan 17-02 added it, and a call that omits it silently does nothing. And the rejected-URL outcome constant is dead code with zero call sites: the fetch collapses a refused URL and a genuine network failure into the same result, so there is one honest generic failure message here, not a per-cause copy deck.

Output: four flash keys with their copy and their announcement roles, one new request handler, one new special case in the flash resolver, one new page-context key, and the corrected comment where the old one asserted a process boundary that never existed.
</objective>

2. Call the page module's write function and keep its returned key.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| a failing upstream calendar host → the operator's rendered page | The error material a failed fetch produces is attacker-influenced and, in the ordinary case, contains the full request URL. |
| the authenticated settings write path → an outbound network request | A form submission now causes the server to make a request to a host the submitter chose. |
| a save-triggered refresh → a concurrently running poll cycle's own refresh | Both do a read-modify-write of the same registry file. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-17-FLASH | Information Disclosure | the outcome message and the redirect that carries it | high | mitigate | The message is selected from four fixed server-side strings by an opaque key, and the only runtime value interpolated into any of them is a count read from disk at render time. No error is caught and no error's text is read anywhere on this path — the refresh function is contractually never-raising, so a handler here would be dead code whose only live consequence is putting the request URL back into a message, since that is what name-resolution and connection error strings contain. Proved by Task 3's check 4, which drives a stub whose raised error embeds the full URL and asserts five distinct needles are absent from the location header, the banner and the whole served body; and structurally by Task 2's verify, which fails if any error handler appears in the method at all. |
| T-17-AMP | Denial of Service | the save-triggered outbound fetch | medium | mitigate | Bounded on four independent axes rather than rate-limited on one: the write path is behind the existing session gate, so an unauthenticated party cannot reach it at all; the non-blocking lock acquire serialises it against itself and against the poll cycle, so concurrent saves cannot multiply into concurrent fetches; the existing address-safety gate refuses private and loopback destinations, so it cannot be aimed inward; and the existing per-request timeout and response-size cap bound what a single fetch costs. The residual — one bounded outbound request per authenticated save — is accepted deliberately, because it is the entire mechanism by which a mistyped URL becomes reportable, and a cooldown on top of it would reintroduce the silent-no-op failure the phase exists to remove. The manual poll trigger's own cooldown is deliberately not borrowed: it guards a full render cycle, and sharing it would let a settings save block a real poll. |
| T-17-RACE | Tampering | the calendar registry, under a concurrent save and poll | medium | mitigate | The save-triggered refresh takes the same lock the manual poll trigger takes, not a second one. The module's own write lock guards only the write and not the interval between the read and the write, so two separate locks would permit exactly the interleaving that loses one of the two updates. On contention the save gets an honest deferred answer rather than proceeding, and the lock is released in a `finally` covering every path out so one failure cannot wedge the trigger. Proved by Task 3's checks 7 and 8. |

That claim was false when it was written. The manual poll trigger runs the poll cycle in-process, and that cycle refreshes the calendar, which reads the URL — so the companion process has read the value on a live path since Phase 16 shipped. But the phase's threat model must not rest on a process boundary: all three units run as the same user and load the same environment file, and no such boundary has ever existed. The honest property, which this phase preserves and the closing audit should verify, is that the value has no rendering, logging or flashing call site.
