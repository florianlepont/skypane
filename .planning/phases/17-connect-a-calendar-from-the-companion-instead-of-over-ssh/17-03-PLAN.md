<objective>
Make the input reachable: a write-only feed-URL field and a disconnect checkbox inside the existing Settings Calendar group, a fourth status state for a stored link whose permissions have drifted, and the POST-side resolution that turns three possible form shapes into carry-forward, set, or clear.

Purpose: this is the phase's entire reason for existing. Phase 16 built everything behind this input and then put the input in an environment variable edited over SSH; the developer's own framing of the feature was "connect your calendar", which describes something you do in a browser. The acceptance test is one sentence: pasting a URL and pressing save connects a calendar, and the page says so.

The single design trap is the disconnect signal. The field is write-only, so it renders empty on every page load regardless of state — which means an unrelated settings save submits it empty. Treating an empty field as "disconnect" would therefore disconnect the calendar every time anyone changed a theme. The project already solved this exact problem once, for the arrivals-theme override, and the solution is a checkbox: an unchecked checkbox is absent from the submission entirely, and that absence is the only signal able to distinguish "clear" from "leave alone", because `None` already means "not supplied, carry forward" for every field on this write path. The direction here is deliberately the safe one — default does nothing — which is the mirror image of the arrivals checkbox's polarity.

Output: five new copy constants, four new resolution constants, one new pure resolver function, a widened group renderer, and the POST branch that writes the secret.
</objective>

  <action>
Add four module-level resolution constants — carry-forward, set, clear and invalid — as plain strings that are never rendered and never travel in a URL, and one pure function that maps a submitted form to exactly one of them. Give the function a docstring stating that it is the single definition of this resolution and that both `handle_post()` and the request handler plan 17-04 adds call it, so the two can never drift into disagreeing about what a given submission meant.

Its logic, in this order:

1. Read both fields. Strip the URL when it is a string; treat any non-string as empty.
2. If the checkbox is present with any value other than the expected constant, resolve invalid. A crafted value is a hostile request shape, not a user mistake, and gets the same treatment every other checkbox on this handler already gives it.
3. If the checkbox is present and the stripped URL is non-empty, resolve invalid. This is the contradiction: the operator has asked to disconnect and to connect in the same submission, and there is no defensible guess. Reject rather than pick one.
4. If the checkbox is present, resolve clear.
5. If the stripped URL is empty, resolve carry-forward. This is the branch the whole checkbox exists to make possible, and its comment should say so: the field is write-only, so it renders empty on every page load in every state, which means an unrelated settings save always submits it empty — treating that as a disconnect would disconnect the calendar on every theme change.
6. If the stripped URL exceeds the maximum length, resolve invalid.
7. Otherwise resolve set.

In `handle_post()`, call the resolver once alongside the existing membership gates and return the generic save-failed flash when it resolves invalid, before anything is written. This keeps the all-or-nothing contract intact: a bad value in any field aborts before the persistence call, never persisting the valid remainder.

After the existing device-config persistence call has succeeded, and only then, act on the resolution: on clear, call the secret writer with the sentinel; on set, call it with the stripped URL; on carry-forward, do not call it at all. The last of those is not an optimisation — every successful call to that writer erases the fetched flights, so calling it on an untouched field would wipe the calendar's flights on every unrelated save. Map a false return from either call to the generic save-failed flash.

Add a comment at that call site explaining the ordering choice: the device-config write goes first because it is the pre-existing path and must stay behaviourally unchanged for every form that touches no calendar field, and the secret write is the additive step layered after it. Note honestly that this leaves a narrow partial-write window if the second call fails after the first succeeded, that the operator sees the generic failure and can retry, and that the alternative ordering would perturb the existing path for every save in the application to close a window that only opens when the state directory is already failing.

Extend `handle_post()`'s docstring with a paragraph on the new fields, written in the register of the paragraphs already there for the arrivals checkbox and the calendar theme select — including, explicitly, that this checkbox's polarity is inverted relative to the arrivals one and why.
