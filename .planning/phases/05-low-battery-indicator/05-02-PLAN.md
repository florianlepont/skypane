## Phase Goal

**As a** SkyPane owner with the frame on my wall, **I want to** see a battery icon appear
in the poster's bottom-left corner when the pack is running low, **so that** I can plug it
in before the display goes dark instead of discovering a blank frame.

*(Sourced from `REQUIREMENTS.md`'s DEVICE-04 and `ROADMAP.md`'s Phase 5 Success Criterion 2,
which state the same capability verbatim. `ROADMAP.md`'s `**Goal:**` line for Phase 5 covers
both DEVICE-04 and DEVICE-05 in prose rather than user-story form — see this plan's return
notes.)*

**MVP vertical-slice ordering.** Each task below ends with something a person can observe
that they could not observe after the previous one: Task 1 → a real preview PNG showing the
icon; Task 2 → a real device poll's reading landing in `battery_state.json`; Task 3 → the
served `panel.bin` actually carrying the icon. The "failing test first" step lives *inside*
each task (each has a `<behavior>` block that is written as new `check()` calls before the
implementation): this repo's harnesses are single-file scripts gated on an
`EXPECTED_CHECK_COUNT` constant, so adding a check ahead of its implementation makes the
whole harness — and CI — red. That *is* the RED step, performed as the task's first commit.

## Resolved open items from 05-UI-SPEC.md

`05-UI-SPEC.md` flagged two items for the planner. Both are resolved here; neither is left
to the executor's discretion.

**1. Empty-state ink colour — CONFIRMED as `IDX_BLACK`, and the icon renders in all three
states.** A battery reading is a device-health fact, entirely independent of whether an
aircraft happens to be over Runway 3 right now. The empty state is in fact the *most* likely
state for a frame sitting on a wall overnight — precisely when a low pack gets discovered —
so suppressing the icon there would make DEVICE-04 fail in its single most common real-world
case. `IDX_WHITE` would be invisible against the empty state's flat White background; the
empty state's own established ink for both its heading and its body copy is `IDX_BLACK`, so
the icon inherits its state's ink exactly the way it does under `STATE_INK` for
departing/arriving. No new palette index enters the panel. Task 1 additionally introduces a
named `EMPTY_INK` constant so "each state's own already-established ink" is structurally
true rather than a comment.

**2. Terminal-nub height — CHANGED from 14px to 16px.** `05-UI-SPEC.md` asked whether 14
should become 16 for grid alignment. It should. Every other dimension of this glyph already
lands on the project's existing spacing scale — body width 64 = `SPACE_LG`, body height
32 = `SPACE_MD`, nub width 8 = `SPACE_XS` — leaving 14 as the single unexplained magic
number in the set. 16 is `SPACE_SM`, is exactly half the body height, and keeps the nub
centred on integer coordinates (`nub_top = 1504 + (32 - 16) / 2 = 1512`,
`nub_bottom = 1528`, 8px of clearance above and below). The icon's **total bounding box is
unchanged at `(64, 1504, 136, 1536)`**, so `05-UI-SPEC.md`'s collision analysis against the
frame and the previous-flight card, and its match to the session sketch's ~72×32px reference
size, both survive untouched. The superseded `nub = (128, 1513, 136, 1527)` literal that
appears as an illustrative snippet in `05-RESEARCH.md` and `05-PATTERNS.md` is replaced by
`(128, 1512, 136, 1528)`; this plan is authoritative over those two example blocks.
