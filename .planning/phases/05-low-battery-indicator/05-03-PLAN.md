<objective>
Close DEVICE-04 on real hardware: give the device a real battery-voltage measurement and
put the resulting icon on real glass.

Purpose: plan 05-02 built the entire server path, but the device still reports the
compiled-in unknown sentinel that `api_client.c`'s own head comment names this phase as the
reason for. Until that value is real, the icon can never fire from a real pack, and
DEVICE-04's success criterion ("User can see a low-battery indicator on the frame") is
unmet. D-03 puts that hardware bring-up in scope now rather than leaving the server
plumbing to run against a fabricated value, and D-02 fixes what is measured: raw
millivolts, never a derived percentage.

This is a firmware-and-configuration change only. **No component is added to the board and
nothing is soldered.** The EE02 driver board this device is built on — not the bare XIAO
module — already carries a factory-populated 2:1 battery-voltage divider on `A0`/GPIO1,
gated by an enable line on `D5`/GPIO6, documented on Seeed's own EE0x driver-board cookbook
as applying to the EE02/EE03/EE04/EE05 family (`05-RESEARCH.md` Summary, Pitfall 1,
Pitfall 2, Assumptions A1/A3). The firmware's whole job is to enable that existing circuit,
sample it through ESP-IDF 5.3's current `esp_adc` component, halve-out the divider, and
report the result.

The one residual uncertainty is cheap and safe to settle: the cookbook's applicability
banner names EE02 explicitly, but its worked example says "EE04". `05-RESEARCH.md` holds
that at MEDIUM-HIGH rather than HIGH confidence for exactly that reason. Task 3 settles it
by flashing and looking at the number — if the sense pin reports roughly half a plausible
pack voltage, the circuit is there; if it reports zero or noise, it is not. No tool, no
purchase, and no risk either way.

Output: a host-tested pure conversion function, an ESP-IDF ADC driver module, a real
telemetry value on the wire, and a recorded bring-up log entry with the icon confirmed on
the 13.3" Spectra 6 panel.
</objective>

## Phase Goal

**As a** SkyPane owner with the frame on my wall, **I want to** see a battery icon appear
in the poster's bottom-left corner when the pack is running low, **so that** I can plug it
in before the display goes dark instead of discovering a blank frame.

Same user story as plan 05-02 — this plan supplies the half of it that only real hardware
can: the measurement itself.

**MVP vertical-slice ordering.** Task 1 → the conversion arithmetic is provably correct on
the host with no hardware. Task 2 → a flashed device sends a real, non-sentinel millivolt
value that reaches the live server's `battery_state.json`. Task 3 → the developer sees the
icon on the real panel, with the reported value confirmed plausible. Each task ends with
something observable that the previous one could not show.

## What this plan explicitly does NOT do

Recorded because an earlier draft of this plan got it wrong, and the correction is the
reason the plan was regenerated:

- **No soldering.** Not on any pin, not at any step.
- **No external resistors, no hand-built voltage divider, no hookup wire.** The divider is
  already on the EE02 board.
- **No `hardware/BOM.md` change.** There is no new part to record. `<verification>` below
  asserts that file is untouched rather than leaving it to inspection.
- **No pre-work continuity or pin-isolation measurement.** That step only existed to make
  soldering safe. Nothing is soldered, so it has no purpose here. GPIO10 — the "ADC_BAT"
  label on the *bare* XIAO module — is irrelevant to this board stack and stays claimed by
  the panel's DC line (`05-RESEARCH.md` Pitfall 1, Assumption A2).

    and `#define FP_BATTERY_SETTLE_MS 10` with a comment that the divider needs a moment to
    settle after its enable line goes high before the sample is meaningful.

    Hold a file-scope `static int s_cached_mv = -1;` sentinel meaning "not yet read this
    wake" — deep sleep clears RAM, so this static gives exactly one ADC read per wake with no
    change to `app_main.c`, which is what the deep-sleep architecture requires
    (`05-RESEARCH.md`'s "reading the ADC continuously" anti-pattern). On any later call in the
    same wake, return the cached value without touching the peripheral.

    On the first call, in this order: configure `PIN_BATT_EN` as an output through a
    `gpio_config_t` with `.mode = GPIO_MODE_OUTPUT` and `.pin_bit_mask = 1ULL << PIN_BATT_EN`
    (do not use the abort-on-error macro `epd13in3e.c` uses for its own panel pins — a
    battery-telemetry failure must degrade to the unknown sentinel, never take the device
    down); drive it high; `vTaskDelay(pdMS_TO_TICKS(FP_BATTERY_SETTLE_MS))`; resolve the
    configured sense GPIO to a unit and channel with
    `adc_oneshot_io_to_channel(PIN_BATT_ADC, ...)` rather than hardcoding a channel number, so
    the Kconfig GPIO stays the single source of truth and cannot drift from a separately
    configured channel; if that call fails, or if the resolved unit is not `ADC_UNIT_1`, log a
    warning and take the failure path. Otherwise `adc_oneshot_new_unit()` on `ADC_UNIT_1`,
    `adc_oneshot_config_channel()` with `.atten = ADC_ATTEN_DB_12` and
    `.bitwidth = ADC_BITWIDTH_DEFAULT`, `adc_cali_create_scheme_curve_fitting()` with the
    matching unit/atten/bitwidth, then `adc_oneshot_get_calibrated_result()` into an `int`
    named `pin_mv`. Convert with `battery_math_apply_divider()` and cache the result.

    Every path out of that sequence — success and each error return alike — must first
    `adc_cali_delete_scheme_curve_fitting()` if the calibration handle was created,
    `adc_oneshot_del_unit()` if the unit was created, and drive `PIN_BATT_EN` back low. A
    leaked ADC unit or a divider left enabled on a device that wakes thousands of times is a
    real drain, not a style point (T-05-03-03). Cache zero on any failure so the failed read
    is not retried later in the same wake.

    Emit exactly one `ESP_LOGI(TAG, ...)` line reporting both numbers — the converted pack
    millivolts and the raw `pin_mv` the ADC actually measured — in the shape
    `battery mv=<pack> pin_mv=<pin>`. Both numbers matter: Task 3's whole confirmation is
    "does the sense pin read roughly half a plausible pack voltage", and a line carrying only
    the converted value cannot distinguish a working circuit from a coincidence. This line
    sits outside `firmware/VENDOR.md`'s frozen five-line Log Line Contract and must not
    imitate any of its tokens; it must also not contain the telemetry header's own name, so
    that `hardware/logtools.py`'s `check-battery` — which reads captured stub-server stdout,
    not device console — cannot be confused by a device-console capture being passed to it by
    mistake.

    Use `ADC_ATTEN_DB_12`, not its deprecated pre-5.1 alias, and use only the `esp_adc`
    component's `adc_oneshot`/`adc_cali` surface. The pre-5.0 legacy ADC driver header and its
    raw-read plus calibration-characterisation entry points still compile under IDF 5.3.1 with
    warnings and dominate publicly available tutorials, which is precisely the stale-API trap
    this project's pinned toolchain exists to avoid (`05-RESEARCH.md` Pitfall 3).

    Add the ADC driver translation unit to `firmware/main/CMakeLists.txt`'s `SRCS` and
    `"esp_adc"` to its `REQUIRES`. No dependency is fetched: `esp_adc` ships inside the
    already-pinned `espressif/idf:v5.3.1` image `build.sh` uses, and `driver` (for GPIO) is
    already in that `REQUIRES` list.

    the bottom of the include block (alongside `nvs_schema.h`, `secrets.h`, `wifi.h`) and
    rewrite the battery line of `telemetry_headers()` to follow the `X-Rssi` idiom two lines
    above it: reuse the existing `char buf[16]`, `snprintf` the value of `fp_battery_mv()`
    with `%u` after an explicit `(unsigned)` cast, then `esp_http_client_set_header(http,
    "X-Battery-Mv", buf)`. Reusing `buf` is safe because `esp_http_client_set_header()` copies
    the value it is given. Delete the compiled-in string literal the call currently passes as
    that header's value. Rewrite the head comment above `telemetry_headers()`: the two
    sentences explaining that no ADC driver is wired up and that the header therefore reports

    retained as the unknown sentinel when the read fails. Leave the other three headers, and
    the "all four sent unconditionally" contract, exactly as they are.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| battery pack (analog) → EE02 onboard divider → ESP32-S3 ADC1 pad | Raw analog voltage crosses into the MCU. The board's own factory divider is what keeps a 4.2 V full-charge cell inside the ADC's safe input range; the firmware only enables and samples it. |
| `battery.c` (peripheral read) → `battery_math.c` (arithmetic) → `X-Battery-Mv` header | A hardware-derived integer becomes a value the server acts on. |
| Kconfig / board profile → the two GPIOs the firmware newly drives | A configuration value decides which physical pins this module asserts, on a board where eleven pins are already owned by the panel and the keys. |
| firmware build → pinned `espressif/idf:v5.3.1` toolchain | The only dependency surface this plan touches. |
