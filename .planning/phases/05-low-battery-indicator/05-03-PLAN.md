<objective>
Close DEVICE-04 on real hardware: give the device a real battery-voltage measurement and
put the resulting icon on real glass.

Purpose: plan 05-02 built the entire server path, but the device still sends
`X-Battery-Mv: "0"` — the compiled-in unknown sentinel `api_client.c`'s own comment names
this phase as the reason for. Until that value is real, the icon can never fire from a real
pack, and DEVICE-04's success criterion ("User can see a low-battery indicator on the
frame") is unmet. D-03 puts that hardware bring-up in scope now rather than leaving the
server plumbing to run against a fabricated value, and D-02 fixes what is measured: raw
millivolts, never a derived percentage. This plan identifies a genuinely free ADC1-capable GPIO on the XIAO
ESP32-S3 Plus + EE02 stack, builds the external voltage divider the board does not ship
with, reads it through ESP-IDF 5.3's current `esp_adc` component, and verifies the reported
value against a real multimeter at two states of charge.

Output: a host-tested pure conversion function, an ESP-IDF ADC driver module, a real
telemetry value on the wire, and a recorded bring-up log entry with the icon confirmed on
the 13.3" Spectra 6 panel.
</objective>

## Phase Goal

**As a** SkyPane owner with the frame on my wall, **I want to** see a battery icon appear
in the poster's bottom-left corner when the pack is running low, **so that** I can plug it
in before the display goes dark instead of discovering a blank frame.

Same user story as plan 05-02 — this plan supplies the half of it that only real hardware
can: the measurement itself.

**MVP vertical-slice ordering.** Task 1 → the conversion arithmetic is provably correct on
the host with no hardware. Task 2 → a flashed device sends a real, non-sentinel millivolt
value that reaches the live server's `battery_state.json`. Task 3 → the developer sees the
icon on the real panel, with the reported value cross-checked against a multimeter. Each
task ends with something observable that the previous one could not show.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| battery pack (analog) → ESP32-S3 ADC1 pad | Raw analog voltage crosses into the MCU. Unbuffered, and above the ADC's safe input range without an external divider. |
| `battery.c` (peripheral read) → `battery_math.c` (arithmetic) → `X-Battery-Mv` header | A hardware-derived integer becomes a value the server acts on. |
| firmware build → pinned `espressif/idf:v5.3.1` toolchain | The only dependency surface this plan touches. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-05-03-01 | Tampering | `firmware/main/battery_math.c` — `battery_math_apply_divider()` | high | mitigate | An unsigned multiply that wraps produces an implausibly *small* millivolt value, which reads as a critically low battery and would spuriously arm the warning (or, on the clear side, wedge it). The function saturates to `UINT32_MAX` above `UINT32_MAX / FP_BATTERY_DIVIDER_NUM` instead of wrapping; the exact boundary and both saturating cases are pinned by three of Task 1's nine host assertions. Defence in depth: plan 05-02's `parse_battery_mv()` rejects anything above 10000 mV server-side. |
| T-05-03-02 | Denial of Service | `firmware/sdkconfig.ee02.defaults` — `CONFIG_FP_PIN_BATTERY_ADC` | high | mitigate | Soldering a divider onto a pin the panel already drives corrupts the e-paper data/command line and bricks the display path — the pin the module's schematic labels for battery sense is exactly the one this board profile assigns to that line (`05-RESEARCH.md` Pitfall 1). Three layers: the Kconfig `range 1 10` excludes ADC unit 2 entirely; Task 2's acceptance criteria run a machine check that the configured value appears in none of the eleven `CONFIG_FP_PIN_EPD_*` / `CONFIG_FP_PIN_KEY*` assignments; and Task 3's blocking human checkpoint requires a continuity measurement on the real unpowered board before any solder is applied. |
| T-05-03-03 | Denial of Service | `firmware/main/battery.c` — ADC unit and calibration handle lifecycle | medium | mitigate | A leaked ADC unit, or a re-read on every header call, extends awake time on a device whose entire architecture exists to minimise it. One read per wake via the `s_cached_mv` file-scope sentinel (deep sleep clears it, so the cache cannot go stale across wakes); `adc_oneshot_del_unit()` and the cali-scheme delete on every path including each error return; a failed read caches the `0` unknown sentinel rather than retrying. |
| T-05-03-04 | Spoofing / Tampering | `X-Battery-Mv` in transit | low | accept | The header travels over Caddy-terminated TLS to a bearer-authenticated endpoint. An attacker able to forge it could pin a frame into a permanent warning — cosmetic only, no data loss, no unlock, no state corruption beyond one boolean that self-corrects on the next genuine reading. Accepted at ASVS L1. |
