<objective>
Prove Phase 5's battery-measurement success criterion and requirement DEVICE-05 on real hardware: the device completes many consecutive wake, poll and sleep cycles on battery power alone, and that run yields a measured mAh-per-cycle figure that a wake-interval and battery-life plan can actually be built on.

The method is fixed by **D-07** and is deliberately the simple one. Charge the pack fully, connect it, take the USB cable out, let the device run its normal cycle untouched, check on it every day, and note how long it lasts. Divide the pack's rated capacity by the number of cycles it completed. The user rejected an inline USB power meter explicitly, self-identifying as having very limited hardware experience, and nothing in this plan reintroduces extra instrumentation. The one thing this plan adds beyond D-07's arithmetic is a check that the run was *valid* - because the two ways a multi-day unattended run silently produces a wrong number are cheap to detect and expensive to discover afterwards.

Those two ways define the whole shape of this plan. The first is phantom power: a USB cable left plugged in for the console means the board is not on the battery at all, and the run would report a magnificent battery life for a device that was on mains the entire time. That is why the console is unavailable during this run by construction - the console is USB Serial/JTAG on this board, and USB is also the power rail - and why the observation channel is the server's own stdout instead. The second, amended by quick task 260827-vq3 (2026-08-27): the peer is now `skypane-byos.service` on the production VPS, always on and restarted by systemd, rather than a stub run by hand on a laptop - so the residual interruption risks are the frame losing home Wi-Fi or internet, the service or host going down, and journald rotating entries out of the window being converted. Both failures are visible in the server log, so a checker written before the battery is connected can reject them, in the same discipline plan 01-07 used for the backoff curve.

This is the first plan in the phase permitted to connect the battery. Plan 01-06 confirmed the connector pitch and polarity against the board and deliberately did not plug it in; plan 01-07 required it stay disconnected so that pulling USB would genuinely cut power to the RTC domain. Both named this plan as the one that finally does it, and 01-01's threat register records reversed polarity as the single unrecoverable mistake in the phase - so the first act here is to check the polarity once more against what the BOM recorded.

A note on a forward reference for anyone reading this plan alone: `stub-server/README.md`, written by 01-02, names plan 01-07 as the consumer of the server's telemetry stdout. Plan 01-07 consumed that stream for one baseline wake and recorded that the sustained battery consumption belongs here. Plan 01-05 names this plan as the one that measures through that channel. Both readings are correct, both plans read the same stream, and nothing in 01-02 needs changing.

This plan is inherently long-running: it spans days of real elapsed time, and no amount of structuring makes that not so. It is not autonomous, it cannot be completed in one sitting, and its tasks are written on that assumption - the durable state lives in a committed log and a check-in table on disk, not in any agent's context.

Purpose: DEVICE-05, measured rather than estimated, by D-07's stated method.
Output: A timestamped server-side record of every wake across the run, a post-mortem console capture carrying the closing boot counter, and a write-up carrying the mAh-per-cycle figure and the limits of what it covers.
</objective>

  <action>
    Extend `hardware/logtools.py` with a `check-battery` subcommand. Add no import beyond the six the file already allows - `argparse`, `datetime`, `os`, `re`, `subprocess`, `sys`. Integer division and plain arithmetic cover everything needed here, and 01-07's AST import scan is re-run unchanged as a regression check, so an added module fails the task rather than merely being noticed.

    Determine the millivolt line format from `hardware/logs/backoff-baseline-server.log` before writing the parser. That file is a real capture of the vendored server's stdout with the host timestamp prefix already applied, and the telemetry print is upstream code this project deliberately did not reformat. Search each line for the `X-Battery-Mv` token and take the adjacent integer, tolerating whatever separator and surrounding text upstream actually emits. Do not restructure the server's output to suit the parser - the parser exists to read what the server already prints.

    The subcommand takes one or more server log paths, read and concatenated in the order given, plus these options: `--capacity-mah` as a required integer, `--interval-s` defaulting to 300, `--min-days` defaulting to 1, `--min-coverage` defaulting to 0.95, `--max-gap-intervals` defaulting to 3, `--min-mv-drop` defaulting to 100, `--cutoff-mv` defaulting to 3400, `--boot-start` and `--boot-end` as optional integers, `--expect-depleted` as a boolean, and `--status` as a boolean.

    Parse every line with a regular-expression search rather than a match, since each line carries the bracketed ISO timestamp the `stamp` filter prepends. From each line that carries a battery millivolt reading, extract the timestamp and the millivolt integer. That pair is one observed poll, and therefore one observed wake - the device polls exactly once per wake, which is what makes the server log a wake counter as well as a voltage log.

    Compute and hold: the first and last timestamps, the span in seconds and in days, the observed poll count, the nominal poll count as the span in seconds divided by the interval, the coverage as observed over nominal, the largest gap between consecutive polls expressed in whole intervals, the mean millivolts across the first tenth of the samples and across the last tenth, the drop between those two means, and the last observed millivolt value. Use windowed means rather than single first and last readings, because a single instantaneous reading taken while the radio is transmitting is noisy enough to mislead on its own.

    In gated mode, implement these checks, each printing one line reading either PASS with the check name or FAIL with the check name and the concrete reason, with a final summary line of the form `battery: N/N checks pass` and exit code 0 only when every check passed:

    First, the logs carry timestamps and at least two polls. A log with no timestamps means the stamp filter was left out of the capture pipeline, which destroys the elapsed-time evidence the whole method rests on, and that must be an explicit failure rather than a silent skip.

    Second, the span is at least `--min-days`. A five-thousand-milliamp-hour pack that empties inside a day is not a battery-life result, it is a device that never actually slept, and reporting it as the former would be worse than reporting nothing.

    Third, coverage is at least `--min-coverage`. This is the sleeping-host gate. If the laptop slept, or its DHCP lease moved, or the stub server died, the device stopped polling and backed off exponentially - and the cycles it then performed were nothing like the cycles under test.

    Fourth, no single gap between consecutive polls exceeds `--max-gap-intervals`. Coverage alone can hide a large hole inside a long run; this catches the hole directly.

    Fifth, the drop between the opening and closing millivolt means is at least `--min-mv-drop`. This is the phantom-power gate. A pack that is being held at its charge voltage by a USB cable someone forgot to unplug does not fall, and every other check in this list would pass happily while the device sat on mains.

    Sixth, with `--expect-depleted`, the last observed millivolt value is at or below `--cutoff-mv`, which distinguishes a run that ended because the pack emptied from one that ended because somebody stopped the server.

    Seventh, when both `--boot-start` and `--boot-end` are supplied, report the device's own boot-counter delta alongside the observed poll count and fail when the delta exceeds the observed poll count by more than the reciprocal of `--min-coverage`. A device that woke far more often than it polled was waking and failing, not waking and polling, and its cycles were not the cycles being measured.

    Then compute and print, in both modes, the derived figures: the span in days; the observed, nominal and device-reported cycle counts; the coverage; the milliamp-hours per day as the capacity divided by the span in days; and the milliamp-hours per cycle as the capacity divided by the cycle count, preferring the device boot-counter delta when supplied, falling back to the observed poll count, and falling back again to the nominal count. Print which of the three was used. Print the opening and closing millivolt means and the drop.

    Finally print a projection band for candidate wake intervals of 300, 900 and 3600 seconds. Give two bounds per interval, not a point estimate. The upper bound assumes all drain is per-wake, so life scales linearly with the interval and equals the observed span scaled by the ratio of the candidate interval to the run's interval. The lower bound assumes all drain is standing leakage, so life does not change with the interval and equals the observed span. Print the band as a range with the smaller number first. A single-cadence depletion run genuinely cannot separate the energy of a wake from the leakage during the sleep between wakes - one measurement, two unknowns - and printing a bare linear projection would be a claim the data does not support.

    In `--status` mode, print the same derived figures plus the age of the most recent poll in seconds, skip the PASS and FAIL gating entirely, and exit 0 regardless. This is the daily check-in command, and it must never fail a developer's routine check just because the run has not finished yet.

    Then write three fixture logs under `hardware/fixtures/`, in the exact line format `stamp` produces wrapped around the exact telemetry text the real server emits. Write them at a nominal interval of 3600 seconds spanning roughly thirty hours, so each fixture is around thirty lines rather than the several thousand a five-minute cadence would need; they are checked with `--interval-s 3600 --min-days 1` and exercise every gate identically.

    `battery-good.log` is a healthy discharge: polls one hour apart with no gap, millivolts falling smoothly from about 4150 to about 3300, ending abruptly at the bottom. Checked with `--expect-depleted` it must pass every check.

    `battery-gap.log` is the same discharge with a six-hour hole punched into the middle where the host slept - so both the coverage gate and the maximum-gap gate have something to catch. It must be rejected.

    `battery-flat-mv.log` has full cadence and no gaps, but its millivolts sit between about 4180 and 4190 for the entire run and never fall. It is the phantom-USB-power symptom, and it must be rejected.

    Extend the existing `selftest` subcommand to run the three new fixtures under the flags each is meant to be judged with, alongside the three backoff fixtures it already covers, asserting pass, fail, fail for each trio and exiting zero only when all six outcomes match. A checker that has never been shown a bad log has not been tested, and this is the standard the phase already set twice - plan 01-02 proved its integrity gate by flipping a byte, and plan 01-07 proved its backoff gate by feeding it a fixed-interval retry.

Record: the pack's rated capacity in milliamp-hours transcribed from `hardware/BOM.md`; the server sleep value of 300 seconds, which `stub-server/README.md` already documents as the value chosen for this run so a depletion result arrives in days rather than months; the coverage, maximum-gap, minimum-millivolt-drop and cutoff thresholds this run will be judged by; a ceiling of 21 days after which the developer may end the run; and the exact division being performed, which is rated capacity divided by counted cycles, per D-07.
