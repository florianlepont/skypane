# Phase 06.6.2 Plan 07: Dedicated login_shell() + Allowlisted Deep-Link Return + Login Accessibility Summary

**Login now renders through a genuinely separate, nav-free `login_shell()` (no sidebar, no mobile-nav dropdown, no protected navigation implying the site is usable before sign-in), and an unauthenticated request to any protected route now returns the user to that exact route after a successful password submit via `_validated_next_route()` — an exact-membership allowlist against `layout.NAV_TABS`'s five known routes that makes an open-redirect attack structurally impossible (T-06.6.2-12), plus `autocomplete="current-password"`/`autofocus`/`role="alert"` closing login's remaining accessibility gaps.**

- **Completed:** 2026-08-31T~09:15Z (last task commit)

## Accomplishments

- `companion/layout.py` gained `login_shell(body, ui_theme="auto")`, a deliberately separate, smaller sibling of `page_shell()` — same outer document structure (doctype, `<html lang="en" data-ui-theme="...">`, head with charset/viewport/title/stylesheet link/`FAVICON_LINK_HTML` reused verbatim, not duplicated) but a `<body>` containing only `<div class="login-shell"><div class="login-card">...</div></div>`: no sidebar, no mobile-nav dropdown, no icon sprite, no skip link, no nav-dropdown script tag.
- `companion/static/style.css` gained `.login-shell` (centered flex container, full viewport height) and `.login-card` (max-width 360px bounded card on desktop, full-width with comfortable padding on mobile via the flex-centering shape rather than a media query) — a new component pair not reused by any other page.
- `companion/app.py` gained `LOGIN_EXPLANATION_TEXT` and `_validated_next_route(candidate)` — an exact-membership equality test against `{route for route, _ in layout.NAV_TABS}`, never `startswith`/URL-parsed/regex-matched, mirroring `_referring_tab()`'s own allowlist shape. `require_session()`'s unauthenticated branch now redirects to `/login?next=<allowlisted-route>` (URL-encoded with `safe=""` so `/` is escaped as `%2F`, matching the plan's own acceptance criteria) when the originally-requested path is a `NAV_TABS` member, else the bare `/login` exactly as before. `_handle_login_post()` reads and validates `next` from the form before the lockout/password checks so it survives every branch (lockout, incorrect password, success); on success it redirects to `next_route or CONFIG_ROUTE`, never a raw value. `do_GET`'s `LOGIN_ROUTE` branch validates a `?next=` query value the same way, so an unrecognised value never even renders a hidden field for the user to resubmit. `_login_body()` now opens with `<h1 class="page-title">SkyPane</h1>` and `LOGIN_EXPLANATION_TEXT`, carries `role="alert"` on the error/lockout paragraph, a hidden `next` field only when truthy, and `autocomplete="current-password"`/`autofocus` on the password input (unconditional autofocus — the plan's own reasoning: this is the one page with a single, always-relevant focus target). `_render_login_page()` now calls `layout.login_shell(...)` instead of `layout.page_shell(title="Login", active="", ...)`.
- `companion/test_companion_app.py` grew 73→79 checks: 6 new (deep-link-return round trip; two open-redirect-rejection checks for `https://evil.example` and `//evil.example`; the GET-path `?next=` no-hidden-field check for a non-`NAV_TABS` value; the `login_shell()` markup check; the `page_shell()`/`login_shell()` `lang="en"` agreement guard) plus 6 pre-existing checks updated in place for the new `?next=`-carrying redirect behavior (the five `NAV_TABS`-route unauthenticated-GET checks, the `POST /config` unauthenticated check, and the post-logout `/config` redirect check — none counted as new).

## Decisions Made

- `login_shell()` is a genuinely separate, smaller sibling function of `page_shell()`, not a parameterized branch inside it — exactly per the plan's explicit instruction, since `page_shell()` always renders the full sidebar/mobile-nav/theme-form-footer regardless of any `active=""` value, which is UXA-03's root cause.
- `quote(next_route, safe="")` was used instead of the plan's action-item prose (`quote(next_route)`, no `safe` argument) — Python's `urllib.parse.quote()` defaults to `safe='/'`, which leaves `/` unescaped and would have produced `?next=/health` rather than the plan's own acceptance-criteria-mandated `?next=%2Fhealth`. Verified directly: `quote('/health') == '/health'` vs. `quote('/health', safe='') == '%2Fhealth'`.
- The open-redirect rejection check (Task 3, item 2) exercises both `https://evil.example` and `//evil.example` as two separate `check()` calls rather than picking just one — both are cheap and both are named explicitly in the plan's own `<threat_model>` mitigation text for T-06.6.2-12, and the `<security_note>` accompanying this plan's execution explicitly called for exploit-shaped fixtures. Counted as 2 of the plan's 6 total new checks, not the plan's nominal 5-item list.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 - Bug] `require_session()`'s `quote(next_route)` call needed `safe=""` to match the plan's own acceptance criteria**
- **Found during:** Task 3 (writing the deep-link-return check and verifying the exact `Location` header value)
- **Issue:** The plan's Task 2 action-item 3 literally specifies `quote(next_route)` with no `safe` argument. Python's `urllib.parse.quote()` defaults to `safe='/'`, meaning `/` is left unescaped: `quote('/health')` returns `'/health'`, not `'%2Fhealth'`. The plan's own acceptance criteria (Task 2) and `<verification>` block are unambiguous that the wire format must be `/login?next=%2Fhealth` — a real, reproducible discrepancy between the plan's action prose and its own acceptance criteria.
- **Fix:** Changed the `quote()` call to `quote(next_route, safe="")`, with an inline comment explaining why the default `safe` value is wrong here.
- **Files modified:** `companion/app.py`
- **Verification:** `quote('/health', safe='')` confirmed to return `'%2Fhealth'`; the new `_deep_link_return_round_trip` check in `test_companion_app.py` asserts the exact header value against a real running service.
- **Committed in:** `cff86d4` (bundled with Task 3's test commit, since the discrepancy was only discovered while writing Task 3's exact-header-value assertion; Task 2's own commit had already landed with the plan's literal, incorrect `quote(next_route)` call and was corrected forward here rather than amended).

**2. [Rule 1 - Bug] Six pre-existing `test_companion_app.py` checks asserted the old, now-superseded bare `/login` redirect shape**
- **Found during:** Task 3 (running the full suite after Task 2's `require_session()` rewrite landed)
- **Issue:** `_unauth_redirects_to_login()`'s five `NAV_TABS`-route unauthenticated-GET checks, its `POST /config` check, and `_tab_refused_after_logout()`'s post-logout `/config` redirect check all asserted `Location == "/login"` exactly — the correct pre-06.6.2-07 behavior, now superseded by this plan's own Task 2 change (a `NAV_TABS`-member requested path now carries `?next=`). A correct implementation began failing these six pre-existing assertions immediately.
- **Fix:** `_unauth_redirects_to_login()` gained a `next_route` parameter computing the expected `Location` (`/login?next=<quoted-route>` when `next_route` is truthy, else the old bare `/login`); the five `NAV_TABS` GET checks and the `POST /config` check now pass their own route as `next_route`. `_tab_refused_after_logout()`'s assertion was updated to the exact expected `/login?next=%2Fconfig` value.
- **Files modified:** `companion/test_companion_app.py`
- **Verification:** `server/.venv/bin/python3 companion/test_companion_app.py` — 79/79.
- **Committed in:** `cff86d4` (Task 3 commit)
