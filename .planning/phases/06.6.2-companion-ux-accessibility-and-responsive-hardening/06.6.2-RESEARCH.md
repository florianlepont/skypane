## Summary

This phase has no new technology to select — it is 100% implementation-pattern research against a codebase that already has locked conventions (`companion/layout.py`'s escaping discipline, `companion/static/*.js`'s ES5-safe IIFE pattern, the `check()`-based test harness, the `stat_tile()`/`_nav_links()` shared builders). The correct approach for every one of the six research questions the orchestrator posed is to extend an existing, already-shipped pattern rather than introduce a new one. Nothing in this phase requires a new dependency, a new test framework, or a new external tool — every accessibility/concurrency/filtering problem here has a stdlib-only or vanilla-ES5-only solution, which matters because this project has an explicit "no build step, no framework" constraint (`06.6.1-UI-SPEC.md` Design System) that a naive implementer could easily violate by reaching for a JS bundler-oriented pattern.

The two structurally hardest findings are UXA-02 (closed mobile nav still in the accessibility tree) and UXA-12 (no-JS nav is invisible) — the audit is explicit that these must be fixed *together*, and research confirms the correct joint fix is a `.js`-marker-class progressive-enhancement pattern: the CSS `max-height: 0` clipping rule that currently always applies should only apply once JS has proven it is running (by adding a class to `<html>` at the top of `nav-dropdown.js`, before its existing early-return guard), and the JS's `setOpen()` function should additionally toggle the native `hidden` attribute — applied only after the collapse transition completes (or synchronously under `prefers-reduced-motion`). This is a single coherent design that resolves both findings with one state-transition function, exactly as the audit requires, and needs no new markup element.

**Primary recommendation:** Solve every accessibility/interaction problem in this phase with the smallest extension of an existing pattern (roving-tabindex on `battery-trend.js`'s existing per-point listeners, a `.js`-class + `hidden`-attribute extension to `nav-dropdown.js`'s existing `setOpen()`, a `threading.Lock` extension to `app.py`'s existing process-global singleton pattern already used for `LOGIN_THROTTLE`) rather than introducing new architecture, and verify WCAG contrast with a ~15-line pure-Python function (no external tool, no network call) rather than treating contrast checking as unverifiable in this stdlib-only project.

### Pattern 1: Progressive-enhancement `.js`-marker class (resolves UXA-02 + UXA-12 jointly)

**What:** A tiny script-order trick: the very first statement of `nav-dropdown.js` (before its existing `if (!toggle || !panel) { return; }` guard) adds a class to `<html>` (e.g. `document.documentElement.className += " js"`). CSS rules that should only apply when JS is confirmed running are then scoped under `.js` in the selector, e.g. `.js .mobile-nav { max-height: 0; overflow: hidden; ... }`. Without this class present (JS disabled, or the script failed to load), the panel renders in its natural, fully-visible, unclipped state.

**When to use:** Any time a visual state (collapsed/hidden) must depend on JS actually having run, and the served HTML has no server-side way to know that.

**Example:**
```javascript
// companion/static/nav-dropdown.js — new first lines, before the existing guard
(function () {
  "use strict";

  // Progressive-enhancement marker: CSS scopes the mobile-nav clipping
  // rule under html.js so a no-JS/JS-failed browser sees the panel in
  // its natural, unclipped, fully visible flow (UXA-12's floor) instead
  // of permanently max-height:0 (UXA-12's actual defect). Must be the
  // very first statement — added even if the toggle/panel guard below
  // returns early, so a page with no nav still doesn't accidentally
  // apply .js-scoped rules meant for other components on that page.
  document.documentElement.className += " js";

  var toggle = document.getElementById("site-nav-toggle");
  var panel = document.getElementById("mobile-nav");
  if (!toggle || !panel) {
    return;
  }

  var OPEN_CLASS = "mobile-nav--open";
  var reduceMotion = false;
  if (window.matchMedia) {
    reduceMotion = window.matchMedia("(prefers-reduced-motion: reduce)").matches;
  }

  function isOpen() {
    return toggle.getAttribute("aria-expanded") === "true";
  }

  function setOpen(next) {
    toggle.setAttribute("aria-expanded", next ? "true" : "false");
    if (next) {
      // Opening: remove `hidden` FIRST so the browser has something to
      // transition (a hidden element cannot participate in a max-height
      // transition — it has no box at all until unhidden), then add the
      // open class on the next frame so the transition actually runs
      // instead of jumping straight to its end state.
      panel.hidden = false;
      if (reduceMotion) {
        panel.classList.add(OPEN_CLASS);
      } else {
        window.requestAnimationFrame(function () {
          panel.classList.add(OPEN_CLASS);
        });
      }
    } else {
      panel.classList.remove(OPEN_CLASS);
      if (reduceMotion) {
        panel.hidden = true;
      } else {
        // Apply `hidden` only after the collapse transition completes —
        // applying it immediately would cut the animation short (a
        // hidden element renders nothing, transition or not). `once:
        // true` means this listener never accumulates across repeated
        // opens/closes.
        panel.addEventListener("transitionend", function _onCollapsed() {
          panel.hidden = true;
        }, { once: true });
      }
    }
  }

  toggle.addEventListener("click", function () {
    setOpen(!isOpen());
  });

  document.addEventListener("keydown", function (evt) {
    if (!isOpen()) {
      return;
    }
    if (evt.key === "Escape") {
      setOpen(false);
      toggle.focus();
    }
  });
})();
```
```css
/* companion/static/style.css — .mobile-nav's clipping rule becomes .js-scoped */
.js .mobile-nav {
  max-height: 0;
  overflow: hidden;
  transition: max-height .22s ease;
}
.js .mobile-nav--open {
  max-height: 420px;
}
/* No-JS default (no .js class present): .mobile-nav keeps its natural
   flow-document height, fully visible, no clipping — this is UXA-12's
   floor. The panel's [hidden] attribute (native browser semantics,
   requires no CSS rule) removes it from the a11y tree/tab order
   whenever JS explicitly sets it — UXA-02's floor. */
```

**Rationale for `transitionend` + `hidden` combination (not `inert`):** `hidden` (native HTML boolean attribute) is simpler than `inert` here because the collapsed state is *already* going to zero height via `max-height: 0` — there's no need for `inert`'s "stay visible but non-interactive" behavior. `hidden` also has universal browser support and needs no polyfill. Setting `panel.hidden = true` synchronously (instead of after `transitionend`) would abort the animation, since a `hidden` element renders nothing at all mid-transition — hence the deferred application.

### Pattern 2: Roving tabindex on an already-per-point-wired SVG chart (UXA-11)

**What:** Server renders every battery-chart hit-target `<circle>` with `tabindex="-1"` except the most recent (last) point, which gets `tabindex="0"`. Client JS extends the existing per-point `keydown` listener (already present for Enter/Space, see `battery-trend.js`) with Left/Right/Home/End handling that moves both DOM focus and the `tabindex="0"`/`"-1"` pair.

**When to use:** Any SVG/canvas-based chart where every data point is independently focusable today and needs a normal (one Tab stop) keyboard contract.

**Example:**
```python
# companion/pages/health_page.py — battery_sparkline_svg(), tabindex change
# Only the LAST (most recent, chronologically rightmost) hit target gets
# tabindex="0" — this alone satisfies "adds no more than one entry to
# the page's normal Tab sequence" even before nav-dropdown.js's sibling
# script (battery-trend.js) adds arrow-key roving on top. Every other
# point gets tabindex="-1" (still programmatically focusable via JS,
# just removed from the natural Tab order).
for index, (value, ts) in enumerate(pairs):
    is_last = index == len(pairs) - 1
    tabindex = "0" if is_last else "-1"
    hit_targets.append(
        '<circle class="%s" cx="%.1f" cy="%.1f" r="8" tabindex="%s" '
        'role="button" data-mv="%d" data-ts="%s" aria-label="%s">'
        "<title>%s</title></circle>"
        % (SPARKLINE_HIT_CLASS, x, y, tabindex, value, escape_html(ts), label, label))
```
```javascript
// companion/static/battery-trend.js — added inside the existing per-point
// closure loop, alongside the pre-existing click/mouseenter/focus/keydown
// listeners. `points` is already chronological (oldest→newest), matching
// this file's existing `reveal(point)` helper and DOM order.
point.addEventListener("keydown", function (evt) {
  if (evt.key === "Enter" || evt.key === " ") {
    evt.preventDefault();
    reveal(point);
    return;
  }
  var targetIndex = -1;
  if (evt.key === "ArrowRight") {
    targetIndex = i + 1;
  } else if (evt.key === "ArrowLeft") {
    targetIndex = i - 1;
  } else if (evt.key === "Home") {
    targetIndex = 0;
  } else if (evt.key === "End") {
    targetIndex = points.length - 1;
  } else {
    return;
  }
  // No-wrap (Claude's Discretion, D-13): out-of-range Left/Right is a
  // silent no-op rather than wrapping to the other end — Home/End
  // remain the explicit way to jump to either boundary, which keeps
  // "where am I" unambiguous for a keyboard user exploring the chart.
  if (targetIndex < 0 || targetIndex >= points.length) {
    return;
  }
  evt.preventDefault();
  points[i].setAttribute("tabindex", "-1");
  points[targetIndex].setAttribute("tabindex", "0");
  points[targetIndex].focus(); // triggers the existing 'focus' listener → reveal()
});
```
No new escaping surface is introduced (this only reads/writes `tabindex` attribute values, matching the file's existing "attributes and class names only" no-escaping-needed contract).

### Pattern 3: Non-blocking in-process lock as the correctness boundary (UXA-15)

**What:** A single module-level `threading.Lock()` (same "process-global singleton" shape `LOGIN_THROTTLE = auth.LoginThrottle()` already establishes in `app.py`), acquired **non-blocking** at the very top of `_handle_poll_now()`, wrapping the entire check→run→mark sequence.

**When to use:** Any server-side action that must never execute concurrently within one process, where a concurrent second caller should get an immediate "busy" response rather than queueing.

**Example:**
```python
# companion/app.py — module level, alongside LOGIN_THROTTLE
import threading
_POLL_LOCK = threading.Lock()

# New flash key + copy, defined in config_page.py alongside the other
# FLASH_* constants (single source of truth, same discipline as the
# existing four keys), then rebound here exactly like FLASH_KEY_SAVED etc.
FLASH_KEY_POLL_ALREADY_RUNNING = config_page.FLASH_POLL_ALREADY_RUNNING
FLASH_MESSAGES[FLASH_KEY_POLL_ALREADY_RUNNING] = (
    "A poll is already in progress — try again in a moment.")

def _handle_poll_now(self):
    state_dir = self.args.state_dir
    # Non-blocking acquire wraps the WHOLE check->run->mark sequence, not
    # just run_once() — this is what prevents two requests that both read
    # a zero cooldown (the TOCTOU window: cooldown is only written by
    # mark_poll_triggered() AFTER run_once() completes) from both
    # proceeding. The loser gets an immediate, honest "already running"
    # response instead of blocking behind the first request or silently
    # double-running.
    if not _POLL_LOCK.acquire(blocking=False):
        return self.redirect(
            "%s?flash=%s" % (CONFIG_ROUTE, quote(FLASH_KEY_POLL_ALREADY_RUNNING)))
    try:
        remaining = poll_cooldown_remaining(state_dir)
        if remaining > 0:
            return self.redirect(
                "%s?flash=%s" % (CONFIG_ROUTE, quote(FLASH_KEY_POLL_COOLDOWN)))
        try:
            poll_loop.run_once(state_dir=state_dir, geofence=self.args.geofence)
        except Exception:
            return self.redirect(
                "%s?flash=%s" % (CONFIG_ROUTE, quote(FLASH_KEY_POLL_FAILED)))
        mark_poll_triggered(state_dir)
        return self.redirect(
            "%s?flash=%s" % (CONFIG_ROUTE, quote(FLASH_KEY_POLL_TRIGGERED)))
    finally:
        _POLL_LOCK.release()
```
This is sufficient because `ThreadingHTTPServer` runs a single OS process (`server = ThreadingHTTPServer(("0.0.0.0", args.port), Handler)` in `main()`, one process per systemd unit, no worker pool/replica count) — a `threading.Lock` correctly serializes all request-handling threads within that one process. **Do not reach for a cross-process/file-based/SQLite-advisory lock** — the deployment has exactly one process, so that would be solving a problem this architecture doesn't have.

**Client-side affordance (cosmetic, not the correctness boundary):** add a small inline `<script>` to `config_page.py`'s `poll_trigger_section()` — following the exact `_poll_cooldown_script()`/`_js_literal()` convention already in that file — that disables the submit button and swaps its text to "Polling…" on the form's `submit` event. This is UX polish only; the server-side lock above is what actually prevents double-execution, exactly as the audit states ("The server guard is the correctness boundary; client disabling is only an affordance").

### Pattern 4: Allowlisted return-route for login (UXA-03)

**What:** `require_session()` captures the request path (not the query string) when it redirects to `/login`, appends it as a `next` query parameter, and the login GET/POST handlers validate `next` against the exact same fixed set `_referring_tab()` already uses (`{route for route, _ in layout.NAV_TABS}`) before ever using it as a redirect target.

**When to use:** Any redirect-after-auth flow where the target is derived from user-observable state (the originally-requested URL) rather than a fixed constant.

**Example:**
```python
# companion/app.py
def _validated_next_route(candidate):
    """Return `candidate` if it exactly matches one of the five NAV_TABS
    routes, else None. Exact-membership check against a small fixed set
    — never string-prefix or scheme parsing — which is what makes an
    open-redirect structurally impossible here: there is no parsing
    logic an attacker-controlled value could exploit, only an
    equality test against five known-safe literals. Mirrors
    _referring_tab()'s existing allowlist precedent exactly.
    """
    allowed = {route for route, _ in layout.NAV_TABS}
    return candidate if candidate in allowed else None

def require_session(self):
    if self._is_authenticated():
        return True
    requested_path = urlsplit(self.path).path
    next_route = _validated_next_route(requested_path)
    location = LOGIN_ROUTE
    if next_route:
        location = "%s?next=%s" % (LOGIN_ROUTE, quote(next_route))
    self.redirect(location)
    return False
```
The login GET handler reads `next` from the query string, validates it the same way, and threads it into the rendered `<form action="/login?next=...">` (or a hidden `<input type="hidden" name="next">`) so it survives the POST. `_handle_login_post()` redirects to the validated `next` on success, falling back to `CONFIG_ROUTE` exactly as today when `next` is absent or fails validation. **Never** accept `next` values that aren't exact members of the fixed route set — no prefix matching, no `startswith("/")` check (that alone does not prevent `//evil.com`-style scheme-relative redirects), no URL parsing of the candidate at all.

### Anti-Patterns to Avoid

- **Reaching for `inert` + `aria-hidden` when `hidden` alone is sufficient:** `inert` is for content that should stay visible-but-non-interactive; this panel is already going to zero size via `max-height: 0`, so plain `hidden` (which implies removal from rendering, tab order, and the accessibility tree in one native attribute) is simpler and has no extra ARIA bookkeeping to keep in sync.
- **A `threading.Lock().acquire()` with a blocking default (or a timeout) for UXA-15:** a blocking acquire would make the second concurrent request wait and then *also* run (or silently re-check cooldown after the first finishes, which is fine — but the whole point of the audit's acceptance criterion "an honest `Poll already in progress`" is an *immediate* distinct response, not a delayed success). Always use `blocking=False`.
- **Filtering History/Airlines rows via a new SQL query for D-20:** this directly contradicts D-20's own locked constraint ("no new backend query, no new data source"). Filter the already-fetched, already-bounded Python list in the page module, not the database.
- **A bare `svg` element CSS selector for any new icon/chart:** this project has hit this exact collision three times (documented in `style.css`'s own comments around lines 769 and 800-811). Always scope new SVG-sizing rules to a specific class and verify they don't also match `.icon`.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| WCAG contrast ratio calculation | A hand-rolled "close enough" heuristic (e.g. comparing raw RGB sums) | The exact WCAG 2.x relative-luminance formula (linearize each sRGB channel, weighted-sum, `(L1+0.05)/(L2+0.05)`) — see Code Examples below | The formula is short, has no ambiguity, and is directly verifiable against the audit's own published numbers (confirmed byte-for-byte below) |
| Cross-process concurrency control | A file-lock or SQLite-advisory-lock module | `threading.Lock()` | There is exactly one process; a cross-process primitive adds complexity and I/O for a guarantee this deployment doesn't need |
| Client-side "which nav link is active" logic | Re-deriving active state from `window.location` in JS | Server already renders `aria-current`/active class correctly (`_nav_links()`'s `is_active` computation) — no client re-derivation needed | The server already knows the active route at render time; duplicating that logic client-side risks drift |
| A generic client-side data-table/DataTables-style library for D-20 filtering | `npm install` a table-filter library | ~30 lines of vanilla ES5 `hidden`-attribute toggling against `row.textContent` | Dataset sizes are tiny (≤50 History rows, a short unresolved-prefix list); a library would violate the project's zero-dependency constraint for no benefit |

**Key insight:** Every "hard" problem in this phase (accessibility state sync, concurrency, contrast math) has a well-known small-scale correct solution once you notice this is a single-process, no-framework, small-dataset application — the temptation to reach for a bigger tool (a locking service, a contrast-checker SaaS, a JS table library) should be resisted throughout planning.

## Common Pitfalls

### Pitfall 1: Fixing UXA-02 without also fixing UXA-12 (or vice versa)
**What goes wrong:** Adding `hidden` toggling to `nav-dropdown.js` alone (without the `.js`-marker-class CSS scoping) still leaves the CSS `max-height: 0` rule applying unconditionally — so a no-JS browser still sees a permanently-clipped, unusable menu (UXA-12 persists). Conversely, fixing only UXA-12 (making the panel visible by default) without adding `hidden`-toggling leaves every link exposed to the accessibility tree when visually collapsed (UXA-02 persists).
**Why it happens:** The two findings share one root cause (the panel's closed-state markup/CSS never distinguished "JS is running and chose to collapse this" from "there is no JS to open it with") but were filed as two separate severity-High findings, which can tempt separate, independent fixes.
**How to avoid:** Implement Pattern 1 above as one combined change; write one test that exercises both the no-JS-visible case and the JS-closed-then-hidden case against the same markup.
**Warning signs:** A plan task that touches `nav-dropdown.js` but not `style.css`'s `.mobile-nav` rule (or vice versa) for this finding.

### Pitfall 2: Rewriting the existing `_dropdown_survives_with_javascript_disabled()` test's *intent* instead of its *assertions*
**What goes wrong:** The existing test (`companion/test_companion_app.py`) currently asserts the panel is present with no `hidden` attribute at all — this is the exact behavior UXA-12 identifies as broken. The fix must invert what "surviving" means: the panel must still be link-complete and visible in the *server-rendered, un-styled* state, but the test needs to stop asserting "no hidden attribute ever appears" since `hidden` will now legitimately appear once JS decides to close the menu.
**Why it happens:** The audit explicitly calls this test "the exact behavior that creates the accessibility defect" — a naive fix risks preserving the old assertion shape while only patching the implementation, leaving a test that still enforces the bug.
**How to avoid:** Read `06.6.1-UX-AUDIT.md`'s UXA-12 acceptance criteria verbatim: "The existing test named `_dropdown_survives_with_javascript_disabled()` is rewritten to assert actual visible operability rather than DOM presence alone." Since this is a Python-only test harness (no real browser), "visible operability" must be asserted structurally: no `hidden` attribute and no `.js`-scoped clipping class present in the **server-rendered** document (proving the no-JS default is genuinely unclipped) — a real-browser check (Wave 4) is still required to confirm the CSS actually renders unclipped absent the `.js` class.
**Warning signs:** A green test suite that never runs a real browser with JavaScript disabled (see Wave 4 in Suggested implementation sequence).

### Pitfall 3: Treating `_battery_section()`'s single-argument call-site signature as immovable
**What goes wrong:** `health_page.py`'s own code comment states `_battery_section()`'s single-argument call site "is pinned by sibling phase 06.5's own automated gate." A planner might read this too broadly and avoid touching `battery_sparkline_svg()`'s per-point `tabindex` value, assuming any change there is forbidden.
**Why it happens:** The pinned-signature comment is about the *function signature* (`_battery_section(trend_rows)`), not about the internal markup `battery_sparkline_svg()` produces. Changing which `<circle>` gets `tabindex="0"` doesn't touch either function's signature.
**How to avoid:** Re-read the actual pinned assertion in `companion/test_status_pages.py` before assuming a markup change is blocked; the comment is about call-site arity, not byte-identical output.
**Warning signs:** Skipping the UXA-11 SSR-baseline fix (Pattern 2's Python half) because of signature-pinning concerns that don't actually apply to it.

### Pitfall 4: A dirty-state Save bar that gates the actual save behind JS
**What goes wrong:** If the dirty-state bar's "Save settings" button is implemented as a JS `fetch()`/`XMLHttpRequest` call instead of a real form submit, the no-JS floor breaks — D-03 explicitly requires "a fully functional no-JS path" and "the existing always-available server-rendered `<form method="post">` submit path is preserved unchanged."
**Why it happens:** "Show a bar with its own Save button" naturally suggests giving that button its own click handler that does the saving, rather than delegating to the existing form.
**How to avoid:** Use `<button type="submit" form="config-form">` (the HTML5 `form` attribute lets a button outside a `<form>` element still submit it) so the bar's Save button is a real submit trigger for the exact same, unchanged `<form action="/config">` — zero new POST logic, zero new escaping surface, zero risk of the no-JS/JS paths diverging in what they persist.
**Warning signs:** A new `POST` handler or `fetch()` call introduced specifically for the dirty-state bar.

### Pitfall 5: A History/Airlines filter that only works with JavaScript
**What goes wrong:** If the filter `<input>` has no `<form method="get">` wrapper and server-side read of the query param, it becomes a dead, decorative control the moment JavaScript is unavailable — a real functional regression versus today (where there is no filter at all, so nothing currently depends on it).
**Why it happens:** "Client-side filtering" is the audit's own phrase for D-20, which can be read as implying JS-only by default.
**How to avoid:** Implement the GET-query-param server-side filter first (Python-side filtering of the already-fetched row list — not a new SQL query, satisfying D-20's own "no new backend query" constraint), then layer the JS enhancement on top for instant re-filtering without a full page reload. See the Code Examples section for the concrete shape.
**Warning signs:** A filter `<input>` with no `<form>`/`name` attribute, or `history_page.render(ctx)` never reading a query-string value.

### WCAG contrast verification — pure Python, no library, no network (UXA-04/D-14)
```python
# A ~15-line pure stdlib function — verified in this research session to
# reproduce 06.6.1-UX-AUDIT.md's own published contrast numbers exactly
# (e.g. #E8622C on #FBF9F6 → 3.22, #B13F16 on #FFFFFF → 5.85), confirming
# both the formula's correctness and that no external tool is needed.
# Source: WCAG 2.x relative luminance / contrast ratio formulas
# (W3C WCAG 2.1 Understanding SC 1.4.3, algorithm reproduced from spec text).

def _linearize_channel(value_0_255):
    c = value_0_255 / 255.0
    return c / 12.92 if c <= 0.03928 else ((c + 0.055) / 1.055) ** 2.4


def relative_luminance(hex_color):
    hex_color = hex_color.lstrip("#")
    r, g, b = (int(hex_color[i:i + 2], 16) for i in (0, 2, 4))
    return (
        0.2126 * _linearize_channel(r)
        + 0.7152 * _linearize_channel(g)
        + 0.0722 * _linearize_channel(b)
    )


def contrast_ratio(hex_a, hex_b):
    l1, l2 = relative_luminance(hex_a), relative_luminance(hex_b)
    l1, l2 = max(l1, l2), min(l1, l2)
    return (l1 + 0.05) / (l2 + 0.05)


# WCAG AA normal text floor: 4.5:1. Large text (>=18.66px bold or
# >=24px regular) floor: 3:1. UI-component/focus-indicator floor: 3:1.
```
Recommend adding this as a small, dependency-free module (e.g. `companion/contrast_check.py`, or inlined directly into a new test in `companion/test_companion_app.py`/a dedicated `companion/test_style_tokens.py`) that iterates every `--color-*` token pair `style.css` actually pairs in practice (accent-on-dominant, accent-on-secondary, accent-hover-on-dominant, text-on-dominant, muted-text-on-dominant, both light and dark) and asserts each meets its WCAG floor — this is exactly the "small automated token-contrast check" the audit's UXA-04 acceptance criteria calls for, and it can run inside the existing `check()`-based harness with zero new test infrastructure.

**Confirmed via this research session** [VERIFIED: computed directly]: the audit's own light-mode failing values reproduce exactly —`#E8622C`/`#FBF9F6` → 3.22:1 (fail), `#D2521F`/`#FBF9F6` → 4.02:1 (fail), `#FF8A5C`/`#0D0F14` → 8.25:1 (pass) — and the exploration-palette examples the audit proposes for D-14 also reproduce exactly — `#B13F16`/`#FFFFFF` → 5.85:1, `#B13F16`/`#F7F4EF` → 5.33:1, `#B13F16`/`#EEE8DE` → 4.80:1, all passing AA (≥4.5:1). Whatever final hex values D-14's planner/executor lands on (the audit is explicit these are "an exploration target, not a locked implementation contract"), re-run this exact formula against the final values before treating the contrast fix as done — do not assume the audit's example numbers still hold if a different hue/lightness is chosen.
