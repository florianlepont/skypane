# Phase 06.6.2: Code Review Report

**Reviewed:** 2026-08-31T10:03:12Z
**Depth:** standard
**Files Reviewed:** 17
**Status:** issues_found

## Summary

This phase's stated purpose is UX/accessibility/responsive hardening for the SkyPane companion service, and most of the delivered work (WCAG contrast tooling, open-redirect-safe login `?next=` handling, severity-aware flash/anomaly ARIA roles, whole-site auth-gate discipline, the icon whitelist, path-traversal-safe gallery/runway-image serving) is careful and well-tested. The extensive docstrings and the accompanying test harnesses (`test_companion_app.py`, `test_config_page.py`, `test_contrast_check.py`, `test_status_pages.py`, `test_view_pages.py`) genuinely exercise most of the claimed contracts, including several adversarial cases (path traversal, forged tokens, open-redirect payloads, concurrent poll triggers).

Despite that, one of the phase's own headline accessibility deliverables — the skip-to-content link (UXA-10) — does not actually work for keyboard users because its target lacks `tabindex="-1"`, which is a correctness defect in exactly the area this phase claims to have hardened. I also found a genuine race condition in the new `nav-dropdown.js` open/close state machine, a couple of hardening gaps (missing security response headers, an unauthenticated slow-body read with no timeout), and a duplicated-work correctness smell in the Health severity computation that reopens a narrow version of the exact nav-dot/banner disagreement bug the code's own docstrings say is structurally prevented.

## Critical Issues

### CR-01: Skip-to-content link target is not focusable, so it does not actually skip keyboard focus past the nav

**File:** `companion/layout.py:716-718` (skip link) and `companion/layout.py:767` (`<main>` target)
**Issue:** `page_shell()` renders `<a class="skip-link" href="#main-content">Skip to content</a>` and `<main class="page-content dashboard-main" id="main-content">`, but `<main>` carries no `tabindex="-1"`. Per the HTML fragment-navigation focusing steps, when an in-page `href="#id"` link is activated, the browser only moves keyboard focus to the target element if that element is itself focusable; a plain `<main id="...">` with no tabindex is not focusable, so activating the link scrolls the viewport but focus falls back to the document body. The practical effect: a keyboard-only or screen-reader user who activates "Skip to content" does *not* get their next Tab press land on the first control after the nav — Tab restarts from the top of the document, defeating the one job a skip link exists to do. This is the exact WCAG technique (SCR28/G1) gap that skip-link implementations are specifically required to close, and it directly undermines this phase's own UXA-10 deliverable.
**Fix:**
```python
# companion/layout.py, page_shell()'s <main> element:
'<main class="page-content dashboard-main" id="%s" tabindex="-1">\n'
```
(`tabindex="-1"` makes the element programmatically focusable without adding it to the normal tab order, which is the standard skip-link-target pattern.) Add a regression check to `test_companion_app.py`'s `_page_shell_*` suite asserting `'id="main-content" tabindex="-1"'` (or equivalent) is present.

## Warnings

### WR-01: `nav-dropdown.js`'s open-transition callback can silently re-open the menu after a fast close

**File:** `companion/static/nav-dropdown.js:72-113` (`setOpen()`)
**Issue:** `setOpen(true)` schedules `panel.classList.add(OPEN_CLASS)` inside a `window.requestAnimationFrame()` callback (to let the `max-height: 0` base state apply before the transition starts). That scheduled callback does not check whether the panel's desired state is still "open" by the time it runs. If a user toggles the menu open and then closed again before the next animation frame (`setOpen(true)` then `setOpen(false)`, both synchronous), `setOpen(false)` removes `OPEN_CLASS` and registers a one-shot `transitionend` listener — but the *stale* rAF callback from the earlier `setOpen(true)` call still fires afterward and unconditionally re-adds `OPEN_CLASS`, visually re-opening (or re-animating open) a menu that `aria-expanded` and the toggle button already report as closed. Because the CSS transition then runs from 0 → 420px again, `transitionend` eventually fires and sets `panel.hidden = true`, but only after visibly reopening the panel — a real desync between the announced state (`aria-expanded="false"`) and the rendered state.
**Fix:** Guard the rAF callback with a state check, or track/cancel the pending frame:
```javascript
if (next) {
  panel.hidden = false;
  if (reduceMotion) {
    panel.classList.add(OPEN_CLASS);
  } else {
    window.requestAnimationFrame(function () {
      if (isOpen()) {  // re-check: a fast close may have already run
        panel.classList.add(OPEN_CLASS);
      }
    });
  }
}
```

### WR-02: Every response is missing baseline hardening headers

**File:** `companion/app.py:311-340` (`send_html()`/`send_bytes()`)
**Issue:** No response from this service ever sets `X-Content-Type-Options: nosniff`, `X-Frame-Options`/a frame-ancestors CSP directive, or `Referrer-Policy`. This is an authenticated admin panel (device config, poll trigger, LED control) reachable from the public internet per this file's own docstring ("binds all interfaces... loopback restriction is enforced at the firewall/reverse-proxy layer"); with no `X-Frame-Options`/CSP, the authenticated pages (e.g. `/config`) can be framed by a third-party site for a clickjacking attack against a logged-in user, and with no `X-Content-Type-Options: nosniff`, an upstream misconfiguration or future route serving user-influenced content is one MIME-sniffing quirk away from an XSS vector.
**Fix:** Add the headers once, centrally, in `send_html()`/`send_bytes()`:
```python
self.send_header("X-Content-Type-Options", "nosniff")
self.send_header("X-Frame-Options", "DENY")
self.send_header("Referrer-Policy", "same-origin")
```

### WR-03: Unauthenticated `POST /login` can block a worker thread indefinitely on a slow/lying request body

**File:** `companion/app.py:386-413` (`read_form()`)
**Issue:** `read_form()` calls `self.rfile.read(min(length, MAX_FORM_BYTES + 1))` where `length` comes straight from the client-supplied `Content-Length` header, with no socket read timeout configured anywhere on `ThreadingHTTPServer`/`Handler`. `rfile.read(n)` blocks until `n` bytes arrive or the connection closes. `_handle_login_post()` — reachable with **no authentication** — calls `read_form()` unconditionally. A client that sends `Content-Length: 8193` (or any value ≥ a few bytes) and then trickles the body in slowly (or never finishes it) ties up that connection's worker thread for as long as it holds the socket open; `ThreadingHTTPServer` spawns one thread per connection with no cap, so a modest number of slow-drip connections against the pre-auth login endpoint can exhaust server threads/memory — a classic slowloris-shaped DoS reachable before any credential check.
**Fix:** Set an explicit per-connection read timeout (`Handler.timeout = <N seconds>`, which `socketserver.StreamRequestHandler` honours and turns into a `socket.timeout` on a stalled `rfile.read()`), and treat a timeout the same as any other malformed-body case (degrade to an empty form) rather than let the thread block unbounded. Note this may already be partially mitigated by Caddy's own proxy read timeouts per this project's deployment model — but the companion process itself has no independent bound.

### WR-04: Health severity is computed twice per Health page load from independent, non-atomic DB reads

**File:** `companion/app.py:415-455` (`page_context()`) and `companion/pages/health_page.py:462-518` (`health_severity()`), `731-770` (`render()`)
**Issue:** `page_context()` (called for *every* authenticated route, not just `/health`) calls `health_page.health_severity()`, which independently runs `_read_health_inputs()` (five fresh `_safe_query()`/`open_db()` calls) plus the four section builders just to derive a severity string for the nav-tab dot. When the user is actually on `/health`, `Handler.do_GET`'s `/health` branch then calls `health_page.render(ctx)`, which calls `_read_health_inputs()` and the same four section builders *again*, against fresh DB reads. The module's own docstring states this single-sourcing exists specifically "to make it structurally impossible for the nav dot and the banner to disagree" — but because the two calls open independent connections and read the database at two different wall-clock instants (only the `now` reference string is shared, not the underlying row snapshot), a write landing between the two reads (e.g. the systemd poll timer firing mid-request) can still make the nav dot and the on-page banner disagree, and it doubles the SQLite work needed for every single authenticated page render regardless of which page is being viewed.
**Fix:** Compute `_read_health_inputs()`/the section states once per request (e.g. cache the tuple on `ctx` in `page_context()`) and have `health_page.render()` accept the already-computed inputs instead of re-deriving them, restoring the "one computation, two consumers" property the docstring already claims.

## Info

### IN-01: Mobile nav dropdown's fixed `max-height: 420px` is close to its own content budget

**File:** `companion/static/style.css:377-379` (`.js .mobile-nav--open`)
**Issue:** `.js .mobile-nav--open { max-height: 420px; }` caps the open dropdown's height. Five nav links at the documented 44px floor (`companion/static/style.css:397-409`) already account for 220px, and the footer adds two more 44px-min controls plus padding/borders (`.mobile-nav__footer`, `:426-431`). The current English copy fits, but there is no scroll affordance (`overflow: hidden`) if a future label/icon change or a slightly taller rendered font pushes total content past 420px — content would silently clip with no visual indication anything is missing.
**Fix:** Consider `max-height: min(420px, calc(100vh - <header height>))` or simply raising the cap with headroom, and/or adding `overflow-y: auto` inside `.mobile-nav__nav` as a safety net.

### IN-02: `health_page.py` imports `server.poll_loop` for an unused, purely-documentary "parity" reason

**File:** `companion/pages/health_page.py:42`

This is explicitly called out as deliberate, but it is still an unused import that will confuse a future reader/linter run without the `noqa` comment's context.
