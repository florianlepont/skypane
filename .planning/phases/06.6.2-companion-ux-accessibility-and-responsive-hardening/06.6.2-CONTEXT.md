<decisions>
## Implementation Decisions

**How these were captured:** the developer was offered a normal multi-area discussion and explicitly declined it — "rien, je veux que tu corriges l'ensemble des points de l'audit en suivant les recommandations ou tes propres décisions" (nothing to discuss, apply the audit's recommendations or your own judgment for everything). Every decision below therefore has an explicit rationale so the developer can override anything at plan/execute time without another discussion round. Findings that already carry a single clear "Recommended direction" in the audit (UXA-01, 02, 03, 04, 07, 11, 12, 14, 15, 16) are NOT re-decided here — research/planning should follow the audit's own Detailed Findings sections directly for those. This section only resolves the audit's explicit "Open product decisions for discussion before planning" list, plus the three developer-raised Config items.

### Language & terminology
- **D-01:** English-only interface. `<html lang="en">` and all copy stay English; no translation catalog is introduced. Rationale: the entire codebase, docs, and every shipped string are already English; the audit itself notes French-language collaboration on this project is not evidence the *product* must be French, and warns that partial/mixed-language chrome is worse than a consistent single language. Lowest-scope choice; revisit explicitly if the developer wants French later (own future decision, not silently mixed in).
- **D-02:** `Bring-up LED` is renamed to `Diagnostic LED` in every user-facing string (H2, fieldset legend, helper text). Internal Python identifiers (`LED_HELPER_TEXT`, `led_fieldset`, etc.) are unchanged — this is a copy-only rename resolving UXA-05's "internal identifiers leak into operator copy" for this specific term.

### Config page (folds the developer's original ask + UXA-08)
- **D-03 — Save behavior, overrides an earlier in-conversation preference:** ships as a **dirty-state action bar**, not full auto-save. A "N unsaved changes" bar with explicit `Save settings`/`Cancel` actions appears only once a Theme/Runway value actually changes; the existing always-available server-rendered `<form method="post">` submit path is preserved unchanged for no-JS use. Earlier in this conversation the developer said "explorer l'auto-save" for the Save button — flagging explicitly that this decision **does not do full auto-save**. Rationale for the override: the audit's own Config-page-redesign section explicitly recommends dirty-state + explicit save over auto-save, because auto-save on a Theme/Runway pick — which only takes effect on the device's *next scheduled poll*, per D-06/D-28 in `06-CONTEXT.md` — risks silently persisting a still-being-decided choice before the developer has settled on it; an explicit Save keeps that one-poll-cycle lag legible. The no-JS floor is also simpler to keep correct without a JS-driven auto-save path. If the developer still wants literal auto-save after seeing this, that's a one-line override at plan time.
- **D-04:** The Theme fieldset becomes a **read-only status display with a small preview swatch**, not a one-choice radio group, since exactly one hardware theme ("sky") exists today (confirmed live-glass-corrected per `STATE.md`'s Phase 7 notes) and a one-option radio has no real decision value. Reverts to an editable picker automatically once a second theme is added to `device_config.THEMES` — this is a rendering-count check (`len(THEME_IDS) == 1`), not a hardcoded assumption.
- **D-05:** Runway radios become **selectable cards** — designation + orientation + the optional airport-diagram `<img>` (already wired in Phase 06.4) inside one card, the whole card is the label/hit target, and the selected card gets a clear border/check rather than relying on the native radio's own visual alone. This directly answers the developer's original complaint ("les boutons radio runway sont surdimensionnés/incohérents avec le reste du design"). The three runway images the developer is separately producing (from the Orly ground-movement chart they shared) drop into this same card once supplied — no code change needed for that part, per the existing `RUNWAY-IMAGES.md` contract.
- **D-06 (from UXA-08):** The duplicate `Bring-up LED` / `Diagnostic LED` (per D-02) heading is de-duplicated to one accessible group name (keep the fieldset legend, drop the redundant `<h2>`, or vice versa — planner's call, just not both). Native radio/checkbox controls (Theme swatch's underlying markup if still a control, Runway cards, LED checkbox) get `accent-color: var(--color-accent)` so they stop rendering browser-default blue against the terracotta system, after confirming contrast still holds.

### Mobile data density
- **D-07:** History's mobile representation becomes **one compact card per flight**: primary line = callsign + relative time, secondary line = route + state, remaining fields (aircraft/airline, corroboration, runway, hex, absolute timestamp) sit behind a per-card disclosure (e.g. `<details>`). All seven data categories UXA-01's acceptance criteria requires stay reachable, just not all on the visible face of the card. Desktop keeps the existing table; the desktop-overflow half of UXA-01 is a straight containment bug fix per the audit's own direction (constrain `.dashboard-main`/`.data-table-wrap` so intrinsic table width can never expand the document) and isn't a decision point.
- **D-08:** The Battery Health readings table is **collapsed behind a closed-by-default `View {N} readings` disclosure**, and the chart is moved to appear immediately after the Battery status summary — before the (now-collapsed) table, matching UXA-06's acceptance criterion that the chart precede raw readings in visual and DOM order.
- **D-09:** Timestamps default to **relative + concise local time** everywhere (already the house style per 06.6 D-02); the full ISO value is demoted to a `title`/details-disclosure attribute rather than shown inline by default, per UXA-05's recommended direction. This doesn't change the already-decided relative-vs-absolute ordering fight noted in `06.6-CONTEXT.md` — that ordering stays as-is, only the ISO-suffix's default visibility changes.
- **D-10:** Every bounded dataset gets a visible **"Latest N" label** (History "Latest 50", Battery "Latest 20 readings", Gallery "Latest 12 renders"). No pagination or older-data access is added this phase — deliberately narrower than the audit's optional "add pagination if older data has diagnostic value" branch, to keep this hardening phase from growing a new backend capability.

### Auth, freshness & interactions
- **D-11:** `/logout` moves from **GET to POST**. Single-user tool, so the risk this closes is minor (a stray prefetch/crawler/link-scan GET-triggering a logout), but it's a small, correct fix consistent with "state-changing actions are POST," and the audit explicitly offered this as the follow-up phase's call to make.
- **D-12:** Health/Preview (the long-lived monitoring pages) get an **explicit Refresh action plus a stale-view warning** past a defined age threshold — no automatic background polling. This is the audit's own more conservative recommended default ("prefer a restrained freshness pattern over continuous background polling"); avoids new steady-state request volume and keeps authoritative health severity server-computed only.
- **D-13:** The battery chart's keyboard model becomes **roving tabindex**: the chart adds exactly one stop to the page's normal Tab order, Left/Right arrow keys move chronologically between readings and update the existing readout line, Home/End jump to first/latest. Chosen over "single chart focus target" (functionally similar, roving tabindex is the more conventional/testable pattern) and over "make it non-interactive" (which the audit itself ranks lower and which would be a real regression from the per-point interactivity Phase 06.5 deliberately built) — this preserves full interactive parity while fixing the 20-Tab-stop problem.

### Claude's Discretion
- Exact `<details>` vs. custom-disclosure markup for History's mobile per-card details and Battery's readings-table collapse — whichever composes more cleanly with the existing `data_table()`/`stat_tile()` helpers.
- Exact swatch styling for the read-only Theme status (D-04) and exact card visual treatment for Runway (D-05) — should read as siblings of each other and of the existing `.runway-option` styling `06.4-01` already shipped, not as a third unrelated pattern.
- Exact stale-view threshold (D-12) and exact roving-tabindex wrap/no-wrap behavior at the chart's first/last point (D-13) — pick sensible defaults, document them in the plan.
- All 10 findings the audit already gives a single "Recommended direction" for (UXA-01, 02, 03, 04, 07, 11, 12, 14, 15, 16) — implement per the audit's own text, no re-decision needed here.

## Existing Code Insights

### Reusable Assets
- `companion/layout.py::status_dot()`, `stat_tile()`, `icon_html()`/`ICON_DEFS_HTML` — the existing status/card/icon primitives every UXA finding's fix should compose with rather than duplicate.
- `companion/static/nav-dropdown.js` — the ES5-safe vanilla-JS pattern (`"use strict"` IIFE, no framework) this phase's new client-side bits (roving-tabindex chart nav, dirty-state Save bar, explicit Refresh) should follow.
- `companion/pages/config_page.py::runway_fieldset()` / `RUNWAY_IMAGE_ROUTE_PREFIX` — the existing registry-driven, session-gated image wiring D-05's card redesign extends.

### Established Patterns
- Every page module reads `ctx` computed once per request in `companion/app.py::page_context()` — cross-page signals (like 06.6.1's `health_anomaly_active`) are threaded this way, never via one page module importing another (`companion/pages/__init__.py` forbids it). D-12's freshness signal and D-13's chart data likely follow the same pattern.
- Asymmetric read/write validation discipline (`config_page.py::handle_post()`'s docstring) — the read path forgives unrecognised values via `normalise_*()` fallbacks, the write path rejects the whole submission. D-03's dirty-state Save must not weaken this.
- No-JS floor is a running project discipline (battery chart, poll-cooldown countdown, nav dropdown all ship a working no-JS fallback) — D-03, D-12, D-13 all need one too, and UXA-12 is specifically about a floor that currently fails this test.

### Integration Points
- `companion/app.py` — where D-11's `/logout` method change, D-12's refresh-action route (if server-rendered), and any new `ctx` signals get wired.
- `companion/static/style.css` — the single stylesheet every visual-consequence fix (D-04 swatch, D-05 cards, D-06 accent-color, UXA-04's contrast tokens) lands in.
