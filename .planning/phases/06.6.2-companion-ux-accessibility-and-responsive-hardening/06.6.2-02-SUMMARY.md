# Phase 06.6.2 Plan 02: Poll-trigger concurrency lock and Polling affordance Summary

**Non-blocking `threading.Lock()` around POST /poll-now's entire check-run-mark sequence, an honest "already running" redirect for the losing concurrent request, and a cosmetic "Polling…" disable-on-submit script — closing UXA-15's TOCTOU race with a genuine two-thread concurrent-request test, not merely a claim verified by reading the source.**

## Performance

- **Started:** 2026-08-31T07:39:56Z (approx., first commit of the plan's execution window)
- **Completed:** 2026-08-31T07:49:48Z
- **Tasks:** 2
- **Files modified:** 4

## Accomplishments
- `companion/app.py` gained `_POLL_LOCK = threading.Lock()` (process-global, mirrors the existing `LOGIN_THROTTLE` shape) and a rewritten `_handle_poll_now()`: `_POLL_LOCK.acquire(blocking=False)` is the first statement, the entire cooldown-check → `run_once()` → `mark_poll_triggered()` sequence is wrapped in `try`/`finally: _POLL_LOCK.release()`, and a failed acquire returns an immediate `poll_already_running` redirect with no cooldown check and no `run_once()` call.
- `companion/pages/config_page.py` gained `FLASH_POLL_ALREADY_RUNNING = "poll_already_running"` (distinct from `FLASH_POLL_COOLDOWN`), and `companion/app.py` rebinds it as `FLASH_KEY_POLL_ALREADY_RUNNING` with a new `FLASH_MESSAGES` entry, following the pre-existing four-key pattern exactly.
- `config_page.py`'s zero-cooldown branch of `poll_trigger_section()` now carries `id="poll-trigger-btn"` (matching the disabled branch's existing id) and a new `_poll_submit_script()` — an ES5-safe, `_js_literal()`-gated IIFE that disables the button and swaps its label to "Polling…" on the form's `submit` event, guarded with `if (!btn) { return; }`. Documented in its own docstring as cosmetic only: `_POLL_LOCK` is the real correctness boundary.
- `companion/test_companion_app.py` gained a genuine two-thread concurrent-request test: two threads block on a shared `threading.Event`, are released together, and both `POST /poll-now` against a fresh session with zero cooldown — exactly one response must carry `flash=poll_already_running`, the other must not (order not asserted). `EXPECTED_CHECK_COUNT` bumped 69 → 70.
- `companion/test_config_page.py` gained a check asserting `_poll_submit_script()`'s sink-safety and `_js_literal()` discipline, and a rewritten check asserting `poll_trigger_section(0)` now ships exactly one `<script>` (the submit-affordance script, not the countdown script) alongside `id="poll-trigger-btn"`, while `poll_trigger_section(30)` still carries its own unchanged `_poll_cooldown_script()` output byte-for-byte. `EXPECTED_CHECK_COUNT` bumped 37 → 38.

## Decisions Made
- Used a process-global `threading.Lock()` rather than a per-session or file-based lock — correct because `main()` runs exactly one `ThreadingHTTPServer` in a single OS process, verified against `deploy/skypane-companion.service`'s lack of worker/replica config.
- `_POLL_LOCK.acquire(blocking=False)` only — never a timeout — so a losing request always gets an instant, honest reply rather than a staggered eventual `run_once()` call.
- Reused the existing `POLL_TRIGGER_BUTTON_ID` constant for the zero-cooldown branch's new `id` attribute rather than introducing a second id, keeping one stable DOM contract across both branches.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 - Bug] Two pre-existing test_config_page.py checks false-positived against the new script's own text**
- **Found during:** Task 2 (writing `_poll_submit_script()` and the new test coverage the plan's Task 2 item 3 requires)
- **Issue:** `_poll_trigger_enabled_at_zero_cooldown()` (pre-existing, untouched by the plan's own instructions) and the plan's own required new check both used a bare `"disabled" in rendered` whole-document substring search to assert the zero-cooldown button carries no `disabled` HTML attribute. `_poll_submit_script()`'s own body legitimately contains the substring "disabled" as the JS property name in `btn.disabled = true;`, so both checks began failing the instant the new script was appended — a correct implementation tripping an over-broad pre-existing assertion, not a real regression.
- **Fix:** Rescoped both checks to extract the `<button ...>` tag itself via `re.search(r"<button\b[^>]*>", rendered)` and search for `"disabled"` only within that tag's text, not the whole rendered string.
- **Files modified:** `companion/test_companion_app.py` was not touched by this fix; `companion/test_config_page.py`'s two checks (`_poll_trigger_enabled_at_zero_cooldown` and the new zero-cooldown submit-affordance check) were updated.
- **Verification:** `server/.venv/bin/python3 companion/test_config_page.py` — 38/38 pass.
- **Committed in:** `5689ce1` (Task 2 commit)
