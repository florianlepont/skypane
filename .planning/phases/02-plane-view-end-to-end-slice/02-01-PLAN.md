## Phase Goal

**As a** person glancing at the frame on my wall, **I want to** see the plane that is using Orly runway 3 right now, **so that** the frame is a live, satisfying ambient window onto the airport next door rather than a static picture.

<locked_decisions>

Decisions this plan implements, and two the planner resolved for the phase. Later plans inherit both.

- **D-01** (locked, CONTEXT.md): plane detection is built on the free ADS-B aggregators (airplanes.live primary, adsb.fi secondary per the Phase 1 `aggregator-sufficient` verdict in `adsb-test/RESULTS.md`). No RTL-SDR, no local receiver, no schedule API. ROADMAP/PROJECT wording that still says "local ADS-B receiver" is known Phase 1 doc-drift, not a live decision.
- **D-04** (locked, CONTEXT.md): between flights, the last detected flight stays on screen. There is no waiting state and no artificial expiry.
- **D-P2-01** (planner-resolved, closes 02-RESEARCH.md Open Question 1 — multi-aircraft selection): when more than one aircraft is inside the runway-3 geofence in the same poll, select by a **total order**: (1) lowest effective altitude, where an on-ground aircraft (string `alt_baro` sentinel) has effective altitude `0`; (2) tie-break on smallest `seen_pos` (freshest position report); (3) tie-break on lexicographically smallest `hex`. Rationale: lowest-and-closest-to-the-ground is the aircraft actually committed to the runway right now, which is what "the plane using runway 3" means to a person looking at the frame; the two tie-breaks make the pick independent of the aggregator's array ordering, so the same snapshot always yields the same flight and the display never flickers between two simultaneous aircraft. Known limitation (accepted for v1, inherited from `adsb-test/runway3.json`'s own sourcing note): the bbox is not perfectly exclusive of the nearby 06/24 runway, so an occasional wrong-runway aircraft can win the selection.
- **D-P2-02** (planner-resolved, cross-cycle state): `poll_loop.py` is a systemd **oneshot** script, so it has no in-process memory between cycles. Cross-cycle state that 02-RESEARCH.md describes as "in-process" (last detected flight, last confirmed runway configuration, enrichment cache) lives in `server/state/poll_state.json`, written with the same tmp-write-then-`os.replace()` pattern as `byos_server.py`'s `save_state()`. An unreadable or malformed state file is treated as "empty" (Empty state), never as a crash. D-04 is satisfied structurally: when a cycle detects nothing, `panel.bin` is simply not rewritten, so the previous panel keeps being served.
- **D-P2-03** (planner-resolved, closes the 02-UI-SPEC.md "panel RGB values unverified" blocker): the Spectra 6 sRGB swatch values are **render-internal only**. What the device receives is the six PROTOCOL.md nibble codes (`0x0` black, `0x1` white, `0x2` yellow, `0x3` red, `0x5` blue, `0x6` green), which are already fixed and verified. The Pillow palette RGB triples exist solely so `ImageDraw` has a palette to attach to and so an optional developer preview PNG is viewable; they never cross the wire. Therefore no hardware measurement blocks implementation — but the palette table carries a comment recording that the RGB triples are nominal, and any preview output is labelled approximate. Real-panel colour fidelity is verified on glass in 02-05.
</locked_decisions>
