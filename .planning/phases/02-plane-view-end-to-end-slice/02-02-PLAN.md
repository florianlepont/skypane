**As a** person glancing at the frame on my wall, **I want to** see the plane that is using Orly runway 3 right now, **so that** the frame is a live, satisfying ambient window onto the airport next door rather than a static picture.

This plan advances that slice from "which flight" to "which flight, and which way it is going."

<locked_decisions>

- **D-03** (locked, CONTEXT.md): departure vs. arrival is inferred directly from the ADS-B track data already collected — climbing = departure, descending = arrival. No external NOTAM or runway-configuration feed. Exact thresholds were left to the planner and are fixed below.
- **D-P2-04** (planner-resolved thresholds for D-03, from Phase 1's real sample data): use a **deadband**, not a zero crossing. `vertical_rate_fpm >= +200` → `"departing"`. `vertical_rate_fpm <= -200` → `"arriving"`. Anything strictly between, or a missing/non-numeric reading, **holds the last confirmed state** rather than re-inferring. Evidence: the real observations of `hex` `440cb1` / `EJU84YF` (committed as `server/fixtures/track_arrival_440cb1.json`) show `-640` followed by two consecutive `+48` readings on an aircraft that is unambiguously landing — the Mode-S vertical-rate field is quantised in 64 ft/min steps and genuinely goes near zero during the flare. A `+200` deadband sits above that observed `+48` noise floor and above 3× the quantisation step. Heading-based "toward/away" inference from D-03's wording is **deliberately not implemented**: vertical rate alone cleanly separated every real track in Phase 1's sample, and adding a second, unvalidated signal would add a failure mode without adding evidence. If real-world QA in 02-05 shows vertical rate alone is insufficient, heading is the documented next lever.
</locked_decisions>

<assumption id="A-02-02-01" severity="medium">
**The departure-side threshold is inferred by symmetry, not observed.** Every one of the 20 real tracked aircraft in Phase 1's ~92-minute sample was a descending arrival — runway 3 was in arrival configuration for the entire sampled window (02-RESEARCH.md Open Question 2). The `-200 ft/min` arrival threshold is therefore well evidenced by real data; the `+200 ft/min` departure threshold is **derived by symmetry from the descent-side data and has never been checked against a real climbing runway-3 track.**

Consequences that must not be lost:
1. `server/plane/runway_config.py`'s module docstring states this asymmetry explicitly, naming `CLIMB_THRESHOLD_FPM` as provisional and `DESCEND_THRESHOLD_FPM` as data-backed.
2. `server/test_runway_config.py` marks its climb-side cases as **synthetic** in their assertion messages, so a green suite is never misread as departure-side validation.
3. 02-05's real-hardware QA checkpoint carries an explicit item: observe at least one real runway-3 departure end to end and confirm the panel shows `DEPARTING`. That observation, not this test suite, is what retires this assumption.
</assumption>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| aggregator `vertical_rate` field → runway-state inference | An untrusted, noisy, quantised third-party numeric field drives which colour the entire panel becomes. |
| `poll_state.json` on disk → next poll cycle | Cross-cycle state read back from a file that a previous crashed cycle may have left in an unexpected shape. |
| Vendored Lucide PNG masks → render pipeline | Third-party static assets loaded and composited at render time. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-02-02-01 | Tampering | `runway_config.infer_runway_config` fed a malformed or noisy `vertical_rate` | medium | mitigate | Explicit `isinstance` checks with a bool rejection before the numeric comparison; anything non-numeric holds the last state and never raises (ASVS V5). The `±200 ft/min` deadband absorbs the real `+48 ft/min` flare artefact captured in `track_arrival_440cb1.json`. Asserted by the type-hostile cases in `test_runway_config.py`. |
| T-02-02-02 | Tampering | `poll_state.json` truncated, corrupt, or hand-edited | medium | mitigate | Written only via tmp-write + `os.replace()` (D-P2-02). Read path catches `(OSError, ValueError)` and returns empty state, matching `byos_server.py`'s `load_state()`. A corrupt state file degrades to the Empty panel, never to a crash-loop or a confidently wrong colour. |
| T-02-02-03 | Spoofing | An aircraft's ADS-B vertical rate is spoofed or erroneous, producing a wrong DEPARTING/ARRIVING call | low | accept | Accepted for v1: ADS-B is an unauthenticated broadcast protocol and this project deliberately consumes public aggregator feeds (D-01).
