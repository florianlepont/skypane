<locked_decisions>

- **PROJECT.md hosting constraint (locked):** an always-on small cloud VPS, never a home server and never a scale-to-zero tier, because the device must always find a reachable server.
- **D-P2-06** (research-resolved, infrastructure specifics — CONTEXT.md left these to Claude's discretion): Hetzner CX22 (2 vCPU / 4 GB / 40 GB NVMe, roughly EUR 4.35/mo) in Falkenstein or Nuremberg, Ubuntu 24.04 LTS, systemd service plus timer for the poll loop, a second systemd service for `byos_server.py`, and Caddy for automatic Let's Encrypt TLS. No Docker for the server (unlike Phase 1's containerised firmware build), no FastAPI, no APScheduler, no `python-dotenv` — systemd's native `EnvironmentFile=` covers secrets and systemd timers cover scheduling, per 02-RESEARCH.md's Don't Hand-Roll table.
- **D-P2-07** (planner-resolved, deviating deliberately from 02-RESEARCH.md's recommendation): 02-RESEARCH.md's Common Pitfall 2 recommends changing `byos_server.py`'s hardcoded `image_url` scheme to `https://` unconditionally. **This plan makes it a CLI flag instead**, `--image-url-scheme` defaulting to `http`. Reason the research could not see: Phase 1 plans 01-06, 01-07 and 01-08 are still unexecuted and drive the device against the **local** stub over plain HTTP on the LAN. An unconditional `https://` would break them the moment the hardware arrives. The flag closes the production gap (the systemd unit passes `https`) while leaving the vendored default byte-compatible with the Phase 1 flow, and it makes the fix testable locally without any TLS setup — an unconditional change is only assertable against a deployed Caddy instance.
- **02-RESEARCH.md Package Legitimacy note (locked):** Caddy is installed from the **official Caddy apt repository** (or its signed static binary), never from npm. An unrelated, irrelevant low-download npm package also carries the name `caddy` and must not be installed under any circumstance.
</locked_decisions>
