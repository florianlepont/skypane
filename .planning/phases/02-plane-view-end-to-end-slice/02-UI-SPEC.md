# Phase 02 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

**Revision 1 note (2026-08-05):** This is a structural revision of the original draft. The original contract was a text-first "departure board" (top mode badge, big flight-number hero text, route line, airline line — no aircraft artwork). After reviewing a mockup, the user compared it against **flightportrait.com** — the reference project this device's wake→poll→display→sleep architecture is explicitly built on (`.claude/CLAUDE.md` "Project" section) — whose actual product is an illustrated poster: a solid-color background with a detailed side-profile aircraft silhouette as the visual centerpiece, with small caption text (airline, route, altitude/speed) stacked underneath. The user chose to bring this device's plane view closer to that composition: **the aircraft silhouette becomes the dominant visual centerpiece, and flight number / route / airline are demoted to supporting captions below it.** This revision replaces the "Layout & Composition," "Spacing Scale," "Typography," and "Color" sections' zone/role assignments accordingly, and adds a vendored silhouette asset to "Design System." The palette, copywriting contract, and registry-safety sections are otherwise unchanged from the original draft.

**Revision 2 note (2026-08-05):** Second structural revision. The Revision 1 silhouette-centerpiece composition above still didn't read as a "poster" the way flightportrait.com's own artwork does when compared side-by-side again. Investigation into flightportrait's public GitHub repo (`flightportrait/frame`, linked from `stub-server/VENDOR.md`) confirmed why it couldn't be replicated directly: **the poster renderer is explicitly closed source** — the repo's own README states *"FlightPortrait's cloud, mobile app, and the poster renderer are separate, closed components — this repo is everything the device speaks and runs."* The public repo contains only device firmware and a minimal reference server that serves an already-rendered image; there is no vendorable rendering code or asset pipeline to copy. **This composition is therefore an independent design decision reverse-engineered from flightportrait.com's public visual reference (screenshots), not a copy of their implementation** — see the "Source-code investigation finding" callout in Design System below. The actual visual difference identified: flightportrait's poster uses a **full-bleed, solid, saturated color field as the entire background**, with the aircraft artwork rendered in a light contrasting color on top — not a white background with a small colored badge in the corner (which is what Revision 1 still did: the silhouette was black-on-white, and blue/green were confined to a small top badge, so it still read as "a departure board with a picture" rather than "a poster"). This revision inverts the color contract for the two active states: **the departing/arriving accent color (Blue/Green) becomes the full-bleed dominant background field, White becomes the secondary color for the silhouette and all caption text, and Black drops out of the active-state palette entirely** (see Color section for the full state-scoped rationale). The Empty/neutral state (no flight detected) is unchanged — it has no accent color to represent, so it stays White-dominant/Black-secondary. This revision replaces the Design System, Layout & Composition, and Color sections' role assignments accordingly, and adds a legibility flag to Typography. The copywriting contract, spacing token *values*, silhouette shape/vendoring, registry safety, and D-03/D-04 state logic are unchanged from Revision 1.

**Scope note:** This is not a web/React UI. The "frontend" here is a Python/Pillow raster-rendering pipeline on the server that produces a single 960,000-byte, 4-bit-per-pixel indexed-color panel image (`docs/PROTOCOL.md` §1), which the device blits directly to a 13.3" E Ink Spectra 6 panel. There is no browser, no DOM, no component tree, and no user input during this phase (the physical button ships in Phase 4). The shadcn initialization gate therefore does not apply — confirmed by scanning the repo for `components.json`/`tailwind.config.*`/`package.json`: none exist, and the stack is Python (`stub-server/byos_server.py`), not React/Next/Vite. This contract instead specifies the fixed 6-color hardware palette, the type/spacing scale for a 1200×1600 @ ~150 PPI portrait panel viewed from a few feet on a wall or desk, and the exact copy for every state PLANE-01/02/03 can produce.

**Source-code investigation finding (Revision 2, binding):** flightportrait's actual poster-rendering implementation was checked directly against `flightportrait/frame` on GitHub (the repo linked from this project's `stub-server/VENDOR.md`, and the upstream reference for this device's wake→poll→display→sleep architecture per `.claude/CLAUDE.md`). The repo's own README states plainly: *"FlightPortrait's cloud, mobile app, and the poster renderer are separate, closed components — this repo is everything the device speaks and runs."* The public repo contains only device firmware and a minimal reference protocol server (`stub-server/byos_server.py`, already vendored in this project) that serves an already-rendered image — there is no vendorable rendering code, layout logic, or asset pipeline for the poster artwork itself. **This means the full-bleed color-field composition specified below is an independent design decision reverse-engineered from flightportrait.com's public visual reference (screenshots compared by the user), not a copy of their implementation.** Document this clearly for any future contributor who goes looking for "the flightportrait renderer" in that repo — it does not exist there; only firmware and the minimal reference server do.

**Rendering rule (hardware-specific, binding — same mechanism as Revision 1, now applies across more color pairs):** disable anti-aliasing (or explicitly threshold edges to the two flat legal colors in use) for **all shapes and glyphs** before quantizing to the Spectra 6 palette — this now includes White-on-Blue and White-on-Green edges in the Departing/Arriving states, not just Black-on-White. AA'd grayscale edges dither into visible halftone noise on this panel regardless of which two palette colors border each other; flat, hard-edged shapes do not. Reserve Floyd-Steinberg dithering (Pillow's `Image.quantize(..., dither=Image.FLOYDSTEINBERG)`) for any future photographic content only — every state in this phase is flat text + flat silhouette + solid full-bleed fill, quantized with `dither=Image.NONE` against the exact 6 legal palette entries.

**Explicit hardware constraint (why this isn't flightportrait's poster art, unchanged from Revision 1):** flightportrait's print poster renders the aircraft in full photographic/gradient airline-livery color. This device's panel is a flat, hard-edged, 6-color (Spectra 6) e-ink display with dithering disabled — it **cannot** reproduce that photorealistic livery art. The silhouette here necessarily renders as a **flat shape in a single legal palette color** — White in the Departing/Arriving states, not shown at all in the Empty state (see Color section) — not a colored livery illustration. This is a deliberate, hardware-forced simplification of the flightportrait reference, not an oversight.

**Legibility flag (Revision 2, new — flagged rather than assumed):** White text/silhouette on a full-bleed saturated Blue or Green field is a new contrast pairing this phase didn't previously need (Revision 1 only used Black-on-White). Spectra 6's six pigments are formulated by the manufacturer to be visually distinct from each other at full saturation, which is a reasonable basis to expect strong value contrast between White and Blue/Green — but **this is unverified for this specific panel** and should not be assumed correct sight-unseen. This is the same open item already flagged below ("Exact panel RGB reference values are unverified") — resolving it also resolves this legibility question. Confidence: LOW until spot-tested on physical hardware; treat as a Phase 2 execution/QA checkpoint, not a blocking design question — there is no legal 6-color alternative to White for content on a Blue/Green field, so the design has no fallback pairing to switch to. If contrast proves insufficient on real hardware, the fix is a bolder stroke/weight or a thin outline treatment on the text, not a color change.

**Exact panel RGB reference values are unverified** — PROTOCOL.md §1 fixes only the nibble codes (`0x0` black, `0x1` white, `0x2` yellow, `0x3` red, `0x5` blue, `0x6` green), not their sRGB values. Confirm the true swatch RGB against the Waveshare `EPD_13in3e` reference driver or panel datasheet before implementation; do not guess hex values into the render code. Confidence: LOW until sourced.

## Spacing Scale

Panel is 1200×1600 px, ~150 PPI (13.3" diagonal, portrait), viewed from a few feet on a wall or desk — denser and physically larger than a typical web viewport, so the standard 8-point scale is scaled up ~2-3x to preserve legible physical spacing. Still strictly multiples of 4. **Token values are unchanged since Revision 1 and unchanged again in Revision 2 — this revision is a color/composition change, not a spacing change.** The "Usage" column below is updated only to drop references to the now-removed mode badge rectangle (see Layout & Composition's "Mode badge removed").

| Token | Value | Usage (Revision 2) |
|-------|-------|-------|
| xs | 8px | Icon-to-label gap within the state label row |
| sm | 16px | Gap between the flight-number caption and the route line (tight caption cluster) |
| md | 32px | Gap between the route line and the airline line |
| lg | 64px | Panel content margin (all four edges) and section padding |
| xl | 96px | Gap between the silhouette centerpiece and the caption cluster below it |
| 2xl | 128px | Gap between the state label row and the silhouette centerpiece |
| 3xl | 192px | Minimum white space above and below the silhouette's own bounding box within its zone — deliberate poster-style breathing room around the centerpiece, consistent with flightportrait's illustration-on-solid-field composition |

Exceptions: the lg (64px) content margin is inviolable on all four edges regardless of content length — nothing may render under the physical bezel.

## Layout & Composition

*(Non-template addition: a raster full-bleed layout needs spatial zones the base template doesn't capture. Included because the planner/executor have no other spatial source of truth for this phase.)*

Canvas: 1200w × 1600h, portrait, full-bleed, hard-edged rectangles and shapes only (no rounded corners, no soft/curved decorative elements beyond the silhouette itself — curved edges dither poorly on Spectra 6 and the silhouette's edges are handled by the AA-disabled rendering rule above). Content safe-box after the lg (64px) margin: 1072w × 1472h.

**Hierarchy (Revision 2, unchanged from Revision 1):** the aircraft silhouette is the primary visual anchor — the first thing the eye lands on, before any text. Flight number, route, airline, and state are all supporting captions arranged around/below it. **What changes in Revision 2 is composition, not hierarchy:** the entire canvas background now carries the departing/arriving state color, so the poster reads as "a colored field with a plane and captions on it" — matching flightportrait's actual full-bleed composition — rather than "a white card with a plane and a small colored tag."

**Mode badge removed (Revision 2, explicit decision, not left ambiguous):** Revision 1's small filled-rectangle badge (colored background + icon + label, top-anchored) is **removed entirely**, not kept-but-restyled. Rationale: a badge's whole function is to stand out by contrasting against its surroundings — that only worked when the surroundings were neutral (Revision 1's white canvas). Once the *entire* background is the state color (this revision), a same-color badge would be invisible (zero contrast against its own background), and a different-color badge would require introducing a color outside the two the state can legally use, breaking the "one dominant state color per screen" contract. It's also now genuinely redundant: the full-bleed field communicates departing/arriving state far more prominently than a small corner badge ever did, and the silhouette's horizontal mirroring (below) already provides a second, non-color-dependent cue. The state label **text itself is retained** — it's still useful as an explicit, literate confirmation of state, and it's required by the Copywriting Contract's "Primary readout" row — but it's repurposed as plain White text + White icon glyph directly on the color field, with no filled rectangle behind it.

Top-to-bottom zones, in the safe-box (Departing/Arriving states):

1. **State label** (top-anchored, supporting element, no background fill — see "Mode badge removed" above) — `plane-takeoff` or `plane-landing` Lucide glyph (White fill) + Label-size text (`DEPARTING`/`ARRIVING`, White), per D-03's inferred state, never both at once. Occupies roughly the same vertical footprint Revision 1's badge did (~96px), but as bare icon+text rather than a filled rectangle.
2. **2xl (128px) gap**
3. **Aircraft silhouette centerpiece** — the vendored passenger-jet side-profile SVG (see Design System above), rendered as a flat fill in **White** (Secondary role in the active states — see Color section; size/position unchanged from Revision 1: max ~900px wide within the 1072px safe box, ~220-260px tall preserving aspect ratio, horizontally centered, minimum 3xl (192px) white-space padding above/below within its zone). **Mode reinforcement (non-color-dependent, unchanged from Revision 1):** mirror the silhouette horizontally by state — nose pointing right for DEPARTING (reads as climbing away), nose pointing left for ARRIVING (reads as descending in). This remains a second, non-color-dependent visual cue beyond the state label, now reinforcing rather than duplicating the full-bleed color signal.
4. **xl (96px) gap**
5. **Flight number caption** (e.g. `AF1380`) — Heading size, bold, **White**, horizontally centered. Remains the largest text element, subordinate to the silhouette centerpiece above it.
6. **sm (16px) gap**
7. **Route line** — a Label-size, uppercase, tracked prefix ("TO" for departing / "FROM" for arriving) followed by Body-size destination or origin city name (sentence case), **White**. **Clarification (resolves RESEARCH.md Open Question 3):** the destination/origin city comes from the same single D-02 enrichment lookup (keyed by callsign) as the airline name — there is no scenario where one resolves and the other doesn't. On enrichment failure this entire zone (prefix + city) is omitted, not rendered empty or with a placeholder.
8. **md (32px) gap** — omitted along with the Route line on enrichment failure (see above); the Airline line's fallback copy sits directly where the Airline line normally would, not doubled up with an empty Route line above it.
9. **Airline line** — Body size, regular weight, **White** (e.g. "Air France"). On enrichment failure, this line is replaced by the fallback copy in the Copywriting Contract below (also rendered White), rather than left blank. This fallback line stands alone — it is not paired with a Route line above it (see zone 7 clarification).
10. Remaining space is empty — filled with the full-bleed state color (Blue/Green), not white space; deliberate negative space within the poster field, consistent with the "ambient piece" core value and with flightportrait's own solid-field-plus-illustration composition. This is not a dashboard and should not be filled with filler content.
11. **Bottom-anchored static tag** — Label size, **White**, e.g. `ORY · RWY 3`. Does not change per flight; reinforces place/context at a glance. Content unchanged from Revision 1.

**Empty/neutral state layout (unchanged from Revision 1):** White full-bleed background, Black text, no silhouette, no state label/icon — there is no flight yet to depict or describe. See the Copywriting Contract's Empty state rows and the Color section's Empty/Neutral State table below.

**What did NOT change from Revision 1:** the state label's position (top-anchored), the route-line prefix convention (TO/FROM), the airline-line fallback behavior, the bottom static tag's content, the silhouette's size/mirroring logic, and the "no artificial expiry, last flight persists" behavior (D-04) — only the state label's presentation (bare text/icon vs. filled badge) and every foreground element's ink color (White vs. Black) changed in this revision.

## Typography

**Reduced from 4 to 3 declared sizes** (still within the template's required 3-4 range) — the original draft's Display size (160px) was the flight-number hero text; now that the silhouette is the primary visual anchor and the flight number is a supporting caption, no element on the panel needs to be larger than Heading size. Display is dropped rather than kept-but-unused, to avoid an ambiguous unused role in the contract.

| Role | Size | Weight | Line Height |
|------|------|--------|-------------|
| Label | 36px | 700 (Bold) | 1.2 |
| Body | 56px | 400 (Regular) | 1.3 |
| Heading | 88px | 700 (Bold) | 1.2 |

Role usage (revised):

- **Label** (uppercase, widened letter-spacing — Pillow: manual glyph-advance widening, no native tracking API): state label text (`DEPARTING`/`ARRIVING`, Revision 2: no longer inside a badge — see Layout & Composition); the "TO"/"FROM" route-line prefix; the bottom static tag (`ORY · RWY 3`).
- **Body** (sentence case): the route line's destination/origin city name; the airline line (including its "Route unavailable" fallback copy).
- **Heading**: the flight number caption only — the single largest text element on the panel, visually subordinate to the silhouette centerpiece above it.

**Color per state (Revision 2, cross-reference only — full contract lives in the Color section below):** weight/size/line-height are unchanged across all three display states; only the ink color swaps per state. All three type roles render **Black** on the Empty state's White background, and **White** on the Departing/Arriving states' Blue/Green full-bleed background. See the Design System section's "Legibility flag" above for the open verification item on White-on-saturated contrast — that flag applies to every role in this table, not just one.

## Color

Fixed 6-color Spectra 6 hardware palette (`docs/PROTOCOL.md` §1) — the contract here is *which of the 6 legal colors is used for which role*, not a free hex choice. **Revision 2 restructures this section: color roles are now defined per display state, not as one fixed global table** — see rationale below, then the three state tables.

### Why state-scoped instead of one fixed global assignment

The standard 60/30/10 dominant/secondary/accent rule assumes a single, mostly-static surface (e.g. a white card UI where an accent color marks a few interactive elements). This phase's canvas has no such single surface — it fully repaints between three mutually exclusive states (Empty, Departing, Arriving), and Revision 2's entire point is that the state color becomes the *full-bleed background field*, not a 10%-budget accent. Applying one fixed 60/30/10 table across all three states would either force the state color to stay a minority presence (exactly what Revision 1 got wrong, per the user's flightportrait comparison) or force White/Black to be labeled "dominant" even when the panel is genuinely a solid saturated color field. **What's preserved is the underlying principle — one clearly dominant surface color, one clear secondary for content, minimal-to-no use of a third color — not the literal percentages, which necessarily invert once the state color goes full-bleed.** Each table below is a complete, self-contained color contract for one state; only one state is ever on screen at a time (per D-03/D-04), so there is no risk of these tables conflicting with each other at render time.

### Empty / Neutral State (no aircraft detected since server start)

Unchanged from Revision 1 — there is no flight yet, so there is no accent/state color to represent.

| Role | Value | Usage |
|------|-------|-------|
| Dominant | White (nibble `0x1`) | Full-bleed background canvas |
| Secondary | Black (nibble `0x0`) | Empty-state heading + body text only — no silhouette, no state label/icon (nothing detected yet, nothing to depict) |
| Accent | not applicable | No flight state exists yet to color-code |

### Departing State (full-bleed poster field)

| Role | Value | Usage |
|------|-------|-------|
| Dominant (full-bleed) | Blue (nibble `0x5`) | Entire background canvas — the primary visual signal for "departing," reinforced (not duplicated) by the silhouette's nose-right mirroring |
| Secondary | White (nibble `0x1`) | Aircraft silhouette fill, state label icon + text (`DEPARTING`), flight number caption, route line, airline line, bottom static tag — every foreground element |
| Tertiary (Black) | not used | See "Why Black drops out of the active states" below |

### Arriving State (full-bleed poster field)

| Role | Value | Usage |
|------|-------|-------|
| Dominant (full-bleed) | Green (nibble `0x6`) | Entire background canvas — the primary visual signal for "arriving," reinforced (not duplicated) by the silhouette's nose-left mirroring |
| Secondary | White (nibble `0x1`) | Aircraft silhouette fill, state label icon + text (`ARRIVING`), flight number caption, route line, airline line, bottom static tag — every foreground element |
| Tertiary (Black) | not used | See below |

### Why Black drops out of the active states

Revision 1 kept the silhouette and all text in Black regardless of state, reasoning that a large Black shape would blow past a 10%-accent budget if colored instead. Revision 2 removes that constraint by making the *state* color the background rather than a budgeted accent — so the question becomes purely "what color makes foreground content most legible against a solid Blue or Green field," and White is both the only remaining legal palette color with strong expected value contrast against saturated Blue/Green, *and* the same color across both active states, which keeps the Departing/Arriving contracts symmetric and avoids readers having to learn two different foreground-color rules. Black-on-Blue or Black-on-Green would have weak value contrast (dark-on-dark) on a saturated field and is explicitly not used for any foreground element in the active states. Black isn't banned outright from ever appearing — the Empty state above still uses it — it's specifically unused whenever the panel is in a full-bleed state-color field. (See the Design System section's "Legibility flag" for the caveat that White-on-saturated contrast is expected but not yet hardware-verified.)

### Reservation language (Revision 2 — replaces Revision 1's single "Accent reserved for" line)

In the Departing/Arriving states, Blue/Green is reserved for **the full canvas background field only** — it is the sole means of representing state, used nowhere else (not text, not the silhouette). White is reserved for **foreground content only** in those states — it is never used as a background fill. This is the inverse of Revision 1's reservation (where Blue/Green was reserved for a small badge and White was the background) — a genuine role swap, not an additive change. In the Empty state, White remains the background and Black remains the only foreground color, unchanged from Revision 1.

**Cross-phase reservation note (unchanged from Revision 1):** Yellow (`0x2`) and Red (`0x3`) are intentionally unused in this phase's palette across all three states, held in reserve for Phase 3's disruption banner (RER-03) and Phase 4's low-battery indicator (DEVICE-04) so those later semantic colors don't collide with this phase's departure/arrival color-coding.

**Destructive:** not applicable — no destructive actions exist on a passive, buttonless display this phase.

## Copywriting Contract

No clickable UI exists this phase (passive e-ink display, no buttons until Phase 4), so "Primary CTA" is reinterpreted as the single most important glanceable readout. **The copy strings themselves are unchanged from Revision 1** (this revision only changed color/composition, not wording). Two rows are relabeled/clarified below because the visual element they described (the "mode badge") no longer exists as a distinct object after Revision 2 — see Layout & Composition — and one row's fixed "black" color note is now state-dependent per the Color section; the copy text in each row is otherwise identical to Revision 1.

| Element | Copy |
|---------|------|
| Primary readout (state label — Revision 2: rendered as plain icon+text, not inside a badge; see Layout & Composition) | `DEPARTING` or `ARRIVING` — exact uppercase string, mutually exclusive, per D-03's inferred runway configuration |
| Empty state heading (no aircraft ever detected since server start / cache empty) | "Watching Runway 3" |
| Empty state body | "No aircraft detected yet — the display updates the moment one is." |
| Empty state — silhouette | **Not shown.** The empty state remains a text-only composition (no silhouette, no state label) — there is no flight yet to depict, so nothing renders in the silhouette zone; the panel shows only the empty-state heading/body, vertically centered, on white (Black text — see Color section's Empty/Neutral State table). |
| Between-flights state | Not a distinct visual state — per D-04, the last detected flight (silhouette, flight number, route, airline, and state label together) stays on screen indefinitely; no separate "waiting" copy or blank silhouette is ever shown once at least one flight has rendered |
| Error / partial-data state (D-02 enrichment lookup fails or returns no route for a real detected callsign) | **Both** the Route line (zone 7) and its preceding md gap (zone 8) are omitted — not rendered empty, not rendered with a placeholder — and the Airline line (zone 9) alone falls back to: "Route unavailable" (Body size, regular, **White** in the Departing/Arriving states / Black in the Empty state — see Color section). Resolves RESEARCH.md Open Question 3: the destination/origin city and the airline name come from the same single D-02 lookup keyed by callsign, so a lookup failure always takes out both fields together — there is no partial case where one resolves and the other doesn't. | Destructive confirmation | not applicable — no destructive actions exist on this passive display this phase |
