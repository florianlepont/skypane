# Phase 02 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

**Revision note (2026-08-05):** This is a structural revision of the original draft. The original contract was a text-first "departure board" (top mode badge, big flight-number hero text, route line, airline line — no aircraft artwork). After reviewing a mockup, the user compared it against **flightportrait.com** — the reference project this device's wake→poll→display→sleep architecture is explicitly built on (`.claude/CLAUDE.md` "Project" section) — whose actual product is an illustrated poster: a solid-color background with a detailed side-profile aircraft silhouette as the visual centerpiece, with small caption text (airline, route, altitude/speed) stacked underneath. The user chose to bring this device's plane view closer to that composition: **the aircraft silhouette becomes the dominant visual centerpiece, and flight number / route / airline are demoted to supporting captions below it.** This revision replaces the "Layout & Composition," "Spacing Scale," "Typography," and "Color" sections' zone/role assignments accordingly, and adds a vendored silhouette asset to "Design System." The palette, copywriting contract, and registry-safety sections are otherwise unchanged from the original draft.

**Scope note:** This is not a web/React UI. The "frontend" here is a Python/Pillow raster-rendering pipeline on the server that produces a single 960,000-byte, 4-bit-per-pixel indexed-color panel image (`docs/PROTOCOL.md` §1), which the device blits directly to a 13.3" E Ink Spectra 6 panel. There is no browser, no DOM, no component tree, and no user input during this phase (the physical button ships in Phase 4). The shadcn initialization gate therefore does not apply — confirmed by scanning the repo for `components.json`/`tailwind.config.*`/`package.json`: none exist, and the stack is Python (`stub-server/byos_server.py`), not React/Next/Vite. This contract instead specifies the fixed 6-color hardware palette, the type/spacing scale for a 1200×1600 @ ~150 PPI portrait panel viewed from a few feet on a wall or desk, and the exact copy for every state PLANE-01/02/03 can produce.

## Design System

| Property | Value |
|----------|-------|
| Tool | none — not a component-based web project; server renders a raw raster buffer with Pillow |
| Preset | not applicable |
| Component library | none — custom Pillow drawing primitives (text blocks, filled rects, glyph masks, single-path silhouette fills) |
| Icon library | Lucide (MIT license), static SVG → rasterized at render time: `plane-takeoff` (departing) and `plane-landing` (arriving), used only inside the small mode badge. No other Lucide icons this phase. |
| Aircraft silhouette (NEW — centerpiece asset) | **freesvg.org / OpenClipart SVG ID 178507, "Passenger aircraft silhouette clip art"** — a generic modern passenger-jet side profile (fuselage, swept wings, tail, engine pod), released **Public Domain / CC0**, originally derived by OpenClipart from a public-domain drawing on Wikimedia Commons. Chosen over the alternative candidates found in research — OpenClipart SVG ID 18321 ("generic plane silhouette," CC0, cruder amateur-drawn outline) and SVG ID 37085 ("airplane silhouette," CC0, but depicts a **propeller/biplane**, thematically wrong for commercial ORY departures) — because it is the only CC0 candidate found that reads clearly as a modern commercial jet in profile, matches the flight data this phase actually displays (Airbus/Boeing-class airliners at a major international airport), and is a single generic shape, not per-airline-livery art (per-model/per-livery vector art is explicitly out of scope for a hobby project's palette and asset budget — every flight this phase renders the same silhouette shape, only the caption text below it changes). Vendor the source SVG into `server/assets/icons/aircraft-silhouette.svg` with a `VENDOR.md` provenance note (source URL, SVG ID, license, retrieval date), following the vendoring discipline already established in `stub-server/VENDOR.md`. **Executor note:** freesvg/OpenClipart traced artwork sometimes carries stray anchor points or overly fine detail that won't hold up at a flat single-color fill and small render size — if the vendored path doesn't simplify cleanly, trace/simplify a cleaner single-path version that preserves the same recognizable proportions (nose, wing sweep, tail, engine pod) rather than switching to a different, unlicensed source. |
| Font | Inter (SIL OFL 1.1), static TTF, Regular 400 + Bold 700. Vendor `Inter-Regular.ttf` and `Inter-Bold.ttf` into `server/assets/fonts/` with a VENDOR.md provenance note, following the vendoring discipline already established in `stub-server/VENDOR.md` |

**Rendering rule (hardware-specific, binding):** disable anti-aliasing (or explicitly threshold edges to pure black/white) for **both glyphs and the silhouette** before quantizing to the Spectra 6 palette. AA'd grayscale edges — text or curved silhouette outlines alike — dither into visible halftone noise on this panel; flat, hard-edged black-on-white shapes do not. Reserve Floyd-Steinberg dithering (Pillow's `Image.quantize(..., dither=Image.FLOYDSTEINBERG)`) for any future photographic content only — this phase's layout is flat text + flat silhouette + solid fills and should be quantized with `dither=Image.NONE` against the exact 6 legal palette entries.

**Explicit hardware constraint (why this isn't flightportrait's poster art):** flightportrait's print poster renders the aircraft in full photographic/gradient airline-livery color. This device's panel is a flat, hard-edged, 6-color (Spectra 6) e-ink display with dithering disabled — it **cannot** reproduce that photorealistic livery art. The silhouette here necessarily renders as a **flat shape in a single legal palette color** (Black — see Color section below), not a colored livery illustration. This is a deliberate, hardware-forced simplification of the flightportrait reference, not an oversight.

**Exact panel RGB reference values are unverified** — PROTOCOL.md §1 fixes only the nibble codes (`0x0` black, `0x1` white, `0x2` yellow, `0x3` red, `0x5` blue, `0x6` green), not their sRGB values. Confirm the true swatch RGB against the Waveshare `EPD_13in3e` reference driver or panel datasheet before implementation; do not guess hex values into the render code. Confidence: LOW until sourced.

## Spacing Scale

Panel is 1200×1600 px, ~150 PPI (13.3" diagonal, portrait), viewed from a few feet on a wall or desk — denser and physically larger than a typical web viewport, so the standard 8-point scale is scaled up ~2-3x to preserve legible physical spacing. Still strictly multiples of 4. **Token values are unchanged from the original contract; only the "Usage" column changes to reflect the new silhouette-centerpiece composition:**

| Token | Value | Usage (revised) |
|-------|-------|-------|
| xs | 8px | Icon-to-label gap inside the mode badge |
| sm | 16px | Badge internal padding; gap between the flight-number caption and the route line (tight caption cluster) |
| md | 32px | Gap between the route line and the airline line |
| lg | 64px | Panel content margin (all four edges) and section padding |
| xl | 96px | Gap between the silhouette centerpiece and the caption cluster below it |
| 2xl | 128px | Gap between the mode badge zone and the silhouette centerpiece |
| 3xl | 192px | **Reassigned from "reserved for future use" to active use:** minimum white space above and below the silhouette's own bounding box within its zone — deliberate poster-style breathing room around the centerpiece, consistent with flightportrait's illustration-on-solid-field composition |

Exceptions: the lg (64px) content margin is inviolable on all four edges regardless of content length — nothing may render under the physical bezel.

## Layout & Composition

*(Non-template addition: a raster full-bleed layout needs spatial zones the base template doesn't capture. Included because the planner/executor have no other spatial source of truth for this phase.)*

Canvas: 1200w × 1600h, portrait, full-bleed, hard-edged rectangles and shapes only (no rounded corners, no soft/curved decorative elements beyond the silhouette itself — curved edges dither poorly on Spectra 6 and the silhouette's edges are handled by the AA-disabled rendering rule above). Content safe-box after the lg (64px) margin: 1072w × 1472h.

**Hierarchy (revised):** the aircraft silhouette is now the primary visual anchor — the first thing the eye lands on, before any text. Flight number, route, airline, and mode are all supporting captions arranged around/below it, matching flightportrait's illustration-plus-caption-stack composition rather than the original text-first departure-board layout.

Top-to-bottom zones, in the safe-box:

1. **Mode badge** (top-anchored, supporting element — no longer the primary readout) — filled rectangle, ~96px tall (reduced from the original draft's 120px, since it now reads as a small supporting tag rather than the top of a text-dominant hierarchy), containing the takeoff/landing icon + label text (Label size), background = Accent-Departing (blue) or Accent-Arriving (green) per D-03's inferred state, never both at once.
2. **2xl (128px) gap**
3. **Aircraft silhouette centerpiece** — the vendored passenger-jet side-profile SVG (see Design System above), rendered as a flat fill in Black (Secondary role — see Color section; **never** in the Accent blue/green, for reasons explained there). Scaled to a maximum width of ~900px within the 1072px safe box (leaving ~86px of horizontal breathing room on each side even at max width), preserving the source's aspect ratio. Passenger-jet side-profile silhouettes are wide-and-short (roughly 3.5:1–4:1 width:height), so at 900px wide this renders roughly 220–260px tall. Horizontally centered. Padded with a minimum of 3xl (192px) of white space above and below the shape within this zone (see Spacing Scale). **Mode reinforcement (non-color-dependent):** mirror the silhouette horizontally by state — nose pointing right for DEPARTING (reads as climbing away), nose pointing left for ARRIVING (reads as descending in). This gives the departing/arriving distinction a second, non-color-dependent visual cue beyond the small badge, consistent with not relying on color alone to convey state.
4. **xl (96px) gap**
5. **Flight number caption** (e.g. `AF1380`) — Heading size, bold, black, horizontally centered. **Demoted from the original draft's Display-size hero role** — it is no longer the primary visual anchor, but remains the largest text element, since it's still the single most useful glanceable fact once the silhouette has been seen.
6. **sm (16px) gap**
7. **Route line** — a Label-size, uppercase, tracked prefix ("TO" for departing / "FROM" for arriving) followed by Body-size destination or origin city name (sentence case), black.
8. **md (32px) gap**
9. **Airline line** — Body size, regular weight, black (e.g. "Air France"). On enrichment failure, this line is replaced by the fallback copy in the Copywriting Contract below rather than left blank.
10. Remaining space is empty white — deliberate negative space, consistent with the "ambient piece" core value and with flightportrait's own solid-field-plus-illustration composition; this is not a dashboard and should not be filled with filler content.
11. **Bottom-anchored static tag** — Label size, black, e.g. `ORY · RWY 3`. Does not change per flight; reinforces place/context at a glance.

**What did NOT change:** the mode badge's position (top-anchored), its Accent-color fill logic (D-03), the route-line prefix convention (TO/FROM), the airline-line fallback behavior, the bottom static tag, and the "no artificial expiry, last flight persists" behavior (D-04) are all carried over unchanged from the original draft — only their relative visual weight shifted now that the silhouette, not the flight number, is the focal point.

## Typography

**Reduced from 4 to 3 declared sizes** (still within the template's required 3-4 range) — the original draft's Display size (160px) was the flight-number hero text; now that the silhouette is the primary visual anchor and the flight number is a supporting caption, no element on the panel needs to be larger than Heading size. Display is dropped rather than kept-but-unused, to avoid an ambiguous unused role in the contract.

| Role | Size | Weight | Line Height |
|------|------|--------|-------------|
| Label | 36px | 700 (Bold) | 1.2 |
| Body | 56px | 400 (Regular) | 1.3 |
| Heading | 88px | 700 (Bold) | 1.2 |

Role usage (revised):

- **Label** (uppercase, widened letter-spacing — Pillow: manual glyph-advance widening, no native tracking API): mode badge label (`DEPARTING`/`ARRIVING`); the "TO"/"FROM" route-line prefix; the bottom static tag (`ORY · RWY 3`).
- **Body** (sentence case): the route line's destination/origin city name; the airline line (including its "Route unavailable" fallback copy).
- **Heading**: the flight number caption only — now the single largest text element on the panel, but visually subordinate to the silhouette centerpiece above it.

## Color

Fixed 6-color Spectra 6 hardware palette (`docs/PROTOCOL.md` §1) — the contract here is *which of the 6 legal colors is used for which role*, not a free hex choice. **Unchanged from the original draft**, with one addition: the silhouette's color assignment.

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | White (nibble `0x1`) | Background canvas |
| Secondary (30%) | Black (nibble `0x0`) | **Aircraft silhouette fill (NEW)**, flight number caption, route/airline text, dividers, default icon fill, bottom static tag |
| Accent (10%) — Departing | Blue (nibble `0x5`) | Mode badge fill + `plane-takeoff` icon, DEPARTING state only |
| Accent (10%) — Arriving | Green (nibble `0x6`) | Mode badge fill + `plane-landing` icon, ARRIVING state only (mutually exclusive with Departing — only one is ever on screen per D-03) |
| Destructive | not applicable | No destructive actions exist on a passive, buttonless display this phase |

**Why the silhouette is Black, not Accent:** the silhouette occupies a large, prominent area of the canvas (up to 900×260px). Filling a shape that size in the Departing/Arriving accent color would consume far more than the reserved 10% accent budget and break the 60/30/10 color contract established for this project. The silhouette therefore always renders in Black (Secondary role) regardless of departing/arriving state; mode is communicated exclusively via the small badge's fill color (10% accent, as originally specified) plus the silhouette's horizontal mirroring described in Layout & Composition.

Accent reserved for: the mode badge fill/icon only, nothing else — **not** the silhouette, regardless of its visual prominence. Body, heading (flight number), and static-tag text stay black regardless of departure/arrival state — color communicates *state*, not general decoration.

**Cross-phase reservation note (unchanged):** Yellow (`0x2`) and Red (`0x3`) are intentionally unused in this phase's palette, held in reserve for Phase 3's disruption banner (RER-03) and Phase 4's low-battery indicator (DEVICE-04) so those later semantic colors don't collide with this phase's departure/arrival color-coding.

## Copywriting Contract

No clickable UI exists this phase (passive e-ink display, no buttons until Phase 4), so "Primary CTA" is reinterpreted as the single most important glanceable readout. **Unchanged from the original draft**, with one clarifying addition about the silhouette's behavior across states.

| Element | Copy |
|---------|------|
| Primary readout (mode badge label) | `DEPARTING` or `ARRIVING` — exact uppercase string, mutually exclusive, per D-03's inferred runway configuration |
| Empty state heading (no aircraft ever detected since server start / cache empty) | "Watching Runway 3" |
| Empty state body | "No aircraft detected yet — the display updates the moment one is." |
| Empty state — silhouette | **Not shown.** The empty state remains a text-only composition (no silhouette, no mode badge) — there is no flight yet to depict, so nothing renders in the silhouette zone; the panel shows only the empty-state heading/body, vertically centered, on white. |
| Between-flights state | Not a distinct visual state — per D-04, the last detected flight (silhouette, flight number, route, airline, and mode badge together) stays on screen indefinitely; no separate "waiting" copy or blank silhouette is ever shown once at least one flight has rendered |
| Error / partial-data state (D-02 enrichment lookup fails or returns no route for a real detected callsign) | Airline line falls back to: "Route unavailable" (Body size, regular, black) — the silhouette, mode badge, and hero flight number all still render normally from ADS-B data alone (the silhouette is generic and does not depend on enrichment data); only the airline/route line degrades |
| Destructive confirmation | not applicable — no destructive actions exist on this passive display this phase |
