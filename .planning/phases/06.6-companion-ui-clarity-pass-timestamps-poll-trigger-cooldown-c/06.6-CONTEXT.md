# Phase 06.6: Companion UI clarity pass - timestamps, poll-trigger cooldown, corroboration copy - Context

**Gathered:** 2026-08-28
**Status:** Ready for planning

<domain>
## Phase Boundary

Three independent clarity fixes to the companion web app, raised during Phase 6's live developer sign-off: (1) standardize inconsistent timestamp presentation across pages, (2) make the poll-trigger cooldown a live countdown instead of a static, load-time-frozen number, (3) verify/polish ADS-B corroboration copy. Investigation found the third item is largely already done — this phase should confirm it meets the bar rather than rebuild it.

</domain>

<decisions>
## Implementation Decisions

### Poll-trigger cooldown
- **D-01:** The cooldown becomes a **live, ticking countdown** — a small bit of JS counts the seconds down in place and re-enables the trigger button automatically at zero, replacing today's "frozen at page-load, only updates on manual refresh" behavior.

### Timestamp consistency (derived from existing in-app precedent, not separately asked)
- **D-02:** Extend `health_page.py`'s own existing "absolute + relative" format (e.g. `"2026-08-28T13:58:02 (3m ago)"`, already used for Device/Pipeline rows) to the three spots that currently lack it: Health's own Battery Trend table (currently ISO-only), History's table (currently raw `ts` only), and Preview's "Captured" caption (currently absolute-only). This is the obviously-consistent choice since the target format already exists and works in the same app — not treated as an open question.

### Corroboration copy
- **D-03:** Investigation found the existing corroboration copy (`_CORROBORATION_ROWS` in `health_page.py`, mirrored in `history_page.py`'s `_CORROBORATION_LABELS`) already satisfies "never mislabel the unknown state as failure" — `"None"` already maps to `"ok"`, not a warning. **This part of the phase is verify-and-polish, not build-from-scratch** — the planner should confirm this against the live page before assuming rework is needed, and should not invent new copy changes without a concrete found problem.

### Claude's Discretion
- Exact JS implementation for the live countdown (vanilla inline script vs. a small shared script block in `layout.py`).
- Whether `_relative_age_text()` is imported/reused directly across `history_page.py`/`preview_page.py` or a small shared helper is factored out — avoid duplicating the same relative-time logic three times.

</decisions>
