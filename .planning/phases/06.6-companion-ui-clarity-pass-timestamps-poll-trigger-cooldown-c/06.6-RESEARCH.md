## Summary

This phase is three small, independent clarity fixes layered onto an already-shipped, fully-tested companion web app (Phase 6, complete). None of the three needs new libraries, new architecture, or new external services — every fix reuses code and conventions that already exist and already work elsewhere on the same site. The work is genuinely "polish," but it lands in a codebase currently being touched by three other sibling phases (06.3, 06.4, 06.5 — all fully planned, none yet executed) that edit the exact same files (`health_page.py`, `config_page.py`) this phase also edits. The real risk in this phase is not technical difficulty — it's **stale line-number assumptions and signature collisions with sibling unexecuted phases**, not "how do I format a timestamp."

Fix 1 (timestamp consistency) is pure reuse: `health_page.py`'s `_relative_age_text()`/`_age_seconds()`/`_parse_iso()` already produce the exact target format (`"ISO_TS (Nm ago)"`) for the Device/Pipeline sections. The only real design decision is **where these helpers should live** — they are currently private (`_`-prefixed) module functions in `health_page.py`, but `companion/pages/__init__.py`'s own documented contract forbids one page module importing another page module. That means `history_page.py` and `preview_page.py` cannot import `health_page._relative_age_text()` directly without violating an established architectural rule; the correct fix is to promote the three helpers to public functions in `companion/layout.py` (which every page module already imports), and have all three page modules — including `health_page.py` itself — call the shared version.

Fix 2 (live poll countdown) requires zero new server infrastructure: `companion/app.py`'s `poll_cooldown_remaining(state_dir)` already computes the exact seconds-remaining figure server-side, persisted via `history_db`'s meta table (`META_LAST_POLL_TRIGGER`), and it is already threaded into every page's `ctx["poll_cooldown_remaining"]`. The only new code is a small, self-contained, inline `<script>` block that seeds a JS countdown from that already-correct server value and ticks it down client-side with `setInterval`, re-enabling the button and clearing the message at zero. **This will be the first JavaScript this project's `config_page.py` route ever ships** — but a sibling unexecuted phase, 06.5, is *already* building the project's first JS file (`companion/static/battery-trend.js`) with its own "first JavaScript file this project has ever shipped" claim baked into its plan's own prose. To avoid falsifying that claim regardless of execution order, 06.6's countdown script should stay an **inline `<script>` block embedded directly in the rendered HTML response**, not a new `companion/static/*.js` file — this also avoids needing new static-route-serving plumbing in `app.py` for a ~15-line script.

Fix 3 (corroboration copy) is verify-only per the user's own locked decision (D-03) and this research confirms the investigation's finding: `health_page.py`'s `_CORROBORATION_ROWS` and `history_page.py`'s `_CORROBORATION_LABELS` are already textually consistent (`"True"`→Agreement/ok, `"None"`→Single-source (uncorroborated)/ok, `"False"`→Disagreement/warn) and neither mislabels the unknown state as failure. No code changes are expected here unless the planner finds a concrete problem while reading the live page.

**Primary recommendation:** Promote `_relative_age_text()`/`_age_seconds()`/`_parse_iso()` to `companion/layout.py` as shared public helpers; reformat the three named spots to call them; ship the poll countdown as a small inline `<script>` (not a new static file); leave corroboration copy untouched unless a real defect surfaces. Every edit should locate its target by function/section name at execution time, not by the line numbers cited in `06.6-CONTEXT.md`'s canonical_refs — those numbers describe the pre-06.3/06.4/06.5 file state and will very likely have shifted by the time 06.6 executes.

### Pattern 1: Promote existing "absolute + relative" formatting to a shared layout helper

**What:** `health_page.py` already contains `_parse_iso(ts)`, `_age_seconds(ts, now_ts)`, and `_relative_age_text(age_seconds)` — three small, pure, already-correct functions. Their combined effect (as used inline in `_device_section()`/`_pipeline_section()`) is:

```python
# companion/pages/health_page.py (existing, lines ~353-355)
detail = (
    "no reading yet" if ts is None
    else "%s (%s)" % (escape_html(ts), escape_html(_relative_age_text(age)))
)
```

**When to use:** Any place a stored ISO-8601 `ts` string needs to render as `"2026-08-28T13:58:02 (3m ago)"` next to a `now` value already present in `ctx`.

**Example (recommended shared form in `companion/layout.py`):**
```python
# Source: adapted from companion/pages/health_page.py's existing, already-shipped

def relative_age_text(age_seconds):
    age_seconds = max(0, int(age_seconds))
    if age_seconds < 60:
        return "%ds ago" % age_seconds
    if age_seconds < 3600:
        return "%dm ago" % (age_seconds // 60)
    if age_seconds < 86400:
        return "%dh ago" % (age_seconds // 3600)
    return "%dd ago" % (age_seconds // 86400)


def absolute_and_relative(ts, now_ts, fallback="no reading yet"):
    """Render ts as "ISO (Nm ago)", or fallback when ts/now_ts can't be
    parsed — the one, escaped, shared form of health_page.py's existing
    Device/Pipeline convention. Callers still escape their own strings
    per this module's single-escaping-choke-point discipline; this
    helper returns plain text, not markup.
    """
    ...
```
`health_page.py`, `history_page.py`, and `preview_page.py` then all import from `companion.layout` (already an existing import in every one of them) rather than duplicating the logic a third time.

**Note on `panel_preview.panel_file_mtime_iso()`:** returns a `"...Z"`-suffixed ISO string (`"2026-08-28T13:58:02Z"`), not the `"+00:00"`-suffixed form `history_db.utc_now_iso()` produces. `[VERIFIED: local Python 3.14 REPL, this session]` `datetime.fromisoformat()` parses both forms correctly (Python's `fromisoformat` has accepted the `Z` suffix since 3.11; this project targets 3.12+ per CLAUDE.md) and both parse to timezone-*aware* datetimes, so subtracting them against `ctx["now"]` (also tz-aware, from `history_db.utc_now_iso()`) will not raise `TypeError: can't subtract offset-naive and offset-aware datetimes`. No format-compatibility fix is needed before reusing the shared helper here.

### Pattern 2: Zero-dependency inline countdown script, seeded from a server-computed value

**What:** A `<script>` block emitted only on the disabled-button branch of `poll_trigger_section()`, using `json.dumps()` to safely embed the server-computed integer and the (fixed, non-user-controlled) message template as JS literals — avoiding hand-rolled string-escaping bugs in a `<script>` context.

**When to use:** Exactly one call site: `config_page.poll_trigger_section(cooldown_remaining)`'s non-zero branch.

**Example:**
```python
# Source: pattern adapted from companion/static/battery-trend.js's own
# documented constraints (06.5-01-PLAN.md Task 1) — IIFE + "use strict",
# no HTML-writing sink beyond textContent, no fetch/XMLHttpRequest/eval,
# no persistent state, IIFE-scoped so it cannot leak globals.
import json

def poll_trigger_section(cooldown_remaining):
    if cooldown_remaining:
        cooldown_text = POLL_COOLDOWN_HELPER_TEXT.format(n=cooldown_remaining)
        script = (
            "<script>"
            '(function () { "use strict";'
            "var remaining = %s;"
            'var btn = document.getElementById("poll-trigger-btn");'
            'var text = document.getElementById("poll-cooldown-text");'
            "if (!btn || !text || remaining <= 0) { return; }"
            "var timer = setInterval(function () {"
            "  remaining -= 1;"
            "  if (remaining <= 0) {"
            "    clearInterval(timer);"
            '    btn.removeAttribute("disabled");'
            '    text.textContent = "";'
            "    return;"
            "  }"
            "  text.textContent = %s.replace(%s, String(remaining));"
            "}, 1000);"
            "})();"
            "</script>"
        ) % (json.dumps(cooldown_remaining), json.dumps(POLL_COOLDOWN_HELPER_TEXT.format(n="__N__")), json.dumps("__N__"))
        return (
            '<form method="post" action="/poll-now">'
            '<button type="submit" id="poll-trigger-btn" disabled>Trigger Poll Now</button>'
            "</form>"
            '<p class="text-body" id="poll-cooldown-text">%s</p>'
            "%s"
        ) % (escape_html(cooldown_text), script)
    return (
        '<form method="post" action="/poll-now">'
        '<button type="submit">Trigger Poll Now</button>'
        "</form>"
    )
```
This is illustrative, not prescriptive down to the byte — the planner should design the exact DOM-id/template-substitution mechanics, but the load-bearing constraints are: (1) `json.dumps()` for every server value entering the `<script>` block, never raw `%s`/f-string interpolation of a Python string into JS source; (2) the script only renders on the disabled branch (never shipped when the button is already enabled — matches 06.5's own precedent of only emitting its `<script src>` when there's something for it to do); (3) DOM mutation via `textContent`/`removeAttribute` only, never `innerHTML`.

### Anti-Patterns to Avoid

- **Re-deriving the cooldown countdown client-side from scratch (e.g., a hardcoded 45s):** `POLL_COOLDOWN_S = 45` lives in `companion/app.py`; a page rendered mid-cooldown must seed its JS countdown from the *actual remaining* value (`ctx["poll_cooldown_remaining"]`), not a fresh 45. `06.6-CONTEXT.md`'s canonical_refs are explicit about this: "the countdown's starting value must derive from this same persisted state, not a client-only guess."
- **Interpolating a Python string directly into a `<script>` block with `%s`/f-strings:** breaks on any future copy change containing a quote, backslash, or `</script>`-like sequence, and is a documented XSS-adjacent pitfall for hand-built HTML-with-embedded-JS. Use `json.dumps()`.
- **Creating a second `.js` static file for this phase:** collides with 06.5's own "first JavaScript file this project has ever shipped" framing (see Summary) — keep this phase's script inline.
- **Trusting `06.6-CONTEXT.md`'s pinned line numbers (`~384-386`, `~105-124`, etc.) as exact edit targets:** three sibling phases (06.3, 06.4, 06.5) are fully planned but unexecuted against these same files as of this research; by the time 06.6 executes, those line numbers will very likely have moved. Locate insertion points by function/section name, not line number.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Relative-time formatting ("3m ago") | A new duration-formatting function, or a `dateutil`/`humanize`-style dependency | The existing `_relative_age_text()` (promoted to `companion/layout.py`) | It already exists, is already tested (implicitly, via Device/Pipeline sections' existing coverage), and is deliberately simple (s/m/h/d thresholds, no library needed) — this app has a standing zero-new-dependency discipline |
| Embedding a server value safely inside a `<script>` block | Manual string escaping / regex-based sanitization of the value before interpolation | stdlib `json.dumps()` | `json.dumps()` of a Python `int` or `str` produces a syntactically valid, safely-escaped JS literal — this is the standard technique for server-to-inline-script value passing and needs no new dependency |
| A "live" countdown | A polling `fetch()` loop re-querying `/config` every second | A single client-side `setInterval` ticking down a known, server-seeded integer | The cooldown duration and start time are both already known at render time; there is nothing on the server that can change mid-countdown that the client needs to re-fetch for |

**Key insight:** Every piece of this phase's "new" behavior is a recombination of code and conventions that already exist and already work in this exact codebase (the absolute+relative format, the server-persisted cooldown value, `json.dumps()` from the stdlib). The temptation to reach for something more sophisticated (a JS templating trick, a new timestamp library, a polling mechanism) would be over-engineering for a page that has zero other client-side interactivity as of this writing (before 06.5 lands its sparkline JS).

## Common Pitfalls

### Pitfall 1: Editing `_battery_section()`'s call signature breaks a sibling phase's already-written automated gate

**What goes wrong:** `06.5-02-PLAN.md`'s Task 1 acceptance criteria include a literal grep: `render()` must still contain the exact substring `battery_html, battery_state = _battery_section(trend_rows)` (single positional argument). If 06.6 needs a `now` value inside `_battery_section()` to compute the relative-age text for the Battery Trend table, and does so by changing the function's signature to `_battery_section(trend_rows, now)`, this breaks 06.5's pinned check regardless of which phase executes first (if 06.6 runs first, 06.5's grep never matches when it later executes; if 06.5 runs first locking in the 1-arg form, a later 06.6 edit to 2 args makes 06.5's already-shipped assertion stale/wrong).

**Why it happens:** Two sibling phases independently modify the same function without a formal dependency link between them.

**How to avoid:** Do not change `_battery_section()`'s parameter list. Instead, compute `now` independently inside `_battery_section()` itself via `history_db.utc_now_iso()` (a fresh call, matching the pattern `render()` already uses at the top of the function to compute its own `now` once) — this keeps the call site `_battery_section(trend_rows)` byte-identical no matter which phase runs first. The very small clock-skew risk (the battery table's "ago" text is computed a few microseconds later than `render()`'s own `now`) is immaterial at minute/hour granularity.

**Warning signs:** `grep -n "_battery_section(trend_rows" companion/pages/health_page.py` should still find exactly one call site with exactly that argument list after 06.6's edit.

### Pitfall 2: Assuming `_section()`/pinned line numbers still describe the current file

**What goes wrong:** `06.6-CONTEXT.md`'s canonical_refs cite `health_page.py`'s Battery Trend table at "~384-386" and `config_page.py`'s `poll_trigger_section()` at "~105-124." Three sibling phases (06.3's dashboard/`stat_tile()` wrap, 06.4's runway-picker changes, 06.5's badge/readout/script additions to `_battery_section()`) are fully planned against these same files and may execute before 06.6 does — each one adds lines, so these numbers drift.

**Why it happens:** All four phases (06.3, 06.4, 06.5, 06.6) were discussed/researched/planned close together against a shared starting snapshot, but only 06.3-06.5 are far enough along to have PLAN.md files; 06.6 is being researched last.

**How to avoid:** Every plan task should locate its edit target by grepping for the function name or a stable string (e.g. `def _battery_section`, `def poll_trigger_section`, `layout.data_table(\n        \["Timestamp", "Battery`), not by a fixed line number. Re-read the target file fresh at plan-execution time. `06.5-02-PLAN.md` itself already establishes this exact precedent for the 06.3-vs-06.5 ordering ambiguity ("Do not fight it. Read `_battery_section()` and `render()` fresh and target whatever structure is actually there.") — 06.6 should follow the same discipline for all three sibling phases, not just 06.5.

**Warning signs:** A diff that touches lines far from where the intended function actually starts, or a plan step whose "expected surrounding context" snippet doesn't match what's actually in the file.

### Pitfall 3: Forgetting to bump `EXPECTED_CHECK_COUNT` after adding tests

**What goes wrong:** This project's test harnesses (`companion/test_status_pages.py`, `companion/test_view_pages.py`, `companion/test_config_page.py`) are hand-rolled (stdlib-only, no pytest) with a pinned `EXPECTED_CHECK_COUNT` module constant that the harness's own exit code depends on (`return 0 if (passed == total and total == EXPECTED_CHECK_COUNT) else 1`). Adding a new `check(...)` call without bumping this constant makes the harness report failure even though every individual check passed.

**Why it happens:** The constant is a deliberate drift-guard (catching accidentally-skipped or accidentally-duplicated checks), but it's easy to forget when adding tests for a new format/behavior.

**How to avoid:** Whenever a task adds a `check(...)` call to any of the three affected test files, increment that file's `EXPECTED_CHECK_COUNT` by the same amount in the same task/commit.

**Warning signs:** `scripts/run-all-tests.sh` (or the individual test file) exits non-zero despite every printed check line showing a pass.

### Pitfall 4: Treating `06.3-UI-SPEC.md`'s "3m ago (14:02:11)" example as a format mandate

**What goes wrong:** A planner reading `06.3-UI-SPEC.md`'s Typography → Usage table in isolation could conclude the Body-text style's example ("stat-tile supporting detail line (e.g. '3m ago (14:02:11)')") is a locked content-format spec requiring `_relative_age_text()`'s actual convention (absolute-first: `"ISO (Nm ago)"`) to be reversed to relative-first.

**Why it happens:** The example superficially resembles a real timestamp render, and it sits in a design-system document that otherwise does carry locked decisions.

**How to avoid:** See the dedicated "Open Question" resolution below — this research confirms (by reading every 06.3 plan file) that the example is illustrative prose only, not implemented or referenced by any 06.3 plan task, and `stat_tile()` (06.3's actual code contribution touching this area) is documented to pass its `content_html` argument through byte-for-byte, never reformatting timestamp content itself. Treat `_relative_age_text()`'s existing, shipped, tested convention as canonical.

**Warning signs:** A diff that changes `_relative_age_text()`'s or `_device_section()`'s existing output ordering — this should not happen in 06.6 at all.

## Open Questions

1. **06.3-UI-SPEC.md's "3m ago (14:02:11)" ordering — RESOLVED by this research, not left open for the planner.**
   - What we know: `06.3-UI-SPEC.md`'s Typography → Usage table (line 64) lists, as one example among several, a "stat-tile supporting detail line (e.g. '3m ago (14:02:11)')" under the Body (16/400) text style. No 06.3 plan task reads, writes, or depends on `_relative_age_text()`'s actual output ordering. `06.3-01-PLAN.md`'s own contract for the one relevant code change 06.3 makes near this area (`layout.stat_tile()`) states explicitly: "A `stat_tile()` builder wraps already-built section markup in a status-coloured card without altering that markup by a single byte" — i.e., 06.3's actual code is documented to pass timestamp content through completely unchanged, regardless of its internal ordering.
   - What's unclear: Nothing technical remains unclear — the example is demonstrative prose describing what *kind* of short text might occupy a Body-style line (illustrating the font-size/weight token, not specifying exact content), not a locked format contract. Note also that the example's own shape ("14:02:11", a bare time, no date) doesn't even match `_relative_age_text()`'s companion absolute format (`"2026-08-28T13:58:02"`, a full ISO-8601 datetime) — reinforcing that it's a loose illustrative sketch, not a literal spec pulled from real code.
   - Recommendation: **Do not change `_relative_age_text()`'s existing ordering.** Keep `_relative_age_text()`'s established, already-shipped, already-tested convention (absolute-first: `"ISO (Nm ago)"`) as canonical everywhere D-02 applies. If the planner wants a belt-and-suspenders fix, a single-line documentation note could be added to `06.3-UI-SPEC.md`'s Typography example clarifying it's illustrative-only — but this is optional polish outside 06.6's actual code scope, not a blocking dependency.
