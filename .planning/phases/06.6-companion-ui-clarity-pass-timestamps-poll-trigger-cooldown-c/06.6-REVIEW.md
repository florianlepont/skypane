**Reviewed:** 2026-08-30T00:00:00Z
**Depth:** standard

## Summary

Reviewed the three plans that make up this phase: (1) promotion of the "absolute + relative" timestamp helpers from `health_page.py` into `companion/layout.py` and their application to Health's Battery Trend table; (2) `config_page.py`'s live, ticking JS poll-cooldown countdown; and (3) History's Timestamp column, Preview's Captured caption, and the new History/Health corroboration-copy regression guard.

The escaping/injection discipline this review was specifically asked to scrutinize holds up well: every new timestamp interpolation site (Battery Trend table, History's Timestamp column, Preview's Captured caption) routes through `escape_html()` or `layout.data_table()`'s own per-cell escaping, and the new inline JS in `config_page.py` never interpolates a Python value with `%`/f-string — every value crossing the Python→JS boundary goes through `_js_literal()` (`json.dumps()` + `</`-breaking), and `cooldown_remaining` itself is server-computed, not client-supplied, so there is no injectable string reaching the `<script>` body. No XSS, script-injection, or unescaped-interpolation defect was found in the reviewed surfaces.

Two robustness (not security) gaps were found: the promoted `age_seconds()`/`absolute_and_relative()` helper can raise `TypeError` on a naive/aware `datetime` mismatch despite its docstring's explicit "never raising" guarantee, and `poll_trigger_section()` has no defensive floor against a negative `cooldown_remaining`, which would render a permanently-stuck disabled button with an inert countdown script. Two minor code-quality items are also noted.

## Warnings

### WR-01: `layout.absolute_and_relative()` can raise `TypeError`, contradicting its own "never raising" contract — now shared across 4 render paths

**File:** `companion/layout.py:260-268` (`age_seconds()`), referenced by `companion/layout.py:287-316` (`absolute_and_relative()`)

**Issue:** `age_seconds()` calls `(now_parsed - parsed).total_seconds()` with no guard against one side being timezone-aware and the other timezone-naive. `datetime.fromisoformat()` (via `parse_iso()`) happily returns a naive `datetime` for an ISO string with no UTC offset and an aware `datetime` for one that has one; subtracting an aware value from a naive one (or vice versa) raises `TypeError: can't subtract offset-naive and offset-aware datetimes`. Neither `age_seconds()` nor `absolute_and_relative()` catches this.

`absolute_and_relative()`'s own docstring states this promotion is "a deliberate hardening over the pre-promotion health_page.py path, where an empty-string `ts` would have reached the relative-age helper as `None` and raised a TypeError mid-render" and explicitly promises the function "never rais[es]." That promise is not fully kept: a syntactically-valid-but-naive ISO timestamp reaching either argument still raises mid-render, exactly the class of failure the promotion says it closes. Because this helper is now the single call site for 4 render paths (Health's Device/Pipeline rows plus the newly-added Battery Trend table, History's Timestamp column, and Preview's Captured caption), a single malformed/naive timestamp anywhere in `device_health`, `runway_events`, or the panel file's mtime can now 500 four different pages instead of the one page the pre-promotion code protected.

Every currently-observed timestamp source in this codebase (`history_db.utc_now_iso()`, the `Z`/`+00:00`-suffixed writers) produces timezone-aware strings, so this is not known to be triggered by any current code path — but it is a real, reachable gap in a function whose entire stated purpose is to never raise mid-render, and its blast radius just grew 4x.

**Fix:**
```python
def age_seconds(ts, now_ts):
    parsed = parse_iso(ts)
    now_parsed = parse_iso(now_ts)
    if parsed is None or now_parsed is None:
        return None
    try:
        return (now_parsed - parsed).total_seconds()
    except TypeError:
        return None
```

### WR-02: A negative `poll_cooldown_remaining` renders a permanently-disabled "Trigger Poll Now" button with an inert countdown script

**File:** `companion/pages/config_page.py:294` (`if cooldown_remaining:`) and `companion/pages/config_page.py:244` (`if (!btn || !text || remaining <= 0) { return; }` inside `_poll_cooldown_script()`)

**Issue:** `poll_trigger_section()` branches on `if cooldown_remaining:` (truthy check), so any non-zero value — including a negative one — takes the "disabled" branch: it renders `disabled`, the copy `"Poll triggered recently — try again in -Ns."`, and emits `_poll_cooldown_script(cooldown_remaining)`. That script's very first line is `if (!btn || !text || remaining <= 0) { return; }` — for a negative seed this is true, so the script does nothing at all: no timer starts, the button is never re-enabled, and the stale copy never clears. The user is left with a permanently-disabled button and nonsensical negative-seconds copy until they reload the page (which would only recover if the server-computed value has since become non-negative).

The docstring for `poll_trigger_section()` states the seed is "the server-computed, history_db-persisted figure" and treats it as trustworthy, but nothing in this module clamps or validates it before branching on truthiness — a transient clock-skew or off-by-one in the server-side cooldown computation would surface here as a stuck control with no client-side recovery path, which is a worse failure mode than simply showing 0/enabled.

**Fix:**
```python
def poll_trigger_section(cooldown_remaining):
    if cooldown_remaining and cooldown_remaining > 0:
        ...
```
(and/or clamp `cooldown_remaining = max(0, cooldown_remaining)` at the top of the function before either branch runs).

## Info

### IN-01: Local variable named `html` shadows the module-name convention this file is contractually forbidden from importing

**File:** `companion/pages/history_page.py:176`

**Issue:** `_merged_cell()` assigns its accumulator to a local variable literally named `html`:
```python
html = '<span class="%s">%s</span>' % (
    CELL_PRIMARY_CLASS, escape_html(primary))
if secondary:
    html += ...
```
This file's own module docstring and `test_status_pages.py`'s companion checks make a point of asserting page modules never `import html` directly (the stdlib module) — using `html` as a local variable name for built markup in the one file class that explicitly documents avoiding that name is confusing to a reader scanning for the (forbidden) import, and increases the odds of an accidental future `import html` shadowing/no-op inside this function without either raising an ImportError or a lint the test harness would catch (the existing regression check only greps for `import html` as a standalone line, not for local shadowing).

**Fix:** Rename to something unambiguous, e.g. `cell_html`.

### IN-02: The `setInterval`-based poll-cooldown countdown can drift from the server's real cooldown state in a backgrounded/throttled tab

**File:** `companion/pages/config_page.py:215-265` (`_poll_cooldown_script()`)

**Issue:** The countdown relies purely on a client-side `setInterval(fn, 1000)` seeded once from the server value at render time. Browsers (notably Chromium's background-tab timer throttling) can slow or batch 1-second intervals in an inactive/backgrounded tab, so the on-screen "try again in Ns" text and the button's re-enable moment can lag behind the actual server-side cooldown expiry. This is not a security or correctness bug — `companion/app.py`'s `_handle_poll_now()` independently re-validates the cooldown server-side before ever calling `poll_loop.run_once()`, per this module's own docstring — but it is a real UX inconsistency a user could notice (a still-disabled-looking button after the real cooldown has already elapsed).

**Fix:** Optional — no action required given the server-side re-validation backstop. If desired, reconcile on `visibilitychange`/`focus` by re-deriving `remaining` from `Date.now()` deltas instead of a pure decrement-per-tick counter.
