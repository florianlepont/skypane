# Phase 06.6.1: post-release UI/UX audit

**Audited:** 2026-08-30  
**Target:** `https://config-92-222-92-167.nip.io/`  
**Status:** Issues found; suitable as the canonical input to a follow-up phase  
**Suggested follow-up phase:** `06.6.2-companion-ux-accessibility-responsive-hardening` (number/name to be confirmed when the roadmap is amended)

## Purpose

This document records a hands-on UI, UX, responsive-layout, and accessibility audit performed after Phase 06.6.1 was completed and formally verified. It does not invalidate `06.6.1-VERIFICATION.md`: that report correctly verifies the phase against its locked decisions and plan must-haves. This audit asks a different question: now that the interface is populated and exercised as an operator-facing product, what still makes it difficult, confusing, or inaccessible to use?

The findings below are intentionally written as future implementation input. Each material finding includes observed evidence, likely cause, recommended direction, acceptance criteria, likely files, and regression coverage. A future planner should treat the acceptance criteria as the minimum behavioral contract, while retaining discretion over exact implementation details.

## Audit scope and method

### Surfaces reviewed

- Production login page reached by opening `/health` without a session.
- Authenticated Config, Health, Airlines, History, and Preview pages on a local instance running the current worktree.
- Empty states on every authenticated page.
- Populated Health and History states using synthetic, non-production data written to a temporary state directory.
- Auto, Light, and Dark theme behavior.
- Desktop layout at 1440 × 900.
- Mobile layout at 390 × 844.
- Mobile navigation closed and open states.
- DOM/accessibility snapshot, semantic markup, computed layout metrics, focus styling, touch-target sizing, and color-token contrast.

### Production vs. local coverage

The production URL was inspected through its unauthenticated login surface only. No production password was requested, entered, or exposed. The authenticated pages were exercised against the same code from this worktree, with a temporary local password and synthetic state data.

Consequently, this audit validates the current UI implementation and its populated/empty rendering paths, but it does not validate:

- the exact production database contents;
- production-only runway images or gallery images;
- live post-save, post-poll, or poll-failure behavior against the real device pipeline;
- production authentication success and lockout behavior;
- real assistive-technology output from VoiceOver, NVDA, or TalkBack.

Those items belong in the follow-up phase's final verification matrix.

## Executive assessment

The interface has a credible and coherent visual foundation. Its warm palette, serif headings, card treatment, two themes, 44 px control floor, semantic fieldsets, status labels, and honest empty states are all good decisions. Config and Health are understandable without onboarding, and the mobile hamburger is visually much more discoverable than the horizontal-strip navigation it replaced.

The main remaining weaknesses are structural rather than cosmetic:

1. populated History can expand the desktop document beyond the viewport, while its mobile presentation hides nearly all useful columns behind a horizontal swipe;
2. the visually-collapsed mobile menu remains present in the accessibility tree and can retain focusable descendants;
3. the login experience uses the authenticated application shell, loses the originally requested destination, and provides no visible logout control after authentication;
4. the light-theme accent fails WCAG AA contrast for normal-sized text.

The next tier of findings concerns information architecture and product language: raw ISO timestamps, implementation identifiers such as `D-04`, state values such as `on_runway`, a generic anomaly summary, and a battery chart placed after as many as 20 raw table rows. These make the site read like a well-styled engineering console rather than a finished operator tool.

### Indicative scorecard

| Dimension | Score | Summary |
|---|---:|---|
| Visual consistency | 7/10 | Cohesive palette, type, spacing, cards, and theme treatment. |
| Task clarity | 6/10 | Core controls are understandable, but authentication and feedback flows need work. |

## Strengths to preserve

The follow-up phase should preserve these behaviors unless a new design decision explicitly supersedes them:

- All standard controls have a 44 px minimum width/height floor.
- Focus outlines are visible and use the product accent.
- Form controls use labels, fieldsets, and legends rather than placeholder-only labeling.
- Theme controls expose their selected state with `aria-pressed`.
- Health statuses include text labels; status is not communicated by color alone.
- The Health navigation notification includes visually-hidden explanatory text.
- The hamburger button uses `aria-expanded` as its state signal.
- Escape closes the open mobile menu and returns focus to its toggle.
- Empty states state honestly that data is unavailable rather than rendering broken tables or images.
- Preview and gallery images have alternative text.
- Mobile pages avoid document-level horizontal overflow in the empty/config states.
- The stylesheet uses shared tokens rather than page-local colors and spacing values.
- Both light and dark modes are first-class implementations rather than a color inversion hack.

## Visual direction: from a solid utility UI to a distinctive SkyPane interface

Fixing the findings will make the interface correct and accessible. Reaching a visual 9–10/10 also requires a clear aesthetic hierarchy. The recommended direction is **warm editorial aviation instrument**: retain the crafted serif/terracotta identity from Phase 06.6.1, then combine it with the precision, density control, and status clarity of a good operations console.

This should not become a glossy airline-booking site, a generic SaaS dashboard, or a glassmorphism demo. SkyPane is a small, physical, personal object. The web interface should feel equally tactile and deliberate.

### Visual north star

The desired impression in five words:

- calm;
- crafted;
- precise;
- tactile;
- quietly technical.

The visual hierarchy should read in this order:

1. **What is the system doing now?**
2. **Is anything wrong?**
3. **What can I change or trigger?**
4. **What are the technical details?**

Today, titles, helper text, raw timestamps, status explanations, and controls often receive similar visual weight. Beauty here will come primarily from reducing that competition, not from adding decoration.

- two-column mini-stat layout only where values remain legible, otherwise one column;
- no desktop table shrunk into a phone;
- primary action either full width or placed in a clearly separated bottom action region;
- details collapsed by default only when their summary remains complete and accessible.

### Color and surface system

The current warm palette is the right direction, but the surfaces need more separation and the light accent needs accessible darkening.

The following values are an exploration target, not a locked implementation contract. They were selected to illustrate the intended relationships and have been contrast-checked for their named text uses:

| Token role | Light exploration | Dark exploration | Purpose |
|---|---|---|---|
| Canvas | `#F7F4EF` | `#0C0F14` | Warm page background. |
| Primary surface | `#FFFFFF` | `#151922` | Cards and main controls. |
| Secondary surface | `#EEE8DE` | `#1C222D` | Sidebar, table headers, quiet grouped regions. |
| Primary text | `#17191F` | `#F4F1EC` | Body and headings. |
| Muted text | `#66645F` | `#A8ACB4` | Secondary metadata; both examples remain comfortably readable. |
| Interactive terracotta | `#B13F16` | `#FF9B73` | Links, active nav, button borders/fills according to foreground pairing. |
| Interactive hover | `#963610` | a measured lighter/darker companion | Hover/active state, chosen after component-level contrast checks. |

Measured examples for the exploration palette:

- `#B13F16` on white: 5.85:1;
- `#B13F16` on `#F7F4EF`: 5.33:1;
- `#B13F16` on `#EEE8DE`: 4.80:1;
- `#FF9B73` on `#0C0F14`: 9.31:1;
- `#66645F` on white: 5.91:1;
- `#A8ACB4` on `#151922`: 7.73:1.

The important design change is not any one hex value. It is the introduction of three visibly distinct surface levels:

1. canvas;
2. normal card/control surface;
3. secondary/elevated/navigation surface.

Current dark cards often share the page's dominant background and depend on a dark shadow that cannot create convincing separation on an already-dark canvas. Dark mode should use tonal elevation plus a restrained light border, not shadow alone.

### Typography hierarchy

Retain the serif/sans division but make it do more work:

| Role | Suggested size | Treatment |
|---|---:|---|
| Wordmark | 26–28 px | Serif, regular, slightly positive tracking. |
| Page title | 30–34 px | Serif, regular, tight line height. |
| Section title | 20–22 px | Serif, regular. |
| Primary stat/value | 28–36 px | Sans or mono semibold according to content. |
| Body | 16 px | Sans, 1.5 line height. |
| Label/caption | 13–14 px | Sans, medium/semibold where needed. |
| Technical metadata | 12–13 px | Mono, muted but AA-compliant. |

Use serif for narrative hierarchy, not for every card caption. A Health card title such as `Device` can stay sans-serif/medium while the page and section titles carry the editorial personality. This creates a cleaner distinction between brand voice and instrumentation.

Suggested font stack, preserving the no-external-font constraint:

```css
--font-serif: ui-serif, "Iowan Old Style", Charter, "Palatino Linotype", Georgia, serif;
```

The exact stack must be tested across macOS, iOS, Windows, and Linux. Do not choose a stack that changes metrics so much that headings wrap unpredictably.

### Spacing, radius, border, and shadow

Recommended starting relationships:

- page gutter: 48–64 px desktop, 20–24 px mobile;
- card padding: 24 px desktop, 20 px mobile;
- major section gap: 32–40 px;
- card grid gap: 20–24 px;
- card radius: 12–14 px;
- control radius: 8–10 px;
- borders: one quiet 1 px structural border, especially in dark mode;
- resting shadow: barely visible, used to lift rather than outline;
- hover shadow: modest increase only for genuinely interactive cards.

Avoid giving non-interactive status cards a hover lift. Movement implies clickability. If a card has no action, visual response on pointer hover should be minimal or absent.

### Sidebar refinement

The sidebar should feel like a calm control rail rather than a large empty column.

Recommended changes:

- wordmark at 26–28 px with a compact contextual line below, e.g. current runway;
- optional small, single-color outline icon beside each navigation label, using the existing icon language;
- active navigation as a low-contrast tinted pill/surface plus strong text, not only a 3 px vertical orange line;
- preserve a visible Health warning indicator, but use the correct warning/error severity;
- group theme and logout in a clearly separated footer region;
- make the sidebar sticky on long desktop pages if zoom testing remains clean;
- reduce the impression of unused space with deliberate grouping, not extra decoration.

Do not add a large illustrated logo; Phase 06.6.1's text-wordmark decision remains appropriate.

### Page-header pattern

Every authenticated page should begin with one consistent header component:

- page title;
- one short purpose sentence when the title is not self-explanatory;
- page freshness for status/data views;
- at most one contextual action on the right.

Examples:

- Health — `Device, pipeline, source agreement, and battery condition.`
- History — `Latest detected runway events.` plus `Latest 50`/filter context.
- Preview — `What the physical frame is currently showing.`
- Airlines — `Route-resolution coverage and unresolved callsign prefixes.`

This removes the current pattern where some pages open directly into a bare H1 and others introduce a second heading immediately below it.

### Config page redesign

Config currently looks the most like a traditional HTML form. It can become more tactile without becoming complex.

#### Theme

- If only one hardware theme exists, show it as current status with a small preview swatch rather than a one-choice radio fieldset.
- When multiple themes exist, use compact selectable preview cards with name, mini palette, and selected checkmark.

#### Runway

- Turn each runway into a selectable card containing runway designation, orientation, and optional airport diagram.
- Use the full card as the label/hit target.
- Show a clear selected border/check, not only a large browser-native radio.
- Keep one consistent label (`07/25`) throughout the application.

#### LED

- Present as a compact setting row with label, one-line explanation, and switch/checkbox aligned consistently.
- Rename according to the future terminology decision.
- Avoid repeating the same title as H2 and legend.

#### Saving

- Show a sticky/local action bar only after a value changes: `2 unsaved changes` plus `Save settings` and `Cancel`.
- Preserve a server-rendered always-available submit path for no-JS use.
- Keep Poll visually separate from persistent settings; it is an operation, not a preference.

### Health page redesign

Health should be the strongest page visually because it expresses the product's live state.

Recommended composition:

1. **Status summary banner/hero** — `All systems healthy`, `1 warning`, or `1 error`, with named cause.
2. **Three compact signal cards** — Device, Pipeline, Sources. Each shows a short primary verdict (`Online`, `Fresh`, `1 disagreement`) and relegates the exact timestamp/explanation to secondary text.
3. **Battery hero card** — current voltage as the primary number, delta/time window as secondary, chart immediately visible.
4. **Readings disclosure** — raw table below `View 20 readings`.

Visual refinements:

- use a 2–4% semantic tint in a card background or icon circle, not only a thin top border;
- keep status colors restrained and reserve red for true error;
- use a subtle area fill under the battery line;
- show min/max/current markers and, once hardware calibration is authoritative, an honest low-battery threshold line;
- avoid equal-height cards when one explanation is much longer.

### History page redesign

Desktop table treatment:

- sticky header inside the table wrapper;
- human-readable timestamp first, full ISO in secondary detail/title;
- callsign visually primary, hex secondary;
- state and corroboration displayed as compact text badges with accessible contrast;
- subtle row hover only if rows open details;
- fixed/controlled column widths so one long label does not dominate;
- optional filter row above the table, not inside its header.

Mobile treatment:

- record cards or compact disclosure rows;
- first line: callsign, route, relative time;
- second line: aircraft/airline and state;
- third/details: corroboration, runway, hex, absolute time;
- no horizontal swipe required for core identity.

Use badges sparingly. If every cell becomes a pill, the page will look noisy and less premium.

### Preview page redesign

The live preview should be presented as the product, not merely as an `<img>` dropped into a card:

- center it in a quiet matte/frame treatment matching the physical display aspect ratio;
- use a subtle inner edge to evoke e-paper glass without photorealistic decoration;
- place `Captured …` and the color-accuracy caveat below as a caption block;
- make the caveat concise by default, with technical detail available through disclosure;
- gallery cards should use capture time/state as captions rather than raw filenames;
- allow opening a render at full useful size.

### Airlines page redesign

The page currently opens with `Airlines` → `Coverage` → cards containing more coverage labels. Simplify the hierarchy:

- one page header;
- one prominent `Resolved over 30 days` value with numerator/denominator;
- a compact source-distribution visual only if it improves comparison over the current table;
- unresolved prefixes as the primary actionable list;
- explain the manual resolution workflow once, near that list, not as equal-weight body copy inside a status card.

Avoid a decorative donut chart if four labeled counts communicate the result more accurately. Data visualization should earn its space.

### Empty states

Current empty states are honest but visually austere. Improve them with:

- one existing outline icon at 28–36 px;
- a short heading;
- one explanatory sentence;
- one contextual link/action only when the page genuinely offers a next step.

Examples:

- History: `No flights detected yet` plus when the next poll is expected.
- Preview: `No panel render yet` plus a link to Config/Poll if appropriate.
- Airlines: `No unresolved prefixes` as a positive completion state, not merely an absence.

Do not use large generic illustrations or celebratory confetti in this operational tool.

### Buttons and controls

Define explicit variants rather than styling every submit button identically:

- primary: one main action per section/page;
- secondary: neutral action;
- quiet/ghost: theme, refresh, disclosure;
- destructive/session: sign out only needs destructive styling if product testing supports it;
- status action: refresh/retry with accompanying state.

Include small outline icons only where they improve recognition (`Refresh`, `Save`, `Sign out`). Do not add icons to every text button.

Primary buttons should feel intentional through color, weight, and placement—not through excessive width, gradient, glow, or shadow.

### Motion and interaction polish

Use motion to explain state changes:

- 120–180 ms color/border/shadow transitions;
- mobile menu height/opacity transition with a reduced-motion path;
- button pending state without spinner-only communication;
- save confirmation appearing without layout jump;
- chart active-point transition kept subtle.

Avoid:

- bouncing cards;
- large scale transforms;
- continuous pulsing status dots;
- parallax;
- animated gradients;
- motion on non-interactive content.

### Details that disproportionately improve perceived quality

- Ensure every icon uses the same stroke weight, optical size, and baseline.
- Align numbers vertically and use tabular numerals for timestamps/measurements.
- Use true minus signs and consistent units (`3.92 V`, `−77 mV`).
- Keep date/time punctuation and capitalization consistent.
- Give tables and cards intentional empty/loading/error states rather than changing height abruptly.
- Avoid orphaned one- or two-word final lines in helper copy where practical.
- Keep paragraph line length near 55–75 characters on large screens.
- Reserve monospace for identifiers and exact measurements, not full explanatory sentences.
- Use one border/shadow model consistently per surface level.
- Verify hover, focus, active, disabled, busy, success, warning, and error states as part of the component design—not after it.

### Aesthetic anti-goals

To protect the product identity, the follow-up UI-SPEC should explicitly reject:

- generic Bootstrap-like fieldsets and default browser-blue selected controls;
- a different card style on every page;
- heavy gradients or glassmorphism;
- excessive pills/badges;
- pure black/pure white dark-mode contrast;
- low-contrast beige-on-beige light mode;
- decorative charts that are less clear than a number/table;
- putting every secondary detail on the initial visual layer;
- adding a front-end framework solely to achieve the redesign;
- copying the physical e-paper palette so literally that the web UI loses readability.

### Visual acceptance criteria

A future visual phase should add these criteria alongside the functional audit gates:

- A first-time user can identify page purpose, current system state, and primary action within five seconds.
- Page title, section heading, primary value, body text, and metadata are visually distinguishable without reading their content.
- Light and dark themes each expose at least three clear surface levels.
- Non-interactive cards do not imply clickability through hover movement.
- Config no longer reads as three unstyled fieldsets stacked around generic submit buttons.
- Health's current verdict and battery condition are visible above the fold at representative desktop and mobile heights.
- History's most important fields are identifiable at a glance without every cell competing equally.
- Preview visually centers the panel render as the page's hero object.
- Empty states feel intentional but remain restrained.
- Every component state is reviewed with real screenshots in both themes and at mobile/desktop sizes.
- Final approval includes side-by-side before/after captures, not only isolated new screenshots.

## Detailed findings

### UXA-01 — Populated History overflows on desktop and hides its meaning on mobile

**Severity:** High  
**Primary user impact:** An operator cannot reliably scan recent flights without horizontal panning; at desktop width the entire document can become wider than the viewport.

#### Observed evidence

With three representative History rows rendered at a 1440 × 900 viewport:

- browser document client width: 1425 px;
- browser document scroll width: 1712 px;
- `.dashboard-main` left edge: 272 px;
- `.dashboard-main` rendered width: 1440 px;
- document-level horizontal overflow: 287 px.

At a 390 px mobile viewport:

- document width correctly remained 390 px;
- `.data-table-wrap` visible width was 342 px;
- the table's intrinsic width was approximately 1358 px;
- only the Timestamp column was visible without horizontal scrolling;
- Callsign, Type, Route, State, Corroboration, and Runway were all off-screen.

The mobile result technically permits horizontal scrolling, but the interaction does not expose the information hierarchy of a flight. A user sees three timestamps and a subtle scrollbar, not three recognizable flight records.

#### Likely cause

- `companion/static/style.css:594-601` gives `.data-table-wrap` horizontal scrolling and `.data-table` `min-width: max-content`.
- `companion/static/style.css:961-965` gives `.dashboard-main` `max-width: 1440px` and `margin: 0 auto`, but no explicit `width: 100%`/`max-width: 100%` constraint relative to its grid track.
- The table's intrinsic max-content width can therefore influence the grid item's used size on populated History.
- `companion/pages/history_page.py` always renders the same seven-column table at all breakpoints.

#### Recommended direction

Treat the desktop overflow bug and the mobile information-design problem as two related but distinct tasks:

1. Constrain the desktop grid item and table wrapper so intrinsic table width can never expand the document.
2. Design a mobile History representation around flight records rather than around a desktop table.

Preferred mobile pattern:

- one compact card/list row per flight;
- callsign and relative time as the primary line;
- route and state as the secondary line;
- aircraft/airline, corroboration, runway, hex, and absolute timestamp in a compact details region;
- retain the desktop table at a sufficiently wide breakpoint.

If the table is deliberately retained on mobile, add a strong scroll affordance, keep at least the flight identity sticky/visible, and prove with usability testing that the remaining fields are discoverable. A barely-visible horizontal scrollbar alone is not sufficient.

#### Acceptance criteria

- No document-level horizontal scrolling at 960, 1024, 1280, 1440, or 1920 px with populated History data.
- `.data-table-wrap` may scroll internally on desktop only when truly necessary; the sidebar and page heading remain fixed within the viewport.
- At 320, 375, 390, and 768 px, a user can identify each flight's callsign, relative time, route, and state without horizontal scrolling.
- The mobile presentation preserves access to all seven existing data categories.
- Long airline names, missing routes, long corroboration labels, and maximum-length timestamps do not overflow their containers.
- Empty History retains its current simple empty-state behavior.
- A regression test asserts that the History page emits the chosen responsive structure/classes.
- A real browser check asserts `document.documentElement.scrollWidth <= document.documentElement.clientWidth` at every target viewport.

#### Likely files

- `companion/static/style.css`
- `companion/pages/history_page.py`
- `companion/test_view_pages.py`

### UXA-02 — The closed mobile menu is visually hidden but remains exposed semantically

**Severity:** High  
**Primary user impact:** Keyboard and screen-reader users can encounter navigation links and theme buttons that are visually absent.

#### Observed evidence

At 390 × 844 with the hamburger closed:

- the panel had `max-height: 0` and `overflow: hidden`;
- the toggle correctly exposed `aria-expanded="false"`;
- the accessibility/DOM snapshot still contained the full Primary navigation and all three theme buttons;
- the panel has no `hidden`, `inert`, or synchronized `aria-hidden` state.

- Preview/gallery `<img>` elements have no `width`/`height` or reserved `aspect-ratio` container.
- Gallery images have no `loading="lazy"` or `decoding="async"` hint.
- Gallery entries are images only, not links, so opening/zooming an individual full render is less discoverable.

#### Recommended direction

- Reserve the known panel aspect ratio before image arrival.
- Keep the primary live preview eager/high priority.
- Lazy-load below-the-fold gallery images and allow asynchronous decoding.
- Consider linking each gallery tile to its own image route for native open/zoom/save behavior, with a clear accessible name.

#### Acceptance criteria

- Populated Preview has negligible cumulative layout shift.
- The primary preview loads eagerly; off-screen gallery images load lazily.
- Image failure has an honest visible fallback rather than leaving an empty card.
- A gallery item can be opened at useful size with keyboard and pointer.
- No external image or script dependency is introduced.

#### Likely files

- `companion/pages/preview_page.py`
- `companion/static/style.css`
- `companion/test_view_pages.py`

### UXA-17 — Display limits are silent and can make partial data look complete

**Severity:** Low  
**Primary user impact:** Operators can mistake the latest subset for the full retained history.

#### Observed evidence

- History retains data indefinitely but displays at most 50 events.
- Battery Health displays at most 20 readings.
- Preview displays at most 12 gallery renders.
- The visible pages do not say `Latest 50`, `Last 20 readings`, or `Showing 12 most recent renders`.
- There is no pagination or route to older retained entries.

#### Recommended direction

- Label every bounded dataset with its display window.
- If older data has diagnostic value, add pagination or a deliberate `Older entries` route.
- If older data is intentionally inaccessible, state that the view is a recent snapshot and point to the authoritative diagnostic path.

#### Acceptance criteria

- A bounded list always states its limit/window in visible copy.
- The empty state does not mention a limit unnecessarily.
- The UI distinguishes `no older data exists` from `older data exists but is not shown` when that distinction can be computed cheaply.
- Pagination/filtering, if added, preserves deterministic newest-first ordering.

#### Likely files

- `companion/pages/history_page.py`
- `companion/pages/health_page.py`
- `companion/pages/preview_page.py`
- relevant page test harnesses

### UXA-18 — Expert/operator workflows have no acceleration layer

**Severity:** Low / optimization after core fixes  
**Primary user impact:** Once data volume grows, repeated diagnosis requires scanning rather than narrowing or navigating directly.

#### Opportunities

- History has no callsign, state, corroboration, runway, or time-range filter.
- Airlines has no prefix search, even though it can contain a long unresolved registry.
- Desktop sidebar is not sticky, so navigation can leave the viewport on long Health pages.
- Gallery captions are filenames rather than task-oriented dates/states.
- No page provides copy-to-clipboard actions for callsigns, hex IDs, or full timestamps.

These are not prerequisites for a correct interface. They are the difference between a pleasant small dataset and a truly efficient daily operations tool.

#### Recommended direction

Only add the accelerators justified by real usage:

- client-side filtering over the already-rendered bounded History/Airlines rows;
- sticky desktop navigation for long pages;
- task-oriented gallery captions using capture time;
- native links or copy actions for technical identifiers;
- persist filters in the query string when deep-linking a diagnosis is useful.

Avoid adding a generic dashboard framework or complex state layer for these small datasets.

#### Acceptance criteria

- Any filter has a visible label, clear/reset action, result count, empty result state, and keyboard operation.
- Query parameters are validated and never affect filesystem paths or raw SQL construction.
- Sticky navigation does not create nested scrolling or obscure content at 200% zoom.
- Copy actions provide non-intrusive success feedback.
- Features are omitted if user testing does not demonstrate a recurring need.

## Recommended follow-up phase boundary

The follow-up should be a focused UX/accessibility hardening phase, not another open-ended visual redesign. It should preserve the Phase 06.6.1 identity while correcting structural behavior, information hierarchy, and operator copy.

### In scope

- History desktop containment and mobile representation.
- Mobile navigation semantic closed state and keyboard behavior.
- Dedicated login shell, deep-link return, visible logout, and login-form accessibility.
- Light-theme contrast/token correction.
- Health anomaly summary and chart/table ordering.
- Human-readable timestamps, states, runway labels, and removal of internal planning identifiers.
- Feedback roles/focus behavior.
- Heading hierarchy, active-page semantics, skip link, control accent, and duplicate LED labeling.
- Battery-chart keyboard model with no more than one normal Tab stop.
- A genuinely visible mobile navigation fallback when JavaScript is unavailable.
- Page-freshness signaling for monitoring views.
- Warning-versus-error propagation into navigation and banners.
- Manual-poll pending state and server-side concurrent-run exclusion.
- Transparent display-window labels for bounded datasets.
- Preview/gallery image layout stability and loading hints.
- Explicit language decision.
- Real browser/device verification with populated data.

### Out of scope unless separately approved

- New backend data sources.
- Per-user accounts or role-based authorization.
- A client-side framework or build system.
- Redesigning the physical panel artwork.
- Changing poll, detection, corroboration, or battery business rules.
- Editing production data during visual verification.
- Replacing the established serif/terracotta brand direction wholesale.
- Adding new hardware themes before their real-glass validation.

### Viewports

Test at minimum:

- 390 × 844
- 768 × 1024
- 959 px wide (last mobile breakpoint)

At each width, assert there is no document-level horizontal overflow. Any intentional internal table scrolling must be visually discoverable and scoped to its component.

- Auto with dark system preference.
- Explicit Light.
- Explicit Dark.

- Fresh install / no data.

- Twenty battery readings.

- Session expiry while submitting a changed form.

### Keyboard checks

- Skip link reaches main content.
- Closed mobile menu descendants are skipped.
- Open menu exposes links in logical order.
- Escape closes and restores focus.
- No-JS mobile navigation remains visibly operable.
- Active page is announced.

- The battery chart adds no more than one normal Tab stop and exposes its chosen arrow-key model.

### Accessibility checks

- WCAG AA contrast for all normal text.
- 3:1 contrast for essential component boundaries/focus states.
- 200% zoom without lost content or two-dimensional page scrolling.
- One Primary navigation landmark exposed at a time.
- One page H1.
- Ordered heading hierarchy.
- Labels and group names remain unique and non-redundant.
- Status/error feedback has an appropriate programmatic role.
- Content language matches the `lang` attribute.
- Reduced-motion behavior does not leave the mobile menu in an intermediate state.
- Warning-only and error Health states remain programmatically and visually distinct.
- Long-lived monitoring pages communicate their own freshness.

### Production sign-off

After automated and local checks pass, the developer should authenticate personally in the production browser and perform a read-only walkthrough of all five pages. Any save, poll trigger, or logout verification that changes real external state should be an explicit checkpoint in the plan rather than an incidental test step.

## Proposed minimum exit criteria

The follow-up phase should not be considered complete until all of the following are true:

1. Populated History never expands the document horizontally on desktop.
2. Core flight identity is readable on mobile without horizontal scrolling.
3. Closed mobile navigation is absent from the accessibility tree and tab order.
4. Login preserves the originally requested protected route.
5. Login does not show unusable protected navigation.
6. A visible logout action exists at desktop and mobile widths.
7. All light-theme normal text and button labels meet WCAG AA contrast.
8. No planning IDs or raw underscore-delimited state values appear in the visible interface.
9. Health identifies the active anomaly and places the trend chart before raw readings.
10. Save, poll, and authentication outcomes are programmatically announced.
11. Active navigation uses `aria-current` and a skip link reaches main content.
12. The battery chart adds no more than one normal Tab stop.
13. Mobile navigation remains visibly operable when JavaScript is disabled.
14. Warning-only Health state does not render as a global error state.
15. Long-lived Health and Preview pages communicate or refresh their own freshness.
16. Two overlapping manual-poll submissions cannot execute two poll cycles concurrently.
17. Bounded History, battery, and gallery datasets state what subset is shown.
18. The full viewport/theme/data-state verification matrix is recorded in the phase verification report.

## Open product decisions for discussion before planning

The following questions materially affect the UX and should be decided in the future phase's CONTEXT rather than guessed during implementation:

1. Is the companion interface English-only, French-only, or bilingual?
2. On mobile, should History use always-expanded compact cards or disclosure rows?
3. Should full ISO timestamps remain visible anywhere by default, or only in technical details?
4. Should the Theme hardware field remain an editable one-option fieldset until more themes ship, or become read-only status?
5. Should logout remain a GET for this single-user tool or move to POST as part of the authentication cleanup?
6. Should Health's raw battery table be collapsed by default or reduced to the latest few readings?
7. Is `Bring-up LED` operator terminology, or should it become a friendlier label such as `Diagnostic LED`?
8. Should monitoring pages refresh automatically while visible, or expose only explicit refresh plus a stale-view warning?
9. Should the battery chart use roving point focus, a single chart focus target, or become non-interactive with the table as its accessible equivalent?
10. Which bounded datasets need real access to older rows, versus a clear `latest N` label only?
11. Are History filters and a sticky desktop sidebar validated daily-use needs or optional post-hardening enhancements?

## Audit conclusion

Phase 06.6.1 succeeded at establishing a recognizable and substantially better visual system. The next phase should not restart the design. It should make the existing design trustworthy under real content, narrow viewports, keyboard/screen-reader use, and authentication transitions.

The four high-severity findings are concrete and reproducible. Addressing them first will remove the largest usability and accessibility risks. The medium findings then provide the path from a styled engineering console to a finished operator interface.
