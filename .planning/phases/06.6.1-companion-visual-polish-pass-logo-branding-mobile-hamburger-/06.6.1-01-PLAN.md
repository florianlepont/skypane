## Two things this plan settles that the spec left slightly open

### Reconciliation 1 — where the 2xl/3xl padding promotion actually lands

`06.6.1-UI-SPEC.md`'s Spacing Scale promotes `.page-content` to `2xl` (48px) top/bottom and `3xl` (64px) "left/right **at the content-column level**". Taken literally as one flat rule it would put 64px of side padding on a 375px phone, leaving 247px of content — which directly contradicts `06-CONTEXT.md` D-22's mobile floor that the same UI-SPEC restates as still binding.

**Decided here, do not re-derive:** the 2xl/3xl pair applies to `.dashboard-main` (the ≥960px content column — the "content-column level" the spec names), and the base `.page-content` rule gets a smaller but still genuinely airier bump. Concretely:

- base `.page-content`: `var(--space-xl) var(--space-lg) var(--space-2xl)` (was `0 var(--space-lg) var(--space-lg)`) — the top padding goes from zero to 32px, the bottom from 24px to 48px, sides stay at a phone-safe 24px.
- `.dashboard-main` (inside the existing 960px block): `var(--space-2xl) var(--space-3xl)` (was `var(--space-lg) var(--space-3xl) var(--space-2xl)`) — exactly the promotion the spec asks for, on the element the spec names.

Write that reasoning into a comment above the base rule so the next reader does not "fix" the apparent mismatch with the spec table.

### Reconciliation 2 — the horizontal nav strip is deleted, not merely hidden

`06.6.1-UI-SPEC.md`'s Component Patterns says the dropdown lives "alongside `_nav_html()`/`sidebar_nav()`" (reading as three live renderers), while its Layout Contract says "the horizontal nav-bar itself is gone below 960px" and calls the 480px rule "dead code … remove it rather than leaving an orphaned, unreachable CSS rule". Those cannot both be true: the existing 960px block already sets `.site-header { display: none }` at desktop width, so a strip that is also gone below 960px is visible at no width at all.

**Decided here:** the horizontal strip's selectors are **removed** from this stylesheet, and plan 05 removes the matching builder from `companion/layout.py`. The live renderers after this phase are two — the desktop sidebar and the mobile dropdown. This supersedes D-00's crush-bug fix (commit `b90ed88`) by deleting the element that had the bug, rather than re-tuning its flex sizing a second time; say so in the comment that replaces it, and keep D-00's CSS-Flexbox-4.5 explanation in that comment as the reason the pattern was abandoned rather than repaired.

## Scope note — one ROADMAP goal item is deliberately NOT covered here

`ROADMAP.md`'s Phase 06.6.1 goal line lists "smaller theme-toggle buttons on desktop". That item survives in neither `06.6.1-CONTEXT.md`'s locked decisions (D-01..D-06) nor its `<domain>` scope paragraph, and `06.6.1-UI-SPEC.md` — the approved, checker-signed contract that supersedes the goal line — instead **restates the 44px minimum tap target as still in force on every interactive element**, theme-picker buttons included. Shrinking them here would contradict the approved contract.

**Do not implement it.** The theme picker's sizing is unchanged by this plan except for inheriting `--radius-control`. The gap is surfaced to the developer in this planning run's return; if they want it, it needs a fresh decision about the desktop-only tap-target exception, not an executor's improvisation.
