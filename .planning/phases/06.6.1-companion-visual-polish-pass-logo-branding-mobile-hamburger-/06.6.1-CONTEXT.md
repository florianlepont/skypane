# Phase 06.6.1: Companion visual polish pass - Context

**Gathered:** 2026-08-29
**Status:** Ready for planning

<domain>
## Phase Boundary

A visual/UX refresh of the SkyPane companion web app, raised from real-device testing during 06.5-03's phone verification — the developer had never actually looked at 06.3/06.4/06.5's shipped UI on real hardware before that session, and found real issues the automated visual sign-off (computed-style/DOM inspection, no human eyes) missed. Scope: header branding/wordmark, mobile navigation (currently a horizontally-scrollable strip that real-device testing found effectively hides most tabs), a broader aesthetic direction shift (warmer, more "crafted" feel, referenced against Goodreads), Health page density/redundancy cleanup, and data-density fixes on History's table and the battery trend chart. This is a genuine visual redesign iteration on top of 06.3's original pass, not a light polish — the discussion surfaced a real color/typography direction change, not just spacing tweaks.

</domain>

<decisions>
## Implementation Decisions

### Bug found and already fixed (not part of this phase's remaining work)
- **D-00:** The mobile nav-bar being crushed to ~26px by the theme-form (a real CSS flexbox bug: `.nav-bar`'s `overflow-x: auto` zeroes its automatic minimum width per spec, letting `.theme-form` — which has no such override — take all available space) was found and fixed during 06.5-03's real-device testing. Fixed in commit `b90ed88` on `companion/static/style.css` (`.nav-bar` given `flex: 1 1 200px`, `.site-header` given `flex-wrap: wrap`). This phase's own navigation work builds ON TOP of that fix, replacing the horizontal-scroll pattern itself (see D-05) — it does not need to re-fix the crush bug.

### Branding
- **D-01:** No logo icon. Keep "SkyPane" as a text wordmark, but redesign its typography/spacing to feel more crafted (not just default bold sans-serif) — no icon asset to design, source, or maintain.

### Visual direction (the "Goodreads" reference, unpacked)
- **D-02:** User selected all four attributes as resonating: cards with visible relief (soft shadows, more breathing room between blocks — moving away from "flat form" feel), warmer typography for headings, more vivid/varied color, and an overall airier layout with more whitespace and stronger visual hierarchy between titles and content.
- **D-03:** Typography: a warm serif face for page/section **headings only** (`<h1>`/`<h2>`-equivalent text-heading elements) — not the whole page. Body text, data tables (History, Battery trend), and any dense/tabular content stay on the current sans-serif for legibility. Concretely: `text-heading` gets a new serif font-family token; `text-body`/`text-label`/`.mono` classes are untouched.
- **D-04:** Color: the palette is explicitly in scope for this phase (not locked to 06.3's tokens). New direction: introduce a **new primary accent color — warm orange/amber** — replacing or supplementing the current single blue accent (`--color-accent`). **Constraint the planner/executor must respect:** the new accent must stay visually distinct from the existing semantic status colors already in use (`dot--ok` green, `dot--warn` orange/amber-ish, `dot--error` red — check `companion/static/style.css`'s current `--color-*` token values before picking the exact orange/amber hue, since an accent too close to the warn-status color would make status dots and accent-colored UI chrome ambiguous at a glance). Density: the airier-layout direction (D-02's "mise en page plus aérée") applies **globally**, not just to the specific pages the developer flagged — this is broader than a targeted fix.

### Process
- **D-05 (locked, drives sequencing):** Given this reopens the same territory as 06.3's original UI-SPEC.md-driven redesign, and given 06.3's own automated visual sign-off missed real defects a human only caught on real hardware, this phase goes through the **same formal rigor 06.3 used**: a `/gsd-sketch` throwaway HTML prototype pass first (explicitly requested by the developer, "meme rigueur et sketch pour proto") to visually validate the new direction (typography, color, card treatment, hamburger nav) cheaply before committing, THEN a proper `/gsd-ui-phase` UI-SPEC.md design contract (validated by `gsd-ui-checker` against its 6 quality dimensions) before planning/execution. Do not skip straight to `/gsd-plan-phase` from this CONTEXT.md alone — the next step is `/gsd-sketch`, not `/gsd-plan-phase`.

### Mobile navigation
- **D-06:** Replace the horizontal-scroll nav strip with a real hamburger menu below 960px (or whatever breakpoint the sketch/UI-SPEC settles on) — real-device testing found the scroll-strip pattern (even after the D-00 crush-bug fix) still effectively hides Health/Airlines/History/Preview behind an undiscoverable swipe; only 3-4 tabs are visible at once on a real phone screen.

### Claude's Discretion
- Exact hamburger icon/interaction details (☰ icon, overlay vs. push-down, close-on-outside-click/Escape, where the theme picker relocates to inside the open menu) — developer explicitly deferred this to standard UX judgment, to be nailed down concretely in the sketch/UI-SPEC step, not guessed now.
- Exact serif font choice and exact orange/amber hex value — to be proposed in the sketch prototype for visual approval, not decided blind in this discussion.
- Card shadow/radius specifics — "a little relief," not a precise spec; sketch will make this concrete.

</decisions>

<code_context>
## Existing Code Insights

### Reusable Assets
- `companion/static/style.css`'s existing custom-property tokens (`--color-*`, `--font-*`, `--space-*`, `--font-display-size`) — the new serif heading font and new accent color should be added as new tokens alongside these, not as one-off hardcoded values, matching 06.3's own established discipline.
- `layout.status_dot()` (`companion/layout.py`) — the existing 3-state (`ok`/`warn`/`error`) status pattern this phase's new Overview-tile icons and Health nav-tab indicator should compose with, not duplicate.
- `layout.stat_tile()` — the dashboard-grid card component from 06.3 that Health/Airlines already use; the new card "relief" treatment (D-02/D-03) likely lives here as a shared style change rather than being redone per-page.

### Established Patterns
- `.theme-form .theme-option` / `button[type="submit"]` CSS specificity collision (06.3-REVIEW.md WR-finding) — any new interactive control (hamburger toggle button, new accent-colored buttons) must be checked against this exact class of bug before shipping.
- `.dashboard-sidebar` / `.nav-bar` dual-copy pattern (`companion/layout.py`'s `page_shell()` renders both a horizontal nav and a vertical sidebar nav, CSS alone decides which is visible at which width) — the new hamburger menu is a THIRD navigation rendering mode for the <960px range, replacing the horizontal nav-bar's role at that breakpoint specifically. Desktop's sidebar nav (>=960px) is unaffected by this phase.
- Real-device testing gap: 06.3/06.4/06.5's verification relied on `read_page`/`get_page_text`/`javascript_tool` computed-style inspection (screenshots were unavailable in that session) — no human ever looked at the actual rendered pages until 06.5-03's real-phone test. This phase's own verification MUST include actual visual sign-off (screenshots or a real device/browser), not just computed-style assertions, to avoid repeating the gap that caused this phase to exist.

### Integration Points
- `companion/layout.py::page_shell()` — where the hamburger toggle button and its markup get added (alongside the existing `_nav_html()`/`sidebar_nav()`/`_theme_form_html()` builders).
- `companion/pages/health_page.py::render()` — where the anomaly-banner text removal, Overview-tile icons, and battery-chart full-width layout all land.
- `companion/app.py` — if the Health nav-tab notification indicator needs to know "is there an active anomaly" outside of the Health page's own render, this may need a small `ctx` addition (check how `ctx["runway_images"]` was threaded through in 06.4 as the precedent for adding a new cross-page ctx signal).
