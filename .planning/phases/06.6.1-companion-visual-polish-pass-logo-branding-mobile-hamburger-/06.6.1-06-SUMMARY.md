## Confirmed defects — root-caused, not fixed (checkpoint discipline)

### Gap 1: Hamburger dropdown covers content instead of pushing it down (item 2)

**Traces to:** Plan 05 (`companion/static/style.css`, `.mobile-nav` rule).

**Root cause, confirmed by reading the shipped CSS:** `.mobile-nav` is declared `position: absolute`. An absolutely-positioned element is removed from normal document flow — it cannot push sibling content down, only overlay on top of whatever follows it in the DOM. D-06 and the UI-SPEC both call for the panel to push content down, matching sketch 002's winning Variant C behavior ("Header dropdown — pushes content down"). This is not a device quirk or a judgment call; it is a direct consequence of the positioning scheme chosen.

**This traces back further than plan 05's own execution.** `.claude/skills/sketch-findings-skypane/references/mobile-navigation.md` (written during this phase's own sketch wrap-up) states: *"`position:absolute` on the dropdown plus `position:relative` on the header is correct and sufficient here (unlike `position:fixed`, `absolute` IS contained by the nearest positioned ancestor without needing a `transform`/`filter` trick)."* That statement is accurate about *containment* but wrong about *flow*: absolute positioning solves the "stay inside the phone frame" problem sketch 002's demo had, but it does not achieve "pushes content down" — that requires the element to stay in normal flow (e.g. `position: static`/default, animated via `max-height`, as the plan-level CSS pattern in the same reference file's code sample actually shows using `max-height` transition — but sketch 002's own demo wrapper used `position:absolute` for the *phone-frame containment trick*, and that detail leaked into the reference doc's general guidance for the real implementation). The reference doc's own guidance was internally inconsistent between its CSS pattern and its prose, and plan 05 followed the prose.

**Fix direction (for gap-planning, not applied here):** Remove `position: absolute` from `.mobile-nav`; keep it in normal document flow (default `position: static`, or `position: relative` purely for future-proofing without taking it out of flow) so the `max-height` open/close transition genuinely displaces the content below it, matching the already-correct CSS pattern shown in `mobile-navigation.md`'s own code sample.

### Gap 2: Health icons render oversized on mobile (items 9, 19)

**Traces to:** Plan 04 (icon sprite, `companion/pages/health_page.py`) colliding with a pre-existing rule from an earlier phase (`companion/static/style.css`).

**Root cause, confirmed by reading the shipped CSS:**
```css
.icon {
  width: 20px;
  height: 20px;
  flex: none;
  vertical-align: middle;
}
/* ... */
.stat-tile svg {
  width: 100%;
  height: auto;
}
```
`.stat-tile svg` predates this phase — it exists specifically to shrink the battery sparkline's SVG (which carries fixed `width="300" height="60"` attributes) down to fit inside a 240px-floor tile. Plan 04's new `<svg class="icon">` elements are also descendants of `.stat-tile`, so `.stat-tile svg` matches them too. `.stat-tile svg` (specificity 0,1,1 — one class, one element) beats `.icon` (specificity 0,1,0 — one class) regardless of source order, so every icon stretches to `width: 100%` of its tile — exactly the giant-checkmark rendering in the developer's screenshot. This is a selector-collision bug of the same general class this project has hit repeatedly (06.3's `.page-section`/`button[type=submit]` cascade bugs, 06.3's mobile nav-bar crush) — a new element unexpectedly falling inside an existing broad selector's reach.

**Fix direction (for gap-planning, not applied here):** Scope `.stat-tile svg`'s sizing override to the sparkline specifically (e.g. target a sparkline-only class, or exclude `.icon` via `:not(.icon)`), so it no longer captures the icon SVGs. `.icon`'s own `width: 20px; height: 20px` rule is correct and does not need to change.
