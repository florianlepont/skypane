## Accomplishments
- `companion/static/nav-dropdown.js` — the project's second JavaScript file, following every convention `battery-trend.js` set: one strict-mode IIFE, ES5-safe, no dependency, no network call, no timer, no persistent state; reads the open state from `aria-expanded` (the single source of truth, keeping the visual and announced states physically the same attribute) and closes on a second toggle click or on Escape (scoped to open-only), returning focus to the toggle

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 - Bug] Task 2's own verify script's `'_nav_html' not in src` assertion is unsatisfiable together with the plan's own required symbol name `_mobile_nav_html`**
- **Found during:** Task 2 self-verification
- **Issue:** The plan's Artifacts table and Task 2's acceptance criteria both mandate a new function named exactly `_mobile_nav_html`. That identifier necessarily contains `_nav_html` as a trailing substring, so the plan's own literal `assert '_nav_html' not in src` check can never pass once the required new function exists — regardless of implementation quality.
- **Fix:** For self-verification, substituted a corrected assertion testing the real intent (`'def _nav_html(active):' not in src` — the *old* renderer's exact definition is gone) rather than the naive substring ban. The shipped code satisfies both the plan's required symbol name and the genuine "old renderer fully removed" invariant.
- **Files modified:** None (verification-script-only issue; `companion/layout.py`'s actual content was already correct).
- **Verification:** Corrected inline check passes; `companion/layout.py` contains no `_nav_html(active):` definition and no reference to the removed strip's CSS class tokens (`nav-tab nav-tab`, `class="nav-bar"`).
- **Committed in:** `505ed1a` (Task 2 commit)

**2. [Rule 1 - Bug] Task 3's own verify script's naive `doc.index(L.MOBILE_NAV_ID)` slice lands inside the toggle's `aria-controls` attribute, not the real panel, because the two must share the literal id text**
- **Found during:** Task 3 self-verification
- **Issue:** `aria-controls` on the toggle must equal the panel's own `id` (a correct, required ARIA reference — Task 2's own acceptance criteria mandates it), and the toggle necessarily precedes the panel in source order (also mandated). A bare `doc.index(MOBILE_NAV_ID)` search therefore always matches the earlier `aria-controls="mobile-nav"` occurrence first, pulling the toggle's own icon markup (which carries `aria-hidden="true"`, containing the substring `hidden`) into the "panel" slice and failing the plan's literal `'hidden' not in panel` assertion — even though the real panel carries no `hidden` attribute at all.
- **Fix:** In the actual `companion/test_companion_app.py` checks (`_dropdown_contents_and_order`, `_dropdown_survives_with_javascript_disabled`, the retargeted dashboard-shell and notification-dot checks), anchored the panel slice on the more specific `'id="%s"' % MOBILE_NAV_ID` needle instead of the bare id text — this string is unique to the panel's own opening tag and does not collide with the toggle's `aria-controls` attribute (which reads `aria-controls="mobile-nav"`, not `id="mobile-nav"`). Used the same corrected needle when self-verifying with the plan's own `<verify>` script.
- **Files modified:** `companion/test_companion_app.py` (the checks were written correctly from the start using this needle; this entry documents why the naive form in the plan's own bash `<verify>` block needed the same substitution when run manually).
- **Verification:** All four Task 3 checks pass against the real panel; the corrected self-verification script (see the executor's own `-c` run in the transcript) confirms `'hidden' not in panel` and `'display:' not in panel` genuinely hold once anchored correctly.
- **Committed in:** `bdee089` (Task 3 commit)

**3. [Rule 1 - Bug] A third pre-existing check (plan 06.6.1-04's `_health_nav_notification_dot`) broke alongside the two the plan named, and needed retargeting too**
- **Found during:** Task 2 → Task 3 transition (running the full suite after Task 2)
- **Issue:** Task 3's own `read_first` section names only two checks as "the two checks Task 2 breaks" (`_page_shell_marks_only_the_active_nav_tab` and the dashboard-shell check). Empirically, a third pre-existing check from plan 06.6.1-04 — `_health_nav_notification_dot`, which asserted the Health notification dot appears exactly once — also broke, since `_mobile_nav_html()` now legitimately renders the dot a second time (once per nav renderer), exactly as this plan's own Task 2 acceptance criteria already specifies ("the document contains exactly two notification dots, one inside each Health link").
- **Fix:** Retargeted `_health_nav_notification_dot` to expect two occurrences of `NAV_NOTIFICATION_CLASS`/`HEALTH_ALERT_SUFFIX_TEXT` (one per renderer) and to confirm the dot sits inside the Health link in *both* the sidebar and the dropdown, keeping both original directional assertions (present when true, absent when false/omitted, never on another link) intact.
- **Files modified:** `companion/test_companion_app.py`
