<objective>
Close A-32 (D-15), A-33 (D-16) and A-34 (D-17): make the login lockout
self-releasing, stop signing session tokens with the raw password, revoke a token
on Sign out, and make the `Secure` cookie flag explicitly opt-out-able for a
plain-http LAN/dev run instead of silently bouncing that run back to /login.

Purpose: one shared password means a household member who fat-fingers it five
times currently locks the owner out forever (A-32); and a stateless HMAC keyed by
the password itself turns any leaked cookie into an offline guessing oracle
(A-33). Both are the highest-severity open auth findings in the audit.
Output: a hardened `companion/auth.py`, a revocation check wired into the single
auth predicate in `companion/app.py`, a documented dev-only env flag, and new
harness checks for every one of those behaviours (none exist today).
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| public internet -> `POST /login` | untrusted password attempts; the only access control on the whole companion |
| browser cookie jar -> every authenticated route | the session token is the sole bearer credential; it crosses this boundary on every request |
| process environment -> cookie flags | `SKYPANE_COMPANION_INSECURE_COOKIES` is operator-controlled config that can weaken transport security if it fails open |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-19-01 | Information Disclosure / Elevation of Privilege | `auth.issue_session_token()` / `verify_session_token()` | mitigate | Task 2: HMAC-as-KDF signing key from `configured_password()` + a per-process `secrets.token_bytes(32)` salt that never leaves the process, so a leaked `(expiry, signature)` pair is not an offline password oracle. Proven by the new "old raw-password signature does not verify" check |
| T-19-02 | Denial of Service | `auth.LoginThrottle.record_failure()` | mitigate | Task 1: reset the counter once the window has elapsed, so a lockout can never become permanent and one household member cannot permanently lock out another (A-32). Proven by the two new post-window checks |
| T-19-07 | Elevation of Privilege | Sign out / `app._is_authenticated()` | mitigate | Task 2: `auth.revoke()` on the logout route + `auth.is_revoked()` inside the single `_is_authenticated()` predicate; proven by the real-HTTP cookie-replay-after-logout check |
| T-19-03 | Information Disclosure | `auth.session_set_cookie_header()` / `logout_set_cookie_header()` | mitigate | Task 3: `Secure` stays on unless the env var is EXACTLY "1" (fail closed), and the env template documents it as never-set-in-production. Proven by the "true" fail-closed check |
| T-19-14 | Denial of Service (resource exhaustion) | `auth._REVOKED` revocation set | mitigate | Task 2: entries are pruned by their own embedded expiry on every `revoke()`/`is_revoked()` call, so the set cannot grow unbounded on a long-running process; proven by the pruning check |
| T-19-15 | Tampering (race) | `auth._REVOKED` under ThreadingHTTPServer | mitigate | Task 2: a `threading.Lock()` guards every read-modify-write, mirroring `app.py`'s existing `_POLL_LOCK` precedent rather than relying on GIL atomicity |
| T-19-SC | Tampering (supply chain) | package-manager installs | n/a | zero packages installed; `secrets`, `hmac`, `hashlib`, `threading` are all stdlib |
