<objective>
Prove ROADMAP success criterion 2 on real hardware: when the stub server is unreachable, the device backs off exponentially instead of retrying at a fixed interval - and its place on that curve survives a total loss of power, not merely a deep sleep.

Plan 01-03 already proved the arithmetic. `fp_backoff_seconds` is asserted across its whole input domain by a pure-C test that runs on the laptop in under a second. What no laptop test can answer is whether a real device, waking from real deep sleep, with a real radio and a real NVS partition, actually walks that curve. That is what this plan observes, and per 01-VALIDATION.md's Per-Task Verification Map it is manual and hardware-in-the-loop by nature - the only automation available is machine-checking the log the hardware produced.

The single most important observation here is not the doubling. It is the power cycle. Plan 01-05 persists the failure counter in NVS specifically because RTC memory survives deep sleep but not a brownout or a battery disconnect, and a counter that resets on brownout is exactly the counter that lets a device hot-loop until the battery is flat. A firmware that used RTC memory would pass a doubling observation perfectly and still fail in the field. This plan therefore removes power entirely - with the battery deliberately not attached, so the RTC domain really does go dark - and asserts the curve picks up where it left off.

A note on a forward reference in the existing plan set: `stub-server/README.md` (written by 01-02) names plan 01-07 as the consumer of the stub server's telemetry stdout. This plan does consume that stream, for the baseline healthy wake that establishes a known starting state. The sustained battery telemetry consumption that README also describes belongs to plan 01-08, which 01-05 names as the plan that measures through that channel. Both plans read the same stream; nothing in 01-02 needs changing.

Purpose: DEVICE-03's exponential-backoff clause, observed rather than asserted.
Output: Two timestamped console logs, a checker that produced the verdict from them, and a recorded observation document.
</objective>

  <action>
    Write `hardware/logtools.py`, a Python 3 stdlib-only script with three subcommands. Import only from `argparse`, `datetime`, `os`, `re`, `subprocess`, `sys`. No pip install: the phase's zero-external-install property holds here as everywhere else, and the script must run on the system Python 3.9.6 already on this machine.

    Subcommand `stamp` reads lines from standard input, writes each one to standard output prefixed with the local wall-clock time as an ISO-8601 string with second resolution inside square brackets followed by a single space, and flushes after every line. Line-at-a-time flushing is not a nicety here - the capture runs for over an hour through a pipe, and a block-buffered writer would produce a file whose timestamps all cluster at the moment the pipeline was torn down, which silently destroys the interval evidence.

    Subcommand `check-backoff` takes one or more log file paths, read and concatenated in the order given, and the flags `--min-steps` defaulting to 5, `--tolerance` defaulting to 15 (a percentage), `--expect-persist` and `--expect-reset` as booleans. It parses every line with a regular-expression search rather than a match, because each line carries a host timestamp prefix from `stamp` and an ESP log prefix before the contract text. Extract, per line: an optional leading bracketed ISO timestamp; a wake event with its reason token and boot count; a successful poll with its sleep seconds and hash-skip flag; a failed poll with its step token, backoff counter and sleep seconds; and a sleep-entry event with its sleep seconds.

    Drive the whole check from one small state machine over that event stream, holding a single expected counter value that starts at zero. On a successful poll the expected counter resets to zero. On a failed poll the reported backoff counter must equal the expected value, and then the expected value increments. A wake event never touches the expected counter - and that is the entire point of the `--expect-persist` check, because a wake with reason `power-on` that is followed by a failed poll reporting zero is precisely the RTC-memory symptom this plan exists to rule out.

    Implement these checks, each printing one line reading either PASS followed by the check name or FAIL followed by the check name and the concrete reason, with a final summary line of the form `backoff: N/N checks pass` and exit code 0 only when every check passed:

    First, at least `--min-steps` failed polls are present across the supplied logs.

    Second, every failed poll reports a sleep interval equal to the curve value for its own backoff counter, where the curve is the table 300, 600, 1200, 2400, 4800, 9600, 19200 for counter values 0 through 6 and 21600 for anything higher. Hold that table as a literal in this script and add a comment naming `firmware/main/backoff.c` as the authority and `firmware/tests/run_host_tests.sh` as the thing that proves it - this script checks the device against the curve, it does not define the curve.

    Third, every failed poll's reported backoff counter equals the state machine's expected value, so the sequence has no gaps and no resets that a success did not cause.

    Fourth - the direct form of ROADMAP criterion 2 - the number of distinct sleep intervals seen across the failed polls is at least four. A fixed-interval retry produces exactly one distinct value however many times it retries, so this check is what separates the behaviour under test from the behaviour it must not be.

    Fifth, every failed poll is followed by a sleep-entry event reporting the same interval, so the value the device logged is the value it actually armed.

    Sixth, when timestamps are present, the wall-clock gap between one wake event and the next lies between the previously armed interval reduced by the tolerance percentage and the same interval increased by the tolerance percentage plus sixty seconds of grace. The grace absorbs the awake time - joining the radio and failing a connection - which is additive on top of the sleep, and the tolerance absorbs the drift of the internal RTC oscillator. Skip this check with an explicit SKIP line, not a silent pass, when the logs carry no timestamps.

    Seventh, with `--expect-persist`, at least one wake event with reason `power-on` is followed by a failed poll, and every such failed poll reports a non-zero backoff counter matching the expected value carried across the power cycle.

    Eighth, with `--expect-reset`, at least one successful poll is followed later by a failed poll reporting backoff counter zero and sleep interval 300.

    Then write three fixture logs under `hardware/fixtures/`, each in the exact format `stamp` produces wrapped around the exact contract lines, with plausible timestamps consistent with the intervals they claim.

    `backoff-good.log` is a full healthy run: one successful poll, then failed polls at counters 0 through 4 with the matching intervals and sleep-entry lines and wake lines with reason `rtc`, then a wake with reason `power-on` followed by a failed poll at counter 5 with interval 9600, then a successful poll, then a final failed poll back at counter 0 with interval 300. Checked with both expectation flags it must pass every check.

    `backoff-fixed-interval.log` is the same wake and failure structure with every failed poll reporting counter 0 and interval 300 - a device that retries on a fixed timer. It must be rejected.

    `backoff-rtc-reset.log` is the good run up to the power cycle, but the failed poll after the `power-on` wake reports counter 0 and interval 300 - a device whose counter lived in RTC memory and was cleared when the rails went down. It must be rejected when `--expect-persist` is set.

    Subcommand `selftest` takes no arguments. It runs `check-backoff` against each of the three fixtures with the flags each one is meant to be judged under, asserts that the good fixture exits zero and both negative fixtures exit non-zero, prints one line per fixture stating the fixture name and whether its actual outcome matched the required one, and exits zero only when all three matched. A checker that has never been shown a bad log has not been tested, and this is the phase's own established standard - plan 01-02 proved its integrity gate by flipping a byte and truncating a buffer rather than by feeding it good input twice.
