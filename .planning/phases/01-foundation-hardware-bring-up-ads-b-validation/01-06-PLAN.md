<objective>
First light. Take the assembled XIAO ESP32-S3 Plus on the EE02 driver board from a sealed box to a picture on the glass, driven end to end by the Phase 1 firmware polling the local stub server - the moment the Walking Skeleton stops being a compile target and becomes a working device.

This plan carries the phase's single largest unknown. The EE02 board profile is flagged by its own authors as never having been driven against real hardware, and a wrong chip-select or power-enable value on this board does not fail cleanly - it drives the panel incorrectly, so the symptom is a wrong-looking picture rather than an error message. The first correct blit is therefore not a formality; it is the verification event that profile has been waiting for, and this plan is structured so a wrong picture is diagnosed rather than shrugged at.

Every task here needs a human physically present - unboxing, seating a connector, watching an e-paper panel take thirty seconds to refresh. None of it is autonomous, and pretending otherwise would produce a plan that stalls silently.

Purpose: DEVICE-03's first success criterion - a full wake, poll, download, display, deep-sleep cycle on real hardware.
Output: A picture on the glass, a captured console log proving how it got there, and a bring-up record.
</objective>

<task type="auto">
  <name>Task 2: Flash the image, verify it back, and capture the first boot</name>
  <files>firmware/flash.sh, firmware/monitor.sh, hardware/logs/first-light.log, hardware/BRINGUP-LOG.md</files>
  <read_first>
    - `hardware/BRINGUP-LOG.md` - the serial device path recorded in Task 1
    - `firmware/build.sh` - the container build whose artifact is being flashed, and the comment recording that flashing is deliberately native rather than containerised
    - `firmware/VENDOR.md` `## Log Line Contract` - the five fixed log-line shapes this task's capture is checked against
    - `stub-server/README.md` - the commands to generate a panel image, start the server, and print the laptop's LAN address
    - `.planning/phases/01-foundation-hardware-bring-up-ads-b-validation/01-RESEARCH.md` - the Supporting stack note that USB flashing from inside Docker Desktop on macOS is unreliable without extra passthrough setup, and Pitfall 4 on the ESP-IDF host Python environment
  </read_first>
  <action>
    Establish a host-side flashing tool. Docker Desktop on macOS does not pass USB serial devices into containers, so the container that builds the image cannot flash it. Install Espressif's `esptool` through Homebrew rather than through pip, which keeps this phase's zero-pip-install property intact. Confirm the installed tool reports its version, and record that version in the bring-up log. If Homebrew is unavailable, fall back to a native ESP-IDF install and use its bundled tooling, taking care to use a Python 3.12 environment - the reference project's own notes record that Python 3.9 is missing a required package for the ESP-IDF tooling and 3.13 is unsupported, and that neither failure mentions Python in its first line.

    Write `firmware/flash.sh`, an executable POSIX shell script with `set -e`. It resolves its own directory; requires the serial port as its first argument and refuses to run without one, with a message pointing at the `ls /dev/cu.*` method - never accept a wildcard or guess a port, because flashing the wrong device is not recoverable by re-running the script. It reads the flash offsets and the file list from the build directory's generated flash-arguments file so the offsets are never hand-typed. It flashes the bootloader, the partition table and the application. It then verifies the write by reading the application region back off the device and comparing it against `build-ee02/inkframe.bin` - a partial or corrupted flash must be caught here, not misdiagnosed later as a firmware bug. It prints the verification result and exits non-zero if verification fails.

    Write `firmware/monitor.sh`, an executable script taking the serial port as its first argument and an optional output path as its second, defaulting to a timestamped file under `hardware/logs/`. It opens the serial console at the ESP32-S3's default console baud rate and tees everything it receives to that file so the session is captured rather than scrolling away. Print the output path on start.

    Now run the first end-to-end attempt. Generate the palette panel image with the stub server's generator. Start the stub server serving that image with a sleep interval of 300. Print the laptop's LAN IPv4 address and confirm it matches the value in `firmware/main/secrets.h`; if it does not, correct `secrets.h` and rebuild, since a laptop's DHCP address changes and a stale address here presents as an unexplained connection failure. Confirm the Mac will not sleep during the run.

    Flash the device and immediately start the monitor, capturing to `hardware/logs/first-light.log`. Let the device complete at least one full wake. Watch for the five contract log lines in order: the wake line naming the reason and boot count, then either a successful poll line or a failure line naming the failing step, then the blit line, then the sleep-entry line.

    If the first attempt fails, diagnose from the failing step token rather than guessing. A `wifi` step means credentials or the radio; an `http` step means the LAN address, the port, or the Mac's firewall; a `status` step means the server rejected the request, which the stub server's own stdout will explain; a `verify` step means the download was truncated, which the stub's byte count will show; a `blit` step means the panel. Record each failure and its resolution in the bring-up log - that record is the phase's most reusable output.

    If the console produces no output at all, the most likely cause on this board is a console configuration problem rather than a dead board: the panel's master chip-select and power-enable signals share GPIOs with UART0, so the profile routes the console to USB Serial/JTAG. Confirm the built configuration actually has that routing before suspecting hardware.

    Record in `hardware/BRINGUP-LOG.md`: the esptool version, the exact flash command that worked, the flash verification result, the number of attempts needed, and every failure and fix along the way.
  </action>

checks={

" && echo "first light captured: full wake -> poll -> blit -> sleep present in log"</automated>

  <how-to-verify>
    1. Look at the panel. The generated palette image is six full-height vertical bands, each 200 pixels wide, in this exact left-to-right order: black, white, yellow, red, blue, green.
    2. Check the colour order. If the bands are in the wrong order or the colours are wrong, the pixel nibble packing or the palette mapping is wrong.
    3. Check the seam. The panel has two controllers, each driving one 600-pixel-wide half. Look at the vertical line down the middle of the image. The bands must run continuously across it with no offset, no duplication, and no half of the image being blank or stale. A visible discontinuity there points at the master or slave chip-select assignment.
    4. Check completeness. The whole panel should be covered, top to bottom. A partial refresh - some rows updated and some not - points at the busy or reset line.
    5. Check orientation. The image is authored portrait and the panel is portrait-native; no rotation should be applied anywhere. Bands running horizontally instead of vertically would mean a row-order or rotation problem.
    6. Confirm the device is now asleep: the console has printed its sleep-entry line and gone quiet, and no further output appears until the sleep interval elapses.
    7. If anything above is wrong, do not accept it. Report exactly what you see - the reference project's triage page maps each of these symptoms to a specific signal.
  </how-to-verify>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| host flashing tool -> device flash memory | A host-side binary writes the image that the device will execute on every boot |
| Homebrew formula -> developer's machine | A third-party-distributed build of Espressif's flashing tool is installed and run |
| local network -> device during bring-up | The device joins the developer's Wi-Fi and polls a plain-HTTP stub on the LAN |
| device console -> committed log file | Console output is captured verbatim into a file that gets committed |

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
