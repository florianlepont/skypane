<objective>
Stand up the firmware half of the Walking Skeleton's foundation: a real ESP-IDF project that compiles to an ESP32-S3 binary from a container, plus the two pure-C firmware behaviours that can be proven correct on a laptop with no hardware at all - the exponential backoff curve and the server-URL normaliser.

This closes three of the four Wave 0 gaps VALIDATION.md names (backoff unit test, ESP-IDF build environment confirmed working, and by extension the toolchain risk) while the EE02 kit is still in transit (per D-08). Firmware development goes straight to ESP-IDF with no Arduino prototyping detour (per D-06), and the board target is the XIAO ESP32-S3 Plus on the EE02 driver board (per D-05).

RESEARCH.md's Pitfall 4 is the reason this plan exists as its own unit of work: `idf.py --version` answers happily on a broken Python environment and only a real build proves the toolchain works, and the failure does not mention Python in its first line. Discovering that on hardware day would burn the scarcest resource in the phase.

Purpose: DEVICE-03's exponential-backoff success criterion is the one firmware behaviour that is fully testable before hardware exists. Prove it now, in assertions, so that when the device later fails to reach the server the only open question is the radio and not the arithmetic.
Output: A buildable `firmware/` ESP-IDF project, a containerised build command, and a green hardware-free test suite.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| upstream GitHub -> vendored firmware sources | Third-party Apache-2.0 C code is copied into this repository and compiled into an image that will run on the device |
| Docker Hub image -> local build environment | The ESP-IDF toolchain container executes with access to the mounted project directory |
| future server response -> `fp_backoff_seconds` input | The backoff counter is driven by observed failures; its arithmetic determines whether a failing device sleeps or drains its battery |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-01-03-01 | Denial of Service (self-inflicted) | `fp_backoff_seconds` | high | mitigate | The curve is vendored unchanged from the reference implementation and asserted across its whole domain by `tests/test_backoff.c`, including the 21600-second cap at n=7 and the absence of overflow at n=255. An arithmetic error here is precisely the failure that turns an unreachable server into a flat battery, which is why it gets an assertion suite rather than a code review. |
| T-01-03-02 | Tampering | Vendored firmware sources (supply chain) | medium | mitigate | Every vendored file is pinned to commit ce3335fc5e566bcc6ccd29966ec39bf5c5318f12 rather than a moving branch, recorded with its upstream path and licence in `firmware/VENDOR.md`, and `backoff.c` is byte-diffed against a freshly fetched copy of that exact blob in the acceptance criteria. A future re-pin is a deliberate, reviewable act. |
| T-01-03-03 | Tampering | ESP-IDF build container | medium | mitigate | `firmware/build.sh` pins the image tag to `espressif/idf:v5.3.1`, the version the reference project's own CI verifies, rather than a floating `latest` tag that could change under the project without notice. The container is run as the invoking user with a scoped mount of the firmware directory only, not the repository root or the home directory. |
| T-01-03-04 | Information Disclosure | Credentials accidentally committed to git | high | mitigate | `firmware/.gitignore` excludes `main/secrets.h` from the moment the firmware directory is created, before plan 01-05 introduces any credential file - so there is no window in which Wi-Fi credentials or a bearer token could be committed by accident. The reference project's own build notes make the same point: secrets never go in configs. |
