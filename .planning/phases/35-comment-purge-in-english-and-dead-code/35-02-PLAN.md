<purge_rules>
- Keep: what the code does when that is not obvious; the why (constraints, trade-offs, upstream
  quirks); invariants; security invariants (why a check exists), which you rewrite and never
  drop; units and formats; pointers to external specs (RFCs, datasheets, upstream API docs).
- Drop: plan/ticket/decision/review/threat IDs, `Phase N`, quick-task ids, `.planning/` paths,
  change narratives ("previously…", "was removed in…", "the developer asked…"), quotes from
  review rounds, and restatements of the code.
- When a comment mixes history with a real why, rewrite it to the why in 1-2 plain sentences.
- Docstrings: one summary line, plus args/returns/raises or an invariant only when they add
  something. Never delete a docstring that is the only body of a def or class; shorten it.
- English only. Translate or drop French in comments.
- Never edit string literals (user-facing text, HTML inside strings, assertion messages, i18n),
  identifiers, test names or code.
- Keep pragmas, shebangs, encoding lines and SPDX/copyright lines verbatim. A pragma's trailing
  justification may be trimmed to its why.
- A module docstring read through `__doc__` stays accurate `--help` text.
</purge_rules>
</context>
