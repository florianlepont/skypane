<interfaces>
Contract this plan creates (downstream plans 36-03..36-07 code against it exactly):

- `DEFAULT_FILE_MODE: int` = `0o666 & ~umask`, read once at import. Read the umask from
  `/proc/self/status` (`Umask:` line, octal) when present, which does not change the process
  umask; fall back to the `os.umask(0)` / `os.umask(old)` pair only when that line is missing.
- `atomic_write(path, data, mode=None) -> None`: `data` is `bytes` or `str` (str encoded
  UTF-8). Temp created with `tempfile.mkstemp(dir=os.path.dirname(path) or ".",
  prefix="." + os.path.basename(path) + ".", suffix=".tmp")`. Then `os.fchmod(fd, mode if mode
  is not None else DEFAULT_FILE_MODE)` before writing, write all bytes, flush, `os.fsync`, close,
  `os.replace(temp, path)`. Any exception: close the fd if open, unlink the temp (ignore
  `FileNotFoundError`), re-raise. Does not create the parent directory (callers already do).
- `staged_write(path, data, mode=None)`: a context manager with the same temp, mode and fsync
  rules. On entry the temp is fully written and fsynced; it yields a `commit()` callable that
  does `os.replace(temp, path)` once. Leaving the block without `commit()`, or with an
  exception, unlinks the temp and leaves `path` untouched. `atomic_write` is implemented as
  `with staged_write(...) as commit: commit()`.
- `class LockBusy(TimeoutError)`: raised when a lock cannot be taken.
- `LOCK_POLL_S = 0.05`
- `exclusive_lock(lock_path, timeout_s, blocking=True)`: a context manager. Creates the parent
  directory (`os.makedirs(..., exist_ok=True)`), opens `lock_path` with
  `os.open(lock_path, os.O_CREAT | os.O_RDWR, 0o600)`, then tries
  `fcntl.flock(fd, LOCK_EX | LOCK_NB)`: with `blocking=False` a busy lock raises `LockBusy` at
  once; otherwise it retries every `LOCK_POLL_S` until `time.monotonic()` passes
  `start + timeout_s`, then raises `LockBusy`. Errnos other than `EACCES`/`EAGAIN` propagate.
  Unlocks and closes in `finally`. Without `fcntl` (non-POSIX) it yields without locking,
  a documented gap copied from the existing calendar lock.
- Module docstring documents the lock order used across the codebase: an in-process
  `threading.Lock` first, then `poll.lock`, then `calendar_rules.lock`; `device_config.lock` is
  never taken while another of these file locks is held. It also notes that flock locks belong
  to the open file description, so two threads that each call `exclusive_lock` exclude each
  other on Linux, and that callers still keep their thread locks.

Reference pattern to generalise (read it, do not edit it here): `_calendar_registry_lock` in
`server/plane/calendar_rules.py`.
</interfaces>

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-36-01 | Information disclosure | `atomic_write(mode=0o600)` for secrets | mitigate | the temp is created by mkstemp (0600) and fchmod'ed before any byte is written; the final path is never chmod'ed afterwards; test stats the temp at rename time |
| T-36-02 | Tampering | temp-file name collisions and symlink planting | mitigate | mkstemp uses O_EXCL with a random name in the destination directory; no predictable name exists to pre-create |
| T-36-03 | Denial of service | a stuck lock holder | mitigate | every blocking acquire is bounded by `timeout_s` and raises `LockBusy`; flock is released by the kernel when the holder dies |
| T-36-04 | Information disclosure | default mode widening or narrowing | mitigate | default is `0o666 & ~umask`, identical to the `open()` behaviour it replaces, so group read for the operator and the backup is kept and nothing becomes world-readable under `UMask=0027` |
</threat_model>
