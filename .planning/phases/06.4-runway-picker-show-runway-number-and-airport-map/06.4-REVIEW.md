# Phase 06.4: Code Review Report

**Reviewed:** 2026-08-28
**Depth:** standard
**Files Reviewed:** 6
**Status:** issues_found

## Summary

Phase 06.4 adds a runway-picker upgrade to the companion Config page (`companion/pages/config_page.py`'s `runway_fieldset()`) and a new session-gated `/runway-image/{id}.png` route (`companion/app.py`). This is genuinely new attack surface serving bytes from disk based on a URL path segment, and it was the focus of this review.

**Path traversal / access control verdict: sound.** `Handler._serve_runway_image()` performs `if runway_id not in device_config.RUNWAY_IDS: return 404` as its literal first statement, strictly before `_runway_image_path()` ever calls `os.path.join()`. Because `RUNWAY_IDS` is a fixed 3-member tuple (`"3"`, `"06-24"`, `"02-20"`) containing no `/` or `.` characters, **no crafted `runway_id` string — traversal-shaped, percent-encoded, absolute, or otherwise — can ever reach the path-join call**, since the membership test rejects it first regardless of its shape. Verified this holds at the wire level too: `http.client`/`urllib.request` do not collapse `../` dot-segments before sending the request line (confirmed directly), so the three adversarial payloads in the test suite (`..%2F..%2Fetc%2Fpasswd.png`, `../../../etc/passwd.png`, `style.png`) exercise the real code path, and all correctly return 404.

**Auth verdict: sound.** The route is registered as its own branch in `do_GET()`, calling `self.require_session()` as its first statement — the same idiom every other data-bearing route in this file uses — and does *not* extend `/static/`'s deliberately-unauthenticated namespace. Confirmed the pre-existing `GET /static/style.css succeeds without a session` assertion in `companion/test_companion_app.py` still passes unmodified.

**Enumeration verdict: sound.** A non-member id and a member-id-with-a-missing-file both return the exact same `self.send_html(404, self._not_found_page())` call — byte-identical response — so a caller cannot distinguish "not a real runway" from "no image for a real runway."

**Membership-before-path-construction: sound**, confirmed by direct code reading, not just by the plan's grep-based acceptance criteria.

All 34/34 checks in `companion/test_config_page.py` pass, and the full `companion/test_companion_app.py` suite (55/55) passes unmodified, confirming this phase did not regress the pre-existing auth surface.

Two warnings and one info-level note below — none rise to blocker severity; the core security properties this phase was built around hold up under adversarial reading.

## Warnings

### WR-01: `try/except OSError` around `os.path.isfile()` is dead code that never executes

**File:** `companion/app.py:216-223`
**Issue:** `runway_images_available()` wraps `os.path.isfile(_runway_image_path(runway_id, image_dir))` in `try/except OSError: continue`, and both the function's own docstring and the plan's threat model (T-06.4-03) claim this is what makes "a permissions error or symlink loop" degrade gracefully instead of raising. This is incorrect: CPython's `os.path.isfile()` (`genericpath.isfile`) already catches `OSError` (and `ValueError`) internally and returns `False` — it never lets an `OSError` propagate to its caller. Verified directly:
```python
def isfile(path):
    try:
        st = os.stat(path)
    except (OSError, ValueError):
        return False
    return stat.S_ISREG(st.st_mode)
```
`os.path.join()` (used to build the path passed in) also does not raise `OSError`. So the surrounding `try/except OSError` in `runway_images_available()` can never actually trigger — it is unreachable defensive code. The *behavior* is still correct (permission errors and symlink loops do degrade to "no image," exactly as intended), but that correctness comes entirely from `os.path.isfile()`'s own internal handling, not from this function's exception handling. The comment/docstring overstates what the `try/except` is doing, which will mislead a future maintainer who, e.g., changes `os.path.isfile()` to something that *can* raise (a raw `os.stat()` call) and assumes the existing wrapper already covers that case correctly (it does, coincidentally, but for the wrong stated reason) — or who removes the wrapper believing it's protecting against a scenario `os.path.isfile()` was never going to expose in the first place.

**Fix:** Either drop the dead `try/except` (since `os.path.isfile()` already provides the guarantee), or replace the docstring/comment so it accurately states that the graceful-degradation guarantee comes from `os.path.isfile()`'s own contract, not from this loop's exception handling. If the intent is genuinely defense-in-depth against a future refactor to `os.stat()`, say so explicitly rather than implying it is load-bearing today:
```python
def runway_images_available(image_dir=_RUNWAY_IMAGE_DIR):
    """... os.path.isfile() already swallows OSError/ValueError
    internally (permissions, symlink loops, a missing image_dir) and
    returns False, so this function never raises without any extra
    handling here. ...
    """
    available = set()
    for runway_id in device_config.RUNWAY_IDS:
        if os.path.isfile(_runway_image_path(runway_id, image_dir)):
            available.add(runway_id)
    return available
```

### WR-02: Runway images are cached with `Cache-Control: public`, but this is inherited from a pre-existing helper, not introduced by this phase

**File:** `companion/app.py:414` (calls `send_bytes(..., cache_seconds=300)`), helper at `companion/app.py:240-248`
**Issue:** `_serve_runway_image()` serves an authenticated, session-gated image with `Cache-Control: public, max-age=300`. `Cache-Control: public` explicitly permits *shared* caches (e.g. a corporate/ISP proxy sitting between an operator's browser and the VPS) to store and later replay the response to a *different* client on that shared cache, without that second client ever presenting a valid session cookie — effectively letting a shared cache bypass `require_session()` for anyone behind the same proxy within the 300s window. This exact pattern (`public` + a positive `max-age`) is pre-existing in `send_bytes()` and already used by `_serve_gallery_image()` (`cache_seconds=3600`) and `_serve_stylesheet()` (`cache_seconds=300`, but that route is intentionally unauthenticated so it's not a problem there). Because it's inherited, unmodified infrastructure and the runway images themselves carry no user-specific data (every authenticated caller sees the identical PNG for a given runway id, and this is explicitly a single-operator tool per the project's own threat model), the practical exposure is low — but this phase's threat model (T-06.4-01 through T-06.4-04) never evaluates the caching directive at all, even though it reused a helper whose caching behavior has this property for the first time on an *access-controlled* image route (as opposed to gallery images, which arguably have the same latent issue already).

**Fix:** For session-gated resources, prefer `private` over `public` so intermediate shared caches don't store the response, e.g. add a `private` variant of `send_bytes()` or a boolean flag:
```python
def send_bytes(self, code, content_type, payload, cache_seconds=0, private=False):
    ...
    if cache_seconds > 0:
        scope = "private" if private else "public"
        self.send_header("Cache-Control", "%s, max-age=%d" % (scope, cache_seconds))
```
and call `send_bytes(200, "image/png", payload, cache_seconds=300, private=True)` from `_serve_runway_image()`. This is a good candidate for a follow-up rather than blocking this phase, since it affects pre-existing gallery-image behavior equally and isn't a regression this phase introduced.

### IN-01: The plan's own literal must-have (`EXPECTED_CHECK_COUNT = 25`) is not present in the delivered code — intentional, but worth recording

**File:** `companion/test_config_page.py:49`
**Issue:** `06.4-01-PLAN.md`'s `must_haves.artifacts` list states the test file must `contain: "EXPECTED_CHECK_COUNT = 25"`. The actual file reads `EXPECTED_CHECK_COUNT = 34`. This is a genuine, literal mismatch against the plan's stated must-have — grepping for the exact string the plan specifies fails. The `06.4-01-SUMMARY.md` explains why: the plan was authored assuming a stale baseline of 15 pre-existing checks, but the real on-disk baseline had already grown to 24 (from an unrelated phase 06.2 LED-toggle feature) by the time this phase executed, so the increment-by-one-per-task-batch (+4, +3, +3) was applied against 24 instead of the plan's assumed 15, landing on 34 instead of 25. The harness's own fail-closed invariant (`total == EXPECTED_CHECK_COUNT`) is satisfied at 34/34 — the *intent* of the must-have (test count and constant stay in lockstep) holds — but a naive automated re-check of the plan's literal must-haves would report this as unmet. Since the review brief specifically asked to verify must-haves are "genuinely met in the actual code, not just claimed," this is worth flagging even though it's a documented, reasoned deviation rather than an oversight.

**Fix:** No code change needed. Consider amending `06.4-01-PLAN.md`'s must-have to the *pattern* `EXPECTED_CHECK_COUNT = \d+` (as the plan's own `key_links` section already does for other constants) rather than a literal value baked in at authoring time, so future baseline drift doesn't produce a false-negative on an otherwise-correct execution.
