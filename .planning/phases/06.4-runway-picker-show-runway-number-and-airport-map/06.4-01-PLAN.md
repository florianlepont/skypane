<objective>
Upgrade the companion Config page's runway picker so each runway's number/heading is visually prominent (D-01) and, when a real airport-diagram image exists for that runway, the diagram renders beside it — while shipping a fully working graceful fallback so the phase is complete and verified today, with zero image files present (D-02/D-03).

Purpose: The runway picker is currently three small radio labels with no visual reference for what "Runway 06/24" actually means on the ground. D-01 makes the map a real airport diagram or satellite excerpt with the tracked runway highlighted. D-02 makes supplying that image the user's job, not Claude's — so D-03's asset contract is the actual deliverable: a predictable, documented drop-in convention plus code that renders correctly in both the image-present and image-absent states.

Output:
- `companion/app.py`: a registry-bounded existence check (`runway_images_available()`), a new `ctx["runway_images"]` key, and a session-gated, membership-validated `/runway-image/{id}.png` route.
- `companion/pages/config_page.py`: `runway_fieldset()` renders a Display-size runway number and a conditional `<img>`, driven purely by ctx.
- `companion/static/style.css`: three presentation rules built from existing tokens.
- `companion/static/RUNWAY-IMAGES.md`: the D-03 asset contract the user follows.
- `companion/test_config_page.py`: 10 new checks; `EXPECTED_CHECK_COUNT` 15 → 25.

**This plan deliberately produces no image files.** Sourcing, generating, fetching, or synthesising a satellite/chart image is explicitly the user's job per D-02 and is out of scope. Every check in this plan passes with `companion/static/` containing nothing but `style.css` and `RUNWAY-IMAGES.md`.
</objective>
