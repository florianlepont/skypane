## Summary

This phase upgrades `companion/pages/config_page.py`'s `runway_fieldset()` to show each runway's number/heading prominently and, when a user-supplied image file exists, a real airport-diagram/satellite excerpt next to it. The image assets do not exist yet (D-02) — the entire deliverable is code that works correctly in both the "image present" and "image absent" states, verified by an automated test that exercises both.

The codebase already has every pattern this phase needs, twice over. `companion/app.py`'s `_serve_stylesheet()` is the precedent for serving a single named static file from `companion/static/`, and `gallery_entries()`/`gallery_bytes()` (also in `app.py`) is the precedent for **existence-checking a small, registry-bounded set of files and exposing the result through `ctx`** so a page module never touches the filesystem itself. This phase's job is to compose those two existing patterns for a new, three-member, registry-bounded set: the `RUNWAY_IDS` already defined in `server/device_config.py`.

**Primary recommendation:** Do not add a new field to `device_config.RUNWAYS`. Derive each image's filename by convention directly from the existing runway id (`runway-{runway_id}.png`, e.g. `runway-3.png`, `runway-06-24.png`, `runway-02-20.png`), store the three files (once supplied) in `companion/static/`, existence-check them in `companion/app.py`'s `page_context()` (mirroring `gallery_entries()`) into a new `ctx["runway_images"]` set, and have `config_page.runway_fieldset()` consult that set — never `os.path.isfile()` — to decide whether to emit an `<img>` tag. Serve the images through a new, narrowly-scoped route that validates the requested id against `device_config.RUNWAY_IDS` (never against the raw path suffix) before ever building a filesystem path, gated behind `require_session()` like every other data-bearing route (deliberately *not* following `_serve_stylesheet()`'s unauthenticated precedent, because these images — unlike the CSS the pre-login page itself needs — are only ever referenced from the already-authenticated `/config` page).

### Pattern 1: Registry-bounded existence set, computed once per request in the backend tier
**What:** A page module never calls `os.path.isfile()`/`os.scandir()` itself. `companion/app.py`'s `page_context()` computes the existence facts once (already the case for `gallery_entries()`) and hands the *result* — a small Python collection, not a filesystem handle — to the page module.
**When to use:** Any time a page needs to know "does file X exist" for a small, registry-bounded set of candidate files.
**Example:**
```python
# Source: companion/app.py (existing, lines ~154-169) — the pattern to mirror
def gallery_entries(state_dir, limit=GALLERY_DEFAULT_LIMIT):
    gallery_dir = os.path.join(state_dir, GALLERY_DIRNAME)
    try:
        entries = sorted(
            (entry.name for entry in os.scandir(gallery_dir)
             if entry.is_file() and entry.name.endswith(".png")),
            reverse=True,
        )
    except OSError:
        return []
    return entries[:limit]

# NEW — same shape, applied to the runway-image set:
_RUNWAY_IMAGE_DIR = os.path.join(_HERE, "static")


def _runway_image_filename(runway_id):
    return "runway-%s.png" % runway_id


def _runway_image_path(runway_id, image_dir=_RUNWAY_IMAGE_DIR):
    return os.path.join(image_dir, _runway_image_filename(runway_id))


def runway_images_available(image_dir=_RUNWAY_IMAGE_DIR):
    """The subset of device_config.RUNWAY_IDS that currently has a real
    image file on disk. A missing companion/static/ directory or a
    missing individual file is not an error — it is D-03's documented
    graceful-fallback state, so this never raises.
    """
    return {
        runway_id for runway_id in device_config.RUNWAY_IDS
        if os.path.isfile(_runway_image_path(runway_id, image_dir))
    }
```
Note the `image_dir=_RUNWAY_IMAGE_DIR` default-parameter shape — this is what makes the function testable without touching the real `companion/static/` directory (see Validation Architecture below); it mirrors `gallery_entries(state_dir, ...)`'s own parameterize-the-directory idiom, just applied to a module-level default instead of a CLI-supplied `state_dir`.

### Pattern 2: Registry-membership validation before any filesystem path is built (path-traversal defense)
**What:** The new image route must validate the requested runway id against `device_config.RUNWAY_IDS` (an exact-membership test) *before* it is used in any `os.path.join()` call — never build a path from an unvalidated suffix and then check `isfile()`.
**When to use:** Any route serving a file whose name is derived from request input.
**Example:**
```python
# Source: companion/app.py's existing gallery pattern (lines ~172-187),
# adapted — gallery_bytes() validates by exact-match against a real
# os.scandir() listing (because gallery filenames are timestamp-generated
# and unbounded); the runway-image case is even stronger, because the
# candidate set is the fixed 3-member RUNWAY_IDS tuple, not an open set.
RUNWAY_IMAGE_ROUTE_PREFIX = "/runway-image/"


def _serve_runway_image(self, runway_id):
    if runway_id not in device_config.RUNWAY_IDS:      # membership test FIRST
        return self.send_html(404, self._not_found_page())
    path = _runway_image_path(runway_id)                # path built only from a validated id
    try:
        with open(path, "rb") as fh:
            payload = fh.read()
    except OSError:
        return self.send_html(404, self._not_found_page())
    return self.send_bytes(200, "image/png", payload, cache_seconds=300)

# In do_GET(), alongside the existing GALLERY_ROUTE_PREFIX handling:
if path.startswith(RUNWAY_IMAGE_ROUTE_PREFIX) and path.endswith(".png"):
    if not self.require_session():
        return None
    runway_id = path[len(RUNWAY_IMAGE_ROUTE_PREFIX):-len(".png")]
    return self._serve_runway_image(runway_id)
```
Using a dedicated `/runway-image/` prefix (rather than layering onto `/static/`) keeps the auth-gate decision unambiguous at the route-matching level: everything under `/static/` stays the pre-login-safe stylesheet-only namespace exactly as today, and the new authenticated image route is a visibly separate branch — no risk of accidentally widening `/static/`'s existing unauthenticated exposure.

### Anti-Patterns to Avoid
- **Filesystem I/O inside a page module (`config_page.py` calling `os.path.isfile()` directly):** breaks the documented `companion/pages/__init__.py` contract that page modules are presentation-only and receive all facts through `ctx`; also makes the graceful-fallback path untestable without a live subprocess (see Validation Architecture).
- **Building a runway-image path from a raw, unvalidated URL path segment:** even though `RUNWAY_IDS` values (`"3"`, `"06-24"`, `"02-20"`) contain no path-traversal characters today, validating by membership *first* (Pattern 2) is what makes that safety a property of the code rather than an accident of the current registry's contents — if a future runway id ever contained `/` or `..`, an unvalidated join would silently become exploitable.
- **A new mutable field on `server.device_config.RUNWAYS` for an image path:** violates that module's own documented "leaf module, no structural change needed to add an entry" design; also puts a companion-app-specific filesystem concern (`companion/static/`) inside a module that must stay importable and meaningful for the device/render pipeline too.
- **Serving the runway images unauthenticated under `/static/`:** the `_serve_stylesheet()` precedent's lack of auth is specifically because the pre-login page needs it — copying that precedent for images that are only ever shown post-login would be an unforced widening of the site's default-authenticated posture (06-RESEARCH.md's whole-site auth-gate discipline, D-02).

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Static-file MIME/caching headers | A general-purpose static-file server / `send_from_directory`-style helper | The existing `send_bytes(code, content_type, payload, cache_seconds)` helper already on `Handler` | It's already correct (Content-Length, Cache-Control, no-store default) and used by every other binary response (`_serve_preview_image`, `_serve_gallery_image`) — a new helper would just be a second, drifting copy |
| Path-traversal protection | A path-sanitization/normalization utility (`os.path.normpath` + prefix check, `werkzeug.utils.secure_filename`, etc.) | Exact membership test against `device_config.RUNWAY_IDS` (a fixed 3-value tuple) before any path is built | The candidate set is closed and tiny; membership-testing against it is strictly stronger than sanitizing an open string, and it's the same technique this codebase already uses for theme/runway POST validation (`config_page.handle_post()`) |

**Key insight:** every "don't hand-roll" risk in this phase is already solved elsewhere in this exact codebase (gallery serving, style serving, registry-membership validation for POST bodies). The task is composition, not invention — deviating from the existing three precedents is the actual risk to avoid, not a missing library.

## Common Pitfalls

### Pitfall 1: Testing "image present" against the real `companion/static/` directory
**What goes wrong:** A test that copies a real PNG into `companion/static/runway-3.png` to exercise the "present" branch, then deletes it afterward, pollutes the real repo directory if the test crashes before cleanup (no `finally`), or produces flaky cross-test interference if two test runs overlap (this repo's harnesses run serially via `scripts/run-all-tests.sh`, but a developer running one file directly could still collide with a real user-supplied asset sitting in that directory in production-adjacent checkouts).
**Why it happens:** `_RUNWAY_IMAGE_DIR` is naturally a fixed, `_HERE`-relative constant (matching `_STYLE_CSS_PATH`'s own pattern) — there's no obvious injection point unless one is deliberately added.
**How to avoid:** Give `runway_images_available()` and `_runway_image_path()` an `image_dir=` parameter defaulting to the real directory (Pattern 1's code example already does this). Unit tests then call these functions directly with a `tempfile.mkdtemp()` path, exactly like every other test in this suite uses `state_dir`. Never write a test fixture into the real `companion/static/`.
**Warning signs:** A test harness `import shutil; shutil.copy(..., "companion/static/...")` — this is the tell that the directory should have been parameterized instead.

### Pitfall 2: End-to-end (subprocess) tests can't observe an in-process monkeypatch of the image directory
**What goes wrong:** `test_config_page.py`'s Section 2 pattern spins up `companion/app.py` as a **separate subprocess** (`subprocess.Popen([sys.executable, APP_PATH, ...])`). Any in-process monkeypatch of `companion_app._RUNWAY_IMAGE_DIR` in the test process has zero effect on that subprocess, which re-imports the module fresh.
**Why it happens:** This is exactly why `_save_oserror_returns_failure_key_not_raise` (the existing OSError-simulation test) is a **Section 1 unit check** (direct in-process function call), not a Section 2 (subprocess) check — the existing test suite already avoids this trap for a different function, but a new contributor extending the pattern to images could miss it.
**How to avoid:** Keep the "image present" and "image absent" graceful-fallback assertions as **Section 1 unit checks** against `runway_images_available(image_dir=tmpdir)` and `config_page.runway_fieldset(runway_id, images_available_set)` called directly — no subprocess needed for these two states. Reserve the Section 2 end-to-end subprocess check for confirming the *route* returns 404 for a real request when no file exists in the real (test-fresh, empty) `companion/static/` directory the subprocess actually sees — which is naturally the "absent" state in CI, since no image files are ever committed to the repo (D-02).
**Warning signs:** A new Section 2 check trying to assert `<img>` markup appears in a subprocess-served page — this needs a real file to exist in the directory that specific subprocess resolves, which is exactly the pollution risk in Pitfall 1.

### Pitfall 3: Forgetting the CFG-05-style "degrade one section, not the whole page" discipline
**What goes wrong:** A raised `OSError` from a transient filesystem issue while checking one runway's image (e.g., a permissions problem, a symlink loop) propagates out of `render()` and 500s the entire `/config` page — including the theme picker and poll-trigger button, which have nothing to do with runway images.
**Why it happens:** `os.path.isfile()` is documented to return `False` on most errors rather than raising, but this is worth confirming explicitly rather than assuming, since the rest of this codebase's convention (`load_device_config`, `gallery_entries`, `gallery_bytes`) is to wrap filesystem calls in `try/except OSError` defensively even where the specific stdlib call is unlikely to raise.
**How to avoid:** Match the existing defensive style — wrap the per-runway `os.path.isfile()` loop (or the whole `runway_images_available()` function body) so a single bad entry degrades to "no image for that runway" rather than raising, consistent with `gallery_entries()`'s own `except OSError: return []`.
**Warning signs:** `runway_images_available()` has no `try/except` at all, unlike every other filesystem-touching function in `companion/app.py`.

### Known Threat Patterns for this stack

| Pattern | STRIDE | Standard Mitigation |
|---------|--------|----------------------|
| Path traversal via a crafted runway-id-shaped URL segment (e.g. `/runway-image/..%2f..%2fetc%2fpasswd.png`) | Tampering / Information Disclosure | Exact membership test against the fixed `device_config.RUNWAY_IDS` tuple before any `os.path.join()` — never sanitize-then-join; validate-then-join (Pattern 2) |
| Unauthenticated disclosure of images intended for the authenticated companion UI | Information Disclosure | `require_session()` as the new route's first statement (Anti-Patterns; deliberately deviates from the unauthenticated `/static/style.css` precedent) |
| A missing/corrupt image file causing a 500 that also breaks the rest of the `/config` page (theme picker, poll trigger) | Denial of Service (self-inflicted) | Wrap the existence-check loop in the same defensive `try/except OSError` style as `gallery_entries()` (Pitfall 3); a missing file must degrade to "no `<img>` tag for that runway," never an unhandled exception |
