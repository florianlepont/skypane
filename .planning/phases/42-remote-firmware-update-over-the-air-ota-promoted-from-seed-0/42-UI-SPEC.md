## Design System

| Property | Value |
|----------|-------|
| Tool | none — this project has no shadcn/component-library layer |
| Preset | not applicable |
| Component library | none — companion is a hand-written, build-step-free, zero-external-reference stylesheet (`companion/static/style.css`); the frame's on-device screens are drawn with Pillow (server-side generator) / raw framebuffer primitives (firmware), never a UI toolkit |

### Page composition (D-03)

The page follows the established **card-per-concern** grammar (`settings-page-patterns.md`, `companion/pages/health_page.py`'s section builders): one `layout.page_header()` at the top, then ordered `.page-section` cards, each with a `<h2 class="text-heading">` title (22 px serif regular — this route has no supersections, so the nested-card-title 16 px tier does not apply anywhere on this page). Reuses `layout.page_shell(title=..., active=nav_slug(UPDATE_ROUTE), body=..., ...)` exactly as Health/Device do.

**Card order, top to bottom:**

1. **Running version + update state card** (D-03 items 1–3, combined into one card — they describe one live status, not three independent facts)
2. **Version history card** (D-03 item 4)

#### Card 1 — Status

| Element | Content | Component reused |
|---|---|---|
| Running version | "Running **fw-v1.3.0**" (or "Running **fw-v1.3.0-dirty**" for an untagged dev build, D-16) as last reported by `X-Fw-Version`, plus its report timestamp via `layout.concise_timestamp_html()` | `stat_tile()` verdict/detail pattern (`health_page.py`'s `_tile_body()`), reusing `.widget-verdict`/`.widget-detail` — **not** `empty_state()`'s classes, since this is a filled tile |
| Update state | One of five words — **Available** / **Scheduled** / **In progress** / **Installed** / **Failed** — rendered via `status_dot()` (`layout._STATUS_DOT_CLASSES`), colour-mapped below, with its own timestamp | `status_dot(state, label)` |
| Scheduled detail | "at the next wake, around **08:14**" via `layout.relative_time_html(..., countdown=True)` reusing the exact wording register `frame_state.py`'s `_FRAME_HEADLINE_DUE_TEXT` ("Next update ≈ %s") already establishes for "next wake" language | new sentence, same register: `"Scheduled — installs at the next wake, around %s."` |
| Rollback warning (D-03 item 3) | Only rendered when the frame's last report shows it came back on the previous image after a failed trial. A `.banner` at `role="alert"`, warn-coloured (never error — a completed, safe rollback is the system working as designed, not a fault), text: **"Firmware rolled back — the update to fw-v1.4.0 failed on trial boot; the frame is back on fw-v1.3.0."** (version numbers interpolated) | Reuses the existing neutral/anomaly banner pattern (`health_page.py`'s `_anomaly_banner_html()`), warn variant |
| Cancel button (D-05) | Visible only while state is **Scheduled** AND the device has not yet acknowledged the offer. Once acknowledged (device started downloading), the button is gone entirely — not disabled, not greyed out, since D-05 says Cancel "is gone," matching the existing pattern of a control disappearing rather than becoming inert (compare the poll-cooldown button, which disables rather than vanishes — deliberately different here because D-05's wording is explicit) | `<form method="post" action="/update/cancel">` — plain POST, no confirmation needed (cancelling is non-destructive and immediately reversible: Install again) |

**State → colour mapping** (executor verification item: confirm each maps to an *existing* dot class, introduce no new one):

| State | `status_dot()` class | Rationale |
|---|---|---|
| Available | `dot--off` (neutral) | Nothing is happening yet; not a problem, not a success — matches `.dot--off`'s own definition ("a neutral, everyday state ... never a problem") |
| Scheduled | `dot--off` (neutral) | Still waiting on the device's own clock, not yet an outcome |
| In progress | `dot--warn` — **not** an error colour, but the one "something is actively different from steady-state" tone the palette has short of ok/error; matches how a poll-in-progress reads elsewhere in the app | Discretion — no direct precedent exists for a transient in-progress state in this app's dot vocabulary; `dot--warn` is chosen over inventing a new colour, since UIR's colour-separation contract (`contrast_check.py`) gates any *new* hue and this phase adds no new tokens |
| Installed | `dot--ok` | A completed, successful outcome |
| Failed | `dot--error` | D-15's terminal failure state |

**Accent-reservation check:** none of the five state words or the Cancel/Install buttons introduce a new accent consumer. Install is `type="submit"` on its own form → covered by the existing "primary/`type=submit` buttons" accent-reservation entry (`style.css`'s own header comment). Cancel is a secondary action and must **not** be `type="submit"` styled as primary — render it with the plain/quiet button treatment the Frame strip's own switch buttons use since Phase 22 C2 (`.frame-strip__cell button`'s equal-specificity quiet-wash mechanism), so only one accent-toned action (Install) exists per row.

#### Card 2 — Version history (D-03 item 4, D-07, D-18)

| Element | Content | Component reused |
|---|---|---|
| Table | Every published release, newest first: columns **Version**, **Date**, **Notes** (generated commit summary, D-07), **Installed** (a checkmark + timestamp when that release was ever running, blank otherwise), **Action** | `layout.data_table(headers, rows, mono_columns=(0,), desc_columns=(2,), modifier="firmware-history")` — `mono_columns=(0,)` puts the version tag in monospace (an identifier, per the Time value / label-voice contract: "monospace is now reserved for identifiers ... and a wall-clock time is not one" — a version tag **is** an identifier, so mono is correct here, unlike a bare timestamp column) |
| Notes column | The CI-generated `git log` summary (D-07), rendered as prose — pass this column through `desc_columns` (description-role class) and `prose=True` on the table overall, since a multi-sentence commit summary must wrap rather than crop, matching `data_table()`'s own documented `prose` release valve | — |

**Confirmation flow for Install (D-04) — reuses the calendar-disconnect two-step pattern exactly:**

The confirm page is the **real security gate**; the `<dialog>` (with JS) is UX sugar only, matching the project's own stated convention ("the client-side confirm dialog is a misclick guard only, never the real gate," `companion/pages/config_page.py`'s `calendar_disconnect_confirm_page()` docstring).

1. **No-JS path (canonical, must work standalone):** `POST /update/install` with `version` and no `confirm` field renders `update_install_confirm_page(ctx, version, next_wake_text)` at **200**, without touching anything — byte-for-byte the same control-flow shape as `_handle_calendar_disconnect_post()`. That page's body:
   - Heading: **"Install firmware fw-v1.4.0?"** (version interpolated)
   - Body sentence: **"The frame will download and install this version at its next wake, around 08:14. It will keep the update after one successful check-in — otherwise it rolls back automatically."** (next-wake time interpolated via the same `relative_time_html()`/absolute-clock convention Card 1 uses)
   - A form re-posting to `/update/install` with `version` and `confirm=yes` pre-filled, a single submit button labelled **"Install"**
   - A plain cancel link back to `/update` labelled **"Cancel"** (a link, never a second form — matches `calendar_disconnect_confirm_page()`'s own "cancel is a plain link ... never a second form")
2. **With-JS enhancement:** the Install button in Card 2's table carries `data-confirm` (the `confirm-submit.js` misclick-guard pattern, e.g. `data-confirm="Install fw-v1.4.0 now? It will apply at the next wake."`) so a JS-enabled visitor gets a native `window.confirm()` before the POST ever leaves the browser — but the POST still lands on the same no-JS-safe handler above, which still renders the full confirm page if `confirm` is absent (a scripted browser sending `data-confirm`'s own implicit consent must still pass through the real gate; `confirm-submit.js` does not set the `confirm` field itself, it only gates the click).
   - **The `<dialog>`/`panel-lookup-dialog` pattern is NOT used here.** That pattern is for a lookup/detail *view* (`panel-lookup.js`), not a destructive-adjacent confirmation; the calendar-disconnect precedent is the correct model for "confirm a state-changing action," and D-04 explicitly names it ("may use the existing `<dialog>` pattern ... with JS") as *optional*, not mandatory — Claude's Discretion resolves this by choosing the plain `confirm-submit.js` misclick guard over a full `<dialog>`, since the real gate is already the server-rendered confirm page and a second, richer client dialog would duplicate that page's content for no behavioural gain. If the checker or a later review wants the `<dialog>` version instead, the confirm page's content above is what the dialog's body should mirror.

**Downgrade (D-06):** the Install button/confirm page render identically whether the chosen version is newer or older than the running one — no separate "downgrade" wording, copy, or extra confirmation step. D-06 states this is a first-class supported action, not a hazard requiring a heavier gate; adding downgrade-specific scare language would misrepresent the decision as riskier than the phase treats it.

## Surface 2 — the e-ink "Updating…" hold screen (D-14)

### Discretion resolution: on-device, static, fault_screen.c-style (not a served image)

**Decision:** the screen is drawn **entirely on-device**, reusing `fault_screen.c`'s exact technique — a committed, build-time-generated ink mask (`firmware/tools/gen_fault_screen.py` → a new `updating_screen_mask.h`) stamped onto an on-device Floyd-Steinberg dithered dark field, with **zero server round trip** and **no dynamically rendered text**.

**Rationale (recorded per the auto-mode instruction):**
- RESEARCH.md's own architecture diagram already names this as the intended shape ("draw 'Updating…' screen (on-device, fault_screen-style — no server round trip, D-14)") — this UI-SPEC confirms rather than overrides that lean.
- A served image would need an extra HTTPS round trip during a wake that is already spending its budget downloading a ~1 MB firmware image under `wake_guard.c`/`wake_deadline.c`'s cap — the energy/time cost D-14 itself calls out.
- Static, mask-baked text (identical mechanism to NO CONNECTION) means **no on-device font-rendering engine** is needed for this transient, few-seconds screen — avoiding new firmware complexity for a screen that exists for the duration of one OTA attempt.
- Consequence: the screen **cannot show the target version number** (mask text is fixed at build time, not interpolated at runtime). This is an explicit, justified trade-off, not an oversight — see "What the screen does NOT show" below.

### Visual composition — mirrors Phase 12's hold-screen grammar exactly

D-14 explicitly instructs following "the frame's existing language and visual conventions (Phase 12 hold screens)." Per `server/plane/render.py`, the **dimmed hold composition** (`_build_dimmed_hold_canvas()`) is the shared template for DISPLAY OFF, QUIET HOURS, BATTERY EMPTY and — despite being a fault state rather than a deliberate rest — NO CONNECTION too. "Updating…" joins this same family rather than the *white* "empty/watching" composition, because CONTEXT.md points explicitly at the **hold screens** as the model, not the empty state:

| Property | Value | Precedent |
|---|---|---|
| Field | `DIMMED_FIELD_IDX` = `IDX_BLACK`, Floyd-Steinberg dithered toward White at the shared `DITHER_TARGET_LEVEL = 102` constant | Identical constant, identical dither spec, both sides (`server/plane/dither.py` / `firmware/main/fault_screen.c`) — this phase adds **no new dither parameter** |
| Ink | `DIMMED_INK` = `IDX_WHITE` | Same as all four dimmed-composition screens |
| Icon | New glyph, drawn from primitives (no vendored asset, matching every existing icon in this module) — a circular refresh/progress mark: two opposing arcs each ~90° with an arrowhead, Bold-class **8 px stroke** (matching `POWER_ICON_STROKE_PX`/`DISPLAY_OFF`'s own stroke weight, "safe against the dither" per that constant's own comment) | New `draw_updating_icon()` alongside `draw_power_icon()`/`draw_moon_icon()`/`draw_alert_icon()` in `server/plane/render.py`; height budget ~76 px, matching `POWER_ICON_DIAMETER_PX`'s total footprint (`POWER_ICON_BAR_RISE_PX + POWER_ICON_DIAMETER_PX` = 86 px is the largest existing sibling; keep at or below it) |
| Label font | `DIMMED_LABEL_FONT` = `(PT_SERIF_BOLD, 40, 700)`, `DIMMED_LABEL_TRACKING_PX = 10` — unchanged, reused verbatim | Same as all four |
| Rule | `DIMMED_RULE_WIDTH_PX = 120`, `DIMMED_RULE_HEIGHT_PX = 4` — unchanged, reused verbatim | Same as all four |
| Body font | `DIMMED_BODY_FONT` = `EMPTY_BODY_FONT`, `DIMMED_BODY_LINE_GAP_PX = 6` — unchanged, reused verbatim | Same as all four |
| `source_fault`/`battery_low` badges | **Neither is drawn.** D-12 already refuses to start an update while the battery-low alert is active, so `battery_low` is structurally always False at this point — drawing the badge would be dead code implying a state that cannot co-occur. `source_fault` (ADS-B corroboration) is orthogonal to firmware and would confuse the reader mid-update. | Discretion — both existing dimmed screens accept these as optional booleans; this call site simply never passes them True |
| Persistence / "already shown" sentinel | **None needed.** Unlike NO CONNECTION (which persists across many wake cycles of an outage and needs `FP_NVS_IMAGE_HASH`/`already_shown` bookkeeping to avoid redrawing every 5 minutes), the Updating screen is drawn once per OTA attempt, for the duration of a single wake, and the device either reboots into the trial image or gives up and resumes normal polling — there is no multi-wake "still showing this" state to deduplicate. | Discretion, follows from D-15's "three attempts" model: each attempt is its own wake, drawing its own fresh screen |

### Copywriting (locked English, do not localise — matches every existing on-device string)

Every existing hold-screen string in `server/plane/render.py` carries the comment "Locked English copy ... Do not localise" — the frame's own display has never been bilingual (only the companion is); this phase does not change that.

| Element | Text | Constraint |
|---|---|---|
| Heading | **"UPDATING"** | Uppercase, no punctuation, no ellipsis — matches the exact register of "NO CONNECTION" / "QUIET HOURS" / "DISPLAY OFF" / "BATTERY EMPTY" (all uppercase two-word-or-shorter nouns, zero punctuation). An ellipsis ("UPDATING…") was considered and rejected: it would be the only punctuated heading in the whole vocabulary. |
| Body line 1 | **"Installing a firmware update."** | States what is happening, matching the register of "The frame can't reach its server." / "Switched off from the companion page." |
| Body line 2 | **"The frame will restart when it's ready."** | States the honest, non-alarming next step — deliberately does not promise success ("when it's ready" covers both a clean install and a silent rollback-and-resume, both of which end the same way from the reader's perspective: the frame restarts and resumes). Matches the reassurance register of "It will try again on its own." / "It will pick up where it left off." |
| Target version | **Not shown** (see Discretion resolution above) | The version is visible in the companion Update page instead — an operator watching a physical update in progress already scheduled it there and knows which version it is |
