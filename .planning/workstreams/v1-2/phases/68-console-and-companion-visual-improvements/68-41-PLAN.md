**Decisions made here (the owner can overturn at Task 5; items the owner has not yet ruled on are listed in the success criteria):**

- FLT-01 Storage: keep the JSON-file-per-concern format. The audit found SQLite not worth it (the three files total under 150 KB: 200 + 200 + 300 entries at most, point lookups, one writer, an existing atomic-write + process lock + never-raising validator contract). Each file keeps its name and its format; its ONE location becomes the fleet root (the state root, `args.state_dir` of the companion, `ledger_root` of the poll cycle). The live frame's state directory IS the state root (`device_dirs.LIVE_STATE_PATH == "."`), so the live frame's existing files are already the fleet files: only the other frames' files need merging in.
- FLT-02 One seam, no call-site edits: add `device_dirs.fleet_root_for(state_dir)` (pure shape check, same rule as `poll_cycle._ledger_root_for`: when the parent directory is named `devices` and the leaf matches `DEVICE_ID_RE`, the root is the grandparent; otherwise `state_dir` itself) and make `manual_resolutions.manual_resolutions_path`, `name_overrides.name_overrides_path` and `airline_default_types.default_types_path` join their filename onto `fleet_root_for(state_dir)`. Every existing caller (companion page context, handlers, preview images, freshness stamp, poll cycle) keeps passing its own `state_dir` and silently reads and writes the fleet files; no caller can be forgotten. Side effect wanted: `freshness.py` stamps `manual_resolutions_path(state_dir)`, so a name change on any frame now refreshes the freshness signature of every frame.
- FLT-03 Because of FLT-02, code that must read or write a PER-DEVICE file (the migration only) uses `manual_resolutions.load_registry_file(path)` (path-based, already public) and a new path-based `airline_default_types.load_default_types_file(path)` extracted from `load_default_types`; it never calls the `state_dir` loaders on a device directory (they would return the fleet file).
- FLT-04 Poll process: unchanged call sites. `poll_cycle.load_cycle_context` still calls the loaders once per cycle with its `state_dir`; by FLT-02 that is the fleet file. The separate systemd poll unit and the companion read the same files; the companion remains the only writer (atomic write, unchanged `_WRITE_LOCK`), so no cross-process lock is added.
- FLT-05 Migration: a new pure module `server/plane/fleet_registries.py` with `plan_merge(root)` and `apply_merge(root, plan, now=None)`, hooked into `server/fleet_migrate.py` `migrate()` so the existing deploy steps (`deploy/activate.sh` runs a pre-migration backup, `--dry-run`, then the real run, all BEFORE the symlink swap) print the plan and apply it. No lazy migration on read (reads stay side-effect free, the poll unit must never write, and "the migration never runs at service start" is the stated deploy rule). A marker `airline_registry_migration.json` in the root records, per source file, the SHA-256 that was merged, so a second run with unchanged sources does nothing and prints nothing new, and a source changed since (written by the previous release during a rollback period) is merged again once.
- FLT-06 Conflict rule, one total order, identical on every run: among all candidates for one prefix (the root file's entry and each frame's), the entry with the latest `created_at` (parsed ISO-8601 UTC; an unparsable stamp ranks oldest) wins; on a tie the root entry (the live frame) wins, then the lowest device id. For `airline_default_types.json`, which has no stamps, the root entry wins, then the lowest device id. Losers are never discarded: each is written as one log line (prefix, both names, both stamps, the frame ids) and recorded, bounded to 50, in the marker; the per-device files keep them anyway (FLT-07). Two extra refusals keep the registries' own invariants: a merged name override whose artwork key equals the key of a built-in curated airline, or of an override held by a prefix of a different built-in airline, is not merged (`name_overrides._name_is_taken` semantics, the older one loses) and is logged; entries beyond `MANUAL_RESOLUTION_MAX_ENTRIES` (200) or `airline_default_types.MAX_ENTRIES` (300) are not merged and are logged with a count (nothing is deleted anywhere).
- FLT-07 Rollback: the per-device files are never modified, renamed or deleted by this release (the owner's alternative, renaming them to `.migrated`, would make the previous release read an empty registry and lose the names on rollback, so it is rejected). They become frozen dead copies that this release never reads and never writes; they disappear with their frame (`device_dirs.wipe_device_dir`). Rollback caveat to write in `deploy/README.md` next to "Rollback caveat (expand-only)": the previous release reads per-device files, so after a rollback every non-live frame sees its own old names again, and names given or changed after the upgrade exist only in the root files (visible to the previous release on the live frame only); a later roll-forward merges again only the per-device files that changed in the meantime (hash differs), by the same conflict rule, which can bring back a name deleted fleet-wide before the rollback: re-check the Airlines editor after a roll-forward that followed a rollback.
- FLT-08 Suggestions: `airline_suggestions.json` is already root-level and `record_outcome` is already called with `self.args.state_dir`. With fleet-wide names a prefix named on any frame is excluded from every frame's unidentified list (`_gap_rows_for_grid` skips prefixes of the registry), so the tombstone and the name can no longer disagree. The migration creates no tombstone and no suggestion (a prefix merged in is simply named). `_handle_manual_resolve_post` gains one guard: a prefix already present in the fleet registry is refused as stale (existing `FLASH_KEY_MANUAL_PREFIX_STALE`), so two administrators on two frames cannot overwrite each other's name by a stale unidentified row.
- FLT-09 Backup: the three fleet files and the marker are root files: `INCLUDE_FILES` of `deploy/backup/skypane_backup.py` lists `manual_resolutions.json` (main) plus `airline_name_overrides.json`, `airline_default_types.json`, `airline_suggestions.json` (PR #507) and `airline_registry_migration.json` (this plan; an unlisted root file is logged as drift). The per-device copies STAY archived: `DEVICE_INCLUDE_FILES` lists `manual_resolutions.json` and gains `airline_name_overrides.json` and `airline_default_types.json` (today those two per-device files are not archived and are reported as drift). Reason: they are the rollback source and, in the pre-migration backup `activate.sh` takes just before the merge, the only copy of the data being merged.
- FLT-10 Rename route: a NEW route `POST /airlines/rename/manual` (`airlines_page.RENAME_MANUAL_ROUTE`), not an extension of `POST /airlines/rename`. Reason: the existing route's identity field is the built-in airline name, re-validated against the built-in prefix table and writing `name_overrides`; a hand-named airline has no built-in name, its identity is its stored prefix and it writes `manual_resolutions`. Mixing both identities in one handler would blur two validation paths in a security-relevant route. Form fields: `prefix` (normalised, re-validated against the fleet registry, never trusted for a path), `airline_name`, `csrf_token`. Access: `ADMIN_DEVICE` with `csrf=True` on its own `Route`, registered in `_ACTION_KEYS` (device-scoped) like `airlines_page.AIRLINE_SUGGEST_ROUTE`; owners, co-managers and anonymous get the same refusals as `/airlines/resolve`.
- FLT-11 Rename semantics: a hand-named airline row stands for every prefix of the registry whose stored name resolves to the same artwork key (`manual_resolutions.illustration_key_for_name`); Rename changes all of them in one write (like `name_overrides.set_names` for a built-in airline's prefixes) with a fresh `created_at`. Refused (stale): the prefix is not in the registry or the entry is superseded by the built-in tables (`enrich.static_airline_name_for_prefix(prefix)` or a name-only prefix: the row is then a built-in row with its own Rename). Refused (taken): the new name's artwork key equals that of a built-in curated airline, of an override, or of a manual entry of a prefix OUTSIDE the group (two prefixes of one carrier may share a name; two carriers may not). A new name with the same key as the old one (case or spacing) is allowed and only changes the shown name. Existing refusals map to existing flash keys: empty, unusable, too long, reserved, registry full, save failed, taken (`FLASH_KEY_RENAME_TAKEN`), stale (`FLASH_KEY_RENAME_STALE`), success `FLASH_KEY_RENAMED`.
- FLT-12 Artwork and default type on rename: `illustration_key_for_name` links the name to the artwork slug, so a renamed airline would lose its pictures and its default type. Decision: CARRY OVER in ONE place, copy never move, exactly like the built-in rename (`post_actions._carry_artwork_to_new_name`, which this plan makes delegate to one shared function so both renames behave identically): for the old key `K` and each suffix in `"" + "-" + slug` for every slug of `post_actions.type_slugs()`, copy `K[suffix].png` to the new key's file in the override directory of the acting `state_dir` when the new key has no artwork at all there; the old files stay, so renaming back finds them. There is NO loop over frame directories: artwork becomes fleet-wide in plan 42, where that directory is the single fleet directory (`illustrations.override_dir_for_state_dir` resolves to the fleet root), so the one carry serves every frame. Until plan 42 ships the carry reaches only the acting frame, which is why the two plans ship together. The default type entry of the old key is copied to the new key when the new key has none (`airline_default_types.set_default_type`, which is fleet-wide after Task 1; a full registry is logged and ignored); the old entry stays.
- FLT-13 Deferred cleanup (NOT built here, no task): after the rollback window, a later release deletes the frozen per-device copies of `manual_resolutions.json`, `airline_name_overrides.json` and `airline_default_types.json` (owner, 2026-11-21: yes, later), together with the matching `DEVICE_INCLUDE_FILES` entries and the README caveat. Record it as an item for plan 32 (final plan) and for STATE.md's deferred list; this plan does not edit either.
