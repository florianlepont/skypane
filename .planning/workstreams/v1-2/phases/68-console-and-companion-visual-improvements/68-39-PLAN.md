**Decisions made here (owner can overturn at Task 2):**
- AIS-01 Where: unidentified prefix rows of `/airlines/manage` only (the only place unresolved airlines are handled; Health's registry table is untouched).
- AIS-02 Model: `claude-haiku-5-5` (Claude Haiku 5.5, retirement not before 2027-10-07). Verified 2026-11-21 against platform.claude.com docs (models overview, API versioning, errors, thinking); the `claude-api` skill is not installed in this environment, so the docs are the source. One constant `MODEL_ID`.
- AIS-03 Where the call lives: `server/plane/airline_suggest.py` (pure logic, cache, client; stdlib plus `requests`, already in `server/requirements.in`, so no new dependency and no SDK, hashes untouched), called only from the companion's admin route handler. NOT from the systemd poll timer (oneshot every 30 s with `TimeoutStartSec=90s`: a hot path that would spend money when nobody looks, and would put a network call inside the detect/render cycle) and NOT during page rendering.
- AIS-04 Async design: pages render from the cache only. A prefix with no cache entry renders a "Looking for a name" pending tag carrying `data-suggest-*` attributes; `airline-suggest.js` asks `POST /airlines/suggest` for ONE prefix at a time (at most 3 per page load) and swaps the returned server-rendered row. `ThreadingHTTPServer` already gives each request its own thread, so a slow API call blocks only that one request, never the page, other pages or the poll. No background thread, no in-process queue state, no new systemd unit. Without JavaScript the page shows cached suggestions and the Name it button (the editor must work with scripts blocked).
- AIS-05 Cache: `{root_state_dir}/airline_suggestions.json`, written with `server/atomic_io.atomic_write` under a module lock, one entry per prefix: state (`suggested`, `none`, `rejected`, `accepted`, `edited`, `failed`), proposed name, `model`, `asked_at` (UTC ISO), `failed_until`. Global (root), not per frame: a callsign prefix means the same airline for every frame. At most one request per prefix ever; `none`, `rejected`, `accepted` and `edited` are permanent tombstones (a prefix that is un-named later is not re-asked). `failed` is retried after `FAILURE_TTL_S` (900 s transient: timeout, 429, 5xx, 529, network) or `AUTH_FAILURE_TTL_S` (21600 s: 401, 402, 403, 400). Entry cap 500, oldest `asked_at` evicted.
- AIS-06 Rate cap: persisted call timestamps in the same file; at most 10 calls per rolling hour and 60 per rolling day across all prefixes; over the cap the route answers `busy` without calling the API.
- AIS-07 Timeout: `requests.post(..., timeout=(3.05, 8), allow_redirects=False)`, `max_tokens` 120, one attempt (no retry loop; the cache-on-failure rule is the retry policy).
- AIS-08 Reject/edit: the Edit dialog (prefilled with the suggestion) carries a secondary "Remove the suggestion" action (`POST /airlines/suggest/reject`, state `rejected`, row falls back to Name it). Naming by hand through the resolve route records `accepted` (posted name equals the cached suggestion, compared server-side, never a client flag) or `edited`.
- AIS-09 Livery illustration: OUT OF SCOPE and DEFERRED. Generating a livery drawing for the named airline is a different feature (image generation, storage, moderation, a different cost profile) and is not coupled to naming; it is not planned, not mocked and not built here. If the owner wants it, it needs its own mockup, research and plan.
- AIS-10 Access: administrators only, same `ADMIN_DEVICE` routes as the rest of the editor; owners and co-managers get the unknown-path 404 like `/airlines/resolve`.
