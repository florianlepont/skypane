<task type="checkpoint:decision" gate="blocking">
  <name>Task 2: Owner decides the OTA signing option</name>
  <decision>Which OTA signing option does the owner choose for the fleet: S, P, M, N, or a combination (S+M, P+M)?</decision>
  <context>
    Today every OTA image is signed with one RSA-3072 key and the live frame trusts the key of the image it runs. The choice fixes how a second hardware type is protected from receiving the wrong binary on the device side, and whether the live frame or the second board needs a one-time cable flash. It must be recorded before any second hardware is provisioned. Read the option matrix in firmware/SIGNING.md "Decision record (OTA-03)" first.
  </context>
  <options>
    <option id="option-s">
      <name>S - one key for all hardware types (status quo)</name>
      <pros>No change for the live frame, no cable flash for it, no CI change; the second board is cable-flashed once with the existing key.</pros>
      <cons>Signature gives no cross-type protection; one key compromise affects the whole fleet; same chip plus same project name relies on server typing alone.</cons>
    </option>
    <option id="option-p">
      <name>P - one key per hardware type</name>
      <pros>A wrong-type binary fails the device's signature check even if the server is wrong; the live frame keeps its key.</pros>
      <cons>A second signing secret and per-type CI signing step, per-type public keys committed, more keys to back up and rotate.</cons>
    </option>
    <option id="option-m">
      <name>M - single key plus a unique project_name per type</name>
      <pros>The live frame's existing project-name check already rejects other names with no firmware change; cheap.</pros>
      <cons>Needs per-type build parametrisation of the project name (second-hardware work); no cryptographic separation.</cons>
    </option>
    <option id="option-n">
      <name>N - do not sign the new type (TLS and SHA-256 only)</name>
      <pros>No signing machinery for the new board.</pros>
      <cons>Weakest integrity; the new type's sdkconfig must opt out of the shared signing lines; a later move to signing needs a cable flash.</cons>
    </option>
  </options>
  <files>firmware/SIGNING.md</files>
  <action>Stop and present the options to the owner; do not choose. Continue only on the owner reply.</action>
