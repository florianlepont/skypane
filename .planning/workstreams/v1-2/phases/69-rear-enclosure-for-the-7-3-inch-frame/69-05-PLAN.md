<objective>
Write the improved Wi-Fi comparison protocol and take the bare-frame baseline now, while the prints are still to come.

Purpose: success criterion 5 (Wi-Fi no worse than without the enclosure) needs a baseline measured before the enclosure exists, at the spot where the frame will hang, and a protocol that is not fooled by one noisy snapshot per wake. The earlier "20 wakes then 20 wakes, medians within 3 dB" rule compared two point estimates with about 1 dB of standard error each and a time-drift confound, so it is replaced.
Output: `hardware/ENCLOSURE-WIFI-TEST.md` with the protocol and the block A1 readings. The blocks with the enclosure (B1, A2, B2) and the verdict are done in the validation plan, after the enclosure is assembled.

Runs in wave 2 with no dependency on any print: it can start today and run in parallel with the print rounds.
</objective>

Create `hardware/ENCLOSURE-WIFI-TEST.md` in English, plain prose, no plan, decision or phase IDs. Contents:

1. "What is measured": the frame's own received signal strength, one integer in dBm per wake (the value the firmware sends in the X-Rssi header with each display request; 0 means the reading failed and is not data). Say that no measured attenuation figure for PETG at 2.4 GHz was found, so this is measured, not predicted; the antenna sits above the board on a block 7 mm from the screen, near the battery pocket (design values, not measured).

2. "Why not 20 wakes then 20 wakes": one snapshot per wake, 1 dB resolution, wake-to-wake spread assumed 2 to 4 dB (an assumption, measured from the data here), a standard error of the difference of medians of roughly 1 dB or more at n = 20, and time of day, other users of the access point and small position changes are confounded with the enclosure when the runs are sequential.

3. "Protocol": (a) the bare frame baseline A1 is taken now at the exact spot and orientation where the frame will later hang; mark the spot with tape and keep a photo (the owner keeps the photo, it is not committed); record the access point name, whether USB is plugged, and how the battery was charged; (b) after assembly the blocks run in the order B1, A2, B2 (enclosure, bare, enclosure) at the same spot, same orientation, same access point and about the same time of day, so the arms are interleaved A1, B1, A2, B2; (c) each block is at least 15 kept wakes; at the live frame's 300 second cadence a block takes about 75 minutes (the second hardware's own cadence is asked in Task 2); (d) discard the first wake after moving or reassembling the frame; (e) drop every row with rssi 0 and report how many were dropped per block; (f) report per block: wakes kept, zeros dropped, minimum, first quartile, median, third quartile, maximum, standard deviation; (g) fewer kept wakes than planned means "not done", never extrapolated or filled; (h) in this file keep the raw rssi integers of each block in time order (without timestamps beyond the block start and end, without device identifier) so the statistic can be recomputed.

4. "Statistic and verdict rule (design values, the owner may adjust and records any change with date)": difference of medians, all B readings minus all A readings (A1 and A2 pooled, B1 and B2 pooled), with a one-sided 95 percent bootstrap interval: resample each arm with replacement 5000 times with a fixed seed of 1, take the difference of medians each time, lower bound is the 5th percentile. Pass if the lower bound is above -3 dB. With a standard deviation of 3 dB and 30 kept wakes per arm this means the observed difference has to be no worse than about -1 dB (arithmetic, not a source). Also report the original rule (medians of B no more than 3 dB below A) as a second line and say which rule the verdict applies. Drift check: report the difference between the medians of A1 and A2; more than 2 dB is flagged "access point drift suspected" (design value). The statistic is computed by Claude from the raw readings in this file in a throwaway computation, nothing committed; the file states "computed by Claude from the owner's readings recorded above" and the owner's acceptance with date.

5. "If it fails": a block C with the enclosure open and the lid off separates the plastic from the antenna move and the battery; a U.FL antenna extension is the documented fallback; choices (change the lid or hook design, accept, retest) are the owner's and are recorded with date. Optional: a phone Wi-Fi analyser reading at the frame's spot is a sanity check of the access point strength only, not of the frame's antenna.

6. "Export": read-only `GET /api/export/battery-history` for the frame's device with `since` as a UTC ISO time, with the export bearer token supplied by the owner from the environment; the token, the device identifier and the access point password are never written to this file or to any message; the owner pastes only the rssi values (and block start and end), not the rows' other columns; only the access point name is recorded.

7. "Block table" (columns Block, Condition (A bare, B enclosure), Order, Start, End, Wakes kept, Zeros dropped, Min, Q1, Median, Q3, Max, Std dev, Access point name, Position (tape-marked spot yes or no), Power (USB or battery), Source), rows A1, B1, A2, B2, all empty. Then "Raw readings" with one empty line per block, and "Verdict" as a bulleted list (not a table, so the empty-template check below stays meaningful) with fields: n kept in A, n kept in B, difference of medians, one-sided lower bound, rule applied, second-line result, drift check, computed by, owner accepted on (date), result (pass, fail or not done). All empty or "not done". No row may contain a date or the word pass in the empty template.
