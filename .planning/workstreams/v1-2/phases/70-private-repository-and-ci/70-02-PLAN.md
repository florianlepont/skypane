  <action>
Session prepares and shows the owner these exact steps (it does not run any of them, and never asks for a secret value). Owner steps, on the Mac, in a terminal where `gh` is logged in as the owner:

1. List where the secrets live. Run `gh secret list`, then `gh secret list --env production`, then `gh secret list --env firmware-signing`, then `gh variable list`. Reply with the NAMES only (never values). Expected repository-level names: DEPLOY_SSH_PRIVATE_KEY, DEPLOY_HOST_KEY, DEPLOY_SSH_TARGET, PRODUCTION_HOST. If any of the first three appears only under `--env production`, the owner re-creates it at repository level in step 3.
2. Create the dedicated deploy key pair on the Mac: `ssh-keygen -t ed25519 -f ~/.ssh/skypane-deploy-ci -C skypane-deploy-ci -N ""` (a new file; do not reuse the login key).
3. Install the public half on the VPS: append the single line from `~/.ssh/skypane-deploy-ci.pub` to the deploy user's `~/.ssh/authorized_keys` on the VPS (log in with the existing key, as for any admin task). Keep the old key line until the proof run passes.
4. Store the private half and any missing secret at repository level: `gh secret set DEPLOY_SSH_PRIVATE_KEY < ~/.ssh/skypane-deploy-ci`, and if needed `gh secret set DEPLOY_HOST_KEY` and `gh secret set DEPLOY_SSH_TARGET` (the value is typed or pasted at the prompt by the owner, never given to a session). Then `shred -u` or securely delete nothing yet: keep the private key file on the Mac only until step "revoke" below.
5. After the proof (Task 3) passes, remove the OLD key line from the VPS `authorized_keys`, so only the dedicated key remains; the old repository secret value is overwritten by step 4 itself.

Session records in `70-EVIDENCE.md` under a heading "Manual deploy proof": which secret names exist at which level (names only), the date, and that the dedicated key was installed (yes/no). Never include a value or a fingerprint.
  </action>
