# Phase 55 — UI Design Contract

> Visual and interaction contract. Generated by gsd-ui-researcher, verified by gsd-ui-checker.
> This phase adds NO tokens, NO colours, NO accent consumers, NO fonts, NO motion to the companion stylesheet. Every companion value is read from `companion/static/style.css` and the `sketch-findings-skypane` skill (locked). If a sentence here seems to need a new value, reuse an existing one. The only genuinely new visual artefacts are the two e-ink screens (Surface 7), which live in the frame's own palette and never touch `style.css`.
> Owner decisions D-06..D-21 of 55-CONTEXT.md are inputs, not questions. Nothing was asked of the user.

## Surface Contracts

Every console page (Fleet, Users, Locations, Audit log) renders a **section sub-nav** at the top of the content: a wrapping row of five chips (Fleet, Users, Locations, Audit log, Releases) using `.filter-bar__chips` styling, current page selected, wrapping to two lines at 360px, no horizontal scroll. **User, sidebar:** wordmark (links to the first frame's Home, or `/account` with no frames), "Account" link, then the frame pages for the selected frame: Home, Flights, Display, Calendar, Airlines, Health. ### 1. Fleet page (admin; "Fleet")

`layout.page_header("Fleet", purpose="Every frame on the platform, with its owner and state.")`, section sub-nav, then three cards in this order: Fleet table (`.page-section`), "Pair a frame" (`.page-section--nested`-tier title), "Register a frame". Pair is above Register because pairing is the frequent act; Register is the rare provisioning step.

**Fleet table card.** Columns (>=960px, `.data-table` in `.data-table-wrap`, `th` in 12px label voice):
Frame (name 16px semibold; second line 14px mono id, `.cell-secondary`) | Owner (email, or "Unassigned" / "Non attribué" in muted text for pending; retired shows previous owner with "formerly" prefix) | Hardware (display name, e.g. "13.3 in Spectra 6") | Last seen (`.time-value` + relative age) | Battery (percent + `.time-value`-style tabular number; "n/a" when unknown) | Firmware (version string, 14px mono) | Status (badge) | Actions.
Sorting: live first, then pending, then retired; inside each, most recently seen first. No client sort, no search box in v1 (fleet is small; a `.filter-bar` search is NOT added). Row count caption in `.filter-bar__count` style: "3 frames".

**Below 960px each row becomes a stacked `.data-card` block** (label voice labels, value 16px), with Status badge beside the frame name and the Actions group at the bottom of the card, buttons wrapping at 44px height. No horizontal scroll at 360px (assert scrollWidth <= clientWidth).

**Row actions by state** (all quiet secondary buttons, 30px >=960px / 44px below; the first action is a `.text-link`):
| State | Actions |
|-------|---------|
| Live (non-live-frame) | Open frame (link to `/devices/<id>/`), Reassign, Retire |
| Live frame (`state_path = "."`) | Open frame, Reassign (owner only; confirm text says data is NOT wiped); Retire is NOT rendered (refused server side; absent here, tooltip-free) |
| Pending | Open is absent (no pages yet), Show code status is not offered (the code is only on the panel). Action: none except Retire is also not offered; pending frames can be removed only by CLI. Row shows the text "Waiting for pairing" in the Owner cell |
| Retired | Re-activate |

**Confirm pattern (no JS required, no dialog, no motion).** Reassign, Retire and Re-activate use an inline two-step `<details>` in the actions cell: the `<summary>` is the quiet action button ("Retire"); opening it reveals, in flow, a confirm block containing (1) one sentence naming consequence (Copywriting below) with the toast `error`/`warning` glyph in front, (2) for Reassign a `<select>` of target users (own label "New owner"), (3) a quiet submit button with the action verb ("Retire frame") and a specific keep-as-is `.text-link` (never a generic "Cancel"): "Keep frame" (Retire, Reassign, Re-activate, frame actions), "Keep user" (Disable, Demote, Unlink identity), "Keep location" (Delete location), "Keep as is" (fallback for any other confirm). It is a `<label for>` / second `<summary>` that re-closes the details (no script); strings in the Copywriting table. At most one is open at a time is NOT enforced (no JS). The form carries the hidden CSRF field. Below 960px the confirm block spans the card width. After submit: PRG redirect to Fleet with a flash toast (success tone) naming the result; a refused action (live frame retire, stale state) is an `error` flash toast, not an inline error. No browser `confirm()` and no `<dialog>` in this phase.

**Empty state (no frames at all):** `empty_state` full-card: heading "No frames yet", body "Register a frame below, then enter the code shown on its screen." Table is not rendered. The two form cards still render.

### 2. "Pair a frame" claim card (Fleet page)

Title (nested tier): "Pair a frame". Purpose line (14px): "Enter the code shown on the frame's screen and choose who it belongs to."
Fields, stacked, full width:
1. "Pairing code": one text input, mono, uppercase, `autocomplete="off"`, `autocapitalize="characters"`, `spellcheck="false"`, `inputmode="text"`, `maxlength="12"`, placeholder "XXXX-XXXX". Case-insensitive; the server normalises look-alikes (O->0 not applicable: alphabet excludes 0/1/I/L/O/U, so I/L->1 style mapping is server-side only). The hyphen is optional on input. No client-side formatting script (no JS).
2. "Owner": `<select>` of active users (email, role in parentheses for admins). Required. Disabled users are not listed. Own label.
3. Primary submit "Pair frame", 44px, full width at 360px, auto width above.
Hidden CSRF field. Autofocus on the code input only when the page is reached with `?pair=1`; otherwise no autofocus (the page has a table first).

States (rendered as one `toast--docked` in flow directly above the form inside the card, `role="alert"` for errors, `status` for success; no field-level colour change except `.field-error` on the code input):
| State | Presentation |
|-------|--------------|
| Success | PRG redirect to Fleet; success flash toast: title "Frame paired", detail "{frame} now belongs to {email}. It shows its first image at the next update." The new live row is visible in the table (this answers the owner-reported "white after claim" fact: the detail text says "at the next update" and nothing more) |
| Invalid, expired or already claimed | ONE identical message for all three: error docked toast title "Code not recognised", detail "The code is wrong, expired or already used. A new code appears on the frame within 35 minutes." Code input keeps the typed value (re-rendered escaped, upper-cased), `.field-error` under it repeats "Check the code and try again." |
| Throttled (per session or global) | warning docked toast title "Too many attempts", detail "Wait a few minutes before trying again." No countdown number, no live timer (avoid leaking the threshold and keep the page script-free); submit stays enabled (the server decides) |
| No owner chosen / empty code | `.field-error` under the offending field, "Enter the pairing code." / "Choose an owner." (400, no throttle count) |
| No pending frames exist | The card still renders; below the form a `.text-label` line: "No frame is waiting for a code. Register one first." (informational only, form not disabled, since a frame can register mid-way) |
| Selected owner has no valid role (race) | `.field-error` under Owner: "That user is no longer available." The code is NOT consumed (single transaction rolls back) |

Never echo the guess in an audit-visible place, in the URL, in a toast, or in `title` attributes. The typed value is re-rendered only into the input's `value` on the immediate error response (POST response, no-store).

### 3. "Register a frame" card (Fleet page)

Title: "Register a frame". Purpose (14px): "Use the MAC and secret hash printed by the provisioning script. The secret itself is never entered here."
Fields: "MAC address" (mono text, `placeholder="AA:BB:CC:DD:EE:FF"`, accepts `:` `-` or none, server normalises), "Secret hash (SHA-256)" (mono text, 64 hex characters, `placeholder="64 hex characters"`, `maxlength="64"`, `pattern` for 64 hex; `autocomplete="off"`, NOT `type=password`, because it is a hash and the operator needs to verify a paste), "Hardware" (`<select>` of hardware profiles from `server/hardware.py`, label = display name). Submit "Register frame": quiet secondary button (not accent), 44px height; the claim card's "Pair frame" is the page's single primary.
Guard text under the hash field (14px, `.section-caption`): "Paste the SHA-256 value only. If you paste anything that is not 64 hex characters it is refused." Errors: `.field-error` per field: "Enter a valid MAC address." / "Enter the 64-character hash." / "Choose the hardware type." / duplicate MAC: error flash "A frame with this address is already registered." Success: flash success "Frame registered", detail "Power it on. It shows a pairing code within 5 minutes." Pending row appears in the table.

### 8. E-ink screens (pairing and retired; 1200x1600 portrait, `server/pairing_image.py`)

Separate design system: frame palette only, indices Black 0 (0,0,0), White 1, Yellow 2 (240,224,80), Red 3 (160,32,32), Blue 4 (45,95,155), Green 5 (50,105,65). The panel is ~150 ppi, so 1px = 0.17 mm; the type sizes below are chosen for reading at 2 m (cap height >= 10 mm needed for the code, >= 5 mm for secondary text at ~1 m viewing for the instructions).

**Determinism rules (both screens):** no clock, no countdown, no expiry text, no frame id, no MAC, no RNG-derived decoration; the only varying input is the code string. Same inputs produce the same bytes. Text is drawn with antialiasing OFF (Pillow `fontmode = "1"`) in exact palette indices, no gradients, no dithering, no transparency; layout coordinates are integer constants; fonts are the vendored files only, never a system font. Backgrounds are pure White (1). Dark/colour fills are flat. Other hardware profiles (non-1200x1600) scale all coordinates and sizes by `min(w/1200, h/1600)`, margins likewise, never re-flowing text.

**Pairing screen layout (EN on top half, FR below; one code shown once):**
| Zone | y range | Content |
|------|---------|---------|
| Header band | 0..220 | Red (3) full-width band; White text "PAIR THIS FRAME" in Inter Bold 88px, left margin 80px, vertically centred; thin Black rule is NOT used |
| English block | 260..520 | Inter Regular 52px Black: "1. Open SkyPane on your phone or computer." / "2. Ask your administrator to enter this code." (2 lines wrapped at 1040px, 68px line pitch) |
| Code block | 560..1040 | Black 6px frame (80px side margins) around a White box; inside, the code `XXXX-XXXX` centred horizontally and vertically in Inter Bold 168px Black, tracking +10px, hyphen 0.6x width. 8 characters + hyphen must fit in 1040px minus 96px padding; if the measured width exceeds 944px the font size steps down in 8px decrements to a floor of 128px (deterministic: depends only on glyph metrics). A Yellow (2) 24px strip along the box's bottom edge is NOT used (keep it plain; yellow is not legible at distance) |
| Validity line | 1060..1130 | Inter Regular 44px Black centred: "Code changes about every 30 minutes." / "Le code change environ toutes les 30 minutes." (static text, no times) |
| French block | 1180..1440 | Inter Regular 52px Black, same structure: "1. Ouvrez SkyPane sur votre téléphone ou ordinateur." / "2. Demandez à votre administrateur de saisir ce code." |
| Footer | 1500..1600 | Blue (4) 8px rule at y=1500; below it Inter Regular 40px Blue: "SkyPane" left-aligned at 80px; right-aligned "Waiting for pairing / En attente d'association" |
Minimum text size anywhere on the screen is 40px. Left margin 80px, right margin 80px. All lines left-aligned except the code, validity line and header, which follow the table. The code uses only the 30-symbol alphabet, so no glyph ambiguity (no 0/O, 1/I/L); the code is shown in upper case.

## Interaction and Accessibility Requirements

- 360px: every console table collapses to `.data-card` blocks below 960px; assert `scrollWidth <= clientWidth` at 360 on Fleet, Users, Locations, Audit; keep the 320px assertions passing.
- Touch targets: claim form, invite form, location form controls and every confirm button >= 44px (measured by hit-testing in own container, per the skill's rule); `<summary>` actions and "Older/Newer" links >= 44px; row actions at 30px only at >=960px.
- Focus order follows reading order; the opened `<details>` confirm block's first focusable element is its `<select>` or submit; visible focus ring is the existing accent ring. After a PRG redirect, focus lands at the top; the flash toast is `role="status"` (success) or `role="alert"` (warning/error) per the toast contract; success auto-hides at 6s, warning/error never auto-hide.
- Docked toasts above forms have no dismiss and no timer.
- Forms are native POSTs with a hidden CSRF input (`name` defined by planner, value never visible, never in a URL). A missing/bad token answers an error flash "This page expired. Reload and try again." / "Cette page a expiré. Rechargez-la et réessayez." (no state change).
- No new motion: no animation on `<details>` open, no spinner, no counting numbers; `--motion-*` tokens unspent. Reduced-motion block count unchanged (2).
- No JavaScript is required for any new surface; `.js`-gated enhancements are not added. Every hidden-for-role section is absent from the served HTML.
- Both themes verified via the existing theme-switch browser harness; all pairs are existing tokens (no new contrast pair). Status never by colour alone.
- Dates are Paris local via `.time-value`; MAC/hash/id in `--font-mono`; the full hash is selectable and the table shows 12 characters plus an existing `.copy-btn` for the full value.
- Tests assert served HTML/CSS and browser results (button measured sizes, absence of admin links and sections for `user`, 404 body identity, no `<dialog>`/`confirm(` in served scripts for the new pages), plus pixel-exact determinism of the e-ink screens (same code -> identical bytes; only palette indices; no pixel outside the six colours; text >= 40px).
