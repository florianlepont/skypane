- Decided mechanisms (so the executor does not invent them): (1) Re-showing the name after a refused code. A refused code is answered with a redirect (`h.redirect(again, set_cookie=pair_code_cookie.keep_header(key, code))`, Post/Redirect/Get) and `h.redirect` carries exactly ONE Set-Cookie, so the name rides in the SAME existing cookie `sp_pair_code`, never in a URL, flash, audit row or log: the cookie value becomes `<session key>.<CODE>.<name as lowercase hex of its UTF-8 bytes>` (the hex alphabet keeps the value cookie-safe and inert). `pair_code_cookie.keep_header(session_key, raw_code, name="")` gains the optional name (stored only when `frame_name_page.normalise_name` accepts it; at most `MAX_NAME_CHARS` = 40 characters, so at most 320 hex characters); a new `pair_code_cookie.take_with_name(cookie_header, session_key)` returns `(code, name, clear)`, re-validating the name with `normalise_name` and returning "" for another session's cookie or a malformed value; the existing `take` keeps its `(code, clear)` result as a thin wrapper so its callers and tests are unchanged. The cookie keeps its flags (HttpOnly, SameSite=Strict, Path `/pair-frame`, 120 s) and is cleared the first time the form shows. `handle_get` puts the name back into the name input once. (2) Applying the name after a successful claim. `frame_rename._store(h, device, name)` is private (it stores and audits in one transaction); add a small public function `frame_rename.store_name(h, device_id, name)` holding that body, and make `_store(h, device, name)` call it with `device.id`, so the rename dialog behaves exactly as before. `user_pairing.handle_post` validates with the already public `frame_name_page.normalise_name` BEFORE the claim and calls `frame_rename.store_name(h, device_id, name)` only after `claim_code` succeeds.
