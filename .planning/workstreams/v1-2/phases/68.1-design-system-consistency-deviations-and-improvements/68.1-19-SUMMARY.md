# Phase 68.1 Plan 19: Add a frame in two steps (P06) Summary

`/pair-frame` is now two numbered steps on one card: Step 1 "name it" (optional frame name) and Step 2 "enter its pairing code" (code, plus the administrator-only Owner), with one Add frame button; the name goes through the existing rename rules after a successful claim.

## What changed

- `pair_frame_page.py`: ordered list `.pair-steps` of two `.pair-step` items (title carries its number as text), `PairView.name_value` and `name_error`, `NAME_FIELD = "frame_name"` (maxlength 40). The old card heading message was replaced by the two step titles and one help line; the name label and the invalid-name error reuse the rename dialog's `frame_name.label` / `frame_name.error`.
- `user_pairing.py`: a blank name is no name and no error; a non-blank name that `normalise_name` refuses answers 400 with `name_error` before the throttles and the claim; a valid name is applied with the new public `frame_rename.store_name` only after `claim_code` succeeds. The lockout (429), empty-code, invalid-name and owner-gone answers echo the typed name through the view; only the redirect after a refused code uses the cookie. The administrator-for-another-owner flash names the frame by the applied name.
- `pair_code_cookie.py`: `keep_header(session_key, code, name="")`, `take_with_name(...) -> (code, name, clear)`; `take` is a thin wrapper. The name rides as lower-case hex of its UTF-8 bytes in the same `sp_pair_code` cookie (`<key>.<CODE>.<hex>`), stored only when `normalise_name` accepts it and re-validated on read; same flags, path and lifetime.
- `frame_rename.py`: `store_name(h, device_id, name)` holds the former `_store` body; `_store` calls it.
- `frame_name_page.py`: `_LABEL` renamed to the public `LABEL` so the pairing page can reuse the message (no behaviour change).
- `style-admin.css`: `.pair-steps`, `.pair-step`, `.pair-step__title` (tokens only; `.pair-card__heading` removed, unused). No new token, no new animation, no new reveal block (the page still has its one `.reveal` form).
- EN and FR strings in `companion/i18n_fr/pair_frame.py` (two step titles, one help line).
- No new route, table, column, cookie or helper design.

## Tests

- `companion/test_browser_add_frame_steps.py` (red first, 48 failures before the feature): EN/FR, Light/Dark, 360 and 1280px, user and administrator (Owner only for the administrator), 44px targets, no sideways scroll, code field keeps the uppercase identifier treatment and the name field does not, text contrast at least 4.5:1, no running animation under reduced motion, a named frame is paired under its name, a refused code keeps the (escaped) name for the retry and stores nothing, an invalid name is refused in words beside the field.
- `companion/test_user_pairing.py`: two steps, named pairing, blank name, invalid names (400, nothing claimed), markup stored as text and escaped, refused code never stores or echoes the name (Location, cookie, database), the four direct re-render paths, cut at 40 characters, administrator flash names the applied name (EN and FR), a plain user cannot reach another frame.
- `companion/test_pair_code_cookie.py`: round trip, inert hex, refused names not stored, another session's cookie, tampered values, unchanged code-only behaviour, flags.
