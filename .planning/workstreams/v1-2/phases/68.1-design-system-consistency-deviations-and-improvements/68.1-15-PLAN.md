- PR #583 (the Plan 05 fixes) is already merged (commit 491f39e6 in main); start from current main, after plan 14.
- CI is the reference for browser tests. Draft PR only. No production deploy. No REQUIREMENTS checkbox ticking. No change to e-ink frame screens.
- Source of the build id (decision of this plan, from the mockup's "to confirm where it comes from"): no build info exists in `companion/` today. The release is staged to `/opt/skypane/releases/<sha>/` by `deploy/activate.sh` and the app runs from it, so `companion/build_info.py` derives the short SHA (7 hex characters) from the name of the release directory the code runs from when it is a 40-hex name, else from a `SKYPANE_BUILD` environment value matching 7 to 40 hex characters, else `dev`. Symlink rule: the service runs `/opt/skypane/current/companion/app.py` and `current` is a symlink to `releases/<sha>` (`deploy/activate.sh`, `CURRENT_LINK`), so `__file__` may resolve under `/opt/skypane/current/`, whose name is not a SHA. `build_info.py` therefore MUST call `os.path.realpath` on the path of the code (the module's `__file__`) before reading the release directory name; without it the VPS would always show `dev`. `SKYPANE_BUILD` is NOT set by any deploy file today (`deploy/skypane-companion.service`, `deploy/activate.sh`, `.github` workflows: grep returns nothing); it is only a test and manual override, and the plan does not add it to any deploy file. If during Task 2 this proves not to hold on the VPS (check `deploy/README.md` and `deploy/skypane-companion.service`), stop and ask: do not change deploy files in this plan.
</preconditions>
