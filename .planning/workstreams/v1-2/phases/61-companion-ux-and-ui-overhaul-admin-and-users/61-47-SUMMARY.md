## Security note

- The only new write path is `POST /pair-frame`. It claims a code for the caller only; registration by MAC or enrolment secret (`/fleet/register`) and owner choice (`/fleet/pair`) remain administrator-only and are covered by matrix rows and a test that a user gets 404 on all three.
- Code handling is the same as the admin route: both throttles are checked before any code is evaluated, a refusal advances both counters, the typed code is never stored, audited, logged, put in a URL, cookie or flash and is echoed (capped to 32 characters, escaped) only into the input of the immediate no-store refusal.
- The global lockout bucket is shared between users and administrators (by design the same as before), so a user burning 20 wrong guesses in 15 minutes locks pairing for everyone for that window; this bounds guessing of the 8-character code space but means a hostile signed-in user can deny pairing temporarily. Accepted (sign-in is invitation-only); a per-user cap could be a later hardening.
- A session without a user id (legacy shared-password principal) gets the unknown-path 404 on `/pair-frame` since no owner can be derived.
- No change to the frame protocol or to the server's behaviour towards a frame.

## Deviations from Plan

- **"User Home" empty state is on Account.** There is no Home without a frame, so the zero-frame landing (already `/account`) carries the calm empty state with the single primary action; frame pages for a frame-less user redirect there instead of 404 (an intentional change to an existing matrix test).
- **No dialog variant for users.** The Add a frame entries are plain links to the page (which also works with script); the existing dialog stays the administrator's Fleet flow. Reason: the dialog needs an owner chooser, the user flow has none.
- The strip still renders only with two or more frames (unchanged), so a one-frame user adds from Account.
