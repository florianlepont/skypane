# Phase 60 — UI Design Contract

> Visual and interaction contract for Device Co-Management (AUTH-08). Generated by gsd-ui-researcher, verified by gsd-ui-checker.
> This phase adds NO design tokens, NO colours, NO font sizes, NO weights, NO scripts and NO new component family. It composes existing `companion/static/style.css` pieces (see `.claude/skills/sketch-findings-skypane/`). Where this spec names a class, the executor must confirm it exists in `style.css` before use; the only new CSS permitted is a small additive rule block built from existing tokens (listed under Layout).

---

## Design System

| Property | Value |
|----------|-------|
| Tool | none (hand-written stylesheet, server-rendered Python markup; no component library) |
| Preset | not applicable |
| Component library | none |
| Icon library | in-repo inline SVG sprite (`layout.ICON_DEFS_HTML` / `layout.toast_icon_html`); this phase adds no new icon |
| Font | `--font-ui` system sans (body, controls); `--font-serif` Iowan Old Style / Charter stack for section headings only; `--font-mono` NOT used (e-mail addresses are not identifiers in the sketch-findings sense) |

Surfaces in scope (all server-rendered, no client JS, works with scripts blocked):

1. Co-managers card on the frame's Home page (`/devices/<id>/`), three variants: manage (owner or admin), read-only member (co-manager, non-admin), hidden (no fleet row / synthetic `live` frame / unreadable fleet.db).
2. Account page frames list: "Shared" mark on a co-managed frame.
3. Flash toasts for add / remove / leave / refusal (device-page query-string mechanism, `?flash=<key>`).
4. Leave confirmation (inline two-step, no dialog).

Existing tokens, unchanged (all multiples of 4):

| Token | Value | Usage in this phase |
|-------|-------|---------------------|
| xs `--space-xs` | 4px | Gap between a member's e-mail and its pill(s) when they wrap |
| sm `--space-sm` | 8px | Gap between the Add form's field and button when stacked; gap between a row's text block and its action |

Touch targets: Add button, Leave button and the `<details>` summary are the base `button` (36px below 960px / 30px at >=960px) or `.calendar-disconnect-btn` (min-height 30px) geometry, which is the project's already-registered "traded-away" entry, not a new trade. The e-mail text input and the admin `<select>` take the global 44px native-input floor, unmodified. Do not add a per-card height override.

## Color

No new colour, no new token. Existing three-surface model.

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | `--color-canvas` | Page background behind the card |
| Secondary (30%) | `--color-dominant` (card surface) / `--color-secondary` | The card (`.page-section`), member rows (`.data-card`) |
| Accent (10%) | `--color-accent` | See reserved list |
| Destructive | none | The app has no red destructive button (standing precedent). Remove and Leave are quiet greys; consequence is carried by copy and the warning glyph in the Leave confirm |

Accent reserved for (all pre-existing consumers, nothing added):
1. The single primary submit "Add co-manager" (`button[type="submit"]` accent fill) when the card shows the Add form.
2. Links (`.text-link` "Stay on this frame", the Account "Open" link).
3. The focused-input outline and the `:focus-visible` ring on every control.
4. The `<summary>` disclosure chevron of the Leave confirm.

Never accent: Remove buttons, Leave button (`.calendar-disconnect-btn` quiet treatment), pills, row backgrounds, the "Shared" mark.

Status colour: none. "Disabled" and "Shared" are neutral `.banner__pill`; state is never colour alone (the word is the signal). Error refusal uses the existing error toast tone (glyph + spoken prefix + colour).

## Layout and Components

### 1. Co-managers card (Home)

Placement: its own `<section class="page-section" aria-labelledby="home-co-managers">` after `.home-facts` in `home_page.render`, outside every freshness swap region and outside any `<form>` that wraps settings. Full-width like the other Home sections; follow the exact wrapper/heading classes of the sibling `home-flights` / `home-frame-state` sections. (Recommended default per RESEARCH A2; flagged below.)

Structure, top to bottom:

1. `<h2 class="text-heading" id="home-co-managers">Co-managers</h2>`
2. Purpose caption `<p class="section-caption">` (14px muted).
3. Member list `<ul class="data-cards">` of `.data-card` rows. Row 1 is always the owner; remaining rows are co-managers ordered case-insensitively by e-mail. Each row:
   - Primary line: e-mail (`.co-manager__email`, body 16px) followed by pills in a wrapping inline group (gap `--space-xs`): "Owner" on row 1; "You" on the viewer's own row; "Disabled" (manage variant only) on a disabled co-manager.
   - Manage variant, co-manager rows only: a trailing "Remove" button (`button.calendar-disconnect-btn`, `type="submit"` in its own `<form method="post">` carrying the CSRF field). Row layout: text block left, button right on one line when it fits; the button wraps beneath the text at 360px with `--space-sm` gap (flex-wrap, as `.status-row` already does). The owner row never has a Remove button.
   - Read-only variant: no per-row buttons.
4. Empty state (only reachable in the manage variant, since the owner row always exists and a co-manager always sees themselves): when there are zero co-managers, the list contains the owner row only, followed by `layout.empty_state(heading, body, compact=True)` beneath it.
5. Manage variant only: the Add form (below).
6. Read-only variant only, and only for a non-admin viewer who has a membership row: the Leave block (below).

Variant rules (derive from principal role and `device.owner_user_id`, never from "gate passed"):

| Viewer | Sees | Controls |
|--------|------|----------|
| Frame owner (any role) | owner + all co-managers (+ Disabled pills) | Add form, Remove per co-manager row |
| Admin (not a member) | same as owner | Add form (select variant), Remove per row |
| Admin who is also a co-manager | same as owner | Add form, Remove; NO Leave (admin keeps access regardless) |
| Co-manager (non-admin) | owner + all co-managers' e-mails, "You" pill on own row | Leave this frame only; no Add, no Remove |
| Anyone else | 404 (never reaches the page) | none |

Card is not rendered at all when the frame has no fleet row (synthetic `live` fallback) or fleet.db cannot be read (fail closed; mirror `console_locations.display_picker_html` guards). No placeholder, no error text.

### 2. Add form (manage variant)

Locked by CONTEXT D-08: a non-admin owner TYPES an e-mail; an admin MAY be offered the list. Spec:

- Owner variant: `<label for="co-manager-email">E-mail address</label>`, `<input type="email" id="co-manager-email" name="email" autocomplete="off" autocapitalize="none" spellcheck="false" required maxlength="254" aria-describedby="co-manager-email-help">`, helper `<p id="co-manager-email-help" class="text-label section-caption">`, then the primary submit "Add co-manager". Field and button stack (field full width, button below, `--space-sm` gap) at every width below 960px; at >=960px they may sit on one row centre-aligned ("separate objects" composition rule: each keeps its own registered geometry).
- Admin variant (recommended default, flagged): a native `<select name="email" id="co-manager-person">` replacing the text input, same label slot ("Invited person"), first option `Choose a person` (value empty, `required` so it cannot submit blank), then one `<option value="{email}">{email}</option>` per eligible candidate (invited, non-disabled, not owner, not already co-manager; ordered by e-mail). Option VALUE is the e-mail so both variants post the same `email` field and hit one server code path with one generic refusal. If there are no candidates the select and button are not rendered; show the Label-size line "Everyone who is invited is already on this frame." instead.
- The list of invited users is NEVER rendered for a non-admin (no privacy disclosure; resolves RESEARCH Open Question 1 in favour of CONTEXT D-08).
- No autocomplete datalist, no live validation, no script. Browser-native `type="email"` validation only; server remains authoritative.
- A refused add redirects back with an error toast. The typed address is NOT echoed (it would have to travel in the URL). Accepted trade-off; field returns empty.

### 3. Leave this frame (read-only variant)

Reuse the Fleet two-step pattern (`details.fleet-confirm`, `_confirm_html` shape in `fleet_page.py`): `<details class="fleet-confirm"><summary>Leave this frame</summary><form method="post" action="…/co-managers/leave" class="fleet-confirm__form">` + CSRF field + `<p class="text-body">` with the warning toast icon and the consequence sentence + `<div class="update-actions">` holding `<button type="submit" class="calendar-disconnect-btn">Leave this frame</button>` and `<a class="text-link" href="…">Stay on this frame</a></div>`. No `user_id` or frame id field is posted (server reads both from the session and the gate). Closed by default; opens natively; works with scripts blocked.

Flag: `grep fleet-confirm companion/static/style.css` returned no rule in this session. Research states a 44px target for the summary is asserted by `test_browser_fleet_page.py`; the executor must confirm where that geometry comes from (global `summary` rule at style.css:3593) and that the Leave summary measures >=44px in height at 360px in the card's own container (measure, do not borrow).

Remove (manage variant) is deliberately ONE step, no confirm: it is reversible (re-add), low blast radius, and the toast confirms. Leave is TWO steps because it is self-inflicted loss of access the user cannot undo.

### 4. Account page "Shared" mark

In `account_page._frame_row_html`, when `FrameSummary.shared` is true:
- Add a `.banner__pill` "Shared" beside the frame name in `.data-card__primary` (name left, hardware label then pill; wrapping allowed, gap `--space-xs`).
- Add a `<p class="text-label">` line "Owner: {owner e-mail}" under the name, escaped, `overflow-wrap: anywhere`. (D-06 permits co-managers to see the owner e-mail.)
- Everything else (last contact, battery, Open link and its `aria-label`) is unchanged. Heading "Your frames" and the empty-state copy are unchanged.
- Ordering unchanged (by name, casefolded). No separate group or sub-heading: a co-managed frame sits in the same list.
- An admin sees only frames they own or co-manage here (not every frame), per RESEARCH Pitfall 11.

### 5. Flash toasts

Device-page query-string flash registry (`companion/flash.py`), fixed keys, fixed text, no user value ever placed in a toast. Toast title and detail split at " — " (existing rule). Tones from the existing five.

| Key (suggested) | Tone | Role |
|-----------------|------|------|
| `co_manager_added` | success | status |
| `co_manager_removed` | success (bin glyph, like calendar disconnect) | status |
| `co_manager_left` | success | status |
| `co_manager_add_refused` | error | alert |
| `co_manager_failed` | error | alert |
| `co_manager_leave_noop` | info | status |

Post-action navigation:
- Add / remove / refusal / failure: redirect to the frame's Home via `device_scope.scoped("/")` with `?flash=<key>`.
- Leave success: the frame will now 404 for this user, so redirect to `/account?flash=co_manager_left`. The Account page does not render a flash toast today (no flash handling found in `sign_in.py`); the executor must wire the existing `flash_toast_html` into Account rendering for this one key, or, if that is judged too invasive, redirect to `/account` without a toast (the frame disappearing from "Your frames" is then the confirmation). Recommended default: wire the toast. Flagged.
- Leave by a viewer with no membership row (owner, admin non-member, crafted request): no change, redirect to Home with `co_manager_leave_noop`.

### Responsive and accessibility

- 360px contract: card content column is 360 - 2x24 page padding - 2x16 card padding = 264px at minimum. Verify at 360px in EN and FR with a 40-character e-mail: no `.data-table-wrap`-style inner scroll, `documentElement.scrollWidth == 360`, every row box contains its own content (measure the e-mail span against a `Range` over its contents, per the data-density lessons).
- Landmarks and names: section labelled by its `<h2>`; member list is a real `<ul>`; each Remove button has `aria-label="Remove {email} from this frame"` (visible text stays "Remove"); the Add control has a real `<label>`; the select's empty option is disabled-selected placeholder semantics via `required`.
- Pills carry text; "You" and "Owner" are not colour-coded. Disabled state is announced by the pill text inside the row.
- Focus: global `:focus-visible` 2px accent ring applies; DOM order equals visual order (list, Add form, Leave block); no focus trap; no `tabindex`.
- Errors: refusal and failure toasts use `role="alert"`; successes `role="status"`. No `aria-live` regions are added to the card. Toasts persist per existing rules (error never auto-hides).
- Motion: none added. `<details>` opens natively; no transition; the reduced-motion budget (keyframes 4, reduce blocks 2, no-preference 1) must not move.
- No script: nothing in this card uses the `.js` gate; every control is a native form post. Both themes: use tokens only; do not hard-code any colour (the stylesheet-structure guard rejects literals).
- Contrast: all text sits on existing token pairs already covered by `test_contrast_check.py`; no new pair is introduced.

Rules:
- One refusal for EVERY add failure a non-admin could trigger: unknown address, not invited, disabled, the owner's own address, already a co-manager, malformed. Never differentiate in text, status, redirect target, timing-visible behaviour or the flash key. (The audit row may record the specific internal reason; the user never sees it.)
- The admin select path can produce the same refusal for a stale candidate (disabled or added between render and post); it uses the same single message.
- No e-mail address, id or frame name ever appears in a flash string or the `?flash=` value.
- Destructive actions in this phase: Remove co-manager (one step, reversible, no confirm, toast confirms) and Leave this frame (two-step inline `<details>` confirm). Nothing in this phase deletes data; reassign and retire cascades are admin-console actions that already exist and are not re-specified here.
- Audit labels (Audit page, not this card): "Co-manager added" / "Co-gestionnaire ajouté" and "Co-manager removed" / "Co-gestionnaire retiré", added to `ACTION_LABELS` with French in `i18n_fr/admin_lifecycle.py`.

## Open Choices Flagged for the Planner (recommended defaults already applied above)

1. Add control for admins: select of eligible users, posting the e-mail value (owner variant stays a typed e-mail, per D-08). Alternative: admins also type. Default chosen because CONTEXT says "an admin may be offered the list". 3. Leave success lands on `/account` with a toast (requires adding flash rendering to the Account page for one key) versus plain redirect.
4. Remove has no confirmation; Leave has a two-step confirm.
5. French noun for "frame" and "owner" must be aligned with the existing French catalogue before shipping.
6. `.fleet-confirm` has no dedicated CSS rule found; confirm the 44px summary geometry by measurement.
7. The typed e-mail is not echoed after a refusal (it cannot travel in the URL); acceptable.
