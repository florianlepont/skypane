<objective>
Owner decision D-12 (a)(1): UNIFY the SQLite migration mechanism of history.db and fleet.db. Behaviour-identical for every existing file; no schema change, no version change, nothing applied to production. Builds on the Phase 66 results (do not reopen security review of file modes or access).

Why two policies are still needed (from the persistent-state map, 67-02): companion and the poll oneshot can open a fresh history.db at the same moment, so its steps must stay idempotent and race-tolerant ("duplicate column name" counts as done) and a newer stamp is never refused; fleet.db steps are one-time, run under BEGIN IMMEDIATE with the version bump in the same transaction, and a newer file is refused before the journal mode is touched (`FleetDbTooNew`). One mechanism, two explicit policies; no behaviour is merged away.

Output: `server/sqlite_migrations.py`, both modules rewired, characterisation and report tests, a backup/restore round trip. Three tasks, one draft PR. Safe by construction: tests that pin current behaviour are written and run green BEFORE the refactor.
</objective>
