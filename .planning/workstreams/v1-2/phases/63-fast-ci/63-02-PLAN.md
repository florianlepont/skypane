## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| PR code -> workflow | pull-request code runs in the test jobs with a read-only token |
| job -> job (artifacts) | coverage and junit files from test jobs are consumed by the aggregate |
| aggregate -> deploy | the `test` result gates a production deploy on main |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-63-04 | Elevation of privilege | `deploy` gating | mitigate | job id `test` and `needs: test` unchanged; aggregate uses `if: always()` but its first step fails unless every need is `success`, so skipped or cancelled jobs cannot yield a green result; proven by the throwaway-failure run |
| T-63-05 | Tampering | artifacts | mitigate | `permissions: contents read` stays; artifacts contain only coverage and junit data, are used only inside the same run, short retention; no secrets in any new job |
| T-63-06 | Repudiation | silently lost tests | mitigate | totals gate with executed floor, skipped ceiling and zero failures over every junit file; completeness check in the static job |
| T-63-07 | Tampering | new actions | mitigate | only `actions/*`, pinned by commit SHA with tag comment; tag-to-SHA verified through the REST API |
| T-63-SC | Tampering | package installs | accept | no new Python packages (coverage already comes with pytest-cov in the hash-locked requirements-dev.txt) |
</threat_model>
