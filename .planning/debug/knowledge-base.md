## illustration-crop-text-margin — aircraft-to-text gap and centering varied per airline illustration
- **Date:** 2026-08-28
- **Error patterns:** margin, gap, spacing, varies per file, illustration, alpha, transparent padding, getbbox, bbox, crop, centering, alignment, layout drift, render, e-ink panel, no error message, visual only
- **Root cause:** Layout anchored to the illustration's full source rectangle while the renderer hard-thresholds alpha at `> 127` before `paste()`. Every vendored PNG carries a soft drop-shadow band (alpha 1..127) that is therefore never painted, so the rectangle's edges sit 37-174px (bottom) / 3-32px (sides) away from the aircraft's real visible edges, by a per-file amount. The design constant had been "verified" with `Image.getbbox()`, which counts the sub-threshold shadow as content — and the two files checked at design time both happened to report a naive bottom padding of exactly 0.
- **Fix:** `draw_illustration()` returns an `IllustrationPlacement` carrying both `.rect` (full placement, for containment guards and stable sizing) and `.content` (the tight bbox of pixels actually painted, measured with the same named threshold the paste uses). All *position* anchors read `.content`: both text blocks' vertical gaps, the main illustration's horizontal centering, and the previous card's right-alignment and vertical centering. Gap/centre constants were re-derived from the developer-confirmed reference render so the approved look was reproduced rather than redesigned. *Sizing* deliberately still reads `.rect`, to avoid making one card's size depend on another file's padding.
- **Files changed:** server/plane/render.py, server/test_render.py, .planning/phases/03-visual-polish-on-real-glass/03-UI-SPEC.md, server/assets/icons/illustrations/HANDOFF.md
- **Transferable lesson:** When code both *measures* and *renders* an asset, make the two share one named threshold/expression. A "verified" measurement that used a different predicate than the renderer is indistinguishable from a correct one until something drifts. Also: a spot-check on one or two files was recorded as a fact about all files — the wording ("this specific illustration file") was the tell.

## heading-color-consistency — accent colour collided with the error colour, and section headings rendered four different ways
- **Date:** 2026-08-31
- **Error patterns:** no error message, visual only, UI, UX, CSS, design inconsistency, heading, typography, serif, font-weight, legend, fieldset, colour, color, accent, terracotta, status error, WCAG, contrast, AA, palette, token, design token, theme, dark mode, card surface, shadow, hairline border, table row separator, capitalization, acronym
- **Root cause:** One failure mode with two instances, not the five independent oversights it looked like. The design contract for headings *and* colours existed only as prose in `companion/static/style.css` comments, with nothing executable enforcing it — and each prose rule had a coverage hole. (a) COLOUR: the separation guarantee named exactly one pair to keep apart, accent vs `--color-status-warn`. So when phase 06.6.2 darkened the accent `#E8622C` -> `#B13F16` to fix a WCAG AA failure (UXA-04), it moved the accent to ΔE76 22.9 / 15.9° from `--color-status-error` — *closer* than the ΔE76 28.6 warn separation the direction had examined and accepted — and all 16 contrast checks stayed green, because contrast and separation are orthogonal questions. Same collision in dark mode (22.3 / 16.9°). In both themes the accent's nearest neighbour was the one status colour nobody had ever measured it against, so "Save Settings" and "something is wrong" became near-identical brick reds. (b) HEADINGS: the serif allow-list omitted `legend`, which is a real section-heading role (Config's D-06 uses `<legend>` *instead of* an `<h2>` so a group is never named twice). The standalone `legend` rule's own `font-weight: var(--weight-semibold)` sat later in source order at equal specificity, silently beating the serif rule's `--weight-regular` — stacking a sans-semibold `<legend>Diagnostic LED</legend>` directly above a serif-regular `<h2 class="text-heading">Poll</h2>` at the identical 20px. With no single enforced heading role, per-page implementers reached for four different treatments on Config alone, where the Runway group ended up with no name at all.
- **Fix:** Made both contracts executable rather than advisory. Headings: `legend` added to the serif selector and its competing weight declaration removed; explicit heading rhythm so the role spaces identically on an `<h2>` or a `<p class="text-heading">`; Config's Runway group given a heading and Theme's label promoted to match, so all four groups are named once at one level. Colour: `hue_degrees()`, `hue_separation()` and `perceptual_distance()` (CIE76) added to `companion/contrast_check.py` with `MIN_SIGNAL_PERCEPTUAL_DISTANCE = 28.0` calibrated to the accent-vs-warn pair the direction had already validated; every accent/status pair now checked in both themes. The accent was deliberately NOT touched (UXA-04 stays intact) — the error token moved instead, to `#BE123C`, which also lifted its own worst-case text contrast 3.96 -> 5.16. Also swept up by the same audit: `--color-destructive` duplicating `--color-status-error` across four token blocks, `.page-section` never updated when the surface model went from two levels to three, the dark-mode card-edge override naming only three of six card components, and `.data-table td`'s separator drawn in the same token as `.row-alt`'s background (invisible on alternate rows).
- **Files changed:** companion/static/style.css, companion/contrast_check.py, companion/pages/config_page.py, companion/pages/health_page.py, companion/test_contrast_check.py, companion/test_companion_app.py, companion/test_config_page.py, companion/test_status_pages.py
- **Transferable lesson:** A design rule written as a prose comment is not a constraint — it is a wish, and it will be violated by the next change that has a good reason. The specific trap here: the guarantee was written as a *pair* ("accent must stay distinct from warn") rather than as a *property* ("accent must stay distinct from every status colour"), so it kept passing while the thing it was protecting broke. When a token is enumerated against named neighbours, ask which neighbours are missing from the list. Second lesson: contrast and perceptual separation are orthogonal — a full-green WCAG suite says nothing about whether two colours read as the same colour. Third: a CSS rule that restates a property already set by a shared rule, at equal specificity and later in source order, is a silent override; the fix is to delete the restatement, not to raise the winner's specificity. Fourth, process: five symptoms across three pages turned out to be two root causes, and enumerating them page-by-page would have produced five spot-fixes and left the mechanism intact.

## location-top-status-bar-band — Location map did not reach under Safari's status bar or bottom toolbar in an iPhone tab
- **Date:** 2026-11-12
- **Error patterns:** no error message, visual only, iPhone, iOS Safari, Safari tab, status bar, top band, flat colour band, ground colour, bottom band, collapsing toolbar, address bar, full-bleed, map, Leaflet, position fixed, 100lvh, 100dvh, safe-area-inset, viewport-fit cover, obscured inset, scroll pocket, scroll-edge blur, veil, seam, dark mode, frost, backdrop-filter, splash, Home Screen app, standalone
- **Root cause:** In an iPhone Safari tab the status-bar zone (63pt) and the toolbar zone (97pt expanded, 57pt collapsed) are obscured insets of the scroll view outside the layout viewport (safe-area-inset-top is 0). Safari shows there the document that lies above or below the window, or a flat colour where there is none; a `position: fixed` box never paints into them (WebKit only extends a detected fixed top box's colour as an opaque `WKColorExtensionView`, which is how a 4px fixed ground strip produced the flat ground band). The page sat at scrollY=0 with the map at the document top, so the top was always a flat band (the "good" reference build had a flat bluish band too, misread as map). At the bottom, 100lvh (754) is screen minus status bar minus collapsed toolbar, so a 100lvh map ended 57-59pt above the screen in every state, and a drag on the sheet scrolled the short page to its end (98pt band) because Safari never collapses its toolbar on that page. Follow-on polish: Safari's own soft pocket blur covers only the top ~48pt and ends in steps (a seam); a dark-theme frost tint gave a pale-to-dark gradient; Safari keeps its pocket's look from the page's last scroll, which happened under the dark opening splash; and the frost layer (stacked above the search field) reached 36px into the field.
- **Fix:** Safari tab on a phone only (`navigator.standalone === false`, class `place-lead` from place-map.js): 80px of map lead above the page with the page opening scrolled past it, an 80px tail below (container and map = lead + 100lvh + tail), `overflow: hidden` on `<html>` so a drag cannot scroll the page, and a settle-back to the lead from either side (keyboard reveal, rotation). The app bar's `::before` is one frosted layer (8px backdrop blur, eased mask) from the top of the lead to the search field's top edge (bar + 12px), drawn with the light palette's tokens in both themes (also on the brand and the frame button). 400ms after the opening splash has gone, the page nudges its scroll by 1px for two frames so Safari re-samples its pocket from the map. Home Screen app and wide screens keep the previous rules (fixed ground strip, plain fade, no lead or tail).
- **Files changed:** companion/static/place-map.js, companion/static/style-place.css, companion/test_browser_place_document_map.py, companion/testdata/render_baseline.json, .planning/workstreams/v1-2/phases/61-companion-ux-and-ui-overhaul-admin-and-users/61-UI-SPEC.md
- **Transferable lesson:** Re-run the "good reference" build before trusting it: the build the ledger recorded as having the map under the status bar showed a flat band in the same simulator, and three plans had chased its `position: fixed` premise. For any iOS edge-to-edge question in a Safari tab, measure the obscured insets (innerHeight vs 100lvh vs screen) and read what WebKit does with fixed boxes there before writing CSS; content under Safari's chrome is document content scrolled there, not a fixed layer. Also measure every toolbar state and the post-drag state, not just "no change against HEAD": cycle 1 called a pre-existing bottom band "identical", which only proved no regression. And when a decorative layer is stacked above interactive controls (header z-index over the floating search field), assert in a test that the control's pixels are unchanged with and without the layer.
