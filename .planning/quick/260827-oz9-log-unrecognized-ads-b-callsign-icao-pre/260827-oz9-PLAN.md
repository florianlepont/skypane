<design_decisions>
**These are settled. Implement them; do not re-derive an alternative shape.**

- **QT-oz9-D-01 — the record lives in `poll_state.json`, not a new side-file.** That file is already created, already atomically written via tmp-write-then-`os.replace()`, already deployed to `${SKYPANE_STATE_DIR}` by `deploy/provision.sh`, already survives restarts, and already holds a bounded accumulator (`enrichment_cache`, capped at 300 entries by `trim_cache()`). A second state file would need its own atomic write, its own corruption tolerance, its own provisioning line, and its own place in the runbook, for zero benefit. Registry key: `unresolved_prefixes`.

- **QT-oz9-D-02 — keyed on the 3-letter ICAO prefix, not the full callsign.** Prefix-level is what a coverage gap actually is, and it is what bounds cardinality: at most 26³ possible keys by construction, versus unbounded distinct callsigns.

- **QT-oz9-D-03 — an entry is recorded only when the callsign passes `_AIRLINE_PREFIX_SHAPE_RE` and `airline_from_callsign()` returns None.** Both halves matter. A `"miss"` from `resolve_route()` covers two very different situations: a real carrier this project cannot name (worth recording), and a missing, empty, malformed, or hostile callsign field (worth nothing, and actively harmful in a bounded store). Only the first is recorded.

- **QT-oz9-D-04 — eviction is lowest `count`, then oldest `last_seen`, then lexicographically smallest prefix.** Deliberately *not* `trim_cache()`'s insertion-order eviction: the oldest entry here is the longest-standing coverage gap, the single most valuable row in the file. A recurring prefix must outrank any number of one-off arrivals. The three-level ordering makes eviction a deterministic total order, matching `select_runway3_aircraft()`'s house style.

- **QT-oz9-D-05 — `example_callsign` tracks the most recent sighting**, so it always pairs with `last_seen` and is a callsign a developer can curl against adsbdb *now*. It is truncated to a fixed maximum length. A future reader must not "fix" it to first-seen — the first-seen timestamp is retained separately and is what carries the historical signal.

- **QT-oz9-D-06 — `count` counts poll cycles, not distinct flights.** One aircraft held on the runway across ten cycles reads as ten. This is an accepted simplification (deduplicating by hex would need per-prefix hex history, which is unbounded state for a marginal gain), but it must be stated wherever the number is presented, or a reader will overstate a carrier's real presence.

- **QT-oz9-D-07 — one new field on the existing single log line**, extending the precedent quick task `260827-itz` set when it added `corroborated=` the same way. No second `print`, no logging module, no new stream.

- **QT-oz9-D-08 — documentation split.** The *mechanism* (what the registry is, where it lives, what bounds it, what its numbers mean) goes in `ARCHITECTURE.md`'s Enrichment section, next to the adsbdb cache it sits beside. <ground_truth_corrections>
Four things where the obvious assumption is wrong:

1. **`server/test_poll_loop.py` makes live network calls today.** Its five existing checks call `run_once()`, which calls `enrich.resolve_route(flight.get("callsign"), cache)` with no transport argument, which reaches `default_transport` and hence `requests.get("https://api.adsbdb.com/...")` for callsigns `FLIGHT1`–`FLIGHT4`. They pass either way (a 404 and a connection error both degrade to a cached miss), which is why nobody noticed. Your new checks must not inherit that fragility — stub `enrich.default_transport` in a try/finally. Do not attempt to fix the existing five checks; that is out of scope.

2. **A side effect on those existing five checks is expected and correct.** `FLIGHT1`–`FLIGHT4` are shape-valid callsigns whose prefix `FLI` is absent from the table, so after this change they will populate the registry during the harness run. That is the feature working. Their assertions are about `last_flight`/`previous_flight` and are unaffected. Do not rename them to dodge the recorder, and do not add an opt-out flag to `run_once()`.

3. **README's stated check total is currently ACCURATE, not stale.** The nine harnesses sum to exactly 203, and README says 203. The precedent task `260827-itz` faced a stale number for an unrelated merge reason; you do not. Recompute the sum from the files anyway (the command is in Task 3's verify) — but expect the delta to be exactly the checks this plan adds.

4. **`resolve_route()` returning `"miss"` for a callsign whose prefix IS in the table is impossible.** If the prefix resolves, `airline_from_callsign()` returns a name and the source is `"airline_only"`, never `"miss"`. So "miss plus shape-valid callsign" is exactly equivalent to "unrecognized prefix" — this is why no new resolution logic is required. Task 1's full-table check pins that equivalence so it cannot quietly stop being true.
</ground_truth_corrections>
