Radius and ceiling
- server/detection.py: `POSITION_ALT_CEILING_FT = 10000` (line 74), `RADIUS_KM_MIN = 4` (75), used by `validate_position` (~217), the apply path (~448), `_position_doc` (`"alt_ceiling_ft": POSITION_ALT_CEILING_FT`, ~260), and the `km_to_nm` docstring ("2.16 to 15.12 NM").
- server/plane/detect.py `position_candidates` (~592-619) does `float(geofence["alt_ceiling_ft"])` and filters `_MIN_AIRBORNE_ALT_FT (-1500) <= alt <= ceiling`. `filter_in_geofence` (line 449) also reads the key but is only reached for runway docs (`runway_candidates` dispatches position docs to `position_candidates` first). Runway docs keep their ceilings (legacy `LEGACY_ORLY_ALT_CEILING_FT = 3000`, `ALT_CEILING_FT = 3000`).
- Plan for the ceiling: the position doc keeps the `alt_ceiling_ft` key with value `None`; `position_candidates` treats a missing/None ceiling as "no upper bound" and keeps the lower bound and `_airborne_altitude_ft` rejections (on_ground, bool, string 'ground', None, NaN/inf).
- Zone: `fleet_zones.Zone` only requires radius > 0, so 2 km -> `km_to_nm(2)` = round(2/1.852, 2) = 1.08 NM (= 2.0002 km) is valid. 28 km -> 15.12 NM unchanged. Providers receive `dist=1.08`.
- Rounding soundness at 2 km: the centre is rounded to 2 decimals (`round_coordinate`, single choke point `position_zone`; not changed). Worst-case offset between true and rounded centre = 0.005 deg lat (0.56 km) combined with 0.005 deg lon (0.39 km at 45 N, 0.37 km at 48.9 N) = about 0.68 km, so up to about 0.7 km. Consequence at 2 km: an aircraft directly over the true location is always inside the circle (offset 0.7 < 2), the guaranteed-covered disc around the true location has radius about 1.3 km and the circle can reach about 2.7 km on the far side. Acceptable; the page's existing ROUNDING_NOTE ("rounded to about 1 km") stays true. Document this in the D-29 line and in a code comment next to `RADIUS_KM_MIN`.
