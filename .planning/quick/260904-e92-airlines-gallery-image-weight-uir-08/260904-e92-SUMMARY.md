# Quick Task 260904-e92: Halve the Airlines Gallery's Image Weight Summary

**Halved the Airlines gallery's server-side illustration normalization frame from 900x263 to 450x132 (DP-1, developer-chosen), cutting the 27-card gallery's download weight from 3.92MB to 1.20MB, with a new harness byte-ceiling regression check and real-browser verification across 4 breakpoint/theme combinations.**

## DP-1, restated as resolved

The developer resolved this plan's original blocking `checkpoint:decision` before dispatch, choosing **option-a: target width 450** (the audit's own recommended number) over option-b (a srcset multi-size mechanism, rejected as premature abstraction, DP-3). The accepted desktop-lightbox consequence — the enlarged click-to-view illustration shrinks from ~852px to ~402px predicted, **~400px measured** — was on the table when that choice was made and is not a defect.

## Performance

- **Duration:** ~25 min

## Before/After Normalized Byte Figures

Measured with `server/.venv/bin/python3` against the real vendored files, over the 27 gallery-visible airline illustrations (`illustrations.target_airline_names()`):

| Target | min | mean | max | Gallery total (27 cards) | vs baseline |
|---|---|---|---|---|---|
| 900x263 (before) | 132.5 KB | 148.8 KB | 175.5 KB | 3.92 MB | 100% |
| 450x132 (after) | 40.8 KB | 45.6 KB | 53.1 KB | 1.20 MB | 31% |

Both rows reproduce the plan's own plan-time measurements exactly. A new harness check (`_all_43_normalized_outputs_serve_well_under_the_byte_ceiling`, 64KB ceiling) guards against a silent revert: the old measured minimum (132.5KB) is more than double the new ceiling, so a dimensions-only revert would fail it loudly.

## Before/After Worst Centring Drift

Measured across all 43 vendored files under `server/assets/icons/illustrations/` (read-only), via `panel_render._opaque_bbox()` on the normalized output:

| Target | worst drift x | worst drift y |
|---|---|---|
| 900x263 (before) | 1.00px (air-algerie.png) | 0.50px (iberia-airlines.png) |
| 450x132 (after) | 1.00px (wizz-air.png) | 1.00px (air-caraibes.png) |

Both rows reproduce the plan's own predicted numbers exactly. **Zero-margin note:** at 450x132 the y-axis worst-case drift sits exactly at the existing check's 1.0px tolerance edge — not over it, so the `_all_43_normalized_outputs_are_centred_and_unclipped` check still passes, but there is no headroom left on that axis. This is a fact for the developer to be aware of, not a defect: a 1px offset inside a 132px-tall frame is visually imperceptible, and the tolerance itself was not loosened to make this pass.

## 4-Run Browser Measurement Table

**Method:** cached Playwright Chromium (`~/Library/Caches/ms-playwright/chromium-1228`), launched with the legacy `--headless` flag (never `--headless=new`) plus `--remote-debugging-port`, driven over raw CDP via a hand-rolled minimal WebSocket client (no external deps). Authentication was a real server-side `POST /login` (via `http.client`), with the issued `sp_session` cookie handed to the page target via CDP `Network.setCookie` — never a UI-driven login. Ran against a fresh companion instance on a scratch state dir under the session scratchpad, stopped cleanly afterward. `Page.captureScreenshot` was not attempted (documented hang in this sandbox); every assertion below went through `Runtime.evaluate` / `getBoundingClientRect` instead. Theme was confirmed genuinely applied per run via `getComputedStyle(document.body).backgroundColor` (`rgb(247, 244, 239)` light / `rgb(12, 15, 20)` dark, matching `--color-canvas` in both themes).

All 4 runs pass the plan's checklist: `naturalWidth`/`naturalHeight` equal 450x132 on all 27 cards (proving the served bytes are the new size end to end, through the real route); zero upscaled cards (rendered width never exceeds natural width); zero aspect-ratio mismatches; the lightbox opens with a non-empty `.lightbox__image` src in every run.

**Desktop measured enlarged width (~400px) matches the plan's ~402px prediction closely** (224px card -> ~1.8x enlargement, down from the pre-change ~3.8x, exactly as DP-1 accepted). **Mobile's "enlarged > card" column reads "no" by design, not by defect:** `.lightbox`'s own base width formula (`calc(100% - var(--space-lg) * 2)`, ~327px at a 375px viewport) plus the dialog's own `--space-lg` padding on each side already constrained the enlarged image to ~277px — narrower than the 309px rendered card — architecturally independent of whether `.lightbox--wide`'s max-width is 900px or 450px, since both values are larger than the ~327px the base formula ever allows on mobile. This reproduces the RESOLVED DECISION block's own prediction verbatim ("On mobile: zero change... the enlarged image renders at the same size before and after") and is not a new finding introduced by this task.
