<objective>
Add an OFF-by-default server-side experiment that separates the frame's check
interval from its redraw interval: the frame wakes every `check_interval_s`
(floor 60 s) while the poll cycle replaces the normal flight image at most once
per saved `wake_interval_s` (N), so the firmware's hash-skip leaves the panel
alone in between. Self-expiring (hard max 72 h), ignored at or below 3700 mV.

Purpose: let the owner measure a "check every minute, redraw every 15 minutes"
cadence on the wall without touching firmware, with zero change to served bytes
when the experiment is off.
Output: `server/check_interval.py` (shared logic + CLI), wiring in
`stub-server/byos_server.py` and `server/poll_cycle.py`, three behaviour test
files, a README runbook entry, one commit, and PR text.
</objective>

## Design decisions fixed by this plan (and the ambiguities they resolve)

Storage: a sidecar file `<device state dir>/check_interval_experiment.json`
holding `{"check_interval_s": int, "expires_at": float epoch}`, NOT a new key in
device_config.json. Reason: `device_config.load_device_config()` returns only
its thirteen registry keys and `save_device_config()` rewrites the file from
that dict, so an extra key would be silently dropped by the next companion save,
and adding a fourteenth key changes the loader's contract that config-history
and companion tests pin. The sidecar lives in the same per-device state dir that
`read_wake_interval_s()` and `load_device_config()` read (live frame: the root
state dir; fleet frames: `devices/<id>`), so it reuses the per-device mechanism
and N is read through the existing readers. When the file is absent, nothing
anywhere changes.

Exposure: a CLI, `python3 -m server.check_interval`, not the companion Advanced
page. A companion control would need a form, a POST handler, FR+EN strings,
validation and a browser test; that is not a small change. The CLI is
documented in server/README.md and tested.

Ambiguities in "N = wake_interval_s", each resolved here (list them again in the
PR text):
- A1. wake_interval_s unset in device_config.json: byos then falls back to
  `--sleep` and the companion/poll side to SKYPANE_SLEEP_S (deployed 30 s). That
  fallback is not a redraw period the owner chose, so the experiment is
  INACTIVE unless device_config.json holds a valid wake_interval_s (read via
  `read_wake_interval_s(state_dir, None)` in byos and `device_cfg["wake_interval_s"]`
  in poll_cycle; both give the same value or None).
- A2. check_interval_s >= wake_interval_s: no separation to make; INACTIVE.
  The CLI refuses to set it; the reader also treats it as inactive because N can
  change after the experiment is set.
- A3. battery_critical / display_off / quiet hours: the experiment only replaces
  the base value; those overrides keep their effect and order (they win).
  `server.wake.effective_wake_interval_s()` (companion "next wake", device-tile
  staleness, the wake_epochs history row) is NOT changed and keeps reporting
  wake_interval_s while the experiment runs - flag this in the PR (the history
  row records N, not the actual 60 s cadence).
- A4. "Last battery reading": byos uses this request's X-Battery-Mv when valid,
  else `state_store.load_battery_state()`; poll_cycle uses ctx.battery_mv
  (battery_state.json, which byos writes from the same header). A missing
  reading counts as "unknown" and the experiment is IGNORED (fail-safe to the
  normal cadence). Exactly 3700 mV is ignored (at or below).
- A5. Which panel changes are spaced: only the flight path - bootstrap
  promotion (empty screen to first flight), queue advance to a new aircraft, and
  the refreshed re-render of the same aircraft. NOT spaced, still immediate:
  every run_hold_cycle() screen (battery empty, display off, quiet hours entry),
  the hold-exit repaint and the source-fault / battery-low badge transition
  repaints inside _render_held(), the no-location (setup) screen
  (run_no_location_cycle) and _render_empty(). Only a flight-path panel change
  stamps the redraw clock; a forced repaint does not reset it.
- A6. While spacing blocks, distinct aircraft still enqueue and still expire
  after MAX_STALENESS_S (150 s). At the next due cycle the panel shows a fresh
  queued aircraft (detected within the last 150 s) or a newly detected one;
  if none is fresh, the old flight stays until the next detection. Expected and
  acceptable for the experiment; state it in the PR.
- A7. Clock stepped backwards (now < last redraw): treated as due, same rule as
  advance_is_due().
