<objective>
The developer tested the deployed quick task 260921-n2n ("Lot A") Task 1 fix on real Safari and reported the contact-autofill dropdown ("09 51 90 38 96 – domicile" / "06 15 82 72 84 – iPhone") STILL appears on the filter field. Lot A added `autocomplete="off" spellcheck="false" autocapitalize="characters"` to all three filter inputs but never touched their `id`, and a documented WebKit quirk is keyed on the `id`: when a text input's `name` — or, in its absence, its `id` — contains a hyphen, Safari renders a contacts icon in the field and offers phone numbers from the user's own Contacts card, **ignoring `autocomplete="off"` in exactly this case**. All three of this app's filter inputs have hyphenated ids and no `name`, which is precisely the shape the two independent sources found during the orchestrator's investigation describe.

Purpose: remove the actual trigger. Lot A treated the symptom's documented remedy (`autocomplete="off"`), which Safari disregards for this specific field shape; this task removes the input characteristic the heuristic fires on. Lot A's attributes stay — they remain necessary for every engine and every case where the hyphen is not the (sole) trigger.

Output: three hyphen-free filter-input id values, one retargeted test literal, and one new standing invariant check that makes "no filter-input id contains a hyphen" a machine-enforced property of the whole app rather than three values somebody has to remember.

Two things this task deliberately does NOT do, both settled during the orchestrator's investigation and not to be relitigated by the executor:

- **It does not rename any other id.** This codebase's id convention is hyphen-case everywhere (`calendar-connect-url`, `frame-strip-heading`, `notifications-topic-url`, `home-day-band`, dozens more). None of those has been reported showing this behaviour, and none is a `type="search"` field with no `name` — the one shape the sources describe. An app-wide rename is out of scope and unjustified by the evidence.
- **It does not attempt a Chrome fix.** The developer also reported (unconfirmed root cause) that Chrome offers to save a password for the same field. The filter bar is not inside any `<form>` (it renders as `<div class="filter-bar">`) and no `type="password"` field exists on any of these pages, so no mechanism connecting a single code change to that symptom could be identified; Chromium documents that its password-manager heuristic deliberately ignores `autocomplete="off"` by design. The Chrome symptom is reported to the developer as still open, needing a live repro, not guessed at here.

One open question is recorded but explicitly NOT acted on: the two filter labels that showed the defect both contain the French word "indicatif" (which can also mean "phone dialling code"), while Health's label ("Filtrer par préfixe") does not and was not reported — suggestive, but unconfirmed (the developer may simply not have tested Health). "Indicatif" is this app's established, correct French translation of "callsign" and must not be changed to dodge a browser heuristic. **Do not touch `companion/i18n_fr/*` or any copy constant in this task.**
