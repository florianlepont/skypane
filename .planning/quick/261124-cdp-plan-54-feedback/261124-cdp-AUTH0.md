# Auth0 invitation link not created: investigation (read-only)

Symptom: after "Inviter un utilisateur" the Users page shows "Lien d'invitation non créé"
(`admin_users.invitation_not_created`). The person is invited locally; no Auth0 link exists.

No production config, env file or Auth0 setting was touched or read. Everything below comes from
`companion/auth0_management.py`, `companion/console_users.py`, `companion/pages/users_page.py` and
`deploy/README.md`.

## Code path

`POST` invite -> `console_users.handle_invite` -> local `fleet_db.add_user` (committed) ->
`console_users._send_invitation` -> `auth0_management.create_invitation(os.environ, email,
_app_url(h), ttl)`. `ttl` is 5 days for a first invitation, 24 h for "Send a new invitation".

`_app_url(h)` is `https://<Host header>` (http only for loopback); `""` when the Host header does not
match `_HOST_RE`.

## Exact requests made (in order, all `POST`, JSON, no redirects, TLS verified)

Base URL is `https://$SKYPANE_AUTH0_DOMAIN` (the same variable as the sign-in domain).

1. `POST https://$DOMAIN/oauth/token`
   `{"grant_type":"client_credentials","client_id":$MGMT_CLIENT_ID,"client_secret":$MGMT_CLIENT_SECRET,"audience":"https://$DOMAIN/api/v2/"}`
   Expected 200 with `access_token`. Failure reason: `token_failed` (or `rate_limited` on 429).
2. `POST https://$DOMAIN/api/v2/users` with `Authorization: Bearer <token>`
   `{"email":<lowercased>,"email_verified":false,"connection":$SKYPANE_AUTH0_DB_CONNECTION,"password":<random 32 bytes>,"verify_email":false}`
   Expected 201 with `user_id`. 409 means the user exists (go to step 3b). Other status: `create_failed`.
3. a. new user: `POST https://$DOMAIN/api/v2/tickets/password-change`
      `{"user_id":<id>,"result_url":<app url>,"ttl_sec":<ttl>,"mark_email_as_verified":true}`
   b. existing user (409): same endpoint with `{"email":<email>,"connection_id":$SKYPANE_AUTH0_DB_CONNECTION_ID,...}`;
      needs `SKYPANE_AUTH0_DB_CONNECTION_ID` of the form `con_` + 16 alphanumerics, else
      `user_exists_connection_id_missing` / `connection_id_invalid`.
   Expected 201 with `ticket`. Status other than 201: `ticket_failed`. A 201 whose `ticket` host is
   neither `$DOMAIN` nor `$SKYPANE_AUTH0_CUSTOM_DOMAIN` (or is not https): `ticket_url_rejected`.

## Which setting is most likely missing

The French title is shown for every failure; only `not_configured`, the two connection-id reasons and
`rate_limited` get their own sentence. Everything else (all the cases below) falls into the generic
"Le service de connexion n'a pas accepté la demande ... vérifiez les réglages Auth0 du serveur".
`FAIL_NOT_SET_UP` ("pas configurées") was not what the owner reported, so the four required variables
(`SKYPANE_AUTH0_DOMAIN`, `..._MGMT_CLIENT_ID`, `..._MGMT_CLIENT_SECRET`, `..._DB_CONNECTION`) are all
set. The failure is therefore after configuration, in one of these, most likely first:

1. **`SKYPANE_AUTH0_CUSTOM_DOMAIN` missing (`ticket_url_rejected`).** If the tenant uses a custom
   domain, Auth0 returns a ticket URL on the custom domain while `$DOMAIN` is the canonical
   `*.eu.auth0.com`; `_ticket_url_ok` then refuses to show it, by design. The user is created
   (step 2 succeeded), which is why a retry afterwards takes the "user already exists" branch.
   Fix: set `SKYPANE_AUTH0_CUSTOM_DOMAIN=<custom domain>` and restart `skypane-companion`.
2. **Management API permissions (`create_failed` or `ticket_failed`, HTTP 403).** The machine-to-machine
   application must be authorised on the Auth0 Management API with exactly `create:users` and
   `create:user_tickets`. A missing `create:user_tickets` gives step 3 a 403 after step 2 worked (user
   created, no link); a missing `create:users` fails at step 2.
3. **Wrong database connection name (`create_failed`, HTTP 400/404).** `SKYPANE_AUTH0_DB_CONNECTION`
   must be the exact name of the Database connection (Authentication > Database), and that connection
   must be enabled for the application.
4. **`$DOMAIN` is a custom domain (`token_failed`).** The Management API audience is the canonical
   tenant URL; requesting a token for `https://<custom>/api/v2/` against the custom domain is refused.
   `SKYPANE_AUTH0_DOMAIN` should be the canonical tenant domain for the Management calls.
5. **Empty `result_url` (`bad_result_url`).** `_app_url` returns `""` if the `Host` header seen by the
   companion is not a plain host name (for example when the reverse proxy rewrites it). Unlikely behind
   Caddy with the default config, but it fails before any Auth0 call is made.

For an existing Auth0 account ("Send a new invitation"), the 409 branch also needs
`SKYPANE_AUTH0_DB_CONNECTION_ID`; that case has its own message, so it is not what was reported.

## How to confirm without changing anything

The exact reason is already recorded: the audit row for `user.invitation` with outcome `failed` has
`detail.reason` set to one of the codes above (see `_send_invitation`). Open the Audit page (or read the
audit table) for that row; the code tells which of items 1 to 5 applies. No secret ever appears in it.

## Suggested follow-up (not done here)

Surface the reason code in the admin message (it is already safe to show: short codes only), so an
administrator does not need the audit page to tell a permission problem from a custom-domain problem.
