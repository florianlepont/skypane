<objective>
Flashing this board today gives no feedback. Power it up and it is indistinguishable from
a brick until either the console prints or, half a minute later, the panel redraws. The
developer named this directly while flashing for the 05-03 battery-ADC checkpoint: it is
unclear whether anything is actually happening.

The fix costs no hardware. The XIAO ESP32-S3 module carries a built-in "User LED" —
distinct from the charge-status LED — on **GPIO21**, active-low, and GPIO21 appears nowhere
in this project's claimed-pin list (SCK=7, MOSI=9, CS_M=44, CS_S=41, DC=10, RST=38, BUSY=4,
EN=43, KEY0=5, KEY1=3, KEY2=2, BATTERY_ADC=1, BATTERY_ADC_EN=6). Driving it costs one small
module and two call sites.

**The one real design constraint is power, and it is a hard requirement.** An LED draws
single-digit-to-tens of mA. This device's deep-sleep budget is tens of µA. Left lit through
sleep, the LED would plausibly cut battery life by an order of magnitude and directly
undermine DEVICE-05 — the phase currently in flight. Left lit only during the active wake
window, next to a Wi-Fi radio and a panel refresh that already dominate that window, its
cost is close to free. So the LED must be strictly scoped to the wake window, and the plan
treats "off before sleep on every path" as the load-bearing property, not as a detail.

The structure of `app_main.c` makes that cheap to guarantee rather than merely intend.
`enter_deep_sleep()` is marked `noreturn` and is the only exit — the failure/backoff branch,
the deferred-draw branch and the healthy branch all funnel through it, and the file's own
head comment records that as an invariant ("there is no path out of app_main that does not
enter it, because a device that stays awake on an unexpected path is a flat battery"). One
call inside that function covers every path there is. Task 2's acceptance check reads the
function body mechanically and asserts the last two statements are the LED-off call followed
by the sleep call, so the invariant is enforced rather than reviewed.

**GPIO21's identity is a claim, not a measurement.** It comes from web aggregation of Seeed
community and board-reference sources, not from an official schematic — unlike the panel
pins, which came from a vendor header. That is the same confidence posture the battery-sense
pins started from, and it gets the same cheap resolution: flash and look. If an LED lights
during the wake window and goes dark in sleep, the claim holds. If nothing lights, the
firmware is harmless — GPIO21 is unclaimed, so at worst an unconnected pad toggles once per
wake — and the pin can be re-sourced later. If the LED is dark while awake and lit while
asleep, polarity is inverted, which is the one outcome that actually costs battery; that is
why the polarity is a config bool rather than a hardcoded ternary, so the correction is a
reflash and not a code edit. No soldering, no purchase, no risk either way. The developer is
flashing for the 05-03 checkpoint regardless, so this rides along in that same session.

**The toggle's reading half has to ship now; its setting half does not.** The developer's
first instinct was to defer the remote on/off entirely until the companion web interface
(CFG-01..CFG-04) exists, on the reasonable ground that a toggle nobody can set is a
half-built feature. He then reversed that, for a reason that is specific and correct: the
two halves of a toggle do not live in the same place and do not have the same cost to add
later. The *setting* half is server state and a web control — changeable any afternoon, on
a machine you can redeploy in seconds. The *reading* half is firmware — it lives on a board
that has to be physically connected and reflashed to change. Shipping the LED without the
firmware knowing how to read a `led_enabled` field therefore does not defer the cost; it
guarantees a reflash later for something that costs a struct member and one branch today.
So the field goes on the wire now, in both directions: `byos_server.py` emits it as a
hardcoded `True`, and the firmware parses it and acts on it. Making it a *real* per-device
setting — NVS, web UI, per-frame state — is explicitly still deferred, and after this task
that work is a server-only change with no firmware impact. That asymmetry is the whole
point.

**The field must never be able to make things worse than not having it.** Two properties
carry that. First, `led_enabled` is optional in the parse, not required: absent, null or
wrong-typed all resolve to enabled, and none of them can reject the display response the
way a bad `image_url` or `sleep_s` rightly does. A server that predates this change, or a
future server bug, must degrade to "the LED behaves as it always did" — not to a rejected
poll and an exponential backoff, which would trade a cosmetic feature for the device's
actual function. Second, the field gates exactly one thing: whether the LED *stays* lit
through the active window. It does not gate the boot-time on (which fires before any
network exists and cannot depend on an answer that has not arrived), and it emphatically
does not gate the off-before-sleep call, which stays unconditional at the single exit. The
worst a hostile or broken server can do with this field is turn a debug LED off.

Purpose: turn every future flash and power-cycle into a visible event, without spending a
microamp of the sleep budget this phase exists to protect — and put the toggle's
firmware-side half on the board now, so the web-side half never costs a reflash.
Output: a two-function `fp_led` module, two unconditional call sites in the wake dispatcher,
a `led_enabled` field carried end-to-end from the stub server through the display parse to
one conditional off-early call, a pinned and provenance-annotated board-profile entry, and a
bring-up log section written before the board is flashed rather than after.

## What this plan explicitly does NOT do

Recorded because the developer drew these lines himself, and because the seed file this task
came from contains a second, larger idea that must not leak in. Note the first two entries
are where the line actually falls now — an earlier revision of this plan drew it one step
further back, excluding the protocol field too, and the developer reversed that specifically
to avoid a future reflash (see the objective's third paragraph):

- **No NVS-backed setting.** `nvs_schema.h` stays at exactly its four keys. The `led_enabled`
  value is read from each poll response and used within that wake only; nothing about it is
  persisted, so there is no key, no migration and no default to reconcile.
- **No real server-side configuration.** `byos_server.py` returns a hardcoded constant. There
  is no per-device state, no store, no endpoint to set it, and no web control — those wait for
  the companion interface (CFG-01..CFG-04). What ships here is the wire field and the
  firmware's ability to read it, precisely so that the deferred work is server-only.
- **No change to `server/`.** The production server is untouched; only the stub server, which
  is what the firmware is developed and tested against, learns the new field.
- **No change to `api_base.c`, `wifi.c` or the request/telemetry-header path.** The addition is
  one optional response field and its consumer, not a protocol version bump.
- **No blink pattern, no fault-conditional lighting, no error codes in flashes.** The seed
  lists those as undecided alternatives; this task takes the simplest one — lit for the whole
  active window unless the server says otherwise — because it is the one that is free and the
  one that answers the actual question ("is anything happening?").
- **No change to the frozen Log Line Contract.** No new, removed or reworded log line in
  `app_main.c` or `state_machine.c`.
