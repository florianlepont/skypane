<objective>
Flashing this board today gives no feedback. Power it up and it is indistinguishable from
a brick until either the console prints or, half a minute later, the panel redraws. The
developer named this directly while flashing for the 05-03 battery-ADC checkpoint: it is
unclear whether anything is actually happening.

The fix costs no hardware. The XIAO ESP32-S3 module carries a built-in "User LED" —
distinct from the charge-status LED — on **GPIO21**, active-low, and GPIO21 appears nowhere
in this project's claimed-pin list (SCK=7, MOSI=9, CS_M=44, CS_S=41, DC=10, RST=38, BUSY=4,
EN=43, KEY0=5, KEY1=3, KEY2=2, BATTERY_ADC=1, BATTERY_ADC_EN=6). Driving it costs one small
module and two call sites.

**The one real design constraint is power, and it is a hard requirement.** An LED draws
single-digit-to-tens of mA. This device's deep-sleep budget is tens of µA. Left lit through
sleep, the LED would plausibly cut battery life by an order of magnitude and directly
undermine DEVICE-05 — the phase currently in flight. Left lit only during the active wake
window, next to a Wi-Fi radio and a panel refresh that already dominate that window, its
cost is close to free. So the LED must be strictly scoped to the wake window, and the plan
treats "off before sleep on every path" as the load-bearing property, not as a detail.

The structure of `app_main.c` makes that cheap to guarantee rather than merely intend.
`enter_deep_sleep()` is marked `noreturn` and is the only exit — the failure/backoff branch,
the deferred-draw branch and the healthy branch all funnel through it, and the file's own
head comment records that as an invariant ("there is no path out of app_main that does not
enter it, because a device that stays awake on an unexpected path is a flat battery"). One
call inside that function covers every path there is. Task 2's acceptance check reads the
function body mechanically and asserts the last two statements are the LED-off call followed
by the sleep call, so the invariant is enforced rather than reviewed.

**GPIO21's identity is a claim, not a measurement.** It comes from web aggregation of Seeed
community and board-reference sources, not from an official schematic — unlike the panel
pins, which came from a vendor header. That is the same confidence posture the battery-sense
pins started from, and it gets the same cheap resolution: flash and look. If an LED lights
during the wake window and goes dark in sleep, the claim holds. If nothing lights, the
firmware is harmless — GPIO21 is unclaimed, so at worst an unconnected pad toggles once per
wake — and the pin can be re-sourced later. If the LED is dark while awake and lit while
asleep, polarity is inverted, which is the one outcome that actually costs battery; that is
why the polarity is a config bool rather than a hardcoded ternary, so the correction is a
reflash and not a code edit. No soldering, no purchase, no risk either way. The developer is
flashing for the 05-03 checkpoint regardless, so this rides along in that same session.

Purpose: turn every future flash and power-cycle into a visible event, without spending a
microamp of the sleep budget this phase exists to protect.
Output: a two-function `fp_led` module, two call sites in the wake dispatcher, a pinned and
provenance-annotated board-profile entry, and a bring-up log section written before the
board is flashed rather than after.
</objective>

## What this plan explicitly does NOT do

Recorded because the developer drew these lines himself, and because the seed file this task
came from contains a second, larger idea that must not leak in:

- **No protocol field.** No `led_enabled` in the `/display` response, no change to
  `api_client.c`, `state_machine.c` or `api_base.c`.
- **No NVS-backed setting.** `nvs_schema.h` stays at exactly its four keys.
- **No server-side or stub-server change.** Not one file under `server/` or `stub-server/`.
- **No remote toggle mechanism of any kind.** The web side waits for the companion interface
  (CFG-01..CFG-04) to exist. Building a toggle with no way to set it is the specific outcome
  the developer said he wants to avoid.
- **No blink pattern, no fault-conditional lighting, no error codes in flashes.** The seed
  lists those as undecided alternatives; this task takes the simplest one — lit for the whole
  active window — because it is the one that is free and the one that answers the actual
  question ("is anything happening?").
- **No change to the frozen Log Line Contract.** No new, removed or reworded log line in
  `app_main.c`.
