<objective>
When the battery is nearly flat, the frame should show a deliberate "BATTERY EMPTY" screen instead of freezing mid-refresh. That freeze is what happened on the 2026-09-14 depletion run: the device died at about 2946 mV during a transition.

All of this is server-side, per the user's decision. poll_loop latches a critical state from the X-Battery-Mv reading the device already sends and renders the new screen once. byos then pins the device to an hourly check-in, and every check-in sees an unchanged image hash, so the panel never refreshes again until the pack is recharged. The firmware isn't touched, flashed or deployed.

Output: the new hold screen and its glyph, the poll_loop latch and hold kind, a critical-aware wake-interval mirror, the byos sleep pin, tests in the existing harnesses, docs, a single-screen preview PNG, and a side-by-side preview (DISPLAY OFF, QUIET HOURS, BATTERY EMPTY).
</objective>

## Concrete issues found in the code (why the plan goes beyond the four files the design names)

1. **The monitoring mirror has to learn the pin, or the pin causes false alerts.** `server/wake.py`'s `effective_wake_interval_s(device_cfg)` mirrors byos's sleep_s chain, and several things read it: poll_loop's `_notify_silence_transition` (`wake.device_staleness_thresholds(...)`: warn at 3 missed wakes, floor 300 s), poll_loop's per-cycle wake-epoch history, and the companion's frame strip and flash text (`wake.next_wake_status` in companion/layout.py and companion/app.py). If byos alone pins 3600 s, a frame configured at 300 s crosses the 900 s warn threshold every hour while parked. The result is an hourly "The frame has not checked in" / "The frame is back" push pair and a "late" frame strip. So wake.py gets a `battery_critical` flag, and every caller passes the latch.
2. **Recovery has to be anticipated by byos, not only latched.** poll_loop clears the latch up to 30 s *after* the recovering check-in, but that check-in has already been answered. With a plain latch read, byos would hand the recovering device another 3600 s, even though monitoring expects the normal cadence 30 s later. That means one false silent push per recovery, and a resume delay of up to 2 h. Fix: byos skips the pin when the reading in that same request is at or above BATTERY_CRITICAL_RECOVER_MV (a parity-checked copy). poll_loop's latch stays the single source of truth for the *state*; byos only avoids handing out a stale long sleep.
3. **Six existing poll_loop tests use 3000 mV as their "battery low" reading** (`_write_battery_state(..., 3000)` in the b2, cal1, cal4, cal7, d13 and off checks). Once this lands, 3000 mV parks the frame. Move them to 3400: still below the 3500 badge threshold, above the 3300 critical one. Each check keeps its original intent.
4. **`_hold_state()` only recognises the kinds in `_HOLD_KINDS`.** If "battery_empty" isn't added there, a persisted park reads back as "not holding" and the screen re-renders every 30 s.
5. **D-07's hold-branch rule is "render only on entry from the live board", and it has to widen.** Otherwise entering BATTERY EMPTY from an active DISPLAY OFF or QUIET HOURS hold would never draw it, and recovering into one of those holds would leave BATTERY EMPTY on the glass. New rule: render when `was_hold is None`, or when the battery_empty boundary is crossed (`(was_hold == "battery_empty") != (hold_kind == "battery_empty")`). Moves between quiet hours and display off stay silent, as D-07 requires.
6. **Data correction.** BATTERY-RUN's table has 3500 mV at about **43 h** before the last reading (2026-09-13 02:04 to 2026-09-14 21:05), 3364 mV at about 21.5 h, and 2960 mV at about 17 min. Cite these figures.

## Decisions taken at planning time (Claude's discretion)

- **Latch semantics** mirror `apply_battery_hysteresis` exactly. `None` returns `was_active` unchanged: an unknown reading can neither enter nor clear the latch. Already active: stays active while `mv < 3700`. Not active: enters at `mv <= 3300`. byos never persists a rejected reading (0, junk), so "rejected" arrives as the last valid reading or as None.
- **Priority** on the display axis is battery_empty, then display_off, then quiet_hours. On the sleep axis the composition is `quiet_hours_sleep_s(battery_critical_sleep_s(display_off_sleep_s(base), ...), ...)`: the critical pin replaces display-off's 300 s, and a longer quiet-hours window can still extend it through the existing max().
- **Constants.** `BATTERY_CRITICAL_SLEEP_S = 3600` originates in `server/device_config.py`, next to `DISPLAY_OFF_SLEEP_S`, and byos keeps a parity-checked copy, following the same precedent. The thresholds live in poll_loop next to `BATTERY_LOW_*`. byos copies only `BATTERY_CRITICAL_RECOVER_MV`, also parity-checked. The latch key lives in wake.py (a leaf module the companion can import); poll_loop writes it through that constant.
- **Fixed pixels.** The BATTERY EMPTY canvas ignores `source_fault`, `battery_low` and theme, so its bytes, and therefore its hash, stay constant for the whole episode. The low badge would be redundant on it anyway.
- **Detection is skipped** while parked: it's a hold, and the hold branch returns before any ADS-B query.
- **Notifications (ntfy): skipped.** The 3500 mV battery-low push already fires about 43 h earlier under the same `battery_low` preference. A separate critical push would need its own dedup latch, a new English and French body in notify.py's `_BODY_FR`, and new checks, which is more than one line. **Companion copy: none.** The screen appears in the companion gallery through the existing `_save_to_gallery`. The only companion change is the monitoring fix in issue 1.
- **Glyph:** an upright hollow battery, 48 x 76 px, with a 20 x 8 px nub centred on top and an 8 px outline (`POWER_ICON_STROKE_PX`). It has the same 76 px height as the crescent and the runway strip, and the same width as the runway strip, the family's other upright glyph. Ink is whatever `ink_idx` `_build_hold_canvas` passes (DIMMED_INK), never hardcoded. The interior is left unpainted so the dithered field shows through; render.py's crescent comment gives the reason. A horizontal battery at the 76 px family height would be about 150 px wide and heavier than the ring and the crescent, so the upright form was chosen.
