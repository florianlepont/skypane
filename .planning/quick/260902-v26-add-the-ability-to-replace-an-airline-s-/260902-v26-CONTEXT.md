<decisions>
## Implementation Decisions

### Scope: the replacement must reach the real physical panel, not just the web preview
`server/plane/illustrations.py`'s selection logic (`select_illustration()`/`illustration_path_for_key()`) is shared between the companion web gallery and the actual e-ink panel compositor (`server/plane/render.py`). An uploaded replacement must be resolved at that shared layer so it affects both — not a companion-app-only cosmetic override the panel renderer never sees.

### Storage: must survive a redeploy — cannot write into the git-tracked source tree
Ground truth already investigated: `ILLUSTRATION_DIR` (`server/assets/icons/illustrations/`) is INSIDE the git-tracked source tree, and `deploy/deploy.sh`'s repeatable-deploy path rsyncs `server/`, `stub-server/`, and `companion/` on every deploy. Writing an uploaded replacement directly into `ILLUSTRATION_DIR` on the live production filesystem would appear to work, then silently revert on the next unrelated deploy. Uploaded replacements must live in a location `deploy.sh` never touches and that survives redeploys — analogous to how `companion/app.py` already takes a `--state-dir` argument (separate from the source tree) for `poll_state.json`/`device_config.json`/`history.db`. The illustration-resolution logic needs to check that override location first, falling back to the vendored `ILLUSTRATION_DIR` when no override exists for a given key. The vendored/curated originals in `server/assets/icons/illustrations/` are never modified or deleted by this feature — they stay the "factory defaults."

### Normalization: uploads go through the same pipeline as vendored illustrations
An uploaded replacement must be processed through the same alpha-threshold/bbox-centering pipeline (`companion/illustration_normalize.py`'s existing logic, already proven against all 43 vendored files) as every other illustration, for visual consistency with the rest of the gallery. Do not special-case uploads to skip normalization.

### Revert-to-original: explicitly deferred, not in scope for this task
No "reset to the original vendored image" UI/capability is being built now. The vendored original stays intact on disk regardless (this task never touches `server/assets/icons/illustrations/`), so reverting is technically always possible later (even manually, by deleting the override file) — but no user-facing "revert" button/flow is part of this task's scope. Do not build one.

### Claude's Discretion
- Exact override-storage layout (e.g. `{state_dir}/illustration_overrides/{key}.png` or similar) — pick something clear and consistent with this project's existing state-dir conventions.
- Upload mechanism: this codebase has NO existing multipart/file-upload precedent (verified by grep — `companion/app.py` has never handled a file upload before). Design the simplest correct approach using only the stdlib (this project's established discipline — no new dependencies), likely parsing `multipart/form-data` by hand or via `email.parser`/`cgi` (check what's actually available and not deprecated in the pinned Python version) rather than reaching for a third-party multipart library.
- Accepted upload formats/validation (PNG only vs. broader image format acceptance auto-converted to PNG; file size limits; dimension sanity checks; rejecting non-image uploads safely).
- Exact UI trigger location on the Airlines page (e.g. from within the click-to-enlarge lightbox added in quick task 260902-tli, from the card itself, or a dedicated control) — check the current card/lightbox markup and pick whatever fits the established page patterns best.
- Whether this fits as a single quick-task plan or needs to split (this task's own planner should make that call, same as illustration-centering's split into panel-side vs. web-gallery-side — this feature has real security/validation surface (untrusted file upload) that may warrant careful, possibly multi-task treatment).

</decisions>
