# Quick Task 260902-v26 Plan 02: Illustration-Replace Upload Route Summary

**POST /illustration/{key}.png — this codebase's first file-upload route: a stdlib-only single-part multipart parser (email.message, no cgi), validate-then-re-encode through Pillow, and an atomic os.replace() into {state_dir}/illustration_overrides/{key}.png, proven live end-to-end over real HTTP against a real running companion/app.py subprocess.**

## Performance

- **Duration:** ~35 min
- **Completed:** 2026-09-02
- **Tasks:** 3/3 completed
- **Files modified:** 3

## Accomplishments
- `parse_single_uploaded_file()` (companion/app.py): a strict, stdlib-only, single-part `multipart/form-data` parser built on `email.message.Message` (not the deprecated/soon-removed `cgi` module). Accepts exactly one file part and rejects everything else; discards the part's header block entirely so a client-declared filename can never influence anything; never raises.
- `POST /illustration/{key}.png` (`Handler._handle_illustration_replace()`): membership-tests the URL key against the same closed 43-member set the GET route uses, bound-reads the body (`_read_upload_body()`, 4 MiB cap, drains an over-cap body so the connection stays healthy), parses it with the new parser, writes the raw payload to a temp file, runs it through the SAME `illustrations.validate_illustration_file()` every vendored asset must pass (>=1200px width, landscape, non-fully-opaque alpha), and only then decodes with Pillow, converts to RGBA, and re-encodes to a second temp file before an atomic `os.replace()` onto the override path. The client's original bytes are never stored.
- `_serve_illustration_image()` now resolves through plan 01's `illustrations.resolved_illustration_path(key, state_dir)`, so an uploaded override is served back immediately on the next GET, through the same `illustration_normalize` pipeline every vendored file goes through. Its stale "never user-supplied image bytes" comment was corrected to explain why decoding an override is still safe.
- Three new flash keys (`illustration_replaced`/`illustration_rejected`/`illustration_replace_failed`) defined in `companion/pages/airlines_page.py`, mirroring `config_page.py`'s own `FLASH_*` ownership pattern, wired into `app.py`'s `FLASH_MESSAGES`/`FLASH_ROLES`. Rejection copy states the real requirements in user terms (transparent PNG, >=1200px wide, landscape) without ever echoing a server path or file content.
- Live-verified end-to-end against a real running `companion/app.py` subprocess (not just source-level reasoning): a real PNG uploaded over real HTTP changes what the GET route serves; the override and a fresh normalization of the same source image are byte-identical (confirmed live — the store-time Pillow RGBA re-encode is lossless for this asset, so the plan's documented fallback path was never needed); the vendored original is hash/size/mtime-identical after upload; `illustrations.select_illustration()` picks up the override via the harness's own `state_dir` — the panel-side effect, asserted against the exact file the real route wrote, not a hand-placed fixture; and every rejection path (non-image, oversized, unknown key, traversal key, unauthenticated) writes nothing.

- Split the parser's own tests from the route's live-HTTP tests exactly as the plan specified (Task 1 in-process, no `Harness`; Task 3 real subprocess) — kept the fast/pure-unit and slow/integration checks in their existing, already-established sections rather than mixing them.

- Confirmed live (not assumed) that the store-time Pillow `convert("RGBA")` + PNG re-encode is lossless for this asset: the D-03 same-pipeline check's primary byte-equality path passed, so the plan's documented fallback (length + signature only) was not exercised. Verified independently with a standalone script reproducing the exact re-encode step before trusting the test's PASS.
- Both upload temp files are written inside the destination's own override directory (never a system tempdir) so the final `os.replace()` is guaranteed same-filesystem and atomic — named from the validated key + this process's pid, never from anything in the request.
