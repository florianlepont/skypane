<objective>
Fix the Runway picker's three hidden native radio inputs on the companion Settings page, which render as real 44x44px boxes instead of the intended 1x1px off-screen boxes, letting some mobile browsers paint a visible native radio dot on top of each runway tile.

The cause is fully diagnosed and confirmed against current source: the site-wide `input, select { min-height: 44px; min-width: 44px }` WCAG 2.5.5 floor clamps `.visually-hidden`'s `width: 1px; height: 1px` back up, because `min-*` is a separate property applied as a floor at layout time rather than a cascade competitor that specificity can settle.

Purpose: the developer sees a stray radio dot on their actual phone. Beyond the cosmetic fix, this closes the third instance of a bug class this stylesheet has already hit twice (`.filter-bar__field input`, `.led-checkbox input[type="checkbox"]`) and records it in the design skill so the fourth instance is caught at review instead of on a phone.

Output: one narrowly scoped CSS rule, one regression check, three design-skill register updates, and live before/after measurements at mobile and desktop widths proving the runway radios shrank and nothing else moved.

Non-goals, stated so they cannot be drifted into:
- The global `input, select` 44px floor is NOT edited, weakened, or scoped. It is a documented decision (style.css ~1190-1204) that must survive byte-identical.
- The `.visually-hidden` utility block itself is NOT edited. It is correct as written for the `<span>` elements that are its majority consumers, and the design skill documents its exact declaration list.
- `companion/pages/config_page.py` is NOT edited at all. The markup is already correct; this is purely a stylesheet gap.
- The Theme radios (`config_page.py:229`) are NOT touched. They carry no utility class and are intentionally plain visible radios.
- No `!important`, no `display: none`/`visibility: hidden` on anything carrying the utility class, no `:has()`.
</objective>
