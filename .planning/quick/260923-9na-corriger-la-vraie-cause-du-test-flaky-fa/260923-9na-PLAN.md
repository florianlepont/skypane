<objective>
Fix the real cause of the long-running `fallback-Save` flake in `companion/test_browser_ux.py`, and pre-empt the identical latent race in the shared `_save_via_bar()` helper.

The race: `with page.expect_navigation(): fallback.click()` starts the navigation timeout the instant the `with` block is entered — before `.click()`'s own actionability polling (visible / stable / receives-events / enabled) has even begun. Under CI load that polling silently eats the SAME budget the navigation-completion wait needs. This is why one check has produced two completely different-looking failures over time from one root cause:

1. `Locator.click: Timeout 30000ms exceeded ... element is not stable ... element was detached from the DOM` — recorded in `.planning/phases/30-aspect-rebuilt-one-tile-three-rows-one-palette-the-calendar-/30-01-SUMMARY.md` line 107, and attributed at the time to "an intermittent arm64-Chromium DOM-detach compositor race".
2. `TimeoutError('Timeout 31ms exceeded ... "domcontentloaded" event fired')` — real CI, run 35818514258 on `main`, 2026-09-23. **31ms is the tell**: the navigation wait was handed 31ms of a 30000ms budget because the click's actionability poll had already consumed 29969ms of it.

Purpose: two additive statements that decouple the two waits, retiring one of the three known pre-existing failures in this suite's flake floor.
Output: one added statement in each of two test files. No production code. No timeout widened. No assertion touched.
</objective>
